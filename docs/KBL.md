# kernel_boot_loader: подтверждённые данные

`kernel_boot_loader.self` (KBL/SKBL) — ARM-загрузчик из SLB2 прошивки 1.04: second loader (CMeP) расшифровывает его в DRAM и запускает на `0x40020000`; KBL поднимает периферию, строит карту памяти, создаёт менеджер объектов ядра и передаёт управление NSKBL. Подтверждено трассой (`--stage kbl`, `runm`), дизассемблером, дампами eMMC/DRAM и вики; отменённые выводы не переносились, при противоречии взята поздняя поправка. Полный образ: 355 220 байт из eMMC SLB2 (`dumps/emmcdump.zip`, `Out/SLB2_dec/`; сборка `build_slb2_container()`/`build_idstorage_image()`).

Карта документации: `docs/BOOT.md`, `docs/STATUS.md`, `docs/NSKBL.md`, `docs/SYSCON.md`.

## 1. Образ и сегменты

| vaddr | размер | что |
|---|---|---|
| `0x40020000` | `0x3BFE0` | код RX, вход `0x40020000` |
| `0x4005C000` | `0x5706C` | `.bss` RW, filesz `0xF0` |
| `0x50000000` | `0x194CF` | второй RX |

* 355 220 байт, `entry = 0x40020000`, слово 0 `0xF10C00C0`, код ARM (не Thumb); ELF-сегмент `vaddr = 0`, 0xC0 байт: 8× `ldr pc,[pc,#0x18]` + указатели, `vector[4] → 0x40020394` (data abort); `paddr == vaddr` у всех трёх (`tools/self_phdrs.py`). `0x40000000` — окно DRAM (до MMU), `0x80000000` — окно модулей ядра; `.bss` = 0 в `0x400211C4` на `[0x40061100,0x400B306C)`.
* PA: `0x00000000`/`0x40000` ARM Boot = алиас `0x1F000000` (`kArmBootWindowSize = 0x40000`); `0x00040000`/`0x20000` MeP boot = зеркало `0x00800000`; `0x00800000`/`0x20000` CMeP 128 КиБ SRAM (second_loader, secure_kernel, Secure Modules); `0x1F000000`/`0x8000` SPAD32K (fallback DIP `+0x80`); `0x1F840000`/`0x20000` SPAD128K; `0x1C000000` 2 МиБ Scratchpad SRAM (`L1[0x1C0] = 0x1C01158E`); `0x1D000000`/`0x1000` `/dev/null` (`L1[0x1D0] = 0x1E0`); `0x40000000`/`0x200000` Secure DRAM (FW ≥ 0.996); `0x40200000` NS Shared DRAM; `0x40000000`/`0x20000000` DRAM 512 МиБ (`kermit::kScuSize`).
* Окна машины из-за KBL: `0x40000000`+128 МиБ (`arm_priv`), `0x50000000`+4 МиБ (`arm_buf`), `0x1A000000` PL310 (`+0x77C` `+0xF60` `+0xF80`), `0x34000000` второй L2, `0xE20A0000` GPIO, `0xE31000C0` `Ernie.SC::events_c0_`; позже `Kermit.UnkE8000`, `Kermit.UnkE20B6`, `Kermit.Null`, `Kermit.Sdif0`, `kScWindowSize = 0x20000`.
* FW 3.60 secure DRAM: `0x40000000` 0xC0 reset vector; `0x40000500` `0x9500` `kprx_auth_sm.self`; `0x40009B00` `0x780` `prog_rvk.srvk`; `0x4001FD00` `0x100` SceKblParam (без magic); `0x40020000` `0x370C8` SKBL seg0; `0x40073570` `0x200` SceKblParam. NSKBL: `0x50000000` сжатый, `0x51000000` распакованный, `0x52000000`+ модули. Стейджинг модели: `kSecondLoaderStagingDram = 0x407C0000`, `kprx_auth_sm` `0x00800500`, `prog_rvk` `0x00809B00` (ранние `0x40780000`/`0x407A0000`/`0x40000500`/`0x40009B00` — устаревшие слои).

## 2. Последовательность загрузки (подтверждено трассой)

1. `cpsid if`, `clrex`, SCTLR = 0, кэши/TLB, стек на режим; D-кэш `0x4002005C..0x4002007C` (DCISW, 4×256).
2. `mcr p15,0,r0,c1,c0,2` (CPACR), `vmsr fpexc,#0x40000000`, `vmsr fpscr,#0`, NEON `vdup.32 q0,r0` + 15× `vorr qN,q0,q0`.
3. PL310: `+0x100` `+0x104` `+0xF60` `+0xF80`, затем `+0x77C = 0xFFFF` + ожидание сброса бита 0; база из указателя `0x4005C03C` = `0x1A002000`; блок `0x1A000000`: `+0x00 = 0x61`, `+0x0C = 0xFFFFFFFF`, `+0x50 = 0x0F`, `+0x54 = 0x0FFF`.
4. Векторы `0x0`: `4E 04 00 00 4E 04 00 00 4E 24 00 00 4E 34 00 00`.
5. CPU0: `0x40039F88` (`mrc p15,0,r0,c0,c0,5`; `and #0xF`), ветка `cmp r0,#0; beq 0x400211C4` взята на шаге 6448; `_start` per-core `0x40020B3C`.
6. Порядок (после правки Thumb-2): SC/SDIF/eMMC, MMU — в хвосте SC-блока (`0x400215A2 bne.w` / `0x400215BE b.w 0x40020B62`).
7. Вход: `0x40020320 mov r1,#0`; `40020328 teq r0,#4`; `4002032C mrs r0,cpsr`; `40020330 bic r0,r0,#0x100`; `40020334 msr cpsr_x,r0`; `40020338 ldr r15,#0x4002033C`; `4002033C .word 0x40020340`; `40020340 blx 0x40020B3C`.
8. Развилка `0x40020284`: `movw r0,#0x100`; `[r0+0xC4]` (SPAD+0x1C4) vs `0x80`; `[r0+0x6C]` (SPAD+0x16C) vs `0x20000`; A: memcpy `0x4005C000 → 0x4005C078`, `*0x4005C000 = 10`; B (наш случай): обратно, `= 0`; сход `0x40020328`. Прошивка читает поля до `+0x184` → SceKblParam на железе ≈ 0x200 байт (модель пишет 0x100).
9. MMU (`0x40020C0E` `0x40020C18..0x40020C36`): TTBR0 `0x4010804A`, TTBR1 `0x4010C04A`, TTBCR 2, DACR `0x55555555`, CONTEXTIDR; `VBAR` 0 → `0x16100` (`0x40020CD0`) → `0x120` (`0x40020CDE`); `SCTLR = 0x20005805` (`0x40039FC4`); `MVBAR = 0x120`.
10. `0x16100`: `ctx[0x22C] = ctx[0x9C]+0x100`, `ctx[0x9C] = 0x16000`; литерал `mov.w r7,#0x16000; str.w r7,[r5,#156]` (`0x4002100A`), затем `r2 = [r5+156]+0x100; str r2,[r5,#0x22C]` (`0x40020E16`); `MVBAR = (r6+r3+0x23+r7) & ~0x1F`.
11. Конфиг `.bss`: `0x400B2B30`, указатель `0x400B2EC8`, сигнатура `0xCBAC03AA` (`0x400B2EC4`); `config[0x40] = 0x40108000`, `config[0x60] = 0x4010C000`, `config[0x0C] = 0x40000000`.
12. Строитель карты `0x40020E48..0x400211xx`, без циклов: 3× `0x40020A98` (`0x40021072` `0x4002108E` `0x400210AC`), писатель L1 `0x4003A824` (`0x40021102`), заливка `0x1E0` `0x4003A804` (`0x4002104E` TTBR0, `0x40021054` TTBR1), L2 `0x4003AB04` (`0x4002110A`), `0x400211C2 b 0x40020C0E`. Индекс L1 = `VA>>20` **без маски** (запись `0x40000000` — по `0x4010D000`).
13. Отображение `0x4003AD40` (`r0` таблица, `r1` attr, `r3` VA, PA на стеке): `L2[r3>>12] = (pa & ~0xFE0 & ~0x1F) | convert(attr)`; `0x4003AD78` диапазон; вызовы `0x40020AFE` `0x40021126` (attr `0x1061D006`) `0x4002118A` (attr `0x1021D005`) `0x4002BCCA` `0x40031C4C` `0x40034016` `0x4003414E`; дескриптор страницы `0x4003A6F4`. Аргументы `0x4002118A`: `r0 0x80200000`, `r1 0x1021D005`, `r2 0x00016000`, `r3 0` (`[r5+156]-[r5+120]`), `r7 0x40000000` → VA 0, не `0x16000`; `0x40021126` берёт `r3 = [r5+180]-[r5+120]`.
14. Boot-info `0x4000`: `0x40036534`, `memset` через `0x40038F00`; `dst = ctx[0x220] = ctx[0xE4] = 0x4000`, `len = ctx[0xE8] = 0x4000`; литерал `mov.w r2,#0x4000` (`0x40020ED2`); затем `0xBA97F5A1` (`+0xC`), `0xA008B0C3` (`+0x250`), размер `0x4BC` (`+0x8`), самоуказатель на `ctx` (`+0x254`), `ctx[0xE8]` (`+0x14`).
15. ARM-контекст: `0x40850` = бит 7 слова hardware info (`00040596 lw $8,0x3c($sp)`; `srl $8,7`; `and3 $8,$8,1`; `00040850 beqz $8,0x40858`). Слово — ответ syscon на SC-команду `0x0010`, формирует `0x446F2` (`$2 = 16; jmp 0x44274` → `0x44246`); модель: `{0x14,0xFF}` → `0x0000FF14`, бит 7 = 0. Взятая ветка `0x40858` — холодная (`0x4112E → 0x40A4A → 0x41A64/68/6C → 0x40F5E`), строит контекст; невзятая резюм-ветка `0x40852` копирует сохранённый: `00040A86 movh $1,0x1f00` (dst `0x1F000000`), `00040A8A movh $2,0x4000` (src `0x40000000`), `00040A8E mov $3,256`, `00040A92 jmp 0x40AEC`. Холод: `0x0010` → `0xFF14`; resume → `0xFF80`.
16. Трап записей DRAM `0x40000000…0x40001000`: 4606; осмысленные `+0x400..+0x407` = `21 40 05 02 23 …` (pc `0x48102…0x48148`) и `+0x500..` = `F5 FF F5 FF …` (листья idstorage, `0xFFF5`, pc `0x481E2`); `DRAM+0x0..0x400` = 0.
17. Вторая стадия: 4121 чтение eMMC, стоп `pc = 0x5FF1E`; история PC `000403BE..00040404` → `0005FF00..0005FF1C`; перед вызовом сервиса (`0x403C0..0x40404`) обнуляются `$11 $12 $tp $gp $sp`, затем `$1 0xE005001C`, `$2 0xE0050024`, `$3 0xE005009C`, `$4 0xE00500A4`, `$5 0xE0000000`, `jmp 0x5FF00`; `sleep; bra` (`0x5FF1C`) — штатный idle/вызов сервиса, не сбой.
18. Хук `0x5FF00`: `MePCore::pc_hook` + `Vita::cmep_pc_hook`; PC == `board::kFirstLoaderServiceEntry` → `Vita::serve_cmep_service_call()` перезапускает CMeP (вики, шаг 4). `secure_kernel` грузится по `board::kCmepSecureKernelBase = 0x00800000` (31744 байта, MeP).
19. Secure kernel: обмен `0x8003E6…0x800478`; `0x9 → 0x101 → 0x102 → 0x106`, затем «done»-прыжок в `0x40000` → `ErnieBlock::release_soc()` (SC `soc_release = 0x2080`); 117 083 инструкции (было 17 476); ожидание: `00800454 ei`; `0080045E bsr 0x801D5A`; `00800462 bnei $0,0x9,0x800488`; `00800488 sleep`; `0080048A bra 0x80045E`.
20. GPO `0xE20A0008`/`0xE20A000C`, код в битах 16..23 (`raw >> 16`): KBL `0x00840000` (`0x84`), CMeP `0x00490000` (`0x49`); `0x40..0x7F` second_loader, `0x81..0x8F` secure kernel bootloader, `0xA1..0xAF` NSKBL. Буквы `A` → `ABCDE` → `ABCDEH` → `ABCDEH T` (метка `T` `0x4063E`; ошибка `0x40650`). Выход: `0x40346 lw $0,(0x5513c)`; `0x4034A bnez $0,0x40388`; `0x4037C mov $6,768` (успех `0x300`, шаблон `0x40180`); `0x4039A mov $6,1280` (ошибка `0x500`, `0x40100`); `0x403A2` — 32 слова в `0x5FF00`, обнуление регистров, sleep.
21. Обычный прогон без `stage` проходит шаги 1-4: `first loader reported SUCCESS` → `CMeP handed off to the staged image at 0x40000` → хук `0x5FF00` → `secure kernel loaded directly at 0x00800000 (31744 bytes)` → `0x9 → 0x101 → 0x102 → 0x106` → `release_soc()` → `KBL image: 355220 bytes from eMMC SLB2 -> entry=0x40020000` → `ARM started on kernel_boot_loader at 0x40020000`; `stage=cmep-second-loader cmep=40002 arm=4003B3D2`; порядок лога `47 CMeP handoff 0x402FC` → `64 handoff 0x40002` → `67 second loader finished … releasing the ARM` → `73 mirrored the CMeP scratch (32 KiB) to ARM PA 0` → `77 ARM started`. Строки `71 SceKblParam built` в этом прогоне **нет** — при включённых подстановках C++-сборщик не вызывается, а вторая стадия успевает только обнулить запись (см. §6).
22. TrustZone: `ArmCore::ns_` + `scr` (CP15 `c1 c1 0`; запись только из secure; бит 0 NS); `mvbar` (`c12 c0 opc2=1`); банк VBAR (secure и `VBAR_NS`), `effective_vector_base()`; исключение в monitor → `MVBAR+8`; `SMC` (A32 `0x01600070`, T32 `0xF7F0 0x80i0`): `LR_mon = pc+4`, режим MON, PC = `MVBAR+8`, I/F замаскированы; `HVC` (вектор `0x14`); `CPSR.NS` не алиасится в бит 4 (`arm_defs.h`). `tools/dbg_r36b.cmd`: до `PC=0x40020000 CPSR=0x1D3 SVC secure`; после `PC=0x40021008 CPSR=0x1D6 MON secure R14=0x40020004`.
23. `SCR = 0x00000004` в `0x400201A8` (бит 2 SCR.FIQ → FIQ в monitor), NS = 0; в раннем прогоне `stage kbl` + 200 млн шагов `MVBAR`/`VBAR` не выставлялись, `exceptions = 0`.

## 3. SC-протокол и периферия, которую использует KBL

### 3.1 SC (`0xE3100000`, `Ernie.SC`)

```
4003C014 movs r3,#0x5C / movt 0xE310 → 0xE310005C
4003C01E str r1=1,[r3]                      дверной звонок
4003C020 ldr r0,[r2]; tst #1; bne           ждать бит0 = 0
4003C02E tst [0xE31000C0],#8; beq           ждать бит 3
4003C040 str #8,[0xE31000C0]                write-1-to-clear
4003C042 ands r0,r3,#8; bne                 ждать снятия бита 3
4003C066 tst [0xE31000C0],#0x10; beq        ждать бит 4
4003C04C str #1,[0xE3100060]; ждать бит0=0
4003C088 доступ к 0xE3102100 (program-and-poll)
```

* Модель: `Ernie.SC` (`ernie_sc.cpp`, `events_c0_`) + зеркало `Vita::wire_bridges()`; `ScWindowDevice`: `kScReq5C = 0xE310005C`, `kScReq60 = 0xE3100060` (запись не хранится, чтение 0), `kScWindowSize = 0x20000`; `CmepBlock::attach_shared_sc` → `Ernie.SC`.
* 2-я стадия: `0x40DB6` → `[0xE3101000] == 0x0001000F` (иначе `0x800F0010`); `[0xE0010004]`: `(v&5) == 5`, `(v&8) == 0`; страп `([0xE0062020]&7) == 0` (retail 0; бит 0 — выбор `'A'`/`'!'` баннера, `0x5C116`, `0x5C510: bgei $0,0x0`); `0xE3105000` pc `0x4003BC10`/`0x00048848` = `0x4`/`0x1001A`; `0x4882A` пишет `0x101` в `+0x64` окна `0xE2030000+idx*0x10000`, ждёт 0.

### 3.2 CMeP

* Ящик `0xE0000000`: `1` (pc `0x5C5F2`), `9` (`0x4107C`), `0x500` (`0x5FF18`). `erepeat` = `[RPB,RPE]` + слот после RPE, выход только по взятому переходу: `00049536 sw $2,($3)` (`*(0xE3102100) = 1`), `00049538 erepeat 0x4953e`, `0004953E lw $2,($3)`, `00049540 beqi $2,0x1,0x49544`.
* Таймер: `0x5E686` (`and $0,$2` маска 1, `beqz`) и `0x45516` (`ldcb $3,0x404 / and3 $3,$3,1 / bnez $3,0x45520`); `ControlBus`: reload 16 бит BE `0x400`/`0x401`, `0x402` бит 0 пуск, `0x404` бит 0 «счёт дошёл до нуля» (сброс записью 0); задержка = 152 703 инструкции.
* `0xE6008000`: `+i*8` запись 3 бит (`0x482CE`); `+0x20` чтение 4 бит (`0x482E6..0x482F0`); `+0x100+i*8` 16 бит (`0x48310`); `+0x120+i*8` байт, ответ в битах 8..15 (`0x48370`); `+0x180` стробировать 1, ждать 1 (`0x48422`). Идентификация `0x4838A`: `5` в слот 0 → `(ответ&7) == 1`; `8` → `(ответ&3) == 0` и `((ответ>>2)&0xf)` = 4 или 5; слоты `0x48412`/`0x4841A`: 2 в два слота, ждать статус 2.
* Неотображённые: 19 в `0xE0100000` (код `0x49568..0x495E0` обходит таблицу `0x561A4`: 0 — GPIO `0xE20A0000`, 1 — `0xE0100000`; `+0x00` `+0x14..+0x2C` `+0x38..+0x48`) → `CmepStorageDevice` (4 КиБ); `CMeP.SecureCtl` 16 → 64 КиБ (`0xE3100000..0xE310FFFF`; `0x48794` `0x48848` → `0xE31040A4` `0xE3105000`); после правок таких обращений 0. Окно «EC» в модели нет (чтение 0): `0xE6000090/94` `0xEC570078/7C` `0xEC560880…8C` `0xEC370078` `0xEC070078` `0xEC170078` `0xEC060480…8C` (pc `0x400209E4…0x40020A36`); после `0xE6000090/94` пишется `0xE8000010 = 0x0A` (`Kermit.UnkE8000`).

### 3.3 SPI к syscon

* `0xE0A00000` — SPI0 (`SceSpi0Reg`); тот же блок у ARM `syscon.elf` (`0x8100003C`); модель `kermit::Spi` (`spi.cpp`) = `Kermit.Spi0/1/2`, зеркало в CMeP, пакеты `ernie_spi.cpp` → `ErnieBlock::dispatch_command`.
* Формат (`0x439CC` запрос, `0x43C92` проверка): запрос `[cmd_lo][cmd_hi][len = payload+1][payload][checksum]`, ответ `[cmd_lo][cmd_hi][len = payload+2][flags][payload][checksum][pad]`, `checksum = ~(сумма байт перед ним)`; CMD `0x0001` = `01 00 01 FD` (FIFO `0x4376C`); ответ `0x0005` = `04 00 06 00 00 60 40 00 55`; ответ `0x1082` кончается `DD`.
* Команды 2-й стадии: `0x0001` → `0x0002` → `0x0080` → `0x0000`; после правки маски + `0x0080` → `0x0010`. Опрос `0x0000`: `0x449F0` шлёт CMD и ждёт код по маске; `0x44986`/`0x44ACE` — `$1 = 32` (`0x20` ack), `0x44A80` — `$1 = 4` (`0x04`); `lbu $3,52($sp)` + `and $3,$7`, цикл пока 0; ответы `0x0024` (бит 5), `0x0004` (бит 2).
* Длины: `0x44274` принимает кадр при `len-3 <= 3` (payload ≤ 4, `0x442AE..0x442C6`); ответ `0x0001` = `0D 06 00 01`; `0x0010` = `14 FF`; `0x44634` (команда `0x0002`, timestamp) копирует 12 байт; при 6 байтах 2-я стадия возвращала `0x80250100` и повторяла команду.
* eMMC через syscon: `0x1082` (emmc_get_csd, payload 3 → 16), `0x00B2` (set_power_hold, 1 → 0), `0x1083` (emmc_get_ext_csd, 19 → 32); за прогон 9 команд: `0x0000`×2 `0x0001` `0x0002` `0x0010` `0x0080`×2 `0x00A0`×2 (обе с запросом `30 00 00 0B`).
* Syscon RL78: `USS-1001.bin` (1 МиБ, reset `0x0E000`), 114 SFR; 45 SC-команд: `get_status`×13, `get_boot_info`, `get_model_id`, `get_version` (wakeup `0xFF14`), `get_rtc`×2, `get_gauge_status`×4, `get_gauge_reg`×2, `charge_set_limit`×2, `set_power_hold`×2, `emmc_get_csd`×14, `emmc_get_ext_csd`, `storage_read`.

### 3.4 NVS (`0x00A0`)

* Шаблон 40 байт `{0x30, версия, тип, индекс, …}`; валидатор `0x48E24`: `0x48E46 lbu $2,($6)` = `0x30`; `0x48E4E lbu $3,1($6)` = `1`; `0x48E56 lbu $3,2($6)` = 0..5 или 16; `0x48E72 lbu $1,3($6)` = индекс; пара `0x48D28` («записи нет» `{0x30,0,0,index,…}`), `0x48D78` (путь записи, версия 0 → 1). Второй валидатор `0x4906C` (из `0x40C10`, индекс 11): `0x4909E` → `0x30`; `0x490AE` → `3`; `0x490B6` = 0..5 или 16; код `0x800F0027` в `0x49182`. Ответ транспорта: `30 2A 30 01 00 0B … 95` = `{len 0x2A, {0x30, версия 1, тип 0, индекс 0x0B}, checksum}`.
* Нагрузка: `0x4910C $4 = *(0x556C0+индекс*4)+16`; `0x4911C bsr 0x49272` (keyed); `0x49122 bnez $0` → отказ; `0x4912A`/`0x49134 bsr 0x48CDE`; валидатор записи `0x0F` (`0x429xx`) считает keyed-дайджест `0x42E42`, сравнивает через `0x4C3AA`, иначе `0x800F0027`.

### 3.5 SDHCI/eMMC (`0xE0B00000`) и idstorage

* База `0xE0BF0000 + (канал << 16)` (`0004752C movh $7,0xe0b0`; `00047534 movh $3,0xe0bf`; `00047538 sll $7,0x10`; `0004753A add3 $7,$7,$3`); тот же контроллер, что у ARM `sdif.elf`; окно `0xE0B0FF00` в 64 КиБ — старый путь «SC transfer с 28-байтовым дескриптором» (`sc transfers = 0`).
* Смещения: `+0x08` arg; `+0x0C`/`+0x0E` mode/cmd (CMD1 `0x0102`); `+0x24` present state (биты 0/1 `0x477E8`; биты 16/17 = Cmd Inhibit / Card Inserted); `+0x28` HC1 (бит 2); `+0x29` power (`or 0x0B`); `+0x2C` clock (`(div<<8)|1`, ждать бит 1); `+0x2F` sw reset (`1`, ждать 0); `+0x30`/`+0x32` int status (биты 0/2, `0x0F`); `+0x34..0x3A` маски `507`, `895`.
* Команды: CMD0 `0x0000`; CMD1 `0x0102`; CMD2 `0x0209`; CMD3 `0x031A`; CMD9 `0x0909`; CMD7 `0x071A`; CMD8 `0x083A d=1 r=1` (512 байт) — все `status=0x1`, CMD8 `0x21`; затем CMD16, CMD17 `lba=1` (512 байт, ADMA2), CMD13, повтор CMD17. CMD1: `0xC0FF8000` (busy, бит 31 OCR), далее `0x40FF8000`; `0x46F2E` до 100 раз вызывает `0x47772`, выход при ответе < 0 (`00046F6E lw $3,0x14($sp)`; `00046F70 bgei $3,0x0,0x46f7a`). CMD3 (MMC): ненулевой arg → RCA (`arg >> 9 = 128` = `0x00010000`), ответ `0x00000900`; нулевой → SD R6. Ошибки: `0x47DE2` маскирует `0xFDFFE008`, возвращает `0x80320100 + <номер младшего установленного бита>` (`0x110` = бит 16).
* ADMA2: таблица `0x40000400` (`[gp-0x7FFC]`, заполняет `0x41002`: `movh $1,0x4000; or3 $1,$1,0x400`, длина `0x100` = 32); записи 8 байт `{u16 attribute, u16 length, u32 address}`, `attribute = 0x21` (VALID | ACT 10b TRAN), последней `+0x02` (END) — SD Host Controller Simplified Spec 2.0 §2.2.13; `0x48158` → ADMA_SYSTEM_ADDRESS (`0x58`), block size/count из `[desc+0x24]`/`[desc+0x28]`, бит 0 transfer mode; `0x4708C` строит дескриптор: `+0x00` 52, `+0x04` флаги (`0x114` без DMA, `0x514` с DMA), `+0x08` cmd, `+0x0C` arg, `+0x20` буфер, `+0x24` длина, `+0x28` число блоков. Трасса `[sdif] CMD idx=17 arg=0x00000200 tm=0x0013 block=0x00010200 size=512 count=1 data=1 read=1 multi=0 dma=1 adma=0x40000400 cmep_pc=000481E2`; `[sdif] adma table=0x40000400 moved=512/512 ok=1`; `tm=0x0013` = биты 0 (DMA), 1 (block count), 4 (read).
* Драйвер: циклы порта `0x20` (`0x47B12`, `0x47BAC`) при `(desc+4)&0x700` = `0x100`/`0x200`; у загрузчика `0x514` (бит 10 `0x400` = DMA, ставится `0x48158`). ### 3.6 Bigmac / bignum / SCE

* Bignum (по `0x5CE04`, `0x4BA20`): `0xE0040108` основание (64 слова) [`0x5CE0C` `0x4BA52`]; `0xE0040400` модуль (64) [`0x5CE28` `0x4BA6E`]; `0xE0040808` слово экспоненты [`0x5CE50` `0x4BAF6`]; `0xE0040800` управление `0x91000000 | n1<<18 | n2<<9` [`0x5CE5C` `0x4BAA0`]; `0xE0040804` статус [`0x5CE68..0x5CE8E` `0x4BAC2..0x4BB3E`]; `0xE0040508` результат (64) [`0x5CECA` `0x4BB52`]; `0xE0020020` семафор [`0x5CF12` `0x4BBB0`]. * Слово функции (обёртка `0x453AA`): `base | (режим&7) | ((арг<<3)&0x38) | ((арг<<8)&0x300)`; `base` из дескриптора ключа (`0x2300` для keyslot `0x213`); наблюдённые `0x2309` `0x238A` `0x2093`; бит 13 (`0x2000`) = ключ из keyring по индексу в flags (трасса `0x00000213`), бит 7 (`0x80`) = ключ из памяти; модель знает `0x0301` `0x030A` `0x010A` `0x000C…0x0013` `0x0033`, `0x0102` — семья `0x010A` (режим `(2,0,1)`), `0x033B` — SHA-256 с keyring `0x212`. `ZLB_BIGMAC_TRACE`: 16 операций за прогон — 14 у 1-го загрузчика (keyring, расшифровка образа в `0x40000`, SHA-256), одна `0x000C` (AES-CBC, ptr `0x56600`, len `0x5A00`) тоже у него, одна «фантомная» из шаблона выключения (pc `0x5FF04`); крипто 2-й стадии — код MeP (`0x46C7A`, библиотека `0x4C000`).
* SCE: `0x4A6DE` гоняет 48-байтовый запрос через транспорт по указателю (`jsr $0` `0x4A756`); магия `SCE\0`: `0x4A774 lw $1,($6)`; `0x4A77A movu $2,0x454353`; `0x4A786 bne` → `0x800F0624`; `0x4A78E` слово 1 `== 3`; `0x4A796 and3 $1,$2,0x40` (бит `0x40` байта 8). Транспорт `0x4AC44`; наш путь — заглушка `0x4A034` (три слова со стека, возврат 0). Кадр `0x5DE00`: `+0x00` указатель на `0x5FFC0000`, `+0x08` `0x40000`, `+0x0C` буфер `0x5E800`, `+0x10` `0x1000`, `+0x14` `0x56B94`, `+0x18` `0x200`; проверки `0x4144E lhu $3,16(ответ); bnei $3,0x2`; `0x41462 bsr 0x49F42`; `0x4147A lbu $3,24(ответ+16); blti`.
* Причина отказа: запрос копируется в `0x5FFC0000` (memcpy `0x40AEC`, pc `0x40B10`: `0x454353`, `3`, `0x10140`, `0x600`, `0x1000`), адрес не отображён, чтение давало `0xFF`; заведено окно `CMeP.SceBlock` (64 КиБ, `kSceBlockBase`/`kSceBlockSize` в `cmep.h`), затем `SceBlockDevice` (`cmep_internal.h`): магия `SCE\0`, слово 1 `== 3`, байт 8 бит `0x40`, `+0x08 = 0x10140`, `+0x10 = 0x1000`; буфер `0x5E800` после прохождения: `53 43 45 00 | 03 00 00 00 | 40 01 01 00 | 00 06 00 00 | 00 10 00 00 | 94 5B 05 00 …`.
* Аргументы SCE (сайт `0x4A99A`): `0x4A976 $1 = $7; bsr 0x49FE8`; `0x4A984 bsr 0x49FF6`; `0x4A98A $5 = 0x800F0616`; `0x4A992 $0 = *($6+8)`; `0x4A99A bne $0,$1,0x4ABEC`, `$1 = [sp+0x2C] = 5`, в `[структура+8]` = `0xC7D4904F`; `$6 = 0x5EE70` (выше стека CMeP `$sp = 0x5E000`, вне BSS `0x55710..0x56554`); в образе по смещению `0x2E70` нули; watchpoint `0x5EE70`/`0x5EE78` не сработал за 8 млн шагов. Сравнение диапазонов `0x49F7A..0x49FE6`: `0x800F0624` при разных длинах, `0x800F0602` при равных и разном содержимом (сайт `0x49FCC`); валидатор `0x49D4E..0x49D5C` сверяет `+0x10`, `+0x14`, размер `0x90`. ## 6. Boot-контекст и SceKblParam

* **PA `0x00000000..0x7FFF` на ARM — CMeP scratch (32 КиБ), он же shared SRAM, видимый CMeP по `0x1F000000`.** ARM стартует с PC `0x00000000`, где second loader оставил векторы: `ldr pc,[pc,#0x18]` → литерал по `0x20` = `0x40020000`. `0x0000..0x3FFF` — boot context (KBL читает до MMU `+0x1C4`, слова `0x000`/`0x100`), `0x4000..0x7FFF` KBL очищает под свой boot-info. Вики `Boot Sequence`: second loader «writes the ARM exception vector and some boot context information to the 32kB scratch buffer (mirror mapped to `0x00000000` on ARM)», затем secure kernel велит Syscon сбросить ARM CPU на `0x00000000`.
* **SceKblParam: база PA `0x1F000100`, размер `0x100`, magic `0xCBAC03AA`; копия без magic — PA `0x4001FD00`.** База подтверждена дизассемблером сборщика (`0x41B4A` грузит `0x1F000100`; `0x41B38` обнуляет там 256 байт) и сверкой полей с вики (DRAM base `+0x60`, `kprx_auth_sm` `+0x90`); ранняя `0x1F000040` — ошибка на `0xC0` ниже (из фразы про fallback DIP switches по PA `0x80`) и перекрывала заголовок структуры. Константы: `kKblParamBase = 0x1F000100`, `kKblParamDram = 0x4001FD00`, `kKblParamSize = 0x100`, `kKblParamMagic = 0xCBAC03AA`.
* Раскладка вики `KBL_Param` (0x100 или 0x200 байт): `0x00/0x02` version/size; `0x04/0x08` текущая/минимальная версия прошивки; `0x20/0x30` QA flags / boot flags; `0x40..0x5F` DIP switches; `0x60/0x64` DRAM base/size; `0x6C` boot type indicator 1; `0x80/0x84` paddr/size `secure_kernel.enp`; `0x90/0x94` `0x98/0x9C` paddr/size `kprx_auth_sm.self` и `prog_rvk.srvk`; `0xC0/0xC4` sleep/wakeup factor (syscon cmd 3 / `0x10`); `0xD4` hardware info (cmd 5); `0xFC` magic. Модель (`Vita::build_kbl_param()`, порядок: структура, затем зеркало scratch на PA 0): version `1`, size `0x100`, версия `0x01040000`, QA/boot flags 0, DIP release (`+0x50` SDK 0, `+0x54` shell 0, `+0x58 = 0x00080002`, `+0x5C = 0x20000000`), DRAM `0x40000000` + `kermit::kScuSize`, boot type `4`, `secure_kernel` `0x00800000` + размер, `kprx_auth_sm` `0x00800500`, `prog_rvk` `0x00809B00`, session id, sleep/wakeup factor, hardware info `0x00406000` (IRS-002 — ответ модели на команду 5), power info, ревизия, magic `0xCBAC03AA`; `Vita::mirror_cmep_scratch_to_arm()` копирует первые 32 КиБ SRAM в ARM-овское PA 0 (проверено дампом).
* **Состояние записи в обычном прогоне (измерено покрытием и трапом).** В дефолтной конфигурации запись по PA `0x1F000100` **нулевая**: вторая стадия исполняет только обнуление (`0x41B38` → memset 256 байт), а до сборщика (`0x41B4A`) не доходит, потому что модель останавливает CMeP на «done»-прыжке secure kernel; C++-сборщик при включённых подстановках не вызывается вовсе (`bootchain.cpp`: `if (!substitutions_enabled_static()) build_kbl_param();`). Трап `ZLB_RTRAP=0x100-0x1D0` показывает чтения KBL по `0x400376E4` (128 байт PA `0x100` → `0x400B2DC8`) и `0x4002028C` (`+0x1C4`) — все слова `0`. **KBL доходит до Non-Secure с пустой записью.**
* Дамп PA `0x100`, когда запись пишет **C++-сборщик** (проверено с `ZLB_NO_SUBSTITUTION=1` + `--stage kbl`; в обычном прогоне этих значений нет): `+0x00 = 0x00000060` sleep, `+0x04 = 0x0000FF14` wakeup (холод), `+0x08 = 0x40` USB, `+0x10 = 0x00406000` hardware info, `+0x14 = 0x0C` power, `+0x38 = 0x00010000` revision, `+0x3C = 0xCBAC03AA` magic; PA `0x1A0` = `FF FF FF FF FF FF 00 3F` (записал second_loader, pc `0x41A9C..0x41AC8`). DRAM-копия `0x4001FD00` = `01 00 00 01 00 00 04 01 00 00 04 01 …` (version 1, size `0x100`, firmware 01.04.0000). `SceKblParam + 0xC0` = PA `0x100`. Потребление: `0x400376E4` копирует 128 байт PA `0x100` → `0x400B2DC8` (вызывающий `0x40021203`), затем → PA `0x40300100`. Гейт `ZLB_ARM_WAIT_CMEP` снимает объяснение «порядок событий», но стену Stage 1 не убирает.
* «Холодная» ветка `0x40858` (`0x4112E → 0x40A4A → 0x41A64/68/6C → 0x40F5E`) собирает KBL-параметр (`0x40A4A` вызов, `0x41A64/68/6C` записи полей); `0x40850` = бит 7 слова hardware info: `0x0000FF14` (холод) → бит 7 = 0 → ветка берётся; `0xFF80` (resume) → бит 7 = 1 → контекст из DRAM не копируется.

| Подстановка таблицы классов: адрес не запоминался; не проверялась DRAM; транслировался адрес таблицы вместо слота | в лог попало `class table supplied at VA 0x0004705F` | `class_table_va_`, проверка `region_base ∈ [0x40000000,0x80000000)`, трансляция слота |

## 7.1 Secure KBL (SKBL) в честном прогоне: что исполняется и что держат подстановки

Изолированный замер — `--stage kbl` (CMeP-подстановки при этом не участвуют), сравнение
с `ZLB_NO_SUBSTITUTION=1`:

| | с подстановками | без подстановок |
|---|---|---|
| чекпойнты GPO | `0x81…0x87`, `0x88`, `0x89`, затем `SCR.NS=1` и NSKBL | `0x81…0x87`, затем **`0x8D`** |
| покрытие ARM (окно `0x40020000-0x40080000`, gran 2) | 11 828 сайтов (6.8 %) | 9 664 (5.5 %) |
| ARM | 51 млн инструкций, NSKBL на `0x51000D0C` | 51 млн инструкций в петле `0x400219DC` (Thumb `FE E7` = `b .`) |

**Отказ [Р].** Трасса `ZLB_ARM_TRACE_RANGE=40021900-40021A00`:

```
4002F074  ldr r4, [r0, #0x34]     r0 = 0  →  чтение VA 0x00000034
4002F078  cbz r4, 0x4002F08C      ← pc в логе отказа, lr = 0x4002F078
→ data abort → обработчик 0x40020394 (clrex/push) → movs r0,#0x8D
→ 0x400219D0 (GPO-чекпойнт 0x8D) → sleep-петля
```

Это **единственный** непреобразованный отказ ARM за прогон (`ZLB_ARM_FAULT_LOG=1`).
Тот же чекпойнт `0x8D` даёт и полная цепочка: `--first-loader pch` + `ZLB_NO_SUBSTITUTION=1`
до ARM не доходит (встаёт на `0x54` у CMeP), а без подстановок в цепочке ARM не
запускается вовсе; `--stage kbl` — единственный способ увидеть SKBL изолированно.

**Почему отказ возникает.** Гостевые таблицы самого KBL не описывают низкое окно:
`TTBR0 = 0x40108000`, `L1[0] = 0x40101181` (coarse), `L2 @ 0x40101000`:

| слот | с подстановками | без подстановок |
|---|---|---|
| `[0x00]` (VA `0x00000`) | `0x0000047E` | `0x00000000` |
| `[0x01]` (VA `0x01000`) | `0x0000047E` | `0x00000000` |
| `[0x10]` (VA `0x10000`) | `0x4010305F` | `0x00000000` |
| `[0x19]`, `[0x1A]` (VA `0x19000`/`0x1A000`) | `0x0000047E` | `0x00000000` |
| `[0x40]` (VA `0x40000`) | `0x4011845F` | `0x4011845F` (гость) |

То есть низкие записи ставит именно модель (`satisfy_arm_boot_fault`), а не гость:
`L2[0x40]` KBL пишет сам (`{vpa 0x40000, pbase 0x40118000}` в записи карты
`0x400B2B30`), остальные — нет. На железе эти адреса — алиасы, на которых работал
предыдущий этап: VA 0 «ARM Boot. By default, alias of physical address 0x1F000000
i.e. ScePower scratchpad», VA `0x40000` — «MeP boot. Mirror of physical address
0x00800000». Их должен оставить ARM boot ROM вместе со второй стадией.

**Проверенная попытка снять подстановку [Р, откачена].** Записи ставились заранее,
из `Vita::install_inherited_low_window()` (в том же месте, где восстанавливается
вектор-страница), атрибуты брались у самого загрузчика — из его секции TTBR1
`L1[0x400] = 0x4001158E`. Результат: слоты `[0x00]`/`[0x01]` заполнялись, но отказ
**сдвигался**, а не исчезал: следующий фолт — чтение VA `0x000010B0` при
`pc=0x4002DBD4` (страница `[0x01]`, которую модель уже отобразила). Ошибка не в
наличии записи, а в правилах/атрибутах, поэтому эксперимент откачен, а подстановка
остаётся. Открытый вопрос для следующего раунда: какие PA и атрибуты нужны страницам
`0x00000`/`0x01000`/`0x10000`/`0x19000`/`0x1A000` (сравнить с ScePower scratchpad и
окном `0x00800000` по картам `docs/HARDWARE.md`), и почему атрибут `0x58E` вместо
`0x47E` не проходит.

**Барьер/WFE.** Помимо отказов, SKBL держит две подстановки в `Vita::run_slice`
(§`docs/STATUS.md` 4): распарковка счётчика барьера (`barrier parked … 0x4003B3D6`,
`0x4003B3C8`, 7 раз за прогон) и пробуждение кластера из WFE. Их снимать нужно не
заплаткой, а моделью: таймерное прерывание GIC, доставляемое ядру в WFE (сейчас не
доставляется), и фазовая машина барьера на разделяемом стеке вторичных ядер.

**Вектор-страница.** Стейджинг 0xC0 байт ELF-сегмента в `PA 0x16100`/`0x40000100`
идёт **безусловно** (не проверяет `ZLB_NO_SUBSTITUTION`) — это конструкция модели, а
не переключаемая подстановка. Переключаемо только зеркало runtime-страницы SKBL в
`PA 0x40326100`, и оно нужно из-за MMU-off выборки монитора (MVBAR `0x16140`).

Диагностика, добавленная этим разбором: `ZLB_ARM_FAULT_LOG=1` (отказы ARM в режиме без
подстановок) и `ZLB_SECURE_FAULT_LOG=1` (отказы с признаком `secure`, TTBR0/TTBR1,
DFSR/DFAR, IFSR/IFAR — при подстановках `ZLB_KBL_FAULT_TRACE` для secure-этапа молчит,
потому что хук выходит раньше своей трассы).

**Кто на самом деле пишет низкое окно [Р, трап `ZLB_WTRAP=40101000-40101008`].** Записи
в `L2 @ 0x40101000` делает **сам загрузчик**, а не модель — за прогон их всего четыре, от
кода ARM:

```
+0x101000 = 0x00000000  pc=4003AB0E   ← обнуление (цикл затирания таблицы)
+0x101004 = 0x00000000  pc=4003AB12
+0x101000 = 0x0000047E  pc=40029F34   ← KBL описывает VA 0x00000000
+0x101004 = 0x0000147E  pc=4002DBD0   ← KBL описывает VA 0x00001000, XN установлен (0x1000)
```

`pc=0x4002DBD0` — это ровно та инструкция, после которой идёт отказ: `0x4002DBD4`
(`ldr.w r0,[r4,r1,lsl #3]` при `r4 = 0x1000`, `r1 = 0x16` → VA `0x10B0`). То есть
загрузчик **сам** пишет запись и на следующей инструкции читает ту же страницу — с XN,
то есть «данные без исполнения», и чтение данных XN не запрещает.

Отсюда важный вывод для прошлой редакции этого раздела: формулировка «KBL не описывает
низкое окно» неверна для слотов `[0x00]`/`[0x01]` — он их описывает сам, начиная с
`0x40029F34`/`0x4002DBD0`, и модель в эти два слота **не пишет вообще** (в трапе нет ни
одной записи с подстановочных pc).

Решающее сравнение — тот же трап с `ZLB_NO_SUBSTITUTION=1`: за прогон есть **только две
записи**, обе нулевые.

```
+0x101000 = 0x00000000  pc=4003AB0E
+0x101004 = 0x00000000  pc=4003AB12
```

Второй замер (`ZLB_SKBL_ORDER_LOG=1`) уточняет картину: расходится **не таблица и не
первый вход** — входы совпадают до инструкции вызова. Для входа `0x6400`
(`0x40031CB0` ← `0x4002C6C0`, `r0=0x6800`/`r1=0x4005AB0C`/`r2=0x10009`) оба прогона
проходят один и тот же путь:

```
40031CC6  bl 0x4002BA7C        → r0 = 0x00006400
40031CD4  mov r5, r0
40031CD6  bl 0x4002F070        r0 = 0x6400, r1 = 0x1060D006, r2 = 0x40060FCC
```

и `0x4002F070` уходит в `0x4002F08C` (`ldr r3,[r0,#56]` → `0x64C0`,
`ldr r1,[r3,#28]` → `0x4002A6E4` → `0x400318E8`), где оба прогона возвращают
`r0 = 0x00010000` (положительное, `blt` не срабатывает). Значит, расхождение лежит
**позже по потоку**, а не на этом входе: фиксированный в прошлой редакции вывод
«в честном прогоне первый вход не проходит» неверен — первый вход проходит, и падение
наступает дальше.

Что подтверждено: в честном прогоне есть четыре входа `0x40031CB0`
(`r0 = 0x6800`, `0x6AC0`, `0x6D80` и далее; `lr = 0x4002C6C5/C713/C761`) с одинаковыми
`r1/r2`, а `0x4002DBD0` (описание VA `0x1000`) не исполняется ни разу; в прогоне с
подстановками он исполняется. Ошибка возникает на одном из последующих входов этой же
функции, и её надо локализовать трассой участка между `0x40031CB0` и паникой
`0x4002F070`/`0x40020394` в честном прогоне.

Третий замер (`ZLB_ARM_TRACE_RING=0x4002F090`, `…_SIZE=64`) показывает, что **до ветки
`cbz` оба прогона идут одинаково** — оба проходят `0x4002F1D4 → 0x40033720 → … →
0x4002F0C2 → 0x4002F1BA → 0x4002F1BC → 0x4002F0DA … 0x4002F0E4`; расхождение лежит
внутри тела, вызываемого из `0x4002F090`. В честном прогоне ветка в тело доходит, а
падение наступает на следующем проходе того же пути — на `0x4002F074`
(`ldr r4,[r0,#0x34]` при `r0 = 0`), где прогон с подстановками эту же инструкцию
проходит. Значит, в подстановочном прогоне до этого места уже выполнено описание
низкого окна (`0x4002DBD0`), а в честном — нет, и следующий шаг: снять кольцо на
`0x4002F074` **в подстановочном** прогоне и сравнить, что именно предшествует ему там.

### 7.1.1 Где именно расходится честный прогон (последовательность событий)

`ZLB_SKBL_ORDER_LOG=1` даёт полную последовательность. Честный прогон:

```
0x40029F34  r0=0x80020001 lr=0x4002C0A5     ← первый вход в описание окна (уже ПОСЛЕ отказа)
ENTER 0x40031CB0 r0=0x6800 lr=0x4002C6C5    → 0x4002F070 r0=0x6400   (проходит)
ENTER 0x40031CB0 r0=0x6AC0 lr=0x4002C713    → 0x4002F070 r0=0x6400   (проходит)
ENTER 0x40031CB0 r0=0x6D80 lr=0x4002C761    → 0x4002F070 r0=0x00000000
→ 0x40020394 (data abort) → 0x400219D0 (GPO 0x8D) → петля 0x400219DC
```

Прогон с подстановками отличается ровно одним: **первый** `0x4002F070` идёт с
`r0=0x6400` ещё до `ENTER`, а третий вход `0x6D80` не приводит к `r0=0`
(`0x4002DBD0` исполняется). То есть до последнего вызова оба прогона совпадают
(`0x40031CB4..0x40031CD6`, `lr=0x40031CDB`, `sp=0x40060FB8`), и расхождение возникает
**на возврате `0x4002F070` → `0x40031CDA`**: в честном прогоне вызывающий получает
`r0 = 0` и передаёт его дальше (`mov r5,r0`), после чего следующая же инструкция
`0x4002F074` (`ldr r4,[r0,#0x34]`) обращается к VA `0x34`.

| | подстановки вкл | `ZLB_NO_SUBSTITUTION=1` |
|---|---|---|
| цепочка `0x4002F090 → 0x4002A6E4 → 0x400318E8` | `r0=0x6400`, возврат `0` | то же (`r0=0x6400`, возврат `0`) |
| три входа `0x40031CB0` | `0x6800`, `0x6AC0`, `0x6D80` | те же |
| `0x4002DBD0` (описание VA `0x1000`) | исполняется | **не исполняется** |
| `0x4002F074` (`ldr` VA `0x34`) | проходит | **data abort → `0x8D`** |

Вывод для следующего шага: разница не в разборе дескрипторов и не в таблицах, а в
содержимом boot-контекста, которое читает `0x4002D400`/`0x400318E8` при **третьем**
входе (`0x6D80`). Проверять нужно ту запись, которую этот вход читает, — и смотреть
кольцо на `0x4002F070` в подстановочном прогоне, чтобы увидеть, что там возвращается
вместо нуля.

### 7.1.2 Настоящая причина: до отказа доходит только честный прогон

Кольца на `0x4002F074` (первое попадание, `ZLB_ARM_TRACE_RING=0x4002F074`) показали,
что расходится **не значение на входе, а сам путь**:

| | подстановки вкл | `ZLB_NO_SUBSTITUTION=1` |
|---|---|---|
| путь до `0x4002F074` | `0x400316E8 → 0x400316FA → 0x4003CCC0 → 0x4003CCD8 → 0x4003CE90 → 0x400316FE → 0x40031700…0x40031744` (машинерия таблицы классов и менеджера объектов) | `0x4002B844 → 0x4002BA82 → 0x40031CCA … 0x40031CD6 → 0x4002F070 → 0x4002F072` |
| `r0` на входе в `0x4002F074` | **`0x6400`** (валидный указатель) | **`0x00000000`** |
| `[r0+0x34]` | VA `0x6434` — читается | VA `0x0034` — **data abort → `0x8D`** |
| `0x4002DBD0` (описание VA `0x1000`) | исполняется | не исполняется |

То есть честный прогон первым попадает в `0x4002F074` **с нулевым указателем** и там
падает; прогон с подстановками доходит до этой же инструкции с валидным `0x6400` и
проходит. Нулевой указатель приходит из вызывающего (`0x40031CD6`: `mov r5,r0` после
`bl 0x4002F0??`), а тот — из поиска `0x4002BA7C`/`0x4002D400`, который для первого
входа (`0x6800`) в честном прогоне даёт `0x6400`, а на четвёртом входе — `0`. При этом
до четвёртого входа честный прогон идёт **тем же** путём, что и подстановочный
(`0x4002F090 → 0x4002A6E4 → 0x400318E8`, `r0=0x6400`, возврат `0`), — то есть расходится
уже *внутри* `0x4002F090`, а не на его вызове.

Практический вывод: подстановка низкого окна нужна не потому, что KBL не умеет
описывать окно, а потому, что она уводит загрузчик на другую ветку (машинерия таблицы
классов), где до `0x4002F074` доходят с валидным указателем. Пока эта ветка не
воспроизведена без подстановок, снимать `satisfy_arm_boot_fault` нельзя. Следующий шаг
(узкий): снять кольцо на `0x4002F090` в **честном** прогоне и найти в нём точку, где
возврат становится нулевым (сравнивать с подстановочным кольцом того же участка).

### 7.1.3 Точка отказа: четвёртый дескриптор обхода (`0x6D80`)

Замеры `r0` на каждом входе `0x4002F070` (`ZLB_SKBL_ORDER_LOG=1`) и трасса поиска
`0x4002BA7C` (`ZLB_ARM_TRACE_RANGE=4002BA7C-4002BA90`) закрывают вопрос:

| | честный прогон | с подстановками |
|---|---|---|
| вход `0x40031CB0` #1–#3 | `0x6800`, `0x6AC0`, `0x6D80` | те же |
| `0x4002F070` #2, #3 | `r0 = 0x6400` | `r0 = 0` |
| `0x4002F070` #4 | **`r0 = 0`** → `0x4002F074` (`ldr r4,[r0,#0x34]`) → abort `0x8D` | `r0 = 0`, отказ не наступает (ветка другая) |
| поиск `0x4002BA7C` | три вызова из `0x40031CCB` с `r0 = 0x10009`, все возвращают `0x6400`; следующий поиск уже из `0x40032E6D` | — |

То есть до третьего дескриптора включительно обход корректен (поиск отдаёт `0x6400`),
а падает **четвёртый** дескриптор: у него `r0 = 0`, и первая же инструкция тела
обращается по `[0+0x34]`, то есть к VA `0x34` — а эта страница не описана (см. таблицу
`L2 @ 0x40101000` выше). Причина нуля — не в поиске и не в таблице: между третьим и
четвёртым вызовом честный прогон проходит ~640 инструкций другой ветки (спинлок
`0x4003A224`, копирование `0x4002AF…`, четырехъядерный барьер `0x4003B384`), которых в
подстановочном прогоне на этом месте нет; кольцо на `0x4002F070` (600 инструкций) их
видно целиком.

Остаётся один открытый выбор, и он определяет, снимаема ли подстановка вообще:

1. **Список дескрипторов на железе длиннее трёх** — тогда четвёртый вход законен, и
   модель обязана описать его страницу (`0x6D80`) и/или довести обход до конца;
2. **Список кончается на третьем** — тогда честный прогон заходит в четвёртый вход
   потому, что модель не воспроизвела условие останова (границу списка), и чинить надо
   именно это, а не таблицы.

Различить их можно по источнику границы обхода: вызывающий (`0x4002C6xx`, три вызова с
`lr = 0x4002C6C5/C713/C761`) набирает адреса с шагом `0x2C0` из структуры, которую
строит сам; нужно найти поле-счётчик/указатель конца и проверить, чем оно заполняется в
модели.

### 7.1.4 Итог раунда 4: расхождение начинается раньше обхода дескрипторов

Трасса line-walker'а `0x40030D1C` (`ZLB_SKBL_ORDER_LOG=1`) закрывает вопрос о
первопричине:

| | честный прогон | с подстановками |
|---|---|---|
| входы `0x40030D1C` | **ни одного** | 6 (четыре с `lr=0x4002DBCD`, `r0=0x80024A00`, `r1=0x2C`) |
| `0x4002DBD0` (описание VA `0x1000`) | не исполняется | исполняется 4 раза из `0x4002DBCD` |
| `r0` на фатальном входе `0x4002F074` | `0` → abort `0x8D` | `0x6400` (валидный указатель) |

Связующее звено — **подстановка другого раунда**, которая видна в логе только у
подстановочного прогона:

```
low window L2[0x12] given its own page 0x40140000 (diagnostic)
```

То есть при подстановках три младших окна (`VA 0x10000`/`0x12000`/`0x14000`), которые
KBL сводит в одну физическую страницу 0, модель разводит, и это уводит загрузчик на
ветку, где к `0x4002F074` приходят с валидным указателем. В честном прогоне этого
разведения нет, машинерия классов идёт другим путём (`0x400316E8 → 0x4003CCC0 →
0x4003CE90 → …`), line-walker не вызывается вовсе, и рано или поздно доходит до того же
`0x4002F074`, но с `r0 = 0` — и падает на первой же инструкции тела.

**Вывод для цели:** `satisfy_arm_boot_fault` снимать нельзя до тех пор, пока не
воспроизведено это разведение страниц (и машинерия классов за ним). Причина отказа SKBL
теперь прослежена до конкретной подстановки другого этапа, а не до отсутствующей записи
в таблице: сами записи низкого окна KBL при честном прогоне успевает создать
(`0x40029F34` исполняется в обоих прогонах), но до четвёртого дескриптора обход доходит
только на «разведённой» ветке.

### 7.1.5 Раунд 5: разведение страниц к честному прогону отношения не имеет

Проверено напрямую (`--stage kbl`, `ZLB_NO_SUBSTITUTION=1`, меняется только
`ZLB_KBL_LOWALIAS`):

| конфигурация | ARM | GPO |
|---|---|---|
| `ZLB_KBL_LOWALIAS=0` (разведения нет вовсе) | `pc=400219DC`, 51 194 417 инструкций | `0x8D` |
| `ZLB_KBL_LOWALIAS=12,30` (штатное разведение) | `pc=400219DC`, 51 194 417 инструкций | `0x8D` |

Прогоны **совпадают побитово** по PC и GPO. То есть подстановка `0x4003AD6C`
(`L2[0x12] given its own page`) — не причина расхождения, а безразличный к нему
диагностический рычаг; её отключение ничего не меняет.

Матрица остальных флагов (`ZLB_KBL_CLASS_TABLE`, `ZLB_PART_BLOCK_CACHE`,
`ZLB_NSKBL_LOWWIN`, `ZLB_KBL_OBJMGR_NOLOCK`, `ZLB_NSKBL_BOOTCFG`, `ZLB_KBL_HEAP`,
`ZLB_KBL_CARVE_STATE` в `0` при `ZLB_NO_SUBSTITUTION=1`) даёт тот же `0x8D`: в честном
режиме все они уже выключены, потому что `ZLB_NO_SUBSTITUTION` имеет приоритет.

**Что остаётся открытым (главный вопрос следующего раунда).** Таблицы трансляции у
обоих прогонов в момент первого обращения к VA `0x34` одинаковы
(`TTBR0 = 0x40108000`, `L1[0] = 0x40101181`, coarse-таблица `L2 @ 0x40101000`), но
подстановочный прогон доходит до `0x4002F074` с валидным указателем и **не** отказывает,
а честный — отказывает на первом же обращении. Поэтому дальше надо ловить не *что*
записано в таблицу, а *как* идёт обращение: поставить в подстановочном прогоне
watchpoint на VA `0x34` (или точку останова на `0x4002F074`) и снять TTBR0/TTBCR/DFSR в
этот момент, а также проверить, не идёт ли чтение через другой ASID/домен. Пока эта
разница не объяснена, снятие `satisfy_arm_boot_fault` двигать нельзя: сама по себе
запись в L2 (проверено в раундах 2-3) отказа не убирает.

### 7.1.6 Раунд 6: запись окна идёт из другого пути — причина в таблице классов

Ключевая точка найдена: `0x40029F34` — та самая инструкция, которая пишет дескриптор
окна. В обоих прогонах она исполняется **ровно один раз**, но с разными аргументами и
возвратом в разные места:

| | подстановки вкл | `ZLB_NO_SUBSTITUTION=1` |
|---|---|---|
| `r0` | `0x80020001` | **`0x00000000`** |
| `r1` / `r2` | `0` / `0x6000001F` | **`0x12980`** / `0x12980` |
| `r5` (таблица классов, глобал `0x400B291C`) | `0x400B2900` | `0x400B2900` |
| `lr` (вызывающий) | `0x4002BFDD` | **`0x4002C0A5`** |

`r5` — это тот самый глобал `0x400B291C`, который создаёт подстановка таблицы классов
(«class table created at VA 0x400B0000»): KBL его **сам не пишет**. При включённых
подстановках туда до записи окна успевает лечь валидная таблица, и запись окна идёт из
ветки `0x4002BFDD`; без них регистрация классов уходит другим путём (`lr=0x4002C0A5`) и
доходит до той же инструкции с нулевым `r0`/`r2`, после чего таблицы низкого окна
остаются в другом состоянии.

**Вывод:** причина отказа SKBL — не в записях низкого окна и не в разведении страниц
(раунд 5), а в **подстановке таблицы классов**. Она меняет поток до того, как
исполняется запись окна, и именно поэтому честный прогон рано или поздно приходит к
`0x4002F074` с нулевым указателем. Порядок работ для цели (2) меняется: сначала нужно
воспроизвести предзаполненное состояние, из-за которого KBL находит таблицу классов
(либо честно доказать, что KBL пишет её сам в невоспроизведённой ветке), и только потом
снимать `satisfy_arm_boot_fault`. Замеры этого раздела дают для этого точную точку
сравнения — единственную инструкцию `0x40029F34` и её `lr`/`r0`.

### 7.1.7 Раунд 7: расходится порядок инициализации, а не путь

Кольцо на `0x40029F34` (`ZLB_ARM_TRACE_RING`, 80 инструкций) показывает, что **путь до
записи окна у обоих прогонов побайтово один и тот же**:

```
4002BDE8 … 4002BE0C → 4002BF7C → 4002BF96 (bl 0x40032260) → … → 4003A28C/4003A300
(спинлоки) → 4002BFDC → 4002BFE2 → 4002BF90 → 4002C160 → 40029F30 → 40029F32
```

Различие — только в аргументах и в адресе возврата. Точка входа билдера окна
`0x40029EE0` (`lr=0x4002C637` в обоих случаях, т.е. вызывающий один и тот же) даёт
разные кадры стека, и это не данные, а **порядок**:

| | подстановки вкл | `ZLB_NO_SUBSTITUTION=1` |
|---|---|---|
| вход #1 | `r7=0xFFFFFFFF`, `sp=0x40060FF8`, стек `08400000 02000000 …` | `r7=0x400B2CCC`, `sp=0x4005DFF8`, стек `00000000 00010000 00000003 …` |
| вход #2 | `r7=0x400B2CCC`, `sp=0x4005FFF8`, стек `00000000 00040000 00000001 …` | `r7=0xFFFFFFFF`, `sp=0x40060FF8`, стек `08400000 02000000 …` |

Кадры `08400000 02000000` и `00000000 000?0000 …` присутствуют **в обоих** прогонах —
поменяны местами два входа, идущие с разными `sp` (то есть с разных ядер). Отличается
также `00010000`/`00000003` против `00040000`/`00000001` в кадре, то есть одно ядро
получает другое сочетание «размер окна / счётчик».

**Вывод:** `0x40029F34` исполняется в обоих прогонах одним и тем же путём, но **на
разных ядрах и с разными параметрами окна**; расхождение — в порядке инициализации ядер
и в их параметрах, а не в отсутствующей записи таблицы. Это объясняет, почему прошлые
попытки «дописать L2» не помогали: запись делается позже и всё равно переписывается
своим ядром. Для цели (2) это означает, что снимать `satisfy_arm_boot_fault` можно
только вместе с выравниванием пофайловой инициализации ядер (что выходит за рамки трёх
подстановок, перечисленных в цели).

### 7.1.8 Раунд 8: WFE-подстановка и отсутствующий источник прерываний

Отдельная ветка работы — распарковка барьера и пробуждение кластера
(`Vita::run_slice`, флаги `barrier parked …` и `all cores asleep in WFE`). Замеры:

* Ядро моделирует WFE/SEV **правильно** (`arm_core.cpp`: WFE спит при
  `!event_pending_`, SEV вызывает `sev_hook`, который снимает `halted` со всех
  ожидающих ядер). То есть механика «разбудить кластер» в ядре есть.
* Но за весь прогон **ни одно прерывание не ассертится**:
  `ZLB_ARM_IRQ_LOG` не даёт ни одной строки, а состояние на конце —
  `Kermit.GIC idle pending=0 ack=0x3FF`, `Kermit.PT core0 timer=stop(0) wdt=stop(0)
  expiries=0`.
* KBL не программирует ни GIC, ни таймеры: трапы `ZLB_WTRAP` по
  `1E000000-1E000100` (дистрибьютор), `1E001000-1E002000` (cpu interface) и
  `1E000200-1E000220`/`1E000600-1E000620` (глобальный и приватные таймеры) **пусты**.

Отсюда: четыре ядра стоят в WFE, и разбудить их внутри модели нечем — ни SEV (последнее
ядро уже вышло из барьера), ни прерывания (источника нет). Подстановка
`run_slice` поэтому не «патчит сломанный WFE», а **подменяет отсутствующий источник
тика**: она прямо пишет в счётчик барьера (`0x4005C004+4`) значения, которые ждут
циклы (`4`/`0`). Чтобы снять её честно (пункт 3 цели), нужен реальный периодический
источник: `Kermit.PT`/`GlobalTimer` с включённым `irq_enable` и доставкой через
`GicCpuInterface` (интерфейс сейчас `idle`), после чего WFE проснётся от ассерта линии
— для этого достаточно, чтобы линия ассертилась, даже если IRQ замаскирован в CPSR
(ядро обязано выйти из WFE и перепроверить условие).

Проверено, что это именно отсутствующий источник, а не поломка WFE: механика SEV
измерена рабочей (см. выше), а состояние GIC/таймеров — `idle`/`stop` на протяжении
всего прогона. Дальше требуется определить, кто на железе тикает в этот момент
(свободно бегущий глобальный таймер или тик secure world) — в дампах этого нет, поэтому
следующий шаг начинается с проверки, включает ли таймер сам KBL в невоспроизведённой
ветке, либо тик приходит от syscon.

### 7.1.9 Раунд 9: тик реализован и измерен — одного тика не хватает

В модель добавлен честный тик (`Vita::run_slice`, `ZLB_KBL_WFE_TICK=1`):
`ArmCore::irq_hook` (новый хук: ассерт линии IRQ выводит ядро из WFE — на железе это
происходит до проверки маски CPSR) плюс драйвер, который при простое кластера
(64 слайса без единой вышедшей инструкции) поднимает `PPI 29` и уведомляет ядра.
Измерено:

| путь | результат |
|---|---|
| тик (`ZLB_KBL_WFE_TICK=1`) | ядра **просыпаются** (`timer tick 1: cluster idle for 64 slices, raising PPI 29`), но цикл не сходится: `pc=0x4003A01C`, 11 252 083 инструкции, **чекпойнт `0x88`** |
| старый движок (по умолчанию) | `barrier parked … 0x4003B3D6/0x4003B3C8`, запись счётчика `4`/`0` + пробуждение → `pc=51000D0C`, 50 473 211 инструкций, **`0xA9`** (NSKBL) |

То есть одного тика недостаточно: с ним кластер просыпается, перепроверяет условие и
снова засыпает, а прогресс даёт **запись счётчика**. Значит в теле цикла барьера
чего-то не хватает — не пробуждения, а самого изменения счётчика, которое на железе
делает одно из ядер. Это отдельный и более глубокий пункт, чем «доставить прерывание»
(формулировка цели 3): цикл барьера не сходится даже когда прерывание доставлено.

Поэтому по умолчанию оставлен прежний движок (иначе теряется `0xA9` и 11 828 сайтов
покрытия), а тик включается флагом `ZLB_KBL_WFE_TICK=1` — состояние измеряется и оба
пути воспроизводимы одной переменной. Следующий шаг: разобрать тело `0x4003B384`
(счётчик `0x4005C008`, фазы «приход/уход») и найти, какая запись/чтение в нём зависит от
модели и почему без посторонней записи счётчик остаётся в состоянии, которое цикл не
принимает.

### 7.1.10 Раунд 10: отказ по VA `0x34` — настоящий промах гостевых таблиц

`ZLB_ARM_FAULT_LOG=1` расширен снимком таблиц (`TTBCR`, первый и второй уровень для
отказавшего VA). Честный прогон даёт однозначную картину:

```
VA=0x00000034 read pc=0x4002F078 sctlr=0x20005805 M=1
ttbr0=0x40108000 ttbr1=0x4010C04A ttbcr=0x2
L1=0x40101181  L2=0x00000000
```

То есть: MMU включён, `TTBCR=2` (для VA < 0x40000000 выбран TTBR0), первый уровень —
**валидная coarse-таблица** `L1[0x000]=0x40101181`, а второй уровень для страницы
VA `0x00000` — **ноль**. Гостевые таблицы действительно не описывают эту страницу, и
чтение `0x4002F074` падает настоящим промахом трансляции, а не из-за модели. Это
закрывает вопрос «одинаковы ли таблицы в обоих прогонах»: в честном прогоне страница не
описана гостём, и любой «дописывающий» костыль только маскирует это.

Одновременно доказано, что `0x4002F074` в подстановочном прогоне **не** исполняется на
этом пути (кольца на `0x4002F074` показывают только возвраты из предыдущего вызова;
все шесть посещений `0x40030D1C` приходятся на другие ветки) — то есть подстановки
уводят поток мимо этого чтения, а не «удовлетворяют» его.

Итог для цели (2): чтобы снять `satisfy_arm_boot_fault`, нужно не описывать страницу за
гостя, а воспроизвести путь, на котором загрузчик доходит до записи окна
(`0x4002DBD0`/`0x40029F34`) **до** этого чтения — то есть повторить порядок
инициализации ядер и их параметры (раунд 7) — либо найти, какая ветка KBL обязана
исполняться вместо текущей.

### 7.1.11 Раунд 11: тик против счётчика — точное сравнение

Замеры двух путей при одной и той же длине прогона (`--stage kbl`, `runm 200000`):

| путь | GPO |
|---|---|
| по умолчанию (счётчик барьера) | `0xA9` — NSKBL: kernel pre-init done |
| `ZLB_KBL_WFE_TICK=1` (таймерный тик) | `0x49` — second loader: loading kernel_boot_loader.self |
| `ZLB_KBL_WFE_TICK=1` в последовательности `boot` + `runm 200000` + `boot` | `0x88` — secure kernel bootloader: boot setup complete |

То есть в честной последовательности тик доводит загрузчик только до `0x88`
(«boot setup complete», перед загрузкой secure kernel) и дальше кластер стоит:
ядра просыпаются от тика, снова проверяют условие и снова уходят в WFE, а счётчик
барьера при этом не меняется. Счётчикная ветка доходит до `0xA9`.

Это подтверждает вывод прошлого раздела: **тик — необходимое, но не достаточное
условие**. Пробуждение от прерывания в модели теперь есть и проверено
(`ArmCore::irq_hook`, `PPI 29`), но прогресс барьера даёт именно изменение счётчика,
которое на железе выполняет одно из ядер в теле `0x4003B384`; пробуждённые ядра лишь
перечитывают `[r4+4]` (`0x4003B3D6`) и `[r4+8]`, не меняя их.

Оба состояния воспроизводимы одной переменной (`ZLB_KBL_WFE_TICK=1`), значение по
умолчанию оставлено прежним, чтобы не терять `0xA9` и 11 828 сайтов покрытия ARM.

### 7.1.12 Раунд 12: сколько именно мешает тик и что реально двигает барьер

В отчёт `boot` добавлена строка `WFE: ticks=… irq_wakeups=… counter_patches=…
cluster_wakeups=…`, чтобы два пути сравнивались числами. Замеры (`--stage kbl`,
`runm 200000`, подстановки включены):

| путь | ARM | WFE | GPO |
|---|---|---|---|
| счётчик (по умолчанию) | `pc=51000D0C`, 51 154 683 | patches=23, wakeups=8 | **`0xA9`** |
| тик 64 слайса | `pc=4003A01C`, 11 252 657 | ticks=2402, irq_wakeups=9608 | `0x49` |
| тик 512 | `pc=4003A01C`, 11 223 285 | ticks=304, irq_wakeups=1216 | `0x49` |
| тик 2048 | `pc=4003A01C`, 11 220 093 | ticks=76, irq_wakeups=304 | `0x49` |
| тик 8192 | `pc=4003A01C`, 11 219 295 | ticks=19, irq_wakeups=76 | `0x49` |

Два независимых вывода:

1. **Тик помогает при любой частоте одинаково — никак.** От 19 до 2402 тиков дают один
   и тот же `0x49` и один и тот же PC: ядра просыпаются, перепроверяют условие и снова
   засыпают. То есть пробуждение по прерыванию (реализовано и проверено) не является
   тем звеном, которого не хватает циклу.
2. **Реально двигают барьер ровно 8 «парковок»** (`barrier parked`: 5× `0x4003B3D6`
   `want=0` и 3× `0x4003B3C8` `want=4`; `counter_patches=23` — это записи по всем
   ядрам). Последовательности записей счётчика при этом совпадают у обоих путей
   **побайтово до последней записи тик-прогона** (151 из 151), то есть сам барьер в
   тик-режиме исполняется так же и просто не получает внешней записи, которая выводит
   его из тупика.

Отсюда точная постановка для пункта 3: нужно не «доставить прерывание» (сделано), а
найти **алгоритмическую причину**, по которой цикл `0x4003B3D6`/`0x4003B3C8` не
сходится сам — то есть какое ядро и на каком шаге должно изменить `[0x4005C004+4]`/
`+8`. Восемь парковок в счётчиковом режиме — это места, где модель подставляет запись
вместо невоспроизведённого шага; их и надо объяснить. Флаг
`ZLB_KBL_WFE_TICK_SLICES=<n>` оставлен, чтобы период тика был измеримым параметром.

## 8. Проверено и опровергнуто

1. «Пустая таблица — следствие отсутствующего boot-info в r0..r3» → KBL сам читает MPIDR и строит карту в `.bss`, r0..r3 = 0 корректны; причина — декодер Thumb-2 и ветка `0x400212AC`.
2. «Порядок MMU → векторы → SC/eMMC» → артефакт сломанного декодера; порядок SC/SDIF/eMMC, MMU позже (`0x400215A2`/`0x400215BE`).
3. «TTBR0 целиком fault, в TTBR1 только индекс 0, L2 — 4 записи» → дампы из зацикленного грязного прогона; после правок `L1[0] = 0x80200181`, `L2[0..7]`.

6. «Сканируемые блоки генерируются шифром из состояния сессии (`0x46AB8`)» → загрузчик читает слот 192 (блок `0x2C0`).

11. «Первое чтение NVS даёт версию 1, второе — 3» → валидатор (`0x48EFA`) читает второе чтение; верная последовательность — две выдачи 1, затем 3.
12. «Отказ второй стадии — `HALTED: sleep instruction`» → `sleep; bra` (`0x5FF1C`) — штатный idle/вызов сервиса (`$1..$5`, `jmp 0x5FF00`).

## 9. Текущая стена

Эталон: `zeliboba.exe -q --stage kbl -ex "runm 200000" -ex "core arm" -ex "regs" -ex "quit"`; работает только `runm` (`satisfy_arm_boot_pc` — только из `Vita::run_slice`, `vita.cpp:454`; `Debugger::run` крутит `step(1)`).

* **Раунд 140, барьер `0x4003B384` и общий стек.** Вторичные ядра arm1/2/3 делят стек (`SP = 0x3F00`), а барьер хранит «old» в `[sp+6]` (`strh.w r1,[sp,#6]` `0x4003B3AE`, чтение `0x4003B3BA`); при round-robin слот затирается, лидер (old == 4) читал чужое old == 2 и уходил в фазу 1 вместо сброса счётчика; в дампе `R3 = {1,2,2,2}` вместо `{4,3,2,1}`. Фикс: декремент (`0x4003B3A6`) запоминает `barrier_old_[core]`, подстановка на `0x4003B3BA` переигрывает значение в `r3`. Результат: барьеры `0x4005C004`/`0x4005C00C` релизятся чисто (счётчик 4, core_slot 4), прогон идёт дальше (кэш страниц раздела, heap-маршрутизация `0x4B656353 → 0x5900`, low-kernel mapping `VA 0x00100010`, восстановление векторов `PA 0x40000100`). Попытка сделать WFE блокирующим (event-регистр на ядро, SEV всем четырём) **зависла**: все 4 ядра спали на WFE (`pc=0x4003A01C`), никто не слал SEV.
* **Новый фронт (раунд 140).** arm0 ловит data abort `DFSR=0x807`, `DFAR=0x00100000` (чтение VA `0x100000`), уходит в обработчик abort'а KBL, оттуда — `undefined instruction 0xFFFFFFFF` на `0x2C`. Причина: `vpa 0x100000` → `L1[0x001] = 0x00000001` (coarse-таблица, база L2 = PA `0x0`), `L2[0x00]@0x0 = 0x00005340` (мусор, зеркало scratch CMeP): KBL сам перезаписал 1-МиБ секцию (подстановка раунда 110) своей coarse-таблицей на PA 0, но L2 не наполнил.
* **Раунд 141.** В `satisfy_arm_boot_fault` для VA `0x100000-0x3FFFFFFF`, если L1 — coarse (`bits[1:0] = 0b01`), патчится **L2-запись** (small page, `PA = 0x40000000 + VA`, attr `0x47E`) вместо секции: data abort ушёл, boot **52.9M → 153.9M** инструкций.
* **Раунд 142.** Добавлены 2 МиБ Scratchpad SRAM (`0x1C000000`) и 4 КиБ `Kermit.Null` (`0x1D000000`); карта исправлена, цикл бигнума не разомкнулся: **153 948 095** инструкций до и после маппинга, `runm 1` (256 ARM-инструкций) даёт то же состояние (период делит 256), `PC 0x4003CA74`, arm1/2/3 спят на WFE.
* **Раунд 143.** Post-indexed load/store без write-back ⇒ `strb r2,[r12],#1` в цикле `0x4003CA6C..0x4003CA78` не инкрементировал `r12` (`0x1C000001` не доходил до `r6 = 0x1C000002`). После фикса цикл разомкнут, но boot идёт **другим путём и падает раньше: 52.9M вместо 153.9M**: arm0 ловит section translation fault `DFSR=0x5`, `DFAR=0x65486470` на `ldr r3,[r3,#12]` (`0x40033FF2`), где `r3 = [r0+56] = 0x65486465`.
* **Раунд 144.** `0x65486465` = «edHe» — байты 12..15 строки `SceKernelFixedHeap32`, лежащей по PA `0x0` (туда `vmem 0x12000` резолвится через `L2[0x12] = 0x0000045F`). Поиск `65 64 48 65` в KBL — 11 вхождений (`0x4005B693` `0x4005B6AF` `0x4005B6C8` `0x4005B6D7` `0x4005B889`…). Дамп структуры по PA `0x0` (VA `0x12000`): строка `SceKernelFixedHeap32\0` (20 байт), далее `[+0x1C] = 0x9E9B`, `[+0x20] = 0x010041`, `[+0x28] = 2`, `[+0x2C] = 1`, `[+0x30] = 1`, `[+0x3C] = 0xD2519E9B` (magic). Функция `0x40033FD0` читает `r0 = [r4+40]` (r4 = `0x12000` → `[0x28] = 2`), затем `r3 = [r0+56]` — по замыслу там **указатель**, а не строка/хеш.
* **Раунд 146.** Трап `ZLB_WTRAP=28-2C` — история поля `[0x28]` (= `[this+40]` в методе `0x40033FC8`): (1) `0x01131000` — указатель (pc `0x4002B0F8`); (2) `0` — конструктор `0x40033F12` зануляет `+8..+44` и ставит magic `0xDFB73368` в `+60`, затем `[r4] = r3`; (3) `0x6400` (pc `0x4002F53E`); (4) `0` (pc `0x4002A710`); (5) `2` — флаги (pc `0x4002F104`: `[r3+8] = (arg3&0xF) | (old&~0xF)`). Итог: после зануления конструктором **указатель аллокатора в `[+0x28]` никогда не перезаписывается** — каскад `2 → [0x3A] = 0 → [0xC] = «edHe» → section translation fault`.
* **Точка стены.** arm0 на section translation fault `DFSR=0x5`, `DFAR=0x65486470` / `ldr r3,[r3,#12]` `0x40033FF2`; дескриптор класса по PA `0x0` (VA `0x12000`) заполнен моделью частично (строка имени + magic), поле-указатель `[+56]` не проинициализировано; незаполнимо и `[+0x28]` (раунд 146).
* **Тесты.** Последняя измеренная база — **415/0** (после фикса write-back), `verify.ps1` — все шаги ok; ранее 210/15/22 → 211/15/22 → 235/15/22 → 354/15 → 405/19 → 413/0.
* **Поздняя поправка (раунды 155-157, по `src/machine/bootchain.cpp` и `docs/NSKBL.md` §7.1-7.4).** Три младших окна (`L2[0x10] = L2[0x12] = L2[0x14] = 0x45F`, VA `0x10000`/`0x12000`/`0x14000`) ведут на одну физическую страницу 0, из-за чего класс-дескрипторы, heap-объект и узлы региона накладываются. Разделение **только VA `0x12000`** пускает загрузчик за стену: чекпойнт `0x8A` вместо `0x87`, трансляций `2.0M → 17.8M`; разделение всех трёх хуже. Запись карты `0x400B2B30` с `vbase 0x12000` и `pbase 0` — причина; какая страница правильная, открыто. После этого стена инициализации менеджера объектов **снята**, NSKBL доходит до чекпойнта `0xA9` («kernel pre-init done, before first external load»).

## 10. Что осталось сделать

* Найти, кто на железе заполняет `[+0x38]` (указатель) дескриптора класса, и воспроизвести в подстановке (раунд 144).
* Найти код, который **после** конструктора пишет указатель аллокатора в `[+0x28]` (вероятно, регистрация класса через `0x4003128C`) — то же «пустое звено» менеджера объектов/реестра (раунд 146).
* Определить правильную физическую страницу для окна VA `0x12000` (поле записи карты `0x400B2B30` или страница, которую загрузчик должен был выделить) — открыто с раунда 156.
* Продолжить цепочку после чекпойнта `0xA9` NSKBL (первая внешняя загрузка) — см. `docs/NSKBL.md`.
