# NSKBL — Non-Secure Kernel Boot Loader (прошивка 1.04)

Документ описывает небезопасный загрузчик ядра: откуда он берётся в дампе 1.04,
чем распаковывается, как модель его запускает и где следующая стена. Общая
картина цепочки — `docs/BOOT.md` и `docs/STATUS.md`, журнал по ARM-половине —
`docs/KBL.md`, по Syscon/DRAM — `docs/SYSCON.md`.

Обозначения статуса фактов: **[В]** — проверено на дампе/в модели, **[Р]** —
вывод из разбора, **[М]** — модель/подстановка.

---

## 1. Где лежит NSKBL

`kernel_boot_loader.self` (355 220 байт, eMMC SLB2) состоит из пяти сегментов;
все, кроме нулевого, зашифрованы AES-128-CTR по метаданным SELF (`self_to_elf()`
их расшифровывает):

| # | paddr | filesz | что это | [В] |
|---|---|---|---|---|
| 0 | 0 | 0xD4 | PT_NULL/метаданные, `SecureBool UNUSED` | да |
| 1 | 0 | 0xC0 | таблица векторов ARM (`ldr pc,[pc,#0x18]` ×8 + указатели) | да |
| 2 | 0x40020000 | 0x3BFE0 | SKBL — код secure kernel bootloader'а (Thumb-2 + ARM) | да |
| 3 | 0x4005C000 | 0xF0 | данные SKBL (`.data`, memsz 0x5706C) | да |
| 4 | **0x50000000** | 0x194CF | **ARZL-поток NSKBL** | да |

Первый байт сегмента 4 — `41 52 5A 4C` (`"ARZL"`), то есть ровно то, о чём
говорит вики: SKBL кладёт **сжатый** NSKBL по физическому `0x50000000`,
распаковывает его в `0x51000000` и передаёт туда управление в Non-Secure
состоянии.

В `.text` SKBL есть **второй** ARZL-поток (paddr `0x4003DF14`, 123 084 байта) —
это **TrustZone-ядро**: в нём строки `SceSysmemForTZS`, `SceDipswForTZS`,
`SceUartForTZS` и нет ни `Kernel Boot Loader`, ни `psp2bootconfig`. То есть
раскладка ровно как в викиной Boot Sequence: сначала ARZL-TrustZone, потом
ARZL-NSKBL. **[В]**

## 2. Формат ARZL

`ARZL` (в потоке — big-endian `LZRA`) описан на вики: `magic[4]`, затем байт
флагов и четыре байта `ctrl`; кодек — range-кодер с LZ-копиями (минимум 2
байта, максимум 0xFF, длина 0x100 = конец потока), поверх которых applied ARM
filter — перестановка бит в словах, которые попадают под маску `0xF800F800`
(это кодировка Thumb BL/BLX, поэтому фильтр фактически «доводит» смещения
вызовов). Флаги нашего потока — `0x16` (сжатый, `ctrl = C8 F8 F2 73`).

Готовой реализации в проекте не было; в воркспейсе лежит декомпиляция
процедуры распаковки — `pup_fiction/unarzl/unarzl.c` (`arzl_decompress` +
`arzl_deobfuscate`). Она использовалась как оракул (**[М]**).

**Выбор версии ARM-фильтра.** В `unarzl` версия фильтра задаётся вручную; для
проверки были собраны варианты 0/1/2 и «без фильтра», а также порт старого
байтового фильтра из вики. Критерий: доля целей Thumb-BL/BLX, попадающих внутрь
самого образа (0x51000000..0x5102B08C):

| вариант | вызовов найдено | внутрь образа |
|---|---|---|
| без фильтра | 3306 | 69.4 % |
| **версия 0** | 3306 | **94.4 %** |
| версия 1 | 3306 | 53.4 % |
| версия 2 | 3306 | 94.4 % |
| старый (порт из вики) | 656 | 74.2 % (и рвёт поток инструкций) |

Версия 2 отличается от 0 только правилом «поменять местами полубайты» — и
именно оно ломает `movt r3,#0xE20A` в писателе GPO-чекпойнта (получается
`movt r14,#0x320A`, испорченный LR и дикий прыжок). Версия 0 даёт корректный
`movt r3,0xE20A` и корректный чекпойнт. **[В]**

## 3. Декодер и фильтр — в самом KBL

Искать реализацию в модели не нужно: **SKBL распаковывает NSKBL своим же
кодом**, и обе процедуры есть в нашем дампе (ARM-режим, найдены по возврату
`0x80560201`/`0x80560200` — кодам ошибок из `unarzl`):

| функция | адрес в 1.04 | подпись |
|---|---|---|
| `sceArlzDecode` | **0x4003C330** | `int (void *dst, unsigned dst_max, const void *src, void **dst_end)` |
| `sceArlzArmFilter` | **0x4003CB40** | `int (void *data, unsigned size, unsigned version)` |

Место вызова в самом SKBL — `0x40020588`:

```
40020584  cbnz r0, 0x400205AE      ; blx 0x40039F88 = MPIDR & 0xF: распаковывает только ядро 0
40020586  mov  r3, r0              ; dst_end = NULL
40020588  mov.w r1, #0x1000000     ; 16 МиБ (KBP bootkernimg)
4002058C  ldr  r2, [pc, #320]      ; = 0x50000004 (поток сразу после "ARZL")
4002058E  mov.w r0, #0x51000000    ; цель распаковки
40020592  blx  0x4003C330          ; sceArlzDecode
40020596  mov  r2, r5              ; version = r5 = id ядра = 0
40020598  mov  r1, r0              ; size
4002059A  mov.w r0, #0x51000000
4002059E  blx  0x4003CB40          ; sceArlzArmFilter(0x51000000, size, 0)
400205B4  movs r0, #0x89           ; чекпойнт 0x89: "loading NSKBL"
400205BA  mov.w r0, #0x51000000
400205BE  blx  0x40021AE0          ; прыжок в NSKBL (после установки SCR.NS)
```

То есть **версия фильтра для NSKBL = 0**, и это не догадка модели, а аргумент
самого загрузчика (номер ядра: распаковкой занимается только ядро 0). **[В]**

## 4. Стадия `stage nskbl` в модели **[М]**

Холодный путь SKBL в модели до этого места не доходит (он стоит в инициализации
менеджера объектов — `docs/STATUS.md` §3), поэтому стадия вызывает **те же две
функции прошивки** на эмулируемом ядре:

1. `kernel_boot_loader.self` из eMMC/SLB2 (или из `Vita_104_Firmware/Out/SLB2`)
   грузится `load_image()` — сегменты ложатся по своим paddr, то есть сжатый
   NSKBL оказывается по `0x50000000`, а код декодера — по `0x40020000`;
2. `SceKblParam` строится и зеркалится в PA 0 (как при обычном отпускании ARM);
3. `Vita::arm_call(0x4003C330, {0x51000000, 0x1000000, 0x50000004, 0})` — вызов
   прошивочного декодера (AAPCS: r0..r3, временный стек в свободной DRAM,
   `lr` = часовой-адрес, по которому цикл шагов останавливается);
4. `Vita::arm_call(0x4003CB40, {0x51000000, size, 0})` — ARM-фильтр версии 0;
5. все четыре ядра переводятся в **Non-Secure** (`ns_ = true`, SCR.NS) и
   стартуют с `0x51000000`, MMU выключена, SVC — как в викином описании Reset.

Прогон (`--stage nskbl`):

```
[info] machine  firmware call 0x4003C330 returned r0=0x0002B08C after 20242228 steps
[info] machine  firmware call 0x4003CB40 returned r0=0x0002B08A after   901191 steps
[info] machine  NSKBL: ARZL 0x194CF bytes at PA 0x50000000 decoded to 0x2B08C bytes at 0x51000000
```

`0x2B08C` = 176 268 байт — ровно столько же даёт `unarzl` на том же потоке,
то есть модель и внешний декомпилированный декодер совпадают байт в байт.
`0x2B08A` — «фактический размер» из фильтра (он на 2 байта меньше; `unarzl`
пишет полный буфер, как и SKBL).

Дальше NSKBL реально исполняется: ставит стеки (`sp = 0x51030100` для ядра 0),
проходит свой pre-init и **рапортует первый документированный чекпойнт**:

```
zlb> bp arm 0x510008E2
zlb> runm 100
zlb> gpo
GPO raw=0x00A10000 checkpoint=0xA1 - NSKBL: core 0 (non-secure) pre-init complete
```

`0xA1` — это `movs r0,#0xA1; bl <писатель GPO>` на `0x510008DC`, то есть код
фирменного NSKBL, а не подстановка. Проверка закреплена самотестом
`machine_nskbl_stage_decodes_the_non_secure_loader` (вектор по `0x51000000`,
указатель `0x51000100`, строки `Starting PSP2 Kernel Boot Loader` и
`psp2bootconfig.skprx`, состояние четырёх ядер).

## 5. Следующая стена: SMC в монитор TrustZone

Сразу после чекпойнта NSKBL делает `blx 0x510002E0`:

```
510008E2  blx 0x510002E0
...
510002E0  movw r12, #0x103        ; номер secure-сервиса
510002E4  smc  #0                   ; -> монитор (MVBAR)
510002E8  bx   lr
```

Это `smc` в монитор, то есть вызов secure-мира. Монитор ставит SKBL; в модели
TrustZone нет (`MVBAR = 0`, secure-банки не заполнены), поэтому ядро уходит по
вектору монитора в низкую страницу, где модель положила векторы KBL, и
оказывается в панике загрузчика:

```
[warn] cpu      ARM Cortex-A9 halted: undefined instruction 0xF3FF8300 at 0x400219B0
arm0  pc=400219B4 HALTED Thumb MON non-secure   <- паника KBL
arm1..3 pc=510147DC                              <- вторичные ядра ждут ядро 0
```

То есть **NSKBL работает до первого secure-вызова**. Дальше нужно решать, что
делает монитор на номер `0x103` (и на следующие номера, которые NSKBL
запрашивает: сервисы вокруг `SceKblParam`, DIP-switch'ей и cold-boot-флагов).

## 6. Что дальше (по порядку)

1. **Смоделировать монитор/SMC.** Минимум — таблица secure-сервисов с номерами
   (`r12`) и аргументами `r0..r3`, отвечающая так, как это делает монитор SKBL:
   для `0x103` — вернуть ожидаемое NSKBL значение (сейчас неизвестно; искать по
   потребителю результата в `0x510008E6..`). Пока это подстановка, но она должна
   повторять *контракт* вызова, а не глушить NSKBL.
2. **Проверить адрес KBL Param, который читает NSKBL.** В образе NSKBL есть
   литерал `0x1F000000` (scratchpad) — то есть запись он берёт из SPAD32K, а не
   из secure DRAM `0x4001FD00`; адрес поля нужно уточнить по коду `boot()`.
3. **Довести `SceKblParam`** до полного набора полей (сейчас часть per-console
   полей нулевая — `docs/SYSCON.md` §8.15).
4. **eMMC/SDIF**: NSKBL поднимает eMMC заново и читает `os0:psp2bootconfig.skprx`
   — это первый выход на файловую систему (`os0`), см. `docs/EMMC.md`.

## 7. Запуск NSKBL «с самого начала»: что осталось

Цель — чтобы NSKBL запускался обычным прогоном (`boot` + `runm`), без команды
`stage nskbl`, то есть чтобы его распаковал сам SKBL на `0x40020588` и передал
управление на `0x51000000`. Состояние цепочки на раунде 154 (актуальное
состояние — в таблице ниже и в §7.2-7.4):

| Звено | Состояние | [В] |
|---|---|---|
| First loader (CMeP) | проходит полностью, рапортует SUCCESS, отдаёт управление на `0x40000` | да |
| Second loader, холодный путь | проходит: строит `SceKblParam`, поднимает SC, доходит до `jmp 0x5FF00` | да |
| Secure kernel (CMeP) | 117 083 инструкции, возврат в `0x40000`, затем ARM отпускается | да |
| ARM KBL (SKBL) | проходит всю стадию boot-setup: чекпойнты `0x88` → **`0x89`**, распаковывает NSKBL своим кодом и передаёт управление в Non-Secure на `0x51000000` (раунды 158-161, §7.5-7.7) | да |
| Распаковка NSKBL (`0x40020588`…`0x40020592`) | **выполняется**: `r3=0`, `r1=0x1000000`, `r2=0x50000004`, `r0=0x51000000` → `blx sceArlzDecode` → `sceArlzArmFilter` | да |
| NSKBL на `0x51000000` | **запускается естественным путём** (`trace pc=0x51000000 … from pc=0x40021AFC`, `SCR=0x5`) и рапортует **чекпойнт `0xA1`** | да |

Две стены SC-протокола, которые держали вторую стадию (раунд 154), сняты:

* `0xE31000C0` — регистр событий SC. CMeP ждёт в нём **ровно** `1`
  (`485E2 lw` / `485EC beqi $0,0x1`), ARM ждёт биты 3 и 4 (`4003C02E`,
  `4003C066`); раньше обе стороны получали маску ARM (`0x18`), и CMeP крутился в
  петле вечно. Теперь у CMeP свой бит 0 (сброс — 1, ack — запись 1).
* `0xE3101000` — «защёлка» статуса интерфейса: вторая стадия **пишет** в неё
  `0x0001000F` и опрашивает (`48516`), а позже пишет `0` и опрашивает ноль
  (`486BA`). Модель отдавала константу `0x0001000F` → петля на `0x486C2`.

Плюс окно `CMeP.SecureCtl` расширено до 128 КиБ (как у Ernie): вторая стадия
трогает `0xE3110C00` (`4864C`), которое в 64-КиБ окне было не отображено.

Оставалась **одна** стена — та, что описана в `docs/KBL.md` (раунды 143-150) и
`docs/STATUS.md` §3.2-3: инициализация менеджера объектов KBL. Симптом:
`ldr r3,[r3,#12]` на `0x40033FF2`, где `r3 = [r0+56] = 0x65486465` («edHe» —
фрагмент строки `SceKernelFixedHeap32`), то есть поле дескриптора класса
содержит строку вместо указателя. Разбор причины — в §7.1-7.3; после
разделения окна кучи эта стена **снята**, и дальше выяснилось, что путь вперёд
держала ещё и подстановка арены экземпляров (§7.5): с ней загрузчик не доходил
до чекпойнта `0x88`.

### 7.1 Что дал разбор стены (раунд 155)

* **Функция `0x400204A8` не вызывается ни одним `bl`/`blx`/`b.w`, но её адрес
  всё-таки материализуется в коде — и раунд 158 его нашёл.** Проверено тремя
  способами: (а) поиск 32-битного литерала `0x400204A8`/`0x400204A9` по всем
  образам воркспейса (KBL, `.seg01`, second_loader, secure_kernel, PUP-файлы,
  `dumps/`) — ни одного попадания; (б) полный перебор BL/BLX и B.W по всем
  halfword-смещениям KBL — ни одного; (в) поиск `movw`+`movt`-материализаций
  адреса. Третий сканер сначала был **сломан** (проверял фиксированный бит не в
  том halfword и не находил вообще ничего, включая заведомо существующие пары),
  после починки и проверки на контрольной паре `0x400204E6 → 0x40021BA5` вывод
  «нет ссылок» был признан подтверждённым — **и это было ошибкой**: сканер
  требовал, чтобы `movw` и `movt` стояли подряд, а в KBL они разнесены
  посторонней инструкцией. Реальная ссылка есть, и она ровно такая:

  ```
  400207F8  movw r1, #0x04A9
  400207FC  mov  r0, r4            ; аргумент стадии
  400207FE  movt r1, #0x4002       ; r1 = 0x400204A9
  40020802  ldr.w r2, [r6, #444]   ; r2 = стек стадии (0x1A140 на ядре 0)
  40020806  blx 0x4003A140         ; mov sp, r2 ; bx r1
  4002080A  b .                    ; стадия не должна возвращаться
  ```

  То есть путь к распаковке NSKBL всё-таки статический, а вывод §7.1 о
  «недостижимости» снят. Трамплин `0x4003A140` — тонкая ARM-обёртка
  (`mov r13, r2` / `0x4003A144 bx r1`), которая переключает стек и передаёт
  управление thumb-функции.
* **Стену строит сам KBL, а не подстановки.** Отладчик показывает, что до
  падения KBL успевает собрать свою карту памяти (`0x400B2B30`: записи вида
  `{pbase, psize, vbase, vsize}` — таблицы страниц `0x40108000`/`0x4010C000`,
  окно `0x40100000`), список классов по глобалу `0x400B291C` (там семь
  указателей: `0x6580, 0x6380, 0x5380, 0x5340, 0x5F00, 0x5F40, 0x6280`) и
  объекты в низком окне (`0x51C0` — раздел, `0x5900` — куча, `0x6400` —
  менеджер). Ошибка возникает уже в этих структурах: вызов метода
  `0x40033FC8` приходит с `this = 0x12000`, у которого `[this+40] = 2`, а код
  читает это поле как указатель (`ldr r0,[r4,#40]` → `ldr r3,[r0,#56]` →
  `ldr r3,[r3,#12]`).
* **Три низких окна отображены на одну физическую страницу.** Трап записей в
  таблицу `0x40101000` показал, что записи `L2[0x10]`, `L2[0x12]` и `L2[0x14]`
  (VA `0x10000`, `0x12000`, `0x14000`) получают один и тот же дескриптор
  `0x45F`, то есть **базу PA 0**. Пишет их сам загрузчик через хелпер
  `0x4003AD40` (`str r3,[r5,r4,lsl #2]`), а физическую страницу он берёт из
  `0x4003223C` (`ldr r0,[r0]; lsls r0,r0,#12` — «номер страницы → адрес»), то
  есть номер страницы в его структуре равен нулю. Через эти окна KBL пишет свои
  объекты (трап: `0x4002AD5C` пишет `0x4000` по PA `0x0`, `0x4002B0F8` пишет
  `0x01131000` по PA `0x8`), поэтому класс-дескрипторы, куча и узлы дерева
  оказываются наложенными друг на друга.
* **Эксперимент с разделением окон не помог.** Диагностический ключ
  `ZLB_KBL_LOWALIAS=1` (см. `Vita::satisfy_arm_boot_pc`) выдаёт каждому из трёх
  окон отдельную страницу DRAM. Результат *хуже* базового: загрузчик
  останавливается на чекпойнте `0x84` вместо `0x86/0x87`, а arm0 застревает на
  `0x4003A01C` с выключенным MMU. Значит, выравнивание на одну страницу — не
  побочный эффект ошибки, а осознанная схема (в терминах вики это
  `KBPMappingInfo.extraHigh`: одна физическая страница, несколько виртуальных
  окон), и корень стены — не в самих окнах, а в том, что KBL **пишет объекты
  через них**. Ключ оставлен выключенным как готовый инструмент для следующего
  раунда: он проверяет гипотезу «объекты должны жить в DRAM, а не в этих окнах».
* **Boot-контекст приходит, но пустой.** На точке останова `0x40020000` (первая
  инструкция KBL) зеркало PA 0 содержит ровно то, что оставила вторая стадия:
  заглушку векторов (`0x00..0x3F`), `SceKblParam` по `+0x100`
  (`01 00 00 01` = version 1 + size 0x100, boot-флаги `0xFF00FFFF` в `+0x130`),
  и нули во всём остальном. Источник, который печатает `bootctx`
  (`DRAM 0x40000000`), — полностью нулевой.

**Следующий шаг (конкретный вопрос).** Куча (`VA 0x5900`, magic `0xFD9B28A6`)
ссылается полем `+0x38` на объект `VA 0x12000`, а код поиска блока по UID
(`0x4002F00C`)
```
4002F032  ldr  r3, [r6, #56]      ; heap->[0x38] = 0x12000
4002F034  ldr  r0, [r3, #16]      ; [0x12000+0x10] -> таблица блоков
4002F036  ldr.w r4, [r0, r4, lsl #2]   ; base = table[index]
```

читает у этого объекта `+0x10` как **указатель на таблицу блоков** — но в
`0x12000..0x12013` лежит inline-имя класса `SceKernelFixedHeap32`, то есть
`+0x10` попадает внутрь строки. Значит либо `heap+0x38` должен указывать на
другой объект (таблицу блоков, а не класс-дескриптор), либо объект по `0x12000`
должен быть другим. Ответ ищется по тому, кто пишет `0x12000+0x38` (куча) и что
KBL кладёт в `0x12000` (`ZLB_WTRAP=0-2FF`, писатели `0x4002AD5C`, `0x4002B0F8`,
`0x40033F00`, `0x4002F0F6`).

### 7.2 Стена снята: окно `VA 0x12000` делит страницу с класс-дескрипторами (раунд 156)

Ответ на вопрос §7.1 найден, и он подтверждён экспериментом.

* **Кто даёт `0x12000` куче.** Конструктор кучи `0x40031AC8` пишет
  `heap+0x38 = heap+0x3C = r3` (аргумент 4), а его вызывает обёртка
  `SceKernelFixedHeapInit` (`0x40031BC0`), которая берёт это значение из
  `[r13,#48]` — то есть аргумент 6 **своего** вызывающего, а тот, в свою
  очередь, читает его из карты памяти KBL: у `SceSysmem`-инициализации
  (`0x40031D58`) `r10 = [0x400B2B30 + 0x100]`, а второй вызов
  (`0x40031E3C`) передаёт `[0x400B2B30 + 0x118]`. В дампе карты по `+0x118`
  лежит запись `{..., vbase = 0x12000, psize = 0x1000, vsize = 0x2000}` — то
  есть **`heap+0x38` — это виртуальная база окна кучи**, а не «указатель на
  таблицу». Дальше код `0x4002F00C` читает по этой базе `+0x10` как таблицу
  блоков — и попадает в inline-имя класса, потому что по этому же физическому
  адресу лежат класс-дескрипторы.
* **Эксперимент.** Ключ `ZLB_KBL_LOWALIAS` теперь принимает список индексов L2:
  * `10`, `14` — без изменений (чекпойнт `0x87`, падение на `0x40033FF2`);
  * **`12` — стена снята**: чекпойнт `0x8A` вместо `0x87`, число обходов
    таблиц 2.0M → 17.8M, падение переезжает на `0x40031674`
    (`DFAR = 0xD2519EF4`, обработчик undef).
  То есть губит загрузчик именно наложение **окна кучи** (`0x12000`) на
  страницу, где живут класс-дескрипторы (их имена начинаются с `0x12000`), а
  окна `0x10000`/`0x14000` можно оставить как есть.
* **Новая стена.** С разделённым окном KBL доходит до `0x40031674`, где в
  качестве указателя используется константа `0xD2519E9B` — magic класса
  (в `r3`/`r1` на входе undef-обработчика `0x40020344`, `LR = 0x40031678`), и
  уходит в обработчик неопределённой инструкции (`0x40021998` → чекпойнт `0x8A`
  → `b .`). Это следующий узел того же класса: «поле объекта содержит magic
  вместо указателя».

**Что осталось выяснить по окну.** Карта памяти KBL сама содержит запись с
`vbase = 0x12000` и, судя по полям, `pbase = 0`. Либо это поле испорчено (и
загрузчик должен был положить туда выделенную страницу DRAM), либо окно
действительно алиасит физическую страницу 0 — но тогда `heap+0x38` не может
использоваться как указатель на таблицу блоков. Разрешение этого вопроса и есть
следующий шаг: либо исправить `pbase` в карте, либо (если алиас настоящий)
найти, где загрузчик должен был положить таблицу блоков кучи.

### 7.3 Откуда берётся физическая страница окна (раунд 157)

Ответ найден, и он объясняет, почему «нулевые» страницы вообще возникают.

* **Первое слово страницы, которую выдаёт раздел, — это её номер.** Цепочка для
  окна кучи (`SceKernelFixedHeapInit`, ветка `size == 0x1000`):
  ```
  40031BE4  bl 0x40032278        ; аллокатор раздела: r3 = &out (кадр heap-init)
  400322F4  str r3,[r6]          ; out = адрес выданного блока
  ...
  40031C32  ldr r0,[sp,#20]      ; r0 = этот блок
  40031C38  bl  0x4003223C       ; r0 = [r0] << 12  — то есть НОМЕР СТРАНИЦЫ
  40031C40  str r0,[sp]          ; 5-й аргумент map_page
  40031C4C  bl  0x4003AD40       ; L2[VA>>12] = attrs | PA
  ```
  То есть блок, который раздел отдаёт из кэша, в первом слове несёт **свой
  физический номер страницы**, и именно он становится базой окна.
* **Подстановка модели этот номер затирала.** `supply_kbl_partition_block`
  засевала кэш страниц и обнуляла каждую страницу («чтобы объекты, которые
  строит загрузчик, были чистыми»), поэтому `[block] << 12` давало **PA 0** для
  всех трёх низких окон (`0x10000`, `0x12000`, `0x14000`) — а на PA 0 лежит
  scratch с boot-контекстом и **класс-дескрипторы** (`SceKernelFixedHeap32` и
  остальные, с inline-именами). Отсюда и наложение из §7.2.
* **Попытка записать настоящие номера страниц делает хуже.** Ключ
  `ZLB_KBL_PAGENUM=1` пишет в первое слово страницы её номер: тогда все три окна
  получают *свои* страницы блоков и загрузчик останавливается раньше — чекпойнт
  `0x84` вместо `0x87` (`arm0` на `0x4003A01C`, MMU выключен). Значит окна
  `0x10000`/`0x14000` действительно должны смотреть на страницу 0 (там его
  класс-дескрипторы), а разделять нужно только окно кучи — что и подтвердил
  эксперимент §7.2.
* **Что теперь по умолчанию.** Подстановка низких окон оставлена включённой и
  делит **только** окно кучи (`ZLB_KBL_LOWALIAS=12`, `0` выключает, `all` делит
  все три): прогон уходит дальше чекпойнта `0x87`, но `0x8A`, который он тогда
  рапортует, — это **паника** (см. §7.5), а не нормальный путь «resume
  0x1F000000»: до чекпойнта `0x88` дело тогда ещё не доходило.

### 7.4 Следующая стена: magic класса вместо указателя (раунд 157)

С разделённым окном кучи KBL идёт дальше и падает на `0x40031674`
(`DFSR = 5`, `DFAR = 0xD2519EF4`, `R3 = R4 = 0xD2519E9B` — magic класса):

```
40031654  push {r4-r11,lr}
4003165E  r4 = r0              ; «this» — сюда пришёл magic
4003166A  r3 = r4 + (core << 4)
40031674  str r0,[r3,#92]      ; запись по адресу magic+...
```

`0x40031654` — это метод, к которому ведут тонкие обёртки-стабы
(`0x400318E8`: `movs r1,#0; bl 0x40031654; pop`), а сами стабы вызываются из
`0x4002A4AE` (`bl 0x400318E8`, причём `this` берётся из **второго** аргумента
вызывающего: `mov r0,r1 / mov r1,r3`) и из `0x40033EB2`. То есть где-то выше по
цепочке поле, содержащее magic класса, используется как указатель на объект —
это следующий узел того же семейства и следующий шаг разбора.

### 7.5 Раунд 158: откуда берётся magic — и как подстановка модели держала
загрузчик *до* чекпойнта `0x88`

**Цепочка к magic найдена целиком** (трассировка `ZLB_KBL_TRACE_PC`, лимит
64 записи пришлось временно поднять — вызовов `0x40031654` за прогон ~16 400):

| pc | что делает |
|---|---|
| `0x4002F12E` | цикл аллокатора: `bl 0x4002F090(B, …)` на каждую страницу региона |
| `0x4002F090` | `r3 = [r0+0x38]`; `r1 = [r3+0x1C]`; `bl 0x4002A6E4` |
| `0x4002A6E4` | `r0 = r1` (то есть `this` = `[r3+0x1C]`), `bl 0x400318E8` |
| `0x400318E8` | `movs r1,#0`; `bl 0x40031654` |
| `0x40031654` | `r4 = r0`; `add r3,r4,core<<4`; `str r0,[r3,#0x5C]` → data abort |

Значения в момент падения: `obj = 0x6400` (объект в низком окне),
`[obj+0x38] = 0x0110B000`, `[[obj+0x38]+0x1C] = 0xD2519E9B`. Дамп `PA 0x4110B000`
(куда подстановка раунда 110 кладёт это VA) показывает **список 0x20-байтных
записей** с `+0x1C = 0xD2519E9B` в каждой — это ровно те объекты, которые
инициализирует сам `0x4002A6E4` (он и штампует подпись класса в `+0x1C`). То
есть «magic вместо указателя» — не порча памяти: `[obj+0x38]` указывает на
**страницу арены экземпляров**, а код читает поле подписи класса как указатель.

**Кто заполняет арену.** Подстановка раунда 108/114 (`ZLB_KBL_INSTANCE_BLOCK`):
геттер `0x4002C1AC` считает экземпляр как `[obj+0x14] + table[size_class]`, поле
`[obj+0x14]` в модели равно сентинелу `0xFFFFFFFF`, и подстановка писала туда
адрес выдуманной арены `VA 0x01100000` (1 МиБ, `PA 0x41100000`).

**Это и была стена.** С выключенной подстановкой
(`ZLB_KBL_INSTANCE_BLOCK=0`) загрузчик больше не попадает в `0x40031674`:
он **входит в свою настоящую стадию boot-setup `0x400204A8` на всех четырёх
ядрах** и рапортует чекпойнт `0x88` (было `0x87`). Поэтому подстановка теперь
**по умолчанию выключена** (`ZLB_KBL_INSTANCE_BLOCK=1` возвращает раунд 114).

**Как вызывается `0x400204A8`.** Статически на него нет ни одной ссылки (§7.1) —
вызов идёт через ARM-трамплин `0x4003A140` (`mov r13, r2` / `0x4003A144 bx r1`):

```
trace pc=0x400204A8 arm0 from pc=0x4003A144 lr=0x4002080B
      r0=0x400B2B30 r1=0x400204A9 r2=0x0001A140 r3=0
      (arm1/2/3: r2=0x4000, r3=3/2/1, остальное так же)
```

То есть `r1 = 0x400204A9` — не таблица, а литерал в коде (см. поправку в §7.1:
`movw`/`movt` на `0x400207F8`/`0x400207FE`), а `r2` задаёт **новый стек**
(`0x1A140` для ядра 0). На этом стеке, по адресу `0x1A13C`, KBL сам кладёт
возврат `0x4002080B` — то есть стадия должна вернуться в `0x40020806`, хотя
сразу за `blx` там стоит `b .` (стадия задумана как «запустить и не
возвращаться»).

**Следующая стена (после `0x88`).** Ядро умирает на выходе из функции внутри
стадии:

```
40021C48  add sp, #12
40021C4A  pop {r4-r7, r15}      ; SP = 0x1A040: r4 = 0x00200000, r5-r7 = 0,
                                ;             pc = [0x1A050] = 0
```

Слот возврата в кадре равен нулю, поэтому `pc = 0` — ядро уезжает в низкое окно
(сейчас там уже не вектор-страница SKBL, а данные KBL: `[VA 0] = 0x4010047E`),
исполняет мусор и в итоге останавливается на `0x40021998` — писателе чекпойнта
`0x8A`. Отсюда важный вывод для чтения чекпойнтов: **`0x8A` в нашем прогоне —
это паника `0x40021998` (`movs r0,#0x8A; bl gpo; b .`), а не код «resuming
context at 0x1F000000»**, и достигается он исполнением мусора; «прогресс до
`0x8A`» из раундов 156-157 так читать нельзя.

Что уже известно про этот кадр (трассировка `ZLB_PCTRAP=40020000-40022000`):

* верх стека стадии KBL заполняет сам — `[0x1A13C] = 0x4002080B`, а кадр самой
  стадии лежит в `0x1A074 = 0x400204F7`, то есть раскладка «стадия → её вызовы»
  правильная;
* плохой кадр — у **вложенного** вызова: `SP = 0x1A040`, PC берётся из
  `[0x1A050]`, там `0`, а рядом лежат правдоподобные значения
  (`[0x1A054] = 0x40021C79` — возврат внутрь той же функции);
* перед падением ядро идёт по `0x40021B04` (`push.w {r4-r10,lr}`, цикл обхода
  списка `ldr.w r7,[r6,#8]!` / `cmp r7,#0` / `bne`) и входит в `0x40021BB4`
  падением с `pc=0x40021BB0` (то есть продолжением, а не вызовом), с
  `r0 = 0x400B2B30`, `r1 = 0`, `r2 = 0x4003BAAD` (похоже на указатель на
  консольный вывод), `r3 = 0x40037515`.

Следующий шаг: понять, какой именно вложенный вызов должен вернуться по
ненулевому адресу, и какая подстановка оставляет его слот пустым (кандидаты —
список, который обходит `0x40021B04`, и таблица указателей, откуда берутся
`r2`/`r3`).

### 7.6 Раунды 159-160: стадия доведена до распаковки NSKBL и до передачи в NS

Ответ на предыдущий вопрос оказался **багом ядра ARM, а не подстановкой**.

**159. `ldmia sp!, {…,pc}` не делал write-back.** Трассировка `ZLB_PCTRAP` по
стадии показала: `SP = 0x1A058` на `0x40021C74` (перед `blx 0x4003C330`) и
`SP = 0x1A034` сразу после возврата — ровно `0x24` (36 байт) потеряно. В
`0x4003C330` (ARM-код) пролог `push {r4-r11,lr}` (9 регистров = 36 байт) и
эпилог:

```
4003C47C  add sp, sp, #0xC4
4003C480  add sp, sp, #0xC00
4003C484  pop {r4-r11, pc}      ; = ldmia sp!, {r4-r11, pc}
```

`execute_arm_block_transfer` ветвился на `pc` в списке **до** применения
write-back (`if (w && rn != 15) r[rn] = new_base;` стоял ниже), поэтому `sp` не
возвращался на 36 байт. Дальше стадия читала свой кадр на 36 байт ниже и её
`pop {r4-r7,pc}` (`0x40021C4A`) брал `0` → `pc = 0`. Починено в
`arm_core.cpp` (write-back выполняется и в ветке с `r15`), добавлен тест
`arm_ldm_with_pc_in_list_still_writes_back`.

**160. Кластер засыпал в WFE, и никто не мог его разбудить.** Следующая стена —
`0x4003A01C` (`wfe`+4) на всех четырёх ядрах: это цикл ожидания барьера
(`0x4003B3C4`: ждёт `[obj+4] == 4`; `0x4003B3D2`: ждёт `[obj+4] <= 0`).
`wfe` в модели блокирующий (раунд 140) и просыпается только по `sev`, а барьер
на железе будит **таймерное прерывание**, которого модель в спящее ядро не
доставляет. Плюс сам барьер изредка «зависает» на общем стеке вторичных ядер
(примечание раунда 140): после ~200 чистых кругов счётчик остаётся на `3` и все
четыре ядра паркуются в одном ожидании. В `Vita::run_slice` добавлен сторож:

* если **все** отпущенные ядра спят в `wfe` — разбудить кластер (эквивалент
  таймерного тика);
* перед этим каждому ждущему положить в `[r4+4]` то значение, которое проверяет
  именно его цикл (`4` для ожидания сбора, `0` для ожидания выхода).

Это подстановка в духе раундов 136-140, и она видна в логе
(`all cores asleep in WFE - waking the cluster`, `barrier parked (arm… waits for …)`).

**Что теперь проходит стадия.** С чекпойнта `0x88` KBL идёт дальше и
**сам** вызывает свой распаковщик:

```
40020586  mov  r3, r0            ; r3 = 0        (аргумент 4 = NULL)
40020588  mov.w r1, #0x1000000   ; размер
4002058A  ldr  r2, [pc, #320]    ; r2 = 0x50000004 (ARZL-поток NSKBL, "ARZL" виден)
4002058C  mov.w r0, #0x51000000  ; куда распаковывать
4002058E  blx  sceArlzDecode     ; 0x4003C330
4002059E  blx  0x4003CB40        ; sceArlzArmFilter
400205B4  movs r0, #0x89
400205B6  bl   <gpo>             ; чекпойнт 0x89 "secure kernel loaded, loading NSKBL"
400205BA  mov.w r0, #0x51000000
400205BE  blx  0x40021AE0        ; вход в Non-Secure
```

`0x40021AE0` — ARM-помощник: `cpsid if, #0x16` (Monitor), кладёт на стек
`0x93` и целевой адрес, ставит `SCR.NS = 1` (в логе `SCR = 0x5 -> non-secure
world at 40021AF8`) и возвращается по этому адресу уже в NS-мире.

**Новая стена: сам вход в NS.** После передачи ядра стоят в мусорных адресах:
`arm0 = 0x31C` с `CPSR = 0x10000000` (поле режима = 0, недопустимый режим),
`arm1 = 0x34`, `arm2 = 0x3EE4`, `arm3` — запарковано. При этом
`mem 0x51000000` показывает `18 F0 9F E5` (ARM-заглушки векторов), а источник
`mem 0x50000000` — `41 52 5A 4C` («ARZL»).

### 7.7 Раунд 161: вход в NS — RFE грузил PC и CPSR в обратном порядке

Трассировка самого помощника входа (`ZLB_PCTRAP=40021AC0-40021B10`) показала, что
KBL делает всё правильно, а ошибается ядро модели:

```
arm0 0x40021AE0  cpsid if, #0x16     ; Monitor, SP -> 0x400B4B10
arm0 0x40021AE4  movw r1, #0x93      ; CPSR цели: SVC (0x13), IRQ выключены, ARM
arm0 0x40021AE8  str r1, [sp, #-4]!  ; [sp+4] = 0x93
arm0 0x40021AEC  str r0, [sp, #-4]!  ; [sp]   = 0x51000000
arm0 0x40021AF0  mrc  p15,0,r1,c1,c1,0
arm0 0x40021AF4  orr  r1, r1, #1
arm0 0x40021AF8  mcr  p15,0,r1,c1,c1,0   ; SCR.NS = 1
arm0 0x40021AFC  rfeia sp!               ; 0xF8BD0A00
```

`decode_arm_rfe_srs` читал слова наоборот (`CPSR ← [addr]`, `PC ← [addr+4]`),
поэтому RFE клал в CPSR `0x51000000` (режим 0 — недопустимый) и прыгал на `0x93`;
ядро уезжало в низкое окно, и «стена входа в NS» была этим. Настоящее железо
грузит **PC из адресуемого слова, а CPSR — из следующего** (иначе этот код Sony
не работал бы вообще). Исправлено; тест `arm_rfe_restores_cpsr_and_pc`
переписан под этот порядок (SRS оставлен как был — в загрузке 1.04 он не
используется, а его пара с RFE требует отдельной проверки).

**Результат.** Обычный прогон (`boot` + `runm`), без команды `stage nskbl`:

```
trace pc=0x51000000 arm0 from pc=0x40021AFC lr=0 r0=0x51000000 ... SCR=0x5
GPO raw=0x00A10000 checkpoint=0xA1 - NSKBL: core 0 (non-secure) pre-init complete
```

То есть цепочка first_loader → second_loader → secure_kernel → ARM KBL → NSKBL
проходится целиком, NSKBL распакован **кодом самого KBL** и дошёл до первого
своего чекпойнта. Дальше NSKBL продолжает в Monitor-режиме
(`CPSR = 0x1D6`, `SCR = 0x5`, `pc = 0xD4CAD8`) — это уже следующий участок
(глава 5 про `smc`/MVBAR относится к нему же).

## 8. После `0xA1`: путь к модулям os0 (раунды 162-163)

Цель следующего этапа — `os0:psp2bootconfig.skprx`, `SceSysStateMgr` и загрузка
модулей ядра из `SceKernelBootimage`, а затем пользовательские модули `vs0` и
Live Area.

### 8.1 Раунд 162: `smc` из NSKBL не доходил до монитора

Первое состояние естественного прогона: arm0 уходил на `0xD4CAD8` (адрес вне
отображённой памяти, шина отдаёт `0xFFFFFFFF` → undefined → halt), arm1 стоял на
`0x2C`, arm2 — на `0x3EE0` (Thumb UDF `0x0000DEE4`), arm3 — запарковано на WFE.
Сайт `smc` в NSKBL (`0x510002E4`, `movw r12,#0x103; smc #0`) тогда не
достигался.

Найдены две причины, обе устранены в раундах 162-163:

1. **Мониторные векторы SKBL писались в занятую страницу.** Трап записей
   (`ZLB_WTRAP=40000140-40000160`) показал, что SKBL **строит** таблицу монитора
   в `PA 0x40000140` (заглушки `0xE59FF018` в `+0x148/+0x14C/+0x150/+0x158/+0x15C`),
   а также таблицу обработчиков исключений в `PA 0x40000120`
   (`{0x4002826C, 0x400288C4, 0x40028294, 0x400286C4, 0x40028460, 0x400282C4,
   0x400282DC, 0x40028308}`) и обработчик `smc` в `PA 0x40000168` (`0x4002831C`).
   Но `PA 0x40000000+` в модели занимал блок `Kermit.GIC` (окно 64 КиБ,
   `kermit::kScuBase = 0x40000000`), и `Bus::find_device` предпочитает устройство
   RAM — записи уходили в GIC, а в DRAM оставались нули (`map 0x40000140` →
   `device=Kermit.GIC`, `mem 0x40000140` → нули). Исправлено переносом
   MPCore-блока: `kermit::kScuBase = 0x1E000000`, окно DRAM осталось за
   `kermit::kDramWindowBase = 0x40000000`. После переноса `mem 0x40000100`
   показывает настоящую страницу SKBL (8 заглушек + таблица + монитор).
2. **NSKBL работает с выключенным MMU, и вектор монитора берётся физически.**
   Трассировка входа в NS: `SCTLR = 0x20005805` в момент `rfeia sp!`
   (`0x40021AFC`), а на `0x51000000` — тот же `0x20005805`, но уже на
   `0x51000138` NSKBL выполняет `mov r0,#0; bic ...; mcr p15,0,r0,c1,c0,0` и
   **сам** ставит `SCTLR = 0` (MMU off). Поэтому `smc` на `0x510002E4` берёт
   вектор по **физическому** `MVBAR = 0x16140`, а страница SKBL лежит по
   `PA 0x40000100` (её видно только через маппинг `VA 0x16100 → PA 0x40000100`
   при включённом MMU). В низкой странице `PA 0x16100` модель держала таблицу из
   ELF-сегмента KBL, у которой `+0x40..` — нули, поэтому ядро исполняло нулевую
   страницу (`ZLB_PCTRAP=16000-16400` показал 177 PC с `insn=00000000`,
   `lr=0x510002E8`, `CPSR=0x1D6`). Добавлена подстановка: при входе в векторное
   окно модель **зеркалит** страницу SKBL (`PA 0x40000100`, 0x100 байт) в ту
   страницу, которую реально читает MMU-off выборка.

### 8.2 Раунд 163: результат

После обоих исправлений естественный прогон (без `stage`) даёт:

```
GPO raw=0x00A40000 checkpoint=0xA4 - NSKBL: device buffer initialised
arm0  ARM Cortex-A9  pc=510147DC  SYS ARM  non-secure  mmu=off
```

То есть NSKBL проходит `0xA1` → `0xA2` → `0xA3` → **`0xA4`** и исполняет
**свой собственный код** по `0x5101xxxx` (раньше он уходил в мусор на первом же
`smc`). Сейчас arm0 спит в `wfe` в своём хелпере (`0x510147D8`; `r0 = 3`,
`r4 = 0x5102B000`, `r5 = 0x5102B006`), то есть ждёт события — по нумерации
чекпойнтов следующий шаг (`0xA5`) это «co-processor init, other cores start»,
и ждать он может именно **остальные ядра**.

### 8.3 Что делать дальше

* **arm1/arm2/arm3 не доходят до NSKBL**: они срываются ещё на стадии KBL
  (`0x2C` и `0x3EE0` — низкое окно, где лежит таблица указателей и мусор), а
  arm3 остаётся в барьере `0x4003A01C`. Без них `0xA5` («старт остальных ядер»)
  не наступит. Это следующая задача: провести вторичные ядра через стадию KBL.
  Что уже измерено: arm1 приходит в низкое окно с `LR = 0x4003B3F7` (возврат в
  хвост барьера `0x4003B3xx`, где стоит `blx` на ARM-хелпер вторичных ядер
  `0x40039FD8` — он правит `ACTLR` (`mrc p15,0,r0,c1,c0,1` → `bic/orr` битов
  0x200/0x100/0x80/0x40/0x8/0x1 → `mcr`), то есть ядро уже шло по «вторичному»
  пути KBL; arm2 — с тем же `LR = 0x4003B3F7` и `sp = 0x3EE0`), а сам переход
  в окно происходит не через `pc = 0` (в трассе `ZLB_KBL_TRACE_PC=0x0` попаданий
  нет), а через `0x20`-`0x28` — то есть ядро «въезжает» в таблицу указателей.
  Следующий шаг — трассировать первое попадание в `0x20`/`0x24` и найти, кто
  туда отправляет (`bx`/`pop {pc}` с испорченным адресом или необработанный
  `undef`).

### 8.4 Раунд 164: вторичные ядра убивает общий стек

Причина найдена точно. Добавлена диагностика `ZLB_KBL_TRACE_ZERO=1` (ловит
переход на `pc == 0`; `ZLB_KBL_TRACE_PC` этого не может — у него проверка
`trace_pc != 0`). Первый прогон:

```
trace zero-page: arm1 from pc=0x4003B3D0 lr=0x4003B3F7 sp=0x00003F10
                 cpsr=0x2000001F (SYS, ARM) r4=0x400B2B90 r5=0x400B2CCC
```

`0x4003B3D0` — это `pop {r4-r6,pc}` в хвосте функции барьера (её пролог —
`push {r4-r6,lr}` + `sub sp,#8` в `0x4003B384`), а `sp = 0x3F10` означает, что
кадр барьера лежит в **общем** стеке вторичных ядер: слот `[0x3F1C]`, откуда
берётся `pc`, равен нулю, поэтому ядро уходит на `0x0` и дальше «едет» по
низкому окну до первого неотображённого слова (`0xFFFFFFFF` на `0x2C`).

Откуда общий стек: трамплин входа в стадию KBL (`mov sp,r2; bx r1`) получает
стек из структуры `0x400B2B30` (`r6+0x1BC`, поле у каждого ядра своё —
`0x400B2B50/70/90`), и в модели там оказывается `0x1A140` для ядра 0 и
**`0x4000` для всех трёх вторичных**. Общий стек на три ядра — это и есть
источник порчи кадров; на железе свои стеки ядрам даёт предыдущая ступень через
boot-контекст, который в модели пуст (см. `docs/STATUS.md` §3.1).

**Следующий шаг**: выдать каждому вторичному ядру свой стек (засеять
boot-контекст/поле стека по ядру, как это делает сам NSKBL:
`0x51032100 - core*0x400`), после чего барьер перестанет портить кадры, ядра
дойдут до NSKBL и тот должен пройти `0xA5` («старт остальных ядер»).

### 8.5 Раунд 164: вторичным ядрам выдан свой стек — `0xA7`

Подстановка сделана и включена по умолчанию: на трамплине входа в стадию
(`0x4003A140`, `mov sp,r2; bx r1`) стек вторичного ядра сдвигается на
`core * 0x1000`, то есть каждый получает свою страницу в том же низком окне
(`ZLB_KBL_CORE_STACK=<hex>` меняет шаг, `0` выключает, `ZLB_NO_SUBSTITUTION=1`
снимает все подстановки). Это ровно то, что на железе делает предыдущая ступень
через ARM boot-контекст (в модели он пуст, `docs/STATUS.md` §3.1).

Результат обычного прогона:

```
GPO raw=0x00A70000 checkpoint=0xA7 - NSKBL: nothing since 0xA6
arm0  ARM Cortex-A9  pc=51014990  SYS ARM  non-secure  mmu=on
arm1  ARM Cortex-A9  pc=510147DC  SYS ARM  non-secure  mmu=on
arm2  ARM Cortex-A9  pc=510147DC  SYS ARM  non-secure  mmu=on
arm3  ARM Cortex-A9  pc=510147DC  SYS ARM  non-secure  mmu=on
```

То есть NSKBL проходит `0xA4` → `0xA5` (старт остальных ядер) → `0xA6` (MMU
включён, VBAR) → `0xA7`, **все четыре ядра** вошли в Non-Secure через
`0x40021AF8` (`SCR = 0x5`) и работают с **включённым MMU на своих таблицах**
(`TTBR0 = 0x40308000`, `TTBR1 = 0x4030C04A` — их построил сам NSKBL). Ядро 0
исполняет код NSKBL (`0x51014990`), вторичные стоят в его же цикле ожидания
(`0x510147DC` — это `wfe` в хелпере `0x510147D8`). В логе видно и корректное
поведение TrustZone: `SCR write ... ignored in non-secure world` на
`0x400297E0`/`0x40029898`.

Следующая цель — `0xA8` («boot setup complete, kernel loading»): там начинается
загрузка ядра/модулей `os0` (`SceKernelBootimage`, затем
`os0:psp2bootconfig.skprx` и `SceSysStateMgr`).

### 8.6 Раунд 164: текущая стена — NSKBL стоит на спинлоке с адресом `0x28`

На `0xA7` ядро 0 крутится в собственном спинлоке NSKBL:

```
51014980  ldrex r1, [r0]
51014984  teq   r1, #0
5101498C  wfe (условный, cond = NE - NSKBL ждёт событие, а не крутится)
51014998  strexeq r1, r2, [r0]
510149A0  bne   0x51014980
```

Состояние (раунд 164): `r0 = 0x28`, `r1 = 0x4680`, `r2 = 1`,
`LR = 0x5100B079` (то есть вызов из `0x5100B078`), `TTBR0 = 0x40308000`.
`vpa 0x28` → `PA 0x28` (низкая страница, окно `arm_bootrom`), а `vmem 0x28`
показывает **`0x4680`** — замок «взят» и его никто не отпускает, поэтому
ядро 0 стоит вечно, а вторичные ядра спят в `wfe`-цикле NSKBL (`0x510147DC`).

Кто положил `0x4680`: трап записей по `PA 0x20-0x40` показывает, что это делает
**сам KBL** с `pc = 0x4002CE90` (много раз подряд; там же значения
`0x1131000`, `0x2`, `0xABCE9DA5`, `0xFFFFFFFF` от `0x4002B0F8`, `0x4002F104`,
`0x4002A86C`, `0x40025292` — то есть KBL использует слово по `PA 0x28` как свою
переменную в низкой странице). Адрес `0x28`, который NSKBL берёт как указатель
на замок, выглядит подозрительно маленьким — вероятно, это поле структуры
(размер/идентификатор), прочитанное как указатель; та же семья, что и «magic
класса вместо указателя» в главе 7.

**Следующий шаг**: посмотреть вызывающего `0x5100B078` (что именно он кладёт в
`r0`) и решить, откуда должен браться настоящий указатель на замок; попутно
проверить, не является ли `0x4680` просто счётчиком KBL, который NSKBL
принимает за владельца замка.

### 8.7 Раунд 165: `0xA7` пройден, NSKBL падает на `0xAD` (data abort)

Цепочка от `0x28` прослежена до конца:

```
0x51014970 (спинлок NSKBL)          адрес замка = obj + 28
0x5100B41C  setter(obj, 0, ...)     r4 = obj = 0 (NULL)
0x5100B6D8  обёртка                 r0 = 0
0x5100B726  case 40: ldr r0,[[0x5113B5AC]+0x64]  -> 0
0x5100B4A6  bl 0x5100B054 с r0 = 0
```

`[0x5113B5AC]` = `VA 0x4900` — это **собственный объект карты памяти NSKBL**
(`PA 0x40304900`, заполняется самим NSKBL: `0x40300000`, `0x1FD00000`,
`0x20000000`, `0x08000000`, `0x80000000`, `0x40000000`, указатели
`0x5180/0x5240/0x52C0/0x5300`), а его поле `+0x64` остаётся нулевым. То есть
указатель на объект `NULL` — та же семья «пустой структуры», что и
boot-контекст.

Подстановка модели: на входе спинлока `0x51014970` адрес замка ниже первой
страницы (`< 0x1000`, то есть объект NULL) — захват пропускается
(`ZLB_NSKBL_NOLOCK=0` и `ZLB_NO_SUBSTITUTION=1` выключают). Результат — NSKBL
идёт дальше:

```
arm0 A1 (0x510008DE)
arm0 A2 (0x5100094E)
arm0 A3 (0x51000C1A)
arm0 A4 (0x51000C24)
arm0..arm3 A5 (0x510003CC)   ← «co-processor init, other cores start»
arm0..arm3 A6 (0x510004CC)   ← «MMU enabled, VBAR set up»
arm0..arm3 A7 (0x510004FC)
arm0 AD (0x51000C78)         ← паника
```

(трасса писателя GPO `0x51010F98`: видно, что `0xA5`-`0xA7` пишут **все четыре
ядра**.)

Новая стена — **data abort** сразу после `0xA7`, то есть в подготовке загрузки
ядра. `ZLB_KBL_FAULT_TRACE=1` называет точку: `VA=0x4B656350 read
pc=0x5100B544 lr=0x5100B083`, а причина — тот же `NULL`-объект:

```
0x5100B530  ldr.w r8,[r4,#12]   r4 = 0  -> r8 = [0x0C] = 0x4B656350
0x5100B540  ldr.w r6,[r8]       -> section translation fault (DFSR = 5)
```
(при включённом MMU `VA 0x0C` попадает в собственную низкую страницу NSKBL
`PA 0x40304000`, поэтому чтение поля не падает, а возвращает мусор `0x4B656350`,
который читается как ASCII «PceK»; падает уже разыменование этого мусора.)

Панический обработчик — `0x51000C74`: `movs r0,#0xAD; bl <GPO>; mrc p15,0,r3,
c5,c0,0 (DFSR); b .`. Вся паническая группа `0xAA..0xAF` живёт в
`0x51000C3C..0x51000C98` (у `0xAB` — дамп `SPSR`, у `0xAC` — `IFSR/DFAR/IFAR`,
у `0xAD` — `DFSR`, у `0xAA/0xAE/0xAF` — без дампа); она добавлена в таблицу
чекпойнтов отладчика.

**Следующий шаг**: понять, что должно инициализировать объект, который приходит
в `0x5100B41C` (список `[[0x5113B5AC]+0x64]` и объект вызывающего
`0x5100B4A6`). Пока в модели они нулевые, NSKBL будет падать на `0xAD`; после
этого — `0xA8` («boot setup complete, kernel loading») и загрузка модулей
`os0`.

### 8.8 Раунд 166: паника `0xAD` снята, новая стена — `fatal()` NSKBL

Конструктор `0x5100B41C` получает «пул» объектов из поля объекта карты
(`0x5100B6E4` для типов 20/40/80 читает `[[0x5113B5AC]+0x5C/0x64/0x6C]`), а
код, который эти пулы создаёт (построители списков вокруг `0x51009516`), в
модели **не исполняется вообще** — PC-трап `0x51009518-0x51009548` за весь
прогон не дал ни одного попадания. Подстановка `ZLB_NSKBL_POOL` (по умолчанию
включена) отдаёт конструктору страницу из арены модели
(`kInstanceArenaVa = 0x01100000`, секция ставится в **собственную** L1 NSKBL
через `ensure_arena_section`), когда `r0 = 0`. Паника `0xAD` исчезает —
NSKBL продолжает работу.

Новая стена — собственный `fatal()` NSKBL: это «висячий» `b .` по
`0x51015B7C`, куда ведут `bl` из 11 мест
(`0x5100EBB4`, `0x5100EEA4`, **`0x5100FE16`**, `0x5100FEA4`, `0x510101E8`,
`0x51010300`, `0x51010362`, `0x5101036C`, `0x51010376`, `0x5101055A`).
Сработавший путь — проверка **магики класса**:

```
5100EEA8  push.w {r4-r11,lr}
5100EEB4  ldr r2,[r0,#36]        ; r2 = obj->[0x24]
5100EEBA  ldr r3,[r6]            ; r3 = [0x5113B604]
5100EEBE  cmp r2,r3
5100EEC0  bne.w 0x5100FE16       ; магика не совпала -> fatal()
```

Измерено: `r0 = 0x4010047E`, `[obj+0x24] = 0`, а `[0x5113B604] = 0x19442EA8` —
это значение NSKBL **сам** кладёт на `0x5100E8DA` вместе с дескриптором
`{0xC0, 0x19442EA8, 0x1000, 0x10000}`. Память по `0x4010047E+0x24` в модели
нулевая, а её чтение даже не отображено (`ZLB_KBL_FAULT_TRACE`:
`VA=0x401004A0 read pc=0x5100EEB8` — сработала подстановка fault-hook).
Указатель приходит из поля объекта: вызывающий `0x5100D398` делает
`ldr r0,[obj]` и передаёт результат в `0x5100EEA8`. Область `0x40100xxx` — та
самая DRAM, куда **подстановки стадии KBL** кладут свои синтетические блоки
(`supply_kbl_partition_block`), то есть NSKBL, похоже, читает оставшийся от KBL
указатель и трактует его как свой объект.

Заодно измерено: NSKBL по-прежнему **ни разу не обращается к SDIF/eMMC**
(трап `0xE0B00000`: 714 обращений, все — от CMeP), то есть до чтения ядра с
носителя дело ещё не дошло.

**Следующий шаг**: проследить, откуда берётся объект с полем
`[obj] = 0x4010047E` (вызывающие `0x5100D398`), и решить, какую структуру NSKBL
там ожидает: либо модель обязана её создать (свои дескрипторы NSKBL для этой
области), либо подстановки стадии KBL не должны оставлять там свои блоки.

### 8.9 Раунд 166 (продолжение): корень NULL-цепочки — незаполненные поля объекта карты

Цепочка доведена до корня, и попутно исправлена методика разбора.

**Методика.** Файл `_scratch/nskbl/nskbl.bin` (старая выгрузка) **не совпадает**
с образом, который реально исполняется: побайтовое сравнение с дампом живой
памяти (`save 0x51000000 0x2B08C runtime.bin`) даёт **3777 различий** — в
основном в `movw/movt`-парах (например, там, где старая выгрузка показывает
`movt r5,#0x3113`, живой код содержит `movt r3,#0x5113`). Целевые адреса
ветвлений при этом совпадают (список из 11 вызовов `fatal()` идентичен), но
*регистры и имmediates* читать по старой выгрузке нельзя. Дальше эталон —
дамп из отладчика: `save 0x51000000 0x2B08C <файл>` (или `save <addr> <len>` для
нужного окна).

**Корень.** Проверка магики срабатывает потому, что объект приходит `NULL`:

```
5100B638  ldr.w sl,[r4,#0x48]   ; sl = obj->[0x48]
5100B63C  cmp.w sl,#0
5100B640  bne   0x5100B64C
5100B642  bl    0x5100DEBC      ; «создать» -> r0
5100B648  mov   sl,r0
5100B64A  str   r0,[r4,#0x48]
5100B64E  mov   r0,sl
5100B650  bl    0x5100DE8C      ; с r0 = 0!
```

а «создатель» `0x5100DEBC` — это всего лишь чтение поля объекта карты:

```
5100DEBC  movw r0,#0xB5AC; movt r0,#0x5113
5100DEC4  ldr  r3,[r0]          ; r3 = [0x5113B5AC] = объект карты (VA 0x4900)
5100DEC6  ldr.w r0,[r3,#0xD8]   ; r0 = map->[0xD8]  == 0 в модели
5100DECA  bx   lr
```

То есть **поля объекта карты (в том числе `+0xD8`, `+0x48`) в модели нулевые**:
конструктор объекта карты (окрестность `0x510064A0`) их обнуляет, а код, который
их заполняет (создание пулов/устройств), не исполняется. Дальше NULL едет по
цепочке `0x5100B650` → обёртка `0x5100DE8C` → `0x5100D398` → проверка магики
`0x5100EEA8` → `fatal()` `0x5100FE16`.

Заодно уточнено: «магика» `0x19442EA8` = `align8(v|8)` от `v = 0x19442EA1` —
значения глобальной переменной `[0x5102B030]`, лежащей в образе NSKBL рядом с
переменной чекпойнта (`[0x5102B034] = 0xA7`).

**Следующий шаг**: найти код, который заполняет поля объекта карты
(`str …, [rX, #0xD8]` и соседние), и понять, почему он не исполняется
(трассировка PC по адресам-кандидатам); это и есть недостающая инициализация
NSKBL, после которой освобождается путь к `0xA8` и чтению ядра с носителя.

### 8.10 Раунд 167: инструмент покрытия и проверка `kernel_boot_loader.self.seg02`

**Инструмент покрытия** (нужен был, потому что вопрос «какая функция NSKBL вообще
не исполнялась» решался слишком долго). Модель теперь умеет карту покрытия ARM:

* `ZLB_ARM_COV=1` — включается битовая карта PC (1 бит на 16 байт диапазона
  `0x51000000-0x51040000`, заполняется в `Vita::arm_cov_mark` из `run_slice`);
* `cov [addr] [len]` — попадания по страницам плюс 24 самых длинных
  неисполненных участка;
* `cov save <file>` — сырая карта (2048 байт), её стыкует с дизассемблером
  `_scratch/scan_missed.py`, который печатает **пропущенные рёбра потока
  управления**: ветвления, чей сайт исполнился, а цель — нет.

Первая же карта (обычный прогон) показала: страницы `0x51007000`,
`0x51008000`, `0x51009000` **не исполняются вообще**, и там же лежат
построители списков (`0x51009516`). Уточнение того же раунда: при
**16-байтовой** гранулярности карты скрипт пропущенных рёбер давал ложные
срабатывания (он считал сайт исполнившимся, если в его 16-байтовом блоке
исполнился *любой* адрес — например, `0x5100B630` «срабатывал» из-за
`0x5100B638`), поэтому гранулярность по умолчанию снижена до **2 байт** (одна
Thumb-инструкция; `ZLB_ARM_COV_GRAN` меняет). С точной картой:

* пропущенных **вызовов** (`bl`) внутри Thumb-кода NSKBL **нет вообще** — все
  24 оставшихся «пропуска» оказались артефактами дизассемблирования
  ARM-участков (спинлок `0x51014970`) как Thumb;
* значит код в неисполненных страницах не «пропускается», а просто **не
  вызывается**: это библиотека функций для более поздних стадий (вход в неё
  идёт через вычисляемые переходы/таблицы, а не через прямые `bl`);
* прогон **детерминирован**: три одинаковых запуска дают один и тот же
  чекпойнт `0xA7`, один и тот же PC `0x51015B7C` и одинаковое покрытие, так что
  различия в значениях между прогонами объясняются только сменой подстановок,
  а не таймингом.

Поэтому текущая стена формулируется точнее: NSKBL идёт по
*данным-зависимому* пути в «открытие устройства» **раньше**, чем построены
контейнеры объекта карты (`map->[0xD8] == 0`), и умирает в `fatal()`. Искать
надо не «пропущенный вызов», а то **значение**, которое увело поток в этот путь
(кандидаты — поля загруженного образа/структур, которые в модели нулевые).

### 8.11 Карта чекпойнтов NSKBL и вход в стадию `0xA8`

Тем же сканером (`_scratch/scan_ckpt_sites.py`, ищет `movs r0,#N` + вызов
писателя GPO `0x51010F98`) снята вся карта чекпойнтов NSKBL:

| Код | Где пишется | Смысл |
|---|---|---|
| `0xA1` | `0x510008DC` | core 0 pre-init complete |
| `0xA2` | `0x5100094C` | interrupts registered |
| `0xA3` | `0x51000C18` | serial console ready |
| `0xA4` | `0x51000C22` | device buffer initialised |
| `0xA5` | `0x510003CA` | co-processor init, other cores start |
| `0xA6` | `0x510004CA` | MMU enabled, VBAR set up |
| `0xA7` | `0x510004FA` | nothing since 0xA6 |
| **`0xA8`** | **`0x51000CBC`** | **boot setup complete, kernel loading** |
| `0xA9` | `0x51000CF6` | kernel pre-init done |
| `0xAA..0xAF` | `0x51000C3E…0x51000C92` | панические (см. §8.6) |

Тело стадии `0xA8` (`0x51000CB8`) выглядит так:

```
51000CB8  push {r4,lr}
51000CBA  mov r4,r0
51000CBC  movs r0,#0xA8 ; bl <GPO>        ; «boot setup complete, kernel loading»
51000CC2  bl 0x51010580
51000CC6  movs r0,#4 ; bl 0x51000CA4
51000CCC  blx 0x51014528                  ; (per-core helper)
51000CD0  cbz r0,0x51000D0E                ; если 0 - загрузку пропустить
51000CD2  mov r0,r4 ; bl 0x51018E88
51000CD8  bl 0x51001EAC
51000CDC  mov r0,r4 ; bl 0x51002F4C
51000CE2  mov r0,r4 ; bl 0x51018F20
51000CE8  bl 0x51016CC4
51000CEC  bl 0x5101616C
51000CF0  movs r0,#0x10 ; bl 0x51000CA4
51000CF6  movs r0,#0xA9 ; bl <GPO>
```

Важное: у функции `0x51000CB8` **нет ни одного прямого вызывающего** (`bl` в неё
не найден вообще), то есть стадии NSKBL вызываются **через таблицу** (в низкой
странице `PA 0x40305xxx` действительно лежат таблицы указателей вида
`{0x5100B031, 0x5100B041, 0x5100B73D, …}`). Следующий шаг для стадии `0xA8` —
найти эту таблицу стадий и посмотреть, почему обход не доходит до `0x51000CB8`
(там же станет видно, какое значение уводит поток в «открытие устройства»).

Отрицательные результаты поиска этой таблицы (чтобы не искать дважды): указателя
на `0x51000CB8`/`0x51000CB9` **нет** ни в образе NSKBL (`_scratch/nskbl/
nskbl_runtime.bin`), ни в его рабочем окне `PA 0x40300000-0x40340000` (256 КиБ
живой памяти), ни среди указателей на весь кластер стадий
(`0x51000300-0x51000D00`) в образе и низкой странице. Значит вызов идёт либо
через `blx reg` (вычисляемый переход), либо через компактную таблицу
**относительных** смещений (`base 0x51000000 + 0x0CB8` и т. п.) — это и надо
проверить в первую очередь (поиск 16-битных значений `0x0CB8`/`0x0CF6` в данных
и разбор загрузчиков указателей в стадийных функциях).

### 8.12 Точка ухода потока: `0xA7` → `0x51000FA8` → открытие устройства

Диагностика `ZLB_ARM_BRANCH_LOG` (в `ArmCore::branch_to`, то есть на **всех**
ветвлениях, включая вычисляемые; значение `1` — кластер стадий
`0x51000000-0x51000E00`, значение `<lo>-<hi>` — произвольный диапазон) вместе с
картой покрытия дала точную картину.

Стадия `0xA7` (`0x510004FA`) после записи чекпойнта:

```
51000500  blx 0x51014528          ; per-core helper
51000504  cbnz r0,0x51000530
51000506..5100052C  bl 0x510155C8  ; регистрация регионов 0x8000, 0x40100000,
                                   ; 0x47000000, 0xE0000000 (через &local на стеке)
51000530  ldr r0,[r5]
51000532  bl 0x51000FA8            ; <-- сюда уходит поток
51000536  ...  bl 0x51015874 ...   ; ожидание на объекте 0x5102B008
51000554  b 0x51000554             ; и здесь стадия «зависает»
```

Покрытие показывает: `0x51000500/04/0C/32` и `0x51000FA8` **исполнены**, а
`0x51000540`, `0x51000550`, `0x51000554` — **нет**, то есть из `0x51000FA8` поток
**не возвращается** в стадию.

Дальше из `0x51000FA8` (функция стадии, `push {r4-r8,lr}`, контекст в `r4`)
исполняются **все** её вызовы: `0x51010A60`, `0x51010994`, `0x510106A8`,
`0x510109AC`, `0x51010F14`, `0x51000338` — и поток оказывается в коде устройств
(`0x5100BB41`, `0x5100B638`), где и умирает в `fatal()` `0x51015B7C`
(цепочка §8.9: `map->[0xD8] == 0` → NULL-объект → проверка магики).

Итог: стадия `0xA8` в этом потоке просто не встречается — NSKBL уходит в
«открытие устройства» из `0x51000FA8` и не возвращается. Следующий шаг —
разобрать `0x51000FA8` до конца (какой именно из её вызовов уводит в устройства и
по какому условию) и понять, какое **значение** делает этот путь успешным на
железе (там контейнеры `map[0x5C/0x64/0x6C/0xD8]` уже построены).

### 8.13 Раунд 169: точка принятия решения найдена — пустой пул

Трассировка `ZLB_KBL_TRACE_PC=0x5100B638` назвала вход в блок «открытия
устройства»: **`0x5100B58A`**, и это условный переход:

```
5100B57C  ldrh r1,[r4,#0x30]      ; свободных слотов
5100B57E  ldrh r3,[r4,#0x32]      ; занятых слотов
5100B586  cmp  r1,r3
5100B58A  bls  0x5100B638         ; «нет места» -> открытие устройства -> fatal()
```

В модели ветка берётся потому, что `r4 = 0x01100000` — это **страница арены,
которую выдала подстановка `ZLB_NSKBL_POOL`**, а её счётчики нулевые
(`0 <= 0`). На железе эти поля заполнил бы построитель пулов NSKBL (те самые
неисполняемые страницы `0x51007000-0x51009000`).

Подстановка `ZLB_NSKBL_POOLFIX` (по умолчанию включена) перед этой проверкой
выдаёт пустому пулу один свободный слот и корректные указатели массивов
(`+0x34`, `+0x4C`), если объект лежит в арене и оба счётчика нулевые. Результат:
ветка «нет места» больше не берётся, поток идёт по нормальному пути, и старая
стена `fatal()` `0x51015B7C`/паника `0xAD` **позади**.

Новая стена (паника **`0xAC`**, «fatal: reads IFSR/DFAR/IFAR») — следующий
незаполненный указатель того же объекта:

```
5100B59E  ldr  r2,[r4,#4]      ; r2 = obj->[4]  == 0 в модели (указатель класса/vtable)
5100B5A4  ldr  r3,[r2,#0x38]   ; чтение VA 0x38 -> fault-hook отдаёт мусор
5100B5A6  blx  r3              ; -> 0xFFFFFFFE => prefetch abort => паника 0xAC
```

То есть у объекта в арене нет указателя на класс; `ZLB_KBL_FAULT_TRACE=1`
показывает `VA=0x00000038 read pc=0x5100B5A8` и `VA=0xFFFFFFFE fetch pc=0x00000002
(prefetch)`.

Полезное попутно: таблицы указателей в низкой странице NSKBL (`PA 0x40305xxx`)
**строит сам NSKBL** — трап записей даёт `pc = 0x5100445E…0x510044D2` (плюс
обнуление `0x510135xx`), то есть «классовая» машинерия NSKBL частично работает;
не хватает именно указателя класса в объекте, который модель создала «с нуля».
Ссылок на таблицу классов KBL (`0x400B2xxx`) в образе NSKBL практически нет
(одна, `0x400B4002` в `0x51017470`), так что классы NSKBL строит сам — и искать
надо недостающий шаг этой постройки.

### 8.14 Раунд 170: вместо паники — штатное ожидание (и что именно ждут ядра)

Подстановка `ZLB_NSKBL_CLASS` (по умолчанию включена) дополняет объект
минимальным «классом» модели: в арене (`kInstanceArenaVa + kInstanceArenaSize -
0x1000`) строится страница, все слоты методов которой равны `0x51014B94`
(ARM `bx lr`), а в объект пишется `obj->[4] = <эта страница>`. После этого
виртуальный вызов `ldr r2,[r4,#4]; ldr r3,[r2,#0x38]; blx r3` из `0x5100B59E`
возвращается штатно, паника `0xAC` исчезает, и NSKBL **не падает, а уходит в
штатное ожидание**: все четыре ядра стоят в `wfe` хелпера `0x510147D8`
(`pc = 0x510147DC`), чекпойнт остаётся `0xA7`.

Состояние ожидания измерено по каждому ядру:

| Ядро | Объект ожидания (`r4`) | Поле | Комментарий |
|---|---|---|---|
| arm0 | `0x5102B008` | `+6` (`0x5102B00E`) | блок в данных NSKBL, его **инициализировал KBL** |
| arm1 | `0x00004034` | `+6` | общий объект в низкой странице NSKBL |
| arm2 | `0x00004034` | `+6` | то же |
| arm3 | `0x00004034` | `+6` | то же |

Кто их пишет: трап записей по `PA 0x5102B000-0x5102B020` даёт только **KBL**
(`pc = 0x4003CA6C`, `0x4003C420`, значения `01 00 04 00 …`), то есть этот блок —
часть передачи управления от KBL к NSKBL; трап по `PA 0x4034-0x403C` не даёт
**ни одного** писателя, кроме обнуления моделью. Значит оба ожидания в модели
никто не удовлетворяет — вторичные ядра ждут объект, который не меняется, а
ядро 0 ждёт изменения поля блока KBL.

Заодно измерено, какие периферийные устройства NSKBL вообще трогает за весь
прогон (трап по `0xE2000000-0xE3000000` с фильтром по `pc = 0x51xxxxxx`):
только **UART `0xE2030000`** (1083 обращения — консоль) и **GPO `0xE20A0000`**
(36 — чекпойнты). Ни таймеров, ни GIC, ни SDIF/eMMC — то есть «разбудить» его
таймером, который он сам не программировал, нельзя; ожидание удовлетворяется
либо стороной KBL (secure monitor, `smc`), либо другим ядром.

Следующий шаг: определить, кто обязан выставить эти поля (продолжение обработки
`smc` в мониторе KBL или обмен между ядрами), и почему соответствующая ветка в
модели не исполняется.

### 8.15 Раунд 171: примитивы синхронизации NSKBL и почему система не едет дальше

Разобраны примитивы (все — **ARM**-код, вызовы идут через `blx` на чётный адрес):

| Адрес | Что делает |
|---|---|
| `0x5101474C` | `ldrexh r2,[r0]; strexh r2,r1,[r0]; teq r2,#0; bne …` — атомарная запись полуслова (retry-цикл) |
| `0x5101477C` | `ldrexh r2,[r0]; sub r3,r2,r1; strexh ip,r3,[r0]; …; mov r0,r2` — атомарное вычитание, возвращает старое значение |
| `0x510147D0` | `sev; bx lr` |
| `0x510147D8` | `wfe; bx lr` (в него упираются все ядра: PC `0x510147DC`) |
| `0x510147E4` | `wfi; bx lr` (+ `dsb`/`dmb` рядом) |
| `0x5101586C` | инициализация объекта синхронизации: `[+4]=1`, `[+8]=4`, `[+0xA]=4` |
| `0x510158AC` | «arrive»: ставит токен `[obj+6] = (my_index+1) mod 4` атомарной записью и вычитает счётчик `[obj+4]` |
| `0x51015874` | «wait»: ждёт, пока `[obj+6]` не станет «моим» значением, между попытками `wfe` |

Обёртки барьера: `0x51000314` — `wait(obj = 0x5102B000, 0)` (все четыре ядра
вызывают её из `0x51000320`), `0x51000328` — `arrive(obj = 0x5102B000)`.
То есть барьер NSKBL работает на объекте `0x5102B000` (счётчик `+4`, токен `+6`),
инициализированном **KBL** (`pc = 0x4003CA6C`, `0x4003C420`, значение 4).

Измерено, что барьер **работает**: обе обёртки исполнены, объект пишется самим
NSKBL (`pc = 0x51014750` — 79 раз, `pc = 0x51014784` — 45 раз), а второй такой
объект в низкой странице (`PA 0x40304030`) создаётся кодом `0x5101586C` и его
токен/счётчик тоже ходят (`0x51014750` пишет 0 и 1, `0x51014784` — 3).

Но **прогресса нет**: история PC (`history arm 24`) после 500 000 и после
1 000 000 слайсов совпадает до символа, а после **10 000 000** слайсов чекпойнт
всё ещё `0xA7`, и код `0x51000CBC` (стадия `0xA8`) так и не исполнен. Значит это
**livelock** в цикле, который проходит по адресам

```
5100445A 510063E2 510110CC 51011208 51011216 5101120A 51011366 5101139A
51014530 5101478C 5101586C..51015914 51017564 51017580 51017590 510175A2
510175A8 51017606 5101761A 51017640 5101764E 510258E8 51025A9C 51025AAC
```

(среди них — retry-цикл атомарного вычитания `0x5101478C`). Следующий шаг:
разобрать этот цикл (начать с `0x5101120A`/`0x51011216` и `0x51017564`/`0x51017590`,
они — ядро цикла) и найти условие, которое на железе становится истинным, а в
модели — нет; вероятнее всего это либо ожидание события от другого ядра, либо
проверка, зависящая от значения, которое модель не выставляет.

### 8.16 Раунд 172: консоль NSKBL работает и сама называет стену

Разбор ядра livelock'а дал **прямую улику от самой прошивки**: в логе модели
появился вывод консоли NSKBL (`[info] uart`):

```
0:0x58e51d55:0xc6dcf268:sceKernelAllocHeapMemory failed(NULL), size=12
0:0x58e51d55:0xc6dcf268:sceKernelAllocHeapMemory failed(NULL), size=32
0:0x58e51d55:0xc6dcf268:sceKernelAllocHeapMemory failed(NULL), size=64
0:0x58e51d55:0xc6dcf268:sceKernelAllocHeapMemory failed(NULL), size=44
```

То есть NSKBL **дошёл до своей консоли и до подсистемы памяти**, но
`sceKernelAllocHeapMemory` получает **NULL-кучу** и печатает ошибку; цикл
повторяет попытки (это и есть livelock из §8.15 — история PC не меняется).

Механизм консоли (чтобы это можно было развивать дальше):

* путь регистрации (`0x51000900…0x5100094E`, там же чекпойнт `0xA2`
  «interrupts registered»): `memset` структуры `0x51184E98`, регистрация
  обработчиков `0xC5`/`0xC4` через `0x51015D18`, затем вызов `0x510175DC`
  («включить консоль»: `[0x5102B054] = 1`);
* вывод: `0x510175DC` — постановка (флаг `[0x5102B054] = 1`, вызов `0x51015D18`
  с `0xC5`), `0x51017564` — диспетчер (слоты таблицы `0x5102B054`: `+0` —
  «включено», `+4`/`+8`/`+0x10` — индексы консолей), `0x51017604` — ожидание
  бита 8 (`0x100`) в `[base+0x28]` и запись канала в `[base+0x70]`,
  `0x5101763C` — ожидание бита 9 (`0x200`);
* базы устройств лежат в **собственной таблице NSKBL** `0x5102B06C`
  (счётчик 6 в `0x5102B068`): `0xE2030000` (UART), `0xE2040000`, `0xE2050000`,
  `0xE2060000`, `0xE2070000`, `0xE2080000`, `0xE2090000` — те же окна MMIO, что
  и в таблице сегмента `seg02` KBL (§8.10);
* опросы в модели **проходят**: `[0xE2030028]` возвращает `0x300` (биты 8 и 9
  выставлены; измерено 357 обращений с `pc = 0x51017614/0x51017648`);
* флаг `[0x5102B054] = 1` ставит только `0x510175EA` (сам NSKBL), и его никто не
  снимает — но это «консоль включена», а не «есть работа» (диспетчер при пустых
  слотах `+8`/`+0x10` возвращает 0).

Заодно найден **реестр классов NSKBL** — таблица имён в образе
(`0x510287C0…0x5102892C`): `SceKernelHeapUncache`, `SceKernelHeap`,
`SceKernelPartition`, `SceKernelAddressSpace`, `SceKernelProcess`,
`SceHeapUIDEntry`, `SceKernelSimpleMemBlockClass`, `SceKernelRoot`, а рядом —
форматы ошибок `%d:0x%08x:0x%08x:sceKernelAllocHeapMemory failed(NULL), size=%d`
(`0x5102889C`) и `…AllocHeapMemoryWithOption…` (`0x510288E0`). Дескрипторы
классов NSKBL **строит сам** в низкой странице, например `PA 0x40305C40`:
`{0x5D40, 0x5480, 0x5B80, 0x51028838 ("SceKernelSimpleMemBlockClass"), 0x54C0,
0x10, 0x00400040, 0, 0x51005A81, 0x51005A6D, 0xABCE9DA5, 0}` — то есть имя,
методы (`0x51005A81`, `0x51005A6D` — Thumb) и та самая магика `0xABCE9DA5`,
которую KBL писал в `PA 0x28` (§8.6).

**Итог раунда**: стена теперь не «неизвестный адрес», а названная прошивкой
ошибка — **у NSKBL нет кучи** (`sceKernelAllocHeapMemory` с NULL). Следующий шаг:
найти обёртку аллокации (через формат `0x5102889C` и таблицу сообщений,
указатель на которую лежит в `PA 0x40305C4C` → `0x51028838`) и **кто обязан
создать кучу** — почти наверняка это тот же неисполняемый блок инициализации
`0x51007000-0x51009000`, из-за которого в §8.9-8.13 не строились контейнеры и
пулы объектов.

### 8.17 Раунд 173: реестр классов почти пуст, а стек называет цепочку

Дополнительные измерения того же раунда:

* **реестр классов NSKBL почти не построен**. В живой низкой странице
  (`PA 0x40304000-0x4030C000`, 32 КиБ) есть **ровно один** указатель на имена
  классов — `PA 0x40305C4C → 0x51028838` (`SceKernelSimpleMemBlockClass`).
  Остальные семь имён из таблицы `0x510287C0…0x5102892C` (`SceKernelHeapUncache`,
  `SceKernelHeap`, `SceKernelPartition`, `SceKernelAddressSpace`,
  `SceKernelProcess`, `SceHeapUIDEntry`, `SceKernelRoot`) в живой памяти **не
  встречаются вообще** — то есть их дескрипторы не создавались. Это прямо
  согласуется с тем, что `sceKernelAllocHeapMemory` получает NULL: объекта кучи
  просто нет;
* **таблицы строк**. В образе есть таблицы указателей на строки
  (`0x510281D4-0x510281E0`, `0x5102842C-0x51028448`, `0x51028670+`), а на стеке
  в момент livelock'а лежит **локальный массив таких указателей**
  (`0x51028094`, `0x510280B8…0x51028148`, `0x5102815C/74/8C/A4`);
* **цепочка вызовов видна на стеке** (SP = `0x51030060`): там есть возврат
  `0x51000537` — это ровно адрес после `bl 0x51000FA8` в стадии `0xA7`
  (§8.12), и `0x51000250`. То есть livelock живёт **внутри цепочки
  `0x51000FA8`**, куда стадия `0xA7` уходит и откуда не возвращается;
* любопытно: на стеке NSKBL лежат и **адреса KBL** (`0x400B2C30`,
  `0x400B2CCC` — область таблицы классов KBL). В образе NSKBL на них ссылок
  почти нет (§8.13), значит они попадают туда в runtime — это стоит учитывать,
  когда дойдёт до классов;
* консольный диспетчер пишет в `[base+0x70]` **символы**: брейкпоинт в
  `0x51017604` на инициализации показал `r1 = 0x3D` («=» из сообщения
  `…size=%d`), `r0 = 0` (индекс консоли), `LR = 0x5101759D`.

Следующий шаг (уже подготовлен): поставить брейкпоинт в диспетчере
`0x51017564` **во время печати сообщения** (после длинного прогона) и пройти по
стеку вверх — так найдётся обёртка аллокации, а в ней глобальная переменная
кучи, которую и надо заполнить.

### 8.18 Раунд 174: конструктор классов NSKBL и карта регистрации

Найден **конструктор классов** NSKBL — `0x5100442C`. Он собирает дескриптор:

```
51004440  movw r6,#0xB5AC; movt r6,#0x5113     ; r6 = 0x5113B5AC (глобальный объект карты)
51004444  movw r5,#0xB594; movt r5,#0x5113     ; r5 = 0x5113B594 (глобальный «метакласс»)
51004450  ldr  r7,[r6]                         ; r7 = объект карты (VA 0x4900)
51004452  movw r6,#0x9DA5; movt r6,#0xABCE     ; r6 = 0xABCE9DA5 (магика класса)
51004456  ldr.w ip,[r5]                        ; ip = [0x5113B594]
5100445E  str  r1,[r4,#0x0C]                   ; +0x0C = имя класса
51004462  ldr  r1,[r7,#0x48]                   ; r1 = map->[0x48]  ← ГОЛОВА РЕЕСТРА КЛАССОВ
5100446C  str  r6,[r4,#0x28]                   ; +0x28 = магика
51004470  str.w ip,[r4,#4]                     ; +0x04 = метакласс
51004478/7A  str r0,[r4,#0x20]; str r3,[r4,#0x24]  ; +0x20/+0x24 = методы (аргументы вызова)
5100447C  cmp  r1,#0; beq 0x510044D0           ; связывание со списком реестра
```

Это ровно тот дескриптор, что был найден в живой памяти (`PA 0x40305C40`:
имя `SceKernelSimpleMemBlockClass` в `+0x0C`, методы `0x51005A81`/`0x51005A6D` в
`+0x20`/`+0x24`, магика `0xABCE9DA5` в `+0x28`).

**Реестр классов жив**: `map->[0x48]` = `VA 0x5480` — это дескриптор
**метакласса** (`PA 0x40305480`): `{0x54C0, 0x5480 (сам себе класс), 0,
0x510286F0 (имя), 0, 0, 0x00080008, 0, …}` с методами `0x5100441D`/`0x51004425`
(тот же кластер `0x510044xx`) и магикой `0xABCE9DA5`. Важная деталь: нужный
виртуальный вызов из §8.13 брал метод по смещению **`+0x38`**, а у метакласса
`PA 0x403054B8` = **0**, — поэтому модели и пришлось подставить «класс-заглушку»
(`ZLB_NSKBL_CLASS`).

**Карта регистрации классов** — у конструктора `0x5100442C` девять мест вызова,
и в модели исполнились только четыре:

| Место вызова | Исполнено |
|---|---|
| `0x510043B4`, `0x51004506` | да (ранний кластер `0x510043xx-0x510045xx`) |
| `0x5100E6DC`, `0x5100E70A` | да (кластер устройств/консоли `0x5100E6xx`) |
| `0x510043CC`, `0x51004F28` | **нет** |
| `0x51007EF8`, `0x510082CA` | **нет** (это тот самый неисполняемый «остров» `0x51007xxx-0x51008xxx`, §8.13) |
| `0x51018F0A` | **нет** (поздняя стадия) |

То есть часть системы классов NSKBL построена, а часть — нет, и «остров»
`0x51007xxx-0x51008xxx` (там же построители пулов из §8.8) остаётся
неисполняемым. Именно с ним, судя по всему, связаны и пулы, и часть классов, и
(через аллокацию дескрипторов) **куча**, из-за отсутствия которой консоль NSKBL
печатает `sceKernelAllocHeapMemory failed(NULL)`.

Следующий шаг: найти, кто должен вызывать регистрации `0x51007EF8`/`0x510082CA`
(то есть кто «входит» в неисполняемый остров), и что даёт им вход — почти
наверняка это тот же путь `0x51000FA8`, который стадия `0xA7` вызывает и из
которого не возвращается (§8.12).

### 8.19 Раунд 175: покрытие было устаревшим — уточнённая картина

**Важный урок.** Битовая карта покрытия `_scratch/nskbl/cov2.bin` была снята в
раунде 167 — **до** подстановок `ZLB_NSKBL_POOL`, `ZLB_NSKBL_POOLFIX` и
`ZLB_NSKBL_CLASS`, — а выводы «какой код исполняется» делались по ней вплоть до
§8.18. Её надо переснимать **после каждой смены подстановок**:
`ZLB_ARM_COV=1 … -ex "cov save <файл>"`.

Свежая карта (текущая сборка) меняет картину:

| Что | Было (старая карта) | Сейчас |
|---|---|---|
| регистрации классов | «4 из 9» | **7 из 9** ✅ |
| остров `0x51007xxx-0x51008xxx` | «не исполняется вовсе» | **частично исполняется** (`0x510063D2 → 0x51007E70` работает, регистрации `0x51007EF8`, `0x510082CA` тоже) |
| регистрации `0x51004F28`, `0x51018F0A` | — | по-прежнему **не исполнены** |
| построитель пулов `0x51009516` | не исполнен | по-прежнему **не исполнен** |
| стадия `0xA8` (`0x51000CBC`) | не исполнена | по-прежнему **не исполнена** |

Кроме того, с точной картой пропущенных **прямых вызовов** снова нет (все 28
«пропусков» — артефакты дизассемблирования ARM-участков как Thumb), то есть весь
недостигнутый код вызывается **только вычисляемыми переходами** (указателями).

Новые факты по нерешённым участкам:

* у стадии `0xA8` (`0x51000CB8`) **нет ни одного прямого вызывающего** — только
  вычисляемый вызов; адреса `0x51000CB8`/`0x51000CB9` не найдены ни в образе,
  ни в живой низкой странице, ни в данных `0x5118xxxx`;
* построитель пулов (`0x51009400-0x51009600`) вызывается ровно из двух мест —
  `0x51005D80 → 0x51009594` и `0x510097D6 → 0x51009594`, и **оба не исполнены**;
  значит цепочка к пулам проходит через неисполненную область `0x51005Dxx`;
* вспомогательный скрипт `_scratch/walk_up.py` (обход графа вызовов вверх)
  требует правки: его эвристика «ближайший `push {…,lr}`» не включает сам адрес,
  поэтому для функции `0x51000CB8` он ошибочно вернул `0x51000CA4`.

Следующий шаг: обойти вверх от `0x51005D80` (кто вызывает `0x51005Dxx`) — это и
есть путь к построителю пулов, а значит к пулам, классам и куче.

### 8.20 Раунд 176: livelock — барьер ждёт четвёртое ядро

Трап чтений по блоку, который KBL передал NSKBL (`PA 0x5102B000-0x5102B020`),
дал точный ответ:

```
[rtrap] arm_priv +0x1102B004 r2 = 0x3 pc=510158FE   (2 722 268 раз!)
```

`0x510158FE` — это конец «arrive»-хелпера (§8.15):

```
510158F0  ldrh r2,[r4,#4]      ; счётчик прибывших
510158F2  cmp  r2,#4
510158F4  bne  0x510158EC      ; wfe + перечитать
510158FE  ldrh r3,[r4,#4]
```

Счётчик в горячем цикле читается как **3** и никогда не становится **4**, то есть
**три ядра из четырёх прибыли на барьер, а четвёртое — нет**. Остальные значения
в трассе: 0 (11 раз), 1 (22), 2 (22), 3 (2 722 268) — то есть ядра подходили по
очереди и «застряли» на трёх. Все четыре ядра при этом стоят в `wfe`
(`pc = 0x510147DC`), но в разных хелперах: застрявшие — в «arrive» (ждут 4),
четвёртое — в другом ожидании.

Это согласуется с §8.16: одно из ядер уходит в путь консоли/аллокации и печатает
`sceKernelAllocHeapMemory failed(NULL)` (куча NULL, см. §8.16), то есть **не
доходит до барьера**, и весь кластер ждёт его вечно. Таким образом, корневая
причина текущего livelock — **та же самая отсутствующая куча**.

Итог: чтобы разомкнуть систему, нужно дать NSKBL рабочую кучу (или включить
инициализацию, которая её создаёт). Все остальные наблюдения (§8.8-8.19) — про
пулы, контейнеры и классы — следствия того же дефицита.

### 8.21 Раунд 178: путь аллокации разобран до конца — куча `map->[0x8C]` равна нулю

Диагностика `ZLB_NSKBL_LOG_CALLS=1` (крючок на входе printf-ядра `0x51011078`)
дала и адрес вызывающего, и **стек**, по которому виден весь путь:

```
alloc-report from 0x51011074: format=0x5102889C lr=0x51011B47 sp=0x5102FFA0
             stack=[0, 0x5102FFBC, 0, 0x0000000C, 0x00004900, 0x510060F9]
             (в следующих строках размер 0x20, 0x40, 0x2C — те самые 12/32/64/44)
```

`0x00004900` — это объект «карты памяти» (VA `0x4900`, PA `0x40304900`), а
`0x510060F9` — возврат в код, который печатает сообщение:

```
510060D4  blx 0x51014528                  ; получить значение (id/время)
510060D8  movw r2,#0x1D55; movt r2,#0x58E5 ; r2 = 0x58E51D55  ← как в тексте сообщения
510060DE  movw r3,#0xF268; movt r3,#0xC6DC ; r3 = 0xC6DCF268  ← как в тексте сообщения
510060E2  movw r0,#0x889C; movt r0,#0x5102 ; r0 = 0x5102889C  ← формат сообщения
510060F2  str  r5,[sp]                     ; размер
510060F4  bl   0x51011B14                  ; печать
510060F8  b    0x510060CE                  ; вернуть NULL
```

Цепочка аллокации (все звенья исполняются):

| Адрес | Что делает |
|---|---|
| `0x510060C6` | вызывает `0x5100D49C(0x0001000B, size)` и при 0 печатает ошибку |
| `0x5100D49C` | обёртка: `bl 0x5100D400` |
| `0x5100D400` | сохраняет размер, `bl 0x5100567C`, при 0 → вернуть 0 |
| `0x5100567C` | обёртка: `bl 0x51005434` |
| `0x51005434` | обёртка: `bl 0x51005404`, при успехе — вернуть блок |
| `0x51005404` | проверки аргумента, затем `bl 0x51004AD0` |
| `0x51004AD0` | **резолвер кучи**: `r4 = 0x5113B5AC` (глобальный объект карты), `r3 = [r4]` (карта), `sb = [r3+0x8C]` — **это и есть куча**, далее `bl 0x510049F4` (поиск свободного блока) |
| `0x510049F4` | поиск блока в куче; отрицательный результат — ошибка |

**Ключевой факт**: `map->[0x8C]` = **0**. Трап записей по `PA 0x4030498C` за весь
прогон даёт ровно **две** записи, и обе — ноль:

* `pc = 0x5101354C` — общее обнуление страницы;
* `pc = 0x510064D6` — инициализация самой карты (`0x510064A0-0x510064E2` — длинная
  серия `str r7,[r6,#…]`, где `r7` = 0; среди полей и `+0x8C`).

То есть карта **сама обнуляет** поле кучи и **никто и никогда не записывает туда
объект кучи**. Именно поэтому:

* сообщение печатает `(NULL)` — это буквально нулевой указатель кучи;
* `r4 = sb + 0x9C` при `sb = 0` даёт **`0x9C`** — а это ровно то «bogus address
  0x9C», которое с раунда 168 печатает подстановка `ZLB_NSKBL_NOLOCK`; теперь
  происхождение этого адреса объяснено;
* поиск блока в нулевой куче всегда терпит неудачу → аллокация возвращает 0 →
  печать → цикл повторяется.

Дальше: найти, кто обязан создать кучу (класс `SceKernelHeap` из таблицы имён
`0x510287C0…` — его дескриптор в живой памяти отсутствует, §8.17) и записать её в
`map->[0x8C]`; либо сознательно снабдить модель кучей (подстановка из арены), как
уже сделано для пулов объектов.

### 8.22 Раунд 179: у NSKBL есть рабочая арена, но объект кучи никто не создаёт

Дополнительные факты того же раунда:

* **поиск блока** в куче — `0x510049F4(heap, size, &out)`: `ubfx r1,r1,#1,#0xf`
  (размер в «гранулах» по 2 байта), затем `bl 0x5100B82C` — собственно обход
  структур кучи; при неудаче возвращается ошибка `0x80024501`. Так как `heap = 0`,
  поиск всегда неудачен — отсюда и сообщение. **Синтезировать кучу «наугад»
  нельзя**: нужен точный layout, который понимает `0x5100B82C`;
* трап записей по `PA 0x4030498C` дал ровно две записи, обе нулевые:
  обнуление страницы (`pc = 0x5101354C`) и инициализация карты
  (`pc = 0x510064D6`, серия `str r7,[r6,#…]`). Отдельно найдена **вторая** серия
  обнуления чужой структуры — `0x51005FE8-0x51006022` (`str r3,[r0,#…]`, `r3 = 0`),
  то есть поле `+0x8C` обнуляется в разных объектах; при этом в объекте, который
  настраивает `0x5100062C-0x51000664`, в `+0x8C` кладётся `0x2000` — значит
  `+0x8C` у разных классов означает разное (у карты — куча, у другого объекта —
  размер/гранула), и искать надо именно карту;
* **у NSKBL есть работающая арена**: `0x5101058C(size)` — bump-аллокатор:
  глобальная переменная `0x5113B61C` держит дескриптор арены, `[+0x14]` — лимит,
  `[+0x18]` — текущее смещение, замок — по `descriptor + 0x10`; при нехватке места
  возвращается 0. Именно ей карта выделяет свои таблицы
  (`0x510064E2-0x51006550`: два `bl 0x5101058C` и цикл по `0x1C`-байтовым записям).
  То есть память у NSKBL есть — **нет именно объекта кучи** (`SceKernelHeap`) в
  `map->[0x8C]`, и ни один код в модели его не создаёт.

Практический вывод для модели: если код создания кучи окажется в неисполняемой
инициализации, самый безопасный путь — не синтезировать кучу, а подставить
готовый объект кучи **того же layout**, который ожидает `0x5100B82C`, взяв его из
арены (`0x5113B61C`); для этого сначала нужно разобрать `0x5100B82C`.

### 8.23 Раунд 179 (продолжение): установщик классов обрывается на неудачной аллокации

Функция, которая печатает ошибки, оказалась **установщиком классов**:

* `0x510060B8(size)` — тонкая обёртка, которая зовёт аллокатор (`0x5100D49C`) и
  при нуле печатает `sceKernelAllocHeapMemory failed(NULL)`. У неё всего
  **четыре** места вызова — `0x51007E9A`, `0x51007EA8`, `0x51007EB4`,
  `0x51007EC0`, все внутри функции `0x51007E70` (той самой, что вызывает
  регистрации классов `0x51007EF8`/`0x510082CA`, §8.18/8.19), и размеры — те
  самые 12/32/64/44;
* дальше в `0x51007E70` идёт большой блок заполнения шаблона класса
  (`0x51007F20-0x51007F7E`: методы `0x51007739`, `0x51007769`, магика
  `0x4D95AEEC`, поля `+0x80…+0x94`), и он **не исполнен** — потому что установщик
  оборвался на первой же неудачной аллокации.

Отсюда причинно-следственная цепочка текущего состояния модели:

```
map->[0x8C] = 0 (кучи нет)
   → 0x510060B8(...) возвращает 0 и печатает ошибку
   → 0x51007E70 (установщик классов) обрывается, 0x51007F20+ не исполняется
   → классы/методы не установлены (в живой памяти есть только один дескриптор, §8.17)
   → одно ядро занято этим путём и не приходит на барьер
   → барьер ждёт 4-го (счётчик застыл на 3, §8.20) → livelock
```

Планируемое решение (следующий раунд): подстановка по образцу уже сделанных —
в точке `0x5100D418` (`bl 0x5100567C` в аллокаторе `0x5100D400`) при
`map->[0x8C] == 0` выделять блок **из модельной арены** и возвращать его, минуя
вызов, чтобы установщик классов дошёл до конца. Это должно дать сразу классы,
пулы и разомкнуть барьер.

### 8.24 Раунд 180: подстановка «блок из арены» сделана, измерена и **выключена по умолчанию**

Подстановка `ZLB_NSKBL_HEAP` реализована ровно как планировалось: в точке
`0x5100D418` (внутри аллокатора `0x5100D400`, перед `bl 0x5100567C`) модель
выделяет обнулённый блок из новой арены (`kHeapArenaVa = 0x01400000`, 1 МиБ, та же
dram-abs раскладка, что у остальных арен), кладёт его в `r0` и возвращается сразу
в `0x5100D41C` — то есть установщик классов получает память, хотя
`map->[0x8C]` по-прежнему нулевой. Дополнительно подстановка ограничена вызовами
**из установщика** `0x51007E70-0x51008400` (определяется по адресам возврата на
стеке), чтобы не менять поведение остальных вызывающих.

Результат измерен и оказался **не тем, что ожидалось**:

* подстановка срабатывает (лог: `NSKBL heap block 0x01400000 (12 bytes) ...`), и
  сообщения `sceKernelAllocHeapMemory failed` исчезают;
* но класс-инсталлятор после успешной аллокации уходит по **другой** ветке:
  регистрация `0x51007EF8`, которая раньше исполнялась, теперь **не исполняется**,
  блок шаблона `0x51007F20+` по-прежнему не исполняется, стадия `0xA8`
  (`0x51000CBC`) — тоже, чекпойнт остаётся `0xA7`.

Вывод: неудача аллокации в этом месте **обрабатывается** ниже по коду, и «подменить
память» недостаточно — расходится управляющий поток. Поэтому подстановка оставлена
в коде, но **по умолчанию выключена** (`ZLB_NSKBL_HEAP=1` включает; обычный прогон
по-прежнему печатает сообщения об аллокации и стоит на `0xA7`, то есть поведение
модели не изменилось). Настоящее решение — найти шаг, который создаёт объект кучи
(`SceKernelHeap`) и записывает его в `map->[0x8C]`, а не подменять блоки.

### 8.25 Раунд 181: протокол барьера NSKBL и что именно даёт подстановка кучи

Разобран **полный протокол барьера** (все адреса — Thumb-код NSKBL):

```
; 0x510158AC - "arrive"
510158C6  blx 0x5101474C            ; атомарно: [obj+6] = (my_index+1) mod 4   (токен)
510158CE  blx 0x5101477C            ; атомарно: [obj+4] -= 1, вернуть старое значение
510158E6  cmp r3,#4 ; bne 0x510158F0
510158EA  b 0x510158FE              ; сюда идёт тот, у кого старое значение было 4
510158F0  ldrh r2,[r4,#4] ; cmp r2,#4 ; bne 0x510158EC (wfe)   ; ждать [obj+4] == 4
; 0x510158FE - путь "победителя"
510158FE  ldrh r3,[r4,#4] ; cmp r0,#0 ; bgt 0x510158FA (wfe)   ; ждать [obj+4] == 0
5101590A  str r1,[r4]               ; [obj+0] = 1
5101590E  blx 0x5101474C            ; атомарно: [obj+4] = 4  ← ПЕРЕВЗВОД счётчика
51015916  blx 0x5101474C            ; атомарно: [obj+6] = 4  ← токен
5101591A  blx 0x510147D0            ; sev - разбудить остальных
```

То есть: каждое ядро **уменьшает** счётчик `[obj+4]`, четыре прибытия дают `4 → 0`,
последнее («победитель») перевзводит его в 4, ставит токен и делает `sev`, а
остальные ждут `[obj+4] == 4`. Значит наблюдение «счётчик стоит на 3» (§8.20)
означает **ровно одно прибытие**: три ядра до этого барьера не дошли. Измерение
подтверждает: у второго барьера в низкой странице (`VA 0x4034`) счётчик равен 2,
токен 3 (два прибытия), то есть 1 + 2 = 3 ядра «разошлись» по двум барьерам, а
четвёртое занято путём аллокации.

**Что даёт `ZLB_NSKBL_HEAP=1`** (измерено):

* барьеры **замыкаются и перевзводятся**: `0x5102B000` → `{01 00 00 00, 04 00 04 00,
  01 00 00 00, 04 00 04 00}`, низкая страница `VA 0x4034` → `{01 00 00 00, 04 00 …}`
  (было `02 00 03 00`) — livelock исчезает;
* но машина упирается в **штатную панику** NSKBL: все ядра крутятся в `0x51015B7C`
  (тот самый фатальный `b .`), вход — из `pc = 0x5100FE16`, а там проверка

```
5100FE0E  ldr r1,[r4,#0x10]      ; r1 = 0x40 (размер, записанный аллокатором)
5100FE10  cmp r1,r5
5100FE12  bls.w 0x5100FAC4       ; r1 <= r5 → продолжать
5100FE16  bl 0x51015B7C          ; иначе - фатально
```

то есть NSKBL проверяет **инвариант блока кучи** (`[block+0x10] <= предел`), и
поддельный обнулённый блок его не проходит (`0x40 > r5`).

Вывод: подстановка «блок из арены» действительно снимает livelock, но упирается в
настоящие инварианты кучи — значит путь к разблокировке один: **создать настоящий
объект кучи** (`SceKernelHeap`, имя `0x510287D8`) и записать его в `map->[0x8C]`.
Подстановка остаётся выключенной по умолчанию.

### 8.26 Раунд 182: NSKBL идёт по SAFE MODE — потому что boot-config пуст

Самая важная находка цикла. Диагностика `ZLB_NSKBL_MSG=1` (лог каждого нового
формата, попадающего в printf-ядро `0x51011078`) показала, что за весь прогон
NSKBL печатает **всего три** разных сообщения:

```
0x51027F20: ===================================================
0x510281BC: .Safe Mode : [ YES ]
0x5102889C: %d:0x%08x:0x%08x:sceKernelAllocHeapMemory failed(NULL), size=%d
```

То есть **NSKBL работает в SAFE MODE** — а это ровно тот режим, в котором
нормальная загрузка модулей `os0` не выполняется. Дальше — цепочка до причины:

1. печатает его код `0x5100100E-0x51001022` внутри функции `0x51000FA8` (той
   самой, что вызывает стадия `0xA7`):

```
5100100C  cbz r0,0x51001026        ; r0 из 0x51010F14 - «испециальный ли режим»
5100100E  bl 0x51000338            ; запрос флага
51001012  movw r1,#0x81BC; movt r1,#0x5102   ; формат ".Safe Mode : [ YES ]"
51001016  cmp r0,#0
5100101A  moveq r0,#2 / movne r0,#0          ; уровень сообщения
51001022  bl 0x51011B5C             ; печать
```

2. сам запрос тривиален:

```
51000338  movw r3,#0x4E98; movt r3,#0x5118   ; 0x51184E98
51000340  ldrb.w r0,[r3,#0x2D]               ; байт 0x51184EC5
51000344  and r0,r0,#1                       ; бит 0
```

3. «ворота» `0x51010F14` читают **структуру boot-config**:

```
51010F14  movw r0,#0xB61C; movt r0,#0x5113   ; 0x5113B61C - дескриптор загрузки
51010F1C  ldr r3,[r0]                        ; r3 = 0x00004000 (VA)
51010F1E  ldr r3,[r3,#0x3C]                  ; r3 = boot-config = VA 0x47C0
51010F20  ldrb r2,[r3,#0x33]; cmp r2,#0xFF   ; признак «конфиг валиден»
51010F2C  ldr r1,[r3,#0xC4]; and r2,r1,#0x7F ; режим/причина сброса (0xB, 0x4)
51010F46  ldr r3,[r3,#0xCC]                  ; маски клавиш: 0x54, 0xC0
```

4. **структура boot-config (VA `0x47C0`, PA `0x403047C0`) в модели пуста** — трап
   записей по `PA 0x403047C0-0x403048F0` даёт 142 записи, и **все они нулевые**
   (их делает инициализатор `0x51011D5C-0x51011DA8`). Значит `[+0x33] != 0xFF`,
   ворота возвращают 1, и NSKBL сообщает «Safe Mode : YES».

**Следствие**: нормальный путь загрузки (в строках образа рядом лежат
`psp2bootconfig.skprx` по `0x510281E4` и форматы путей `os0`, `%s:kd/%s` по
`0x510281FC`/`0x51028208`) не выполняется именно из-за пустого boot-config.
По подсказке владельца задачи: режим Safe/Normal определяется нажатыми кнопками,
а состояние кнопок обслуживает **Ernie (Syscon)** — то есть модель должна
предоставить NSKBL «ответ syscon» (состояние клавиш + причина сброса), из которого
и собирается эта структура. Замер §8.9 показывает, что NSKBL в MMIO-окно Kermit
ходит только к UART и GPO, значит обмен идёт **через разделяемую память/почтовые
ящики CMeP**, а не через MMIO.

Следующий шаг: найти этот обмен (кто и когда пишет boot-config `VA 0x47C0` из
ответа syscon) и научить модель отвечать «обычная загрузка, кнопки не нажаты».
Это и есть путь к настоящей загрузке `os0`.

**Где именно NSKBL говорит с syscon** (замер трапами по всему окну
`0xE0000000-0xF0000000`, фильтр `pc = 0x51xxxxxx`):

| Окно | Обращения NSKBL |
|---|---|
| `0xE2030000` | UART: 363 записи, 720 чтений (консоль) |
| `0xE20A0000` | GPO: 34 записи, 2 чтения (чекпойнты) |
| `0xE3100000` | SC (syscon): 6 записей, 7 чтений |
| `0xE3102000`, `0xE3103000` | по 1 записи и 2 чтения |

Раскладка обращений к SC: чтения `+0x0000` = **0x30**, `+0x0004` = 0, `+0x0300`,
`+0x0304`, `+0x0308` = 0, `+0x2100` = 1 (и чтение, и запись), `+0x31A4`, `+0x3124`
= 0; записи `+0x2100` = 1, `+0x0150…+0x0164` = `0x80C6305F`, `0x80C6305F`,
`0x80C6305F`, `0x730`, `0x730`, `0x730`, `+0x3010` = `0x00030003`. Код — ранний
инициализатор `0x51000B5A`/`0x51000B6A` и подсистема `0x51024B06-0x51024D94`.

В модели это окно **уже есть**: `hw/syscon.h` описывает `kScIfType = 0xE3100000`
(модель отдаёт 48 = `'0'`, и это ровно то, что читает NSKBL) и
`kScIfStatus = 0xE3101000` (`0x0001000F`), а канал команд CMeP — `0xE0B00000` /
`0xE0BF0000`. Значит дальше нужно разобрать именно те регистры `0xE3100150`,
`0xE3102100`, `0xE3100300-0x308`, `0xE3103010`, `0xE31031A4`, `0xE3103124`,
через которые ARM (NSKBL) получает от syscon сведения о загрузке, и научить
модель отвечать на них (обычная загрузка, кнопки не нажаты).

### 8.27 Раунд 183: инвентарь SC-регистров NSKBL и что на них отвечает модель

Проверено, что чтение типа интерфейса действительно проходит (код `0x51000B50`):

```
51000B54  movt r7,#0xE310
51000B5A  ldr r1,[r7]            ; тип SC = 0x30 ('0')
51000B60  and r6,r1,#0xFF
51000B66  sub.w r1,r6,#0x30      ; индекс поколения
51000B6C  cmp r1,#0x12           ; '0'..'B'
51000B74  mov.w r0,#-0x5FFF6000  ; 0xA000A000 - таблица допустимых поколений
51000B78  lsls.w r3,r0,r1        ; знак = бит (31-r1) маски
51000B7C  bpl 0x51000BA0         ; иначе - «не то поколение»
```

Маска `0xA000A000` имеет единицы в битах 31, 29, 15, 13, значит принимаются
поколения `'0'` (0x30), `'2'`, `'@'`, `'B'` — 48 (`'0'`), который отдаёт модель,
**входит** в набор, то есть эта проверка проходит.

Затем NSKBL читает состояние SC в структуру (`0x51024B06-0x51024B4A`):
`[0xE3100300]`, `[0xE3100304]`, `[0xE3100308]`, `[0xE31031A4]` (через
`0x51024C94-0x51024CBE`, вместе с указателем `0x51184BC0`) и `[0xE3102100]`,
ставит биты через хелпер `0x51024C00` (`tst`/`bic`/`orr` + `dmb`/`dsb`) и пишет
команду в `0xE3103010` (значение `0x00030003`).

Что отдаёт модель (замер `mem` в конце прогона):

| Адрес | Значение в модели |
|---|---|
| `0xE3100300` и далее | **0** (регистр не описан в `ScBridgeDevice`) |
| `0xE31031A0`/`0xE3103120` | **0** |
| `0xE3102100` | **1** (строб «запустить/шагнуть SC» смоделирован) |
| `0xE3103010` | **3** (запись ARM принята) |

Ключевой вывод раунда: **Никакой CPU-код и никакой DMA не заполняют
boot-config** — трап записей по `PA 0x403047C0-0x403048F0` даёт 142 записи и все
нулевые (их делает инициализатор NSKBL `0x51011D5C-0x51011DA8`), а `strb` по
смещению `+0x33` в образе NSKBL **вообще нет** (единственное обращение — чтение в
воротах `0x51010F20`). Значит структуру должен собирать сам NSKBL из сведений
syscon, и делает он это в ветке, которая в модели не исполняется: ворота
`0x51010F14` из-за нулевого `[+0x33]` уходят в «специальный» путь, где и
печатается `Safe Mode`, и нормальная сборка boot-config пропускается.

Следующий шаг: описать в `ScBridgeDevice`/Ernie регистры `0xE3100300-0xE3100308`,
`0xE31031A4`, `0xE3103124` так, как их отдал бы syscon при обычной загрузке
(кнопки не нажаты, причина сброса — обычная), и проверить, заполнится ли тогда
boot-config `VA 0x47C0` и уйдёт ли NSKBL из Safe Mode.

### 8.28 Раунд 184: подстановка «boot-config валиден» снимает Safe Mode (включена по умолчанию)

Сделана подстановка `ZLB_NSKBL_BOOTCFG` (по умолчанию **включена**,
`=0` выключает): в момент первого обращения к воротам `0x51010F20` модель пишет
`0xFF` в байт boot-config `PA 0x403047F3` (`VA 0x47C0 + 0x33`). Смысл: консоль,
которая уже загружалась, имеет этот признак сохранённым, поэтому подстановка
означает «boot-config валиден».

Измеренный эффект:

| Что | Без подстановки | С подстановкой |
|---|---|---|
| ворота `0x51010F14` | возвращают 1 | **возвращают 0** |
| код `0x51010F2C`, `0x51010F34` (ветка «валидного» конфига) | не исполняется | **исполняется** |
| печать Safe Mode (`0x5100100E`, `0x51001022`) | исполняется | **не исполняется** |
| исполнено 2-байтовых слотов NSKBL | 5804 | **6105** (+301 слот ≈ 600 байт) |

Новая исполняемая область (диф карт покрытия): хвост стадии `0x51001042-0x51001054`,
участок установщика классов `0x51007E88-0x51007EF8`, путь отчёта об аллокации
`0x510060CA-0x510060F8`, `0x510063D6-0x510063E2`, `0x5100D0A4-0x5100D0A8` (всего
182 диапазона).

Проверено и обратное: комбинация `ZLB_NSKBL_BOOTCFG=1` + `ZLB_NSKBL_HEAP=1`
**хуже** — поддельная куча снова приводит к штатной панике `0x51015B7C`, и
исполняется меньше кода (5783 слота). Поэтому подстановка кучи остаётся
выключенной, а marker — включён.

Текущее состояние по-прежнему `0xA7`, но теперь установщик классов доходит до
своей первой аллокации и обрывается на ней (блок шаблона `0x51007F20+` не
исполняется). Следующий шаг: дать NSKBL **настоящую** кучу (объект `SceKernelHeap`
в `map->[0x8C]`) — это единственное, что осталось между текущим состоянием и
дальнейшим путём (пулы → классы → стадия `0xA8`).

### 8.29 Раунд 185: layout кучи NSKBL и структура текущего deadlock'а

**Layout объекта кучи** (из поиска блока `0x5100B82C`, который вызывает
`0x510049F4`; сюда приходит `heap = map->[0x8C]`):

```
5100B832  mov r5,r0              ; r5 = heap
5100B842  ldrh r7,[r0,#0x20]     ; +0x20 (u16) - гранула
5100B844  ldr  r0,[r0,#0x1C]     ; +0x1C       - база
5100B848  blx 0x510258D0         ; = «округлить r0 вверх до кратного r1»
5100B850  blx 0x510258D0         ; то же для размера запроса
5100B856  ldrh r3,[r5,#0x32]     ; +0x32 (u16) - число классов размера
5100B858  cmp r3,r0; bls fail    ; индекс класса должен быть < числа классов
5100B85C  ldr  r1,[r5,#0x34]     ; +0x34       - таблица классов (u32 на класс)
5100B85E  ldr.w r5,[r1,r0,lsl#2] ; голова списка этого класса
5100B862  cmp r5,#-1; beq fail   ; -1 = класс пуст (код 0x80024403)
5100B86C  blx 0x51025AD4         ; вспомогательная арифметика класса
5100B870  mla r7,r7,r1,r5        ; адрес блока
5100B876  str r7,[r4]            ; *out = блок
```

Вспомогательные функции: `0x510258D0(r0,r1)` — округление `r0` вверх до кратного
`r1` (быстрый путь для степени двойки, иначе через `clz`); `0x51025AD4` — парная
арифметика размера/гранулы. То есть куча NSKBL — это аллокатор по классам размера
с таблицей `+0x34`, базой `+0x1C` и гранулой `+0x20`.

**Структура deadlock'а** (замер по каждому ядру в текущем состоянии, marker
включён):

| Ядро | `r4` (объект) | `LR` | Где стоит |
|---|---|---|---|
| arm0 | `0x5102B008` | `0x510158FF` | «победитель» барьера A, ждёт `[obj+4] == 0` |
| arm1 | `0x00004034` | `0x510158F1` | ожидающий барьера B, ждёт `[obj+4] == 4` |
| arm2 | `0x00004034` | `0x510158F1` | ожидающий барьера B |
| arm3 | `0x00004034` | `0x510158FF` | «победитель» барьера B, ждёт `[obj+4] == 0` |

Счётчик барьера A равен 3 — то есть на A пришло **только arm0**, а три остальных
ядра уже на барьере B. «Победитель» каждого барьера ждёт, пока счётчик дойдёт до
нуля (четыре прибытия), но на A их больше не будет, а на B не хватает arm0 —
**ядра разошлись по разным фазам**. Это прямое следствие того, что arm0 занят
путём консоли/аллокации (его фаза отличается от остальных), и именно поэтому
настоящая куча — не «косметика», а способ вернуть ядра в одну фазу: в раунде 184
подстановка кучи барьеры **замыкала и перевзводила** (значения становились
`04 00 04 00`), то есть фазы сходились.

Практический план на следующие раунды: собрать объект кучи в модели по этому
layout (база — новая арена, гранула, число классов и таблица классов с записями
`-1`/адрес блока), положить его в `map->[0x8C]` и проверить, что установщик
классов проходит аллокации без подделки блоков и ядра снова встречаются на одном
барьере.

### 8.30 Раунд 186: объект кучи в модели собран — и этого недостаточно

Объект кучи действительно собран и установлен: `ZLB_NSKBL_HEAP=1` теперь создаёт
его по измеренному layout (`+0x1C` = база, `+0x20` = гранула 16, `+0x32` = 256
классов, `+0x34` = таблица классов, все записи `-1`) и пишет указатель в
`map->[0x8C]` (проверено дампом: `PA 0x4030498C = 0x01401000`).

Измеренный результат — **ничего не меняется**: и без объекта, и с ним исполняется
ровно 5783 двухбайтовых слота, а фатальный `0x51015B7C` по-прежнему срабатывает.

Уточнён и сам источник паники: она приходит **не** из проверки блока, а из
проверки границ в процедуре копирования:

```
5100FD90  cmp  sb, sl
5100FD92  mov  r5, ip
5100FD94  bhi  0x5100FE16      ; sb > sl - «несогласованное состояние»
5100FD96  str.w r8,[r2,r1,lsl#2]
...
5100FDAA  ldr  r3,[r4,#0x10]   ; границы копии берутся из структур блоков
5100FDD8  add.w r2,lr,r1       ; цикл копирования по 0x10 байт до 0x100
```

То есть поддельные (нулевые) блоки не проходят внутренние инварианты аллокатора
— нужен либо настоящий аллокатор, либо блоки с правильными метаданными, а это
отдельный большой реверс (`0x5100F6CC`, `0x5100EF0C`, `0x5100E84C`).

**Решение по раунду**: подстановка кучи остаётся выключенной (по умолчанию), а
работа переносится на вторую часть цели — инфраструктуру GPU по `docs/GPU.md`
(окно регистров SGX, очереди команд, прерывания, MMU, формат командных буферов
GXM), где результат проверяется модульными тестами независимо от хода загрузки.
К boot-цепочке остаётся один известный шаг: научить модель создавать кучу
NSKBL так, как это делает прошивка (объект `SceKernelHeap` плюс блоки с
корректными метаданными).

Побочно в том же раунде:

* добавлена диагностика **`ZLB_NSKBL_LOG_CALLS=1`** — она логирует каждый вызов
  логгера NSKBL (`0x51011B5C`) с адресом вызывающего и указателем формата, что и
  позволило прочитать, что именно печатает прошивка;
* **консоль NSKBL печатает свой баннер** (те же строки, что у KBL, но со своим
  текстом): `Starting PSP2 Kernel Boot Loader (Non-secure) [0x%08x]: %d.`,
  `.BOOTSW.`, `..%d: 0x%08x [0x%08x]`, `: CP time.`, `: CP bid & version.`,
  `: USER.`, `: SDK(SCE).`, `: SHELL.`, `: debug control.`, `: system control.`
  (форматы по адресам `0x51027F58`, `0x51027F94`, `0x51027FA0`, `0x51027FB8`,
  `0x51027FC4`, `0x51027FD8`, `0x51027FE0`, `0x51027FEC`, `0x51027FF8`,
  `0x5102800C`) — то есть NSKBL доходит до своей консоли и печатает баннер, а
  сообщения про аллокацию идут уже после;
* у логгера есть косвенность: печать идёт через указатель `[0x5102B048]`, а
  объект-логгер лежит в `[0x5102B044]` (обёртка `0x51011AC8-0x51011B58`:
  `ldr r4,[0x5102B048]; cbz r4 → пропустить печать; blx r4`);
* методическое замечание: **линейный** дизассемблер (когда capstone идёт подряд
  от произвольного адреса) может «съехать» и показать несуществующие пары
  `movw/movt` — поэтому ссылки надо искать по-инструкционно (как делают скрипты
  в `_scratch`), а результат подтверждать трассировкой или трапом.

Дополнительные измерения того же раунда, чтобы не искать дважды:

* у NSKBL всего **четыре** инструкции `smc` (ARM-кодировка `0xE1600070`):
  `0x510002E4` — исполнена (та самая, что открылась в раунде 163),
  `0x51002BC4`, `0x51002BE0`, `0x510169E4` — **не исполнены**. То есть
  оставшиеся вызовы монитора идут *позже* текущего ожидания, значит ядра ждут
  не ответа монитора, а события от другого ядра/устройства;
* за весь прогон NSKBL обращается только к UART `0xE2030000` (1083 раза) и GPO
  `0xE20A0000` (36 раз) — таймеры, GIC и SDIF он не трогает вообще.

Отдельно проверено: подстановка «выдать пустой контейнер» для `map[0xD8]`
**уводит поток в сторону** — с ней `0x5100E850-0x5100EEA0` (инициализация
дескрипторов) уже не исполняется, поэтому подстановка отключена (её разбор
оставлен комментарием в `bootchain.cpp`).

**Что такое `seg02`.** Сегменты `kernel_boot_loader.self.segNN` (0x3C000-байтовый
`seg01`, 240-байтовый `seg02`, 103631-байтовый `seg03`) — это просто части
образа KBL, и `seg02` **загружается**: сравнение живой памяти с байтами сегмента
показывает его по `PA 0x4005C000` (сразу за `seg01`, заканчивающимся на
`0x4005C000`) ✓. Содержимое — **таблица устройств/консолей**: записи по 120
байт (240 байт = ровно 2 записи), в каждой:

```
+0x00 0, +0x04 1, +0x08 0x00040004, +0x0C 1, +0x10 0x00040004,
+0x14..+0x1C 0xFFFFFFFF, +0x20 0x600BF34C (тег), +0x24/+0x28 0xFF,
+0x30 1, +0x34 0x400B2998 (данные KBL), +0x38 0x40036A75 (Thumb-обработчик KBL),
+0x3C 0x1A002000 (регион: база 0x1A000000), +0x54 6,
+0x58.. 0xE2030000, 0xE2040000, 0xE2050000, 0xE2060000, 0xE2070000,
       0xE2080000, 0xE2090000, 0xE3105000   (окна MMIO: UART, второй консоль,
       DMA и т. д.)
```

Это согласуется с прежними наблюдениями о «таблице консолей» (`0x4005C058`,
окна `0xE2030070` и `0xE2040070`). Область **живая и переписывается самим KBL**:
трап записей по `PA 0x4005C000-0x4005C078` даёт `pc = 0x4003B3A2/0x4003B3AA`
(барьер KBL), `0x4002AE3C` и `0x4003A1A0` (все четыре ядра), а в живой памяти
поля `+0x14`, `+0x24`, `+0x30`, `+0x40` уже отличаются от исходных значений
сегмента.

**К NSKBL `seg02` отношения не имеет**: в образе NSKBL (дамп живой памяти)
**ноль** ссылок на `0x4005C0xx`, `0x400B2998`, `0x40036A75` и на тег
`0x600BF34C`. У NSKBL свои структуры: объект карты по `VA 0x4900`
(`PA 0x40304900`), свои данные по `0x5102B0xx`, причём там лежат значения той же
*формы* — `0x19442EA1` (`0x5102B030`) и `0x1A002000` (`0x5102B04C`), то есть
NSKBL описывает регионы/устройства собственными дескрипторами. Вывод: искать
недостающую инициализацию NSKBL нужно в её собственных данных и коде
(`0x5100xxxx`, `0x5102B0xx`), а не в сегментах KBL.
* Затем — `0xA6` (MMU включён, VBAR), `0xA7`, `0xA8` (загрузка ядра) и переход к
  `os0:psp2bootconfig.skprx` / `SceSysStateMgr` / `SceKernelBootimage`.

### 8.1 Монитор TrustZone (MVBAR) теряется: `PA 0x40000140` занят GIC

Отдельная находка того же раунда — почему в модели вообще нет мониторных
векторов. Трап записей (`ZLB_WTRAP=40000140-40000160`) показывает, что SKBL
**пишет** туда именно таблицу монитора:

```
pc=40037768..40037790   обнуление 0x140..0x15C
pc=400377EC             обнуление 0x140, 0x144
pc=400377F8             +0x148, +0x14C = 0xE59FF018   (ldr pc,[pc,#0x18])
pc=400377FC             +0x150 = 0xE59FF018, +0x154 = 0
pc=40037804             +0x158, +0x15C = 0xE59FF018
```

То есть KBL ставит заглушки монитора по `VA 0x16140 → PA 0x40000140` — это и
есть «SKBL Reset Vector» из вики (PA `0x40000000`), где `MVBAR+8` = точка входа
`smc`. Но:

```
map 0x40000140  ->  arm device=Kermit.GIC region=arm_priv read32=0x00000000
mem 0x40000140  ->  все нули
```

Страница отдана устройству `Kermit.GIC` (окно `0x40000000`-`0x4000FFFF`,
`kermit::kScuBase`), записи в неё уходят в устройство и до DRAM не доходят —
ровно та коллизия, о которой предупреждает комментарий в `bootchain.cpp`
(«the MPCore peripheral block … currently sits at `0x40000000+` … the block has to
move out of the DRAM window first»). Пока это так, любой `smc` из NSKBL идёт на
нули (`MVBAR+8 = 0x16148`) и уводит ядро в мусор.

Заодно видно, что подстановка модели ставит **identity**-маппинг для низких VA
(`boot window mapping supplied: arm0 VA 0x0001A12C -> PA 0x0001A12C`) и
восстанавливает таблицу исключений по `PA 0x16100`, тогда как KBL держит свою
страницу по `PA 0x40000100` — для одного и того же `VA 0x16100` в таблицах
живут два разных физических адреса, и «побеждает» тот, до которого дошёл обход.

**Следующий шаг**: перенести MPCore-блок (SCU/GIC/глобальный и приватный
таймеры) из окна DRAM `0x40000000+` (самотесты используют `kermit::kScuBase`
символически, так что правится константа), после чего мониторные векторы SKBL
должны дожить до `smc`, и можно разбирать обработчик `r12 = 0x103`.

**Сделано (раунды 162-163)**: блок перенесён в `0x1E000000`, окно DRAM осталось
за `kermit::kDramWindowBase = 0x40000000`; добавлено зеркалирование страницы SKBL
в низкую страницу, которую читает выборка вектора при выключенном MMU. Итог —
`0xA4` (§8.2). Оказалось, что `VA 0x16100` действительно имеет два физических
адреса: с включённым MMU это `PA 0x40000100` (страница SKBL), а при MMU off —
`PA 0x16100`; модели нужны обе.


### 8.31 Раунд 194: куча ставится раньше, паника ушла, остался один вызов с нулём

По подсказке задачи проверено, **где вообще берутся параметры кучи**. Измерения
трапами и трассировкой:

* поиск блока `0x5100B82C` впервые вызывается из `0x51004A0A` (внутри поиска
  `0x510049F4`) и получает `r0 = 0`, то есть куча в этот момент ещё нулевая;
* резолвер `0x51004AD0` читает поле `map->[0x8C]` при `r3 = 0x4900` (объект карты
  NSKBL), то есть использует именно ту карту, которую строит сам NSKBL;
* записи в объект карты (`PA 0x40304900` и окрестности) делает только сам NSKBL
  (`0x510064xx` — инициализация карты, и общее обнуление `0x5101354x`). Ранние
  стадии (KBL/CMeP) в это поле не пишут: от KBL в модели остаётся только блок
  передачи `PA 0x5102B000` и структуры ARM-загрузчика.

Вывод, совпадающий с подсказкой: параметры кучи **не приходят из
first_loader/second_loader/SKBL** — их должен построить сам NSKBL, но он этого не
делает в исполняемой части. Поэтому подстановка `ZLB_NSKBL_HEAP` перенесена на
**вход резолвера** `0x51004AD0` (раньше она стояла в аллокаторе `0x5100D418`, то
есть уже после первого использования) и строит объект с гранулой 1 и базой 1: при
таких параметрах хелперы сворачиваются, и адрес блока равен записи таблицы классов
(`block = table[index]`), поэтому таблица, заполненная страницами арены, отдаёт
настоящую память **штатным путём аллокатора**.

Измеренный эффект (подстановка `ZLB_NSKBL_HEAP=1`):

| Показатель | До (раунд 192) | Сейчас |
|---|---|---|
| фатальный `0x51015B7C` | срабатывает | **не срабатывает** |
| исполнено слотов | 5783 | **6105** |
| чекпойнт | `0xA7` | `0xA7` |

Остаток: часть вызовов поиска по-прежнему приходит с `r0 = 0` — это не путь
резолвера, а другой вызывающий `0x510049F4`, который берёт структуру не из
`map->[0x8C]`. Дальше нужно найти этого вызывающего (по трассировке
`0x510049F4` с разбором стека) и понять, какая структура у него должна быть на
самом деле; подстановка по умолчанию остаётся выключенной.


### 8.32 Раунд 194b: оба пути аллокации найдены, куча ставится до них — и что из этого вышло

Трассировка поиска блока `0x510049F4` с аргументами дала точную картину:

| Вызывающий | `r0` (куча) | Что это |
|---|---|---|
| `0x51004AFC` (резолвер `0x51004AD0`) | `0x01401000` (модельная куча) | работает |
| `0x51004C94` (второй путь аллокации) | `0` | срабатывает **раньше** резолвера |

Второй путь (`0x51004C74-0x51004C94`) читает **то же поле**:

```
51004C74  movw r2,#0xB5AC; movt r2,#0x5113   ; 0x5113B5AC - глобальная ссылка на карту
51004C7C  ldr  r1,[r2]                       ; объект карты
51004C7E  ldr.w fp,[r1,#0x8C]                ; fp = map->[0x8C] = куча
51004C82  add.w r8,fp,#0x9C                  ; замок
51004C92  mov  r0,fp
51004C94  bl   0x510049F4                    ; поиск блока
```

Поэтому установка объекта кучи добавлена и в точку `0x51004C7E` (перед чтением
поля). Результат измерен:

* сообщения `sceKernelAllocHeapMemory failed(NULL), size=12/32/64/44` **исчезают
  полностью** — то есть память в модели заработала, ни одна аллокация не
  проваливается;
* но поток уходит по другой ветке: исполняется 5432 слота (было 6105), снова
  срабатывает фатальный `0x51015B7C`, класс-инсталлятор до шаблона `0x51007F20`
  не доходит, пулы (`0x51009516`) и стадия `0xA8` тоже.

Вывод: подстановка «настоящей» кучи по измеренному layout снимает *симптом*
(провал аллокаций), но её семантика всё ещё расходится с ожиданиями прошивки —
при наличии памяти код идёт в ветку, где падает на другой проверке. Поэтому
подстановка остаётся **выключенной по умолчанию**, а правильный путь прежний:
создать кучу так, как это делает сама прошивка (объект `SceKernelHeap` плюс блоки
с корректными метаданными), то есть найти/включить её инициализацию.

Ответ на подсказку про ранние стадии (first_loader/second_loader/SKBL): по
трапам **параметры кучи оттуда не приходят**. Единственные записи в объект карты
NSKBL (`PA 0x40304900`) — собственные: инициализация карты `0x510064xx` и общее
обнуление `0x5101354x`. KBL оставляет в модели только блок передачи
`PA 0x5102B000` и структуры ARM-загрузчика. То есть куча — целиком дело NSKBL, и
именно её инициализация в исполняемой части отсутствует.


## 8.33 Новый цикл, раунд 196: найдена настоящая причина отсутствия кучи

Цепочка «нет кучи → нет sysroot → нет кучи» разобрана до конца. Поиск
инициализатора кучи по полям (`+0x1C`/`+0x20`/`+0x32`/`+0x34`) дал `1454`
совпадения, и все осмысленные — у *других* классов (у них эти смещения значат
другое: например, в объекте-дескрипторе области `+0x1C/+0x20` — это границы
адресов). Зато обход графа вызовов от незарегистрированного класса дал точный
ответ.

**Незарегистрированный класс — `SceKernelSysrootClass`** (имя `0x51028714`),
регистрируется в `0x51004F28` внутри функции `0x51004F00`. Цепочка вызовов:

```
0x51004F00 (регистрация SceKernelSysrootClass)
   <- 0x510057E2   (не исполнено)
0x51005700 (содержит этот вызов)
   <- 0x5100623E   ИСПОЛНЕНО
```

То есть вызывающий `0x5100623E` работает, а внутри `0x51005700` до регистрации
дело не доходит. Причина — ранний выход:

```
51005750  ldr.w sb,[r4,#0x12c]
51005754  ldr.w r7,[r4,#0x130]      ; r7 = размер (0x1000 = страница)
51005758  bl 0x5100460C ; blt выход ; проверка 1
51005762  ldr.w r0,[r4,#0x230]      ; r0 = объект физического раздела
51005766  mov r1,r7                 ; r1 = 0x1000
51005768  add r3,sp,#0x1C           ; r3 = &out
5100576A  bl 0x5100C04C             ; ← ЗАПРОС ОБЛАСТИ ПАМЯТИ
5100576E  cmp r0,#0
51005770  blt 0x51005718            ; ← В МОДЕЛИ ПЕРЕХОД СОСТОЯЛСЯ
51005772  cmp.w r7,#0x1000 ; beq …  ; эти ветки уже не исполняются
```

Внутри `0x5100C04C` видно, что именно проверяется:

```
5100C060  ldr.w sb,[r0,#0x9C]       ; sb = таблица записей по ядрам
5100C068  lsl.w r8,r0,#5            ; запись = 32 байта на ядро
5100C06C  add.w r7,sb,r8
5100C074  ldrh.w ip,[r7,#2]         ; ← счётчик областей в записи ядра
5100C078  cmp.w ip,#0
5100C07C  beq 0x5100C122            ; ← СЧЁТЧИК НОЛЬ → отказ
```

Замеры (живая память и трапы):

* объект раздела — `VA 0x5300` (рядом лежит строка **`ScePhyMemPartKD`**,
  `PA 0x403053A4`), поле `[+0x9C]` = `VA 0x5400` — таблица записей по ядрам;
* запись ядра 0 (`VA 0x5400`, `PA 0x40305400`): `[0] = 7`, `[+2] = 0` — то есть
  **счётчик областей равен нулю**;
* трап записей по `PA 0x40305400-0x40305420` за весь прогон даёт **только
  нулевые** записи от общего обнуления страницы (`pc = 0x51013548-0x51013554`) —
  таблицу областей никто не заполняет.

**Вывод**: корень кучи — не сама куча, а **пустая таблица физических областей
памяти** у раздела `ScePhyMemPartKD`. Из-за неё запрос области (4 КиБ) не
проходит, `0x51005700` выходит раньше времени, `SceKernelSysrootClass` не
регистрируется, sysroot не создаётся, куча не появляется — и всё дальнейшее
(установщик классов, пулы, стадия `0xA8`, загрузка модулей) не наступает.

Это согласуется с подсказкой про ранние стадии: области памяти — как раз те
параметры, которые консоль получает «сверху» (от secure world/загрузочной
конфигурации), а в модели они не заданы.

**Следующий шаг**: разобрать формат записи (`[0] = 7` — тип/идентификатор,
`[+2]` — число областей, далее, судя по коду `0x5100C07E+`, идут сами области) и
заполнить таблицу так, как это сделала бы конфигурация загрузки (основная память
`0x40000000`+ и остальные окна), после чего проверить, регистрируется ли sysroot,
появляется ли куча и идёт ли поток к стадии `0xA8`.


### 8.34 Раунд 197: ворота таблицы областей пройдены — чекпойнт ушёл с 0xA7

Сделана подстановка `ZLB_NSKBL_PHYSPOOL` (включается `=1`): она заполняет записи
таблицы физических областей раздела `ScePhyMemPartKD` свободными страницами
(`+0x02` = 7, `+0x04..+0x1C` = адреса страниц) и **дополняет их заново, когда
прошивка израсходовала все** (счётчик уменьшается самим кодом NSKBL).

Формат записи, восстановленный по коду `0x5100C07E-0x5100C0D8`:

```
+0x00 u16  тип (в живой памяти 7)
+0x02 u16  число свободных областей       <- проверяется и уменьшается кодом
+0x04 u32  значение области 0             <- выдаётся как результат запроса
+0x08 .. +0x1C  ещё шесть значений
```

Измеренный эффект (подстановка включена):

| Показатель | Без неё | С ней |
|---|---|---|
| обход записи `0x5100C07E`, выдача `0x5100C0AE` | не исполняется | **исполняется** |
| чекпойнт | `0xA7` | **`0xAD`** (data abort) |
| исполнено слотов | 6105 | 4457 |

То есть ворота открылись и поток двинулся дальше — но упирается в следующую
стену, и она измерена точно. Трассировка сбоев:

```
ARM fault arm0: VA=0x41501000 read pc=0x5100C014 lr=0x5100E687 (data)
```

NSKBL берёт выданное значение области и **читает по нему как по виртуальному
адресу** (`pc = 0x5100C014`, вызывающий — путь 4 КиБ `0x510058B0`). Значит
значения в таблице областей на железе — это не «сырые» физические адреса, а
адреса, которые менеджер памяти NSKBL уже отобразил (или которые он сам
отображает по этому запросу). Поэтому подстановка оставлена **выключенной по
умолчанию**: обычный прогон сохраняет прежнее состояние (`0xA7`, без паники), а
эксперимент включается `ZLB_NSKBL_PHYSPOOL=1`.

Следующий шаг: разобрать, что именно делает потребитель результата — функция
`0x5100C010` и вызов `0x51015268` в ветке 4 КиБ (`0x510058B0`: `r1 = 0x1061D006`,
`r2 = sb`, `r3 = sb - [r4+0x224]`) — и в каком виде менеджер памяти NSKBL ожидает
области (диапазон, который он отобразит сам, либо уже отображённый VA).


### 8.35 Раунд 198: семантика значения области разгадана — это указатель на номер страницы

Дизассемблирование потребителя выдало точную семантику:

```
5100C010  ldr r0,[r0]        ; значение области РАЗЫМЕНОВЫВАЕТСЯ как указатель
5100C012  lsls r0,r0,#0xc    ; и сдвигается на 12: *(value) - номер физической страницы
5100C014  bx lr              ; → r0 = физический адрес
```

То есть в таблице областей лежит не «сырой» физический адрес (как в первой
попытке), а **адрес слова с номером страницы**. Именно поэтому первый вариант
подстановки давал data abort (гость разыменовывал адрес как VA, которого у него
нет), а исправленный — работает: `0x5100C010` теперь исполняется, сбоев нет,
паники нет, чекпойнт вернулся в обычное состояние `0xA7`.

Заодно трассировка запроса области (`0x5100C04C`) показала, кто и сколько просит:

| Вызывающий | Размер запроса |
|---|---|
| `0x5100576A` (путь sysroot/`0x51005700`) | `0x10000` (64 КиБ) |
| `0x5100B9B4` | `0x10000` |
| `0x5100CBDA`, `0x5100CBE8`, `0x5100CBF8` | `0x4000` (16 КиБ) |
| `0x5100CC08` | `0x00100000` (1 МиБ) |

То есть таблица физических областей — общий аллокатор физической памяти NSKBL,
и запросы бывают разного размера, а моя подстановка выдавала записи по одной
странице 4 КиБ. Кроме того, запись сама уменьшает счётчик (`+0x02`) и обнуляет
использованный слот (`+0x04`), то есть расходуется прошивкой.

Итог раунда: паника снята, семантика известна, но путь `0x51005700` всё ещё не
доходит до `0x51005772` — значит запрос области либо всё ещё отвергается ниже
(например, по размеру), либо результат не принимается потребителем
(`0x51015268` в ветке 4 КиБ ждёт `r1 = 0x1061D006`).

Следующий шаг: выдавать область **нужного размера** (по `r1` запроса) — например,
в момент запроса формировать запись под конкретный размер, кладя в дескриптор
номер первой страницы подходящего диапазона, и проверить, доходит ли
`0x51005700` до конца, регистрируется ли `SceKernelSysrootClass` (`0x51004F28`) и
появляется ли куча в `map->[0x8C]`.


### 8.36 Раунд 199: почему запрос 64 КиБ отвергается — пустые списки по классам размера

Трассировка точки проверки после запроса области (`0x5100576E`) дала точный код
ошибки, который возвращается ядру:

```
trace pc=0x5100576E arm0 from pc=0x5100C0FA lr=0x5100C1B5 r0=0x80020005 r1=0x000000C0
      r2=0x600000DF r3=0x000000D0 r6=0x00004900 r7=0x00010000
```

То есть запрос 64 КиБ (`r7 = 0x10000`) возвращает **`0x80020005`** (ошибка
«нет памяти»), и вызывающий `0x51005700` уходит на выход `0x51005718` — именно
поэтому не регистрируется `SceKernelSysrootClass` и не появляется куча.

Дизассемблирование пути для размеров больше страницы (`0x5100C12A`) объясняет,
откуда ошибка:

```
5100C12A  bics  r0,fp,#0x33      ; проверка флагов запроса (fp = 0x10 → проходит)
5100C138  bne   0x5100C0F6       ; (иначе сразу 0x80020005)
5100C144  cmp.w r5,#0x100000     ; размер >= 1 МиБ → отдельная ветка
5100C150  clz   r3,r5            ; класс размера = 19 - clz(size)
5100C166  lsl.w r3,fp,#3         ; смещение в таблице классов
5100C176  cmp   r5,r4
5100C17A  movs  r0,#5 ; movt r0,#0x8002      ; 0x80020005
5100C180  ldr.w r8,[r8,#0xA0]    ; ← обход СПИСКА СВОБОДНЫХ ОБЛАСТЕЙ этого класса
5100C188  bne   0x5100C176
```

То есть для 4 КиБ работает запись по ядрам (её модель и заполняет), а для
16 КиБ / 64 КиБ / 1 МиБ NSKBL ищет узел в **списке свободных областей класса
размера** — связном списке через поле `[node+0xA0]` (узел не меньше 0xA4 байт:
ровно столько выделяет себе путь sysroot в `0x51005782`: `movs r0,#0xA4;
bl 0x5101058C`). В модели эти списки пусты, поэтому запрос и отвергается.

Итог: корень тот же — **загрузочная конфигурация физической памяти** (области по
классам размера), которую на железе готовит secure world/ранняя стадия, а в
модели не готовит никто. 4-килобайтная часть таблицы уже воспроизведена
(`ZLB_NSKBL_PHYSPOOL`), очередь за списками классов размера.

Следующий шаг: разобрать формат узла списка (`0x5100C176-0x5100C1D0`: что в нём
сравнивается с размером и что читает потребитель) и либо собрать списки в модели
(узлы по 0xA4 байта со ссылкой на диапазон), либо найти в прошивке код, который
их должен строить, и включить его.


### 8.37 Раунд 200: куча СОЗДАНА самим NSKBL — `map->[0x8C] = 0x5C00`

Точечная подстановка (`ZLB_NSKBL_PHYSPOOL=1`) в точке возврата запроса области
(`0x5100576E`): если запрос вернул ошибку, модель обнуляет код ошибки и кладёт в
выходной слот вызывающего (`sp + 0x1C`) адрес дескриптора с номером страницы —
ровно того, что читает потребитель `0x5100C010` (`*value << 12`).

Результат измерен:

* запрос 64 КиБ для пути sysroot считается удовлетворённым;
* **`map->[0x8C]` становится `0x00005C00`** — то есть NSKBL **сам создал объект
  кучи** (VA `0x5C00`), зарегистрировал `SceKernelSysrootClass` и прошёл
  инициализацию памяти. Это первое состояние за весь цикл, когда куча существует
  по-настоящему, а не подставляется моделью.

Новая (и последняя известная на сейчас) стена:

```
ARM fault arm0: VA=0x00030000 write pc=0x5100B4E2 lr=0x5100B4C7 (data)
```

NSKBL пишет по адресу `VA 0x30000` — это внутри его низкого окна
(`VA 0x0-0x3FFFF` → `PA 0x40300000+`), но модель эту страницу не подкладывает, и
запись уходит в data abort. Код записи — `0x5100B4E2`, рядом с конструктором
объектов NSKBL (`0x5100B41C`), то есть уже работает память/объекты нового цикла.

Следующий шаг: подложить низкому окну страницы `VA 0x30000-0x3FFFF`
(расширить сечение низкого окна либо добавить их в подстановку сбоев), после чего
проверить, идёт ли поток дальше — к установщику классов, пулам и стадии `0xA8`.


### 8.38 Раунд 201: низкое окно — эксперимент не помог, индекс найден не тот

С включённой кучей (`ZLB_NSKBL_PHYSPOOL=1`, см. 8.37) поток упирается в запись по
`VA 0x30000` внутри низкого окна NSKBL:

```
ARM fault arm0: VA=0x00030000 write pc=0x5100B4E2 lr=0x5100B4C7 (data)
```

Проверено, что низкое окно в модели раздаётся подстановкой `ZLB_KBL_LOWALIAS`
(точка `0x4003AD6C`, список индексов L2; по умолчанию «12» — окно кучи). Попытка
добавить индекс 3 (то есть `VA 0x30000`) **ничего не изменила**: сбой остался на
том же адресе и с тем же `pc`, то есть страница `VA 0x30000` отображается не этим
индексом (низкое окно строится собственным стором таблиц KBL, и соответствие
«индекс L2 ↔ VA» там другое).

Поэтому изменение откатано: значение по умолчанию снова «12», а отрицательный
результат записан здесь, чтобы не повторять попытку. Обычный прогон не изменился
(`checkpoint=0xA7`, паник нет).

Следующий шаг: разобраться, каким индексом L2 отображается `VA 0x30000` в
таблицах, которые строит KBL (трассировка точки `0x4003AD6C` с выводом `r4`
покажет нужный индекс), либо подкладывать страницу иначе — например, через
подстановку сбоев (`satisfy_arm_boot_fault`), которая уже умеет отдавать данные
для некритичных адресов. После этого с включённой кучей поток должен пойти к
установщику классов `0x51007E70`, построителю пулов `0x51009516` и стадии `0xA8`.


### 8.39 Раунд 202: попытки подложить `VA 0x30000` и уточнённая гипотеза

С включённой кучей поток пишет по `VA 0x30000` (`pc = 0x5100B4E2`) и получает
data abort. Сделаны три попытки закрыть это в подстановке сбоев
(`satisfy_arm_boot_fault`, точка входа после строки «VA 0x00100000 …»):

1. ветка для `VA < 0x40000` с установкой L2-записи (мелкая страница) по правилу
   низкого окна NSKBL `PA = VA + 0x40300000`, гейт — «стадия NSKBL»;
2. тот же код с гейтом «куча уже создана» (`[PA 0x4030498C] != 0`);
3. тот же код с гейтом «`pc` сбоя в диапазоне NSKBL» (`pc >= 0x51000000`).

Ни один вариант **не сработал**: сообщения подстановки не появляются, чекпойнт
по-прежнему `0xAD`, сбой остаётся на том же адресе и `pc`. Значит
`x` обработчик сбоев для этого доступа вообще не вызывается — то есть это,
скорее всего, **не translation fault**, а обращение по *уже отображённому* адресу
в физическую память, которой в модели нет (bus error). Тогда и «доописать»
таблицу нечего: надо либо поправить само отображение, либо подложить
соответствующую физическую страницу.

Добавленный код оставлен в модели (он безвреден: срабатывает только для
`VA < 0x40000` при `pc` в диапазоне NSKBL), но по умолчанию ничего не меняет —
обычный прогон по-прежнему `checkpoint=0xA7` без паники.

Следующий шаг: снять дамп таблиц для `VA 0x30000` в момент сбоя (L1-запись
TTBR0 для блока 0 и соответствующая L2-запись) и посмотреть, на какую физическую
страницу она указывает; затем подложить эту страницу (или исправить отображение).
Это должно снять последний известный сбой на пути с уже созданной кучей — и
открыть установщик классов `0x51007E70`, пулы `0x51009516` и стадию `0xA8`.
