# Отладчик

Отладчик один на два фронтенда: консольный (`zeliboba.exe`) и SDL3
(`zeliboba_ui.exe`). Вся логика — в классе `zlb::Debugger`
(`src/debug/debugger.h`), которая умеет выполнять текстовые команды и отдавать
готовые представления (дизассемблер, дамп памяти, регистры, трейс) для GUI.

Главный принцип: **любое действие доступно и командой, и из окна**, поэтому всё,
что вы делаете мышью, можно записать в скрипт и повторить.

## Запуск без интерактива

```powershell
build\bin\zeliboba.exe -ex "boot" -ex "run 200000" -ex "regs" -ex "quit"
build\bin\zeliboba.exe --script scripts\boot.cmd
```

## Команды

### Исполнение

| Команда | Что делает |
|---|---|
| `step [n]`, `s [n]` | выполнить `n` инструкций активного ядра |
| `run [n]`, `r [n]` | то же, что `step`, но с проверкой точек останова и наблюдения (двигает только активное ядро) |
| `runm [n]` | `n` «срезов» машины: все ядра идут своим бюджетом (256 инструкций), ARM-точки останова при этом точные |
| `until <addr>` | идти до адреса в активном ядре |
| `reset` | сброс машины |
| `core [mep\|arm\|arm0..arm3\|rl78]` | показать или выбрать активное ядро; `arm` выбирает ARM0 |
| `stage first\|second\|secure\|kbl\|nskbl\|kernel` | перевести цепочку загрузки на нужную стадию |

Важно: `run`/`step` двигают только активное ARM-ядро (плюс MeP и RL78), поэтому на
них `kernel_boot_loader` не проходит барьер четырёх ядер (`0x4003B384`): ядро 0
крутится в WFE-цикле `0x4003B3D6`, ожидая счётчик `0x4005C008`, который остальные
ядра уменьшают атомарным `ldrexh/strexh` (`0x4003A41C`). Для прогонов цепочки
используйте `runm` — он делает «срезы» всей машины, то есть шагает всеми четырьмя
ядрами, и проверяет точки останова по всем ядрам.

Точки останова в `runm` **точные и при этом не тормозят прогон**: перед каждой
ARM-инструкцией каждого ядра вызывается `Vita::pc_hook` (`src/machine/vita.cpp`), и при
совпадении срез обрывается *до* выполнения инструкции (PC остаётся на адресе bp).
Бюджет среза (256 инструкций на ядро) не меняется, поэтому KBL, до которого сотни
миллионов инструкций, отлаживается в реальном времени. Возобновление `runm` выполняет
инструкцию под точкой останова ровно один раз и ровно на том ядре, которое
остановилось (для этого у ядер на время прогона «паркуются» их собственные наборы bp,
иначе `Cpu::run` не даёт её выполнить). ARM-точки действуют на все четыре ядра, номер
ядра виден в сообщении: `[stop] arm1 breakpoint at 0x4002C602`.

Единственное исключение — точки наблюдения (`watch`) и точки останова на CMeP/Ernie:
они по-прежнему проверяются на границе среза (шины сравниваются по трассе), поэтому
при установленном `watch` бюджет ARM автоматически опускается до **одной инструкции
на ядро за срез** (ценой скорости).

Для раннего KBL trampoline `0x4003A140` проверяйте исходный `r2` и native
per-core allocation (`record+0x1BC` содержит top). `ZLB_KBL_CORE_STACK=<hex>`
задаёт шаг development fallback только для измеренного shared `r2=0x4000`;
`0` выключает его. Native tops `base+0x4000` сохраняются без bias. Для saved
return используйте `vpa`/`vmem`: нулевое слово в кадре и fetch VA0 могут быть
прямым возвратом по нулю, а не exception entry. `step` при установленном BP
может снова остановиться до инструкции; штатное `runm` возобновляет её один раз.

`history on` включает кольцо PC, `history arm 90` печатает последние 90 значений
PC (сначала старые, затем новые) — и для `run`, и для `runm`. Это основной способ
понять, *как* ядро оказалось в текущем состоянии (например, какая проверка
вывела KBL в заглушку `0x4003B724`).

### Инспекция

| Команда | Что делает |
|---|---|
| `regs` / `reg <имя> <знач>` | регистры активного ядра |
| `dis [addr] [count]` | дизассемблер; для ARM адрес виртуальный, используется выбранное ARM-ядро и его execution/security bank |
| `mem [addr] [rows]` | hex-дамп с ASCII-колонкой (**физический** адрес) |
| `vpa <va> [ttbr0]` | перевод VA через таблицы активного ядра ARM с печатью цепочки (TTBR, L1, L2, домен); второй аргумент переводит адрес в **другом** адресном пространстве (например, в пространстве припаркованного user-потока по его TTBR0 из сохранённого контекста) |
| `vmem <va> [rows]` | как `vpa`, затем hex-дамп по полученному физическому адресу |
| `vpoke <va> <val> [s]` | перевод VA (как `vpa`), затем запись по полученному PA |
| `poke <addr> <val> [8\|16\|32]` | запись в физическую память (например, подложить запись таблицы MMU) |
| `trace [n]` | последние `n` обращений к шине |
| `trace find <addr> [mask]` | кто и когда трогал адрес |
| `devices` | список MMIO-устройств всех трёх шин |
| `devget <dev>.<reg>` | прочитать именованный регистр |
| `devset <dev>.<reg> <v>` | записать именованный регистр |
| `emmc info` / `emmc read <lba> <count>` | состояние карты и чтение блоков |
| `keyring` | захваченные keyring-значения, история `ClearFlags`, счётчики Bigmac/Bignum/SC |
| `cov [mep] [start] [bytes]` | карта покрытия PC: постранично «сколько сайтов исполнилось», плюс самые длинные неисполненные участки. `ZLB_ARM_COV=1` / `ZLB_MEP_COV=1` включают карту; окно задают `ZLB_ARM_COV_BASE`/`_SIZE` (для CMeP — `ZLB_MEP_COV_BASE`/`_SIZE`), шаг — `ZLB_*_COV_GRAN` |
| `cov save <file> [mep]` | записать сырой битмап (по биту на `gran` байт); сводку по образам и проверку точек входа считает `tools/cov_report.py` |
| `boot` | отчёт по цепочке загрузки + план |
| `faults [all]` | кольцо отказов MMU ARM-ядер: `VA`, `pc`, `read/write/fetch`, вид отказа, дескрипторы L1/L2, домен, счётчик повторов (без `all` — только активное ядро) |
| `info` | активное ядро, статистика шины, состояние |
| `event` | состояние сессии событий (ETW-стиль) и фильтра вида |
| `event on\|off` / `event clear` | запись событий включить/выключить; очистить записи и счётчики |
| `event level <lvl>` / `event keyword <mask>` | уровень сессии и подписка по ключевым словам (`boot`, `storage`, ..., `all`, `default`, hex) |
| `event enable\|disable <провайдер\|область\|all>` | подписка сессии на провайдера или область |
| `event providers` | манифест: область, состояние, счётчики, GUID |
| `event dump [n]` / `event stat [n]` | последние записи / сводка Count, Weight, %Weight, min/max |
| `event activities [n]` / `event timeline [buckets]` | пары Begin/End с длительностями / гистограмма по областям |
| `event filter ...` | фильтр вида (`level`, `keyword`, `provider`, `area`, `text`, `time`, `kind`, `clear`), общий с панелью Events |
| `event save <file.csv>` | экспорт отфильтрованных записей в CSV |
| `load <file> [addr]` | загрузить образ в шину активного ядра |
| `savestate <file>` | записать полный снапшот машины: RAM, все устройства, ядра, ключи и цепочка загрузки |
| `loadstate <file>` | восстановить снапшот и продолжить прогон ровно с этой точки |

Зачем `vpa`/`vmem`: `mem` читает физическую память, а `kernel_boot_loader`
**перестраивает свои таблицы страниц по ходу загрузки**, поэтому один и тот же объект
живёт по разным физическим адресам на разных этапах (на этом потеряно несколько
раундов, см. `docs/KBL.md`). Перед дампом объекта всегда лучше сначала спросить
`vpa <va>`.

ARM `dis` и SDL Disassembly читают instruction bytes через RAM-only inspection
таблиц выбранного ядра. Branch targets остаются VA; Thumb32 может пересечь
страницу с несмежным PA. Inspection не меняет CPU/MMU state, fault records,
bus context/statistics/trace и не читает MMIO. При отсутствии mapping или RAM
показывается `<unavailable: ...>`, а не выдуманная instruction из `FF`.
Это отличается от явно физического `mem`/`save`; адрес этих команд не переводится.
Tests: `build/goal-debug-arm-inspection-tests.log`.

Для boot-mode проверяйте фактическую цепочку `Sysmem global → sysroot+0x3C → param`
на выбранном ядре через `vpa`/`vmem`. В captured 1.04 kernel это
`VA 0xCE328 → VA 0x4000 → VA 0x47C0`; адреса относятся к этому размещению модулей.
Текущая ранняя board handoff копирует Ernie NVS `0x4A0/0x481/0x483` в param
`+0x30/+0x31/+0x33`, с `+0x32=0`: свежий NVS даёт `FF FF 00 FF`.
`+0x6C=4` — существующий retail/product профиль. Staging частично обходит native
second-loader builder, поэтому наличие записи не доказывает его исполнение.
`IsUpdateMode` проверяет byte `+0x30 != FF`, `IsExternalBootMode` — bit0 слова `+0x6C`.
Опция `ZLB_NSKBL_BOOTCFG` удалена вместе с поздним marker, который менял эти входы;
текущие измерения делают без неё. Provenance и отменённые выводы описаны в
[KBL §6](KBL.md#6-boot-контекст-и-scekblparam) и [NSKBL §4.7](NSKBL.md).

### Save states

`savestate <file>` пишет один файл со всем состоянием машины: RAM-регионы и
общие буферы, регистры и внутренние поля каждого MMIO-устройства, четыре
ARM-ядра, CMeP, Ernie/RL78, keyring и флаги цепочки загрузки. `loadstate <file>`
возвращает машину в это состояние, поэтому холодная загрузка на 2.5 минуты
перестаёт быть обязательной для каждой итерации. Непрерывный прогон и прогон
после `loadstate` совпадают бит-в-бит; это проверяет шаг `save state
determinism` в `verify.ps1` и тесты `state_*` в `zlb_tests`.

* Образ eMMC — внешний вход: в файл попадают путь и размер карты, но не сам
  образ. Загрузка состояния с образом другого размера отвергается, с другим
  путём — предупреждает.
* RAM пишется по битмапу ненулевых страниц по 4 КиБ, поэтому снапшот ранней
  загрузки занимает килобайты, а не сотни мегабайт.
* Формат версионирован, разбит на именованные секции и снабжён контрольной
  суммой: файл от другой сборки или повреждённый отвергается с сообщением, а не
  читается молча.
* Контракт для новых устройств описан в [SAVE_STATE.md](SAVE_STATE.md).

Нужен там, где `kbl_xref.py` привязан к KBL: примеры — NSKBL (`--image ...\SLB2_dec\nsbl.bin --base 0x51000000 --entry 0x51000100 --arm`) |

### Точки останова и наблюдения

| Команда | Что делает |
|---|---|
| `bp [mep\|arm\|rl78] <addr>` | точка останова |
| `bpc <addr>` / `bpl` / `bpcall` | снять / список / снять все |
| `watch <addr> [rwx]` | точка наблюдения за памятью |
| `watchc [id]` / `wpl` | снять / список |

Точки наблюдения реализованы через кольцевой трейс шины: перед каждым шагом
запоминается номер последней записи, после шага просматриваются новые записи во
всех трёх шинах и сверяется адрес с маской. Поэтому точка наблюдения срабатывает
на **любое** обращение, включая MMIO, и показывает значение, PC и имя устройства.

### Прочее

| Команда | Что делает |
|---|---|
| `log trace\|debug\|info\|warn\|error\|off` | уровень логирования |
| `sc` | последние 32 SC-команды к Ernie с именами из таблицы USS-1001 (кольцо собиралось всегда, но читать его было нечем) |
| `ZLB_DMA_TICKS=<n>` (переменная окружения) | бюджет передачи DMA в тиках (по умолчанию 1000): движок держит busy и завершается по тикам, после чего поднимает прерывание канала |
| `ZLB_DMA_IRQ=<n>` (переменная окружения) | включает прерывание завершения DMA на канале `n` (по умолчанию канал `0x7C` display-модуля). В обычном режиме прерывание **не** поднимается: окно `Kermit.DmaWin` на дверной звонок (`+0x020`) сразу заявляет busy (`+0x24=1`) и готовые каналы (`+0x28=3`), а движок снимает busy по бюджету передачи; гость опрашивает эти два слова. Если поднять прерывание, поток display-модуля засыпает на событии завершения и не программирует scanout (проверено: `IFTU0` остаётся без буфера). Сама передача данных не моделируется — байты не двигаются |
| `nid <0xNID>\|текст>` | база NID из vita_loader (`tools/gen_nid_table.py` → `src/debug/nid_table_data.cpp`, 8614 функций): имя по NID или поиск по имени. Один NID может принадлежать нескольким библиотекам — печатаются все совпадения |
| `help` | полный список |

## Ловушки шины (переменные окружения)

Когда нужно понять, кто в гостевом коде трогает конкретную физическую память,
удобнее не отладчик, а ловушки шины (они пишут в stderr и не тормозят прогон
проверками на каждом шаге):

| Переменная | Что делает |
|---|---|
| `ZLB_WTRAP=<lo>-<hi>` | печатает каждую **запись** в диапазон: регион, смещение, размер, значение, `pc` гостя, ядро |
| `ZLB_RTRAP=<lo>-<hi>` | то же для **чтений** — так восстанавливаются параметрические блоки (`[rtrap] arm_bootrom +0x001C4 r4 = 0x0 pc=4002028C core=ARM Cortex-A9`) |

Обе ловушки покрывают все ширины доступа (8/16/32/64). До этой правки
slow-path `Bus::read16` был единственным аксессором, который **не** сообщал о
себе, поэтому 16-битные чтения MMIO не появлялись в `ZLB_RTRAP` — окно
`0xE3320000` из-за этого выглядело как «только записи» (см. `docs/STATUS.md`).
Если диагностика «ничего не видит», проверьте ширину доступа: `ldrh`/`strh` —
это ровно тот случай, который раньше терялся.

### WSL: переменные надо передавать через `WSLENV`

Эмулятор — Windows-бинарник, и WSL **не** передаёт ему своё окружение: строка
`ZLB_ARM_PC_LOG=pc.log ./build/bin/zeliboba.exe …`, запущенная из Linux-шелла,
не увидит переменную, и диагностика будет молча бездействовать (выглядит как
«фича не работает»). Запускайте через `./run-wsl.sh` — он сам собирает все
`ZLB_*` и публикует их в `WSLENV`:

```bash
ZLB_ARM_TRACE_RANGE=0x4F9D00-0x4F9E00 ZLB_ARM_TRACE_LIMIT=200 \
    ./run-wsl.sh -q -ex "loadstate scratch/s600k.state" -ex "runm 20" -ex "quit"
```

`run-wsl.sh` кладёт в `WSLENV` только имена переменных: относительные пути
(`ZLB_ARM_PC_LOG=scratch/pc.log`) резолвятся от текущего каталога (корень
`zeliboba/`). Бинарник выбирается `ZLB_BIN` (`zeliboba` по умолчанию,
`zeliboba_ui` для SDL3, `zlb_tests` для самотестов).

## Примеры

```
# first_loader: догнать до опроса mailbox и посмотреть, что он видит
core mep

regs

# проверить, что keyring 0x501 действительно опрошен
watch 0xE0030028 w

# посмотреть, что происходит с eMMC после SC-команды
core arm
emmc info

# трассировка событий: что заняло время на старте загрузки
event level verbose

```

## Что показывает SDL3-фронтенд

* **Disassembly** — дизассемблер с подсветкой PC и точек останова, `Enter` ставит
  точку останова на выбранной строке, есть переход по адресу;
* **Registers** — регистры с подсветкой изменившихся;
* **Memory** — дамп памяти с перелистыванием;
* **Events (F4)** — трассировка событий в стиле ETW: Graph Explorer по областям
  и провайдерам (клик фильтрует вид, чекбокс — подписку сессии), стековая
  гистограмма «Utilization by area», полоса «Trace Rundown», дорожки
  Begin/End-активностей и маркеров одиночных событий, таблица записей
  (со сводкой Count/Weight по `s`) и экспорт CSV по `e`
* **Trace** — последние обращения к шине с именами устройств;
* **Devices** — список устройств и регистры выбранного;
* **Boot** — отчёт по стадиям и быстрые кнопки `stage ...`;
* **Display / Panel (F8)** — guest framebuffer, выбранный настоящими IFTU
  registers; для поддержанного RGBA8888 subset frontend показывает RGB
  как непрозрачное изображение;
* **Console** — строка ввода, привязанная к `Debugger::execute`, с историей и
  автодополнением по `Tab`.

Горячие клавиши: `Space` — пауза/пуск, `F10` — шаг, `F11` — шаг с заходом,
`F1..F8` — вкладки, `Esc` — закрыть строку ввода. В шапке любой вкладки есть

(тот же путь, что `runm`).
