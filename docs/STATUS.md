# Состояние проекта Zeliboba (эмулятор PS Vita)

Документ — сводка «где мы сейчас»: что в эмуляторе работает и чем это
подтверждено, чего не хватает до цели, какие места модели являются
**подстановками** (development substitution) и что делать дальше. Рабочий журнал
по звеньям цепочки — `docs/KBL.md` (раунды 1-43), по железу — `docs/HARDWARE.md`,
по eMMC — `docs/EMMC.md`, по Syscon (Ernie), DRAM и JIG — `docs/SYSCON.md`,
по NSKBL (небезопасный загрузчик ядра) — `docs/NSKBL.md`, по отладчику —
`docs/DEBUGGER.md`.

## 1. Цель

* **Stage 1** — загрузить ядро (os0) прошивки 1.04 на ARM (Kermit): цепочка
  Syscon → CMeP first loader → second loader → secure kernel → ARM
  (secure world) → NSKBL → `os0:psp2bootconfig.skprx` → SceSysStateMgr.
* **Stage 2** (после ядра) — движок Venezia MPE (реверс `vnzimg`) и PowerVR
  SGX543MP4+ на OpenGL с шейдерами, чтобы LiveArea отрисовала картинку.

Stage 1 **не достигнут**: ARM доходит до исполнения `kernel_boot_loader`, проходит
инициализацию (сотни миллионов инструкций) и останавливается в цикле регистрации
объектов `0x4002BD16…0x4002BD6E`, потому что boot-контекст, откуда берутся эти
объекты, пуст (см. §3).  CMeP при этом проходит рукопожатия `0x9/0x101/0x102/0x106`
и отрабатывает 117 тыс. инструкций secure kernel.

## 2. Что работает (и чем подтверждено)

| Что | Подтверждение |
|---|---|
| Сборка и самотесты | `build.ps1`; `zlb_tests.exe`: **411 прогонов / 0 падений** (раунд 92 закрыл последние 12 «известных» — см. §7) |
| Реконструкция eMMC из PUP | `verify.ps1` → «verify OK»: 992 файла, 0 расхождений, MBR/SLB2/os0/vs0 |
| Первый загрузчик CMeP (MeP) | реальный дамп `dumps/vita_prototype_bootrom.bin` в окне 0x5C000; SUCCESS + передача на 0x40000 |
| Вторая стадия CMeP | исполняет SLB2-образ из eMMC (4121 чтение eMMC, idstorage в DRAM, SC-команды); заканчивается вызовом сервиса `jmp 0x5FF00` |
| Secure kernel (0x800000) | грузится по своему адресу компоновки, проходит стартовые проверки keyring/sysctl/версии, рукопожатие 0x9/0x101/0x102/0x106 |
| Отпускание ARM | по «done»-прыжку secure kernel: `release_soc()` → `ARM started on kernel_boot_loader at 0x40020000` |

| NSKBL | **обычный прогон доводит NSKBL до чекпойнта `0xA1`** (раунд 161): KBL проходит стадию boot-setup (`0x88`), сам распаковывает NSKBL (`sceArlzDecode` 0x4003C330 + `sceArlzArmFilter` 0x4003CB40: поток `0x50000004` → `0x51000000`), рапортует `0x89` и передаёт управление в Non-Secure через `0x40021AE0` (`SCR.NS=1`) — `docs/NSKBL.md` §7.6-7.7. Стадия `stage nskbl` тоже доходит до `0xA1` (self-тест `machine_nskbl_stage_decodes_the_non_secure_loader`); дальше NSKBL уходит в Monitor-режим, и стена — secure-вызов `smc`/`r12=0x103` |
| Консоль прошивки | команда `console`/`uart` показывает вывод KBL (регистр данных `+0x70` блоков 0xE2030000/0xE2040000) |
| Отладчик | `run/runm/step/until/bp/bpc/bpl/watch/wpl/regs/dis/mem/poke/save/trace/devices/map/devget/devset/emmc/gpo/console/bootctx/faults/boot/stage/keyring/info/load/log` |
| SDL3-фронтенд | `zeliboba_ui` (видео/звук/ввод), скриншоты через `--screenshot` |

Цепочка шагов 1-4 вики проходится **автоматически** в обычном прогоне (`boot` +
`runm`), без команд `stage`.

## 3. Чего не хватает до Stage 1

0. **Цепочка от first_loader доходит до ARM KBL, KBL — до распаковки NSKBL и до
   передачи в Non-Secure.** Раунд 154: сняты две
   стены SC-протокола во второй стадии — регистр событий `0xE31000C0` (CMeP ждёт
   ровно `1`, ARM — биты 3/4) и «защёлка» статуса `0xE3101000` (CMeP пишет в неё
   `0x0001000F`, а позже `0`, и оба раза опрашивает), плюс окно `CMeP.SecureCtl`
   расширено до 128 КиБ (вторая стадия трогает `0xE3110C00`). Теперь холодный путь
   второй стадии **доходит до конца**: `jmp 0x5FF00` → secure kernel (117 083
   инструкции) → возврат → отпускание ARM.
   Раунды 156-158: окно кучи KBL (`VA 0x12000`) делило физическую страницу с
   класс-дескрипторами на `PA 0` — теперь подстановка по умолчанию выделяет ему
   свою страницу (`ZLB_KBL_LOWALIAS=12`); затем выяснилось, что дальше держала
   подстановка арены экземпляров (`ZLB_KBL_INSTANCE_BLOCK`, теперь выключена), и
   KBL вошёл в свою стадию boot-setup `0x400204A8` (чекпойнт `0x88`).
   **Раунды 159-160**: найдена и исправлена настоящая ошибка ядра ARM —
   `ldmia sp!, {…,pc}` не применял write-back, из-за чего arzl-распаковщик KBL
   (`0x4003C484`) возвращался с `sp` на `0x24` ниже и стадия срывалась в
   `pop {…,pc}` с нулём (тест `arm_ldm_with_pc_in_list_still_writes_back`);
   добавлен сторож сна кластера (все ядра в `wfe` → разбудить, а запаркованные
   счётчики барьера выставить в ожидаемое значение). После этого стадия проходит
   целиком: KBL **сам** вызывает `sceArlzDecode`/`sceArlzArmFilter`
   (`0x4002058E`/`0x4002059E`, поток `0x50000004` → `0x51000000`), пишет
   **чекпойнт `0x89`** и уходит в Non-Secure через ARM-помощник `0x40021AE0`
   (`SCR.NS = 1`). **Раунд 161**: «стена входа в NS» тоже оказалась ошибкой ядра —
   `RFE` грузил `PC` и `CPSR` в обратном порядке (`CPSR ← [addr]`, `PC ← [addr+4]`),
   поэтому `rfeia sp!` на `0x40021AFC` клал в CPSR `0x51000000` и прыгал на `0x93`.
   После исправления (PC из адресуемого слова, CPSR из следующего; тест
   `arm_rfe_restores_cpsr_and_pc` переписан) **NSKBL запускается естественным
   путём**: `trace pc=0x51000000 … from pc=0x40021AFC`, `SCR=0x5`, и прогон
   рапортует **чекпойнт `0xA1`** («NSKBL: core 0 (non-secure) pre-init complete»).
   Цепочка first_loader → second_loader → secure_kernel → ARM KBL → NSKBL
   проходится без команд `stage` (`docs/NSKBL.md` §7.5-7.7).
1. **ARM boot-контекст пуст.** Вторая стадия либо копирует контекст из DRAM
   (0x40000000) в scratch (`memcpy` 0x40A86), либо идёт по «холодной» ветке
   0x40858 — выбор делает бит 7 слова, полученного от syscon командой 0x0010
   (get_version), и в нашем прогоне он равен нулю; источник в DRAM при этом
   остаётся нулевым.
2. **KBL строит карту, в которой сам же и тонет** (раунд 47 в `docs/KBL.md`,
   команда `faults all`): из 256 записей L1 рабочая только `L1[0] = 0x80200181`
   (coarse), в L2 — ровно 8 записей `VA 0x0000-0x7FFF → PA 0x40118000` (копия
   низких 32 КиБ). Первое же обращение по `VA 0x40000` (`pc=0x400321B6`, чтение
   таблицы регионов, которую KBL держит в scratch по VA 0x51C0) даёт data abort,
   уходит на `VBAR+0x10 = 0x16110`, а эта страница не отображена → prefetch abort
   на `0x1610C` → `exception loop`.
   **Раунд 48:** подстановка низкого окна (`fault_hook`, отключается
   `ZLB_NO_SUBSTITUTION=1`) + страница векторов PA 0x16100 снимают это падение:
   ARM идёт дальше и упирается в ассерт `0x40034A18`
   (`obj->field != global` при `obj = NULL`) → `bl 0x4003B724` = `b .`.
3. **Менеджер объектов (`ctx+0x8C`) не создаётся: раздел памяти KBL пуст** (раунды
   50-51 в `docs/KBL.md`). Менеджер создаёт **сам KBL** — функция `0x4002BAF8`
   (вызов из `0x4002C602`), она выделяет два объекта (`+0x84`, `+0x88`), зовёт
   `0x4002AA0C` (успех) и затем просит у раздела `0x51C0` блок 0x1000
   (`malloc`-блоков `0x40032278`, аргументы `r0 = 0x51C0`, `r1 = 0x1000`,
   **`r2 = 0x10`** — не 0xA, как было записано в первой редакции раунда 50) →
   **`0x80020005`**, после чего функция выходит в `0x4002BB10`, **не записав** `+0x8C`
   (дамп контекста VA 0x4900/PA 0x4011C900: `+0x8C = 0`). Причина отказа: у раздела
   пуст кэш блоков 0x1000 (`[pool+0x9C] = 0x52C0`, у всех 4 слотов `[+2] = 0`,
   `[+4] = 0`), а флаг 0x10 (`bics flag,#0x21` ≠ 0) запрещает нарезку новых блоков.
   **Замер на 230 млн инструкций: таблица кэша записывается ровно 37 раз, и все
   записи — из собственной инициализации раздела** — то есть KBL ни разу не
   добавляет в раздел память, хотя все 15 мест вызова аллокатора просят блоки
   (0x1000…0x100000). Вывод: раздел должен приходить **уже наполненным** от
   предыдущей ступени (ARM boot context / secure world) — это и есть недостающая
   «карта памяти». Попытка подставить нарезку (`ZLB_ALLOC_CARVE=1`) уводит ядра в
   вечный спин в мьютексе раздела (`0x4003A1B0`), поэтому она **выключена по
   умолчанию** и оставлена как эксперимент.
4. **Ответ syscon «hardware info»** (0x446F2 → 0x44274 → 0x44246, команда
   0x0010 и соседние) содержит только то, что подтверждено вики; для сборки
   контекста нужны поля, которых у модели нет.
5. **Окно `0xECxxxxxx`** (Pervasive/DMAC и прочее), в которое KBL пишет и читает
   (`pc=0x400209E4…0x40020A36`), в модели ARM отсутствует — чтения дают 0.
6. **Per-console ключи** (keyring 0x213) отсутствуют в дампах — из-за этого
   SMI/record/SCE-проверки второй стадии заменены подстановками (см. §4).

## 4. Подстановки (development substitution)

Все они отключаются переменной `ZLB_NO_SUBSTITUTION=1` (тогда поведение
воспроизводит нерешённую проверку и загрузка останавливается там, где
останавливалась бы без ключей).

| Место | Что сделано | Где |
|---|---|---|
| SMI: подпись, два keyed-контроля | ветки-проверки очищены | `src/hw/cmep/bigmac.cpp` |
| Configuration record: MAC-проверки 1-3, дайджест записи 0x0F | ветки очищены | там же |
| SCE: диспетчер команд и валидатор ответа | результат форсирован | там же |
| SMI RSA | результат форсирован | там же |
| ARM boot ROM | нет дампа → шаг реализован на C++ (стейджинг second_loader в SRAM + ящик 0xE0000010) | `src/machine/bootchain.cpp` |
| Сервис first loader'а `0x5FF00` | нет кода в дампах → перехват `pc_hook` и перезапуск CMeP в `secure_kernel.enp` | там же |
| Рукопожатие secure kernel | нет доставки прерываний в MeP → ответ ARM превращается в событие `state = 9` | там же |
| Пробуждение CMeP | нет доставки прерываний в MeP → после записи события `state = 9` модель снимает `halted` (цикл `0x80045E`/`0x800488` перечитывает состояние) | там же |
| Отпускание ARM | нет SC-пути для сообщения → «done»-прыжок secure kernel вызывает `release_soc()` | там же |
| Зеркало scratch CMeP | ARM PA 0 = первые 32 КиБ scratch (вики) | там же |
| ~~Развилка сборки ARM-контекста (0x40850)~~ | **подстановка удалена в раунде 91**: она патчила `0x80850` (адрес записан как абсолютный, а цикл ещё раз прибавлял базу 0x40000) — немапированная память, то есть не делала ничего; кроме того, ветка `0x40850` — это выбор «холодная загрузка / resume» по биту 7 wakeup-фактора syscon (команда 0x0010: 0xFF14 холодная, 0xFF80 resume), и брать её не нужно. В таблице подстановок теперь есть проверка «адрес не замапирован → warn», а тест `second_loader_substitutions_stay_inside_the_staged_image` не даёт внести такую запись снова | `src/hw/cmep/bigmac.cpp`, `tests/test_cmep.cpp` |
| Низкое окно ARM (VA < 1 МиБ) | при translation fault модель дописывает в L2 ядра отображение и повторяет доступ; правило по умолчанию `window`: `VA 0x40000 → PA 0x40118000` (своё окно KBL, по его же записи `{0x40118000, 0x40000, 0x8000, 0x8000}` в объекте 0x400B2B30), ниже 0x40000 — identity; `ZLB_ARM_LOW_MAP=identity\|dram\|dram-abs` дают альтернативы | `src/machine/bootchain.cpp` (`satisfy_arm_boot_fault`) + `ArmCore::fault_hook` |
| Страница векторов PA 0x16100 | 0xC0 байт векторов KBL (сегмент `vaddr=0` его ELF) ставятся по адресу, на который он наводит `VBAR` | `src/machine/bootchain.cpp` |
| Ключи CMeP | синтетическая таблица ключей + переподпись образа | `src/machine/bootkeys.cpp` |

## 5. Как запускать и проверять

```powershell
# сборка
powershell -ExecutionPolicy Bypass -File .\build.ps1
# самотесты (базовая линия 210/15/22)
.\build\bin\zlb_tests.exe
# полная проверка (сборка, раскладка, план загрузки, eMMC)
powershell -ExecutionPolicy Bypass -File .\verify.ps1
# прогон цепочки до ARM
.\build\bin\zeliboba.exe -q -ex "boot" -ex "runm 300000" -ex "core" -ex "console" -ex "bootctx"
# отключить все подстановки
$env:ZLB_NO_SUBSTITUTION=1
```

Полезные диагностические переменные: `ZLB_SDIF_TRACE`, `ZLB_BIGMAC_TRACE`,
`ZLB_SDIF_BYTE_ARG`, `ZLB_MEP_PC=addr[,addr…]`, `ZLB_WTRAP=lo-hi` (логировать
записи в диапазон), `ZLB_RTRAP=lo-hi` (чтения), `ZLB_ARM_LOW_MAP=identity|dram|dram-abs|window`
(правило отображения низкого окна ARM), `ZLB_MMU_WALKS=1` (записывать успешные
обходы таблиц MMU — нужно отладчику для «последней трансляции»), `ZLB_RECORD_VERSION`,
`ZLB_ALLOC_CARVE=1` (**эксперимент, по умолчанию выключен**: заставляет аллокатор
разделов KBL идти по пути «нарезать блок» вместо отказа `0x80020005` — сейчас все
четыре ядра из-за этого встают в мьютексе раздела `0x4003A1B0`, см. раунд 51),
`ZLB_KBL_PANIC_TRACE=1` (раунд 109: при заходе на общий stub паники `0x4003596E`
логировать адрес перехода и регистры — так найдена провалившаяся проверка
`0x40034A18`; раунд 110 добавил туда же таблицу фатальных кодов `0x40021998+`),
`ZLB_KBL_CLASS_TABLE=0` (эксперимент: не подставлять таблицу классов — гость её
сам не строит, см. раунд 110.3), `ZLB_KBL_TRACE_PC=<hex>` (раунд 111: первые 12
попаданий на этот pc с предыдущим pc и регистрами — так найдено, кто затирает
указатель таблицы классов и откуда берётся нулевой указатель).

**Правило измерений (раунд 109):** подстановки цепочки загрузки живут в
`Vita::satisfy_arm_boot_pc`, а её вызывает только `Vita::run_slice`. Команда
отладчика `run` крутит `step(1)` и **обходит** их, поэтому все замеры KBL надо
делать через `runm <срезы>` (и точки останова ставить как `bp arm <addr>` —
без архитектуры адрес уходит в MeP).

## 6. Дальнейшие шаги

1. **Смоделировать пред-наполненный раздел памяти KBL** (раунд 51 в `docs/KBL.md`):
   все 15 обращений к разделу идут с флагом `0x10`, который запрещает нарезку новых
   блоков, а кэш/списки раздела за 230 млн инструкций так и остаются пустыми
   (37 записей, все — инициализация). Значит раздел (и, вероятно, объекты VA
   0x4900…0x5D40) должен приходить готовым от предыдущей ступени — это и есть
   недостающая «карта памяти». Попытка подставить нарезку (`ZLB_ALLOC_CARVE=1`)
   вешает все ядра в мьютексе раздела, поэтому идти надо через наполнение данных.
2. **Добавить остальные консоли из таблицы 0x4005C058** (в ней восемь адресов:
   0xE2030000…0xE2090000 и 0xE3105000, модель знает две) — иначе вывод `os0` может
   пропасть; заодно это даст kernel-логи для отладки следующих стадий.
3. **Развести MPCore-периферию и DRAM**: перенести SCU/GT/PT/GIC из
   `0x40000000+` (и поправить 8 самотестов, которые завязаны на текущее
   размещение), после чего вернуть полноценный вход через reset-вектор
   `0x40000000` (вики: «SKBL Reset Vector (ARM entry!)»).
3. **Окно `0xECxxxxxx`** (Pervasive/DMAC) — хотя бы регистровый файл, чтобы KBL
   не читал нули.
4. **NSKBL → os0**: после KBL — `os0:psp2bootconfig.skprx`, `SceSysStateMgr`,
   загрузка модулей ядра из `SceKernelBootimage`. **NSKBL запускается
   естественным путём и проходит `0xA1` → `0xA7` всеми четырьмя ядрами**
   (раунды 158-165), а затем падает на своей же панике `0xAD` (data abort) в
   подготовке загрузки ядра; прогон без `stage` распаковывает NSKBL
   **собственным кодом KBL** (`sceArlzDecode` 0x4003C330 + `sceArlzArmFilter`
   0x4003CB40, версия фильтра 0) в `0x51000000` и передаёт управление в NS через
   `0x40021AE0`. Чекпойнты `0xA5`/`0xA6`/`0xA7` пишут **все четыре ядра**, MMU
   включён на таблицах NSKBL (`TTBR0 = 0x40308000`), вторичные ядра стоят в его
   цикле `wfe` (`0x510147DC`).
   Понадобились пять правок: перенос MPCore-блока из окна DRAM
   (`kermit::kScuBase` 0x40000000 → 0x1E000000 — иначе GIC съедал страницу
   векторов SKBL `PA 0x40000100` с таблицей исключений и монитором `smc`),
   зеркалирование этой страницы в низкую `PA 0x16100` (оттуда её берёт выборка
   вектора при выключенном MMU — NSKBL сам ставит `SCTLR = 0` на `0x51000138`),
   **свой стек каждому вторичному ядру** (`ZLB_KBL_CORE_STACK`, по умолчанию
   `0x1000` на ядро: KBL выдавал всем трём один стек `0x4000`, кадры
   накладывались и `pop {r4-r6,pc}` барьера читал ноль) и **пропуск спинлока
   NSKBL при NULL-объекте** (`ZLB_NSKBL_NOLOCK`: адрес замка `obj+28` при
   `obj = 0` попадает в низкую страницу, где KBL оставил своё слово `0x4680`).
   Текущая стена (раунд 166) — собственный `fatal()` NSKBL (`b .` на
   `0x51015B7C`, 11 мест вызова): не сходится проверка магики класса
   (`[obj+0x24]` против `[0x5113B604]`). Корень найден: объект приходит `NULL`,
   потому что «создатель» `0x5100DEBC` — это чтение поля объекта карты
   `map->[0xD8]` (`map` = `VA 0x4900`), а поля объекта карты в модели нулевые:
   конструктор (окрестность `0x510064A0`) их обнуляет, а заполняющий их код не
   исполняется. Цепочка: `0x5100B650` → обёртка `0x5100DE8C` → `0x5100D398` →
   магика `0x5100EEA8` → `fatal() 0x5100FE16`. **Раунд 168** уточнил, откуда
   поток вообще приходит в устройства: стадия `0xA7` (`0x510004FA`) в
   `0x51000532` вызывает `0x51000FA8` и **не возвращается** из неё (покрытие:
   `0x51000500/04/0C/32` и `0x51000FA8` исполнены, `0x51000540/50/54` — нет), а
   из `0x51000FA8` исполняются все её вызовы (`0x51010A60`, `0x51010994`,
   `0x510106A8`, `0x510109AC`, `0x51010F14`, `0x51000338`) и поток уходит в
   `0x5100BB41`/`0x5100B638` — то есть стадия `0xA8` на этом пути не
   встречается. **Раунд 169** довёл разбор до точки принятия решения: блок
   «открытия устройства» входится из `0x5100B58A` (`bls 0x5100B638` после
   `cmp [r4+0x30],[r4+0x32]`), а `r4 = 0x01100000` — страница арены от
   подстановки `ZLB_NSKBL_POOL`, у которой счётчики нулевые (`0 <= 0`).
   Подстановка `ZLB_NSKBL_POOLFIX` (по умолчанию включена) выдаёт пустому пулу
   один свободный слот и корректные указатели массивов — ветка «нет места»
   больше не берётся, и стена `fatal()` `0x51015B7C`/паника `0xAD` **позади**.
   Новая стена — паника `0xAC`: у того же объекта нет указателя класса
   (`ldr r2,[r4,#4]` = 0 → `ldr r3,[r2,#0x38]` → `blx r3` на `0xFFFFFFFE` →
   prefetch abort). **Раунд 172** — важный сдвиг: консоль NSKBL **работает** и
   сама называет стену: в логе `[info] uart` появилось
   `0:0x58e51d55:0xc6dcf268:sceKernelAllocHeapMemory failed(NULL), size=12/32/64/44`
   — NSKBL дошёл до подсистемы памяти, но **куча NULL**, и он циклически
   повторяет попытки (это и есть livelock из §8.15: история PC не меняется).
   Найден реестр классов NSKBL (`0x510287C0…0x5102892C`: `SceKernelHeap`,
   `SceKernelPartition`, `SceKernelProcess`, `SceKernelSimpleMemBlockClass`, …)
   и его дескрипторы в низкой странице (например `PA 0x40305C40` с именем,
   методами `0x51005A81`/`0x51005A6D` и магикой `0xABCE9DA5`); механизм консоли —
   `0x510175DC` (включение), `0x51017564` (диспетчер), таблица баз `0x5102B06C`
   (UART `0xE2030000` и др., те же окна, что в `seg02` KBL). Следующий шаг —
   найти, кто обязан создать кучу (вероятно, тот же неисполняемый блок
   `0x51007000-0x51009000`). Перед этим снята паника `0xAD`
   подстановкой `ZLB_NSKBL_POOL` (конструктор `0x5100B41C` получал `r0 = 0`,
   потому что пулы объектов `[[0x5113B5AC]+0x5C/0x64/0x6C]` в модели не
   создаются). NSKBL к SDIF/eMMC пока не обращается (все 714 обращений к
   `0xE0B00000` — от CMeP). Методика: разбирать **дамп живой памяти**
   (`save 0x51000000 0x2B08C`), а не старую выгрузку
   `_scratch/nskbl/nskbl.bin` — она расходится с исполняемым образом на 3777
   байт; полезные инструменты — карта покрытия (`ZLB_ARM_COV=1` + `cov`) и
   `ZLB_ARM_BRANCH_LOG[=<lo>-<hi>]` (лог ветвлений через `ArmCore::branch_to`).
   Подробности — `docs/NSKBL.md` §8.8-8.16.
5. **Stage 2**: Venezia MPE (`docs/VENEZIA.md`, факты из Copetti + вики собраны)
   и PowerVR SGX543MP4+ (`docs/GPU.md`) на OpenGL с шейдерами, затем LiveArea.
   Порядок из `docs/GPU.md` соблюдён: GPU начинается после того, как ядро
   реально грузит модули `os0`.

   **План на оставшиеся раунды цикла** (зафиксировано в раунде 185):
   1. один-два раунда — собрать объект кучи NSKBL по измеренному layout

### Сделано в новом цикле

* **SceKblParam реализована по раскладке вики** (`docs/KBL.md`, раунд 44): 0x100

  (`0x407C0000`, `0x40780000`, `0x407A0000`) — раньше контейнер затирал область

* **Проверено трапом чтений**, что ARM-овский boot loader действительно читает
  структуру (`off=0x100` → `0x60` = sleep factor; `off=0x1C4`), то есть раскладка

* Осталось: карта памяти для низких VA KBL (страница векторов `0x16100`) и старт
  ARM с `0x00000000`.

  scratchpad, PA 0x40000-0x5FFFF — зеркало CMeP SRAM 0x00800000; SceKblParam
  пишется в две копии (scratchpad 0x1F000040 с magic и secure DRAM 0x4001FD00 без
  magic), модули `kprx_auth_sm`/`prog_rvk` ложатся по 0x40000500/0x40009B00
  (раунд 45 в `docs/KBL.md`).
* **Следующий шаг**: смоделировать reset-vector `0x40000000` (0xC0 байт, пишет
  second_loader) — стаб, который готовит начальные таблицы страниц и стеки и
  прыгает в SKBL `0x40020000`; сейчас ARM стартует сразу с SKBL и потому падает на
  векторе `0x16100`.
* **Раунд 47**: починены две вещи в инструментах — дизассемблер ARM теперь
  распознаёт `LDREX/STREX*` до умножений (иначе атомарные хелперы KBL
  (`ldrexh`/`strexh`, `0x4003A41C`) печатались как `smlal r12,r0,r3,r15`), и
  добавлена команда отладчика **`faults [all]`** (кольцо отказов MMU: VA, pc,
  read/write/fetch, дескрипторы L1/L2). С её помощью получена точная цепочка
  отказа KBL и подтверждена poke-экспериментом (см. §3.2 и `docs/KBL.md`).
* **Раунд 48**: низкое окно ARM подано подстановкой (`fault_hook`), окно
  `0x0-0x3FFFF` приведено к вики, страница векторов ставится по PA `0x16100`.
  Результат: **KBL проходит 460 млн инструкций** (было 1.8 млн) и упирается в
  ассерт `0x40034A18` (`obj = NULL` → `bl 0x4003B724` = `b .`). В отладчике:
  точные точки останова в `runm` (бюджет ARM = 1 при bp/wp) и история PC в `runm`
  (`history on` + `history arm N`) — именно ими найдена цепочка до ассерта.
  Найдена и задокументирована коллизия MPCore-периферии с DRAM на `0x40000000`
  (перенос откачен: на текущем размещении завязаны 8 самотестов).

* **Раунд 50**: причина «нет менеджера объектов» найдена до конца — `malloc` блоков
  0x1000 (`0x40032278`) возвращает `0x80020005`, потому что кэш пула `0x51C0`
  (`[pool+0x9C] = 0x52C0`) пуст у всех четырёх ядер; из-за этого `0x4002BAF8`
  выходит до записи `ctx+0x8C`. Отладчик: `Vita::pc_hook` сделал точки останова в
  `runm` **точными и проходимыми** (раньше `Cpu::run` ∧ `hit_breakpoint` не давал
  ядру пройти инструкцию под bp — прогон стоял на месте), ARM-bp теперь действуют
  на все 4 ядра, `StopInfo` знает номер ядра. Исправлен сканер вызывающих
  (`_scratch/chk_bl.py`: не было знакового расширения смещения BL).
* **Раунд 52**: найдена и исправлена **ошибка ядра ARM**: `ArmCore::thumb_add_sub`
  читал оба источника Thumb-инструкции `adds/subs Rd, Rn, Rm` из битов [5:3], то есть
  вычислял `Rn ± Rn` (по ARM ARM второй источник — биты [8:6]); форма с
  непосредственным операндом была верной, поэтому ошибка долго не проявлялась.
  Нашлась она на разборе KBL: строитель региона `0x40032C44` считает `adds r0, r1, r3`
  (размер 0x300000 + база 0x40000000) и получал 0x600000 вместо 0x40300000, из-за чего
  **пропускал обход карты страниц** и раздел памяти оставался пустым. После
  исправления обход выполняется (768 страниц), а выделение 1 МиБ из раздела впервые
  **успешно** (`r0 = 0x40000`). Новый барьер — спин в мьютексе `0x4003A1B0`
  (`r0 = 0x28`). Подробности — раунд 52 в `docs/KBL.md`; базовая линия самотестов
  не изменилась (211 / 15 / 22).
* **Раунд 51**: уточнено, что флаг аллокатора — `0x10` (а не 0xA), и за 230 млн
  инструкций раздел **ни разу** не получает память (37 записей в кэш — все из
  инициализации) ⇒ раздел должен приходить пред-наполненным. Опознаны
  низкоуровневые хелперы KBL в ARM-режиме (MPIDR `0x40039F88`, критсекция
  `0x4003A094/0x4003A0A8`, спин-мьютекс `0x4003A1B0`, освобождение `0x4003A224`,
  memcpy `0x400376xx`). Подтверждено, что KBL читает `SceKblParam` (memcpy 128 байт
  из PA 0x100 = param+0xC0). Консоль: трапом показано, что в UART-окна
  (`0xE2030070`/`0xE2040070`) пишут **и ARM KBL (`0x4003BCA0`), и CMeP (`0x4888E`)**,
  а таблица консолей `0x4005C058` содержит восемь адресов (модель знает два).
  Эксперимент `ZLB_ALLOC_CARVE=1` (нарезка блоков вместо отказа) выключен по
  умолчанию: он уводит все ядра в мьютекс раздела.
* **Раунд 114**: найдена и устранена порча стека из раунда 113. Диагностика
  `ZLB_KBL_CTOR_TRACE=1` показала, что конструктор классов получает объекты из
  обхода региона (`r8 = [cls+0x3c]; r8 += [cls+0x20]`), а подстановка инстансов
  (раунд 108) брала страницы из **хвоста региона раздела** и шагала вниз до самого
  стека (~0x40060xxx): `obj+0x14 = 0xFFFFFFFF` затирало сохранённый LR. Инстансы
  переведены в отдельную арену 1 МиБ (VA `0x01100000` → PA `0x41100000`, свободная
  DRAM), и фолбэк геттера `0x4002C1CC` теперь ловит любой не выровненный по странице
  результат (`0xFFFFFFFF`/`0x0FFF`/`0x1FFF` = база-сентинел + таблица 0x4005A960).
  Итог: порча стека и паника на куке heap исчезли, KBL идёт до **спинлока раздела
  `0x4003A1B0`** (~2.88 млрд инструкций) — книга учёта раздела по-прежнему не
  наполнена (см. раунд 114 в `docs/KBL.md`).

`[heap+0x38]` попадало на страницу арены, её `+0x1C` (подпись класса
`0xD2519E9B`, которую штампует сам `0x4002A6E4`) читалось как указатель, и метод
`0x40031654` получал `this = 0xD2519E9B` → data abort `0x40031674`. Цепочка
найдена трассировкой: `0x4002F12E` → `0x4002F090` (`r1 = [[r0+0x38]+0x1C]`) →
`0x4002A6E4` → `0x400318E8` → `0x40031654`. С выключенной по умолчанию
подстановкой (`ZLB_KBL_INSTANCE_BLOCK=1` возвращает старое) KBL **входит в свою
стадию boot-setup `0x400204A8` на всех четырёх ядрах** (вызов идёт не статически,
а через ARM-трамплин `0x4003A140` `mov r13,r2` / `0x4003A144` `bx r1` из
`0x40020806`; аргумент `0x400B2B30`, новый стек `0x1A140`) и рапортует чекпойнт
`0x88`. Заодно выяснилось, что `0x8A` в этих прогонах — **паника `0x40021998`**
(`movs r0,#0x8A; bl gpo; b .`), куда ядро попадает, исполнив мусор после `pc = 0`;
читать её как «resuming context at 0x1F000000» нельзя. **Раунды 159-160**: причина
нулевого возврата — ошибка ядра ARM (`ldmia sp!, {…,pc}` не делал write-back,
из-за чего распаковщик `0x4003C484` возвращался с `sp` на `0x24` ниже), плюс
сторож сна кластера (все ядра в `wfe` и запаркованный счётчик барьера). Теперь
стадия проходит целиком: `sceArlzDecode`/`sceArlzArmFilter` вызываются самим KBL
(`0x4002058E`/`0x4002059E`), рапортуется чекпойнт `0x89`, и управление уходит в
Non-Secure через `0x40021AE0` (`SCR.NS = 1`). **Раунд 161**: причина мусорных PC
после передачи — `RFE` в ядре грузил `PC` и `CPSR` в обратном порядке; после
исправления NSKBL стартует на `0x51000000` и прогон рапортует **чекпойнт `0xA1`**
(`docs/NSKBL.md` §7.6-7.7).

### Сводка на раунде 192: что закрыто, а что нет

**Часть 1 (естественная загрузка `os0`)** — не закрыта, но продвинулась далеко:
NSKBL стартует от KBL и печатает свой баннер, проходит `0xA1`-`0xA7`, с
подстановкой валидного boot-config (`ZLB_NSKBL_BOOTCFG`, по умолчанию) уходит из
ложного Safe Mode и исполняет на ~600 байт больше кода (установщик классов
`0x51007E88-0x51007EF8`). Стена одна и она измерена: **куча NSKBL**
(`map->[0x8C] = 0`, никто не заполняет), из-за чего установщик классов обрывается
на аллокации, одно ядро не приходит на барьер и ядра расходятся по двум барьерам
(счётчики 3 и 2 из 4) → livelock, стадия `0xA8` не наступает. Layout кучи, путь
аллокации и точки барьеров разобраны и записаны (`docs/NSKBL.md` §8.21-8.30).

**Часть 2 (GPU SGX543MP4+)**: в модели есть окно регистров SGX (`Kermit.SGX`,

из памяти гостя**, прерывание с маской событий, **MMU GPU** (обход таблицы в
памяти гостя, счётчики промахов) и разбор потока команд GXM с записью draw-вызовов
вместе с действующим состоянием (IR для будущей трансляции в OpenGL). Всё покрыто
модульными тестами; фрагмент, которого ещё нет, — реверс настоящего бинарного
формата GXM из `libgxm_es4.elf` и сама трансляция в GLSL.

**Часть 3 (кадр в панели SDL3)**: путь замкнут и проверен — контроллер дисплея
**сканирует кадровый буфер из памяти гостя**, а вкладка Panel показывает кадр;
самотест `ZLB_GPU_SELFTEST=1` рисует восемь цветных полос, и в скриншоте
`--screenshot ... --screenshot-tab panel` найдены все полосы (45 300-45 753
пикселя каждой, область x 238..941, y 8..496). Настоящий кадр Live Area появится,
когда буфер заполнит прошивка, то есть после части 1.

**Итог**: тесты — 428/0, `verify.ps1` — 9/9, обычный прогон машины: чекпойнт
`0xA7`, паник нет.


### Итог цикла (раунд 195, 30/30): цель не достигнута, стена одна и измерена

**Часть 1 (естественная загрузка `os0`) — не достигнута.** NSKBL запускается от
KBL естественным путём, печатает баннер
(`Starting PSP2 Kernel Boot Loader [0x01040011]: 300`), проходит `0xA1`-`0xA7`,
строит карту, регистрирует классы, включает консоль, с подстановкой валидного
boot-config (`ZLB_NSKBL_BOOTCFG`, включена по умолчанию) уходит из ложного Safe
Mode и исполняет на ~600 байт больше кода. Стена: **инициализация кучи NSKBL**
(`map->[0x8C]`). Ни один исполняемый код её не создаёт; оба пути аллокации
(`0x51004AFC` и `0x51004C94`) читают именно это поле — измерено трассировкой.
Подстановки (`ZLB_NSKBL_HEAP`) провал аллокаций снимают полностью, но поток уходит
в другую фатальную проверку (`0x51015B7C`), то есть семантика синтезированной кучи
расходится с ожиданиями прошивки. Правильный путь: найти/включить инициализацию
кучи в самой прошивке (объект `SceKernelHeap` + блоки с корректными метаданными).
Подробности — `docs/NSKBL.md` §8.21-8.32.

**Часть 2 (GPU SGX543MP4+) — частично.** Реализованы и покрыты тестами: окно
регистров SGX, очередь команд с чтением из памяти гостя, прерывания с маской
событий, MMU GPU, разбор потока команд GXM и запись draw-вызовов с состоянием
(IR). Не сделано: реверс настоящего бинарного формата GXM, генерация GLSL и сама
трансляция шейдеров/состояний.

**Часть 3 (настоящий кадр Live Area в панели) — не достигнута**, но путь проверен:
контроллер дисплея сканирует буфер из памяти гостя, панель SDL3 показывает кадр, и
самотест `ZLB_GPU_SELFTEST=1` даёт изображение из восьми цветных полос
(подтверждено подсчётом пикселей в скриншоте). Настоящий кадр появится, когда
буфер заполнит прошивка, то есть после части 1.

**Контрольные цифры цикла**: 428 тестов / 0 падений, `verify.ps1` — 9/9,
обычный прогон машины: `checkpoint=0xA7`, паник нет; `Kermit.SGX` и `Kermit.Display`
видны в `devices`.

### Новый цикл (раунды 196-211): память NSKBL инициализируется, куча создаётся

**Что найдено и сделано.** Корень отсутствия кучи оказался не в самой куче, а в
**загрузочной конфигурации физической памяти**:

* таблица физических областей у раздела ядра `ScePhyMemPartKD` (`VA 0x5300`,
  поле `+0x9C` → `VA 0x5400`, записи по 32 байта на ядро) в модели пуста — никто
  её не заполняет. Из-за этого запрос области `0x5100C04C` возвращал
  `0x80020005`, функция `0x51005700` выходила раньше времени, и
  `SceKernelSysrootClass` (`0x51004F28`) не регистрировался — то есть не
  появлялся sysroot, а вместе с ним и куча;
* подстановка **`ZLB_NSKBL_PHYSPOOL`** заполняет записи областями нужного вида
  (значение области — указатель на слово с номером физической страницы;
  потребитель `0x5100C010` делает `*value << 12`) и дополняет их по мере
  расходования. После неё **NSKBL сам создаёт кучу**: `map->[0x8C] = 0x5C00`,
  sysroot регистрируется, покрытие растёт с 5804 до 6170 слотов;
* затем поток писал объекты по `VA 0x30000` и получал data abort: таблицы KBL
  описывают этот адрес крупной страницей 64 КиБ с базой `PA 0x00000000`, которой
  в модели нет. Подстановка **`ZLB_NSKBL_LOWWIN`** правит записи L2 (`0x30-0x3F`)
  на мелкие страницы `PA = VA + 0x40300000` — сбой снят;
* последняя проверка — магия класса (`0x5100EEBE`: `obj->[0x24] == [0x5113B604]`),
  причём глобальная переменная в модели **никогда не инициализируется** (трап:
  одна нулевая запись от общего обнуления). Подстановка `ZLB_NSKBL_MAGIC` публикует
  её значение из объекта и выравнивает поле.

**Где стоим.** Стадия `0xA8` («kernel loading») пока не наступает: машина
спокойна (`checkpoint=0xA7`, паник нет), но фатальный выход срабатывает — из 39
переходов на общий хвост `0x5100FE16` исполняется ровно один, `0x5100EEC0`
(та самая проверка магии). Дальше нужно понять, почему после публикации магии
сравнение всё ещё не сходится (проверяется ли другой объект, или вход в код
проверки идёт из середины).

Все три подстановки включаются переменными `ZLB_NSKBL_PHYSPOOL=1`,
`ZLB_NSKBL_LOWWIN=1`, `ZLB_NSKBL_MAGIC=1` и по умолчанию выключены, чтобы
документированное состояние оставалось чистым. Подробности — `docs/NSKBL.md`
§8.33-8.47; сводка по всем трём частям цели — ниже в этом файле.

### Раунд 302: путь к `os0` — найдена причина, исправлены две ошибки модели

Разбор «почему том `os0` никто не читает» (§9 в `docs/NSKBL.md`) доведён до корня, и
корень оказался не в гостевом коде, а в **модели SD-контроллера**. Полная цепочка
(все звенья измерены на `runm 400000`):

1. `0x51000E7C` (подъём хранилища) открывает контроллер через
   `0x51021664(dev_id, &0x5102B014)`; трап записей показывает, что `0x5102B014`
   **всегда** остаётся нулём — открытие не проходит, значит блочное устройство
   `0x51184FF8` не работает, значит `read_blocks` возвращает `0x80010013`
   (`0x51000D14`), значит BPB/FAT тома не читаются, значит `0x510232EC` выходит по
   `ble` (разница `[vol+0x38]-[vol+0x30]` отрицательна, `+0x38` конструктор ставит в
   `-1`), и `os0:psp2bootconfig.skprx` не находится → `0x803FF007`.
2. **Ошибка модели №1 — окна SC от Ernie затеняли SDIF0.** `Vita::wire_bridges`
   зеркалил в шину ARM окна сообщений SC (`0xE0B00000`/`0xE0BF0000`, по 0x200 байт),
   а по `0xE0B00000` живёт регистровый блок SDIF0 (`kSdif0Base`, 0x10000). Меньшее окно
   побеждает в `Bus::find_device`, поэтому ARM читал не SDHCI, а SC-окно:
   `map 0xE0B00024` → `arm: Ernie.ScCmd@mirror read32=0x0`, `mep: Kermit.Sdif0@mirror
   read32=0x30000`. NSKBL проверяет ровно этот регистр (`0x5101E970` — бит 16
   PRESENT_STATE «карта вставлена») и отказывался. Исправлено: окна `Ernie.ScCmd` и
   `Ernie.ScReply` больше не зеркалятся в ARM (интерфейс ARM к SC — `Ernie.SC`
   `0xE3100000`). Примечание раунда 260 о том, что «затенение ни на что не влияет»,
   устарело: тогда NSKBL ещё не доходил до драйвера хранилища.
3. **Ошибка модели №2 — CMD8 всегда декодировался как MMC SEND_EXT_CSD.** После
   исправления (2) ARM начал работать с SDIF (`ZLB_SDIF_TRACE=1`: `CMD idx=0`,
   затем `CMD idx=8 arg=0xAA data=0`, три попытки), но модель на CMD8 отдавала 512-байтовую
   фазу данных (путь CMeP: `idx=8 arg=0x0 data=1`) вместо SD-шного SEND_IF_COND с
   ответом R7-эхо. Обёртка гостя `0x51022D84` проверяет `(R7 & 0xFF) == 0xAA` и
   `arg & (R7 >> 8)`. Исправлено: `case 8` ветвится по флагу data-present.

**Где стоим.** С обеими правками открытие устройства проходит глубже и падает на шаг
позже — `0x80320016` из `0x51022FBC`. Причина: поле режима контроллера
`[dev+0x2420]`, из которого процедура опознания `0x5101D720` выбирает флаги
(0 → `0x80`, 1 → `0x300000`, 2 → `0x80`); маску `0x00FF8000` в вызывающем
(`0x51022FCC`) переживает только значение при `mode == 1`, а трап записей по
`0x5117EF00..0x5117EF40` показывает, что **это поле не пишет никто** (в образе там
BSS-нули). Следующий замер — найти, кто обязан выставить `mode = 1` (SD против MMC;
`0x5101D860` при `mode == 2` не трогает clock control), и подать то состояние
железа, из которого он выводится.

**Контрольные цифры**: 436 тестов / 0 падений, `verify.ps1` — 9/9, 992 файла / 0
расхождений, прогон по-прежнему спокойно стоит на `checkpoint=0xA9`; подробности —
`docs/NSKBL.md` §10.

**Чем поле режима важно (измерено пинком отладчика, `poke 0x5117EF20 1`).** Само поле
`[dev+0x2420]` пишет инициализатор хранилища (`0x5101DF88`) — это **счётчик цикла**, то
есть у трёх устройств таблицы `0x5102A150` режимы 0, 1, 2. Контекст `0x5102B010`
открывает устройство с id 0, и процедура опознания выбирает для него шаблон проверки
CMD8 = 0. Если пинком поставить режим 1 (SD), картина меняется радикально:

| замер | режим 0 (по умолчанию) | режим 1 (пинок) |
|---|---|---|
| инструкций | 153 205 277 | 207 050 132 (283 851 186 после правки CMD5) |
| arm0 в конце | `0x51000D0C` (терминальный цикл) | `0x5101F9FA` (внутри стека хранилища) |
| команды SDIF от ARM | `CMD0`, `CMD8 arg=0xAA` ×3 | `CMD0`, `CMD8 arg=0x1AA`, `CMD5 arg=0`, `CMD5 arg=0x300000`, далее цикл открытия повторяется |

Значит SD-путь для этого устройства — правильный, и следующая стена после опознания —
опрос `CMD5` (SEND_OP_COND): обёртка `0x51022DE4` повторяет команду, пока в ответе R4 не
поднят бит 31. Ветка `default` отдавала `0x900` вечно, поэтому добавлен `case 5` с
ответом `0xC0FF8000` («готово, I/O-функций ноль» — так слот без SDIO завершает опрос).
Опрос завершился, прогон дошёл до 283 млн инструкций, но открытие по-прежнему падает
(три попытки), то есть следующая стена — внутри `0x51022FBC`/`0x51023006` уже после
op-cond. В режиме по умолчанию эта правка ничего не меняет: до CMD5 гость не доходит.

**Почему режим 0 не может пройти проверку CMD8 (раунд 303).** Обёртка `0x51022D84`
возвращает успех только если `(R7 & 0xFF) == 0xAA` **и** `arg & (R7 >> 8) != 0`; при
`arg = 0` (режим 0) второе тождественно ноль, то есть нужен не ответ карты, а **отказ
движка запросов**. И он найден: преобразователь ошибок драйвера `0x5101EBE4` отображает
биты SDHCI-статуса ошибок в коды гостя, и **бит 0 (Command Timeout) даёт ровно
`0x80320002`** — то значение, которое принимает вызывающий `0x51022FF6` (таблица
отображения: бит 1 → `0x80320007`, бит 2 → `0x80320008`, бит 3 → `0x80320009`,
бит 4 → `0x80320003`, биты 5/6 → `0x8032000a`/`0x8032000b`, бит 9 → `0x8032000c`).

Замер с включённым таймаутом: до правок машина вставала на `0x5101EDE4`, **оба** регистра
статуса читались нулями, а ветка преобразователя `0x5101EC02` (бит 0) не исполнялась ни
разу. Разбор этого привёл к **двум новым ошибкам модели** того же класса, что и раньше
(регистр в полуслове не едет вместе со своим 32-битным словом):

1. **`ERROR_INT_STATUS` (0x32) был невидим для чтения.** `RegisterBlock::read()`
   декодирует доступ в пределах слова через `read_word(offset & ~3, …)`, то есть чтение
   `0x32` обслуживается словом по `0x30`, а SDIF держал статус ошибок в отдельной
   записи: `poke(kErrorIntStatus, …)` писал 1, а гость читал 0 по тому же адресу
   (замер изнутри SDIF: `stored=0x0001`, а опрос драйвера на `0x5101EDE8` — `0x0000`).
   У `write_word()` зеркальная проблема: он всегда вызывается со смещением *слова*,
   поэтому его `case kErrorIntStatus` не мог сработать никогда. Теперь статус ошибок
   живёт в `Sdif::error_status_` и подмешивается в слово по `0x30`.
2. **Самосброс имел только бит 0 software-reset.** Модель обрабатывала бит 0 (сброс
   всего хоста), но не бит 1 (сброс командной цепи) и бит 2 (сброс цепи данных), а
   аварийный путь драйвера сбрасывает именно командную цепь и опрашивает бит
   (`0x5101ED04` / опрос `0x5101ED0A..0x5101ED12`) — с читаемым статусом ошибок прогон
   встал ровно там. Теперь самоочищаются все три бита.

После правок таймаут CMD8 доходит до преобразователя: точка останова на `0x5101EC02`
срабатывает с `r2 = 1` (Command Timeout) и `r3 = 0x5102BD3C` (слот запроса **не** пуст),
то есть драйвер получает `0x80320002`. Таймаут для CMD8 без VHS теперь поведение по
умолчанию (`ZLB_SDIF_CMD8_NORESP=0` возвращает старое «всегда эхо»), и трасса команд ARM
растёт с 6 (`CMD0`/`CMD8` ×3) до 24 (`CMD0`, пять повторов `CMD8`, затем опрос `CMD5`).
Конечное состояние прогона по умолчанию не изменилось (`0x51000D0C`, `checkpoint=0xA9`):
открытие всё ещё падает уже на фазе op-cond (`0x51023006`), и инициализатор повторяет её
трижды. Важно на будущее: `insns` — это счётчик **планировщика** (цикл среза выполняет
ровно `budget_.arm` шагов на ядро), поэтому о прогрессе гостя судить по нему нельзя —
только по трассе команд и конечному pc.

Скриншоты этого состояния: `screenshots/uart-os0-stage0xA9.png` (лог UART гостя —
баннер NSKBL и `Safe Mode : [ YES ]`) и `screenshots/back-chain-0xA9.png` (панель Boot с
цепочкой и вехами).

### Раунд 304: драйвер доходит до чтения блоков, но паркуется на CMD18

**CMD5 отвечать нельзя.** Прошлая догадка (`0xC0FF8000`) была неверной: обёртка опроса
`0x51022DE4` повторяет команду, пока ответ отрицательный, и только ветка ошибки на
`0x51023012` ведёт к `0x51022ED8` (стадия CID/адреса) и в итоге ставит
`[dev+0x2410] = 1` — тот самый флаг «карта опознана», который открытие проверяет на
`0x5102074A`. С ответом поток уходил на `0x51023034`, оставлял `[dev+0x2410] = 3` и
открытие падало с **`0x80320017`** (замер на `0x51000E94`). Карта за этим контроллером —
eMMC, то есть не SDIO, поэтому теперь `case 5` отдаёт таймаут, как и CMD8 без VHS.

**Что стало.** Драйвер проходит полную идентификацию; трасса команд ARM (26 команд):
`CMD0`, `CMD8(0xAA)` ×5 (таймаут), `CMD5` ×4 (таймаут), `CMD55` ×5, `CMD1(0x40000080)`,
`CMD2`, `CMD3`, `CMD9`, `CMD7`, `CMD6(0x03AF0100)`, `CMD8` с фазой данных (SEND_EXT_CSD),
`CMD16(0x200)`, `CMD23(0x20 = 32 блока)`, а `[dev+0x2410]` становится **1** — проверка
«карта опознана» в открытии проходит.

**Ещё одна ошибка модели (исправлена).** Команда с откликом **R1b** (тип «48 бит с
busy», биты 0..1 командного регистра == 3; CMD6 = `0x61B`) требует *второго* события
обычного прерывания: движок запросов завершает запрос только по следующему прерыванию
после Command Complete (его преобразователь `0x5101EBE4` выходит раньше, пока в слове
состояния запроса поднят бит 3 — это и есть случай R1b). С `transfer_complete_in_ = 8`
для такого типа слово состояния запроса меняется с `0x0000002B` на `0x8000002B` (бит 31 =
«готово»), и драйвер идёт дальше — к чтению EXT_CSD и подготовке блочного чтения.

**Где стоим.** Следующая команда, `CMD18` (READ_MULTIPLE_BLOCK), обнажила новую стену:
запрос лежит в `[dev+0x2428] = 0x5117D400` с `+0x08 = 0x12` (CMD18), `+0x0C = 0`
(аргумент ещё не записан) и `+0x04 = 0` (состояние пустое), то есть **поставлен в
очередь, но не выдан**, а движок вечно опрашивает статус прерываний на `0x5101EDE4`.
Последние записи в регистры перед парковкой — из пути запуска передачи: `0x2C = 0x8003`,
`0x2C = 0x8007` (clock control) и `0x38 = 0xFB` (NORMAL_INT_SIGNAL_ENABLE). Прогон по
умолчанию теперь не останавливается чисто на `0x51000D0C`, а паркуется здесь — это
дальше, чем старый `0x803FF007`, но это парковка.

**Разобрано до конца (см. `docs/NSKBL.md` §10.8).** Причина парковки — поле самого
запроса, а не поведение железа. Рутина выдачи команды `0x5101D860(device, request)`
диспетчеризует по `([request+4] & 7) - 1` через `tbh` на `0x5101D902`: младшие три бита —
это **фаза** (1..4), а биты 3..7 — класс, из которого собираются флаги командного
регистра (класс `0x28` → `0x1B` (R1b, так выдавался `CMD6`), `0x10`/`0x60`/`0x80`/`0x90` →
`0x1A`, `0x30` → `9`, `0x40`/`0x50` → `2`). Фаза 4 (`0x5101DA04`) — это путь **передачи
данных**: он программирует размер/число блоков из `[request+0x24]`/`[+0x26]`, собирает
transfer mode из бит 8 и 11 и пишет команду с битом data-present. А при фазе 0 `subs r2,#1`
на `0x5101D8F2` даёт `0xFFFFFFFF`, ветка `bhi` на `0x5101D8FE` срабатывает, и рутина
выходит на `0x5101DA74`, **не записав командный регистр** — при этом запрос уже помечен
выданным (`[request+0x64] = 2`) и лежит в слоте.

Замер (`ZLB_WTRAP=0x5117D400-0x5117D440`) показывает, что так и есть: запрос чтения
собирается на `0x5101FEA4` с `vstr` нулей в `+0x00`/`+0x04` (то есть фаза 0), далее
`+0x08 = 0x12` (CMD18), `+0x24 = 0x200`, `+0x26 = 0x20` (512 байт, 32 блока),
`+0x20 = 0x51033108` (буфер в собственной кэш-таблице драйвера `0x51033100`), и
`0x5101D88C` снова пишет `+0x04 = 0`. Для сравнения, запрос-команда собирается уже с
готовым словом: сборщик `SWITCH` пишет `+0x04 = 0x2B` на `0x51020D40` (фаза 3, класс
`0x28`) — поэтому `CMD6` и всё до него выдавались.

Следующий замер узкий и проверяемый: **кто обязан выставить класс/фазу у запроса
данных** (писатель `+0x04`, кроме двух сборщиков). Кандидаты: кэш-слой, вызывающий
сборщик чтения (обёртка `0x5101F6BC` передаёт пятый аргумент 1 — ветка «поставить в
очередь»), обработчик завершения `0x5101DAE4` (двигает `[request+0x64]` с 2 на 3, чистит
слот и выдаёт *следующий* запрос через ту же `0x5101D860`) и обработчик фазы данных
`0x5101DBD4`, который движок вызывает на `0x5101EE54`.

### Раунд 305: причина найдена — ошибка модели в VFP, том os0 наконец читается

Ответ на вопрос выше оказался неожиданным: **гость выставляет слово класса/фазы, а
модель процессора теряла его половину**. На `0x5101FEA4` стоит 64-битная запись VFP:

```
5101FE9C  vldr d16, [pc, #0x180]   ; литерал по 0x51020020: {0x00000240, 0x00000514}
5101FEA4  vstr d16, [r0]           ; пишет +0x00 = 0x240 и +0x04 = 0x514
```

`0x514 & 7 == 4` — это фаза пути данных (`0x5101DA04`), а `0x514 & 0xF8 == 0x10` — класс,
дающий флаги команды `0x1A`. Модель сохраняла только младшие 32 бита, поэтому слово
запроса оставалось нулевым и рутина выдачи (`0x5101D860`) выходила, не записав команду.

Причина — **бит размера у Thumb-2 VFP-загрузки/записи**: размер определяется *номером
сопроцессора* (cp10 — одинарная точность, cp11 — двойная), и его младший бит и есть бит 8
инструкции. `thumb32_coprocessor` передавал `(cur_instr_ & 0x100) != 0` как «single», то
есть ровно наоборот: каждая `vldr`/`vstr dN` исполнялась как 32-битный доступ к `sN`
(та самая `vldr d16` грузилась в `s1`, а `vstr` писала четыре байта). В A32-путях
(`execute_arm_coprocessor`, `execute_arm_vfp`) логика была верной (`single = cpnum == 10`),
ошибочным был только Thumb-путь.

Перед правкой теорию подтвердил эксперимент в отладчике: `bp arm 0x5101FEA4`,
`bpc 0x5101FEB2`, `poke 0x5117D404 4 32` — и следующий прогон выдал `CMD18` и прочитал
`lba=0 count=32 ok=1`.

Замеры после правки (`src/cpu/arm/arm_core.cpp`, `thumb32_coprocessor`):

| что | до | после |
|---|---|---|
| `[request+0x04]` (слово класса/фазы) | `0` | `0x514` |
| открытие хранилища на `0x51000E94` (`bp`) | `0x803FF007` (исходный симптом) | **`0` (успех)** |
| трасса команд ARM | обрыв на `CMD23` | `CMD18` выдан, фаза данных пройдена |
| чтения eMMC | 19 (только цепочка загрузки) | + `lba=0 count=32` — первые 16 КиБ тома os0 |

**Том os0 читается.** `zlb_tests` 436/436, `verify.ps1` 9/9 (992 файла, 0 расхождений).

**Новая стена.** Драйвер настраивает ADMA, и модель отказывает в таблице:
`adma=0x0017D480` → `adma: no bus for table 0x0017D480`, `data_pending_` остаётся
истинным, драйвер (он работает через ADMA и порт данных `0x20` не трогает) ждёт на
`0x5101EE06`. Адрес берётся из запроса: `0x51022658` читает `[r5,#0x7c]` и кладёт в
`ADMA_SYSTEM_ADDRESS` на `0x51022660`. По трапу записей (`0x5117D470..0x5117D490`, VA
`0x5117D400` отображается 1:1 в PA) **`+0x7C` не пишет никто**; PA `0x0017D480` в модели
вообще без памяти (`map` — нет устройства, `mem` — `0xFFFFFFFF`; единственная низкая RAM —
алиас `arm_bootrom` размером `board::kArmBootWindowSize = 0x00040000` по PA 0), а у гостя
нет и отображения VA `0x0017D480` (`vmem` → page translation fault). Следующие замеры:
кто должен инициализировать `+0x7C` (трап по всему объекту запроса 0x240 байт + трасса
пула) и что на железе лежит по PA `0x0017D480` (похоже, низкое окно должно быть больше).

**Уточнения по этой стене (тот же раунд).** `+0x7C` **равен нулю в момент сборки
запроса** (`bp arm 0x5101FEA4` → `vmem 0x5117D47C` = 0), то есть значение появляется
позже — но трап записей по `0x5117D470..0x5117D490` за весь прогон не ловит ничего
(значит, писал либо сам механизм подстановок модели — он пишет прямо в шину, — либо путь
DMA, не проходящий через store ядра). Внутри объекта запроса лежит и сама таблица ADMA:
по `+0x80` две записи `{attr 0x21, len 0x38, target 0x0017D5C0}` и
`{attr 0x21, len 0x3FC0, target 0x00033140}`, а по `+0x100` тот же трансфер как
`{0x5117D480, 0x00033140, 0x00003FC0}`. Эти адреса и выдают правило:
`0x0017D5C0 = 0x5117D5C0 & 0x00FFFFFF`, `0x00033140 = 0x51033140 & 0x00FFFFFF` — драйвер
преобразует адрес окна в адрес для DMA **маской 24 бита** (`VA & 0x00FFFFFF`, для этого
окна то же, что `VA - 0x51000000`), тогда как таблицы страниц модели (и вся её
документация) считают это окно тождественным (VA = PA). Что именно верно — вопрос
следующего шага: либо у модели неверна сама конвенция отображения VA `0x51000000+`
(в гостевой таблице `L1[0x510] = 0x5111158E`, и надо посмотреть, кто её пишет), либо на
железе данные NSKBL действительно лежат по низким физическим адресам, а в модели там нет
памяти.

### Раунд 306: ADMA проходит, драйвер читает том

Правило из предыдущего абзаца реализовано: `Sdif::dma_translate()` пробует адрес как есть
и, если ни одна шина его не обслуживает, тот же смещение внутри окна NSKBL
(`address + 0x51000000`, только для адресов ниже `0x01000000`). Через это проходят и база
таблицы, и все цели записей.

Замер (`ZLB_SDIF_TRACE=1`):

```
CMD idx=18 ... count=32 data=1 read=1 multi=1 dma=1
adma rec @0x5117D480 attr=0x0021 len=56    target=0x0017D5C0
adma rec @0x5117D488 attr=0x0021 len=16320 target=0x00033140
adma rec @0x5117D490 attr=0x0023 len=8     target=0x0017D600   (END)
adma table=0x5117D480 moved=16384/16384 ok=1
raise TransferComplete dma=1
```

Все 32 блока (16 КиБ) доехали до буферов драйвера, а в памяти гостя по VA `0x5117D5C0`
лежат первые 56 байт переноса — `Sony Computer En`, то есть мастер-блок eMMC. Парковка на
`0x5101EE06` исчезла, прогон снова заканчивается в знакомом терминальном цикле
`0x51000D0C`.

Что осталось — на уровень выше: открытие хранилища на `0x51000E94` возвращает **0**
(исходного `0x803FF007` там больше нет) и том читается один раз, но первая внешняя загрузка
всё ещё возвращает `0x803FF007` на `0x510014D5`, и **больше ни один сектор не читается**.
Драйвер читает LBA 0 — а это в образе мастер-блок консоли (таблица разделов: `slot03/OS0`
по `0x0001000000` и `slot04/OS0` по `0x0002000000`, оба FAT16; см.
`emmc_rebuild --inspect`) — и на этом останавливается. Следующий замер — внутри обработки
разделов/тома в стеке хранилища: что код после первого чтения делает с мастер-блоком
(точка `0x510232EC` вызывается с объектом тома `0x51184FF8`, у которого `+0x30 = 0xFFFFFFFF`,
`+0x38 = 0`) и почему он считает том непригодным вместо чтения слота OS0 по LBA 32768.

### Раунд 307: разбор разделов заработал, драйвер читает том os0

**Разобрано до конца.** Конструктор тома `0x51023C40` (1) строит заголовок мастер-блока в
своём буфере из констант (`0x51011D00..0x51011DB4` пишет `"Sony Computer Entertainment
Inc."`, версию 3, число блоков и константы `0x30` — тот же layout, что делает
`build_master_block()`), (2) проверяет `[buffer+0x1FE] == 0xAA55` (`0x51023F1C`),
(3) сканирует **16 записей разделов по 17 байт** начиная с `buffer+0x50`, ища запись, у
которой байт **кода** (`record+8`) равен 3 (OS0) и байт **active** (`record+0x0A`) имеет
бит 0 (`0x51023F38..0x51023F48`), и (4) возвращает `0x803FF007` (`0x51023CF4`), если за 16
записей совпадения нет. Константы модели при этом верны (`kPartitionTableOffset = 0x50`,
`kPartitionRecordSize = 17`, `kPartitionTableSlots = 16`, `Os0 = 0x03`).

**Ошибка была в порядке проверок внутри нового перевода адресов.** Запись ADMA с целью
`0x00033140` (буфер кэша драйвера, VA `0x51033140`) попадает внутрь низкого загрузочного
окна модели (`arm_bootrom` по PA `0..0x3FFFF`), поэтому шина её «обслуживала» и адрес
оставался непереведённым: 16320 байт ушли по PA `0x33140`, записи разделов остались нулями
и скан не находил ничего. Первая запись (`0x0017D5C0`, выше окна) переводилась и работала —
поэтому первые 56 байт мастер-блока и оказывались на месте. Правильное решение — решать по
*адресу*, а не по тому, нашлась ли шина: всё ниже `0x01000000` оконно-относительно
(`0x00033140 -> 0x51033140`), всё от `0x01000000` и выше — как есть (таблицы CMeP живут по
`0x40000400`).

Замер после правки (`ZLB_EMMC_LOG=1`):

```
read lba=0     count=32 ok=1   (мастер-блок)
read lba=65536 count=32 ok=1   (АКТИВНЫЙ раздел OS0: os0_1 по смещению 0x02000000)
```

плюс в трассе ARM появляется второе многосекторное чтение:
`CMD13(0x00010000) CMD23(0x20) CMD18(0x00010000, count=32, adma)` и
`adma table=0x5117D900 moved=16384/16384 ok=1`. То есть стек хранилища разбирает таблицу
разделов, выбирает активный слот `OS0` и читает первые 16 КиБ тома.

**Стена сдвинулась.** Ошибка теперь не на разборе разделов (`0x51023CF4`), а на следующей
стадии — `0x51024160`: помощник `0x51023970` (вызов: `r0` = том `0x51184FF8`, `r2`/`r3` —
выходы на стеке, `[sp] = sp+0x10`, `r6 = 0xE`) возвращает **0**, и код ставит `0x803FF007`
(`cmbnz r0` на `0x5102415E`). Рядом на `0x51024140` собирается `0x803FF005` — парная ошибка
для тома, у которого `[+0x1C0]` пуст, то есть это стадия монтирования/чтения тома. Этот
вызов — следующий замер; заметим, что FAT и каталог драйвер после первых 16 КиБ тома
по-прежнему не читает.

### Раунд 308: последний блокер — глобальный метод чтения `[0x51184760]` никто не ставит

Цепочка прослежена до поиска файла целиком, и она упирается в **одно поле**.

Помощник `0x51023970(том, путь, out1, out2, …)` разбивает путь (`0x51024854`/`0x510247A4`) и
обходит его компоненты, вызывая для каждого поиск в томе `0x510232EC`; нулевой ответ ставит
метку «не найдено» (`r5 = -0x63`), и вызывающий пишет `0x803FF007` на `0x51024160`. Путь,
который ему передают, — полный `"os0/psp2bootconfig.skprx"` (`0x5102BDE7`), поэтому первым
компонентом в томе ищется `"os0"`.

Внутри `0x510232EC` чтение каталога идёт через **глобальный** указатель метода:

```
5102338C  r8 = [vol, #0x50]     ; первый блок данных тома (BPB драйвер уже разобрал)
51023392  ip = 0x51184760       ; слот глобального метода чтения
5102339A  r6 = [ip]
510233A2  cmp r6, #0
510233A4  beq 0x51023946        ; <- в модели срабатывает: метода нет, поиск сдаётся
510233BA  blx r6                ; read([0x51184B84], буфер, r8 >> 9, 0x51184780)
```

Замер: `[0x51184760]` **равен нулю и его никто в госте не пишет**. Трап записей по всей
области слота (`ZLB_WTRAP=0x51184700-0x51184800`) даёт только обнуление BSS (`pc 0x510008F8`)
и инициализацию сентинелами, которую делает сам помощник разбора пути
(`pc 0x51023BA4..0x51023BF8`, значения 0/0xFFFFFFFF); поиск по образу пары
`movw/movt 0x4760/0x5118` находит **четырёх читателей** (диспетчер `0x51023128`, дважды
конструктор тома `0x51023CA6`/`0x51023CFE` и сам поиск) и **ни одного писателя**.

При этом диспетчер драйвера показывает, как это задумано: `0x51023128` предпочитает
глобальный метод, а если он нулевой — берёт метод *объекта* `[r0]`, и если нулевой и тот —
отдаёт `0x803FF007` (`0x5102315C`). Метод самого тома **установлен**: конструктор пишет
`[vol+0x54] = 0x51000D55`, `[vol+0x58] = 0x5102B010` (`pc 0x51023FDC`). Поиск этим
фолбэком не пользуется — значит осталось выяснить, что ставит глобальный метод на железе
(стадия регистрации драйвера/устройства, до которой наш поток не доходит), либо подложить
его подстановкой с сигнатурой вызова на `0x510233BA` (контекст, буфер, LBA, `0x51184780`).
Самый дешёвый способ различить эти два варианта — эксперимент в отладчике:
`bp arm 0x510233A2`, `poke 0x51184760 <кандидат> 32`, продолжить.

Всё остальное на этом пути теперь измеряется корректно: мастер-блок прочитан и разобран,
выбран активный раздел `OS0` (`os0_1` по `0x02000000`), прочитаны первые 16 КиБ тома, и его
загрузочный сектор лежит в буферах драйвера байт в байт (`SCEI`, 512 байт/сектор, 8
секторов/кластер, 2 FAT, 512 записей корневого каталога, размер FAT 19) и разобран в том
(`+0x48` — то поле, которое проверяет поиск).

**Проверка подстановкой (отладчик).** `bp arm 0x510233A2`, `poke 0x51184760 <значение> 32`,
