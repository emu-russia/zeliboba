# vnzimg.elf (SceVeneziaImage) — карта модуля и цепочка запуска Venezia

Прошивка **1.04**. Артефакт: `Vita_104_Firmware/Out/fs_dec/os0/kd/vnzimg.elf`
(SLB2-имя `os0:kd/vnzimg.skprx`), 0xF6F54 = 1 011 540 байт.

Отчёт состоит из трёх слоёв:

1. **Контейнер** — ELF-обёртка, `SceModuleInfo`, таблицы экспорта, релокации;
2. **Полезная нагрузка MeP** — сегмент 1, реальный код движка Venezia;
3. **Кто, когда и как** — цепочка `psp2config → vnz_wrapper → vnzimg → MeP`,
   протокол подъёма и RPC;
4. **Инструмент** — перенесённый в zeliboba дизассемблер IVC2.

Два независимых разбора лежат рядом в `_scratch`:
`VNZ_ARM_REPORT.md` (ARM-контейнер, Thumb-2, обёртка, цепочка загрузки) и
`VNZ_BOOT_REPORT.md` (bootimage, psp2config, пользовательский API).
Этот файл — сводка; там, где слои расходятся, расхождение указано явно.

## 1. Контейнер: ELF-обёртка

ELF32 little endian, `e_machine = 0x28`, `e_type = 0xFE04`, `e_flags = 0x05000000`,
`e_entry = 0`, три program header, таблицы секций нет (штатно для kd-модулей).

| PH | тип | файл | vaddr | filesz | memsz | flags | что это |
|---|---|---|---|---|---|---|---|
| 0 | PT_LOAD | 0xA0 | `0x81000000` | 0x84 | 0x84 | R+X | `SceModuleInfo` + таблицы |
| 1 | PT_LOAD | 0x130 | `0x81001000` | 0xF6DF8 | 0xF6E00 | R+W+X | **полезная нагрузка MeP** |
| 2 | `0x60000000` | 0xF6F30 | 0 | 0x24 | 0 | — | таблица релокаций |

### 1.1 SceModuleInfo (файл 0xA0, `e_entry == 0`)

```
+0x00 u32 attribute = 0            (+0x02 u16 modversion = 0x0101)
+0x04 char modname[27] = "SceVeneziaImage"
+0x1F u8  type = 0x06
+0x20 u32 gp = 0
+0x24 u32 export_top = 0x5C        (смещение от базы сегмента 0)
+0x28 u32 export_end  = 0x7C
+0x2C u32 import_top  = 0
+0x30 u32 import_end  = 0
+0x34 u32 module_nid = 0xEEA339DA
```

**Важно:** `0xEEA339DA` — это *module* NID, он одинаков у всей «image»-семьи
(`SceVeneziaImage`, `SceVipImage`, `SceKernelBootimage`, `SceSblPcbcBin`,
`SceSblPcffBin`, `SceWlanBtRobinImageAx`, `SceKernelPsp2Config`); вероятнее всего
это артефакт сборки blob-модулей с `e_entry = 0`, а не идентификатор ABI.

### 1.2 Таблица экспорта (одна запись)

`SceLibEntTable` по адресу `module_info + 0x5C` = файл 0xFC, 0x20 байт:

| поле | значение |
|---|---|
| size (u8 @+0) | 0x20 |
| version (u16 @+2) | 0 |
| attribute (u16 @+4) | 0 |
| num_functions (u16 @+6) | **0** |
| num_vars (u16 @+8) | **1** |
| lib_nid (u32 @+0x10) | **0x6C2224BA** |
| nid_table (u32 @+0x18) | `0x81000080` |
| entry_table (u32 @+0x1C) | `0x81000054` |

То есть модуль экспортирует **не функцию, а переменную**: NID `0x6C2224BA` →
`0x81000054`, а по этому адресу (файл 0xF4) лежит указатель на собственный
`SceModuleInfo` (`0x81000000`). Значение `0x6C2224BA` нигде в дереве прошивки
не разрешается в имя — что именно читает по нему клиент, не установлено.

Импортов у модуля нет вообще: `vnzimg` не вызывает ARM-API, он сам является
драйвером (всю работу с ядром делает `SceVeneziaWrapper`, см. §3).

### 1.3 Трейлер PH[2] — таблица релокаций

`0x60000000` — это не «данные», а SCE-таблица релокаций; записи по 12 байт
`[type][target_off][slot_off]`:

| type | смысл |
|---|---|
| `0x200` | положить в `slot_off` указатель `base + target_off` |
| `0x2F00` / `0x2F10` | младшая половина иммедиата `movw` |
| `0x3000` / `0x3010` | старшая половина иммедиата `movt` |

Записи `vnzimg` (файл 0xF6F30): `(0x200, 0x7C, 0x74)`, `(0x200, 0x80, 0x78)`,
`(0x200, 0x00, 0x80)` — ровно `nid_table`, `entry_table` и указатель на
`SceModuleInfo` из §1.2. Такая же таблица есть у `vipimg.elf` (модуль-близнец
для VIP-движка, байт-в-байт совпадающий заголовок).

## 2. Сегмент 1 = образ MeP (Venezia)

**Кода ARM в модуле нет.** Модули этой прошивки — Thumb-2 (контроль:
`systimer.elf` экспорт `0x810002BC` = `push {r3-r7,lr}`), а в сегменте 1
`push{..,lr}`/`pop{..,pc}` не встречается ни в одном 4-КиБ блоке. Сегмент 1 —
это чистый образ для второго вычислителя.

* **База образа: `0x80000000`** (не `0x81001000` — это ARM-адрес размещения).
* Длина: 0xF6DF8 = 1 010 168 байт.
* Заголовок — таблица векторов:

```
0x80000000  jmp 0x80063c        ; Reset
0x80000004  jmp 0x800a42
0x80000008  jmp 0x800008        ; заглушки: прыжок на себя
0x8000000C  jmp 0x80000c
0x80000010  jmp 0x800010
0x80000014  jmp 0x800014
0x80000018  dret
0x8000001A  ... нули до 0x80000200
```

Расхождение с wiki: там «шесть `jmp 0x800018`»; в 1.04 фактически два
осмысленных вектора и четыре заглушки, а `0x800018` — `dret`.

* детальный дизассемблерный разбор образа (reset-обработчик, цепочка
  инициализации, SPRAM-протокол, 1625 переключений в VLIW, граф вызовов) —
  **`docs/VNZIMG_MEP.md`**;
* `zdis mep`: 419 954 инструкции, `*unknown*` **4.37 %** — это, по-видимому,
  данные и/или неразобранные IVC2-пакеты (см. §5).
* **SPRAM видна ядру MeP как `0xF1840000`**: `0x80011198 movh $10,0xf184`,
  таблица пар `0xF18400C0+8k`, запись `sw #1` в `0xF1840000` на `0x8001155E`.

### 2.1 Карта сегмента 1

| диапазон (ARM VA) | MeP VA | энтропия | что это |
|---|---|---|---|
| 0x81000000–0x81000084 | — | — | `SceModuleInfo` (сегмент 0) |
| 0x81001000–0x8100A000 | 0x80000000–0x80009000 | 5.3–6.9 | вектора, код, таблицы |
| 0x8100A000–0x81010000 | 0x80009000–0x8000F000 | ~0 | нули (bss/резерв) |
| 0x81010000–0x81062000 | 0x8000F000–0x80061000 | 6.0–7.1 | **основной код MeP** |
| 0x81062000–0x810D2000 | 0x80061000–0x800D1000 | 2.1–5.5 | таблицы/данные (много нулей) |
| 0x810D8000–0x810D9000 | 0x800D7000–0x800D8000 | 7.3–7.5 | плотные данные |
| 0x810E6000–0x810FF000 | 0x800E5000–0x800FE000 | 6.1–7.95 | **таблицы IEEE-754 double** |

Высокая энтропия в конце — **не шифр и не сжатие**: это таблицы `double`
(прогрессии 7.703/7.171/6.640…, 4.7e-8/4.1e-7/3.6e-6…), в которые ветвится
MeP-код (1121 ссылка). Ни `\x7fELF`, ни ENP-магии `0x64B2C8E5`, ни LZ-заголовков
в образе нет.

## 3. Кто и когда загружает vnzimg

Порядок (из текстовой конфигурации `fs_dec/os0/psp2config.skprx.seg00`,
`SceKernelPsp2Config`; текст начинается с файла 0xC8):

```
строка 38  os0:kd/fwloader.skprx      (SceSblFwLoader — вшит в bootimage.elf)
строка 39  os0:kd/vnz_wrapper.skprx   (SceVeneziaWrapper — вшит в bootimage.elf)
```

`vnzimg.skprx` в конфиге **нет**: его грузит сам `vnz_wrapper`
(код обёртки, Thumb-2):

| адрес | что делает |
|---|---|
| `0x8100066C` | `ksceKernelAllocMemBlock("ScePervasive2Reg", 0x20100806, 0x1000)` и `("SceVeneziaImage", 0x20108006, 0x1000)` + `GetMemBlockBase` |
| `0x81000780` | программирует Pervasive2: `regs[192]=0x1D001000`, `regs[193..196]`, `regs[224..239]`, `regs[256]`, `regs[898]=0xFFFF0000` |
| `0x81000840` | `SceSblFwLoaderForDriver 0xA6278D27`, `r0 = "os0:kd/vnzimg.skprx"` → **загрузка модуля по пути** |
| `0x81000850` | `SceSblFwLoaderForDriver 0x91C73A54` (r0=1, r1=база образа, r2=размер) → перенос нагрузки в Venezia (DMA или расшифровка внутри Sbl — не проверено) |
| `0x81000862` | `spram[0] = 1` |
| `0x81000866` | `SceCpuForDriver 0xE813EBB2` — L2 (импортируются `ksceKernelCpuDcacheAndL2{Invalidate,Writeback,WritebackInvalidate}Range`) |
| `0x81000872` | `ScePervasiveForDriver 0xA7E64C6F` = **reset_vnz** |
| `0x8100087C..86` | ожидание `spram[0] == 8`, затем ещё `0x10000` (`0x810008A6`) и `0x80000` (`0x8100096C`) |

**Вывод: протокол из wiki подтверждается дословно** (все пять шагов найдены в
коде с точными адресами). Константы `0x110` (L2 clean) в этой цепочке нет.

`bootimage.elf` (`SceKernelBootimage`, NID `0x17E65BD7`) — это **контейнер из 42
образов kd-модулей**, все слинкованы на `0x81000000` и лежат в файле подряд;
`SceVeneziaWrapper` — один из них (module info в контейнере по `0x810A3A94`,
`e_entry = 0xCBA0`, экспорт `SceVeneziaWrapperForDriver` NID `0x4F5231A4`
(47 функций) и `SceVeneziaWrapper` NID `0x2B2DA8E1` (16 функций)). Отдельного
файла `vnz_wrapper.elf` в прошивке нет — это встроенный модуль.

### 3.1 Потребитель: пользовательское пространство

`fs_dec/os0/us/avcodec_us.elf` (`SceAvcodecUser`) экспортирует
`SceVideodecUser 0x163C3727` (42), `SceVideoencUser 0x0BAA6DEF` (20),
`SceCodecEngineUser 0x469AB062` (6) и импортирует библиотеку
**`SceVeneziaWrapper` NID `0x2B2DA8E1` с 6 функциями**
(`0x03DCBDCA, 0x04BA9415, 0x362E9415, 0x489FF965, 0xAD30912D, 0xB0E654EE`).
То есть видеокодек пользователя ходит в Venezia через обёртку, а `vnzimg` —
нижний слой под ней.

### 3.2 RPC и SPRAM

* `SceVeneziaSpram` — membock, PA `0x1F840000`, размер `0x20000`
  (заводится в `0x81000D7C`); чтение/запись `spram[0]` — `0x81000FCC`/`0x81000FE0`.
* Команда ARM → Venezia — 256-байтовый блок: `0x81001034`
  `memcpy(spram, 0x8100ED8C, 0x100)`.
* Объекты RPC: `SceVeneziaRpcCh`, `SceVeneziaRpc` (очередь 0x2000, 8/8),
  `SceVeneziaRpcDebug`, `SceVeneziaRpcBlocking`, `SceVeneziaRpcCommunicationHeap`,
  `SceVeneziaRpcDma`, форматы имён `SceVeneziaMailbox%02u` и
  `SceVeneziaDmacMemcpy%02u`; 16 каналов (номер = аргумент & 0xF), у каждого
  свой регистр статуса `0x8100EE8C+0x10·n` и своё событие (обработчик
  `0x81001060`).
* Идентификаторы и структуры сообщений видны только со стороны MeP — в ARM-коде
  их нет.

## 4. Архитектурные особенности

* **Два ядра в одном модуле.** ARM-часть (`SceVeneziaImage`) — это только
  контейнер и таблицы; исполняемый код — образ MeP в сегменте 1. Из-за этого
  модуль выглядит «мёртвым» для ARM-дизассемблера.
* **Общая память — не окно, а копирование.** ARM пишет 256-байтовые блоки в
  SPRAM (`0x1F840000` / у MeP `0xF1840000`) и синхронизируется байтовым
  почтовым ящиком `spram[0]` (`1` → старт, `8` → «код исполняется»).
* **VLIW (IVC2).** Ядро MeP-c5 расширено копроцессором IVC2: в режиме VLIW
  (PSW.OM, бит 12) выборка идёт 64-битными пакетами, и в одном пакете
  исполняются ядровая инструкция и 1–2 инструкции копроцессора. Три формы
  пакета (V1/V2/V3) и четыре слота (C3, P0S, P0, P1) разобраны в §5.
* **Релокации как часть модуля.** Трейлер PH[2] — это не данные, а таблица
  правок (указатели + половинки `movw`/`movt`), применяемая загрузчиком.
* **SPRAM в модели zeliboba не отображена** — отдельный пункт для второго этапа.

## 5. Дизассемблер IVC2 в zeliboba (перенос)

### 5.1 Что добавлено

| файл | назначение |
|---|---|
| `src/cpu/mep/mep_ivc2.h` | интерфейс: `ivc2_split_packet`, `ivc2_decode_slot`, `ivc2_format`, `ivc2_disassemble_slot` |
| `src/cpu/mep/mep_ivc2.cpp` | разбор пакета V1/V2/V3, декодер и форматтер слотов |
| `src/cpu/mep/mep_ivc2_table.inc` | **сгенерированная** таблица: 688 кодировок (C3 293, P0S 134, P0 131, P1 130) |
| `tools/gen_ivc2_table.py` | генератор таблицы из CGEN-описания |
| `tools/data/mep-ivc2.cpu`, `tools/data/mep-core.cpu` | исходные CGEN-описания (binutils/GDB) |
| `tests/test_mep_ivc2.cpp` | 8 тестов: разбор пакетов, формат, VLIW-режим ядра |

`MePCore::disassemble()` в режиме VLIW печатает пакет как
`<ядро> + <слот> [ + <слот>]`, `zdis` получил флаг `--vliw`.

### 5.2 Формат пакета

Разбор повторяет `opcodes/mep-dis.c` (`mep_examine_ivc2_insns`) для little endian:

| форма | условие (байт 1 памяти) | состав |
|---|---|---|
| **V1** | высокая тетрада < 0xC | `[ядро 16][p0s 16][p1 32]` |
| **V2** | иначе | `[ядро 32]xxxx[p1 32]` |
| **V3** | высокая тетрада = 0xF и младшая тетрада байта 0 = 7 | `[p0 32][p1 32]`, ядра нет |

Слово слота — little endian-сборка байтов пакета (для p0s это байты 2..5, для
p0 — 0..3, для p1 — 4..7); поля извлекаются существующим `mep::raw()`, который
нумерует биты «от старшего» внутри каждой 16-битной половины, как CGEN.

Пример (реальные байты полезной нагрузки по `0x8000067E`):
`07 F8 06 F0 07 F9 06 F0` → V3, слоты P0/P1 (обе кодировки в таблице
отсутствуют и печатаются как `*unknown-p0* + *unknown-p1*`).

### 5.3 Ограничение, которое нужно знать

Генератор читает только `mep-ivc2.cpu` + `mep-core.cpu`. В `mep-core.cpu`
объявлены **не все** поля, на которые ссылается IVC2-файл (`f-ivc2-4u20`,
`f-21`, `f-29`, …), поэтому соответствующие биты операндов остаются
неограниченными и часть кодировок совпадает: **527 различных пар mask/value на
688 форм**. Из-за этого, например, `cmov-crn-rm` и `cmov-rn-crm` дают одну
запись. Для точного разбора нужен полный набор полей MeP-Integrator (либо
сверка с настоящим `mep-elf-objdump`).

Что проверено без него:

* таблица **самосогласована** — для каждой записи заполнение свободных битов
  произвольными значениями возвращает ту же запись (2752 пробы, 0 промахов);
* разбор пакетов и сборка слов слотов сверены с `opcodes/mep-dis.c` и с
  реальными байтами образа;
* 419 954 инструкции ядра MeP в полезной нагрузке разбираются, `*unknown*`
  4.37 %.

Полезная нагрузка **не содержит очевидных VLIW-пакетов** в начале (вектора и
`0x80000200..` — обычный MeP-c5); 4.37 % `*unknown*` — это, судя по карте
сегмента, данные, а не IVC2. Утверждать, что Venezia реально исполняет IVC2,
по этому образу нельзя: нужен трассировщик на работающей машине или сверка с
`mep-elf-objdump`.

## 6. Временное хранение secure_kernel в SPRAM: состояние модели

Wiki ([Venezia](https://wiki.henkaku.xyz/vita/Venezia), раздел «On boot time»)
утверждает: `SceVeneziaSpram` (PA `0x1F840000`, размер `0x20000`) используется
как **временное место хранения зашифрованного `secure_kernel`**; если область
очистить, `secure_kernel` не загрузится, хотя оболочка при resume покажется.

**В модели этого нет.** Проверено (2026-10):

| проверка | результат |
|---|---|
| `grep` по `src/` на `1F84` / `SPRAM` | нет совпадений — область не отображена ни на одной шине |
| загрузка secure kernel | `Vita::load_cmep_secure_kernel()` читает **расшифрованный** `Out/SLB2_dec/secure_kernel.bin` и кладёт сразу на `0x00800000` (CMeP SRAM); файлы `secure_kernel.enp`/`.enc` и SLB2-блок `0x16D` в загрузке не участвуют |
| watchpoints `0x1F840000`, `0x1F850000`, `0x1F858000` на полном прогоне (20 млн шагов, до `ARM started on kernel_boot_loader`) | **ни одного срабатывания** |
| трасса шины (`_scratch/dbg_run.txt`) | все 13 упоминаний `1F84…` — это выборка CMeP по PC `0x0001F83E…` (адрес совпал случайно), обращений ARM к окну нет |
| ссылки в образах | литерал `0x1F840000` есть только у ARM (`kernel_boot_loader.self.seg01` 0x39E66, `bootimage.elf` 0x6840E, `display/excpmgr/lowio/sysmem.elf`, `vnzimg.elf` 0x97CD8 = `0x1F850000`); в `vita_prototype_bootrom.bin`, `second_loader.bin`, `secure_kernel.bin`, `nsbl.bin` его **нет** |

Но и в железе пять сценариев записи вряд ли лежат на смоделированном пути:
MeP-стадии (`first loader` → `second_loader` → `secure_kernel`) адреса SPRAM не
знают вовсе, а ARM-стадии (`KBL` 0x39E66, `SceVeneziaWrapper` 0x81000780)
оперируют уже **дешифрованным** ядром и рабочим каналом RPC. Наиболее вероятная
(и пока не проверенная) реконструкция: зашифрованный `secure_kernel.enp`
укладывается ARM-стадией в `0x1F840000`, оттуда его читает CMeP-загрузчик и
после расшифровки переносит в свою SRAM `0x00800000`. Ни одна из двух сторон
этого шага в модели не реализована.

Что нужно, чтобы закрыть пункт:

1. отобразить `SPAD128K` (`0x1F840000`, `0x20000`) на `arm_bus_` как RAM
   (название региона — `SPAD128K`, алиас/Venezia-SPRAM — это один и тот же
   блок);
2. положить туда зашифрованный `secure_kernel.enp` на том же шаге, где
   реальная ARM-стадия это делает (сейчас — нигде);
3. завести трап-счётчик (как `ZLB_RTRAP`) на окно и проверить под трассой, что
   читает/пишет `second_loader`; watchpoints на полном прогоне уже готовы и
   сейчас молчат;
4. учесть, что при resume область, по вики, сохраняется — то есть в модели это
   должна быть память, переживающая reset ARM, а не обнуляемая при каждом
   старте.

## 7. Что осталось нерешённым

1. Семантика NID `0x6C2224BA` (экспортируемая переменная `vnzimg`).
2. Что именно делает `SceSblFwLoaderForDriver 0x91C73A54` при переносе образа
   (DMA? расшифровка? копия?).
3. Формат 256-байтового командного блока ARM → Venezia.
4. Идентификаторы и структуры RPC-сообщений (видны только со стороны MeP).
5. Точный внешний вызывающий `SceCodecEngineBoot`.
6. Есть ли в образе реальные IVC2-пакеты (см. §5.3).
7. Полный набор полей CGEN, чтобы убрать совпадения кодировок в таблице.
