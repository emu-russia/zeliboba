# vnzimg.elf: дизассемблерный разбор образа MeP (Venezia)

Это детальный разбор **полезной нагрузки MeP** из `vnzimg.elf` — того самого
сегмента 1, который ARM-загрузчик переносит в приватную память Venezia и
запускает. Контейнерная часть, цепочка загрузки и RPC — в `docs/VNZIMG.md`.

Все листинги получены `build/bin/zdis.exe` (тот же декодер, что исполняет
интерпретатор): `MeP/mep-c5` + таблица из `mep-core.cpu`, без IVC2.
Адреса — виртуальные адреса MeP, база образа **`0x80000000`**.
Файл-смещение = `0x130 + (VA - 0x80000000)`.

```
zdis mep <vnzimg.elf> --base 0x80000000 --offset 0x130 --count 600000
```

---

## 1. Что это за образ: карта по 4 КиБ

Всего декодировано **419 954 инструкции**, 151 различная мнемоника.
Распределение по блокам (доля `*unknown*` — маркер данных):

| MeP VA | что там |
|---|---|
| `0x80000000–0x80000020` | векторная таблица (6 `jmp` + `dret`) |
| `0x80000020–0x80000200` | нули (зарезервированный векторный блок) |
| `0x80000200–0x80000D00` | **заголовок образа**: стек ядра, per-core структуры, обработчики |
| `0x80000D00–0x8000062000` | основной код ядра (~400 КиБ) |
| `0x80061800–0x80063000` | таблица точек входа VLIW (см. §6) |
| `0x80063000–0x800D1000` | данные, таблицы, константы |
| `0x800D8000–0x800E6000` | плотные таблицы (энтропия 7.3–7.5) |
| `0x800E6000–0x800FF000` | таблицы IEEE-754 double |

Статистика по инструкциям (весь сегмент, включая данные — точный подсчёт по
полному листингу из 419 954 строк):

```
nop          123533  (29%)   bsr          9019     lmcp        2484
mov           36567            beqz         6051     lmcpi       2214
lw            29942            bra          5905     smcp        1816
sw            25433            lbu          5710     smcpi       1533
*unknown*     18335  (4.37%)   sltu3        5059     ret         1560
add3          16231            sub          5029     bsrv        1556
sb            10492            sh           4802     lwcp        1237
--reserved--  10077            lhu          4412     swcp        1150
add            8498            neg          4210     repeat       709
lb             6651            bnez         3958     jsr          495
slt3           6403            movu         3784     stcb+ldcb    591
                               ldc          2957     cache        310
                               jmp          1929     ei+di        149
                               jsrv           69     sleep+halt     4
```

`nop` + `--reserved--` + `*unknown*` = 151 945 (36 %) — это в основном
выравнивание и содержимое таблиц: линейный проход разбирает и данные. Настоящий
код — диапазон `0x80000200 … 0x80061800`, где доля `*unknown*` падает до 4 %.

Полезные маркеры: `jsrv`/`bsrv` = **1625** переключений в VLIW (см. §6),
`stcb`/`ldcb` = 591 обращение к control bus, `cache` = 310, `swi` = 30,
`break`/`sleep`/`halt`/`dret` — единицы (аварийные пути), `ret` = 1560 при
9019 `bsr` (остальные вызовы — хвостовые `jmp`).

## 2. Векторная таблица образа

```asm
80000000  E8 D9 06 80   jmp 0x80063c     ; reset -> заголовок образа (см. §3)
80000004  18 DA 0A 80   jmp 0x800a42     ; базовый адрес таблицы обработчиков
80000008  48 D8 00 80   jmp 0x800008     ; заглушка (jmp на себя)
8000000C  68 D8 00 80   jmp 0x80000c     ; заглушка
80000010  88 D8 00 80   jmp 0x800010     ; заглушка
80000014  A8 D8 00 80   jmp 0x800014     ; заглушка
80000018  13 70         dret             ; «нет исключения»
8000001A  ...           нули до 0x80000200
```

Расхождение с вики: там «шесть `jmp 0x800018`» — в 1.04 это два осмысленных
вектора, четыре заглушки и `dret`. `jmp` в MeP — абсолютный (24-битное поле
`f-24u5a2n`), поэтому адреса в таблице самодостаточны.

По адресу `0x80000A42` начинается **таблица обработчиков исключений**: каждый
вход — мини-пролог, который кладёт номер вектора в `$tmp` и уходит в общий
вход `0x80000AAE`:

```asm
80000A42  add3 $sp,$sp,-4      ; вектор 1
80000A46  sw   $0,($sp)
80000A48  mov  $0,1
80000A4A  stc  $0,$tmp
80000A4C  lw   $0,($sp)
80000A4E  add3 $sp,$sp,0x4
80000A50  jmp  0x800aae
...                            ; вектор 2 -> $tmp=2, вектор 3 -> 3, и т.д.
80000A36  reti                 ; есть и отдельные reti-входы
```

## 3. Reset-обработчик: `0x8000063C`

Точка входа после сброса ядра. Полный листинг — в `_scratch/mep_listings.md`,
здесь разбор по шагам.

```asm
8000063C  mov $0,0          ; 1) обнулить весь GPR-банк
8000063E  mov $1,$0
   ...                       ; $2..$12, $tp, $gp
80000656  mov $tp,0
80000658  mov $gp,0

8000065A  ldc $1,$opt        ; 2) OPT: сбросить $hi/$lo, если нужен чистый старт
8000065C  movh $12,0x300
80000664  and $1,$12
80000666  beqz $1,0x8000066e
80000668  mov $0,0
8000066A  stc $0,$hi
8000066C  stc $0,$lo

8000066E  ldc $1,$opt        ; 3) OPT бит 4 -> «инициализация внутренней RAM»
80000674  movh $12,0x10
80000678  and $1,$12
8000067A  beqz $1,0x8000069e ;    в обычном запуске бит снят, блок пропускается
8000067C  xor $0,$0
8000067E  ...                ; 32 байта 07 F8 06 F0 .. 07 FF 06 F0 (таблица/патч)
8000069E  movu $5,0x200      ; 4) стек на ядро: 0x200 байт на ядро
800006A2  movh $4,0x4081
800006A6  add3 $4,$4,-29440  ;    r4 = 0x40810000 - 0x7300 = 0x40808D00
800006AA  ldc  $0,$id        ; 5) номер ядра из $id
800006AC  sra  $0,0x10       ;    ($id >> 16)
800006AE  and3 $0,$0,0x7     ;    & 7  -> 0..7 (8 ядер Venezia)
800006B2  mov  $9,$0
800006B4  sll  $9,0x9        ;    * 0x200
800006B6  add3 $4,$4,$9      ;    база стека этого ядра
800006B8  add3 $sp,$4,$5     ;    $sp = база + 0x200
800006BA  movh $9,0xd081     ; 6) адрес per-core записи
800006BE  add3 $9,$9,-23744
800006C2  sll  $0,0x7        ;    * 0x80
800006C4  add3 $9,$9,$0
800006C6  sw   $4,64($9)     ;    +0x40 = база стека
800006CA  sw   $5,68($9)     ;    +0x44 = размер стека
800006CE  movh $12,0x80      ; 7) вызов инициализации ядра
800006D2  add3 $12,$12,3394
800006D6  jsr  $12           ;    $lp = 0x800006d8, прыжок
800006D8  bra  0x800006d8    ; 8) страховка: если инициализация вернулась — вечный цикл
```

Таким образом **§3 — это распределение стека по 8 ядрам** (база `0x40808D00`,
шаг `0x200`) и передача управления в инициализацию. Адрес `0x40808D00` лежит в
DRAM (`0x40800000` — область образа, которую настраивает ARM через Pervasive2
`regs[192..196]`, см. `docs/VNZIMG.md` §3).

Вектор 2 (`0x80000A42`) попадает в ту же логику: это «базовый адрес таблицы
обработчиков», а не отдельный код.

## 4. Цепочка инициализации: `0x80000E40`

`jsr $12` из пролога ведёт в блок инициализации. Хвост цепочки:

```asm
80000EC0  mov  $12,0
80000EC2  movh $11,0xd081
80000EC6  sw   $12,-20512($11)    ; снять флаг «идёт инициализация»
80000ECA  ldc  $12,$psw
80000ECC  or3  $12,$12,0x100      ; PSW.8 = разрешение аппаратных прерываний
80000ED0  stc  $12,$psw
80000ED2  ei                      ; разрешить прерывания
80000ED4  movh $12,0x4080
80000ED8  lw   $1,($sp)           ; эпилог: восстановить $0,$1,$3,$5..$8,$tp
   ...
80000EEA  add  $sp,28
80000EEC  add3 $2,$12,768         ; r2 = 0x40800300
80000EF0  stc  $0,$lp
80000EF2  jmp  0x8036c0           ; переход в основной цикл (адрес берётся из $lp)
```

Инициализация — последовательность вызовов по подсистемам, каждый с
`$1 = $6`:

| вызов | адрес | назначение (по окружению) |
|---|---|---|
| `bsr 0x800012a8` | 0x80000E4A | первый шаг, до проверки готовности |
| `bsr 0x80003e1c` | 0x80000E50 | подсистема A |
| `bsr 0x8000357c` | 0x80000E56 | подсистема B |
| `bsr 0x8000371e` | 0x80000E60 | подсистема C (с аргументами $2,$3) |
| `bsr 0x80005540` | 0x80000E66 | подсистема D |
| `bsr 0x80001630` | 0x80000E7E | вызывается, только если `[0xD081AFE0]==0` и `[0xD081B02C]==0` |
| `bsr 0x8000643a` | 0x80000E84 | подсистема E |
| `bsr 0x800040e8` | 0x80000E8A | подсистема F |
| `bsr 0x80001b40` | 0x80000E92 | подсистема G |
| `bsr 0x80001028` | 0x80000E98 | подсистема H |
| `bsr 0x80001f18` | 0x80000E9E | подсистема I |
| `bsr 0x8000834e`, `0x80004c30`, `0x80004af4` | 0x80000EA4.. | при `$6 != 0` |
| `bsr 0x80000f6c` | 0x80000EBC | при `$7 != 0`, предварительно `[$5] = 1` |

Внутренняя RAM ядра (в MeP это «Hardware Extensions» с окном на data RAM,
`0xD081xxxx` — локальное окно образа) инициализируется отдельно: в районе
`0x80000D80` идёт цикл `repeat` по таблице из 8 записей с шагом `0x80`,
обнуляющий `+0x00..+0x28` — это те же **per-core структуры**, в которые пролог
пишет базу стека (`+0x40/+0x44`).

## 5. SPRAM (`0xF1840000`) и почтовый ящик

В образе ровно **три** обращения к SPRAM по абсолютному адресу:

| адрес | инструкция | смысл |
|---|---|---|
| `0x80011198` | `movh $10,0xf184` | запись в таблицу пар |
| `0x8001119C` | `movh $9,0xf184` | она же |
| `0x8001155E` | `movh $12,0xf184` | запись `spram[0] = 1` |

Это ровно тот протокол, который описала вики («`movh $0,0xf184` … `sw $1,0($0)`»),
но уже в контексте драйвера ядра.

### 5.1 Таблица пар `0xF18400C0 + 8k`

```asm
80011198  21 CA 84 F1   movh $10,0xf184
8001119C  21 C9 84 F1   movh $9,0xf184
800111A0  94 C9 C0 00   or3  $9,$9,0xc0      ; $9 = 0xF18400C0
800111A4  A4 CA C4 00   or3  $10,$10,0xc4    ; $10 = 0xF18400C4
800111A8  10 CC D0 FF   add3 $12,$1,-48      ; индекс = аргумент - 48
800111AC  1F 6C         sll3 $0,$12,0x3      ; * 8
800111AE  AC 90         add3 $12,$0,$10      ; +0xF18400C4
800111B0  9B 90         add3 $11,$0,$9       ; +0xF18400C0
800111B2  BA 01         sw   $1,($11)        ; [0xF18400C0 + 8k]  = arg1
800111B4  CA 02         sw   $2,($12)        ; [0xF18400C4 + 8k]  = arg2
800111B6  02 70         ret
```

Это чистая «запись пары (word0, word1) в слот k» — тот самый вид доступа,
который виден в ARM-драйвере как `spram[0]`/`spram[1]`. Границы: индекс
`arg1 - 48` (то есть `0x30` — начало полезных слотов), шаг 8 байт — согласуется
с 256-байтовым командным блоком ARM (`memcpy(spram, 0x8100ED8C, 0x100)`).

### 5.2 Сигнал «готово»: `spram[0] = 1`

```asm
80011558  0D A1         bnez $1,0x80011564    ; только при аргументе 0
8001155A  21 CB 01 00   movh $11,0x1
8001155E  21 CC 84 F1   movh $12,0xf184
80011562  CA 0B         sw   $11,($12)        ; 0xF1840000 = 1
80011564  02 70         ret
```

Это ровно тот шаг, на котором ARM-драйвер (`0x8100087C..86` в
`SceVeneziaWrapper`) крутит ожидание `spram[0] == 8`. То есть **ответная сторона
протокола найдена в самом образе MeP**: MeP пишет `1` в `0xF1840000`, ARM
(и/или MPE) видит это через `0x1F840000`.

### 5.3 Как эти функции вызываются

Обе точки входа лежат внутри **одной большой процедуры** `0x80011198 …`
(её продолжение — `0x800111B8`, `0x80011226`, `0x80011278`, `0x800114xx`), и
прямых `bsr`/`jsr` на `0x80011198` или `0x80011558` в образе нет — это
внутренние метки одного модуля, куда управление приходит падением:

```asm
8001152A  bsr 0x80011544    ; диспетчер: jmp $1 с таблицей переходов
80011544  sll3 $0,$1,0x2
80011546  movh $11,0xe310   ; окно Ernie/SC (SPI-регистры SoC)
8001154A  or3  $11,$11,0x6010
80011550  lw   $10,($9)
80011554  sw   $10,($12)
80011556  ret
80011558  bnez $1,0x80011564   ; <-- сигнал spram[0] = 1 (см. §5.2)
```

То есть `0x80011558` — это ветка «если аргумент == 0», вызываемая из того же
блока; рядом (`0x80011544`, `0x8001170E`) живёт обработчик, пишущий в
`0xE3106010` — окно Ernie/SC. Обращения к SPI-регистрам SoC из образа MeP
означают, что часть инициализации Venezia идёт через syscon, а не через ARM.

## 6. VLIW: где образ реально переключается в режим IVC2

Самое важное наблюдение для дальнейшей работы: **инструкции переключения в
VLIW-режим в образе есть, и их много**.

```
$ zdis mep ... | grep -E 'jsrv|bsrv'  ->  1625 переходов
```

Из них самые «горячие» точки входа:

| адрес VLIW-входа | вызовов |
|---|---|
| `0x800622E0` | 92 |
| `0x80046B78` / `0x80046B70` | 28 / 27 |
| `0x800AB070` / `0x800AAFE0` | 25 / 20 |
| `0x80013694` | 17 |
| `0x80083558` / `0x80083530` | 16 / 16 |
| `0x8008F290` / `0x8008F268` | 16 / 16 |
| `0x800864B0` | 14 |
| `0x80062328` | 10 |

Типовой вызов и типовой же слот:

```asm
80012FA6  5B D8 E9 04   bsrv 0x800618b0
800138C2  3B DB EA 04   bsrv 0x80062328
80013AE8  CB DF E7 04   bsrv 0x800622e0
```

То есть ядро работает в двух режимах: обычный MeP-c5 (вектора, инициализация,
загрузка) и VLIW — там, где начинается обработка изображения/потоков. Цели
`bsrv` группируются в диапазоне `0x80061800–0x80063000` и в нескольких
«горячих» кластерах выше — это и есть точки входа VLIW-кода.

Разбор самой вызываемой из них (`0x800622E0`: формат пакета, параметры,
листинг и псевдокод на C++) — **`docs/VNZIMG_VLIW_0x800622E0.md`**.

**Проверка `--vliw` на этих адресах** (`zdis … --vliw`) сейчас упирается в
ограничение таблицы IVC2: часть кодировок слотов совпадает (527 различных
пар mask/value на 688 форм, см. `docs/VNZIMG.md` §5.3), поэтому слоты
печатаются как `*unknown-p0*`/`*unknown-p1*`. Пример по адресу `0x8000067E`
(блок, который reset-обработчик пропускает):

```
8000067E  07 F8 06 F0 07 F9 06 F0   *unknown-p0* + *unknown-p1*
```

Это первый конкретный кандидат для проверки таблицы IVC2: байты
`07 F8 06 F0` дают V3-форму пакета (высокая тетрада байта 1 = `F`, младшая
тетрада байта 0 = `7`), и если после уточнения таблицы он разберётся как
осмысленная пара инструкций — значит, таблица верна.

### 6.1 Копроцессорные (32-битные `$c`) операция в образе

Помимо VLIW, образ активно использует **штатные** копроцессорные инструкции
MeP-c5 для работы с 32/64-битными `$c`-регистрами (они есть и без IVC2):

```
0x800145F0  lmcpi $c10,($6+)      0x80014620  smcpi $c10,($5+)
0x8001516A  lmcpi $c13,($2+)      0x8001519A  smcpi $c15,($1+)
0x80013778  swcp  $c12,($sp)      0x80013784  swcp $c12,4($sp)
```

Всего таких обращений `swcp/lwcp/smcp/lmcp*` — **12 058**. Это ожидаемо:
IVC2-аккумуляторы (`$acc0_*`, `$acc1_*`) и 64-битные `$cr` живут в этом же
пространстве, и ядро гоняет их через `smcp/lmcp` парой слов.

## 7. Граф вызовов: ключевые функции

Топ по числу входящих ссылок (адрес → вызовов):

| функция | вызовов | роль |
|---|---|---|
| `0x80006F6E` | 347 | ядро библиотеки: обработка/копирование, вызывается из десятков мест |
| `0x80006F7E` | 300 | то же, соседний вход |
| `0x8005A3F8` | 257 | общий сервис (вызовы идут подряд из `0x8003D72A…`) |
| `0x8003FC66` | 143 | сервис с плотным блоком вызовов из `0x8003FCA4…` |
| `0x80007800` | 140 | утилита |
| `0x800622E0` | 138 | **VLIW-точка входа** (см. §6) |
| `0x80006FA2` | 126 | утилита |
| `0x80054F90`, `0x80056556`, `0x800496B4`, `0x80007756` | 117…99 | сервисы |
| `0x800066A8`, `0x800066BE`, `0x800066BE`-семейство | 95…54 | утилиты; `0x800066BE` вызывается из блока SPRAM (`0x80011166`, `0x80011174`) |
| `0x80002B66` | 79 | утилита |

Характерная деталь: в блоке `0x80006500–0x80008000` плотно живут мелкие

`0x80006F6E`…), которые вызываются по всему образу — это, по-видимому,
библиотека времени выполнения тулчейна Toshiba (memcpy/memset/строки), а не
логика движка.

## 8. Что это даёт для эмулятора

1. **Точка входа для второго ядра MeP**: после сброса PC = `0x80000000`, первый
   `jmp` ведёт в `0x8000063c`; стек ставится в DRAM `0x40808D00 + 0x200*core`,
   номер ядра берётся из `$id` (`ldc $0,$id`, `>>16`, `&7`). Это готовый чек-лист
   для запуска ядра в модели.
2. **Протокол SPRAM двусторонний и найден с обеих сторон**: ARM пишет
   `1` в `0x1F840000` и ждёт `8`; MeP пишет `1` в `0xF1840000` функцией
   `0x80011558` и раскладывает пары по `0xF18400C0 + 8k` функцией `0x80011198`.
3. **VLIW используется по-настоящему**: 1625 переключений `bsrv`, десятки точек
   входа. Значит, без семантики IVC2 движок не поднять — но хотя бы известен
   точный список адресов, на которых проверять дизассемблер (`0x800622E0`,
   `0x800618B0`, `0x80046B70`, `0x800AB070`, …).
4. **Кандидат-эталон для таблицы IVC2**: `0x8000067E` (V3-пакет в заголовке,
   который штатный путь инициализации пропускает) и «горячие» входы из п.3.

## 9. Как воспроизвести

```powershell
# карта кода и статистика
python _scratch/vnzimg_dis.py stats
python _scratch/vnzimg_dis.py map
# аннотированный листинг участка
python _scratch/vnzimg_dis.py listing 0x8000063C 0x80000760
# конкретная функция
python _scratch/vnzimg_dis.py func 0x80011198 20
# VLIW-пакет (пока частично: см. §6)
build\bin\zdis.exe mep <vnzimg.elf> --base 0x8000067E --offset 0x7AE --count 2 --vliw
```

Готовые выдержки с листингами: `_scratch/mep_listings.md`.
Полный листинг образа (419 954 строки, 17.6 МБ) собран в
`_scratch/vnzimg.mep.asm`; воспроизводится так (важно писать файл через Python
или `Set-Content -Encoding utf8`: PowerShell-редирект `>` даёт UTF-16 и ломает
разбор):

```powershell
python -c "import subprocess;VNZ=r'Vita_104_Firmware\Out\fs_dec\os0\kd\vnzimg.elf';Z=r'zeliboba\build\bin\zdis.exe';out=subprocess.run([Z,'mep',VNZ,'--base','0x80000000','--offset','0x130','--count','600000'],capture_output=True,text=True).stdout;open('vnzimg.mep.asm','w',encoding='utf-8',newline='\n').write(out)"
```
