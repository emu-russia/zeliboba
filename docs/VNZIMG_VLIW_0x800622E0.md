# Venezia: VLIW-функция `0x800622E0` — дизассемблер и псевдокод

Разбор одного VLIW-обработчика из образа MeP модуля `os0/kd/vnzimg.elf`.
Это самая вызываемая VLIW-точка входа образа: **138 вызовов `bsrv 0x800622e0`**
(см. `docs/VNZIMG_MEP.md` §6).

---

## 1. Как читать этот код: формат VLIW-пакета

Venezia в режиме VLIW (PSW.OM) выбирает **64-битные пакеты**. Проверено на этом
адресе (см. `_scratch/ground_truth.py`):

```
файл 0x62310:  00 0C 00 00 00 00 00 00  60 B0 00 00 00 00 00 00  C0 09 ...
zdis --base 0x800622E0 --offset 0x62310  ->
   800622E0  00 0C   mov $12,$0
   800622E8  60 B0   bra 0x80062348
   800622F0  C0 09   mov $9,$12
```

* файл-смещение MeP-адреса: `0x130 + (VA - 0x80000000)`;
* пакет `k` = файл `0x62310 + 8k` = VA `0x800622E0 + 8k`;
* **ядровая 16-битная инструкция лежит в байтах 0..1 пакета**, остальные 6 байт —
  два слота IVC2 (p0s и p1);
* в этой функции все слоты нулевые (проверено по всем пакетам) — то есть
  скалярный код, упакованный по одному ядровому действию в 64-битный пакет.

Поэтому в листинге ниже «пустые» байты между инструкциями — это слоты, а не
`nop`-паддинг в обычном смысле.

## 2. Листинг

Снят штатным дизассемблером (тот же декодер, что исполняет интерпретатор),
строки-`nop` из слотов убраны:

```asm
                        ; ---- точка входа VLIW-подпрограммы
800622E0  mov  $12,0            ; r12 = 0   (смещение/счётчик)
800622E8  bra  0x80062348       ; сразу на проверку внешнего условия

                        ; ---- тело: очистка 16 байт и подсчёт
800622F0  mov  $9,$12           ; r9  = r12          (адрес записи)
800622F8  mov  $4,$10           ; r4  = r10          (индекс следующей записи)
80062300  mov  $2,0             ; r2  = 0            (записываемый dword)
80062308  mov  $3,1             ; r3  = 1
80062310  repeat $3,0x80062320  ; повторить блок [0x62318..0x62320) 1 раз
80062318  sw   $2,($9)          ; *r9 = 0
80062320  add  $9,4             ; r9  += 4
80062328  add  $4,1             ; r4  += 1
80062330  add  $10,2            ; r10 += 2
80062338  add  $12,8            ; r12 += 8
80062340  add  $11,1            ; r11 += 1           (номер итерации)

                        ; ---- условие внутреннего цикла
80062348  lw   $9,0x44($sp)     ; r9  = [sp+0x44]    (дескриптор)
80062350  lh   $4,24($9)        ; r4  = (s16)[r9+0x18]  — предел
80062358  sltu3 $0,$11,$4       ; cond = (r11 < r4)
80062360  bnez $0,0x800622F0    ; цикл, пока не прошли все r4 записей

                        ; ---- внешний счётчик и выход
80062368  lw   $12,0x2c($sp)
80062370  lw   $11,0x24($sp)
80062378  add  $12,1
80062380  sw   $12,0x2c($sp)
80062388  sltu3 $0,$12,$11
80062390  bnei $0,0x0,0x80061AE0 ; обратный вызов по «начальному адресу»

                        ; ---- эпилог
80062398  lmcp $c6,80($sp)      ; восстановить $c6 из кадра
800623A0  lw   $1,0x58($sp)
800623A8  lw   $5,0x5c($sp)
800623B0  lw   $6,0x60($sp)
800623B8  lw   $7,0x64($sp)
800623C0  lw   $8,0x68($sp)
800623C8  lw   $tp,0x6c($sp)
800623D0  add3 $sp,$sp,0x70     ; освободить кадр 0x70
800623D8  jmp  $1               ; возврат по $lp
```

## 3. Параметры и соглашение о вызове

Вызывается как `bsrv 0x800622e0` (ветвление в VLIW-подпрограмму, при этом
`$lp = PC+4`). Пример реального места вызова — функция `0x80016330`:

```asm
80016330  add  $sp,-16
80016332  ldc  $0,$lp
80016334  sw   $8,0xc($sp)
80016336  sw   $7,0x8($sp)
80016338  sw   $0,0x4($sp)
8001633A  mov  $8,$1           ; $8 = аргумент вызывающего
8001633C  mov  $2,$8           ; ---- параметр 2 = указатель/значение
8001633E  bsrv 0x800622e0      ; ---- параметр 1 = $1 (не менялся выше)
80016342  mov  $1,0
80016344  mov  $7,$0
80016346  mov  $2,$7
80016348  bsrv 0x800622e0      ; повторные вызовы с разными $1
8001634C  add3 $1,$0,46
80016350  mov  $2,$7
80016352  bsrv 0x800622e0
80016356  add3 $1,$0,-3328
8001635A  mov  $2,$7
8001635C  bsrv 0x800622e0
```

Отсюда соглашение:

| регистр | роль |
|---|---|
| `$1` | **параметр 1** (вход) и **адрес возврата** (`$lp`, восстанавливается через `jmp $1`) |
| `$2` | **параметр 2** (вход) |
| `$5` | указатель на кадр вызывающего (отсюда читается `[sp+0x44]`) |
| `$c6` | копроцессорный регистр, сохраняется в кадре (значит, функция его использует) |
| `$sp` | кадр `0x70` байт; сохраняются `$1, $5, $6, $7, $8, $tp` |

Внутри функции адресация идёт через **указатель на кадр вызывающего**:
`lw $9,0x44($sp)` берёт из своего кадра сохранённый указатель, а `lh $4,24($9)`
читает из него 16-битный предел. То есть параметром фактически является
**дескриптор**, по смещению `+0x18` которого лежит счётчик/предел.

## 4. Что делает функция (разбор по шагам)

1. `r12 = 0`, прыжок на проверку условия.
2. Проверка: `r9 = desc` (из кадра), `r4 = (s16)desc[0x18]`, `cond = (r11 < r4)`.
   `r11` — счётчик итераций, изначально 0, поэтому первый вход в тело
   происходит всегда (если предел > 0).
3. Тело: обнуляет один dword (`sw $2,($9)`, `r2 = 0`), затем сдвигает три
   «курсора»:
   * `r9 += 4` — следующий dword,
   * `r10 += 2`, `r4 += 1` — параллельные счётчики (шаг 2 и 1),
   * `r12 += 8` — смещение (шаг 8),
   * `r11 += 1` — номер итерации.
4. `repeat $3,…` перед телом — обёртка hardware-цикла MeP на одну итерацию;
   фактически это «одно действие за проход», типично для кода, собранного под
   VLIW-упаковку.
5. После прохода по всем `r4` записям — внешний счётчик `[sp+0x2c] += 1`, и
   сравнение с `[sp+0x24]`; если не дошли — **ветвление назад по адресу
   0x80061AE0** (это обращение к вызывающему/внешнему обработчику, а не
   локальный цикл).
6. Эпилог восстанавливает регистры (включая `$c6`) и возвращается `jmp $1`.

Итог по смыслу: **скалярная вспомогательная процедура, которая заполняет
16-байтовый (4×dword) блок нулями и ведёт параллельные счётчики**, вызываемая
138 раз с разными `$1` из разных мест образа. Точная семантика `$1` (вероятно —
индекс канала/класса) и `$2` (вероятно — указатель на буфер) из одного места
вызова не выводится: нужно проследить вызывающих.

## 5. Псевдокод на C++

Записано по листингу. Имена регистров сохранены как локальные переменные,
неизвестные поля дескриптора помечены; семантика `$1`/`$2` выводится только из
мест вызова (см. §3).

```cpp
// Venezia MeP VLIW sub-routine at 0x800622E0.
//
// Calling convention, восстановлено по `bsrv 0x800622e0`:
//   $1 -> arg        (и адрес возврата: подпрограмма уходит через `jmp $1`)
//   $2 -> ctx/desc   (вызывающий выставляет его перед вызовом)
//   $5 -> указатель на кадр вызывающего; из своего кадра функция берёт
//         [sp+0x44] и читает по нему `desc[0x18]` как предел
//
// Свой кадр 0x70 байт, сохраняются $1,$5,$6,$7,$8,$tp и $c6.

struct CallerFrame {                 // то, на что смотрит callee
    uint8_t  pad00[0x18];
    int16_t  limit;                  // +0x18: `lh $4,24($9)`
    uint8_t  pad1A[0x44 - 0x1A];
    uint32_t desc;                   // +0x44: `lw $9,0x44($sp)`
    uint8_t  pad48[0x58 - 0x48];
    uint32_t saved_r1, saved_r5, saved_r6, saved_r7, saved_r8, saved_tp;  // +0x58..0x6c
};

void venezia_sub_0x800622E0(uint32_t arg /* $1 */, uint32_t ctx /* $2 */,
                            CallerFrame& frame)
{
    const auto* table = reinterpret_cast<const uint8_t*>(frame.desc);

    // 0x800622E0: mov $12,0 ; 0x800622E8: bra -> сразу на проверку
    uint32_t offset = 0;             // $12, шаг 8
    uint32_t count  = 0;             // $11, номер итерации
    uint32_t cursor = 0;             // $9,  курсор записи (шаг 4)
    uint32_t cursor2 = 0;            // $10, второй курсор (шаг 2)
    uint32_t parallel = 0;           // $4,  параллельный счётчик (шаг 1)

    // 0x80062348: проверка (unsigned!)
    while (count < static_cast<uint32_t>(frame.limit)) {
        // 0x800622F0..0x80062318: обнулить один dword по курсору
        cursor   = offset;
        parallel = cursor2;
        for (uint32_t i = 0; i < 1; ++i) {              // `repeat $3` = 1 итерация
            *reinterpret_cast<uint32_t*>(const_cast<uint8_t*>(table) + cursor) = 0;
        }

        // 0x80062320..0x80062340
        cursor   += 4;
        parallel += 1;
        cursor2  += 2;
        offset   += 8;
        ++count;
    }

    // 0x80062368..0x80062390: внешний счётчик и уход в другую VLIW-подпрограмму
    uint32_t outer = frame.pad48[0];          // [sp+0x2c]
    uint32_t bound = frame.pad48[1];          // [sp+0x24]
    outer += 1;
    frame.pad48[0] = outer;
    if (outer != bound) {                     // `bnei $0,0x0,...`
        // 0x80061AE0 начинается с `bsrv 0x80006ab4` - это отдельная функция,
        // а не локальный цикл; управление уходит из этой подпрограммы.
        venezia_sub_0x80061AE0(outer, bound);
    }

    // 0x80062398..0x800623D8: эпилог
    //   lmcp $c6,80($sp)        -> восстановить $c6
    //   lw $1/$5/$6/$7/$8/$tp   -> восстановить регистры из кадра
    //   add3 $sp,$sp,0x70       -> снять кадр
    //   jmp $1                  -> возврат
}
```

### Замечания к псевдокоду

* `repeat $3` перед телом — аппаратный цикл MeP на **одну** итерацию: компилятор
  (или упаковщик под VLIW) оборачивает одиночное действие, чтобы уложить его в
  пакет. На поведение это не влияет, но объясняет лишнюю инструкцию.
* Ветка `bnei $0,0x0,0x80061AE0` — **не локальный цикл**: по `0x80061AE0`
  начинается другая VLIW-подпрограмма (её первая инструкция — `bsrv 0x80006ab4`),
  то есть это передача управления наружу.
* Слоты IVC2 в этой функции нулевые, поэтому псевдокод чисто скалярный. В
  соседних функциях слоты ненулевые, и там одну строку листинга надо читать как
  «ядровая инструкция + до двух слотовых в том же такте».
* Смещения `[sp+0x24]`, `[sp+0x2c]`, `[sp+0x44]`, `[sp+0x58..0x6c]` взяты из
  листинга; какие именно поля структуры вызывающего они означают — следующий шаг
  анализа (нужно проследить 138 мест вызова `bsrv 0x800622e0`).
