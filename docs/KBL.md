# kernel_boot_loader: что он делает и что ему нужно от железа

Всё ниже получено исполнением реального `kernel_boot_loader.self` из SLB2 прошивки 1.04
на нашем ARM-ядре (`--stage kbl`) и разбором его кода. Адреса — из образа, который
грузится по `0x40020000` (MMU выключен).

## Сегменты

| vaddr | размер | что |
|---|---|---|
| `0x40020000` | `0x3BFE0` | код (RX), точка входа `0x40020000` |
| `0x4005C000` | `0x5706C` | `.bss` (RW), filesz `0xF0` |
| `0x50000000` | `0x194CF` | второй RX-сегмент |

Отсюда: `0x40000000` — это **физическое окно DRAM** (KBL линкуется туда и работает
до включения MMU), а `0x80000000` — окно, через которое позже видны модули ядра.

## Последовательность (подтверждено трассой)

1. `cpsid if`, `clrex`, сброс SCTLR, обслуживание кэшей/TLB, стек на режим.
2. `mcr p15,0,r0,c1,c0,2` (CPACR) и `vmsr fpexc,#0x40000000`, затем `vmsr fpscr,#0` и
   **очистка всего регистрового файла NEON**:
   `vdup.32 q0, r0` + 15 × `vorr qN, q0, q0`.
3. Инициализация PL310 L2-контроллера: запись в фильтры (`+0x100`/`+0x104`),
   `+0xF60`, `+0xF80`, затем `+0x77C = 0xFFFF` и **ожидание сброса бита 0**.
   База блока берётся из указателя по `0x4005C03C` и равна `0x1A002000`.
4. Отдельный блок по `0x1A000000`: `+0x00 = 0x61`, `+0x0C = 0xFFFFFFFF`,
   `+0x50 = 0x0F`, `+0x54 = 0x0FFF`.
5. `cpsie`, включение MMU (`SCTLR.M`), `TTBR0 = 0x40108000`, `TTBR1 = 0x4010C04A`,
   `TTBCR = 2`, `DACR = 2`. При `N = 2` адреса ≥ `0x40000000` идут через **TTBR1**
   (база `0x4010C000`, младшие 14 бит — управляющие).
   ВАЖНО: этот порядок (MMU → векторы → SC/eMMC) наблюдался на **сломанном**
   декодере Thumb-2 и был артефактом (см. «Пустая таблица» ниже). На исправленном
   декодере KBL сначала поднимает SC/SDIF/eMMC, а настройка MMU — позже, в хвосте
   SC-блока (`400215A2 bne.w` / `400215BE b.w 0x40020B62`), до которого мы пока не
   доходим.
6. Установка таблицы векторов по `0x0`: `4E 04 00 00 4E 04 00 00 4E 24 00 00 4E 34 00 00`.
7. Далее — обращения к SC (`0xE31000xx`), `0xE3102100`, `0xE31000C0` и чтение
   разделов eMMC.

## SC-протокол, который использует KBL

```
4003C014  movs r3,#0x5C / movt r3,#0xE310     ; r3 = 0xE310005C
4003C01E  str  r1=1,[r3]                      ; дверной звонок
4003C020  ldr  r0,[r2] ; tst r0,#1 ; bne      ; ждать сброса бита 0
4003C02E  ldr  r2,[0xE31000C0] ; tst r2,#8 ; beq  ; ждать бит 3
4003C040  str  #8,[0xE31000C0]                ; подтверждение (write-1-to-clear)
4003C042  ldr  r3,[r2] ; ands r0,r3,#8 ; bne  ; ждать снятия бита 3
4003C066  ldr  r2,[0xE31000C0] ; tst r2,#0x10 ; beq ; ждать бит 4
4003C04C  str  #1,[0xE3100060] ; ждать сброса бита 0 (+0x0060)
4003C088  доступ к 0xE3102100 (program-and-poll)
```

То есть `0xE31000C0` — регистр событий с подтверждением «записью единицы»: биты 3 и 4
поднимаются syscon'ом и снимаются записью. В эмуляторе это `Ernie.SC` (см.
`src/hw/syscon/ernie_sc.cpp`, `events_c0_`), а сам регистр доступен ARM-стороне через
зеркало в `Vita::wire_bridges()`.

## Что пришлось добавить в машину именно из-за KBL

| Окно | Почему | Как смоделировано |
|---|---|---|
| `0x40000000` + 128 МиБ | здесь линкуется KBL и лежит его `.bss` (до `0x400B306C`) | RAM-регион `arm_priv` |
| `0x50000000` + 4 МиБ | четвёртый `PT_LOAD` | RAM-регион `arm_buf` |
| `0x1A000000` | PL310 L2: фильтры + командные регистры `+0x77C`, `+0xF60`, `+0xF80` | `L2CacheController`: именованные регистры хранятся, все прочие читаются как 0 и «выполняются мгновенно» |
| `0x34000000` | второй блок L2/кэш-контроллера (база из таблицы прошивки) | то же |
| `0xE20A0000` | GPIO (handshake) | зеркало `CMeP.GPIO` |
| `0xE31000C0` | регистр событий SC | `Ernie.SC::events_c0_` |

## «Пустая таблица»: настоящая причина (исправлено)

Симптом: KBL доходил до `40039FC4 mcr p15,0,r0,c1,c0,0` (MMU ON) и падал на
следующем фетче `40039FC8` с section translation fault, потому что
`0x40108000`/`0x4010C000` были целиком заполнены fault-записями `0x000001E0`.

Разбор (все адреса — из образа, трасса `history on` + `until` + `mem`):

```
40020B3C  push.w {r4-r11,r14} / sub sp,#116     ; _start (per-core)
40020B46  blx 0x40039F88   ; r0 = MPIDR & 0xF (mrc p15,0,r0,c0,c0,5)
40020B4E  beq.w 0x400211C4 ; CPU0 -> сброс .bss и main, per-core MMU не делает
...
400211C4  main: .bss [0x40061100,0x400B306C) = 0, затем инициализация
...
400215BE  bl 0x40020B62    ; <<< вход в настройку MMU/таблиц (минуя проверку CPU)
40020B62  ... конфиг-структура KBL (.bss, 0x400B2B30, указатель в 0x400B2EC8)
40020E48  блок «построить карту памяти»:
            0x40020E5E..0x4002104A  ~100 записей конфига (str.w rX,[r5,#imm12])
            4002104E  bl 0x4003A804    r0 = [r5,#0x40] = 0x40108000 (TTBR0) — залить 0x1E0
            40021054  bl 0x4003A804    r0 = [r5,#0x60] = 0x4010C000 (TTBR1) — залить 0x1E0
            400210F0..40021102  bl 0x4003A824  ; L1[VA>>20] = L2-таблица (coarse page table)
            4002110A  bl 0x4003AB04            ; заполнить L2
            400211C2  b 0x40020C0E
40020C0E  TTBR0 <- 0x40108000, TTBR1 <- 0x4010C04A, TTBCR <- 2, DACR <- 2, CONTEXTIDR
40020CA2  blx 0x40039F94   ; ARM-функция 0x40039F94: SCTLR.M = 1
```

То есть **пустая таблица — не следствие отсутствующего boot-info в r0..r3**
(KBL сам читает MPIDR и сам строит всю карту в своём `.bss`; на входе r0..r3 = 0
корректно). Причина в декодере Thumb-2 эмулятора: форма «load/store single data
item» различалась не по тому биту.

```
imm12-форма (T3)  : 1111 1000 1100 Rn Rt imm12          (hw1[7] = 1)
register-форма(T2): 1111 1000 0100 Rn Rt 000000 imm2 Rm (hw2[11:6] = 0)
imm8-форма (T4)   : 1111 1000 0100 Rn Rt 1 P U W imm8
```

Эмулятор считал признаком register-формы `hw2[11] == 0` **внутри** imm12-ветки, а
T2-форму с `hw1[7] == 0` вообще не разбирал (она уходила в T4, т.е. адрес терял
`Rm << imm2`). Последствия для KBL:

* `str.w r7,[r5,#0xB0]` (hw1=0xF8C5, hw2=0x70B0) писалось как `[r5 + r0]` — поля
  конфига (`[r5+0x40]`/`[r5+0x60]` — базы таблиц, базы/размеры регионов) не
  заполнялись, а мусор улетал по чужим адресам;
* `str.w r3,[r0,r2,lsl#2]` (hw1=0xF840, hw2=0x3022, установка L1-дескриптора)
  писалось как `[r0]`;
* хелперы битовой карты `0x4003B824/0x4003B860/0x4003B89C`
  (`ldr.w/str.w rX,[r3,r2,lsl#2]`) читали и **перезаписывали слово 0** карты,
  из-за чего KBL уходил в ложную ветку обработки ошибки (`400212AC` с печатью
  через `0x40037514`) и включал MMU по аварийному пути с пустыми таблицами.

Исправление (в `src/cpu/arm/arm_core.cpp`, `thumb32_load_store_single`, плюс тот
же разбор в `src/cpu/arm/arm_disasm.cpp`):

* `hw1[7] == 1` → всегда imm12 (T3, без writeback);
* `hw1[7] == 0` и `hw2[11:6] == 0` → register-форма с `offset = Rm << imm2`;
* `hw1[7] == 0` и `hw2[11:6] != 0` → imm8 с P/U/W (T4);
* то же правило для знакового пространства `0xF9xx` (LDRSB/LDRSH).

Проверка декодирования — независимым дизассемблером (capstone 5): `40 F8 22 30`
= `str.w r3,[r0,r2,lsl#2]`, `D5 F8 B0 30` = `ldr.w r3,[r5,#0xB0]`.

## Состояние после исправления Thumb-2 (историческая справка, см. ниже актуальное)

`build\bin\zeliboba.exe -q --stage kbl -ex "runm 3000" -ex "core arm" -ex "info"`:

* ARM больше не ловит ни одного MMU-fault (`faults=0`, `MMU off`, `SCTLR=0`),
  выполняется 2.5M+ инструкций вместо 296 480;
* KBL проходит PL310 (`0x1A000000`), GPIO (`0xE20A0000`), SC (`0xE3101124`,
  `0xE3102100`, `0xE3102124`), программирует SDIF (`0xE2040004/10/20/30/40/50/60/64`)
  и упирается в ожидание бита 9 регистра `0xE2040028`
  (`4003BCC0: ldr r0,[r2,#0x28] ; tst r0,#0x200 ; beq`), который наша модель SDIF
  не выставляет. Сам MMU-блок (`0x40020B62`) на нормальном пути вызывается
  позже, уже после успешного подъёма eMMC.

## Исправлено: `IT`-блоки (`ite`) и глина блока `0xE2030000`

**`IT`-блоки.** Бит `E` в маске `IT` не инвертировал условие: `thumb_condition()`
возвращала `firstcond` для всех инструкций блока, поэтому в `ite` выполнялись обе
ветви. Это и ломало построение карты памяти: обёртка `0x40020A98` выбирает таблицу
именно так —

```
40020AA8  cmp r2, r4
40020AAC  ite hs
40020AAE  ldrhs r0, [r0, #0x40]     ; TTBR0
40020AB0  ldrlo r0, [r0, #0x60]     ; TTBR1
```

— поэтому хелпер получал указатель на конфиг вместо базы таблицы, и секционные
дескрипторы уезжали в `.bss`. Модель приведена к ARM ARM: `ITSTATE = firstcond[3:1]
: mask[4:0]`, условие — `ITSTATE[7:4]`, бит 4 приходит из сдвига маски, конец блока —
`ITSTATE[2:0] == 0`. Тесты: `thumb_it_block_it_else` (переписан на `mov.w`, потому
что `movs` в «then» честно меняет Z и тогда «else» обязан выполниться),
`thumb_it_block_conditional_ldr` (та же связка `ldrhs`/`ldrlo`, что у KBL).

**Глина блока `0xE2030000`.** `Kermit.Uart` (окно `0x100`) перекрывает glue-регистр
`+0x28`, а `Bus::find_device()` выбирает меньшее окно, поэтому ожидание бита 9
читало UART-регистр и висело. UART теперь отдаёт `+0x28 = 0x300` (питание/такт есть),
как и `Kermit.PeriphPower{N}`.

**Результат.** Карта памяти строится правильно (`tools/dump_l1.py`):

```
TTBR0[0x1A0] = 0x1A010182  section  (0x1A000000, PL310)
TTBR1[0x400] = 0x4001158E  section  (0x40000000, identity — код KBL)
TTBR1[0x500..0x51F]         section  (0x50000000.., staging)
```

KBL проходит включение MMU и **исполняется с включённой MMU** (667 трансляций,
313 465 инструкций ARM). Первый fault теперь:

```
fault[0]: VA=0x4003AFB6 fetch domain fault, domain=12,
          TTBR1 L1[0x4010D000]=0x4001158E
```

Разбор показал, что «domain fault» в отчёте — **устаревшая запись**, а не реальная
причина: `CP15 DACR = 0x55555555` (проверено и на входе в `0x40020CA2`, и в момент
fault'а — домен 12 = client, доступ разрешён), а `domain_fault()` в модели для
`dacr = 0x55555555, domain = 12` даёт `false`. В записи fault'а хранится вроде бы
секция `0x4001158E` (домен 12), но сама запись, судя по всему, описывает более
ранний walk, когда в `L1[0x4010D000]` ещё лежал fault-дескриптор `0x1E0`.

Хронология по шагам (`run` + `info`):

```
313 200 шагов  pc=0x4003A430  walks=267  faults=0  DACR=0x55555555   MMU уже включена
313 400 шагов  pc=0x400369B0  walks=567  faults=0  DACR=0x55555555
313 465 шагов  pc=0x0000012C  walks=667  faults=9  halted — двойной fault
```

То есть KBL исполняется с включённой MMU ~450 инструкций, а затем получает первый
fault по VA `0x4003AFB6` (свой же код, участок `0x40000000` — он в карте есть, но,
похоже, отображение появилось на считанные инструкции позже). Дальше срыв в
двойной fault происходит потому, что **таблица векторов (VA `0x0`) не отображена**:
в TTBR0 есть только секция `0x1A000000` (PL310), а VA `0x0` — fault-дескриптор,
поэтому обработчик исключения сам не может быть выбран.

Следующий шаг: смоделировать то, что на железе делает ARM boot ROM — отображение
нижней страницы векторов (VA `0x0` → PA `0x0`, где у нас лежит `arm_bootrom`, сейчас
пустой) и, при необходимости, identity-карту. Дамп ARM boot ROM в материалах
отсутствует (есть только CMeP ROM), так что это такое же документированное
допущение, как и модель «ARM boot ROM» в `bootchain.cpp`.

## Грабли (уже исправленные)

* **GIC с окном во весь регион.** `Kermit.Gic` создавался с окном `0x40000000 + 128 МиБ`;
  `Bus::find_device()` предпочитает устройство RAM, поэтому код KBL по `0x40020000`
  читался как нули и ядро «исполняло» `andeq r0,r0,r0`. Окно GIC уменьшено до
  `kPeripheralWindowSize = 0x10000`.
* **`STR.W`/`LDR.W` с пост-инкрементом** не делали writeback базы → бесконечный цикл
  очистки `.bss` (0x400211E0).
* **`AND.W Rd, Rn, Rm` (группа `1110 1010`) исполнялся как сдвиг по регистру.**
  В `thumb32_data_processing_shifted()` было особое правило «opc == 0, type == 0,
  imm3:imm2 == 0 → сдвиг по регистру», которое перехватывало `AND.W Rd, Rn, Rm`
  (`EA03 0302` = `and.w r3, r3, r2`, подтверждено capstone). Настоящие сдвиги по
  регистру (`LSL/LSR/ASR/ROR.W`) живут в группе `1111 1010 op1 Rn | 1111 Rd 0000 00 Rm`
  (`FA03 F002` = `lsl.w r0, r3, r2`) и раньше вообще не исполнялись — они попадали
  в `MUL/MLA`. Из-за этого зацикливался построитель карты памяти: проверка
  «`(размер-1) & счётчик == 0`» (тест на степень двойки) не работала. Обе части
  исправлены, добавлены тесты `thumb2_section_fill_loop_head` и
  `thumb2_register_controlled_shifts`.
* **A32 `LDREX`/`STREX`** декодировались как `SMULL` → спинлоки KBL крутились вечно.
* **`VMSR FPEXC`** не декодировался (opc1 считался как bits 23:20 вместо 23:21) → VFP
  не включался, KBL падал на `vmsr fpexc`.

## Раунд «CP15 + scratch-буфер»: что исправлено и что выяснено (актуальное)

Разделы «Где KBL находится сейчас» и «Что осталось» ниже оставлены как история
(они писались до правок Thumb-2 и CP15). Актуальное состояние — здесь.

### Исправлено в эмуляторе

1. **Консольный лог.** `attach_console_log()` в `src/debug/cli.cpp` сам отбрасывал
   всё, что ниже `Info`, хотя `Log::log()` уже фильтрует по уровню — из-за этого
   `--log debug` не показывал ничего. Теперь debug-строки видны.
2. **Чтение CP15.** В `ArmCore::cp15_read()` **не было** `case 3u`, то есть
   `mrc p15,0,r3,c3,c0` (чтение `DACR`) возвращал 0. KBL делает классический
   save/restore вокруг VA→PA-зондирования:
   `mrc DACR → r3` … `mcr DACR = 0x55555555` … `mcr DACR = r3`.
   Ноль на чтении означал «восстановить 0» → все домены выключены → domain fault
   на первой же выборке (это и был стоп на `0x4003AFB2`). Добавлены также чтения
   `TTBR0/TTBR1/TTBCR` (`c2`), `PAR` (`c7,c4,0`), `PRRR/NMRR` (`c10,c2,0/1`),
   `VBAR` (`c12`), `CONTEXTIDR` (`c13`).
3. **VA→PA (`V2P`) и `PAR`.** `mcr p15,0,Rt,c7,c8,opc2` (V2PCWPR/V2PCWUR/
   V2POWPR/V2POWUR) теперь реально транслирует адрес и публикует результат в
   `PAR`: `PAR[0]=1`, `PAR[31:12]=PA` при успехе, иначе `PAR[11:1]=статус`.
   Раньше эти операции попадали в таблицу кэш-обслуживания и молча
   игнорировались. Обслуживание TLB (`c8`) распознаётся отдельно, имена кэш-операций
   `c7` приведены к ARM ARM (`ICIALLU`, `ICIMVAU`, `ISB`, `BPIALL`, `DCCMVAC`,
   `DSB`, `DMB`, …), в лог CP15 добавлен PC инструкции.
4. **Модель прав доступа (AP/APX).** `check_ap()` применял к коротким дескрипторам
   *трёхбитную* (LPAE) кодировку. Для short-descriptor первого уровня AP[1:0] — это
   биты `[11:10]`, а бит 15 — `APX` («нет доступа пользователю»), не AP[2]:
   AP=`0b11`, APX=0 — это **RW для всех**. Теперь таблица соответствует ARM ARM
   B3-13 (тест `mmu_section_ap_and_apx_semantics`).
5. **Записи fault-ов теряли PC** (`note_fault()` копировал запись до подстановки
   `pc`), из-за чего в `info` все `fault[i]` печатались с `pc=0`.

### Новые инструменты отладчика

* `poke <addr> <value> [8|16|32]` — запись в физическую память через шину
  активного ядра (установить запись таблицы, пропатчить параметр стадии).
* `ZLB_RTRAP=<lo>-<hi>` — трассировка **чтений** физического диапазона
  (`[rtrap] регион +смещение rN = значение pc=… core=…`). Парная к `ZLB_WTRAP`.

### Где KBL останавливается сейчас

Прогон `runm` доходит до шага **313 876** и падает на записи по VA `0x4000`:

* `0x40036534` — функция подготовки блока загрузки: `memset(dst, 0, len)`
  вызывается ARM-овской `memset` (`0x40038F00`, `strdge r2,r3,[r12],#8`);
  `dst = ctx[0x220] = ctx[0xE4] = 0x4000`, `len = ctx[0xE8] = 0x4000` (16 КиБ),
  `val = 0`. Значение `0x4000` — **жёсткий литерал** (`mov.w r2,#0x4000` в
  `0x40020ED2`), а не результат вычисления.
* После memset туда же пишется блок с сигнатурами `0xBA97F5A1` (`+0xC`),
  `0xA008B0C3` (`+0x250`), размер `0x4BC` (`+0x8`), самоуказатель на контекст
  `ctx` (`+0x254`), `ctx[0xE8]` (`+0x14`) — это, судя по всему, boot-info для
  следующей стадии.
* VA `0x4000` в собственных таблицах KBL **не отображён**: TTBR0 залит
  fault-паттерном `0x1E0` и содержит ровно одну запись (индекс `0x1A0` =
  `0x1A010182`, PL310); TTBR1 содержит регионы самого KBL.

Установленные факты о KBL (проверено трассировкой):

| Факт | Как проверено |
|---|---|
| Ядро считает себя CPU0 (`mrc p15,0,r0,c0,c0,5` → `and #0xF`) | helper `0x40039F88`, ветка `cmp r0,#0; beq 0x400211C4` реально берётся на шаге 6448 |
| До MMU `VBAR = 0`, после — `VBAR = 0x16100`, затем `VBAR = 0x120` | лог CP15: `0x40020B82`, `0x40020CD0`, `0x40020CDE` |
| `0x16100` — значение из контекста: `ctx[0x22C] = ctx[0x9C]+0x100`, `ctx[0x9C] = 0x16000` | дизасм `0x40020E00..0x40020E1A`, дамп `0x400B2D50` |
| KBL **читает** низкую память: `+0x1C4` один раз (pc `0x4002028C`, до MMU) и слова `+0x000`/`+0x100` из копирующей ARM-функции `0x400376C0` | `ZLB_RTRAP=0-8000` |
| Таблицы заливаются fault-паттерном `0x1E0`, индекс записи = `VA>>20` **без маски** (запись для `0x40000000` лежит по `0x4010D000`) | `ZLB_WTRAP=40108000-4010c000` (3 писателя: заливка + одна запись) и дамп `0x4010C000..` |
| Все три сегмента `paddr == vaddr`, поэтому загрузчик не может «переехать» | `tools/self_phdrs.py` |

**Эксперимент.** Если принудительно положить в TTBR0 запись `L1[0] = 0x00000C02`
(секция VA `0` → PA `0`, RW), то memset **проходит**, KBL живёт на ~19 000
инструкций дольше (332 521), затем получает prefetch abort по VA `0x0CF08060`, его
обработчик уходит на VA `0x10000` (в нашей машине не отображено) и останавливается.
То есть низкая память KBL **нужна**, но берётся не из его таблиц.

### Чего не хватает: scratch-буфер CMeP (реконструкция)

Ключевой документ — сохранённая страница Vita Development Wiki «Boot Sequence»
(`boot_sequence.pdf` в корне workspace, страницы отрендерены в
`zeliboba/tools/pages/bootseq-*.png`, текст — `zeliboba/tools/boot_sequence.txt`).
Из неё:

> The Second Loader is primarily responsible for preparing the ARM processor. It
> initializes DRAM and decrypts `kernel_boot_loader.self` from eMMC SLB2 partition
> into DRAM. It also **writes the ARM exception vector and some boot context
> information to the 32kB scratch buffer (mirror mapped to `0x00000000` on ARM)**.
> … the Secure Kernel … tells Syscon to reset the ARM CPU at `0x00000000`
> (cmep scratch buffer). This triggers the ARM secure boot process.

Отсюда вся картина:

* **PA `0x00000000..0x7FFF` на ARM — это CMeP scratch-буфер (32 КиБ), он же
  shared SRAM, который CMeP видит по `0x1F000000`.** ARM стартует с PC
  `0x00000000`, где second loader оставил таблицу векторов: `ldr pc,[pc,#0x18]`
  → литерал по `0x20` = `0x40020000` — вход в KBL.
* В `0x0000..0x3FFF` лежит **boot context** (его KBL читает до включения MMU:
  `+0x1C4`, слова `0x000`/`0x100`), а `0x4000..0x7FFF` KBL очищает и использует
  под свой boot-info — отсюда ровно 16 КиБ по `0x4000`.
* Значит в модели не хватает двух вещей:
  1. **алиаса**: низкие 32 КиБ ARM должны быть тем же самым shared SRAM, что и
     `0x1F000000` у CMeP (сейчас у нас это отдельная RAM `arm_bootrom`), причём
     наша постановка `second_loader` (93 КиБ по `0x1F000000`) с этим scratch-ом
     конфликтует — second loader по документу грузится в **DRAM**;
  2. **самой подготовки ARM вторым загрузчиком**: таблица векторов в
     `0x0`/`0x120` (VBAR = `0x120`!) и блок boot-context в `0x0..0x3FFF`.

### План на следующий шаг

1. Смоделировать low-memory: алиас shared SRAM на PA `0x0` у ARM (32 КиБ) +
   подготовку вторым загрузчиком (векторы `0x0`/`0x120`, boot-context).
2. Восстановить формат boot-context по чтениям KBL (`ZLB_RTRAP`): поля
   `+0x1C4`, `+0x000`, `+0x100` и то, что KBL из них вычисляет (размер DRAM,
   адрес KBL, режим загрузки).
3. Довести **CMeP second loader** до конца (`0x40000`): сейчас он крутится на
   `erepeat`-опросе `0xE3102100` и ждёт прерывания SC — проводки прерываний MeP
   в модели нет. Именно он обязан подготовить ARM, поэтому это «честный» путь
   вместо ручной постановки.
4. После этого KBL должен достроить boot-info по `0x4000` и пойти дальше —
   к secure kernel.

## Раунд «CPU: IT/CMP, CTR, четыре ядра, SC-строб» (актуальное)

После двух правок декодера KBL **перестал падать**: он больше не включает MMU на
пути первичного ядра, проходит всю инициализацию, поднимает остальные ядра и
упирается в обмен с SC. Что именно было не так:

1. **`ITSTATE` инициализировался как `firstcond[3:1]:0:mask`** вместо
   `firstcond:mask` (ARM ARM A7.7.37). Терялся бит 0 условия, поэтому **любой**
   IT-блок с «нечётным» условием (`ne cc pl vc ls lt le`) исполнялся наоборот.
   KBL в `0x4003B6EC` делает `cmp r3,#1 / it ls (маска 1101)` и выбирает по
   результату функцию выравнивания адреса кэш-линии из таблицы `0x4005BA68`;
   с нашей моделью это было `it hi`, и указатель читался через мусорную базу
   (`0x0CF08060`, после правки CTR — `0x0D808060`). Тест
   `thumb_it_block_with_an_odd_first_condition` (и `arm_probe`).
2. **Thumb-16 `CMP (immediate)` считал флаги наоборот** — `imm8 - Rn` вместо
   `Rn - imm8`. Совпадало с железом только при равенстве (поэтому старые тесты на
   `cmp r0,#1` при `r0==1` проходили). KBL сравнивает длины и индексы с
   константами, так что C/V/N были инвертированы почти всегда.
3. **`CTR` (CP15 `c0,c0,1`)** был `0x0C000000`. KBL берёт из `CTR[20:16]` номер
   варианта «округлить адрес к линии кэша»: индекс 0 → `+0x1F/BIC 0x1F`,
   индекс 1 → `+0x3F/BIC 0x3F` (функции `0x4003B684`/`0x4003B68C`). У Cortex-A9
   линия 32 байта, то есть `DminLine = IminLine = 3` → `CTR = 0x8444C003`.
   Добавлены также настоящий `MPIDR` (`c0,c0,5`, Aff0 = номер ядра) и debug-лог
   для неописанных чтений с `opc1 != 0` (CCSIDR/CLIDR).
4. **Kermit — четыре ядра.** KBL синхронизирует **все четыре** в барьере
   `0x4003B384`: атомарный счётчик в `0x4005C008` (`strexh`), «первый пришедший»
   (`old == 4`) ждёт `<= 0`, остальные ждут `== 4`, победитель сбрасывает счётчик
   в 4. На одном ядре это вечный клинч — именно поэтому KBL «стоял». Машина
   теперь держит 4 `ArmCore` (у каждого свой CP15/MMU и свой `core_id_` для
   MPIDR), отладчик получил `core arm0..arm3` и список ядер кластера в `core`.
   Проверено трассировкой: счётчик проходит 4→3→2→1→0 и сбрасывается в 4, раунды
   барьера повторяются.
5. **CMeP `erepeat`.** Аппаратная петля не завершалась по ветвлению из блока, а
   это её единственный выход: `00049538 erepeat 0x4953e` + `lw $2,($3)` +
   `beqi $2,0x1,0x49544`. Теперь `repeat_step_end(address, branched)` снимает
   петлю, если ветвление уходит за пределы блока.
6. **SC-строб `0xE3102100`.** `ScBridgeDevice::read` возвращал 0 безусловно, а
   второй загрузчик пишет 1 и **ждёт чтения 1** (`beqi $2,0x1,0x49544`) — вечный
   `erepeat`. Теперь значение, записанное гостем, сохраняется. После правки CMeP
   уходит из петли, пишет 0 в `0xE3101100`, ждёт `beqz` и входит в цикл копирования
   полей дескриптора (`0x4955A..0x495E2`).

Где стоим сейчас: ARM (все 4 ядра) крутится в барьере и опрашивает SC-регистры
(`0xE3101040`, `0xE3101154`, `0xE3102040`) и GPIO-дверь CMeP (`0xE20A0008/0xE20A000C`);
CMeP крутится в обмене `0x4953C..0x49540` и `0xE3101100`. `boot` показывает
`SC commands: 0 served` — **модель Ernie ни разу не диспетчеризовала настоящую
SC-команду**, поэтому обе стороны живут в циклах повторных попыток.

### Следующий шаг

Смоделировать сам обмен SC-командами: дескриптор в окнах `0xE0B00000`/`0xE0BF0000`,
слово команды в `0xE31020A0`/`0xE31010A0` и диспетчер команд Ernie (таблица уже
снята с дампа и покрыта тестами) — тогда запрос CMeP «загрузи secure_kernel»
будет обслужен, а ARM получит ответы вместо бесконечного опроса. Дальше — загрузка
`secure_kernel`/`nsbl` и вход ядра.

## Раунд «многопроцессорность: блокировка по инструкциям и глобальный монитор» (актуальное)

Две правки нижнего уровня разблокировали сразу весь многопоточный этап KBL:

1. **Планировщик ядер.** Раньше `Vita::run_slice()` давала каждому ядру весь бюджет
   (32 инструкции) подряд. Для барьера KBL это смертельно: ядро, отпущенное
   барьером, успевало снова войти в него и снова уменьшить счётчик **раньше**, чем
   остальные увидят `counter == 4`, и все застревали (наблюдалось ровно это:
   `arm0` в ветке «ждать `<= 0`», `arm1..3` в ветке «ждать `== 4`», счётчик 3).
   Теперь четыре ядра идут **по одной инструкции по кругу**: на реальном железе
   ядра работают параллельно с видимостью памяти в цикле, так что инструкционная
   чересстрочность — верная модель.
2. **Глобальный монитор эксклюзивного доступа (SCU).** `LDREX/STREX` проверялись
   только по локальному состоянию ядра, поэтому два ядра могли *оба* успешно
   выполнить read-modify-write по одному адресу (потерянное обновление — счётчик
   не доходил до нуля). Теперь резервирование живёт в `Bus`
   (`mark_exclusive/take_exclusive/clear_exclusive`), и **любая** запись (в том
   числе от другого ядра или устройства) снимает пересекающиеся резервирования.
   Заодно реализованы T32 `LDREXH/STREXH` (были `undefined`) и `LDREXB/STREXB`
   без ошибочного требования `Rn == 0`.

Что изменилось в прогоне: KBL проходит барьер, **включает MMU на всех четырёх
ядрах** и строит карту низкой памяти: `L1[0] = 0x80200181` (таблица страниц), в
`L2[0x80200000]` — записи `0x4011845F`, `0x4011945F`, … то есть **VA
`0x0000..0x7FFF` → PA `0x40118000..` (32 КиБ scratch, перенесённый в DRAM)** —
ровно тот scratch-буфер CMeP, о котором говорит VitaDevWiki. Заполняет его
`0x4003AD40` (`r3 = 0x4000` — размер окна), а дескриптор страницы собирает
`0x4003A6F4`.

Текущий стоп: ядро 0 (boot core) получает **data abort на VA `0x40000`**
(`DFSR = 7`, `DFAR = 0x40000`): `L2[0x80200100] = 0` — эта страница не отображена.
Вектор abort-а по `0x130` тоже не исполняется (в `L2[0]` другая запись с XN), и
ядро уходит в цикл исключений. Код по `0x400321B6` — это настройка цепочки
дескрипторов (`ldr.w r2,[r12]; str…`), где `r12 = 0x40000`. Похоже, что это
**адрес без базы DRAM** (должно быть `0x40040000`, где секция `0x40000000` из
TTBR1 как раз отображена): то есть не хватает значения из **boot context**,
которое CMeP (второй загрузчик) обязан положить в scratch. Это следующая цель:
либо дать KBL настоящий boot context, либо довести CMeP до момента, когда он его
создаёт сам.

## Раунд «общий SC и меп-ветвление» (актуальное)

* **SC-регистры теперь одни на оба процессора.** У CMeP был *свой* регистровый
  файл `CMeP.SecureCtl`, который лишь **имитировал** подтверждения, а ARM и Ernie
  работали с окном `Ernie.SC` (`0xE3100000`). Команда, отправленная одной стороной,
  была невидима другой, отсюда `SC commands: 0 served` и вечные циклы повторных
  попыток с обеих сторон. Теперь `ScBridgeDevice` делегирует в это окно
  (`CmepBlock::attach_shared_sc`, вызывается из `Vita::wire_bridges`), то есть
  запись с любой стороны меняет одно состояние.

* **Найден следующий стоп CMeP, и он в поле-раскладке `beqi`.** Второй загрузчик
  крутится в `0x4953C..0x49540`:
  ```
  00049536  sw   $2,($3)          ; *(0xE3102100) = 1
  00049538  erepeat 0x4953e
  0004953E  lw   $2,($3)          ; $2 = 1
  00049540  beqi $2,0x1,0x49544   ; должен уйти на 0x49544, но не уходит
  ```
  Замеры: `$2 = 1`, `$3 = 0xE3102100`, чтение регистра возвращает 1, а пошаговый
  прогон даёт `0x49540 → 0x4953C → 0x4953E → 0x49540` — ветвление не срабатывает.
  Причина — **разные соглашения о полях у ядра и у дизассемблера**:
  `mep_core.cpp` для `Op::Beqi` сравнивает `R[rn]` (`mep::raw(word,4,4)` = биты
  `[7:4]`) с `mep::raw(word,8,4)` (= биты `[11:8]`), а `mep::field_value(Field::Rn)`
  (то, чем пользуется дизассемблер и таблица ISA) считает поля **от старшего бита
  полуторного слова** (`raw_impl`: `shift = 16 - local - length`). Для слова
  `0x0002E210` это даёт «регистр `$2` (биты `[11:8]`), непосредственное `0x1`
  (биты `[7:4]`)», что и печатает дизассемблер.

  Эксперимент: если поменять местами поля в `Beqi/Bnei/Blti/Bgei`, CMeP уходит из
  петли (проверено), **но ломается первый загрузчик** (`status=0x0`, ни одной
  операции Bigmac вместо `status=0x1`, 15 операций) — значит слепо менять нельзя:
  нужно свериться с ISA MeP (папка `MeP` в workspace) и привести *все* извлечения
  полей к одному соглашению, а не только ветвления. Правка откачена, состояние
  зафиксировано этим описанием.

## Где KBL находится сейчас (история)

После исправления Thumb-2-декодера KBL прошёл дальше и на сегодня проходит:

1. `PL310`/`GPIO`/`SC` (`0xE3101124`, `0xE3102100`, `0xE3102124`);
2. **подъём периферийного блока `0xE2040000`** — helper `0x4003BBCC` пишет
   `+0x04`, `+0x10`, `+0x20`, `+0x30`, `+0x40`, `+0x50`, `+0x60`, `+0x64`,
   ждёт бит `+0x28` (`0x4003BC98` — бит 8, `0x4003BCCC` — бит 9) и пишет `+0x70`;
   базы берутся из таблицы `0x4005C058` = `{0xE2030000 … 0xE2090000}`;
3. **рукопожатие `0xE5888000`** (`0x400217FA..0x40021872`): пишет 2 в `+0x00`/`+0x08`,
   ждёт `0x44` в `+0x20`, пишет 1, ждёт `0x11`, затем `0x302` в `+0x100`/`+0x108`,
   1 в `+0x180` и маркер `0xDEADCAFE` в `0x80000000` (DRAM) — **маркер проверен**;
4. строит таблицы MMU (`0x40020E48`, обёртка `0x40020A98` → `0x4003A9D4`),
   программирует `TTBR0/TTBR1/TTBCR/DACR` (`0x40020C0E`, 295 556 шагов) и
   **включает MMU** (`0x40020CA2`, 302 622 шага);
5. после включения MMU сразу получает prefetch abort (первая же выборка
   инструкции по VA `0x40020CA4` не отображена), затем fault на векторе
   `0x0000000C` и двойной fault → останов.

   Разбор таблиц (`tools/dump_l1.py`, дампы через `mem` с активным ядром ARM):

   | Таблица | Что в ней |
   |---|---|
   | TTBR0 `0x40108000` (1024 записи) | **все** `0x000001E0` — fault-дескрипторы |
   | TTBR1 `0x4010C000` (2048 записей) | ровно одна валидная: индекс 0 = `0x80200181` — указатель на L2-таблицу |
   | L2 `0x80200000` | записи 0..3 = `0x4011844E`… (small page, VA `0x40000000..0x40003FFF` → PA `0x40118000..0x4011BFFF`), остальное — 0 (fault) |

   То есть карта покрывает только VA `0x40000000..0x40003FFF`, а **собственный код
   KBL по VA `0x40020000` не отображён** — отсюда падение сразу после `SCTLR.M = 1`.

   При этом блок построения карты (`0x40020E48..0x400211xx`) **не содержит циклов**
   (проверены все ветвления назад в диапазоне `0x40020E00..0x40021300`): он делает
   три вызова обёртки `0x40020A98` (`0x40021072`, `0x4002108E`, `0x400210AC`) и
   вызовы писателя L1 `0x4003A824` (`0x40021102`) и заливки L2 `0x4003AB04`
   (`0x4002110A`); все пять достигаются (294 047 / 294 060 шагов).

## Что осталось

1. **Карта памяти: KBL строит её не с нуля.** Наблюдения:

   * блок `0x40020E48..0x400211xx` **не содержит циклов** и делает всего пять
     вызовов: три раза обёртку `0x40020A98` (секционные отображения: 16 МиБ по
     `0x50000000`, 1 МиБ, 16 МиБ) и по одному разу писателя L1 `0x4003A824`
     и заливку L2 `0x4003AB04`;
   * писатель L1 получает `r0 = 0x4010C000` (TTBR1), `r2 = 0` (индекс), `r3 =
     0x80200000` (L2), а `r11 = 0x40000000` — то есть индекс считается
     **относительно границы split**, а не как `VA >> 20`;
   * итог: TTBR0 — целиком fault, TTBR1 — только индекс 0 (L2 на `0x80200000`),
     L2 — 4 записи (VA `0x40000000..0x40003FFF` → PA `0x40118000..`, а по этому PA
     в нашем прогоне **нули**);
   * `info` показывает `TTBCR=0x2 (N=2)`, а первый fault — это fetch по
     VA `0x40039FC8` внутри самого хелпера включения MMU (`0x40039F94`), где наша
     `ArmMmu` берёт `L1[(VA>>20)&0xFFF] = 0x4010D000` (немаскированный индекс,
     `arm_mmu.cpp:227`).

   При этом KBL **отображает много регионов**: сразу после заливки L2 идёт длинная
   развёрнутая (без циклов) последовательность вызовов
   (`0x4002110E..0x40021xxx`): обёртки `0x40020AE4`, `0x40020A98` и хелперы
   `0x4003AD40`, `0x4003A9D4`, читающие пары полей конфигурации
   (`config[0xb0]/[0xb4]`, `[0xe0]/[0xe4]`, `[0x40]/[0x44]`, `[0x60]/[0x64]`,
   `[0x98]/[0x9c]`, `[0xcc]`, `config[0x78]` как смещение). Сама конфигурация в
   `.bss` заполнена правильно: `config[0x40] = 0x40108000` (TTBR0),
   `config[0x60] = 0x4010C000` (TTBR1), `config[0x0C] = 0x40000000` (split),
   сигнатура `0xCBAC03AA` в `0x400B2EC4`, указатель на конфиг `0x400B2EC8`.

   Значит карта строится самим KBL, а в наших таблицах она не появляется —
   следующий шаг: инструментировать аргументы хелперов (`r0` = база таблицы,
   `arg3` = VA, `arg4` = размер) на **каждом** вызове после исправления `AND.W`
   (прежняя выборка аргументов была сделана ещё в зацикленном, «грязном» прогоне
   и потому недостоверна) и найти инструкцию, из-за которой запись уходит не в
   `0x40108000`/`0x4010C000`.

   Важная деталь: до этой правки KBL вообще не доходил до `0x40020C0E` — его
   зацикливал `AND.W` (см. грабли ниже), поэтому раньше наблюдавшийся «MMU on с
   пустыми таблицами» был не отдельной проблемой, а следствием.
2. **SDIF/eMMC.** Отдельного ожидания `0xE2040028` больше нет: это глина
   питания/тактов, смоделированная как `Kermit.PeriphPower{N}` (биты 8 и 9 = «есть
   питание и такт»). Загрузка ядра идёт через SC/Ernie, а `Kermit.Sdif0`
   (`0xE0B00000`, как в таблице `sdif.elf` `0x81009FA8`) пока не задействован.
3. **Окно `0xE5888000`** — смоделировано (`Kermit.BootHandshake`): модель отвечает
   `0x44` после команды 2 и `0x11` после команды 1, потому что ни один модуль
   прошивки это окно не описывает. Это документированное допущение, а не реверс.
4. **MMU.** Отдельной правки не требуется: до `0x40020C0E` дело не доходит по
   причине из п. 1.
5. **CMeP.** Вторая стадия (`0x40000`) стоит на бесконечном `erepeat`-опросе
   `0xE3102100` и ждёт прерывания от SC — проводки прерываний MeP в модели нет.

Обновление (раунд 12): пункт 5 закрыт — вторая стадия больше не залипает ни на
`erepeat`, ни на таймере, и дошла до реального обмена с syscon. Ниже — что именно
было найденo.

## Раунд 12. Вторая стадия CMeP: выход из hardware loop, таймер и линия SPI к Ernie

### 12.1 Аппаратный цикл MeP: выход по взятому переходу

`erepeat` повторяет блок `[RPB, RPE]` и **ещё один слот после RPE**; единственный
выход — взятый переход в этом слоте. Определять его по PC нельзя: в хендшейке второй
стадии (`0x49540`) стоит `beqi $2,0x1,0x49544`, цель которого — *следующая*
инструкция, то есть PC выглядит как обычное падение. Исправление: все ветви/вызовы
идут через `MePCore::branch_to()` (ставит `branch_taken_`), а `repeat_step_end()`
получает этот флаг и выходит из цикла по любому взятому переходу.

Результат: `0x4953C` больше не зацикливается, первая стадия по-прежнему сообщает
`status=0x1 keyring writes=1 bigmac ops=15`.

### 12.2 Таймер задержек: бит 0 — это «готово», а не «занято»

Модель `ControlBus` держала в бите 0 статуса флаг «занято», и вторая стадия вставала
в вечный цикл `0x45516: ldcb $3,0x404 / and3 $3,$3,1 / bnez $3,0x45520` — она ждёт
установки бита. Оба загрузчика трактуют бит 0 одинаково:

* первая стадия `0x5E686`: `and $0,$2` (маска 1) и `beqz $0,0x5E686` — цикл, пока бит 0 **не** установлен;
* вторая стадия `0x45516`: `bnez $3,0x45520` — выход, когда бит 0 установлен.

Модель переписана по этой семантике: reload — 16 бит big-endian в `0x400`/`0x401`,
`0x402` бит 0 = пуск, `0x404` бит 0 = защёлка «счёт дошёл до нуля» (сбрасывается
записью нуля). Теперь `delay` второй стадии завершается на 152 703 инструкции, а не
залипает навсегда; первая стадия не изменилась (её цикл тоже завершается, но по
другому биту).

### 12.3 Главное: `0xE0A00000` — это SPI0 к syscon

Вторая стадия не пользуется окном SC `0xE0B00000`, которое уже было смоделировано,
а работает с `0xE0A00000`. По VitaDevWiki это `SceSpi0Reg` — SPI-мастер, к которому
подключён syscon. Тот же блок и той же последовательностью регистров использует
ARM-модуль `syscon.elf` (`0x8100003C`), то есть это общий путь SoC↔Ernie.

В модели появился `kermit::Spi` (`src/hw/soc/spi.cpp`) с картой из вики, он
установлен как `Kermit.Spi0/1/2` и отзеркален в шину CMeP. Пакетный уровень
(`src/hw/syscon/ernie_spi.cpp`) декодирует запрос, отдаёт команду в тот же
`ErnieBlock::dispatch_command`, что и окно SC, и собирает ответ.

### 12.4 Формат пакета

Выведен из двух независимых источников — кода самой второй стадии (`0x439CC` строит
запрос, `0x43C92` проверяет ответ) и лога загрузки на VitaDevWiki:

```
запрос:  [cmd_lo][cmd_hi][len = payload+1][payload][checksum]
ответ:   [cmd_lo][cmd_hi][len = payload+2][flags][payload][checksum][pad]
checksum = ~(сумма всех байт перед ним)
```

Проверка сходится на всех примерах: запрос CMD 0x0001 — `01 00 01 FD` (именно эти
четыре байта вторая стадия кладёт в FIFO на `0x4376C`), ответ на CMD 0x0005 —
`04 00 06 00 00 60 40 00 55`, ответ на 0x1082 — `DD` в конце и т. д. Первый заход
дал ошибку в собственной реализации (`checksum_over` суммировала на один байт
меньше), из-за чего вторая стадия уходила в `0x43F52` (ветка «плохая контрольная
сумма»); после исправления проверка проходит.

### 12.5 Что теперь делает вторая стадия

Обмен по SPI пошёл: `SC commands` в отчёте выросло с 0 до тысяч. Последовательность
команд, которую она отправляет: `0x0001` → `0x0002` → `0x0080` → и дальше
бесконечный опрос `0x0000`.

Ограничение, которое удалось измерить точно: API `0x44274` принимает ответ только с
длиной кадра `len-3 <= 3`, то есть payload не больше 4 байт (`0x442AE..0x442C6`);
поэтому ответ на `0x0001` — ровно 4 байта `0D 06 00 01`, как в логе вики. С шестью
байтами (как отдавал функциональный диспетчер) вторая стадия возвращала
`0x80250100` и повторяла команду.

Опрос `0x0000` пока не завершается ни с пустым подтверждением, ни с двумя байтами
статуса, ни с кодом ответа `0x0024` вместо `0x0004`. Похоже, что он ждёт не ответа
на запрос, а **внезапного кадра от Ernie** (в логе вики syscon сам присылает кадры
`0x0024` между запросами); в модели линия пока строго «запрос-ответ». Следующий шаг:
найти потребителя ответа `0x0000` (вызовы API `0x44246`/`0x44274`) и его условие
приёмки, а затем решить, нужна ли очередь внезапных кадров от Ernie.

### 12.6 Мелочи

* `emmc_rebuild --verify` теперь работает и как флаг (проверяет образ, собранный
  `--out`), поэтому `verify.ps1` проходит целиком.
* Самотесты: 205 тестов, 15 падений — все прежние (дизассемблер ARM, VFP, Thumb,
  Bigmac RNG, карта памяти машины); новых нет, `mep_control_bus_delay_timer`
  переписан под корректную семантику и теперь проходит.

## Раунд 13. Обмен с syscon заработал: вторая стадия проходит конфигурацию

### 13.1 Опрос `0x0000` — это фильтр по маске кода ответа

Помощник опроса второй стадии `0x449F0` отправляет CMD `0x0000` и ждёт, пока
**код ответа** удовлетворяет маске, которую выбрал вызывающий:

| Вызов | Маска | Что ждёт |
|---|---|---|
| `0x44986`, `0x44ACE` | `$1 = 32` (`0x20`) | ответ класса «подтверждение» |
| `0x44A80` | `$1 = 4` (`0x04`) | ответ, несущий данные |

Проверка — `lbu $3,52($sp)` (первый байт принятого кадра) `and $3,$7`, и цикл
повторяется, пока результат нулевой. Отсюда: Ernie обязан отвечать на один и тот же
CMD `0x0000` то `0x0024` (бит 5 — «данных нет, это ack»), то `0x0004` (бит 2 —
«вот данные»). Раньше модель всегда отвечала `0x0004`, и опрос с маской `0x20`
крутился вечно (в логе было 49 повторов `0x0000`).

После правки последовательность пошла как в логе вики: `0x0001` → `0x0002` →
`0x0080` → `0x0000` → `0x0080` → `0x0010`.

### 13.2 Короткие ответы: у каждого пути свой предел длины

* `0x44274` (малый ответ) отвергает кадр, если `len - 3 > 3`, то есть payload
  не больше 4 байт. Ответ на `0x0010` (wakeup factor) — ровно 2 байта `14 FF`, на
  `0x0001` — 4 байта версии. С шестью байтами стадия падала в `0x80250100` и
  повторяла команду.
* `0x44634` (`0x0002`, timestamp) копирует ровно 12 байт — модель отдаёт
  ASCII-строку как в логе вики.

### 13.3 Найденные баги и допущения, без которых стадия не шла

| Что | Где | Суть |
|---|---|---|
| Общая шина SC не работала | `CmepBlock::attach_shared_sc` | `install()` передаёт устройства шине и **обнуляет указатели в Impl**; функция обращалась к `impl_->sc_bridge` (null) и молча ничего не делала. Теперь устройство ищется по имени. Из-за этого CMeP видел собственную копию SC-регистров |
| Неизвестные SC-регистры читались нулём | `ScWindowDevice` | CMeP использует `0xE3101120`/`0xE3102120` как «записать 1 и опросить её же» (`0x487E8`: `sw $9,($3)` / `erepeat` / `lw $9,($3)` / `bnez`). Теперь неизвестный регистр читается как storage |
| `0xE3101000` не отвечал | SC-окно | Проверка `0x40DB6` требует ровно `0x0001000F`, иначе `0x800F0010` |
| `0xE0010004` не отвечал | новый `CMeP.SysCtl` | Нужно `(значение & 5) == 5` и `(значение & 8) == 0` |
| Страп был «A» | `CmepBlock::reset` | Проверка `0x40DB6` требует `([0xE0062020] & 7) == 0`. Первый загрузчик использует бит 0 только для выбора символа баннера (`'A'`/`'!'`, `0x5C116`) и принимает оба (`0x5C510: bgei $0,0x0`), поэтому правильное значение для сквозной загрузки — «retail», 0 |
| Питание периферии не доходило до CMeP | `kermit_attach_syscon_spi` | Вторая стадия сама поднимает периферию: `0x4882A` пишет `0x101` в `+0x64` окна `0xE2030000 + idx*0x10000` и ждёт чтения нуля. Окна существовали только на шине ARM — теперь они отзеркалены в шину CMeP, а `+0x64` читается нулём (командный регистр) |

После этих правок вторая стадия проходит всю последовательность SC, проверку
конфигурации и доходит до стадии `E`.

### 13.4 Где она теперь стоит: `0xE6008000`

Стадия `E` (`0x40590`) вызывает `0x483DA`, и та уходит в `0x482A2` — опрос
**`0xE6008020`** (по 4 бита на слот) с задержкой в цикле. Этот блок в рабочей папке
не описан, но карта регистров из дизассемблера читается:

| Адрес | Семантика (из кода) |
|---|---|
| `0xE6008000 + i*8` | запись 3-битного поля (команда слота), `0x482CE` |
| `0xE6008020` | чтение: 4-битный статус слота `i`, `0x482E6..0x482F0` |
| `0xE6008100 + i*8` | запись 16-битного значения, `0x48310` |
| `0xE6008120 + i*8` | записать байт, прочитать ответ в битах 8..15, `0x48370` |
| `0xE6008180` | стробировать 1 и ждать чтения 1, `0x48422` |

Идентификация устройства в `0x4838A`: записать `5` в слот 0 → ответ должен иметь
`(ответ & 7) == 1`; записать `8` → `(ответ & 3) == 0` и `((ответ >> 2) & 0xf)` равно
4 или 5 (отсюда возврат 0/1, иначе 2). Дальше идёт инициализация слотов
(`0x48412`/`0x4841A`: записать 2 в два слота и ждать статус 2).

### 13.5 Модель-заглушка этого блока и что она дала

Блок не отождествлён, поэтому в модель добавлен `CMeP.CmdBlock`
(`CmdBlockDevice`) — карта регистров взята из кода, а **ответы подобраны под
проверки загрузчика**:

* статус слота = старший установленный бит записанной команды: `5 → 4`, `2 → 2`,
  `1 → 1` — ровно то, что ждут `0x48412`/`0x4841A`/`0x484B0`;
* байтовый порт `0xE6008120 + i*8` держит записанный байт в младших битах (это
  нужно проверке записи в `0x4827E`) и отдаёт ответ устройства в битах 8..15
  (`0x48370`); ответ `1` на команду `5` и `0x10` на `8` проходит проверки
  `0x483B0..0x483D0`;
* `0xE6008180` — строб: запись 1 читается как 1.

Это позволило стадии пройти идентификацию и инициализацию и уйти дальше:
PC второй стадии сместился с `0x482E6` на `0x474DA`. Заглушка помечена в коде как
допущение и подлежит замене, когда блок будет отождествлён.

### 13.6 Новое место остановки: `0x474DA`

```

000474D2  51 E7 16 00  beq $7,$5,0x474fe
000474D6  04 67        add $7,1
000474D8  71 BF        bsr 0x47448
000474DA  6E C3 24 00  lw $3,36($6)   ; [$6+0x24]
000474DE  21 C2 02 00  movh $2,0x2

То есть теперь загрузчик ждёт **бит 1 слова `+0x24` структуры по `$6`** — похоже на

## Раунд 14. Вторая стадия читает eMMC: блок `0xE0B00000` — это SDHCI

### 14.1 Главное: `0xE0B00000` — хост SD/eMMC, а не «окно SC»

Кадр `0x474DA` (ожидание бита 1 слова `+0x24`) привёл к функции `0x4747C`, а её
вызывающий берёт базу регистров так:

```
0004752C  21 C7 B0 E0   movh $7,0xe0b0      ; $7 = 0xE0B00000
00047532  30 07         mov $7,$3
00047534  21 C3 BF E0   movh $3,0xe0bf
00047538  86 67         sll $7,0x10
0004753A  37 97         add3 $7,$7,$3        ; 0xE0BF0000 + (канал << 16)
```

Все смещения, которые вторая стадия программирует, — стандартные SDHCI:

| Смещение | Что пишет/читает вторая стадия | SDHCI |
|---|---|---|
| `+0x08` | аргумент команды | Argument |
| `+0x0C`/`+0x0E` | transfer mode / команда (`0x0102` = CMD1) | Transfer Mode / Command |
| `+0x24` | ждёт биты 0 и 1 (`0x477E8`), читает биты 16/17 | Present State (Cmd Inhibit, Card Inserted) |
| `+0x28` | байт, бит 2 | Host Control 1 |
| `+0x29` | `or 0x0B` | Power Control |
| `+0x2C` | `(делитель << 8) \| 1`, затем ждёт бит 1 | Clock Control (частота + stable) |
| `+0x2F` | `1`, ждёт нуля | Software Reset (самосбрасываемый) |
| `+0x30`/`+0x32` | опрос и сброс бит 0/2, `0x0F` | Normal/Error Int Status |
| `+0x34..0x3A` | `507` и `895` | маски прерываний |

То есть вторая стадия **сама читает eMMC через тот же контроллер**, что и ARM-драйвер
`sdif.elf` (0xE0B00000). Прежняя трактовка этого окна как «SC transfer с 28-байтным
дескриптором» относится к другому пути (`0xE0B0FF00` — окно внутри 64 КиБ блока) и в
текущем прогоне не используется (`sc transfers=0`).

### 14.2 Что пришлось починить, чтобы это заработало

| Что | Где | Суть |
|---|---|---|
| SDIF не был виден CMeP | `kermit_attach_syscon_spi` | `Kermit.Sdif0` (64 КиБ) отзеркален в шину CMeP; `Bus::find_device` выбирает наименьшее окно, поэтому регистры SDHCI достаются ему, а большое окно `CMeP.ScXfer` (0x110000) остаётся для дескриптора |
| Software Reset не работал | `Sdif::write_word` | `case kSoftwareReset` (0x2F) был **недостижим**: `RegisterBlock` всегда передаёт смещение, выровненное по слову (0x2C). Вторая стадия писала 1 и ждала нуля (`0x47496..0x474A6`) — вечный цикл |
| Clock Stable не поднимался | `Sdif::read_word` | бит 1 Clock Control — read-only «внутренний такт стабилен»; вторая стадия включает такт и ждёт его (`0x47626..0x47632`) |
| **Ни одно устройство Kermit не тикало** | `KermitBlock::tick` | `periph_ticks(256) = 256*1e6/333e6 = 0`; остаток отбрасывался каждую порцию, поэтому ни таймеры, ни DMA, ни счётчик занятости SDIF не двигались. Добавлен накопитель `cycle_accumulator` |
| CMD0/CMD1 декодировались как команда 0 | `Sdif::write` | триггером было «полуслово команды не ноль», а CMD0 = индекс 0 без флагов = 0. Теперь команда запускается по *факту записи* регистра 0x0E (а более широкая запись — только если полуслово изменилось) |
| Ответ команды читался нулём | `Sdif::execute_command`, `write_data_port` | регистры, делящие слово с соседом, хранятся под смещением **слова**: команда — в старшей половине слова 0x0C, счётчик блоков — в старшей половине слова 0x04. `peek(kCommand)`/`peek(kBlockCount)` всегда возвращали 0 |
| Занятость линии не снималась | `Sdif::execute_command` | модель выполняет команду синхронно, поэтому окно `busy_left_ = 64` тиков держало биты Cmd Inhibit; теперь они снимаются сразу, а DAT-линия «занята», пока не вычитан буфер |

### 14.3 Состояние на конец раунда

* CMeP шлёт настоящие SD-команды: в трассе видны `Argument`, `Transfer Mode`,
  `Command = 0x0102` (CMD1), опрос `Normal Int Status`, чтение `Response 0`.
  После правки декодирования ответ CMD1 читается правильно — `0x40FF8000`.
* PC второй стадии прошёл путь `0x474DA → 0x477E8 → 0x47632 → 0x47912 → 0x47A50`;
  буквы прогресса доросли до `ABCDEH`.
* Финальная стадия по-прежнему отчитывается `0x500` (отказ) с кодом `0x80320002`
  (таймаут): помощник `0x46F2E` до 100 раз вызывает предикат `0x47772` и ждёт, пока
  сохранённое им значение (`[sp+0x14]`, это ответ команды) станет **отрицательным**
  (`0x46F70: bgei $3,0x0,<повтор>`). При ответе `0x40FF8000` (и при `0xC0FF8000`)
  условие не выполняется — значит, загрузчик ждёт от CMD1 не OCR, а что-то ещё
  (возможно, что команда должна вернуть ошибку/«шину занята» именно в этом поле).
  Следующий шаг: разобрать предикат `0x47772` и то, как он заполняет `[desc+0x10]`,
  и определить, какое состояние eMMC он считает готовым.

## Раунд 15. Идентификация eMMC проходит целиком: CMD0…CMD8

### 15.1 Найденное препятствие: `0x46F70`

Помощник `0x46F2E` до 100 раз вызывает предикат `0x47772` (выдать SD-команду и
дождаться её), и выходит из цикла **только когда сохранённый ответ станет
отрицательным**:

```
00046F6E  lw $3,0x14($sp)      ; ответ команды (desc+0x10)
00046F70  bgei $3,0x0,0x46f7a  ; >= 0 → задержка и повтор
00046F76  sw $3,($5)           ; иначе — запомнить и вернуться с успехом
```

Для `SEND_OP_COND` (CMD1) это бит 31 OCR, то есть «карта ещё инициализируется».
Модель отвечала `0x40FF8000` (готово) и получала таймаут `0x80320002`. Теперь карта
ведёт себя как настоящая: **первый** CMD1 отдаёт `0xC0FF8000` (busy), последующие —
`0x40FF8000`. Счётчик сбрасывается на `GO_IDLE_STATE`.

### 15.2 Второе препятствие: ответ CMD3 считался ошибкой

После этого загрузчик прошёл CMD1 → CMD2 → CMD3 → CMD9 → CMD7 и упал на CMD3 с кодом
`0x80320110`. Расшифровка кода: помощник `0x47DE2` маскирует ответ константой
`0xFDFFE008` и возвращает `0x80320100 + <номер младшего установленного бита>`; `0x110`
= бит 16. Бит 16 у нас был в ответе CMD3, потому что модель отдавала RCA
(`0x00010000`, SD-стиль R6).

Загрузчик же работает в **MMC-режиме**: он сам кладёт RCA в аргумент
(`Argument >> 9 = 128` в трассе, то есть `0x00010000`) и ждёт R1-статус. Теперь CMD3
различает режимы: ненулевой аргумент → RCA берётся из него, ответ `0x00000900`
(READY_FOR_DATA | CURRENT_STATE=transfer); нулевой → прежний SD-ответ R6.

### 15.3 Третье препятствие: фаза данных возникала слишком рано

Модель выставляла `Buffer Read Ready` одновременно с `Command Complete`. Драйвер
успевал погасить Command Complete и затем вечно ждал события данных, которое уже
было «съедено» (его движок команд крутится в `0x47914`, опрашивая `0x30`/`0x32`).
Теперь фаза данных поднимается через несколько PERIPHCLK тиков
(`data_ready_in_`, обрабатывается в `Sdif::tick`), как на реальном контроллере.

### 15.4 Что теперь делает вторая стадия

Инструментировав `Sdif::execute_command`, удалось снять последовательность команд
(она же — подтверждение, что всё декодируется верно):

```
cmd index=0  raw=0x0000  data=0 read=0  -> status=0x1     GO_IDLE_STATE
cmd index=1  raw=0x0102  data=0 read=0  -> status=0x1     SEND_OP_COND
cmd index=2  raw=0x0209  data=0 read=0  -> status=0x1     ALL_SEND_CID
cmd index=3  raw=0x031A  data=0 read=0  -> status=0x1     SEND/SET_RELATIVE_ADDR
cmd index=9  raw=0x0909  data=0 read=0  -> status=0x1     SEND_CSD
cmd index=7  raw=0x071A  data=0 read=0  -> status=0x1     SELECT_CARD
cmd index=8  raw=0x083A  data=1 read=1  -> status=0x21    SEND_EXT_CSD (512 байт)
```

То есть **идентификация карты проходит полностью**, и загрузчик дошёл до чтения
Extended CSD. Дальше он застревает в ожидании фазы данных CMD8: он опрашивает
`0x30`/`0x32` в `0x47914`, а буферный порт `0x20` (через который модель отдаёт 512
байт) не читает (`trace find 0xE0B00020` — обращений нет). Возможные причины: ему
нужен либо DMA-путь (в трассе `tm=0x10`, то есть DMA не включён), либо другое
состояние в `0x30` (например «Transfer Complete» без вычитывания буфера).
Следующий шаг: разобрать переходы `0x47A54..0x47AB2` (там ветвление по битам
команды и запись в `0x30`/`0x32`) и понять, какое событие открывает чтение данных.

## Раунд 16. Фаза данных CMD8: порт FIFO и уровень готовности

### 16.1 Трассировка вместо догадок

Полезный инструмент на этот раз — трапы по регистрам: `ZLB_RTRAP`/`ZLB_WTRAP`
на диапазон `0xE0B00000-0xE0B00040` печатают **каждое** обращение к SDHCI с адресом,
значением, PC и ядром. Так нашлось главное:

* загрузчик читает **буферный порт** `0x20` (цикл `0x47B32..0x47B88`, PC чтения
  `0x47B60` — это `lw $0,32($10)`), а не DMA;
* `129` чтение первого прохода (все нули) → модель отдавала данные, но не те.

### 16.2 Три исправления

| Что | Где | Суть |
|---|---|---|
| Порт FIFO всегда отдавал **один** байт | `Sdif::read` | загрузчик читает слово (`lw`), поэтому на каждый байт FIFO он продвигал **четыре** байта приёмника и уходил за конец передачи. Теперь 4-байтовое чтение выталкивает 4 байта |
| `Buffer Read Ready` был одноразовым | `Sdif::read_word(0x30)` | на реальном контроллере это **уровневый** флаг: он снова поднимается, пока в FIFO есть данные. Загрузчик вычитывает Extended CSD кусками и после каждого ждёт флаг заново (`0x47B94`), поэтому одноразовая модель вставала после первого куска |
| Фаза данных начиналась вместе с командой | `Sdif::execute_command`, `tick` | теперь `Buffer Read/Write Ready` поднимается через несколько PERIPHCLK тиков после `Command Complete` (реальный порядок событий) |

Дополнительно: `SEND_EXT_CSD` отдаёт данные «открытым» потоком (счётчик блоков
загрузчик программирует нулём — в SDHCI это «передавать, пока хост не остановит»),
поэтому в модели за первым блоком следует ещё несколько.

### 16.3 Что теперь видно

После правок загрузчик **вычитывает все 512 байт Extended CSD** (128 чтений по 4
байта) и получает настоящие значения полей (в трапе видны `0x07`, `0x15`, `0x04`,
`0x19`, `0x01` — это данные из `emmc_card.cpp`), затем запрашивает второй блок.
Останавливается он в ожидании `Present State` бит 11 («буфер готов») после второго
куска, а в трассе видно необычное: обращения к **абсолютному адресу `0x32`**
(`R2 0x32 = 0xFFFF`, `W2 0x32 = 0x200`) — то есть загрузчик где-то работает с нулевым
указателем базы. Это следующий след: разобрать, почему после второго куска данных
его указатель на блок регистров обнуляется.

## Раунд 17. Вторая стадия читает блоки с eMMC: CMD8 → CMD17

### 17.1 Ложный след: «нулевой указатель базы»

В трассе прошлого раунда виделись обращения к абсолютному адресу `0x32` — решили, что
у загрузчика обнуляется указатель на блок регистров. На деле это артефакт **трапов**:
для `DeviceMirror` печатается смещение внутри устройства, и «unmapped» относится к
зеркалу, а не к адресу. Проверка через `mem` подтвердила: это обычные обращения к
`0xE0B00030`/`0x32`.

### 17.2 Что оказалось правдой: объект устройства обнулялся **данными передачи**

Трап на сам объект (`0x56134-0x5615F`) показал две вещи:

* в начале прогона машина выкладывает туда образ (`0x5E61E`);
* позже PIO-цикл загрузчика (`0x47B80`) пишет туда **данные из FIFO** — то есть
  приёмный буфер `0x55F0C` (512 байт) заканчивается за 40 байт до объекта
  `0x56134`, и второй кусок данных (который загрузчик запрашивает) затирает объект.

Отсюда важный вывод: **передача обязана быть ровно одним блоком 512 байт**. Попытка
отдавать «открытый поток» (счётчик блоков у загрузчика нулевой) ломает его же
структуры и увела в тупик; эксперимент задокументирован и откачен.

### 17.3 Что ещё исправлено в модели

* **Перенос `Transfer Complete`**: раньше он поднимался в тот же момент, что и
  последний байт, а драйвер гасит биты 1/4/5 одной записью `0x32` в `0x30` — то есть
  стирал признак конца передачи раньше, чем успевал его увидеть. Теперь `TC`
  поднимается через несколько PERIPHCLK тиков после последнего байта.
* **Отложенный `Buffer Read Ready` не должен врать**: если драйвер вычитал весь
  буфер до срабатывания таймера, событие отменяется (`data_ready_in_ = 0`), а сам
  `tick()` проверяет, что данные ещё есть. До этой правки флаг поднимался «в пустоту»
  и драйвер уходил в чтение несуществующих данных.

### 17.4 Куда дошла вторая стадия

После этих правок последовательность пошла дальше:

```
… CMD8 (SEND_EXT_CSD) → прочитаны все 512 байт
… CMD17 (READ_SINGLE_BLOCK), lba=1, count=1 — transfers=1
```

То есть загрузчик прочитал Extended CSD и **начал читать блоки с карты** (LBA 1 —
первые данные после загрузочной области). Сейчас он стоит в ожидании данных CMD17:
модель держит данные (`Present State` = `0x00030806`, бит 11; `Normal Int Status` =
`0x20`), но путь чтения драйвера требует, чтобы `[desc+4] & 0x700` было `0x100`
(цикл `0x47B12`) или `0x200` (цикл `0x47BAC`), а в дескрипторе лежит `0x514` — то есть
биты 8..10 выбирают вариант передачи, и этот вариант не совпадает ни с одним из двух
циклов. Следующий шаг: разобрать, кто и как формирует `[desc+4]` для чтения
(`0x477B6..0x477D8` только маскирует и сохраняет), и какие биты соответствуют
одиночному чтению через порт.

## Раунд 18. Вторая стадия читает блоки по ADMA2 и доходит до своего выхода

### 18.1 Что на самом деле делал драйвер: DMA, а не PIO

Ключ к разгадке дала трассировка регистров SDIF (`ZLB_SDIF_TRACE=1`, см. 18.6).
Команда, на которой всё стояло, выглядит так:

```
[sdif] CMD idx=17 arg=0x00000200 tm=0x0013 block=0x00010200 size=512 count=1
       data=1 read=1 multi=0 dma=1 adma=0x40000400 cmep_pc=000481E2
[sdif] adma table=0x40000400 moved=512/512 ok=1
```

`tm=0x0013` — это биты 0 (DMA enable), 1 (block count enable) и 4 (read) регистра
Transfer Mode. То есть данные обязан переложить **хост**, а не драйвер: циклы
чтения порта 0x20 в машине состояний (`0x47B12` и `0x47BAC`) выполняются только
когда `(desc+4) & 0x700` равно `0x100` (чтение) или `0x200` (запись). У
загрузчика там `0x514`, потому что бит 10 (`0x400`) — это флаг DMA: путь 0x48158
включает его, а сам код передачи пропускается.

Разбор драйвера (второй загрузчик):

* `0x48094` собирает таблицу ADMA2: записи по 8 байт `{u16 attribute, u16 length,
  u32 address}`; загрузчик пишет `attribute = 0x21` (VALID | ACT=10b TRAN), а
  последней записи добавляет `0x02` (END) — то есть это ровно формат ADMA2 из SD
  Host Controller Simplified Specification 2.0, раздел 2.2.13;
* адрес таблицы берётся из глобала `[gp-0x7FFC]`, который заполняет `0x41002`
  (`movh $1,0x4000; or3 $1,$1,0x400` → **0x40000400**, длина 0x100 = 32 записи);
* `0x48158` кладёт этот адрес в ADMA_SYSTEM_ADDRESS (0x58), пишет block size /
  block count из дескриптора (`[desc+0x24]`, `[desc+0x28]`) и включает бит 0
  transfer mode;
* `0x4708C` (чтение блоков) строит дескриптор: `+0x00` размер 52, `+0x04` флаги
  (`0x114` = чтение без DMA, `0x514` = чтение с DMA), `+0x08` индекс команды,
  `+0x0C` аргумент, `+0x20` буфер, `+0x24` длина, `+0x28` число блоков.

Что было реализовано в модели:

* `Sdif::adma_transfer()` — обход таблицы в гостевой физической памяти
  (чтение/запись данных по описаниям, проверка VALID/END/ACT, счётчик
  перемещённых байт);
* `Sdif::set_dma_buses()` — контроллер зеркалится в два адресных пространства
  (ARM и CMeP), поэтому модель выбирает ту шину, которая реально отображает
  адрес таблицы (см. 18.2);
* `Transfer Complete` для DMA откладывается на 32 тика PERIPHCLK и поднимается
  вместе с битом DMA (3), как на реальном контроллере;
* `describe()` печатает строку `ADMA table=... moved=... ok/FAILED`.

### 18.2 У CMeP не было DRAM

Таблица лежит по 0x40000400, а буфер чтения — по 0x40000500. На шине CMeP эти
адреса были **не отображены** (`mem` возвращал 0xFF), то есть запись таблицы
уходила в никуда, и драйвер читал мусор. В `Vita::build_buses()` добавлено общее
окно DRAM: буфер `dram_` (128 МиБ, `kermit::kScuSize`), на который теперь
ссылаются *обе* шины — `arm_priv` (бывший отдельный регион) и новый `cmep_dram`
по тому же 0x40000000. Физически это один и тот же кусок памяти: CMeP готовит
то, что потом исполняет ARM.

Вторая ловушка: на шине ARM первые 64 КиБ окна 0x40000000 занимает блок MPCore
(SCU/GIC), а `Bus::find_device()` предпочитает устройство RAM. Поэтому первая
версия обхода ADMA всё равно читала нули (в трассировке было
`adma: record 0x40000400 not valid (attr=0x0000)`). Теперь `Sdif::dma_bus_for()`
считает шину пригодной только если адрес отображён **и** не занят устройством.

### 18.3 Куда дошла вторая стадия

```
CMD0 GO_IDLE_STATE
CMD1 SEND_OP_COND (arg 0x40000080)
CMD2 ALL_SEND_CID
CMD3 SEND_RELATIVE_ADDR
CMD9 SEND_CSD
CMD7 SELECT_CARD
CMD8 SEND_EXT_CSD        512 байт через порт (PIO, dma=0)
CMD16 SET_BLOCKLEN
CMD17 READ_SINGLE_BLOCK  lba=1, 512 байт, **ADMA2, ok**
CMD13 SEND_STATUS
CMD17 READ_SINGLE_BLOCK  повтор того же блока
CMD13 SEND_STATUS
```

Буквы прогресса (GPIO 0xE20A0008, ловятся `ZLB_WTRAP=E20A0008-E20A000B`) —
`A B C D E H T`; раньше по цепочке было только `A B C D E H`. Последняя метка
`T` (0x4063E), после неё загрузчик уходит в свой выход:

```
0x40346  lw $0,(0x5513c)
0x4034A  bnez $0,0x40388        ; ненулевой результат 0x404B6 = ошибка
0x4037C  mov $6,768             ; успех: код 0x300, шаблон из 0x40180
0x4039A  mov $6,1280            ; ошибка: код 0x500, шаблон из 0x40100
0x403A2  ... копирование 32 слов в 0x5FF00, обнуление регистров, sleep
```

То есть подтвердилось предположение прошлых раундов: 0x300 — успех, 0x500 —
ошибка. После починки ADMA шаблон действительно скопирован в 0x5FF00, регистры
обнулены, PC = 0x5FF1E (`sleep`), и эмулятор сообщает
`CMeP halted: sleep instruction`. Это не «зависание», а штатный выход по ошибке.

### 18.4 Где именно ломается

Метка `T` — это обработка 4096-байтового буфера по 0x40000500:

```
0x4062C  movh $1,0x4000 / or3 $1,$1,0x500   ; $1 = 0x40000500
0x40630  mov $2,4096
0x40638  bsr 0x46914                        ; запомнить буфер чтения
0x40648  bsr 0x41ae4                        ; разобрать
0x4064E  beqz $0,0x40656                    ; 0 -> дальше (метка U)
0x40650  ... отчёт об ошибке с буквой 'T'
```

`0x41AE4` расшифровывает 512 байт вызовом `0x464C0`; тот требует `size == 512`,
ненулевой приёмник и 4-й аргумент >= 0x200, затем `0x46980` (настройка ключа),
`0x4673C` (операция), `0x46632`, `0x4687C` и в конце копирует результат. Именно
`0x464C0` возвращает ненулевой код, и загрузчик идёт по ветке ошибки.

Что читается: `ARG = 0x200` — это **байтовое** смещение (модель делит на 512;
драйвер сам умножает номер сектора на 512 в 0x470C4). 0x200 — это ровно первый
payload контейнера SLB2 (entry 0, `second_loader.enp`), то есть загрузчик
считает смещение 0x200 смещением *внутри контейнера* и ожидает оттуда
зашифрованные данные.

### 18.5 Что лежит в образе и что не сходится

* user-area копия контейнера (8 МиБ): заголовок SLB2 настоящий
  (`SLB2`, version 1, table size 0x200, 7 entries), но payload 0
  (`second_loader.enp`) — зашифрованные байты (не MeP-заголовок), а payload 1
  (`second_loader.enc`) — **нули**;
* копия в boot0 (файл 0xE3400000 при user area 0xE3400000): payload 0 в
  открытом виде (MeP-заголовок `0x64B2C8E5`), payload 1 зашифрован. То есть
  четыре копии контейнера не идентичны, а `emmc_rebuild --verify` сверяет только
  таблицу (отчёт «4 copies checked» этого не ловит).

Диагностический опыт: собран образ 512 МиБ (`emmc_rebuild --size 512M`) и в нём
512 байт payload 0 подставлены по смещению 0x200. Поведение не изменилось:
ADMA положила подставленные байты в 0x40000500 (проверено `mem`), но
«расшифрованный» буфер по 0x5E000 остался повторяющимся 16-байтовым блоком —
то есть крипто-функция шифрует **не** тот буфер, который заполняет ADMA, а
какой-то другой (нулевой). Значит вход операции надо искать в
`0x4673C`/`0x46632`/`0x4687C` (указатели и ключи), а ключ, скорее всего,
приходит из keyring (`0x47F0C` читает `[obj+0x2B8]`).

### 18.6 Инструментарий этого раунда

  обход таблицы ADMA и опустошение порта; шумные регистры статуса исключены;
* `ZLB_WTRAP=E20A0008-E20A000B` — буквы прогресса загрузчика;
* `emmc_rebuild --size 512M` + `--emmc <файл>` — быстрый диагностический образ
  (можно подменять байты, не трогая основной);
* `zeliboba_ui --screenshot ... --core mep --run 200000000` — снимок состояния
  (screenshots/19-cmep-adma-read.png).

### 18.7 Следующий шаг

1. Найти вход крипто-операции 0x464C0 (кто и какой буфер шифрует) — тогда станет
   ясно, чем именно подменить данные, чтобы 512 байт расшифровались;
2. проверить, как загрузчик получает базу контейнера SLB2: он читает смещение
   0x200 как контейнерное, но база устройства (`0x55C50`, поле +0) явно

3. после этого — чтение secure_kernel / kernel_boot_loader и передача управления

### 18.9 Продолжение раунда: что именно ломается после чтения

Когда ADMA2 заработала, стало видно, что загрузчик читает **один** блок и тут же
пытается его обработать. Разобрана вся цепочка:

```
H (0x405D2)  -> 0x405DE bsr 0x41002   инициализация SD + таблица ADMA
             -> 0x405F8 lw 0xE0070004  проверка бита 0 окна eMMC-крипто
                бит 0 == 0  -> метка T (0x4063E), иначе R (0x4060A)
T (0x4063E)  -> 0x40638 bsr 0x46914   запомнить буфер чтения (0x40000500 в 0x55C70)
             -> 0x40648 bsr 0x41ae4   разобрать прочитанный блок
             -> 0x40650 отчёт об ошибке с буквой 'T'
выход        -> 0x4039A: код 0x500, копия шаблона 0x40100 в 0x5FF00,
                обнуление регистров, sw $6,($5) (код в почтовый ящик) и sleep
```

Что делает разбор (`0x41AE4` -> `0x464C0` -> `0x46980` -> `0x4673C` ->
`0x46632` -> `0x4687C` -> `0x46C7A`):

* `0x464C0` требует ровно 512 байт, ненулевой приёмник и 4-й аргумент `>= 0x200`;
  при ошибке возвращает коды вида `0x800F0016` / `0x800F001C` / `0x800F0005`;
* `0x46980` — настройка ключа: два раза `0x4C33E` (256 байт таблиц `0x4D138`,
  `0x4D144`), затем `0x4C312(handle, 0x4D138, ...)` и **сравнение двух хешей**
  (`0x469CA bne $6,$7`). То есть загрузчик сверяет ключ из keyring с эталоном,
  зашитым в его образ;
* `0x46632` сначала `memset(*(0x55C70), 0, 512)`, затем `0x46C7A(handle, буфер,
  512)`; результат уходит в `0x40001500`, откуда `0x464C0` копирует его
  вызывающему. Именно поэтому в 0x5E000 виден повторяющийся 16-байтовый блок: в
  буфере на момент шифрования лежали нули, а данные чтения к этому моменту уже
  «съедены» сессией (`0x4673C` читает `*(0x55C70)` до memset).

Инструментарий (`ZLB_BIGMAC_TRACE=1`) показал главное: **крипто второй стадии не
обращается к Bigmac вообще**. За весь прогон в движке всего 16 операций: 14 —
первый загрузчик (keyring, расшифровка образа в 0x40000, SHA-256), одна
(0x000C, AES-CBC) — тоже первый загрузчик (0x56600..0x5BFFF), и одна
«фантомная» — шаблон выключения пишет `1` в регистр старта Bigmac, из-за чего
модель запускает команду с оставшимся в регистрах мусором (`pc=0x5FF04`). Значит
вторая стадия считает AES **сама, кодом MeP** (`0x46C7A` и библиотека
`0x4C000`), и всё, что нужно — правильные ключ/сессия.

Заодно:

* исправлена ошибка сборщика образа: 12 зарезервированных байт заголовка
  контейнера SLB2 (0x14..0x1F) заполнялись 0xFF, тогда как и в retail-контейнере
  (`boot_slb2-00.pkg.seg02`), и в обоих дампах (`emmcdump_bls0/bls1.bin`) там
  нули; теперь сборщик пишет нули (`build_slb2_container`);
* проверено, что копии контейнера в user area (8 МиБ) и в boot0 идентичны —
  прежнее расхождение было ошибкой чтения по неправильному смещению (0x802200
  вместо 0x800200);
* добавлен переключатель `ZLB_SDIF_BLOCK_ARG=1` (трактовка аргумента CMD17 как
  номера блока, а не байтового адреса). Прогон с ним даёт ровно тот же результат,
  то есть место чтения не является причиной отказа.

### 18.10 Следующий шаг (уточнённый)

1. Снять состояние **в момент** вызова крипто-цепочки (сейчас после отказа
   область 0x55C70/0x56520 уже затёрта материалом ключа): нужен watchpoint на
   0x56524 (указатель контекста устройства) и на `+0x2B8` объекта — оттуда
   `0x47F0C` берёт handle для keyring;
2. проверить, что keyring-слот, который запрашивает вторая стадия, содержит
   именно retail-ключ (первый загрузчик кладёт его из образа по +0xE0) — тогда
   сверка хешей в `0x46980` пройдёт;
3. после этого блок, прочитанный с карты, разберётся как таблица SLB2 по имени
   (`0x45A3C`: счётчик по +0xC, записи по 0x20 с шагом 0x30, имя по +0x10,
   first_block по +0, size по +4, базы — таблица 0x55C48), и загрузчик пойдёт
   читать secure_kernel / kernel_boot_loader.

### 18.11 Уточнения по итогам зондов (важно для следующего раунда)

Три прогона с ловушками чтения/записи уточнили картину и **отменили** одну
гипотезу из 18.10:

* `0x47F0C` — это **не** чтение ключа, а чтение ёмкости устройства:
  `lw $3,-29148($gp)` берёт объект устройства (в рантайме `[0x56524] = 0x55E74`),
  а `lw $0,696($3)` возвращает `[0x55E74+0x2B8] = 0x71A000` — то есть объявленный
  размер user area в блоках по 512 байт (то же число, что в master block).
  Ловушка чтения: `+0x1612C r4 = 0x71A000 pc=00047F18`.
* индекс слота для крипто-сессии даёт `0x4692A`: он декодирует **глобальное слово
  флагов по 0x55700** (биты 1..4 → 1..4, бит 4 установлен → -1). При нулевом
  слове получается 1, то есть настройка ключа формально успешна — значит отказ
  происходит дальше по цепочке (`0x4673C`/`0x46632`/`0x4687C`/`0x46C7A`).
* Подстановка в образ по смещению чтения (0x200) **ничего не меняет** ни для
  зашифрованного payload, ни для настоящего заголовка контейнера SLB2: буквы
  прогресса остаются `A B C D E H T`, PC выхода тот же. Значит отказ происходит
  до использования прочитанных данных, и «правильные данные» проблему не решают.
* Почтовый ящик CMeP→ARM (0xE0000000) пишется трижды: `1` из первого загрузчика
  (pc=0x5C5F2), `9` из второй стадии (pc=0x4107C) и **`0x500` из шаблона
  выключения** (pc=0x5FF18). То есть ARM получает код ошибки — это уже готовый
  сигнал для boot chain, которым можно пользоваться при отладке следующих стадий.
* Bigmac во второй стадии не используется вообще: за весь прогон 16 операций —
  14 у первого загрузчика, одна (AES-CBC, ptr=0x56600 len=0x5A00) тоже у него, и
  одна «фантомная» из шаблона выключения (запись `1` в регистр старта запускает
  команду с мусором в регистрах, `pc=0x5FF04`). Крипто второй стадии — целиком
  код MeP (`0x46C7A`, библиотека 0x4C000), поэтому моделировать нужно не движок,
  а найти, какое именно условие в этой цепочке не выполняется.

Практический план на следующий раунд — сузить место отказа внутри
`0x464C0`, не угадывая: поставить точки останова/ловушки на возвраты
`0x46980`, `0x4673C`, `0x46632`, `0x4687C` (их адреса возврата известны:
0x4650E, 0x46534, 0x4653E, 0x4655C) и прочитать `$0`/`$7` в каждой — это даст
точный код ошибки (0x800F0005, 0x800F0024 и т.п.) и конкретную функцию.

## Раунд 19. Отказ второй стадии объяснён: idstorage и семантика адреса CMD17

### 19.1 Бисекция крипто-цепочки

Добавлена трасса по адресу (`ZLB_MEP_PC=0x4650E,0x46534,...` — при достижении
адреса печатаются регистры), потому что точки останова в одном скрипте нельзя
перешагнуть (повторный `run` останавливается на том же PC, а `bpc` принимает
адрес, не номер). С её помощью цепочка `0x464C0` разобрана по шагам:

| Точка | Что вернула | Значение |
|---|---|---|
| `0x4650E` | `0x46980` (настройка слота) | `$0 = 1` — успех |
| `0x46534` | `0x4673C` | `0 = 0` — успех |
| `0x4653E` | `0x46632` | **`0` — отказ** (до правок), при отказе код `0x800F0026` |
| `0x4655C` | `0x4687C` | не достигалась |

`0x46632` оказался проверкой: первые **32 полуслова** буфера чтения
(0x40000500) должны быть `0xFFF5`, иначе функция возвращает 0, а вызывающий
уходит в ветку ошибки. Это маркер, а не расшифровка: буфер перед этим
обнуляется (`memset`), а «шифр» в этом режиме данные не меняет.

### 19.2 Дамп подтвердил, что читается idstorage

В `dumps/emmcdump.zip` (`emmcdump.bin`) по смещению **0x40000** лежит ровно то,
что требует загрузчик:

```
0x40000  64 байта  F5 FF ...           (32 полуслова 0xFFF5 — маркер)
0x40040  u16 0x0000, 0x0001, ... 0x007F (индекс листьев)
0x40140  0xFFFF ... до +0x180
0x40180  0x0080, 0x0100, 0x0102, 0x0103, 0x0110..0x0115  (короткий список)
далее    0xFFFF; листья 1..255 — сплошные 0xFF
```

Сборщик образа писал индексную таблицу с нулевого смещения и «пустые» листья в
виде чередования `F5FF/FFFF`, то есть маркера не было. `build_idstorage_image()`
теперь повторяет раскладку дампа (и листья 1..255 остаются стёртыми), тест
`emmc_idstorage_image` обновлён под неё.

### 19.3 Семантика аргумента CMD17

Загрузчик читает `ARG = 0x200` и ожидает там блок с маркером `0xFFF5`, то есть
idstorage по байту 0x40000 = **блок 0x200**. Значит аргумент — номер блока, как и
положено eMMC с установленным битом 30 в OCR (карта сообщает о высокой ёмкости).
`Sdif::current_lba()` теперь трактует его так; прежнее (байтовое) чтение осталось
под `ZLB_SDIF_BYTE_ARG=1`.

### 19.4 Что изменилось

| | до | после |
|---|---|---|
| Чтения CMD17 | 0x200 дважды | **0x200 трижды, затем 0x2C0** (0x98000) |
| Маркер `0xFFF5` | не проходил | **проходит** (`0x46632` возвращает 1) |
| Проверка версии в стадии `T` | не достигалась | **проходит** (`$4 = 0 < 0x10401`) |
| Код ошибки | `0x800F0026` | **`0x800F0024`** (`0x4678C`) |

`0x4678C` — это поиск: он до 32 раз (по `ctx+0x24`) заполняет 512-байтовый блок
через программный шифр `0x46C7A` и ищет в нём полуслово `0x0080` (в дампе это
первый элемент списка листьев, то есть загрузчик ищет лист 0x80). Найденный
индекс возвращается через выходной параметр, и `0x4687C` использует его как
смещение: источник = `0x40000 + idx * 512`. Поиск не находит совпадения — отсюда
`0x800F0024`.

### 19.5 Следующий шаг

Разобраться, откуда `0x4678C` берёт поток для поиска: параметры сессии
(`ctx+0x10 = 0x40000` — это смещение idstorage на карте, `ctx+0x14 = 0`) и что
должно быть в расшифрованном блоке, чтобы `0x0080` в нём нашлось. Вероятно,
сессия должна инициализироваться данными, прочитанными с карты (0x40000500), а не
образом загрузчика, и тогда 32 «блока» — это последовательные 512-байтовые записи
idstorage.

## Раунд 20. Что именно ищет вторая стадия и почему не находит

### 20.1 Проверенный факт: поиск полуслова `0x0080`

Точки останова в `0x4683E`/`0x46842` (цикл поиска в `0x4678C`) дали точную
картину:

```
0x46842  $0 = 0x0080   (искомое значение)
         $1 = 0xFFF5   (полуслово, прочитанное из буфера)
         $2 = 0x40000500 (буфер)
         стек [0x5DC88] = 80 00 00 00 ...  (аргумент поиска = 0x80)
```

а сам буфер `0x40000500` в этот момент содержит **в точности наш leaf 0**:

```
+0x000  F5 FF ... (маркер, 32 полуслова)
+0x040  00 00 01 00 ... 7F 00 (индекс листьев)
+0x140  FF FF ... 
+0x180  80 00 00 01 02 01 03 01 10 01 11 01 12 01 13 01 14 01 15 01
```

То есть расшифровка данных карты работает и даёт ожидаемую раскладку (шифр в
этом режиме данные не меняет), но проверка `0x46632` требует маркера `0xFFF5` в
первых 32 полусловах, а поиск `0x4678C` ищет **другое** значение — полуслово
`0x0080`. Это идентификатор листа: `0x0080` — первый элемент списка листьев в
leaf 0, то есть загрузчик ищет в idstorage лист с id `0x80`.

Структура поиска (`0x4678C`): до 32 итераций (`ctx+0x24`), в каждой — `memset`
буфера, вызов шифра `0x46C7A(handle, буфер, 512)` и сравнение полуслова буфера
со значением аргумента (по `$2 += 2`, `$6 += 1` за итерацию — то есть сканируются
первые 64 байта блока); найденный индекс возвращается через выходной параметр, а
`0x4687C` использует его как смещение источника (`0x40000 + idx*512`). Если
совпадения нет за 32 итерации — `0x800F0024`.

### 20.2 Чего не хватает в образе

В образе листья idstorage 1..255 стёрты (`0xFF`) — ровно как в дампе, где
читается только leaf 0 (маркер + индекс + список), а остальное либо `0xFF`, либо
нечитаемые нули. Наличие листа с id `0x80` подтверждается списком в leaf 0:
`{0x0080, 0x0100, 0x0102, 0x0103, 0x0110..0x0115}`.

Эксперименты с образом (подстановка в листья `0x80` и `0xC0` записей, начинающихся
с `0x0080`, и копии раскладки leaf 0) **не меняют поведение** (тот же PC выхода,
то же число инструкций `200262140`, те же четыре чтения CMD17: `0x200` трижды и
`0x2C0`). Значит сканируемые блоки не читаются с карты по этим адресам, а
генерируются шифром из состояния сессии (`0x46AB8`), и содержимое листьев должно
попадать туда иначе.

### 20.3 Следующий шаг

1. Понять, как сессия (`0x46AB8`, таблица `0x56450`) получает очередной блок: она
   вызывается с адресом `0x40000` (это смещение idstorage на карте) и нулевой
   длиной; чтения с карты идут через 0x46DE3 — вероятно, эти 32 блока должны
   подгружаться чтением последовательных листьев, а не генерироваться;
2. синтезировать листья из списка leaf 0 (id в первом полуслове), начиная с
   `0x80`, и проверить, что поиск проходит, а версия в `[запись+0x80]` меньше
   `0x10401`;
3. если содержимое листьев принципиально недоступно (в дампе их нет), применить
   тот же приём, что уже используется для ключей первой стадии
   (`machine/bootkeys.cpp`): «development substitution» — подготовить данные так,
   чтобы проверка загрузчика прошла, и задокументировать это.

## Раунд 21. SMI-лист: поиск листа проходит, упор сместился на шифрование payload

### 21.1 Поиск листа работает: 0x0080 найдено

Трасса по адресу сравнения (`ZLB_MEP_PC=0x46842`) показала, что цикл поиска
**действительно сканирует все 512 байт блока**, а не только первое полуслово:

```
194 сравнения, указатель идёт 0x40000500, 0x40000502, 0x40000504, ...
последние:  got=0xFFFF ptr=0x4000067E
            got=0x0080 ptr=0x40000680   ← совпадение (полуслово 192)
```

То есть загрузчик ищет в **таблице отображения (первые 512 байт idstorage)** запись со
значением `0x0080` и находит её в слоте 192 ✓. Прежняя версия «сравнивается
только первое полуслово» была неверной: hardware-loop повторяет тело вместе с
хвостовыми инструкциями (`add $2,2`/`add $6,1`), поэтому сканирование идёт по
всему сектору.

### 21.2 Что такое лист 0x80: SMI (по вики)

Пользователь дал ссылку на <https://wiki.henkaku.xyz/vita/IdStorage>; страница
подтверждает всё, что было выведено из кода:

* idstorage = **таблицаотображения** (массив `u16` идентификаторов листьев, `0xFFF5` в
  записях самой таблицы, `0xFFFF` — свободный лист) + **листья по 512 байт**,
  данные листа с индексом `i` лежат по `512*i`;
* лист с идентификатором **`0x80` — это SMI** (Service / Manufacturing
  Information), «Contains minimal firmware version (checked in `second_loader`)»
  — то есть именно та проверка, на которой стоит наша вторая стадия;
* структура: `char magic[4]` = `"SMI\0"`, `u32 version` = 1,
  `u32 minfw_plaintext`, нули до `0x7F` (проверяются загрузчиком), затем
  **payload (0x80..0xFF)** и **подпись (0x100..0x1FF)**; обе зашифрованы
  per-console ключом (keyslot `0x213`), причём payload — **дважды** (outer+inner),
  а подпись — один раз. Именно поэтому `0x464C0` выполняет **две** операции
  шифра (`0x4673C` → `0x46632` и затем ещё раз `0x46632`/`0x4687C`) — это
  outer- и inner-расшифровка.

Наш сборщик до этого писал в листья `0xFF`, поэтому после успешного поиска
загрузчик читал слот 192 (блок `0x2C0`, ровно те чтения, что видны в трассе
SDIF) и получал мусор.

### 21.3 Что сделано

`build_idstorage_image()` теперь дописывает **SMI-лист** в слот 192: `"SMI\0"`,
version 1, `minfw_plaintext` = 0, нули в 0x0C..0x7F; области payload и подписи
оставлены нулями, потому что на железе они зашифрованы ключом консоли. Тест
`emmc_idstorage_image` проверяет и таблицу, и SMI-лист.

Эффект: загрузчик доходит дальше — индексы инструкций `200232080` → `200262140`
→ **`200263307`**, чтения `0x200` ×4 + `0x2C0` (слот SMI), а код ошибки
сменился с `0x800F0024` (поиск не нашёл лист) на **`0x800F0005`** (неудача
шифра: `0x4687C`/`0x468FE`).

### 21.4 Следующий шаг

Payload SMI нужно *зашифровать* так, чтобы гостевая расшифровка дала корректный
`manuSdkVersion` (>= версии загрузчика). Схема известна: AES-CBC-256 с ключом из
keyslot `0x213`, ключи выводятся *шифрованием* «Outer/Inner Key Seed» (seed и IV
зашиты в образ второй стадии — это аргументы вызовов крипто-библиотеки вокруг
`0x46980`/`0x4C33E`/`0x4C312`). В эмуляторе уже есть AES (bigmac.cpp) и
контролируемый keyring, поэтому путь такой:

1. вытащить из образа второй стадии seeds/IV (константы 0x4D138/0x4D144 и
   аргументы `0x4687C`/`0x46980`);
2. реализовать host-side вывод outer/inner ключей и двойное AES-CBC-256
   шифрование payload по образцу `provision_boot_keys` (тот же приём
   «development substitution», уже принятый в проекте для ключей первой стадии);
3. проверить, что `[лист+0x80]` после гостевой расшифровки даёт `0x00010400`
   и загрузчик идёт дальше по стадиям (`U`, `_`, `V`, …).

## Раунд 23. Протокол движка Bignum: рукопожатие вместо «вечного done»

### 23.1 Симптом

Второй загрузчик вставал насмерть в обёртке `0x4B9FC`:

```
0004BAA2  erepeat 0x4baac
0004BAA6  lw $3,($8)          ; $8 = 0xE0040804 (статус движка)
0004BAA8  movh $11,0x400
0004BAAC  and $3,$11
0004BAAE  bnez $3,0x4bab0     ; взятая ветвь = выход из петли
```

`ZLB_MEP_PC=0x4BAA6` дал 38107 попаданий за 400k шагов, `trace 40` — что чтение
`0xE0040804` возвращает `0x400`. Разгадка в одной инструкции: `movh $11,0x400`
грузит **старшее** полуword, то есть `$11 = 0x04000000` — загрузчик ждёт бит 26,
а модель (по ошибочному разбору первого загрузчика) ставила бит 10 (`0x400`).
Отсюда вечный цикл.

### 23.2 Настоящий протокол

Сверка `bignum_op` первого загрузчика (`0x5CE04`) и обёртки второго (`0x4BA20`)
дала один и тот же протокол:

| Регистр | Назначение | Свидетельство |
|---|---|---|
| `0xE0040108` | основание (base), 64 слова | `0x5CE0C`, `0x4BA52` |
| `0xE0040400` | модуль, 64 слова | `0x5CE28`, `0x4BA6E` |
| `0xE0040808` | очередное слово экспоненты | `0x5CE50`, `0x4BAF6` |
| `0xE0040800` | управление `0x91000000 \| n1<<18 \| n2<<9` | `0x5CE5C`, `0x4BAA0` |
| `0xE0040804` | статус (см. ниже) | `0x5CE68..0x5CE8E`, `0x4BAC2..0x4BB3E` |
| `0xE0040508` | результат, 64 слова | `0x5CECA`, `0x4BB52` |
| `0xE0020020` | семафор завершения | `0x5CF12`, `0x4BBB0` |

Биты статуса:

| Бит | Маска | Значение |
|---|---|---|
| 31 | `0x80000000` | занято (операция в работе) |
| 25 | `0x02000000` | ошибка |
| 26 | `0x04000000` | готов принять слово (ставится и в простое) |
| 27 | `0x08000000` | ждёт очередное слово экспоненты |
| 16..23 | `0xFF0000` | длина результата в словах |

Именно поэтому первый загрузчик проверяет **оба** бита 26 и 27 перед подачей слова:
после последнего слова экспоненты бит 26 остаётся (движок снова простаивает), а
бит 27 снимается — петля останавливается. Второй загрузчик считает слова сам и
поэтому проверяет только 26.

Ключевые детали, снятые со второго загрузчика:

* `desc = {модуль, слов модуля, экспонента, слов экспоненты}`; для SMI-ключа это
  `{0x4D024, 64, 0x4D124, 1}`, где `0x4D124` = `00 01 00 01` = e = 65537.
* Экспонента подаётся словами **от старшего к младшему** (поток идёт по
  big-endian строке вперёд) и выравнивается по правому краю 64-словного окна.
* `0xE0020020` — семафор завершения: движок поднимает его по окончании операции,
  `engine_wait` (`0x4BBB0`) крутится до ненулевого значения и снимает записью;
  пока семафор не снят, следующая операция возвращает `0x800F0010` («занято»),
  и вызывающий повторяет её после `engine_wait` (`0x4BD78..0x4BD80`).

## Раунд 24. SMI: подписи и per-console ключ, выход на проверку структуры

### 24.1 Что добавилось в development substitution

Операции движка заработали, и отказ сместился в проверки SMI-листа:

1. `0x4643C` (`beqz $0,0x4648C`) — результат RSA-проверки подписи SMI. Подпись
   подделать нельзя (ключ SCE), а `bignum_run` (`0x4BBCE`) требует корректного
   блока PKCS#1 v1.5 (`0x4BC1E..0x4BD22`), поэтому ветвь заменена на безусловную
   `bra 0x4648C` (слово `0xB050`).
2. `0x464A6` — вторая keyed-проверка целостности открывает keyslot **0x213**
   (per-console ключ, которого нет ни в одном дампе) и гоняет keyed-семейство
   Bigmac (функции `0x2309`, `0x238A`, `0x2093`, бит 13 = «индекс keyring в поле
   flags»). Без ключа операции падают с `0x800F0005` (`0x45042`), и валидатор
   возвращает этот код вызывающему, хотя все ветви, читающие его, уже
   замаскированы. Четыре байта по `0x464A6` заменены на `mov $0,0; bra 0x464AE`.

Обе правки выключаются `ZLB_NO_SUBSTITUTION=1`.

```
0x48E46  lbu $2,($6);   bne   '0'(0x30) -> отказ

```

## Раунд 25. Конфигурационные записи: транспорт SPI 0x00A0 и запись {0x30,1,kind,index}

### 25.1 Как искали

Отказ `0x800F0024` из раунда 24 приходит из функции `0x48E24`, которая
проверяет 40-байтовую запись по `$6`:

```
0x48E46  lbu $2,($6);   bne   '0'(0x30) -> отказ
0x48E4E  lbu $3,1($6);  bnei  0x1       -> отказ   ; версия 1 = «запись есть»
0x48E56  lbu $3,2($6);  0..5 или 16     -> иначе отказ
0x48E72  lbu $1,3($6);  bne   ($8)      -> отказ   ; индекс записи
```

Пара к ней — `0x48D28` (строит шаблон «записи нет»: `{0x30, 0, 0, index, …}`)
и `0x48D78` (путь записи: версия 0 на входе → версия 1 в хранилище). То есть
загрузчик держит конфигурационные записи в NVS syscon: читает шаблоном с
версией 0 и ждёт версию 1.

Что именно читается, показала трасса шины на точке `0x449A6` (перед проверкой):

```
W4  E0A00004 = 0000FB00   pc=00043784 Kermit.Spi0@mirror
W4  E0A00010 = 00000001   pc=00043794 Kermit.Spi0@mirror
...
R4  E0A00024 = 00000200   pc=00043BFC Kermit.Spi0@mirror
R4  E0A00000 = 00000004   pc=00043C26 Kermit.Spi0@mirror   ; первый байт ответа
```

то есть CMeP общается с Ernie по **SPI** (`0xE0A00000` на шине CMeP), а не
через SDIF. `log debug` показал саму команду:

```
[debug] ernie SPI cmd 0x00A0 payload=40 -> code 0x0004 payload=0
```

Сорок байт — это шаблон записи, ответа не было вовсе (в модели команды
`0x00A0` не было), поэтому загрузчик прочитал из порта данных остатки прошлого
ответа (`04 02 80 79` = 0x80020004) и проверка не прошла.

### 25.2 Правка модели

В `ErnieBlock::Impl::dispatch` добавлена команда `0x00A0`: 40-байтовый шаблон
возвращается с версией 1 (`record[1] = 1`, `kind = 0`, хвост обнуляется) —
это документированная development substitution: NVS syscon нет ни в одном
дампе рабочей папки, а формат записи (версия/тип/индекс) проверяет сам
загрузчик. `ZLB_NO_SUBSTITUTION=1` возвращает шаблон без изменений.
Обрамление ответа (4 + payload) для этой команды строится вручную, потому что
`build_reply` держит firmware-размер 4+32; слой SPI теперь переносит до 64
байт полезной нагрузки (раньше — 32).

Добавлена диагностика `ZLB_LOG_DBG("ernie.sc", "cmd 0x%04X payload=%u")`,
включается `log debug` из отладчика.

### 25.3 Новый упор: keyed-семейство Bigmac

Проверка записи пройдена, отказ сместился на `0x800F0005`: снова keyed-операция
Bigmac, на этот раз из `0x4B3B7` (обёртка `0x453AA`, затем проверка состояния
ключа `0x4501E`, код `0x800F0005` при `0x45042`, статус `0x78000`).

Обёртка `0x453AA` собирает слово функции так:

```
function = base | (режим & 7) | ((аргумент << 3) & 0x38) | ((аргумент << 8) & 0x300)
```

где `base` приходит из дескриптора ключа (`0x2300` для keyslot `0x213`), а
режим задаёт вызывающий. Наблюдённые функции: `0x2309`, `0x238A`, `0x2093` —
то есть бит 13 (`0x2000`) = «ключ берётся из keyring по индексу в поле flags»
(в трассе `flags=0x00000213`), бит 7 (`0x80`) — прежний модификатор «ключ из
памяти». Модель пока знает только базовые коды (`0x0301`, `0x030A`, `0x010A`,
`0x000C`…`0x0013`, `0x0033`), поэтому keyed-семейство падает.

Следующий шаг: разобрать режимы `0x309`/`0x38A`/`0x93` (какая именно операция
— AES-CBC с ключом из keyring, RNG или SHA) и реализовать их в `bigmac.cpp`,
после чего проверить, доходит ли загрузчик до передачи на ARM.

### 25.5 Keyed-семейство Bigmac: заглушка как development substitution

Следом отказ вернулся к `0x800F0005` — снова keyed-операция Bigmac, теперь из
`0x4B3B7` (обёртка `0x453AA`, затем проверка состояния ключа `0x4501E`, код
`0x800F0005` в `0x45042` при статусе `0x78000`). Обёртка собирает слово функции
как `base | (режим & 7) | ((a << 3) & 0x38) | ((b << 8) & 0x300)`, где `base`
приходит из дескриптора ключа (`0x2300` для keyslot `0x213`), а режим задаёт
вызывающий; наблюдённые функции — `0x2309`, `0x238A`, `0x2093`, то есть бит 13
(`0x2000`) = «ключ берётся из keyring по индексу в поле flags».

Ключа `0x213` нет ни в одном дампе, поэтому точные режимы по доступным данным не
восстанавливаются. В `bigmac.cpp` добавлена документированная заглушка: если у
слова функции выставлен бит 13, а код операции модели неизвестен, операция
рапортует успех (бит ошибки не поднимается), и в трассе `ZLB_BIGMAC_TRACE`
печатается строка `keyed op ... (development substitution: reported ok)`.
`ZLB_NO_SUBSTITUTION=1` возвращает прежнее поведение (`0x78000`).

### 25.6 Новый упор: запись с версией 3

Заглушка дала +93 тысячи шагов (334921 → 428019) и новый отказ `0x800F0024` из
второго валидатора записей `0x4906C` (вызывается из `0x40C10` с индексом 11):

```
0x4909E  lbu $1,($6);   bne   '0'(0x30) -> отказ
0x490AE  lbu $2,1($6);  bnei  0x3       -> отказ   ; версия 3, а не 1
0x490B6  lbu $2,2($6);  0..5 или 16
```

То есть для того же индекса 11 в одном месте ожидается версия 1 (проверка
`0x48E24`), а позже — версия 3: загрузчик ведёт *жизненный цикл* записи в NVS
(создал → обновил), и модель обязана его повторять. Команда-запрос всегда
одинакова — `30 00 00 0B` (`{0x30, версия 0, тип 0, индекс}`), то есть версия
приходит не из запроса, а из состояния хранилища. Следующий шаг: найти путь
записи (валидатор `0x48D78` вызывается косвенно, через таблицу указателей) и
сделать в модели настоящее NVS-хранилище записей по индексам: запись —
сохранить (вместе с её версией), чтение — вернуть сохранённое, а «пустой»
шаблон (`0x30 00 00 idx`) отвечать версией 1 только пока записи нет.

### 25.7 Что ещё выяснено про записи

* Трасса `trace 60` на `0x490A6` показывает, что ответ разбирается правильно:
  байты `30 2A 30 01 00 0B … 95` — это `{len 0x2A, запись {0x30, версия 1,
  тип 0, индекс 0x0B}, контрольная сумма}`, то есть транспорт отдаёт ровно то,
  что положила модель, и дело только в версии.
* За весь прогон (до отказа на 428019 шагах) в syscon уходит **девять** команд:
  `0x0000` ×2, `0x0001`, `0x0002`, `0x0010`, `0x0080` ×2 и `0x00A0` ×2 — обе
  последние с одинаковым запросом `30 00 00 0B`. Команды записи записи в трассе
  нет, поэтому версия 3 не могла быть записана загрузчиком: её меняет само
  хранилище (либо это отдельный транспорт — образ 3072 байта читается не по SPI,
  а через SD-слой `0x43B2E`, где видны одиночные CMD17 на LBA `0x200`/`0x264`).
* Ручек для эксперимента добавлен `ZLB_RECORD_VERSION=<n>`: с версией 3 отказ
  наступает раньше (334411 шагов) — значит порядок действительно «сначала 1,
  потом 3», и версия 1 обязательна на первом чтении.

## Раунд 26. Жизненный цикл записи и проверка её полезной нагрузки

### 26.1 Эксперимент с версией

Гипотеза «первое чтение — версия 1, второе — 3» проверена прямо: в модели
счётчик чтений на индекс, `reads <= 1 ? 1 : 3`. Результат — отказ на **334411**
шагах, причём трассировка `ZLB_MEP_PC` по адресам `0x48EFA` (валидатор версии 1)
и `0x490A6` (валидатор версии 3) показала `pc=00048EFA` со `$3 = 3`: то есть
проверка версии 1 читает **второе** чтение, а не первое. Значит загрузчик читает
запись дважды до первой проверки, и правильная последовательность — «две выдачи
версии 1, затем 3» (`reads <= 2 ? 1 : 3`). С ней прогон уходит на **428028**
шагов, а код ошибки меняется с `0x800F0024` на `0x800F0027`.

Счётчик — такая же документированная подстановка, как и всё остальное в NVS:
точный триггер смены версии (кто и когда «обновляет» запись) по доступным данным
не восстанавливается, модель воспроизводит наблюдаемую последовательность.
`ZLB_RECORD_VERSION=<n>` по-прежнему переопределяет версию для экспериментов.

### 26.2 Новый упор: полезная нагрузка записи

`0x800F0027` строится в `0x49182` (валидатор `0x4906C`, продолжение после
проверок заголовка). Дальше по коду видно, что проверяется **содержимое** записи:

```
0x4910C  $4 = *(0x556C0 + индекс*4) + 16
0x49116  $2 = запись + 8; $3 = 32; $4 = ...
0x4911C  bsr 0x49272          ; keyed-операция над полем записи
0x49122  bnez $0 -> отказ
0x4912A  bsr 0x48cde          ; ещё одна
0x49134  bsr 0x48cde
```

то есть запись несёт в себе MAC/подпись, которую проверяют keyed-функции
(`0x49272`, `0x48cde`) — те же, что оборачивают Bigmac-семейство с ключом из
keyslot `0x213`. Наши нули такую проверку пройти не могут, поэтому здесь нужна
следующая подстановка (либо синтез правдоподобного поля, либо маскирование
проверок в `0x49122`/`0x4912E`/`0x49136`).

### 26.3 Найдено неотождествлённое устройство `0xE0100000`

Добавлена диагностика шины (`log debug` печатает каждое обращение к
неотображённому адресу с pc). В прогоне видно 19 таких обращений, все — в
`0xE0100000`:

```
[debug] bus  unmapped read  4 byte(s) at 0xE0100000 (pc=0x00049574)
[debug] bus  unmapped read  4 byte(s) at 0xE0100038 (pc=0x0004957C)
[debug] bus  unmapped write 4 byte(s) at 0xE0100038 = 0xFFFFFFFF (pc=0x00049580)
...
```

Код `0x49568..0x495E0` обходит таблицу дескрипторов устройств в `0x561A4`
(запись 0 — GPIO `0xE20A0000`, запись 1 — `0xE0100000`), читает регистры
`+0x00`, `+0x14..+0x2C`, `+0x38..+0x48` и часть из них пишет обратно (сброс
состояния). Значит у CMeP есть ещё один контроллер хранения на `0xE0100000`,
которого в модели нет; на текущем пути он только инициализируется, поэтому
отказ не от него, но заводить его придётся (в `docs/HARDWARE.md` он пока не
описан).

### 26.4 Подстановки для проверки записи

Чтобы валидатор `0x4906C` не валил загрузку, в `apply_development_substitutions`
добавлено четыре правки:

* `0x49122`, `0x4912C`, `0x49136` — три ветви отказа после keyed-проверок
  `0x49272`/`0x48CDE` (двухбайтовые `bnez`, обнуляются);
* `0x4918C` — `mov $0,$5` → `mov $0,0`, иначе код ошибки (`0x800F0005`,
  `0x78000`) остаётся в возвращаемом значении даже при снятых ветвях.

Порядок адресов важен: ветви стоят на `0x49122`, **`0x4912C`** и `0x49136`
(первая попытка с `0x4912E` попала в середину инструкции и ничего не изменила —
проверено по возвращаемому коду).

### 26.5 Новый упор: Bigmac `0x0102`

После этих правок прогон уходит на **436140** шагов, и `ZLB_BIGMAC_TRACE`
показывает следующего виновника:

```
[bigmac] fail code=0x0082 function=0x0102 ptr=0x0005DE1C len=16 flags=0x00000000
```

Это AES-блочная операция (16 байт, ключ из окна), которой в модели нет: известны
только `0x000C`…`0x000F` (CBC/ECB encrypt/decrypt) и `0x010A`. Заодно пришлось
расширить и keyed-заглушку: к семейству `0x2xxx` относятся не все keyed-операции —
`0x033B` (SHA-256 с ключом из keyring 0x212) тоже падал, поэтому заглушка теперь
ловит и `0x03xx`.

## Раунд 27. Записи 0x0B/0x0F пройдены, упор в «SCE»-команду

### 27.1 Семейство `0x01xx` и дайджест записи `0x0F`

* Операция Bigmac `0x0102` (16 байт, ключ из окна, `flags=0`) — та же keyed-семья,
  что и `0x010A`, но с режимом `(2,0,1)` вместо `(2,1,1)` (обёртка `0x453AA`
  собирает слово функции из базового `0x0100` и трёх аргументов режима). Заглушка
  расширена на префикс `0x0100`, после чего прогон уходит на **478088** шагов.
* Следом падает валидатор записи с индексом `0x0F` (функция `0x429xx`): он считает
  keyed-дайджест записи (`0x42E42`) и сравнивает его с сохранённым полем через
  `0x4C3AA`, а при несовпадении выдаёт `0x800F0027`. Обнуление ветви `0x4292E`
  (offset `0x292E`) снимает проверку — прогон идёт на **570516** шагов.

### 27.2 Новый упор: обмен «SCE»

Новый код ошибки — `0x800F0624`, сайт `0x4A782` в функции `0x4A6DE`. Она гоняет
48-байтовый запрос через транспорт, переданный указателем (`jsr $0` в `0x4A756`),
и требует, чтобы ответ начинался с магии `SCE\0`:

```
0x4A774  lw $1,($6)                 ; первое слово ответа
0x4A77A  movu $2,0x454353           ; "SCE\0"
0x4A786  bne $1,$2 -> 0x4ABEC       ; ошибка 0x800F0624
0x4A78E  bnei $2,0x3 -> ...         ; второе слово должно быть 3
0x4A796  and3 $1,$2,0x40            ; бит 0x40 в байте 8
```

Транспорт выбирает сама функция `0x4AC44`; на нашем пути она подставляет заглушку
`0x4A034`, которая просто копирует три слова со стека и возвращает 0 (то есть
ответ остаётся нулевым, и проверка магии не проходит). Вызывающий её код
(`0x41416`, boot-путь) передаёт дескриптор транспорта — глобальный блок
`0x55180`. В прогоне он **не инициализируется**: там всё ещё лежат байты образа
(`7A 7F B1 56 0D CD 12 1C …`), то есть шаг, который должен заполнить этот блок
(и, вероятно, выбрать «настоящий» транспорт вместо заглушки), у нас не
выполняется. Наиболее вероятная связь — неотождествлённый контроллер
`0xE0100000` из 26.3: его драйвер инициализируется первым и мог бы заполнять
дескриптор. Следующий шаг: завести это устройство (пусть минимально —
регистровый файл с осмысленным поведением) и посмотреть, изменится ли выбор
транспорта.

## Раунд 28. Блок «SCE» на 0x5FFC0000, контроллер 0xE0100000 и окно SC

### 28.1 Диагностика неотображённых обращений дала ответ

`log debug` (печатает каждый доступ к неотображённому адресу вместе с pc из
раунда 26) показал, что происходит с «SCE»-запросом:

```
[debug] bus unmapped write 4 byte(s) at 0x5FFC0000 = 0x454353 (pc=0x00040B10)
[debug] bus unmapped write 4 byte(s) at 0x5FFC0004 = 0x3      (pc=0x00040B10)
[debug] bus unmapped write 4 byte(s) at 0x5FFC0008 = 0x10140  (pc=0x00040B10)
[debug] bus unmapped write 4 byte(s) at 0x5FFC000C = 0x600    (pc=0x00040B10)
[debug] bus unmapped write 4 byte(s) at 0x5FFC0010 = 0x1000   (pc=0x00040B10)
...
```

`pc=0x40B10` — это внутренний цикл `memcpy` (`0x40AEC`), то есть загрузчик
копирует 48-байтовый запрос именно в **0x5FFC0000**, а потом читает ответ оттуда
же и проверяет магию (`0x4A774`). Настоящий транспорт тут не при чём: адрес просто
не был отображён, запись «в никуда» терялась, чтение возвращало `0xFF`, и магия
`SCE\0` не совпадала.

Окно `0x5FFC0000` заведено как память (`CMeP.SceBlock`, 64 КиБ, `cmep.h`:
`kSceBlockBase`/`kSceBlockSize`). Это документированная development substitution:
на железе это почтовый ящик secure-движка, который сам формирует ответ; модель
отражает блок (эхо), и все три проверки загрузчика — магия `SCE\0`, слово 1 == 3 и
бит `0x40` в байте 8 — проходят, потому что он сам их и записал.

### 28.2 Контроллер 0xE0100000 и окно SC

* `CmepStorageDevice` (`0xE0100000`, 4 КиБ) — второй контроллер из инициализации
  `0x49568..0x495E0` (см. 26.3). Пока это регистровый файл с нулевыми значениями;
  главное — окно больше не отдаёт `0xFF`, который загрузчик инвертировал и
  сохранял.
* `CMeP.SecureCtl` расширен с 16 КиБ до 64 КиБ (`0xE3100000..0xE310FFFF`): вторая
  стадия обращается к `0xE31040A4` и `0xE3105000` (`0x48794`, `0x48848`), а
  разделяемое окно SC у Ernie и так 64 КиБ.

После этих трёх правок неотображённых обращений в прогоне **ноль**, а загрузчик
проходит проверку «SCE» и уходит на **606273** шага.

### 28.3 Новый упор: аргументы «SCE»

Новый код ошибки — `0x800F0616` (проверка аргументов в семействе SCE-команд,
сайт `0x4A98A`). Функция `0x4A6DE` проверяет переданные структуры: указатель не
ноль, `*(arg)` не ноль, размер `>= 48` (`0x4A72C`) и так далее. Следующий шаг —
разобрать, какая именно структура приходит пустой, и кто обязан её заполнить
(кандидаты — уже известные `0x55180`/`0x561A4`, которые в нашем прогоне не
инициализируются).

## Раунд 29. Аргументы «SCE»: какая именно структура пуста

### 29.1 Где падает проверка

Трассировка всех ветвей на `0x4ABEC` в диапазоне `0x4A9xx..0x4ACxx` показала
последний (то есть сработавший) сайт — **`0x4A99A`**:

```
0x4A976  $1 = $7;       bsr 0x49FE8     ; $6 = *(*(*$7)) + ... + 112
0x4A984  bsr 0x49FF6                    ; второй указатель
0x4A98A  $5 = 0x800F0616
0x4A992  $0 = *($6+8)
0x4A99A  bne $0,$1,0x4ABEC              ; $1 = [sp+0x2C] = 5
```

то есть отказ не в магии и не в размере: `[структура+8]` должно быть **5**, а там
`0xC7D4904F`. Структура (`$6 = 0x5EE70`) лежит выше стека CMeP (`$sp = 0x5E000`)
и вне очищаемой второй стадией области BSS (`0x55710..0x56554`), то есть в
«свободном» буфере.

### 29.2 Кто её заполняет (и почему нет)

* В образе *первого* загрузчика по смещению `0x2E70` (адрес `0x5EE70`) лежат нули.
* Watchpoint на `0x5EE70` и на `0x5EE78`, поставленный **до** запуска, не сработал
  ни разу за 8 млн шагов — то есть ни CPU CMeP, ни его DMA туда не пишут.
* Значит содержимое буфера приходит из подстановок: keyed-операции Bigmac в
  модели рапортуют успех, но не считают криптографию, поэтому структура, которую
  загрузчик ожидает получить от secure-движка, остаётся мусором.

Вывод: дальнейшее «прокалывание» проверок по одной — тупик; нужна правка самого
диспетчера «SCE».

### 29.3 Что сделано

* `0x4ABF0` (`mov $0,$5`) → `mov $0,0`: диспетчер «SCE» (`0x4A6DE`) сообщает
  успех, как и валидатор конфигурационной записи. Это сняло проверку аргументов
  (`0x800F0616`) и перевело отказ на следующую проверку магии (`0x800F0624`).
* `0x5FFC0000` из простой памяти превращён в устройство `SceBlockDevice`
  (`cmep_internal.h`): блок «включается» с готовым ответом — магия `SCE\0`,
  слово 1 == 3, байт 8 с битом `0x40`, `+0x08 = 0x10140`, `+0x10 = 0x1000` — и
  дальше хранит то, что пишет загрузчик. После этого первый обмен «SCE» проходит
  полностью (в буфере ответа `0x5E800` видно `53 43 45 00 | 03 00 00 00 |
  40 01 01 00 | 00 06 00 00 | 00 10 00 00 | 94 5B 05 00 …`).

### 29.4 Текущее состояние и следующий шаг

Отказ снова `0x800F0624`, но уже на **следующем** обмене «SCE» (сайт `0x4A782`,
604353 шага): загрузчик обращается к движку повторно, и на этот раз магия в
буфере не совпадает. Трассировка ветвей `0x4A7xx..0x4A8xx` уточняет картину:

```
pc=0004A87A $1=0005E830 $2=5FFC0000 $3=00000FD0 $6=00000FD0 $5=800F0605
pc=0004A896 $1=0005DE34 $2=00000005 $4=0005DD08 $6=00000FD0 $5=800F0605
pc=0004A8B6 $1=0005DE34 $2=00000005 $4=0005DD08 $6=00000FD0 $5=800F0616
```

то есть второй запрос — это **чтение 4048 байт** (`0xFD0`) через тот же блок
`0x5FFC0000`, и проверки у него свои (`0x4A87A`, `0x4A896`, `0x4A8B6`).
Следующий шаг: научить `SceBlockDevice` отвечать и на этот «большой» вариант
(или, если содержимое принципиально per-console, замаскировать конкретную ветвь
`0x4A8B6`).

дальше начинается сравнение *содержимого* ответа secure-движка с ожидаемым —
ровно то, что подстановки не могут обеспечить (ключи per-console).

валидатора ответа «SCE» (`0x49D4E..0x49D5C`), который сверяет поля ответа

финальный код (значение приходит из другой ветви), но снимает одну из проверок.

## Раунд 31. ARM ждёт CMeP, а SCE-цепочка требует per-console данных

### 31.1 ARM не запускается сам

Проверка через отладчик (`core arm`, `run 100000`) показывает: ARM стоит на
`0x80000000`, все регистры нули, и за 100000 шагов машины он не сдвинулся ни на
инструкцию — шаги уходят CMeP (`stage=cmep-first-loader cmep=5E620`). То есть
ядро удерживается до тех пор, пока CMeP не отпустит SoC (SC-команда
`soc_release` = `0x2080` в таблице Ernie). В SPI-логе этой команды пока нет:
вторая стадия до неё не доходит.

Отсюда важный вывод для плана: **весь Stage 1 упирается в CMeP**; ARM-цепочка
(KBL → secure_kernel → kernel) начнётся только после `soc_release`.

### 31.2 Что именно проверяет SCE-обработчик

Точка останова на `0x4145A` (перед вызовом функции сравнения `0x49F42`) и дамп
кадра `0x5DE00` показывают, как выглядит запрос обработчика:

```
0x5DE00  00 00 00 00 | 00 00 FC 5F   ; указатель на блок SCE 0x5FFC0000
0x5DE08  00 00 04 00                  ; 0x40000
0x5DE0C  00 E8 05 00                  ; буфер ответа 0x5E800
0x5DE10  00 10 00 00                  ; 0x1000 (4096 байт)
0x5DE14  94 6B 05 00                  ; 0x56B94
0x5DE18  00 02 00 00                  ; 0x200
```

и цепочку проверок ответа:

```
0x4144E  lhu $3,16(ответ); bnei $3,0x2 -> отказ   ; версия ответа == 2
0x41462  bsr 0x49F42                              ; сравнение диапазонов
0x4147A  lbu $3,24(ответ+16); blti -> отказ       ; знаковый байт
```

Все они сверяют **содержимое** ответа secure-движка, а он у нас подменён:
`SceBlockDevice` отдаёт канонический заголовок и хранит записанное, но буфер
ответа (`0x5E800`) заполняет не он. Эксперимент с предзаполнением полей блока
(`+0x0C = 0x600`, `+0x10 = 0x1000`) ничего не изменил — финальный код остался
`0x800F0624`, то есть ответ приходит из другого места (транспорт-обёртка
`0x4A034`/её «настоящий» вариант).

## Раунд 32. ARM-цепочка ожила: латчи SC 0x5C/0x60

### 32.1 KBL запускается и висел на SC

Отладчик умеет прыгать по стадиям загрузки (`stage kbl` / `stage kernel`), и это
дало независимую ветку работы — ARM-путь, который в обычном прогоне вообще не
стартует (см. 31.1).

```
zlb> stage kbl
[info] machine KBL image: 355220 bytes from eMMC SLB2 -> kind=self entry=0x40020000
[info] boot    ARM started on kernel_boot_loader at 0x40020000 (eMMC SLB2)
zlb> core arm
zlb> run 40000000
core ARM Cortex-A9 (ARM) pc=0x4003C026 insns=40000000 Thumb SYS
```

То есть KBL загружается из SLB2, ARM стартует на `0x40020000` и доходит до
`0x4003C026`, где встаёт намертво. Дизассемблер показал причину:

```
4003C014  movs r3, #0x5C
4003C018  movt r3, #0xE310     ; r3 = 0xE310005C
4003C01E  str  r1, [r3]        ; r1 = 1
4003C020  ldr  r0, [r2]
4003C026  bne  0x4003C020      ; ждём, пока прочитается 0
```

Это сервисный латч: ARM пишет 1 в `0xE310005C` и ждёт, пока syscon его сбросит.
Модель для неизвестных регистров SC хранит записанное значение, поэтому чтение
возвращало ту же 1 и цикл не заканчивался.

### 32.2 Правка

В `ScWindowDevice` добавлены `kScReq5C = 0xE310005C` и `kScReq60 = 0xE3100060`:
запись в них **не сохраняется**, чтение возвращает 0 — то есть модель
подтверждает запрос сразу, как уже делает для `0xE31010A0`/`0xE31020A0`.
Второй латч нашёлся сразу за первым (тем же паттерном):

```
4003C04C  movs r3, #0x60
4003C050  movt r3, #0xE310     ; 0xE3100060
4003C056  str  r1, [r3]
4003C058  ldr  r0, [r2]
4003C05E  bne  0x4003C058
```

### 32.3 Результат

ARM поехал: `0x4003C026` → `0x4003C05E` → `0x4003A01C` (40 млн шагов) →
`0x4003B3D2` (80 млн шагов), `exceptions=0`, MMU выключен, режимы меняются
(Thumb/ARM). То есть KBL действительно исполняется, а не крутится на месте.

Заодно проверено, что вторая стадия в `stage kernel` доходит до `0x81000044`, где
натыкается на `0xFFFFFFFF` (ядро по этому адресу не загружено) — отдельная задача
для следующего раунда: `enter_stage(kernel)` должен подкладывать образ.

## Раунд 33. `stage kernel` грузит контейнер, а не код

### 33.1 Что показал дамп

Отладочная стадия `kernel` загружает `Vita_104_Firmware/Out/fs_dec/os0/kd/bootimage.elf`
и стартует ARM на его базе (`0x81000000`). Дамп памяти сразу после этого:

```
81000000  00 00 01 01 53 63 65 4B 65 72 6E 65 6C 42 6F 6F  |....SceKernelBoo|
81000010  74 69 6D 61 67 65 00 00 00 00 00 00 00 00 00 06  |timage..........|
81000020  00 00 00 00 5C 00 00 00 9C 00 00 00 00 00 00 00  |....\...........|
```

то есть по базе лежит **заголовок контейнера** `SceKernelBootimage`, а не код:
дизассемблер ARM читает `tsteq r1,r0`, `blmi`, `svcvs` — это данные. ARM исполняет
их 18 инструкций и улетает на `0x81000044`, где пусто (`0xFFFFFFFF`).
`elfinfo.py` подтверждает: у файла `entry=0x00000000`, один сегмент
`vaddr=0x81000000 filesz=0x2A542C` — то есть это образ-контейнер со списком
модулей (`os0:kd/clockgen.skprx`, `os0:kd/idstorage.skprx`, … в строках).

Вывод: `stage kernel` в текущем виде стартует ARM по данным. Настоящий путь —
KBL, который сам разбирает os0 (FAT16-раздел, в модели уже есть монтирование
`os0_0`: 63 файла) и грузит `os0:kd/*.skprx`.

### 33.2 Что ещё видно в прогоне `stage kbl`

* ARM идёт вперёд (см. раунд 32), MMU выключен, исключений нет;
* на 200 млн шагов он исполняет уже настоящий ARM-код в районе
  `0x40039FE0..0x4003A02C` — это библиотека работы с CP15 (`bic`/`orr` по
  управляющему регистру, `mcr p15,0,r0,c1,c0,1` = запись Auxiliary Control
  Register, `mrs r0,cpsr`, `mrs r0,spsr`, барьеры `dsb sy`), то есть KBL занят
  системной инициализацией, а не крутится на месте;
* ни одного неотображённого обращения **со стороны ARM** — весь мусор в логе
  приходит из CMeP (`pc=0x49F7C`, чтение `0x62700`), то есть из уже подменённой
  SCE-ветки, а не из ARM-драйверов;
* eMMC-активность в логе (`CMD13`/`CMD17`, `emmc_get_csd`, `emmc_get_ext_csd`)
  пока принадлежит CMeP (pc `0x47912`/`0x481E2`): KBL до чтения карты ещё не
  дошёл.

### 33.3 Следующий шаг

Дать KBL читать карту: он должен поднять свой SD-контроллер (`Kermit.Sdif0`
`0xE0B00000` в модели есть) и через FAT16 раздела os0 дойти до `os0:kd/`. Полезно
сначала проследить, на каком регистре он остановится, тем же способом, что и
латчи SC (`stage kbl`, `core arm`, `run`, `dis` около текущего pc). Параллельно

## Раунд 35. Boot sequence: три колонки и TrustZone

### 35.1 Что говорит рабочая папка

Схема загрузки (F00D / TrustZone / ARM) и собственный разбор ROM CMeP
(`dumps/bootrom_analysis/ANALYSIS.md`) сходятся:

* `vita_prototype_bootrom.bin` — это **boot ROM CMeP** («первый код, который
  вообще исполняется на Vita, *до* ARM Cortex-A9»), он же «first loader», и он
  работает из окна 0x5C000 (RAM: `_start` пишет 0 в 0x5C000 и чистит `.bss` по
  0x5EB00 — ANALYSIS.md 4.1). Никакой отдельной «самокопии всего образа» в коде
  нет: копируется только 32-байтовый runtime-стаб в 0x5FFE0; в RAM же образ
  оказывается целиком к моменту запуска (окно 128 КиБ 0x40000–0x5FFFF).
* Дальше ROM берёт **физический адрес следующей стадии из почтового ящика
  `0xE0000010`** (бит 0 = «данные есть»), копирует образ в 0x40000, проверяет
  MeP-заголовок и прыгает туда — это `second_loader.enp` (ANALYSIS.md 4.2, режим
  `'A'` = 0x41 = bit0+bit6). То есть ARМ-сторона **действительно** выкладывает
  образ и звонит в ящик — механизм документирован, а вот *кто именно* на стороне
  ARM это делает, из дампа не следует (дампа ARM boot ROM в папке нет).
* По схеме у **TrustZone нет собственного boot ROM**: secure world bootloader
  *загружается* (F00D/second_loader), запускает Secure World Kernel, и только
  потом идёт non-secure world: bootloader → `os0:kd` («ядро») → SceShell.
  `secure_kernel.enp` на схеме относится к колонке **F00D** (цепочка `os0:sm`).

### 35.2 Что из этого реализовано в модели

* шаги 1–3: реализованы (Ernie → CMeP boot ROM → `second_loader`), шаг 3 сейчас
  упирается в per-console SCE-цепочку;
* шаг 2 (ARМ выкладывает образ в общую SRAM и звонит в ящик CMeP) — **подстановка
  на C++** (`Vita::arm_boot_rom_stage_second_loader`), потому что дампа ARM boot
  ROM нет;
* **TrustZone не смоделирован вообще**: у ядра ARM нет состояния secure/non-secure
  (нет NS-бита в CPSR, нет SCR, secure banked регистров), `stage kbl` прыгает
  сразу в non-secure world. Это и есть главный пробел относительно схемы;
* `stage kernel` оказался подстановкой не туда (грузит контейнер
  `SceKernelBootimage`, а не код — см. раунд 33).

### 35.3 Что добавлено в этом раунде

* `plan_boot()` переписан по трём колонкам схемы (F00D → TrustZone → ARM) с
  пометкой, какие шаги в модели подставлены;
* новая стадия отладчика **`stage secure`** — грузит расшифрованный
  `Out/SLB2_dec/secure_kernel.bin` (31744 байта, MeP-образ) в окно 0x40000 и
  запускает CMeP на нём, то есть позволяет упражнять следующее звено цепочки
  F00D, минуя непройденную SCE-проверку второй стадии. Отдельно проверено, что
  «в лоб» он не живёт: без окружения, которое готовит `second_loader`, CMeP
  уходит на `0x1171CFC` (вне RAM) — то есть запускать его имеет смысл только
  после того, как вторая стадия дойдёт до своего конца.

### 35.4 Следующий шаг

Смоделировать TrustZone в ядре ARM: NS-бит в CPSR, SCR, secure banked
регистры/вектора и режим monitor, плюс стадии secure world bootloader и Secure
World Kernel (образами из `SLB2_dec/`: `nsbl.bin` — raw ARM с таблицей векторов
`ldr pc,[pc,#0x18]`, 176268 байт). Тогда `stage kbl` перестанет быть прыжком
через secure world, и можно будет проверить, не потому ли KBL крутится, что
secure-стадии не выставили ему окружение.

## Раунд 36. Имя `vita_prototype_bootrom.bin`, цепочка по wiki и декодер GPO-чекпоинтов

### 36.1 Поправка к имени файла (подтверждена по wiki)

Замечание пользователя: `dumps/vita_prototype_bootrom.bin` назван неправильно —
это прототипный **first_loader**, а не boot ROM. Проверено по
`wiki.henkaku.xyz/vita/First_Loader`:

> First Loader is the Boot Code, ~~also called Boot ROM~~ (To be precise,
> first_loader is not a BootROM), of the PS Vita. It is a short MeP executable run
> by the Cmep processor at boot. After initializing the most secure Cmep keyrings,
> it launches Second Loader.
>
> For all First Loader dumped at physical address 0x5C000.

То есть first_loader — короткий **MeP-исполняемый файл**, живущий в окне
`0x5C000` (ровно поэтому у нас два 16-кибибайтных дампа одного и того же окна:
`vita_prototype_bootrom.bin` — прототип/DEM-плата, `pch-5c-cold_first_loader.bin`
— retail-снимок RAM после загрузки).

Откуда взялась путаница: на странице `Boot_Sequence` раздел «First Loader»
начинается словами «The cmep processor's boot ROM, **nicknamed First Loader**, is
the first known code running on PS Vita start» — там «First Loader» это прозвище
*boot ROM*, а на отдельной странице «First Loader» — уже само MeP-приложение.
Два разных объекта под одним термином; в коде и документации проекта используем
только второе значение.

### 36.2 Документально ли подтверждён шаг 2 («ROM → 0x5C000»)?

Вопрос был: «first_loader содержится в бутроме CMeP, потом он самокопируется как
first_loader в 0x5C000 и продолжает работу — есть ли документальное
подтверждение, что пункт 2 работает так, как написано?»

Что подтверждается **нашими же материалами**:

* окно `0x5C000` — это **RAM, а не ROM**: `ANALYSIS.md` §4.1 — `_start` чистит
  `.bss` (`0x5EB00…0x5EE3C`), а в конце копирует 32-байтовую заглушку из
  `0x5C098` в `0x5FFE0`; заглушка **пишет 0 в `0x5C000`** (самоуничтожение точки
  входа), обнуляет регистры и делает `ret` по `$lp = 0x40000`. Писать внутрь
  собственного кода и обнулять свою точку входа можно только в RAM;
* косвенно то же самое: `pch-5c-cold_first_loader.bin` — это снимок RAM *после*
  загрузки, и его `.data`/`.bss` сдвинуты на `-0x80` относительно чистого
  прототипного образа (`COMPARISON.md`), то есть файл снят с уже
  отработавшей/самомодифицировавшейся копии;
* следовательно, **какой-то код до first_loader обязан положить 16 КиБ образ в
  окно `0x5C000`** — гипотеза пользователя внутренне непротиворечива.

Чего подтвердить **нельзя**:

* *чем именно* это делается — ROM копирует встроенный в него образ, ROM читает
  first_loader из eMMC/SD, или его кладёт CP/ARM отладочной платы. Ни в
  workspace, ни в wiki этого нет; дампа CMeP boot ROM у нас нет вообще, так что
  статически проверить нечего;
* «самокопирование» в буквальном смысле: **единственная** самокопия в коде
  first_loader — это те самые 32 байта `0x5C098 → 0x5FFE0`, а не весь образ.

Что документировано точно (и чем мы реально пользуемся): `ANALYSIS.md` §4.2 —
`check_boot_mode()` (`0x5C0EE`) читает keyring `0x501` и бит 0 регистра
`0xE0062020`, возвращая режим `'A'` = `0x41` либо `'!'` = `0x21`. Бит 0 режима —
«образ приходит от ARM»: опрашивается ящик `0xE0000010` (бит 0 = «данные есть»),
читается физический адрес, 64-байтовый заголовок копируется в `0x40000`,
проверяется, затем подтягивается тело. Это **собственный штатный режим загрузки
first_loader**, и модель использует именно его (`arm_boot_rom_stage_second_loader`
кладёт образ в общую SRAM и выставляет ящик), а не эмулирует несуществующий ROM.

Итог: шаг «ROM кладёт образ в 0x5C000» — **подстановка** (development
substitution), а не воспроизведение; `plan_boot()` переформулирован так, чтобы
это было видно (раньше строка 2 читалась как «известно, что ROM запускает
first_loader»).

### 36.3 Декодер GPO-чекпоинтов

В отладчик добавлена команда **`gpo`**: печатает состояние
`0xE20A0008`/`0xE20A000C` (set/clear), сырое значение последнего чекпоинта и его
расшифровку. Код лежит в **битах 16..23** (`raw >> 16`) — это следует из таблицы
wiki «Known Codes» и подтверждается трассой шины: KBL пишет `0x00840000` =
код `0x84` («Secure Kernel BootLoader: Some device init»), CMeP пишет
`0x00490000` = код `0x49`.

Расшифровка сделана по таблице `Boot_Sequence#Known_Codes`:

* `0x40..0x7F` — second_loader (таблица кодов в `debugger.cpp`);
* `0x81..0x8F` — secure kernel bootloader (TrustZone, ARM secure world);
* `0xA1..0xAF` — NSKBL (ARM non-secure world).

В самой wiki две несовместимые конвенции: текст говорит «Second Loader
checkpoint codes start at 0x40 (e.g. GPO value `0x52` corresponds to SBL code
`0x12`)», а строки таблицы для 1.04 перечислены уже как значения (`0x52` =
«eMMC is not available»). Поэтому декодер печатает значение как есть и для
диапазона `0x40..0x7F` дополнительно приводит чтение «значение − 0x40».

Наблюдение из прогона `stage kbl` + 200 млн шагов: последним писал CMeP —
`raw=0x00490000` → `0x49`. По таблице (строка 0.931.010) `0x49` — это событие
«?Loading `kernel_boot_loader.self`?» с аварийным «?reading/loading/...
`kernel_boot_loader.self` failed?», то есть вторая стадия встаёт как раз на
загрузке KBL — что согласуется с отказом `0x800F0624` на 604505-м шаге. Код
`0x84` в трассе показывает, что ARM-овская secure-стадия KBL успевала дойти до
инициализации устройств.

### 36.4 Следующий шаг

Без изменений относительно 35.4: смоделировать TrustZone в ядре ARM (NS-бит в
CPSR, SCR, secure banked регистры и вектора, режим monitor, MVBAR/VBAR), чтобы
secure-половина `kernel_boot_loader.self` работала не «поверх» non-secure
состояния. Декодер `gpo` теперь даёт точку опоры: по коду чекпоинта видно, до
какой именно стадии цепочки дошёл запуск.

## Раунд 37. TrustZone в ядре ARM: SCR, MVBAR, банк VBAR и SMC

### 37.1 Что добавлено

Ядро ARM (Kermit) теперь знает про Security Extensions настолько, насколько это
нужно цепочке загрузки:

* **`ArmCore::ns_` + `scr`** — текущий мир и конфигурационный регистр SCR
  (CP15 c1 c1 0). Запись SCR разрешена только из secure-состояния, значение
  бита 0 (NS) переключает мир; чтение — `CP15 SCR` в отладчике;
* **`mvbar`** (CP15 c12 c0 opc2=1) — база векторов режима monitor;
* **банк VBAR** — у secure- и non-secure-мира свои базы векторов
  (`CP15 VBAR` и `CP15 VBAR_NS`); `effective_vector_base()` выбирает нужную;
* **исключение в monitor mode** уходит на `MVBAR + 8`, а не на общий VBAR;
* **`SMC`** (A32 `0x01600070`, T32 `0xF7F0 0x80i0`) теперь действительно
  выполняется: `LR_mon = pc+4`, режим MON, PC = `MVBAR + 8`, I/F замаскированы.

Важное архитектурное замечание, зафиксированное в коде: **CPSR.NS в этом ядре не
алиасится в бит 4**. В ARMv7-A бит 4 CPSR — это и есть NS, но все константы
режимов (SVC = 0x13, IRQ = 0x12, MON = 0x16, …) требуют бита 4 = 1, а банк
регистров в интерпретаторе индексируется 5-битным полем режима. Поэтому мир
хранится явно (`ns_`/SCR), а SPSR мир не несёт: monitor переключает его через
SCR — именно так и делает secure kernel bootloader. Это упрощение, а не
архитектурная точность, и оно помечено в `arm_defs.h`.

### 37.2 Найденная и исправленная мёртвая ветка декодера

Обработчики `SMC`/`HVC` в `decode_arm_misc` были **недостижимы**: вход в этот
декодер защищён `is_arm_misc_encoding()`, где SMC/HVC не были перечислены, а
внутри `o1 == 0x16` (это же поле у MSR) перехватывался раньше проверки SMC.
Проверка через отладчик (`poke 0x40020000 0xE1600070`, `reg PC 0x40020000`,
`reg MVBAR 0x40021000`, `step`) показала, что инструкция просто исполнялась как
data-processing и PC уходил на `pc+4`. После правки (SMC/HVC в
`is_arm_misc_encoding` + обработка в начале `decode_arm_misc`) тот же прогон даёт:

```
до :  PC=0x40020000  CPSR=0x1D3 SVC secure
после: PC=0x40021008  CPSR=0x1D6 MON secure   R14(LR)=0x40020004
```

то есть `MVBAR + 8`, как и предписано архитектурой. Скрипт проверки —
`tools/dbg_r36b.cmd`.

### 37.3 Что видно про KBL

Прогон `stage kbl` + 200 млн шагов (`tools/dbg_r36a.cmd`) теперь печатает
состояние TrustZone. KBL на `0x400201A8` пишет **`SCR = 0x00000004`** — это
бит 2 (SCR.FIQ: FIQ уходят в monitor), NS остаётся 0, то есть secure-половина
KBL продолжает работать в secure-мире. `MVBAR`/`VBAR` за 200 млн шагов не
выставлены, `exceptions=0` — KBL крутится в цикле, не доходя до передачи в
NSKBL (то есть до записи SCR.NS=1 и VBAR).

## Раунд 38. Консоль прошивки, четыре ядра и первая настоящая диагностика KBL

### 38.1 Почему вывод KBL не был виден

`putchar` самого KBL (0x4003BC88, Thumb) выглядит так:

```
cmp  r1, #0xA                 ; '\n' -> сначала отправить 0xD
r3 = 0x4005C058               ; таблица консолей
r2 = [r3 + r0*4]              ; r0 = индекс консоли
loop: r0 = [r2 + 0x28]        ; статус
      tst r0, #0x100          ; бит 8 = передатчик свободен
      beq loop
str  r1, [r2 + 0x70]          ; <-- данные консоли
```

то есть **регистр данных — `+0x70`**, а таблица `0x4005C058` содержит
`{0xE2030000, 0xE2040000}` (проверено дампом памяти в работающей машине). Наша
модель UART трактовала `+0x70` как `MCR` (шаг 16550-регистров `(off>>2)&7`), а
`0xE2040000` вообще не была отображена (в `kermit.cpp` она была подписана как
«SDIF0 alias — ASSUMPTION»). В результате весь вывод прошивки терялся.

Исправление: `define(kConsoleData=0x70, ...)` (важно: `RegisterBlock::write()`
вызывает `write_word()` **только для объявленных регистров** — необъявленный
offset просто остаётся в байтовом образе), второй `Uart` на `0xE2040000` с
флагом `mirror` (чтобы не логировать одну и ту же строку дважды), новая команда
отладчика **`console`** (алиас `uart`), которая отдаёт накопленный вывод вместе с
незавершённой строкой.

Итог — эмулятор печатает собственный лог загрузчика:

```
===================================================
Starting PSP2 Kernel Boot Loader [0xrevision   : cp info.   : (N/A)
memory[		Safe Mode : [ YES ]
```

### 38.2 `run` против `runm`: KBL требует все четыре ядра

Отладочная команда `run` (Debugger::step) исполняет **только активное ядро**
(плюс по одной инструкции MeP и RL78), а `runm` идёт машинными слайсами, то есть
крутит все четыре ядра Kermit. KBL набирает ядра сам: каждое читает MPIDR
(0x40039F88), и они встречаются на барьере 0x4003B384 (структура в bss на
0x4005C000: счётчик приходов по halfword +8, «индекс следующего ядра» по +6,
SEV/WFE-рукопожатие). При `run` ядра 1..3 стоят на входе 0x40020000, барьер не
завершается, и boot-ядро навсегда висит в 0x4003B3D2 — до per-core init оно не
доходит.

Поэтому в `runm` добавлена проверка **машинных точек останова**
(`Debugger::machine_breakpoint_check`): после каждого слайса PC всех четырёх ядер
сравнивается с точками останова кластера. Без этого остановиться на коде, который
лежит за барьером, было нельзя.

### 38.3 Где сейчас умирает boot-ядро

После `stage kbl` + 150000 слайсов:

```
arm0  pc=0001610C HALTED ARM ABT secure mmu=on     <- boot-ядро
arm1  pc=4003A018 running ARM SYS secure mmu=on    <- в WFE
arm2  pc=4003A018 running ARM SYS secure mmu=on
arm3  pc=4003B36C running Thumb SYS secure mmu=on
CP15 DFSR=7 DFAR=0x00040000 IFSR=7 IFAR=0x0001610C VBAR=0x00016100 MVBAR=0x00000120
```

Цепочка событий: KBL берёт **неожиданный data abort на VA 0x00040000**
(pc=0x400321B6) → идёт на вектор `VBAR+0x10 = 0x16110`, страница векторов не
отображена → prefetch abort на 0x16110 → вектор `VBAR+0x0C = 0x1610C` → снова
fault → детектор цикла исключений останавливает ядро (всего 14 fault'ов, из них
пять — одиночные «пробы», которые KBL обрабатывает).

Откуда `VBAR = 0x16100`: это **жёстко зашитая константа** —
`mov.w r7, #0x16000; str.w r7, [r5, #156]` (0x4002100A), затем
`r2 = [r5+156] + 0x100; str r2, [r5, #0x22C]` (0x40020E16) и уже оттуда
`mcr p15,0,r3,c12,c0` (VBAR). MVBAR считается рядом из того же контекста
(`(r6 + r3 + 0x23 + r7) & ~0x1F`).

Таблицы, которые KBL построил сам (дамп после остановки):

* `TTBR0 = 0x40108000`, `L1[0] = 0x80200181` — coarse table по PA 0x80200000;
* `L2[0..7]` — small pages → `PA 0x40118000` (8 страниц = 32 КиБ «boot context»);
* `L1[1..7] = 0x000001E0` — fault-дескрипторы (VA 1..8 МиБ закрыты);
* `L2[16+]` **никогда не записывались**: в дампе там 0xFFFFFFFF (неинициализированная
  DRAM), то есть VA 0x16000 не отображён вообще.

Помощник отображения — `0x4003AD40` (одна страница: r0=таблица, r1=атрибуты,
r3=VA, PA на стеке) и `0x4003AD78` (диапазон); вызовы из 0x40020AFE, 0x40021126
(атрибуты `0x1061D006`), 0x4002118A (атрибуты `0x1021D005`, VA из `[r5+156]`),
0x4002BCCA, 0x40031C4C, 0x40034016, 0x4003414E. То есть вызов, который должен
отобразить страницу векторов, в коде есть — но в нашем прогоне он либо не
доходит, либо получает нулевые аргументы (в контексте вокруг `[r5+0x9C]` всё
остальное — нули).

### 38.4 Рабочая гипотеза

KBL ожидает, что низкие VA (в том числе страницу векторов 0x16000) ему уже
отобразил кто-то до него — по вики это делает **second loader**: «It also writes
the ARM exception vector and some boot context information to the 32kB scratch
buffer (mirror mapped to 0x00000000 on ARM)». В `stage kbl` мы перепрыгиваем
second loader, поэтому boot-контекста нет, и карта памяти KBL получается
несогласованной. Проверяемо: либо достроить настоящую цепочку (CMeP
second_loader → secure_kernel → release ARM), либо собрать синтетический
boot-контекст в 32 КиБ scratch и смотреть, изменится ли поведение KBL.

### 38.6 Что ещё удалось выяснить точечными остановками

Остановка на вызове отображения (0x4002118A, `tools/dbg_r38o.cmd`) даёт аргументы:

```
r0 = 0x80200000  таблица L2
r1 = 0x1021D005  атрибуты
r2 = 0x00016000  [r5+156] — та самая «база векторов»
r3 = 0                 [r5+156] - [r5+120], т.е. [r5+120] тоже 0x16000
r7 = 0x40000000  физический адрес, уходит 4-м аргументом на стек
```

Помощник `0x4003AD40` строит дескриптор как
`(pa & ~0xFE0 & ~0x1F) | convert(attr)` и кладёт его в `L2[r3 >> 12]` — то есть
этот вызов отображает **VA 0**, а не 0x16000. Соседний вызов (0x40021126)
использует `r3 = [r5+180] - [r5+120]` и атрибуты `0x1061D006`. Итог: KBL строит
карту только для VA 0x0..0x7FFF (8 small pages → PA 0x40118000).

Опасное обращение, с которого началась гибель ядра, — `pc = 0x400321B6`:

```
40032198  ldr r2, [r2]
400321A2  add.w r1, r2, r3, lsl #2     ; r3 = (size >> 12) страниц
400321A6  cmp r9, r11
400321A8  it lt                        ; IT-блок на две инструкции
400321AA  mov r12, r1                  ; (lt)  r12 = r1
400321AC  mov.w r12, #0                ; (ge)  r12 = 0
400321B6  ldr.w r2, [r12, #0]          ; <-- здесь VA = 0x40000
```

то есть KBL уверен, что **VA 0x40000 существует** (в него указывает вычисленный
указатель). В нашей машине ARM-овский PA 0x00000-0x3FFFF вообще не отображён
(`map 0x16100` → region `-`), тогда как вики прямо говорит про 32-кибибайтный
scratch, «mirror mapped to 0x00000000 on ARM», куда second loader кладёт вектор
ARM и boot-контекст. Отсюда две конкретные задачи следующего раунда:

1. выяснить, какие именно VA/PA-пары KBL просит отобразить (трассировка обоих
   вызовов и их аргументов) и чем должен быть заполнен низкий VA-диапазон;
2. закрыть пробел в машине: низкое окно ARM (scratch CMeP, зеркало на PA 0) —
   сейчас его нет ни в `Vita::wire_bridges`, ни в карте шины.

## Раунд 39. Чем на самом деле заканчивается вторая стадия CMeP: сервис на 0x5FF00

### 39.1 «Halt: sleep instruction» — это не сбой, а вызов сервиса

Нормальный прогон (`docs`/скрипт `tools/dbg_r39c.cmd`) даёт: first loader → передача
на 0x40000 → вторая стадия крутится, делает **4121 чтение eMMC**, и затем
останавливается на `pc=0x5FF1E` с причиной «sleep instruction». История PC
(`history mep 40`) показывает:

```
000403BE .. 00040404      ; код второй стадии
0005FF00 0005FF02 .. 0005FF1C   ; <- прыжок в окно первого загрузчика
```

а `dis` в этой точке:

```
0005FF1C  62 70     sleep
0005FF1E  FE BF     bra 0x5ff1c     ; idle-цикл sleep; bra
```

То есть ядро доходит до `sleep; bra` — это **штатный idle/ожидание
прерывания**, а не отказ. Непосредственно перед этим вторая стадия выполняет
(0x403C0…0x40404):

```
xor $11,$11 / $12,$12 / $tp,$tp / $gp,$gp / $sp,$sp    ; полностью чистит регистры
movh $1,0xe005 ; or3 $1,$1,0x1c     ; $1 = 0xE005001C
movh $2,0xe005 ; or3 $2,$2,0x24     ; $2 = 0xE0050024
movh $3,0xe005 ; or3 $3,$3,0x9c     ; $3 = 0xE005009C
movh $4,0xe005 ; or3 $4,$4,0xa4     ; $4 = 0xE00500A4
movh $5,0xe000 ; or3 $5,$5,0x0      ; $5 = 0xE0000000
jmp 0x5FF00                          ; абсолютный прыжок в окно первого загрузчика
```

Это классический «вызов сервиса со свежим окружением»: регистры обнулены, в
$1..$5 переданы адреса Bigmac (`0xE005001C/24/9C/A4`) и ящика (`0xE0000000`),
после чего управление уходит на фиксированный адрес `0x5FF00` в окне
0x5C000-0x5FFFF.

Декодирование `jmp` проверено: наш дизассемблер совпадает с binutils-листингом
(`vita_prototype_bootrom.annotated.asm`) на всех шести `jmp` первого загрузчика
(0x5C000→0x5C004, 0x5CF54→0x5E660, 0x5DA52→0x5D7D8, 0x5DADC→0x5D898,
0x5DB1E→0x5D814, 0x5C094→0x5C094), так что `jmp 0x5FF00` — не ошибка декодера.

### 39.2 Почему в нашей модели это тупик: прототип против retail

`0x5FF00` лежит в **heap/stack-области** окна первого загрузчика
(`ANALYSIS.md` §3: 0x5EE3C-0x5FFDF — «unused (heap/stack area)», 0x5FFE0-0x5FFFF —
32-байтовый stub). В дампах:

| Дамп | Содержимое 0x5FF00 |
|---|---|
| `vita_prototype_bootrom.bin` (наш рабочий загрузчик) | **нули** |
| `pch-5c-cold_first_loader.bin` (retail, снимок RAM) | кодоподобные слова (`movu $7,0x5da`, `beqi $0,0xc,0x5ae12`, …) |

Кроме того, прототипный загрузчик сам пишет свой стек в 0x5FFxx (трап записей
показывает push'и из `pc=0x5C504/0x5C50A/0x5CC08/0x5CC0E…`), поэтому в нашем
прогоне там оказываются **остатки стека**, которые ядро и исполняет, доезжая до
случайного `sleep; bra`.

Вывод: вторая стадия **retail-прошивки 1.04** вызывает сервис, который живёт в
retail-загрузчике, а мы запускаем её с **прототипным** first loader'ом
(`vita_prototype_bootrom.bin`) — комбинация, которой на реальном железе не
существует. Это же объясняет и то, почему прототипный вариант терпимо относится к
нашему синтетическому образу (см. ниже).

### 39.3 Прогон с retail-загрузчиком: отказ на валидации заголовка

`zeliboba --first-loader ..\dumps\pch-5c-cold_first_loader.bin` + `boot` + `run`:

```
CMeP first loader entered at 0x5C004
first loader failure path taken (mailbox = 2) at pc=0005C62C
stage=failed cmep=5C62C insns=241918
```

то есть retail-загрузчик проходит 120959 инструкций и уходит в свой failure-loop
(`0x5C62C: bra 0x5c62c`), записав в ящик 2. Заголовок, который он валидирует
(0x40000 в адресном пространстве CMeP):

```
+0x00 = 0x64B2C8E5   magic  (совпадает)
+0x04 = 0x000002C0   size   (>= 0x2B0 и < 0x10000 — проходит)
+0x08 = 0x00000010   offset
+0x0C = 0x00000000   length (size == offset + length + 0x2B0 — проходит)
```

Все проверки, задокументированные по прототипу (`ANALYSIS.md` §4.3), этот
заголовок проходит, значит retail-сборка проверяет что-то ещё — по
`COMPARISON.md` она строже в валидации заголовка и добавляет рукопожатие на
SC-регистре `0xE3100194` (в модели этот регистр объявлен, но, судя по всему,
отвечает не то, что ждёт retail-сборка).

Побочный результат: сообщение об отказе теперь печатает PC загрузчика
(`at pc=0005C62C`) — раньше было видно только `mailbox = 2`.

### 39.4 Что это значит для Stage 1

Цепочка сходится к одному из двух решений:

1. **Согласованная пара загрузчиков.** Retail first loader (`pch-5c-cold_first_loader.bin`)
   + retail `second_loader.enp` — как на реальной консоли. Для этого нужно, чтобы
   наш синтетически подписанный образ проходил строгую валидацию retail-сборки
   (и/или её рукопожатие на 0xE3100194).
2. **Подстановка сервиса 0x5FF00.** По вики это ровно шаг 4 цепочки: «the Second
   Loader resets itself with a pointer to `secure_kernel.enp`». То есть сервис на
   0x5FF00 — это перезапуск CMeP на следующей стадии. Мы можем смоделировать его
   явно (загрузка `secure_kernel.enp` из SLB2 в окно и рестарт CMeP), пометив как
   development substitution, — и получить шаг 4 цепочки даже без retail-загрузчика.

Второй путь дешевле и совпадает с тем, что уже описано в `plan_boot()`, поэтому
следующий раунд начинается с него.

## Раунд 40. Шаг 4 цепочки: CMeP сам доходит до secure_kernel, и где он встаёт

### 40.1 Перехват сервиса 0x5FF00 и подстановка

В ядро MeP добавлен машинный хук `MePCore::pc_hook` (вызывается перед исполнением
инструкции; `true` — остановиться, не исполняя). Машина ставит на него
`Vita::cmep_pc_hook`: пока стадия — вторая (0x40000…), PC == `board::kFirstLoaderServiceEntry`
(0x5FF00) → взводится флаг, и на ближайшей границе слайса
`Vita::serve_cmep_service_call()` перезапускает CMeP на следующей стадии. По вики
это ровно шаг 4: «the Second Loader resets itself with a pointer to
`secure_kernel.enp`». Отключается как обычно — `ZLB_NO_SUBSTITUTION=1`.

Нормальный прогон теперь идёт **без `stage`** до secure kernel:

```
first loader reported SUCCESS to the ARM mailbox
CMeP handed off to the staged image at 0x40000
CMeP halted: machine hook at 0x5FF00
second loader called the first-loader service at 0x5FF00 (development substitution:
    restarting the CMeP into secure_kernel.enp)
CMeP secure kernel loaded directly at 0x00800000 (31744 bytes)
stage=cmep-secure-kernel cmep=8000F8
```

### 40.2 secure_kernel грузится на 0x800000, а не на 0x40000

Первая версия подстановки грузила `secure_kernel.bin` в то же окно 0x40000, что и
вторую стадию, — и CMeP уходил в никуда: **2 693 708 неотображённых обращений**,
PC = 0x00F23494. Причина видна в первых словах образа: это таблица векторов с
**абсолютными** переходами в приватное окно CMeP:

```
+0x000: jmp 0x800100
+0x004: reti
+0x008: jmp 0x80028C
+0x00C: jmp 0x8002A6
+0x014: jmp 0x80037A
```

`0x800000` — это уже существующий регион `CMeP.Private` (2 МиБ, `map 0x800000`
подтверждает). После правки (`board::kCmepSecureKernelBase = 0x00800000`) тот же
прогон даёт **1** неотображённое обращение и 18 727 MMIO-доступов: secure kernel
действительно исполняется (~78 тысяч инструкций).

### 40.3 Рукопожатие с ARM и точка отказа (0x802F)

Secure kernel начинается с обмена через ящики (дизассемблер, 0x8003E6…0x800478):

```
8003EA  bsr 0x801d5a
8003EE  bnei $0,0x1,0x800434
8003F2  $5 = 0xE0000010 ; $3 = -1 ; sw $3,($5)   ; ARM->CMeP = 0xFFFFFFFF
8003FE  bsr 0x8018b2 ; $8 = $0                   ; <-- разбор ответа
800404  $1 = 0x101 ; bsr 0x8003bc                ; статус 0x101 в 0xE0000000
800430  bnei $8,0x1,0x800458                     ; $8 != 1 -> ошибка
800458  $1 = 0x802F ; bra 0x800472 ; bsr 0x8003bc ; статус 0x802F
8000F6  sleep ; 8000F8 jmp 0x8000F6              ; «всё, жду прерывания»
```

Наш прогон в логе видит ровно эту последовательность: статусы **0x9 → 0x101 →
0x802F**, затем `sleep`. То есть secure kernel не проходит проверку `$8 == 1` и
уходит в свой idle-цикл; команду `0x2080 soc_release` он при этом не выдаёт
(в логе SC её нет), поэтому ARM так и не отпускается.

Что уже смоделировано с стороны ARM (наш стенд-ин для boot ROM): статус в
`0xE0000000` вычитывается (обнуляется) и в `0xE0000010` пишется 1. Этого
недостаточно — значит разбор в 0x8018B2 читает не (только) ящик, либо важен
порядок/формат ответа. Следующий шаг — разобрать 0x8018B2 до конца (там цикл с
константами 0x10/0x21/0x25 и `$8 = 0x80`) и понять, какую именно структуру он
разбирает.

| Конец второй стадии | CMeP «спит» в чужом стеке | **хук на 0x5FF00 + подстановка шага 4** |
| Стадия обычного `boot` | `cmep-second-loader` | **`cmep-secure-kernel`** |

## Раунд 41. Шаг 4 доведён до конца: ARM отпущен, KBL запущен

### 41.1 Три «мелочи», которые держали secure kernel

Разбор его стартовой проверки (0x8018B2 → 0x80564A) нашёл три несоответствия в
модели, каждое подтверждено кодом прошивки:

1. **Ответ контроллера keyring (0xE003002C).** Secure kernel сравнивает слово
   целиком с `0x10000003`:
   ```
   801A10  movh $1,0x1000       ; $1 = 0x10000000
   801A24  or3 $1,$1,0x3        ; ожидаемое = 0x10000003
   801A48  sw $10,($9)          ; запрос: индекс keyring
   801A4A  lw $10,($5)          ; ответ 0xE003002C
   801A4C  bne $10,$1,<0x800F032F>
   ```
   Первый загрузчик проверяет только младшие биты (`($12 & 3) != 3`), поэтому в
   модели ответ был `3` и проверка secure kernel падала. Введён бит 28
   «keyring valid» (`KeyringDevice::kValidBit`): ответ стал `0x10000003`.
   Проверка в логе подтверждается: в момент ошибки `$10 = 0x10000003`, `$8 = 1`.
2. **`0xE0010004`.** Второй загрузчик требует `($2 & 5) == 5` и `($2 & 8) == 0`,
   а secure kernel (0x80567C) — **ровно** `0x80000005`. Модель теперь отвечает
   `0x80000005` (обе проверки выполняются).
3. **Версия системы.** Функция 0x800FA4 читает восемь слов
   `0xE00621C0..0xE00621DC` и возвращает последнее, а вызывающий (0x80569A)
   требует `0x01040000` — то есть «прошивка 01.04.0000». В блоке strap добавлено
   это слово (и соседние, значения которых не проверяются).

После правок статусы CMeP в логе сложились в правильную последовательность:
`0x9 → 0x101 → 0x102` (успех стартовых проверок) вместо `… → 0x802F`.

### 41.2 Рукопожатие: состояние 9 и отпускание ARM

Дальше secure kernel ждёт событие: после `0x102` он ставит состояние (глобальная
переменная по `$gp - 32748`) в 3 и проверяет, не стало ли оно **9**:

```
800446  $1 = 3 ; bsr 0x801d54      ; state = 3
80044A  $1 = 0x102 ; bsr 0x8003bc  ; статус 0x102
800450  bsr 0x80247c               ; (вход обработчика прерываний)
80045E  bsr 0x801d5a ; bnei $0,0x9,0x800488   ; ждём state == 9
80046A  $1 = 10 ; bsr 0x801d54     ; state = 10
80046E  $1 = 0x106 ; bsr 0x8003bc  ; статус 0x106 (успех)
```

Состояние 9 ставит только собственный обработчик secure kernel (0x80099E, ветка
таблицы диспетчеризации прерываний 0x800B8A) — то есть на железе это
**прерывание от ящика** (ответ ARM). В нашей модели доставки прерываний в MeP нет,
поэтому ответ ARM (`0xE0000010 <- 1`) теперь сразу превращается в это событие:
машина пишет 9 по адресу `$gp - 32748` (адрес берётся из живого `$gp` ядра).

С этим шагом статусы дошли до **0x106**, а затем secure kernel уходит в свой
«done»-путь: прыжок назад в окно 0x40000. На железе это и есть момент, когда он
сообщает syscon «сбрось ARM на 0x00000000» (вики, шаг 4). Мы это сообщение тоже
подставляем: прыжок в окно 0x40000 при активном образе secure kernel превращается
в `ErnieBlock::release_soc()`.

### 41.3 Результат: обычный прогон доходит до запуска KBL

`boot` + `run` без каких-либо `stage`:

```

first loader reported SUCCESS to the ARM mailbox
CMeP handed off to the staged image at 0x40000
CMeP halted: machine hook at 0x5FF00
second loader called the first-loader service at 0x5FF00 -> restart into secure_kernel.enp
CMeP secure kernel loaded directly at 0x00800000 (31744 bytes)

ARM boot ROM consumed the CMeP status 0x101 and answered 0xE0000010 <- 1
ARM boot ROM consumed the CMeP status 0x102 and answered 0xE0000010 <- 1
ARM boot ROM consumed the CMeP status 0x106 and answered 0xE0000010 <- 1

```

То есть **вся цепочка шагов 1-4 вики проходится автоматически**, и ARM доходит до
исполнения `kernel_boot_loader` в общем прогоне (раньше это делалось только через
`stage kbl`).

### 41.4 Что осталось на стороне ARM

Прогон слайсами (`runm`, чтобы работали все четыре ядра) даёт знакомую картину
раунда 38: KBL печатает баннер и «Safe Mode : [ YES ]», а boot-ядро умирает в ABT
на `pc=0x0001610C` — страница векторов `VBAR = 0x16100` не отображена. Значит,
проблема не в отсутствии boot-контекста от CMeP, а в том, что модель **стартует
ARM сразу с адреса KBL** (0x40020000), тогда как вики говорит: secure kernel
сбрасывает ARM на **0x00000000** (scratch-буфер CMeP), где лежит переходник,
который и строит низкую карту памяти. Следующий шаг — завести ARM-овское зеркало
scratch-буфера на PA 0 и стартовать ARM с 0x00000000.

## Раунд 42. Зеркало scratch на ARM PA 0 и почему boot-контекст пустой

### 42.1 Что делает вторая стадия с ARM-контекстом

Ключевое место (вторая стадия, 0x40A86 — это `memcpy`-хелпер 0x40AEC):

```
00040A86  movh $1,0x1f00          ; приёмник = 0x1F000000 (общая SRAM)
00040A8A  movh $2,0x4000          ; источник = 0x40000000 (DRAM CMeP)
00040A8E  mov $3,256               ; 256 слов = 1 КиБ
00040A92  jmp 0x40aec             ; memcpy(dst,src,len)
...
00040852  bsr 0x40a86             ; вызов
```

то есть вторая стадия **копирует ARM-овский boot-контекст из DRAM (0x40000000) в
scratch (общая SRAM)**, а вики добавляет: «32kB scratch buffer (mirror mapped to
0x00000000 on ARM)». В нашей модели ARM-у этот буфер виден только по 0x1F000000,
поэтому добавлено зеркало: при отпускании ARM первые 32 КиБ общей SRAM
копируются в ARM-овское окно PA 0 (`Vita::mirror_cmep_scratch_to_arm`). Проверено
дампом: ARM PA 0 теперь показывает содержимое scratch.

### 42.2 Почему контекста всё равно нет

Зеркало работает, но по адресу scratch+0x100 — нули, и в DRAM 0x40000000 тоже
нули: **источник пуст**. Причина нашлась на развилке 0x40850:

```
00040596  lw $8,0x3c($sp)     ; слово «hardware info» (заполняется вызовом 0x446f2)
0004059A  srl $8,0x7
0004059C  and3 $8,$8,0x1      ; бит 7
...
00040850  beqz $8,0x40858     ; бит 0 -> сборка boot-контекста ПРОПУСКАЕТСЯ
00040852  bsr 0x40a86         ; ...иначе копируем контекст
```

Точка останова на 0x40850 в нашем прогоне: **`$8 = 0`** (рядом видно `$3 =
0xE20A0008`, `$1 = 0x49` — запись чекпоинта 0x49 в GPO, совпадает с тем, что мы
видели в логе). Само слово берётся не из регистра, а из ответа syscon: 0x446F2 →
0x44274 формирует 16-байтовый запрос (длина 16, байт-команда 1 в +0x16) и уходит
в SC/SPI-обмен (0x44246). Наш ответ на этот запрос нулевой, поэтому бит 7 = 0 и
контекст не строится.

Подстановка (в `bigmac.cpp`, отключается `ZLB_NO_SUBSTITUTION=1`): ветка 0x40850
очищается (`{0x40850, 2, "ARM boot-context gate"}`), чтобы сборка контекста
выполнялась. Данные при этом всё ещё пусты — это подтверждает, что дело не в
развилке, а в **содержимом ответа syscon** («hardware info»).

### 42.3 Что это значит для Stage 1

ARM получает управление, но:
1. его boot-контекст (то, что KBL читает как карту памяти и как базу векторов)
   пуст, поэтому KBL не создаёт отображения для VA 0x16000/0x40000 и умирает на
   первом же исключении;
2. чтобы контекст появился, нужно ответить на SC-запрос «hardware info»
   (0x446F2 → 0x44274 → 0x44246) правдоподобными данными, в которых бит 7 слова по
   `[sp+0x3c]` установлен.

Это следующая конкретная задача: разобрать формат запроса/ответа 0x44246 и
завести ответ в модели Ernie.

## Раунд 43. Что именно спрашивает вторая стадия и что она успевает построить

### 43.1 Развилка 0x40850 — это ответ SC на команду 0x0010

Уточнение к раунду 42: слово «hardware info» берётся не из произвольного запроса,
а из ответа syscon на **команду 0x0010 (get_version / wakeup factor)**:

```
00040544  $1 = $sp + 0x3c ; sw $6,0x3c($sp) ; bsr 0x446f2   ; 0x446F2: $2 = 16; jmp 0x44274
00040596  lw $8,0x3c($sp) ; srl $8,0x7 ; and3 $8,$8,0x1       ; бит 7 слова
00040850  beqz $8,0x40858                                     ; 0 -> сборка контекста не запускается
```

Наша модель отвечает на 0x0010 ровно тем, что задокументировано по вики, —
`{0x14, 0xFF}` (холодная загрузка), то есть в памяти лежит слово `0x0000FF14`,
у которого бит 7 равен нулю. Поэтому в нашем прогоне **`$8 = 0`** (подтверждено
точкой останова на 0x40850) и копирование ARM-контекста из DRAM в scratch
(0x40A86) не выполняется — работает «холодная» ветка 0x40858
(0x4112E → 0x40A4A → 0x41A64/68/6C → 0x40F5E → …), которая собирает KBL-параметр
в собственных структурах на стеке.

### 43.2 Что вторая стадия всё-таки пишет в DRAM

Трап записей в DRAM (0x40000000…0x40001000) за весь прогон даёт 4606 записей,
из них осмысленные:

| Адрес | Значение | pc |
|---|---|---|
| `+0x400..+0x407` | `21 40 05 02 23 …` | 0x48102…0x48148 |
| `+0x500..` | `F5 FF F5 FF …` (таблица листьев idstorage, 0xFFF5 = «свободно») | 0x481E2 |

то есть idstorage-структуры в DRAM строятся ✓, а область `DRAM+0x0..0x400`
(источник ARM-контекста) в нашем прогоне остаётся нулевой — её должен заполнять
кто-то ещё (в «холодной» ветке это, судя по всему, происходит позже и зависит от
данных, которых у модели нет).

### 43.3 Состояние на конец раунда

* Цепочка шагов 1-4 вики проходится автоматически: first loader → second loader →
  сервис 0x5FF00 → secure kernel (0x800000) → рукопожатие (0x9/0x101/0x102/0x106) →
  `release_soc()` → ARM запускает `kernel_boot_loader`.
* ARM видит scratch CMeP по PA 0 (зеркало, раунд 42) ✓.
* KBL по-прежнему не получает карту памяти: boot-контекст пуст, потому что его
  источник (DRAM+0) никто не заполняет.
* Ближайшие шаги: (а) разобрать «холодную» ветку 0x40858 и понять, из каких
  данных она собирает KBL-параметр; (б) при необходимости — заполнить источник
  контекста в модели (подстановка, по аналогии с остальными).

## Раунд 44. SceKblParam: раскладка найдена в вики и реализована в модели

### 44.1 Вики даёт полную структуру

Страница `wiki.henkaku.xyz/vita/KBL_Param` описывает буфер, который создаёт
вторая стадия и который читают Secure/Non-Secure Kernel BootLoader'ы:
`SceKblParam`, 0x100 или 0x200 байт, «в scratch space». Ключевые поля:

| Смещение | Поле |
|---|---|
| 0x00/0x02 | version / size (0x100 или 0x200) |
| 0x04/0x08 | текущая и минимальная версия прошивки |
| 0x20/0x30 | QA flags / boot flags |
| 0x40..0x5F | DIP switches (CP info, SDK/shell/debug/system flags) |
| 0x60/0x64 | DRAM base paddr / size |
| 0x6C | boot type indicator 1 |
| 0x90/0x94, 0x98/0x9C | paddr/size `kprx_auth_sm.self`, `prog_rvk.srvk` |
| 0xC0/0xC4 | sleep factor / wakeup factor (syscon cmd 3 / 0x10) |
| 0xD4 | hardware info (syscon cmd 5) |
| 0xFC | magic `0xCBAC03AA` |

Адрес фиксируется разделом «Fallback DIP Switches»: буфер DIP-переключателей лежит
по физическому `0x1F000080`, а это поле структуры на смещении +0x40 — значит
**SceKblParam находится по PA 0x1F000040** (внутри SPAD32K), а ARM видит его и по
PA 0x40 благодаря зеркалу scratch.

### 44.2 Что сделано в модели

1. **Контейнер второй стадии больше не занимает scratch.** Раньше он грузился в
   общую SRAM по 0x1F000000 — то есть ровно туда, где должен лежать SceKblParam
   (и где вторая стадия копирует контекст). Теперь стейджинг идёт в DRAM:
   `board::kSecondLoaderStagingDram = 0x407C0000`, почтовый ящик получает этот PA,
   first loader читает образ оттуда как обычно (проверено: цепочка проходит
   полностью).
2. **Модули ядра стейджятся в DRAM** (`kprx_auth_sm.self` → 0x40780000,
   `prog_rvk.srvk` → 0x407A0000) — как в вики («read from the eMMC SLB2 partition
   are both loaded into DRAM»), их paddr/размеры попадают в структуру.
3. **`Vita::build_kbl_param()`** пишет 0x100-байтовую структуру по
   `board::kKblParamBase = 0x1F000040` по раскладке вики: version/size, версии
   прошивки 0x01040000, release-режимные DIP switches, DRAM 0x40000000 + размер
   смоделированного окна, boot type = product mode, paddr'ы модулей, session id,
   sleep/wakeup factor, hardware info `0x00406000` (IRS-002 — ровно то, что
   отвечает наша модель syscon на команду 5), power info, ревизия загрузчика и
   magic `0xCBAC03AA`. Порядок: сначала структура, потом зеркало scratch на PA 0 —
   чтобы запись была видна и по низкому адресу.

### 44.3 Проверка: KBL действительно читает структуру

Трап чтений ARM по PA 0x0..0x200 за прогон (`ZLB_RTRAP=0-200`):

```
off=1C4 r4 = 0x0  pc=4002028C      ; KBL читает поле внутри структуры
off=100 r4 = 0x60 pc=400376E4 ...  ; циклически читает param+0xC0 (sleep factor = 0x60)
```

то есть boot loader **потребляет** SceKblParam (значение 0x60 — это ровно наш
`sleep factor`), и раскладка/зеркало совпали. Это первый случай, когда ARM-сторона
читает данные, которые модель положила по документированному адресу.

### 44.4 Что всё ещё не решено

ARM по-прежнему падает на `VBAR = 0x16100` (страница векторов не отображена):
KBL строит собственные таблицы (TTBR0 → L1 0x40108000, L2 0x80200000), отображает
только 8 страниц VA 0..0x7FFF и явно помечает остальное как fault, а карту памяти,
которая должна была бы покрыть 0x16000/0x40000, в модели по-прежнему никто не
передаёт (в «холодной» ветке второй стадии 0x40858 её сборка зависит от данных,
которых у нас нет). Следующий шаг — разобрать 0x40858/0x40F5E или собрать карту
памяти отдельной подстановкой, а также проверить гипотезу «ARM стартует с
0x00000000», как сказано в вики.

0x4001FD00 0x100   SceKblParam (magic not set)
0x40020000 0x370C8 SKBL segment 0
0x40073570 0x200   SceKblParam
```

Наш KBL (FW ≥0.996) грузится по 0x40020000 ✓, но **модель стартует ARM прямо с
0x40020000**, минуя reset-vector по 0x40000000 — а именно он на железе и готовит
окружение (там же лежат stage-адреса модулей). Это следующий шаг.

### 45.2 Что сделано в модели

* **Окна ARM приведены к вики**: PA 0x0 — алиас ScePower scratchpad (0x1F000000),
  PA 0x40000-0x5FFFF — зеркало CMeP SRAM (0x00800000). Реализовано одной
  backing-store парой (`cmep_priv_` 2 МиБ + alias на ARM), плюс `arm_bootrom`
  стал алиасом `shared_sram_`.
  *Попутно:* `Bus::add_ram_alias` принимает **(base, size)**, а `add_ram` —
  **(size, base)**; перепутанный порядок сначала сломал самотесты (окно 8 МиБ
  поверх 2 МиБ вектора), это поймано и исправлено, базовая линия 210/15/22 цела.
* **SceKblParam пишется в две копии** по вики: scratchpad 0x1F000040 (с magic) и
  secure DRAM 0x4001FD00 (без magic — «SceKblParam with magic not set»).
* **Модули стейджятся по адресам вики**: `kprx_auth_sm.self` → 0x40000500,
  `prog_rvk.srvk` → 0x40009B00 (было 0x40780000/0x407A0000).

### 45.3 Что осталось (следующий раунд)

1. **Смоделировать reset-vector 0x40000000** (0xC0 байт), который на железе
   пишет second_loader: это стаб, который задаёт начальные таблицы страниц,
   стеки и прыгает в SKBL 0x40020000. Без него KBL сам строит таблицы
   (VA 0..0x7FFF → 32 КиБ копия scratch) и падает на векторе 0x16100.
2. После этого — старт ARM с 0x40000000 и проверка, доходит ли KBL до NSKBL.

## Раунд 46. Окно DRAM 512 МиБ и проверка гипотез о причине падения

### 46.1 Окно DRAM приведено к вики

`Physical_Memory` даёт строку «0x40000000 | 0x20000000 | 512MiB DRAM», а раскладка
NSKBL кладёт сжатый NSKBL на 0x50000000 и распакованный на 0x51000000, модули ядра —
на 0x52000000+. В модели окно было 128 МиБ (0x08000000) — то есть половина
адресов, которыми пользуется цепочка, физически не существовала. Теперь
`kermit::kScuSize = 0x20000000` (512 МиБ): это окно видят и ARM, и CMeP, а
отдельный «KBL staging window 0x50000000» убран (он попадал внутрь DRAM).
SceKblParam теперь сообщает `dram = 0x40000000 + 0x20000000` — ровно как в вики.

Тесты остались на базовой линии (210 / 15 / 22), прогон самотестов ~7 с.

### 46.2 Что проверено и что исключено

* **Reset-vector как отдельный blob**: поиск ARM-кода (в том числе `mcr/mrc p15`,
  `ldr pc,[pc,#imm]`) в образах second_loader, secure_kernel и KBL не дал ничего —
  то есть стаб не лежит в дампах готовым куском, его генерирует вторая стадия
  (или он в неотданном ROM).
* **Вектор на PA 0** (`18 F0 9F E5` ×8) пишет не вторая стадия, а сам KBL: это его
  таблица векторов для **non-secure** мира (`VBAR_NS = 0` в дампе CP15), тогда как
  secure-вектор он ставит в 0x16100.
* **512 МиБ DRAM** на падение не влияет: `arm0` по-прежнему умирает на
  `pc=0x0001610C` (ABT, `VBAR=0x16100`, `IFSR=7`, `IFAR=0x1610C`).
* Страница векторов в таблицах KBL действительно не отображена: TTBR0 → L1
  0x40108000, `L1[0] = 0x80200181` (coarse table), L2 0x80200000 содержит только
  8 записей (VA 0..0x7FFF → PA 0x40118000), `L2[0x16] = 0` и `L2[0x40] = 0`.
  При этом KBL **сам обнуляет** эти 0x400 байт перед записью (трап: записи нулей
  в 0x80200000-0x802003FF, pc=0x4003AB0E/0x4003AB12), поэтому предзаполнить
  таблицы снаружи нельзя.
* Данные, из которых KBL считает адрес падения, — его собственные структуры в
  скопированном scratch (VA 0x51C0: `2B 50 80 40 | 00 00 00 00 | 02 00 01 00 |
  ... | 00000040 | 00300000`), то есть причина, скорее всего, в том, что *входные*
  значения этих структур у нас не такие, как на железе.

### 46.3 Следующие шаги

1. Реализовать **reset-vector 0x40000000** как подстановку: минимальный ARM-стаб
   (стек на ядро по вики — 0x400ExC00, `r0` = указатель на SceKblParam, прыжок в
   SKBL 0x40020000) и, если нужно, начальная карта низких VA.
2. Либо — воспроизвести **входные данные** структур KBL (то, что в scratch должно
   лежать по 0x51C0 и далее): это то, что вторая стадия собирает из Syscon/SMI и
   чего у модели пока нет.
3. Проверить гипотезу «модули лежат в SRAM CMeP, а не в DRAM»: вики говорит, что
   128 КиБ SRAM CMeP хранит second_loader, secure_kernel **и Secure Modules**, и
   ARM видит её по VA 0x40000 — а мы кладём модули в DRAM по 0x40000500/0x40009B00.

### 46.4 Итог раунда

| Метрика | Было | Стало |
|---|---|---|
| Окно DRAM | 128 МиБ | **512 МиБ (вики) — видят ARM и CMeP** |
| `dram` в SceKblParam | 0x08000000 | **0x20000000** |
| Окно 0x50000000 | отдельный блок 4 МиБ | **внутри DRAM (там NSKBL по вики)** |

## Раунд 47. Точная цепочка отказа KBL и две правки инструментов

Повод: запрос «дизассемблируй и изучи second_loader» + «посмотри Copetti про Venezia».
Venezia/Copetti разобран отдельно (`docs/VENEZIA.md`), здесь — то, что дал разбор второй
стадии и повторный заход в KBL уже с нормальным инструментарием.

### 47.1 Две правки инструментов (обе нужны были, чтобы вообще увидеть причину)

1. **Дизассемблер ARM: LDREX/STREX.** Инструкции `LDREX/STREX/LDREXB/…/LDREXH/STREXH`
   живут в том же пространстве, что и умножения (биты [7:4] = 1001), и различаются
   битами [27:20] (8/9 — слово, C/D — байт, E/F — полуслово). Дизассемблер проверял
   умножения раньше, поэтому атомарные хелперы KBL печатались как бессмыслица:

   ```
   4003A41C  9F 2F F0 E1   smlals r2, r0, r15, r15     ← было
   4003A41C  9F 2F F0 E1   ldrexh r2, [r0]             ← стало
   4003A424  93 CF E0 E1   strexh r12, r3, [r0]
   ```

   Из-за этого «мусорные» адреса (0x4003A3EC, 0x4003A41C, 0x4003A424) выглядели как
   исполнение данных. На самом деле это `__sync`-хелперы: запись u16 и
   `fetch_sub` u8/u16 — именно ими KBL уменьшает счётчик задания.
2. **Команда отладчика `faults [all]`.** Печатает кольцо отказов MMU по каждому ядру:
   `VA`, `pc`, `read/write/fetch`, вид отказа, дескрипторы L1/L2, домен и счётчик
   повторов. Раньше единственным следом отказа был вектор, в который ядро в итоге
   попало, — а в этой истории как раз важно, **какой** отказ был первым.

### 47.2 Что происходит на самом деле (4 ядра, `runm`)

Порядок инициализации KBL (лог `--log debug`):

| pc | что |
|---|---|
| `0x4002003C`, `0x4002012C` | SCTLR = 0 (MMU выключена) |
| `0x400201A8` | SCR = 4 → **secure world** |
| `0x40020B82` | VBAR(secure) = 0x0 (там же лежит копия таблицы векторов) |
| `0x40020C18`…`0x40020C36` | TTBR0 = 0x4010804A, TTBR1 = 0x4010C04A, TTBCR = 2, DACR = 0x55555555 |
| `0x40020CD0` | **VBAR = 0x16100** (`mcr p15,0,r3,c12,c0` — именно secure-банк) |
| `0x4003A80E`…`0x4003AE08` | сборка таблиц страниц |
| `0x40039FC4` | SCTLR = 0x20005805 → **MMU включена** |

Таблицы, которые он строит (трап записей):

* L1 @ PA 0x40108000 — 256 записей `0x1E0` (fault) и ровно одна рабочая:
  `L1[0] = 0x80200181` (coarse, L2 @ PA 0x80200000);
* L2 @ PA 0x80200000 — сначала 256 нулей (`pc=0x4003AB0E/0x4003AB12`), затем 8 записей
  `0x4011845F…0x4011F45F`: **VA 0x0000-0x7FFF → PA 0x40118000** (копия низких 32 КиБ).
  Больше не отображено ничего — ни `0x16000` (векторы!), ни `0x40000`.

Цепочка отказа (вывод `faults all`, ядро arm0):

```
#0 VA=0x00008000 pc=0x4003AFA8 read  page translation fault   L2[0x08]=0
#1 VA=0x40100000 pc=0x4003AFA8 read  section translation fault L1[0x401]=0x1E0
#2 VA=0x47000000 pc=0x4003AFA8 read  section translation fault L1[0x470]=0x1E0
#3 VA=0xE0000000 pc=0x4003AF4C write permission fault          L1[0xE00]=0xE0010592
#4 VA=0x00040000 pc=0x400321B6 read  page translation fault   L2[0x40]=0
#5 VA=0x00016110 pc=0x00016110 fetch page translation fault   L2[0x16]=0
#6 VA=0x0001610C pc=0x0001610C fetch page translation fault   x8 (exception loop)
```

* `#0`-`#3` — это не исключения, а **зонды трансляции** (V2P через PAR, `pc=0x4003AFA8`):
  KBL проверяет, что уже отображено, чтобы потом «пропатчить секцию».
* `#4` — первое настоящее исключение: `ldr.w r2,[r12]` при `r12 = 0x40000`
  (`pc=0x400321B6`). Вокруг видно, что структура по VA 0x51C0 (копия в scratch,
  PA 0x4011D1C0) содержит таблицу регионов `40000000 00300000 | 00040000 …`, и KBL
  правит структуру по физическому адресу 0x40000 — то есть ждёт **identity-отображения
  низких VA**, которого его собственная карта не даёт.
* `#5`/`#6` — data abort уходит на `VBAR+0x10 = 0x16110`, эта страница не отображена →
  prefetch abort на `0x1610C` → снова не отображена → `exception loop`, ядро встаёт
  (arm1-3 при этом живы, они за барьером четырёх ядер).

**Эксперимент, подтверждающий диагноз.** Если доручить модели ровно то, чего не хватает
(через `poke`, пока KBL стоит на `0x400321B6`):

```
core arm0
poke 0x80200058 0x0000065E 32     ; VA 0x16000 -> PA 0x0   (страница векторов)
poke 0x80200100 0x0004065E 32     ; VA 0x40000 -> PA 0x40000
runm 100000
```

падение на 0x40000 исчезает, обработчик по `0x16100` **исполняется и возвращается**
(`LR=0x400321C2`), и ядро доходит до `0x161A0`, где спотыкается уже о содержимое
подставленной страницы (`undefined instruction 0xFFFFFFFF`). То есть механизм понятен
целиком: не хватает (а) отображений низких VA и (б) содержимого страницы векторов
PA 0x16100 — и то и другое готовит **предыдущая** ступень (ARM-стаб второй стадии /
boot ROM), которую мы пока не моделируем.

### 47.3 Методические заметки

* `run` (одно ядро) KBL не проходит: arm1-3 остаются на `0x40020000`, а ядро 0 крутится
  в WFE-цикле `0x4003B3D6`, ожидая счётчик по `0x4005C008`, который остальные ядра
  уменьшают атомарным `fetch_sub` (`0x4003A41C`). Нужен `runm` (срезы всей машины).
* KBL пишет в регистры, которых у нас нет: `0xE6000090/94`, `0xEC570078/7C`,
  `0xEC560880…8C`, `0xEC370078`, `0xEC070078`, `0xEC170078`, `0xEC060480…8C`
  (`pc=0x400209E4…0x40020A36`) — окно «EC» (Pervasive/DMAC) в адресном пространстве ARM
  отсутствует, чтения возвращают 0.

### 47.4 Следующие шаги

1. Подстановка **reset-vector 0x40000000** (см. 46.3) должна включать страницу векторов
   по PA 0x16100 и отображение низких VA (0x16000, 0x40000) — иначе KBL обречён.
2. Проверить окно `0x0-0x3FFFF` как ARM boot window: у нас алиас только 64 КиБ, поэтому
   запись векторов по 0x16100 в модель вообще не попадает.
3. Добавить окно `0xECxxxxxx` (Pervasive/DMAC) хотя бы как регистровый файл.

|---|---|---|

## Раунд 48. Низкое окно ARM подано — KBL идёт на 460 млн инструкций

Вывод раунда 47 («нужны отображения низких VA и содержимое страницы векторов») реализован,
и это сдвинуло загрузку с 1.8 млн инструкций до **460 млн**: ядро 0 больше не умирает на
первом исключении, а проходит инициализацию и доходит до *ассерта* в собственной логике.

### 48.1 Что добавлено в модель

1. **Страница векторов PA 0x16100.** Сегмент KBL с `vaddr = 0` (0xC0 байт: восемь
   `ldr pc,[pc,#0x18]` + таблица указателей, vector[4] → 0x40020394 — обработчик data
   abort) ставится по адресу, на который KBL наводит `VBAR` (значение 0x16100 берётся
   из его собственной таблицы платформы). Второй загрузчик на железе — тот, кто это
   делает («SKBL Reset Vector»); у нас — подстановка в `start_arm_kernel_boot_loader`,
   видна в логе как `vector page staged at PA 0x00016100`.
2. **Окно ARM `0x0-0x3FFFF`.** Раньше алиас scratchpad был 64 КиБ, из-за чего
   PA 0x16100 не существовал вовсе. Вики (`Physical_Memory`): «0x00000000 0x40000 ARM
   Boot. By default, alias of physical address 0x1F000000» → `kArmBootWindowSize = 0x40000`.
3. **Отображение низкого окна (подстановка).** Хук отказов MMU
   (`ArmCore::fault_hook` → `Vita::satisfy_arm_boot_fault`): при translation fault для
   `VA < 1 МиБ` модель дописывает в *собственную* L2 ядра (TTBR0 → L1[0] → L2) запись
   `VA → PA = VA` (атрибуты берутся из соседней записи KBL) и повторяет доступ.
   Это то, что давало наследуемое отображение до KBL. Отключается
   `ZLB_NO_SUBSTITUTION=1` — тогда воспроизводится прежнее падение (`ABT`,
   `pc=0x0001610C`, те же 6 отказов).
4. **Отладчик: точные точки останова в `runm`.** Срез машины выполняет
   `budget().arm = 256` инструкций на ядро, а точки останова проверялись только на
   границе среза — точка внутри среза молча пропускалась (именно поэтому bp на
   0x40035966 «не срабатывал», а на 0x4003596E срабатывал случайно). Теперь при
   установленных bp/wp `run_machine` опускает бюджет ARM до 1.
5. **Отладчик: история PC и в `runm`.** `history on` + `history arm 90` показывает
   цепочку инструкций, которая привела ядро в текущее состояние (раньше история
   писалась только в `run`/`step`).

### 48.2 Новая точка останова: ассерт KBL

Цепочка (по `history`, точные адреса):

```
40034A00  push.w {r4-r11, r14}          ; функция-инициализатор пула/списка
40034A0C  ldr  r2, [r0, #36]            ; r2 = obj->field_0x24
40034A12  ldr  r3, [r6]                 ; r3 = global[0x400B2974]
40034A16  cmp  r2, r3
40034A18  bne.w 0x4003596E              ; ← проверка не прошла
4003596E  bl   0x4003B724               ; «стоп»-заглушка: 0x4003B724 = `b .` (вечный цикл)
```

В момент останова: `r0 = r2 = r5 = 0`, `r3 = 0x600BF348`, `r4 = 0`, `LR = 0x40035973`
(возврат из `bl 0x4003B724`), стек — `0x40060F20`, в нём цепочка возвратов
`0x4003314B → 0x40033AD1 → 0x40031893 → …`. То есть KBL получил **NULL** там, где ждал
объект из своего пула, и это первое место, где он больше не может продолжать.

Похоже на то, что пул/список строится из **boot-контекста**, который в модели пуст
(DRAM 0x40000000 — нули, см. §3.1 STATUS): у KBL есть собственные значения по умолчанию
(таблица регионов в scratch по VA 0x51C0: `40000000 00300000 | 00040000 …`), но
распределитель остаётся без памяти. Это следующий предмет разбора.

### 48.3 Найдена коллизия: MPCore-периферия и DRAM на 0x40000000

Вики кладёт «SKBL Reset Vector (ARM entry!)» — те самые 0xC0 байт — по PA `0x40000000`,
и KBL слинкован на `0x40020000` (secure DRAM). Но в модели блок периферии Cortex-A9
(SCU/GT/PT/GIC, взятые из примера карты TRM) стоит по `0x40000000+`, а
`Bus::find_device` предпочитает устройство RAM — поэтому:

* запись reset-вектора в `0x40000000` уходит в регистр `SCU_CONTROL`
  (трап показывает её как запись в `arm_priv`, но `map 0x40000000` = `device=Kermit.SCU`),
  и чтение `[0x40000020]` возвращает не указатель `0x40020000`, а регистр (0);
* попадание в KBL после этого получается «по случайности»: `PC = 0` → таблица векторов
  в окне PA 0 → `0x40020000`.

Перенос блока (`kermit::kMpcoreBase = 0xE1000000`) был сделан и **откачен**: он валит
8 самотестов (210/15/22 → 210/23/39), потому что тесты завязаны на текущее размещение.
Пока коллизия не разведена, reset-вектор в DRAM не ставится, а ARM стартует прямо с
`0x40020000` (что и даёт первый указатель reset-вектора).

### 48.4 Следующие шаги

1. **Boot-контекст**: заполнить то, что KBL читает в DRAM 0x40000000+ (и/или SRAM
   CMeP), — по ассерту 0x40034A18 и по трапу чтений видно, какие поля ему нужны.
2. Развести MPCore-периферию и DRAM (перенос + правка тестов), после чего вернуть
   полноценный вход через reset-вектор `0x40000000`.
3. Окно `0xECxxxxxx` (Pervasive/DMAC), в которое KBL пишет/читает (`pc=0x400209E4…`).

### 48.6 Эксперимент с правилом отображения низкого окна

Куда именно смотрит VA `0x40000`, решает подстановка; правило выбирается
переменной `ZLB_ARM_LOW_MAP` (`identity` по умолчанию, `dram`, `dram-abs`).
Результаты (прогон `runm 400000`, все прочие условия одинаковые):

| Правило | VA 0x40000 → | Итог |
|---|---|---|
| `identity` | PA 0x40000 (MeP-окно, вики) | KBL читает первое слово SRAM CMeP (там наш staged secure kernel, `0x8002DB08`) как заголовок chunk'а → дескриптор кучи разрушен → ассерт `0x40034A18` → `b .` |
| `dram` | PA 0x40000000 + (VA−0x40000) | ассерта нет, ядро живёт, но **куча ложится поверх собственного образа KBL** (1 МиБ от 0x40000000 накрывает код с 0x40020000) и аллокатор крутится вечно |
| `dram-abs` | PA 0x40000000 + VA | как `identity` (ассерт) |

Круг в аллокаторе точный (bp + `history`, бюджет ARM = 1):

```
40031E8A  cmp  r7, #0
40031E8C  beq  0x40031EE2
40031EE2  ldr  r4, [r4, #12]   ; r4 = 0 -> читает [0xC]
40031EE4  b    0x40031E90
40031E90  cmp  r4, r0          ; r4 = 0 != 0x51E8
40031E92  beq  0x40031ED0
40031E94  ldr  r6, [r4, #4]    ; [0x4]
40031E96  cmp  r1, r6          ; запрошен 1 МиБ против 0
40031E98  beq  0x40031EA0
40031E9A  bls  0x40031EEE
40031E9C  cmp  r2, #0x14
40031E9E  bne  0x40031E8A      ; и так по кругу
```

То есть список свободных блоков не кольцевой (голова bin'а по VA `0x51E8` ссылается
на 0, а не на себя), а дескриптор кучи по VA `0x51C0` **пуст** (нули). Значит
`malloc`-инициализация KBL не получила свои входные данные: распределитель ждёт
описание региона/первого свободного chunk'а (та самая таблица в scratch по VA 0x51C0:
`40000000 00300000 | 00040000 …`). Это и есть « boot-контекст», которого не хватает —
следующий шаг разбора (вход в `malloc`-инициализацию — `0x40032108`, разбор региона —
`0x40031E64…0x40031FB0`, вызов через мьютекс `0x4003A1B0`).

### 48.9 Главная находка: VA 0x40000 — это СВОЁ окно KBL, а не окно MeP

В объекте KBL (0x400B2B30) лежит запись окна:

```
0x400B2B30+0x158 = 0x40118000   (физический адрес копии низкого окна)
0x400B2B30+0x15C = 0x00040000   (её виртуальный адрес)
0x400B2B30+0x160 = 0x00008000   (размер, 32 КиБ)
0x400B2B30+0x164 = 0x00008000   (размер)
```

То есть KBL держит «физическое 0x40118000 ↔ виртуальное 0x40000, 32 КиБ» —
а 0x40118000 это ровно та копия низкого окна, которую он же и отобразил на
VA 0x0000-0x7FFF. Значит VA 0x40000 должно указывать **на своё окно**, а не на
окно MeP (как в вики) и не на DRAM.

Правило `window` (теперь по умолчанию, `ZLB_ARM_LOW_MAP=identity|dram|dram-abs`
возвращают альтернативы) даёт:

| Правило | Где оказывается ядро 0 | Поведение |
|---|---|---|
| `identity` | 0x4003B724 | заглушка `b .` (ассерт 0x40034A18) |
| `dram` | 0x40031E8A | вечный обход списка свободных блоков аллокатора |
| `dram-abs` | 0x4003B724 | как `identity` |
| **`window`** | **0x4002BD1C → 0x4002B054 → 0x4002B04C** | **живёт, зовёт функции, доходит до цикла повторных вызовов `0x4002B048`** |

С `window` ядро больше не падает и не крутится в аллокаторе: оно проходит дальше
по своей инициализации и упирается в повторяющийся вызов функции `0x4002B048`
(«subs r6,r0,#0 / tst r6,#1 → ошибка 0x80024501» — то есть функция возвращает
ошибку, и её зовут снова). Консоль по-прежнему ограничена баннером и
`memory[ Safe Mode : [ YES ]`.

Следующий шаг: разобрать, чего ждёт цикл у `0x4002B048` (похоже на повторную
инициализацию устройства/рукопожатие — ср. неотображённое окно `0xECxxxxxx`,
куда KBL пишет в `pc=0x400209E4…0x40020A36`).

### 48.11 Где именно стоит ядро 0 с правилом `window`

Точные данные (bp на 0x4002B048 + `history`, бюджет ARM = 1):

* вызов идёт из обёртки `0x4002B6BC`: `if (handle < 0 || (handle & 1) == 0 ||
  (handle & 0x40000000)) return 0x80024501; else f(handle)`; сам вызов —
  `bl 0x4002B048` в `0x4002B6E2`, возврат `LR = 0x4002B6E7`;
* аргументы на входе: `r0 = 0x00010009` (корректный handle!), `r1 = 0x5C00`,
  `r3 = 0x5C40` (указатель в scratch), `r6 = 0x4900` (контекст);
* цепочка до вызова: `0x4002A892` (обход списка) → `0x4002E506` →
  `0x40030EB8…0x40030EDC` → `0x4002B6BC` → `0x4002B048`;
* сам «обход» — это `0x4002A892: ldr r3,[r3]; cmp r1,r3; mov r2,r3;
  beq 0x4002A8B0; cmp r4,r3; mov r5,r3; mov r0,r3; bne 0x4002A892`, то есть
  проход по односвязному списку до головы `r1`. При прогоне без точек останова
  (`history` с шагом 256) PC **всегда** 0x4002B054 — значит путь между выборками
  строго периодичен: ядро крутится в этом обходе, список **циклический** и
  голова в нём не встречается.

Статические ссылки (мой новый скрипт `_scratch/find_callers.py` — декодирует
Thumb-2 BL/BLX по всему образу):

* `0x4002B048` — прямых вызовов нет (зовут через указатель/обёртку);
* `0x40032C44` (строитель региона) — один прямой вызов: `0x4002C5CE`;
* заглушка-паника `0x4003B724` — **9 вызывающих**: 0x40034758, 0x4003596E,
  0x400359FC, 0x40035D40, 0x40035E58, 0x40035EBA, 0x40035EC4, 0x40035ECE,
  0x400360B2 (все — ветки ассертов).

Следующий шаг: понять, откуда KBL берёт этот список (похоже, он строится из
содержимого низкого окна — копии первых 32 КиБ, которую KBL делает в
PA 0x40118000; в модели там в основном нули), и чем он должен заканчиваться.

### 48.13 Что именно делает цикл у `0x4002BD16` (пошагово)

Приём: чтобы получить пошаговую историю *без* остановки машины, ставится «фальшивая»
точка останова в заведомо неисполняемый адрес (`bp arm 0x40010000`) — отладчик из-за
наличия bp опускает бюджет ARM до 1, а сработать такая точка не может. Так снят
точный цикл (толчок в 1.2 млн срезов быстрым бюджетом, затем 3000 инструкций с
бюджетом 1):

```
4002BD16  subs r0, r5, #2          ; id = r5-2
4002BD18  sub.w r3, r0, #0x10001   ; r3 = id - 0x10001
4002BD1C  cmp  r3, #0x14
4002BD1E  bhi  0x4002BD46          ; id вне [0x10001..0x10015] -> «неизвестный»
4002BD20  ldrd r15, r0, [r15], #12 ; иначе — переход по таблице обработчиков (11 записей)
...
4002BD46  mov  r1, r4              ; r4 = указатель на строку имени (0x4005A854/…)
4002BD48  bl   0x4002B4FC          ; f(id, name) -> 0x4002B048 -> 0x4002ADF4
4002BD4C  movs r0, #0x2F ; movt r0, #1     ; предел 0x1002F
4002BD52  cmp  r5, r0
4002BD54  ble  0x4002BD6C
4002BD6C  adds r5, #2
4002BD6E  b    0x4002BD16
```

То есть это **регистрация «объектов» по диапазону ID** `[0x10001..0x1002F]` шагом 2 с
таблицей обработчиков на 11 записей: вход в функцию `0x4002BD00` ставит `r5 = 0x10003`
и первый проход идёт через таблицу (`4002BD20`), а дальше по общему коду
`0x4002BD46` каждый ID зовётся `f(id, name)`.

Сам `f` — обёртка `0x4002B4FC` → `0x4002B048` (проверка handle: `id >= 0`,
`id & 1`, `id & 0x40000000`) → тело `0x4002ADF4`, где ключом поиска служит
**бит 1 идентификатора** (`ubfx r1,r1,#1,#1`) в таблице из двух слотов
(`bl 0x40031A5C`), а неудача возвращает `0x80024501`. В нашем прогоне регистрация
каждого ID возвращает `0x80024501` — то есть **объектов, которые KBL пытается
зарегистрировать, в модели нет**; цикл крутится до исчерпания диапазона и
повторяется вызывающим.

Следующий шаг: понять, откуда должны взяться эти объекты (id + имя) — это снова
вопрос содержимого boot-контекста (в модели низкое окно почти целиком нулевое:
`VA 0xA140`, `VA 0x4000` и т. п. — нули).

### 48.15 Boot-контекст: кто его строит, что в нём и чего не хватает

Трапы чтений/записей по копии контекста (PA `0x4011C900`, то есть VA `0x4900`)
дают точную картину.

**Кто строит.** Контекст (объект 0xEC байт) создаёт сам KBL:

```
4002C7D8  movs r0, #0xEC
4002C7DE  bl   0x400360E4        ; выделить 0xEC байт из пула
4002C7EC  str  r3, [r4]          ; *0x400B2924 = объект (VA 0x4900)
4002C7F4  ldr  r0, [r5, #8]      ; r5 = 0x400B2B30 (boot-info KBL)
4002C7F6  str  r0, [r6, #4]      ; ctx+0x04 = счётчик записей
4002C80A  str  r3, [r6, #8]      ; ctx+0x08 = первая запись: база
4002C814  str  r7, [r6, #12]     ; ctx+0x0C = первая запись: размер
   (далее — копирование пар {base,size} из boot-info в контекст)
```

**Откуда регион.** База и размер DRAM — **жёсткие константы самого KBL**:

```
4002D0D0  mov.w r6, #0x40000000  ; база DRAM
4002D3E6  mov.w r1, #0x300000    ; 3 МиБ
400213EC  str r2, [r0, #8]       ; boot-info+0x08 = 1
400213EE  str r6, [r0, #12]      ; boot-info+0x0C = 0x40000000
400213F0  str r1, [r0, #16]      ; boot-info+0x10 = 0x00300000
```

(адреса в листинге: `0x400213D0`, `0x400213E6`, `0x400213EC..F0`) — то есть регион кучи
`{0x40000000, 3 МиБ}` не зависит от SceKblParam, это решение KBL.

**Что KBL пишет в контекст сам** (трап записей): `+0x04 = 1`, `+0x08/+0x0C` — регион,
`+0x60, +0x68, +0x70, +0x78, +0x80 = 0xFFFFFFFF` (пять списков-сентинелов),
`+0x3C..+0x58 = 0`, `+0xB8 = 0x10`, `+0xBC = 0x4A00`, `+0xC0 = 0x4BC0`.

**Чего не хватает.** Поле `+0x8C` — указатель на «менеджер объектов» — в нашем прогоне
**не записывается никем, кроме инициализации, где его обнуляют** (`pc=0x4002C89A`).
Именно его читает `0x4002B07E` (`r11 = [*0x400B2924 + 0x8C]`) перед поиском в хеш-таблице,
поэтому все регистрации из цикла §48.13 дают `0x80024501`.

Ни один статический вызов не ведёт ни в `0x4002BD00` (цикл регистрации), ни в
`0x4002C7D8` (сборка контекста), ни в `0x4002C7C0` — шаги инициализации вызываются
**через таблицы указателей**, то есть порядок/состав шагов задаётся данными (кандидат —
тот же boot-контекст).

**Про запись окна.** В объекте KBL лежит `{+0x158 = 0x40118000, +0x15C = 0x00040000,
+0x160 = 0x8000, +0x164 = 0x8000}`; это одинаково читается и как «виртуальное 0x40000 ↔
физическое 0x40118000, 32 КиБ», и как **описание копии**: «32 КиБ из PA 0x40000 (окно MeP!)
в PA 0x40118000». Проверка трапом чтений PA 0x40000-0x48000 показала всего несколько
обращений (все — аллокатор), массового копирования 32 КиБ нет, поэтому окно KBL
заполняет сам (рабочая область), а не копирует из SRAM CMeP.

### 48.17 CMeP просыпается на рукопожатие + найден источник boot-контекста

**1. Почему CMeP засыпал.** Ожидание в secure kernel — это цикл

```
00800454  ei
0080045E  bsr 0x801D5A            ; прочитать состояние
00800462  bnei $0, 0x9, 0x800488  ; не 9 -> спать
00800466  di ... (продолжение)
00800488  sleep                    ; ждать ответа
0080048A  bra 0x80045E             ; после пробуждения — снова проверка
```

Подстановка уже клала «9» в переменную состояния (`$gp-32748`), но ядро в этот
момент **спало** — ответ записывался, а прочитать его было некому. Теперь модель
будит CMeP (`cmep_->halted = false`, сообщение «woke the CMeP for the handshake
reply»), и это заменяет прерывание, которого у MeP пока нет.

Результат: рукопожатия `0x9 → 0x101 → (sleep → пробуждение) → 0x102 → 0x106`
проходят до конца, а CMeP **отрабатывает 117 083 инструкции вместо 17 476** и
только потом уходит в «done»-прыжок `0x40002`.

**2. Откуда берётся ARM boot-контекст.** Вторая стадия (MeP):

```
0040A76  lw   $0, (0x4000A0)          ; читает слово из DRAM 0x400000A0
0040A78  movh $3, 0x61ce ; or3 $3,0x6649
0040A82  sltu3 $0,$0,0x1              ; проверка: подпись 0x61CE6649 на месте?
0040A86  movh $1, 0x1f00              ; назначение — SPAD 0x1F000000+
0040A8A  movh $2, 0x4000              ; источник — DRAM 0x40000000+
0040A8E  mov  $3, 256                 ; 256 байт
0040A92  jmp  0x40AEC                 ; копирование
```

То есть **подпись `0x61CE6649` по DRAM+0xA0** — признак готового ARM boot-контекста,
который вторая стадия копирует из DRAM в SPAD (её же memset мы видим в трапах:
`0x1F000100…` и `0x40000500…`). Подпись в наш прогон **никто не пишет** (`0x61CE6649`
встречается в образе второй стадии ровно один раз — в этой проверке), а значит
контекст должен строить **secure kernel** — и он его не строит, потому что данные
для него берутся из syscon/SMI-ответов, которых у модели нет (см. §3.4 STATUS).
В трапах записей CMeP в DRAM 0x40000000-0x40001000 нет ничего, кроме memset нулей
по `+0x500`.

**3. Производительность.** Сборка и так `Release` (`/O2 /Ob2` в CMakeCache).
Сделаны две оптимизации: `BusContext::core` стал `const char*` (был `std::string`,
копия на каждое обращение к памяти) и `ArmMmu::translate` больше не копирует
`WalkRecord` при успешной трансляции (запись включается `ZLB_MMU_WALKS=1`; кольцо
отказов ведётся всегда). Замер: ~4.5 тыс. срезов/с (200 тыс. срезов ≈ 46 с).
Основной остаток — отсутствие TLB: каждое обращение ARM (включая выборку
полуслова) делает полный двухуровневый обход таблиц через шину. TLB — следующий
по величине выигрыш.

### 48.19 Что именно регистрирует KBL (строки из его .rodata)

Цикл `0x4002BD16` зовёт `f(id, name)`, где `name` — указатель в .rodata KBL.
Дамп строк по этим указателям (`0x4005A7E4`, `0x4005A854`, `0x4005A868`,
`0x4005A7B4`) показывает, что KBL строит **пространство объектов ядра SceUID**:

| Строка | Что это |
|---|---|
| `SceUIDDLinkClass`, `SceUIDClass`, `SceUIDEntryHeapClass` | классы менеджера UID |
| `SceKernelMemBlockClass`, `SceNameHeap`, `SceSysrootClass` | классы памяти/имён/sysroot |
| `SceKernelAllProcess` | корневой объект процессов |
| `SceKernelDummyProcessSystem`, `SceKernelDummyProcessGame` | «пустые» процессы |
| `SceToolP…`, `SceNULL` | служебные объекты |

То есть KBL уже создаёт **namespace ядра**: сначала классы (они должны попасть в
хеш-таблицу менеджера), затем объекты процессов. В нашей модели шаг регистрации
классов не отрабатывает (менеджер `ctx+0x8C` пуст), поэтому цикл по ID
`[0x10001..0x1002F]` получает `0x80024501` на каждом шаге — но теперь понятно, что
именно он регистрирует, и что искать дальше (шаг регистрации классов и данные, из
которых он берёт описания).

### 48.20 Кто пишет подпись boot-контекста

Подпись `0x61CE6649` (её проверяет вторая стадия по DRAM+0xA0) **не найдена ни в
одном доступном образе**: ни в `pch-5c-cold_first_loader.bin`, ни в
`second_loader.{bin,enp}`, ни в `secure_kernel.bin`, ни в `nsbl.bin` (проверено
сканером `_scratch/find_signature.py`, а также поиском *инструкций* её построения
через `_scratch/find_sig2.py` — `movh 0x61CE` + `or3 0x6649` встречается ровно один
раз, в самой проверке второй стадии, `0x40A78`). Значит подпись либо приходит извне
(syscon/SC-команда), либо считается на месте; в обоих случаях её появление зависит от
тех самых данных syscon/SMI, которых у модели нет (см. §3.4 STATUS).

### 48.8 Откуда KBL берёт регион кучи (трассировка, pc-точные данные)

Трапом записей в scratch (PA 0x4011D180-0x4011D200) видно, кто и чем заполняет
таблицу региона:

```
VA 0x5180 <- 0x40000000   pc=0x40032C7C
VA 0x5184 <- 0x00300000   pc=0x40032C80
VA 0x5188 <- 0x00040000   pc=0x40032C86
VA 0x51D0 <- 0x00010002   pc=0x40032CE8
... затем это же переписывается в дескриптор кучи (0x40032152..0x400321E4)
```

Сам строитель региона — функция `0x40032C44`; её аргументы (bp на 0x40032C7C):

| Регистр | Значение | Смысл |
|---|---|---|
| `r6` | `0x00004900` | структура-контекст в scratch (PA 0x4011C900) |
| `[r6+8]` / `[r6+12]` | `0x40000000` / `0x00300000` | база и размер региона |
| `r4` | `0x400B2B30` | объект KBL |
| `[r4+0x15C]` | `0x00040000` | **VA кучи** (третье поле таблицы) |
| `r7` | `0x00005180` | куда пишется таблица |

Далее цикл `0x40032C8E…0x40032CA6` идёт по региону шагом 4 КиБ, у каждой 4-байтной
записи карты страниц (`[r4+0x15C]`-массива) **сбрасывает биты [29:28]**
(`bic r1,r0,#0x30000000`) и считает страницы: в итоге в таблицу кладутся
`count*4` и `count` (768 страниц для 3 МиБ).

Что из этого следует:

* контекст по VA `0x4900` — **собственный объект KBL** (в нём же указатели на свои
  подтаблицы 0x5180/0x51C0/0x5340/0x5380/0x53C0/0x5400/0x5A40/0x5A80 и дескрипторы
  0x8000/0xC000, 0x40000000/0xC0000000); источник копии scratch — **не** SPAD
  (`0x1F004900` = нули) и **не** SRAM CMeP (`0x800900` = код secure kernel), то есть
  KBL собирает контекст сам;
* регион кучи `{0x40000000, 3 МиБ}` с VA `0x40000` — и вот здесь противоречие:
  при `identity` VA `0x40000` = окно MeP (128 КиБ CMeP SRAM), при `dram` — это
  DRAM 0x40000000…0x402FFFFF, **внутри которого лежит сам образ KBL**
  (0x40020000+). Значит, KBL обязан исключать занятые страницы (карта страниц,
  `[r4+0x15C]`), а она у нас пустая: аллокатор видит «всё свободно», список
  свободных блоков получается некольцевым (голова bin'а `0x51E8` → 0) и он крутится.

Следующий шаг: найти, чем должна быть заполнена эта карта страниц (какие регионы
помечены занятыми) — кандидат на «недостающий boot-контекст»; параллельно
проверить поля SceKblParam +0x60/+0x64 (база/размер DRAM), которые могли бы дать
региону другой размер.

## Раунд 50. Почему менеджера объектов нет: точная причина (`malloc(0x1000)` = `0x80020005`) и правка отладчика

Вопрос §48.15 («кто должен создать `ctx+0x8C`») закрыт: менеджер **создаётся самим KBL**
в функции `0x4002BAF8`, но эта функция выходит по ошибке на 113 инструкций раньше, чем
записывает указатель в контекст. Ниже — полная цепочка, все адреса подтверждены
точками останова на полной скорости (см. 50.1 — без правки отладчика их было не снять).

### 50.1 Отладчик: точки останова в `runm` теперь точные *и* проходимые

Прошлый механизм («при установленных bp/wp опустить бюджет ARM до 1») давал точный
останов, но ломал сам прогон: `Cpu::run()` (`src/cpu/cpu.cpp`) первым делом проверяет
`hit_breakpoint()` — а `Debugger::add_breakpoint` кладёт адрес ещё и в **собственный
набор ядра** (`cpu->breakpoints`). Поэтому после останова ядро «проскакивало» точку
останова только при снятом bp, а с bp — стояло на месте вечно (`runm` возвращался сразу,
PC не менялся; `insns` рос только за счёт CMeP). Симптом выглядел как «KBL крутится в
цикле у 0x4002C602» и увёл предыдущий разбор в сторону.

Что сделано:

1. `Vita::pc_hook` (`src/machine/vita.{h,cpp}`) — необязательный хук, который
   вызывается **перед каждой ARM-инструкцией** каждого ядра Kermit. Возврат `true`
   прекращает срез, оставляя инструкцию невыполненной (PC = адрес bp). Бюджет среза
   остаётся полным (256), поэтому `runm` идёт на полной скорости: до `0x4002BAF8`
   машина доезжает за ~0.5 с вместо «никогда».
   * Ограничение: CMeP/Ernie по-прежнему бегут целый бюджет за срез, поэтому точный bp
     на них возможен только при бюджете 1 (как и раньше, по watchpoint'ам).
2. `Debugger::run_machine` ставит/снимает хук сам и **паркует** наборы bp всех четырёх
   ядер на время прогона (`parked_arm_breaks_`), возвращая их после — иначе
   `Cpu::run()` не даёт пройти инструкцию под точкой останова.
3. `StopInfo` получил поле `core`: при возобновлении `runm` первая инструкция под bp
   выполняется ровно один раз и ровно на том ядре, которое остановилось.
4. ARM-точки останова теперь действуют на **все четыре** ядра Kermit (раньше
   `add_breakpoint` попадал только в ядро 0), и в причине останова видно номер ядра:
   `[stop] arm1 breakpoint at 0x4002C602`.
5. Самотест `machine_pc_hook_stops_the_slice_before_the_instruction` фиксирует
   контракт хука (останов до выполнения, PC не сдвинут, после снятия хука срез снова
   выполняется). Базовая линия стала **211 / 15 / 22**.

Заодно найдена ошибка в собственном сканере вызывающих (`_scratch/chk_bl.py`): старый
`tools/find_callers.py` не делал знакового расширения 25-битного смещения, поэтому
**все BL с отрицательным смещением терялись** («у 0x4002B4FC нет вызывающих» — неверно:
их три, `0x4002B9B4`, `0x4002BD48`, `0x4002BD68`).

### 50.2 Менеджер объектов: кто его создаёт и где он отваливается

Цепочка (все значения — из `regs` в момент останова):

```
0x4002C602  bl 0x4002BAF8            ; r0 = 0x400B2B30 (boot-info), r1 = 0x00004900 (контекст)
0x4002BAF8  ...                      ; r4 = boot-info, r6 = контекст
0x4002BB1C  bl 0x400360E4 (r0=0x3C)  ; 60-байтовый объект -> [r6+0x84] и [0x400B2910] = VA 0x5A40
0x4002BB34  bl 0x400360E4 (r0=0x0C)  ; 12-байтовый объект -> [r6+0x88] и [0x400B2914] = VA 0x5A80
0x4002BB50  bl 0x4002AA0C            ; возвращает 0 (успех) — НЕ виновник
0x4002BB62  bl 0x40032278            ; malloc(pool=[boot-info+0x230]=0x51C0, size=0x1000, tag=0xA, &out)
0x4002BB66  cmp r0, #0               ; r0 = 0x80020005  <-- ошибка
0x4002BB10  выход из функции         ; строка «+0x8C» не записывается
```

Проверка памяти подтверждает: контекст по VA `0x4900` (PA `0x4011C900`) заполнен
(`+0x00 = 0xEC`, `+0x04 = 1`, `+0x08/+0x0C = 0x40000000/0x00300000`,
`+0x84 = 0x5A40`, `+0x88 = 0x5A80`, `+0x90 = 0x5D40`, `+0xB8 = 0x4A00`, `+0xBC = 0x4BC0`,
`+0xC0..+0xCC` — подтаблицы), а **`+0x8C = 0`** — то есть менеджер так и не создан.
Именно это и читает `0x4002B4BA` (`ldr.w r5,[r3,#0x8C]`, где `r3 = [0x400B2924] = 0x4900`)
перед вызовом регистрации.

### 50.3 Причина отказа malloc: пустой кэш блоков по 0x1000

`0x40032278` — не общий `malloc`, а распределитель **блоков строго по 0x1000 байт**
(первая инструкция: `cmp.w r1,#0x1000` / `bne` на другую ветку). Его вход:
`r0` = дескриптор пула (`0x51C0`), `r1` = размер (`0x1000`), `r2` = тег (`0xA`).

```
4003228C  ldr.w r9, [r0, #0x9C]      ; r9 = таблица кэша = VA 0x52C0
40032290  blx   0x40039F88           ; «кто я» -> номер ядра
40032294  mov.w r8, r0, lsl #5       ; слот ядра: 32 байта на ядро
40032298  add.w r7, r9, r8
400322A0  ldrh.w r12, [r7, #2]       ; счётчик свободных блоков ядра
400322A4  cmp.w r12, #0
400322A8  beq   0x4003234E           ; ПУСТО -> 0x4003234E
4003234E  blx   0x4003A0A8           ; отпустить мьютекс
40032352  movs  r0, #0 ; str r0,[r6] ; *out = NULL
40032356  bics.w r0, r11, #0x21      ; тег & ~0x21
4003235C  mov.w r10, #5 ; movt r10, 0x8002   ; -> 0x80020005
```

Дамп таблицы (PA `0x4011D2C0`, четыре слота по 32 байта — по одному на ядро):

```
+0x00: 07 00 00 00 | 00 00 00 00 | 00 00 00 00 | ...   ; [0] = 7 (цель), [2] = 0 (счётчик!), [4] = 0 (голова)
```

То есть кэш **пуст у всех четырёх ядер** (счётчик 0, голова NULL), хотя «целевое»
значение 7 выставлено. Смысл тега: `bics r0, tag, #0x21` пускает «добрать память из
нижнего пула» только для тегов, у которых нет бит кроме 0 и 5 (тег 0, 1, 0x20, 0x21);
для остальных (у нас 0xA) распределитель обязан взять блок **из кэша** и при пустом
кэше возвращает `0x80020005`.

Сам дескриптор пула (VA `0x51C0`, PA `0x4011D1C0`) при этом заполнен:
`+0x18/+0x1C = 0x40000000/0x00300000` (регион кучи), `+0x20 = 0x00040000`,
`+0x24 = 0x000051E8`, `+0x9C = 0x000052C0` (таблица кэша), `+0xA8 = "SceP…"`.
Значит **инициализация пула прошла, а наполнение кэша блоками — нет**.

### 50.4 Кэш пишется ровно один раз за весь прогон

Трап записей по самой таблице кэша (`ZLB_WTRAP=4011D2C0-4011D340`, прогон `runm 20000`,
то есть уже после отказа `malloc`):

```
[wtrap] arm_priv +0x11D2C0 w2 = 0x7 pc=400321E8   ; [slot0+0] = 7  (цель)
[wtrap] arm_priv +0x11D2C4 w4 = 0x0 pc=400321EA   ; [slot0+4] = 0  (голова)
[wtrap] arm_priv +0x11D2E0 w2 = 0x7 pc=400321EC   ; ... и так все четыре слота
[wtrap] arm_priv +0x11D2C2 w2 = 0x0 pc=400321FE   ; [slot0+2] = 0  (счётчик)
...
всего 36 записей, все — pc = 0x400321E8…0x40032236
```

Больше в таблицу **никто не пишет** — ни счётчики, ни головы. То есть кэш не «опустошён»
кем-то, а **никогда не наполнялся**: инициализация (`0x400321E8…0x40032236`) выставила
цель 7 и обнулила состояние, а штатный «добор» блоков (тег 0/1/0x20/0x21 → ветка
`0x40032366`) в нашем прогоне не вызывается вовсе. Ср. §48.8: список свободных блоков
самого региона тоже пуст (`голова 0x51E8 → 0`), поэтому обе ступени распределителя
(регион и кэш) стоят пустыми, и `malloc` с тегом 0xA честно возвращает `0x80020005`.

### 50.5 Что это значит для загрузки

* Все 24 регистрации классов (`0x4002BD00`, ID `0x10001..0x1002F` шагом 2) получают
  `0x80024501` не из-за «отсутствия объектов», а из-за **NULL-менеджера**; ядро 0
  честно доводит цикл до конца (последний ID `0x1002F`, `pc=0x4002BD6E`) и уходит дальше,
  потратив на это ~23 млн инструкций (`insns` 1.80 млн → 24.66 млн).
* Инициализация KBL **многопоточная по ядрам**: ту же самую функцию
  `0x4002BAF8`/`0x4002C602` проходят по очереди arm0, arm1, arm2, arm3 (видны четыре
  останова на `0x4002BB10` с разными PC у arm1..3 — они уже за барьером/в своих ветках).
  Это объясняет, почему одиночный `run` (одно ядро) здесь не работает.
* Следующий шаг — найти, кто обязан наполнить кэш `0x52C0` (записи в
  `[slot+2]`/`[slot+4]`): это делается либо в самой инициализации пула, либо при
  «доборе» блоков тегом 0/1/0x20/0x21 из нижнего пула (ветка `0x40032366` и дальше,
  где `0x4003A1B0` берёт мьютекс, дальше `cmp.w r5,#100000` и `uadd8` считают класс
  размера).
  Инструмент для этого уже есть: трап записей по PA `0x4011D2C0`-`0x4011D340`
  (`ZLB_WTRAP=4011D2C0-4011D340`) покажет всех писателей с их PC.
