# vipimg.elf (SceVipImage) — разбор и сравнение с vnzimg.elf

Прошивка **1.04**. Артефакт: `Vita_104_Firmware/Out/fs_dec/os0/kd/vipimg.elf`
(SLB2-имя `os0:kd/vipimg.skprx`), 0x583F4 = 361 460 байт.

Это «близнец» `vnzimg.elf`: тот же контейнер, тот же ABI, та же схема загрузки —
но **совсем другое содержимое**. Ниже — разбор и таблица различий; сквозные
детали (протокол SPRAM, RPC, Pervasive2) описаны в `docs/VNZIMG.md`.

---

## 1. Контейнер: байт-в-байт та же схема

| | `SceVipImage` (vipimg) | `SceVeneziaImage` (vnzimg) |
|---|---|---|
| размер файла | 0x583F4 (361 460) | 0xF6F54 (1 011 540) |
| ELF | `e_type=0xFE04`, `e_machine=0x28`, `e_flags=0x05000000`, `e_entry=0` | то же |
| PH[0] | файл 0xA0 → `0x81000000`, 0x84, RX | то же |
| PH[1] | файл 0x130 → `0x81001000`, **0x58298**, RWX | файл 0x130 → `0x81001000`, **0xF6DF8**, RWX |
| PH[2] | `0x60000000`, файл 0x583D0, 0x24 | `0x60000000`, файл 0xF6F30, 0x24 |
| module NID | **0xEEA339DA** | **0xEEA339DA** |
| type | 0x06 | 0x06 |
| export | одна запись: `nfun=0`, `nvar=1`, **`attr=0x8000`**, NID **0x6C2224BA** → `0x81000000` | то же |
| import | нет | нет |
| PH[2] релокации | `(0x200,0x7C,0x74) (0x200,0x80,0x78) (0x200,0x00,0x80)` | **те же три записи** |

То есть модуль экспортирует **не функцию, а переменную** `0x6C2224BA`, значение
которой — указатель на собственный `SceModuleInfo` (`0x81000000`). У `vipimg`
атрибут библиотеки `0x8000` (в vnzimg было 0 — при одинаковом ABI это не влияет
на разбор, но пусть будет зафиксировано).

**Вывод по ABI:** это не «драйвер с точкой входа», а **описатель ресурса**: ядро
грузит модуль, чтобы получить по NID `0x6C2224BA` адрес (`0x81000000`), по
которому лежит `SceModuleInfo`, и оттуда — образ MeP. Никаких ARM-функций в
модуле нет (в vnzimg это тоже подтверждено: `push{..,lr}` не встречается ни в
одном 4-КиБ блоке; здесь — та же картина).

## 2. Образ MeP: база `0x80000000`, но другая программа

Файл-смещение MeP-адреса: `0x130 + (VA − 0x80000000)`.

```
0x80000000  00 00                 nop
0x80000002  E8 DF 00 00           jmp 0x800000FC
0x80000006  08 DC 00 00           jmp 0x80000080      <- обработчик сброса
0x8000000A  58 DF 00 00           jmp 0x800000EA
0x8000000E .. 0x80000026          jmp 0x800000EA      (шесть одинаковых)
0x80000080  ...                   тело обработчика сброса
0x800000EA  ... 0x800000FC        ещё один вектор
```

Расхождение с `vnzimg`: там векторная таблица начиналась с двух `jmp` на
`0x80063c`/`0x800a42` и четырёх самозаглушек, и вся дальнейшая программа жила
выше `0x80000200`. Здесь вектора ведут на низкие адреса (`0x80`, `0xEA`, `0xFC`) —
то есть **первые 0x100 байт образа являются векторами и диспетчером**, а основной
код начинается с `0x80004000`.

Обработчик сброса (`0x80000080`) работает с control bus и вызывает по указателю:

```asm
80000080  mov   $8,$0
80000082  stcb  $0,0x10
80000086  movu  $0,0x5100
8000008A  ldc   $0,$ccfg
8000008E  movh  $4,0xa028
8000009A  movh  $tp,0x73bb
800000A0  bra   0x800000b8
800000A2  bsr   0x800000da
...
800000B8  beqz  $0,0x800000c2
800000BA  jsr   $sp                 ; косвенный вызов (диспетчер по таблице)
...
800000D0  add3  $2,$0,$1
800000DA  repeat $0,0x80002156     ; RPE = 0x80002156 (спан ~8 КиБ)
```

Про `repeat`: RPC = `$0`, RPB = `0x800000DC`, RPE = `0x80002156` — то есть весь
блок `0x800000DC…0x80002156` объявлен повторяемым. Спан необычно большой, а в
самом конце его (`0x80002140`) лежат данные, а не код:

```
80002144  03 01  sltu3 $0,$1,$0
80002146  02 02  slt3  $0,$2,$0
80002148  06 06  --reserved--
8000214C  04 01  sub   $1,$0
```

Это либо таблица внутри повторяемого блока, либо признак того, что линейная
разметка в этом месте не совпадает с реальным потоком управления. Точный
разбор сброса VIP требует трассы/симуляции, а не только статики.

## 3. Профиль образа: **это scalar-программа, VLIW не используется**

Полный линейный проход (162 919 инструкций, `zdis mep --base 0x80000000 --offset 0x130`):

| мнемоника | vipimg | vnzimg (для сравнения) |
|---|---|---|
| `nop` | 110 201 | 123 533 |
| `--reserved--` | 605 | 10 077 |
| `*unknown*` | **1 270 (0.8 %)** | 18 335 (4.37 %) |
| `bsr` / `jsr` | 913 / 31 | 9 019 / 495 |
| `jmp` / `bra` | 333 / 899 | 1 929 / 5 905 |
| `ret` / `reti` | 470 / 15 | 1 560 / 7 |
| `stcb` / `ldcb` | 1 111 / 366 | 322 / 269 |
| `swcp/lwcp/smcp/lmcp` | 123/74/80/231 | 1150/1237/1816/2484 |
| **`bsrv` + `jsrv` (вход в VLIW)** | **0** | **1 625** |

Ключевое: **`bsrv`/`jsrv` = 0**. В `vnzimg` их 1625 — там VLIW-режим
используется по-настоящему. Здесь переключений в VLIW нет вообще, и доля
`*unknown*` в 5 раз ниже (0.8 % против 4.37 %) — то есть код разбирается
полностью и является обычным 16/32-битным MeP-c5.

Карта образа (по 4 КиБ, доля нулей):

| диапазон | что это |
|---|---|
| `0x80000000–0x80004000` | вектора, диспетчер, таблицы (нулей 94–100 %) |
| `0x80004000–0x80011000` | **основной код** (нулей 9–13 %) |
| `0x80011000–0x80020000` | bss / резерв (нулей 100 %) |
| `0x80020000–0x80023200` | **второй блок кода** (нулей 9–11 %) |
| `0x80023200–0x80039E06` | данные (последний ненулевой байт — `0x80039E06`) |
| дальше до `0x80058298` | нули |

Итого полезное содержимое ≈ 232 КиБ из 361 КиБ сегмента; 35 % байтов ненулевые.

## 4. Что делает код (предварительно)

* **Control bus — основной канал**: 1 111 записей `stcb` и 366 чтений `ldcb`,
  адреса группируются в `0x5A00–0x5C10` (десятки обращений), плюс `0x1000–0x1005`,
  `0x7000–0x704C`, `0x8704`, `0x8718`, `0xB016`, `0xFC04`, единичные
  `ldcb 0xACFD`, `ldcb 0xA51D`. Для сравнения: в `vnzimg` control bus почти не
  используется (322/269), а его MeP работает через SPRAM (`0xF1840000`).
* **Полных 32-битных MMIO-адресов SoC нет**: `movu` даёт значения вида
  `0x6804E4`, `0xB4F5C`, `0x202F0C`, `0x530800` — это смещения/указатели
  внутреннего пространства, а не `0x1F84xxxx` / `0xE3xxxxxx`. То есть VIP-образ
  не «трогает» Pervasive2 напрямую — этим занимается ARM-обёртка.
* Обработчик сброса вызывает код через **указатель** (`jsr $sp`), и в образе
  видны плотные таблицы переходов — типично для загружаемого образа, который
  принимает команды от ARM.
* Горячие функции (по числу входящих ссылок): `0x800053DE`, `0x800053D6`,
  `0x800259C6`, `0x800259BE`, `0x8000C9EE`, `0x8000C9E2`, `0x8000D602`,
  `0x80024F98`, `0x8002FB7E`, `0x8012D7FA`, `0x80004BE4`, `0x80005F8C`,
  `0x80005FF0`, `0x800064E2`. Это ядро обработки изображения.

## 5. Кто грузит и как используется

* Строка `os0:kd/vipimg.skprx` встречается **ровно один раз** в дереве прошивки —
  в `bootimage.elf`, файл `0xA472C`, в том же блоке строк, что и `vnzimg`.
* Рядом (файл `0xA45F0–0xA46B0`) лежат имена **VIP-обёртки**:
  `SceVipLpddrCode`, `ScePervasiveResetReg`, `ScePervasiveMailboxReg`,
  `ScePervasiveTasReg`, `SceVipDriver`, `SceVipMailbox0`, `SceVipDma`,
  `SceVipDmacMemcpy%02u`, `SceVip`, `SceVipSuspend`, `SceCodecEngine`,
  `SceCodecEngineProcessor`.
* Отдельного `vip_wrapper.skprx` **нет** (в отличие от `vnz_wrapper.skprx`,
  строка 0x96DF4): значит VIP-обёртка (`SceVipDriver`) — это встроенный модуль
  внутри `bootimage.elf`, как и `SceVeneziaWrapper`.
* Схема из `docs/VNZIMG.md` §3 повторяется: `SceVipDriver` выделяет
  Pervasive-регионы (`ScePervasiveResetReg`, `ScePervasiveMailboxReg`,
  `ScePervasiveTasReg`), вызывает `SceSblFwLoaderForDriver` с путём
  `os0:kd/vipimg.skprx`, поднимает mailbox (`SceVipMailbox0`) и DMA-каналы
  (`SceVipDma`, `SceVipDmacMemcpy%02u`), после чего общается с MeP через
  mailbox/DMA. Точные адреса и порядок шагов для VIP не дизассемблировались —
  это отдельная задача (см. §7).

## 6. Сводка различий

| признак | vnzimg (SceVeneziaImage) | vipimg (SceVipImage) |
|---|---|---|
| образ MeP | 1 010 168 Б (0xF6DF8) | 360 088 Б (0x58298) |
| начало кода | `0x80000200`, вход `0x80063C` | `0x80004000`, вектор входа `0x80000080` |
| VLIW/IVC2 | **используется**: 1 625 `bsrv/jsrv`, 92 вызова на `0x800622E0` | **не используется**: 0 `bsrv/jsrv` |
| `*unknown*` | 4.37 % | 0.8 % |
| обмен с ARM | SPRAM `0xF1840000` + почтовый ящик `spram[0]`, RPC-каналы `SceVeneziaRpc*` | control bus (`stcb/ldcb`, 1 477 обращений), mailbox/DMA-имена `SceVip*` |
| SPRAM | `SceVeneziaSpram` (PA 0x1F840000) — рабочий канал через Pervasive2 | используется как LPDDR-код (`SceVipLpddrCode`), отдельный регион |
| обёртка | `SceVeneziaWrapper` (+`…ForDriver`), отдельный `vnz_wrapper.skprx` в конфиге | `SceVipDriver` внутри bootimage, отдельного wrapper-файла нет |
| профиль движка | VLIW + SIMD (IVC2), 8 ядер MPE | scalar MeP-c5 |

**Практический вывод для эмулятора:** `vipimg` — существенно более простая цель,
чем `vnzimg`. Его образ полностью разбирается `zdis mep` (0.8 % `*unknown*`),
не требует IVC2/VLIW и общается через **control bus** (`stcb`/`ldcb`) — то есть
для его запуска достаточно: (1) отобразить образ на `0x80000000`, (2) завести
окно control bus с адресами `0x5A00–0x5C10`, `0x1000…`, `0x7000…`, (3) дать
mailbox/DMA-регистры VIP. Всё это ложится на уже существующий `ControlBus` в
`MePCore` (сейчас в нём смоделированы только `0x400..0x405`).

## 7. Что осталось нерешённым

1. Адреса и назначение 1 477 control-bus обращений (`0x5A00–0x5C10` в первую
   очередь) — по ним восстанавливается интерфейс VIP.
2. Точки входа образа: какие из векторов используются при штатном запуске
   (`0x80000080`, `0x800000EA`, `0x800000FC`), и что делает диспетчер `jsr $sp`.
3. Формат команд ARM → VIP (mailbox `0x5A00`/`0x5B00`/`0x5C00`?) и DMA-дескрипторы.
4. Связь `SceVipLpddrCode` с регионом `0x80023200–0x80039E06` (данные образа?)
   и с LPDDR-инициализацией.
5. Дизассемблировать `SceVipDriver` внутри `bootimage.elf` (по аналогии с тем, что
   сделано для `SceVeneziaWrapper`) и получить порядок подъёма VIP.

```powershell
python _scratch\vip_container.py
python _scratch\vip_exports.py

# образ MeP: вектора, точки входа, статистика, карта
python _scratch\vip_mep.py
python _scratch\vip_clean.py
python _scratch\vip_extent.py

# control bus и ближайшие данные
python _scratch\vip_mmio.py
python _scratch\vip_imm.py

# строки загрузчика
python _scratch\vip_boot.py
python _scratch\vip_desc.py
```
