## 1. Питание

1. Ernie (RL78 syscon) стартует с вектора `0xE000` из `USS-1001.bin`.
   Его reset-пролог: `sel rb0 / movw sp,#0xFE20 / clrb !0x02F0 / mov !0x00F5,#0x80 /
   clrb !0x0078 / call !0x104F5`, затем инициализация `0x30035` и цикл ожидания
   `cmp !0xFFFA2,#0xC0 / bnz` на `0x3005A`.
   *Факт*: адреса и поведение восстановлены по дампу (`_scratch/rl78/HANDOFF.md`).
   *Модель*: значение `0xC0` в SFR `0xFFFA2` выставляет наш SFR-слой, то есть
   «железо готово».
2. Ernie снимает сброс с CMeP (`ErnieBlock::release_soc`).

## 2. Роль «ARM boot ROM» (модель)

У нас нет дампа ARM boot ROM, поэтому этот шаг реализован на C++
(`Vita::arm_boot_rom_stage_second_loader`):

1. читает контейнер **SLB2** из загрузочного раздела eMMC (`boot0`, затем `boot1`,
   затем копии в пользовательской области `0x800000`/`0xC00000`);
2. находит запись `second_loader.enp`;
3. копирует её в разделяемую загрузочную SRAM по физическому адресу `0x1F000000`
   (окно 256 КиБ, видимое и ARM, и CMeP — `Bus::add_ram_alias`);
4. пишет в mailbox `0xE0000010` значение `PA | 1` (бит 0 = «образ готов», биты 2+ —
   физический адрес, выровненный на 4).

Это соответствует трактовке из `ANALYSIS.md` §4.2: режим `'A'` = bit0 + bit6, при
установленном bit0 образ берётся от ARM.

## 3. CMeP first_loader (исполняется по-настоящему)

Точка входа `0x5C000`, окно CMeP RAM `0x40000..0x5FFFF` (128 КиБ),
`$0` (будущий `$sp`) = `0x60000`, аргумент `main` = `0x40000`.

```
_start (0x5C004)  очистка .bss [0x5EB00,0x5EE3C), $gp=0x5EB00, $tp=0x5E820
main    (0x5C4FE) init_emmc_keyrings -> check_boot_mode -> выбор пути
   check_boot_mode (0x5C0EE)
       *(0xE0030028) = 0x501            запрос флагов keyring 0x501
       $12 = *(0xE003002C); if (($12 & 3) != 3) return -1
       $12 = *(0xE0062020); return ($12 & 1) ? 'A' : '!'
   путь bit0 (0x5C574)
       ждать (*(0xE0000010) & 1)
       PA = *(0xE0000010) & ~3
       memcpy(0x40000,        PA,        64)
       validate_header(0x40000)
       memcpy(0x40000 + 64,   PA + 64,   size + field_0x10 - 64)
   process_image (0x5CC00)
       img_proc_* : keyring 8/9/0x0A/0x20, RSA через Bignum, AES через Bigmac,
                    массовая инвалидация флагов 0x1C1F/0xFC1F
   успех: keyring_set_value(0x501) и *(0xE0000000) = 1
   отказ: *(0xE0000000) = 2 и вечный цикл
```

Проверка заголовка (`validate_header`, `0x5C61C`):

| Смещение | Проверка |
|---|---|
| `+0x00` | магия `0x64B2C8E5` |
| `+0x04` | `size >= 0x2B0` и `size < 0x10000` |
| `+0x08` | `offset`; `+0x0C` = `length`; требуется `size == offset + length + 0x2B0` |
| `+0x10` | `field`; требуется `field + size < 0x1C000` |
| `+0x16` | `u16` < `0x10` |

Для 1.04 (`Out/SLB2/second_loader.enp`) эти поля равны: magic `64B2C8E5`,
`size = 0x2C0`, `offset = 0x10`, `length = 0`, `field_0x10 = 0x16600`,
`u16@0x16 = 0` — заголовок проходит все проверки, тело = `0x16600` байт.

Затем `_start` кладёт `$lp = 0x40000`, копирует 32-байтовый stub в `0x5FFE0`,
обнуляет слово по `0x5C000` (самоуничтожение точки входа) и делает `ret`, то есть
переход на `0x40000`.

### 3.1 Цепочка проверок проходит целиком (обновлено)

На сегодня first_loader проходит **весь** свой путь и рапортует `*(0xE0000000) = 1`,
после чего отдаёт управление второй стадии. Что для этого потребовалось:

| Шаг | Адрес | Что делает | Как смоделировано |
|---|---|---|---|
| `validate_header` | `0x5C61C` | проверки контейнера ENP | реальный код |
| SHA-256 заголовка | `0x5C7F6` | `0x5CCF0` = SHA-256, `$1`=куда, `$2`=откуда, `$3`=длина, `$4`=32 | `BigmacFunction::Sha256 = 0x0033` |
| RSA-проверка | `0x5C83A` | 64 слова из `image+0x1C0` в окно Bignum, модуль из `0xE0066000` | ключ разработчика, подпись перезаписывается (`machine/bootkeys.cpp`) |
| digest-таблица | `0x5C9BA` | 32 байта `image+0x1A0` через keyring 10 → `0x5EDE0`, затем `memcmp` с SHA-256 тела | `0x030A` + провижининг записи `+0x1A0` |
| keyring-слоты | `0x5C904/0x5C93A` | загрузка слотов 10..15 из образа | `0x030A` (бит 28 = «+0x04 это индекс»), слоты однократно программируемые |
| распаковка образа | `0x5CBCC` | `0x010A`: AES-128-CBC из `image+0x2C0` **в** `image` (0x40000), ключ — слот 10 | **реальный AES** (см. ниже) |
| хвост окна | `0x5CC86` | `0x000C`: операция по месту над `[image+0x16600, 0x1C000)` | модель |
| самоуничтожение | `0x5C000` | stub в `0x5FFE0` затирает `0x5C000..0x5FFE0` нулями и делает `ret` на `$lp = 0x40000` | реальный код |

**Ключ загрузки.** Слот keyring 10 — «fused» ключ чипа: `ENC_KEY || ENC_IV`
(`AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA`, `AF5F2CB04AC1751ABF51CEF1C8096210`) из
`pup_fiction`. Именно им `0x5CBCC` расшифровывает `image+0x2C0` в `0x40000`; в
Python проверено, что AES-128-CBC от тела `second_loader.enc` этим ключом даёт
ровно `Out/SLB2_dec/second_loader.bin`, чей SHA-256 = поле `+0x20` заголовка ENP.
Отсюда два следствия:

* ARM boot ROM должен ставить в общую SRAM **`second_loader.enc`** (не `.enp`) —
  `.enp` остаётся запасным вариантом;
* слот 10 нельзя перезаписать: загрузка из `image+0xE0` (`0x5C904`) игнорируется,
  как и положено однократно программируемому слоту.

`tools/make_boot_keys.py` генерирует dev-ключ под тот образ, который реально
ставится (сейчас — `.enc`), и подписывает блок
`00 01 FF*203 00 || ROM[0x5E774:18] || SHA-256(header[0:0x1C0])`, куда входит и
запись digest-таблицы, поэтому все `memcmp` загрузчика выполняются по-настоящему.

## 4. CMeP second_loader

Исполняется из `0x40000` (образ уже расшифрован туда first_loader'ом). Через SC-канал
(`0xE0B00000` запрос / `0xE0BF0000` ответ, регистры `0xE310xxxx`, `0x30000118`,
`0x30000208`, `0xE0064060`) читает с eMMC `secure_kernel.enp` и
`kernel_boot_loader.self`, после чего снимает ARM.

Первое, что делает вторая стадия (`0x4952C..0x49540`): пишет `1` в `0xE3102100`
(строб SC) и уходит в `erepeat`-цикл опроса этого регистра. Цикл «бесконечный»:
прервать его может только прерывание от SC. Наш `0xE3102100` отвечает `0` (операция
считается завершённой), но **прерываний у CMeP пока нет** — это и есть текущий
блокер второй стадии, тот же подсистемный узел (SC/eMMC), на котором стоит и ARM
KBL (`SDIF 0xE2040028` бит 9 и рукопожатие `0xE5888000`).

## 5. ARM kernel_boot_loader

ARM стартует по `0x1F000000`-схеме из SLB2: `kernel_boot_loader.self` — это SELF
с `self_type = 0x09 (BOOT)`, `keyrev = 1`, который расшифровывается нашим
`self_to_elf` (проверено: 4 секции AES-128-CTR воспроизводят
`Out/SLB2_dec/kernel_boot_loader.self.seg00..seg03` побайтово). KBL монтирует
раздел `os0` (FAT16) и грузит модули ядра из `/os0/kd/`.

## 6. Ядро

«Ядро загружено» = ARM выполняет код модулей ядра в DRAM; признак в эмуляторе —
`Vita::kernel_started()`/`kernel_running()` и запись `kernel entry reached` в
отчёте. Стадия `--stage kernel` грузит модуль ядра напрямую, чтобы ядро можно было
отлаживать, даже если предыдущая стадия ещё не доведена.

## 7. Разделяемая память

| Физический адрес | Кто видит | Назначение |
|---|---|---|
| `0x00040000..0x0005FFFF` | CMeP | RAM CMeP, окно first_loader и staging second_loader |
| `0x00060000` | CMeP | вершина стека (`$0` при сбросе) |
| `0x1F000000..0x1F03FFFF` | ARM и CMeP (алиас одного буфера) | загрузочная SRAM: ARM boot ROM кладёт сюда second_loader |
| `0x80000000..0x83FFFFFF` | ARM | DRAM (64 МиБ окно) |
| `0x40000000..0x400FFFFF` | ARM | приватная область MPCore |

## 8. Что подтверждено, а что модель

**Подтверждено материалом:** формат SLB2 (заголовок и таблица записей — проверено
совпадением магии каждой записи в дампе CP), поля и проверки заголовка `.enp`,
порядок и адреса MMIO first_loader, reset-пролог Ernie, содержимое SLB2 1.04,
формат FAT16 разделов `os0`/`vs0`, код операции Bigmac (`0x0033` SHA-256, `0x030A`
keyring, `0x010A` распаковка образа, `0x000C` операция по месту, `0x0301` запись
keyring), ключ загрузки `ENC_KEY||ENC_IV` (даёт ровно `SLB2_dec/second_loader.bin`),
самоуничтожение ROM `0x5C000..0x5FFE0` перед передачей управления.

**Модель (документированное допущение):** роль ARM boot ROM на C++; адрес
`0x1F000000` для staging; точная раскладка MBR пользовательской области;
адресация периферии Kermit там, где её не удалось подтвердить реверсом модулей
прошивки; начальные значения батареи/RTC syscon; ключ разработчика в таблице
`0xE0066000` и переподпись образа (реальная таблица-ключ в дампы не попала);
запись digest-таблицы `+0x1A0` (на железе она завёрнута ключом, которого нет в
дампах — модель распаковывает её копированием); `0xE3102100` отвечает `0`
(операция SC завершается мгновенно); отсутствие прерываний MeP.
