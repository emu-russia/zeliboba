# CMeP first_loader: поэтапный разбор

Документ разбирает **первый загрузчик CMeP** (MeP-c5, он же F00D) по шагам: один
раздел на шаг, в каждом — листинг исполняемого кода, описание того, что этот код
делает, и то, как этот шаг выглядит в модели zeliboba (что исполняется по-настоящему,
а что подставлено). Все адреса, значения регистров и порядок обращений к устройствам
взяты из прогонов эмулятора, а не из пересказа.

Место в цепочке (`docs/BOOT.md`, `docs/STATUS.md`):

```
Ernie (RL78) -> CMeP first_loader -> second_loader -> secure_kernel -> ARM KBL -> NSKBL
```

## 0. Материалы, метод и сводная карта шагов

### 0.1 Что именно исполняется

| Артефакт | Что это | Роль в разборе |
|---|---|---|
| `dumps/vita_prototype_bootrom.bin` | образ first_loader, 16 КиБ, база `0x5C000` | **исполняется моделью как есть**, все адреса ниже — из него |
| `dumps/pch-5c-cold_first_loader.bin` | retail-сборка того же загрузчика, снятая из RAM после загрузки | второй набор: layout сдвинут на `-0x80`, поведение сверяется в §17 |
| `dumps/bootrom_analysis/vita_prototype_bootrom.annotated.asm` | полный аннотированный листинг (objdump `mep-elf`, binutils 2.37) | источник всех листингов ниже |
| `dumps/bootrom_analysis/ANALYSIS.md`, `COMPARISON.md` | статический разбор и сравнение прототипа с retail | сверка форматов и различий |
| `src/hw/cmep/` | модель CMeP: `keyring.cpp`, `bigmac.cpp`, `bignum.cpp`, `mailbox.cpp`, `cmep_block.cpp` | «в модели» в каждом разделе |
| `src/machine/bootchain.cpp`, `src/machine/bootkeys.cpp` | постановка образа, подстановки, dev-ключ | §16 |
| `src/loader/keys.h`, `src/hw/cmep/keyring.cpp` | `ENC_KEY ‖ ENC_IV` — «fused» ключ слота keyring 10 | §12 |

Листинги приведены в формате аннотированного листинга: `адрес  байты  инструкция`,
адрес — абсолютный (образ слинкован на `0x5C000`). Разбирать их можно и средствами
самого эмулятора — `zdis mep dumps/vita_prototype_bootrom.bin --base 0x5C000
--offset 0x61C --count 40` печатает ровно то, что исполнит интерпретатор.

### 0.2 Как получены измерения

```text
# 1. прогон до передачи управления второй стадии
build\bin\zeliboba.exe -q -ex "boot" -ex "core mep" -ex "bp 0x40000" -ex "run 400000" -ex "boot" -ex "quit"

# 2. пошаговые остановки на каждом шаге (bp без архитектуры адресуется MeP)
... -ex "bp 0x5C61C" -ex "run 400000" -ex "regs" -ex "keyring" ...

# 3. хронология MMIO: каждая запись в блок CMeP с адресом гостевого pc
$env:ZLB_WTRAP="0xE0000000-0xE007FFFF"; $env:ZLB_RTRAP="0xE0030000-0xE0030030"

# 4. покрытие кода
$env:ZLB_MEP_COV="1"   ...   -ex "cov mep 0x5C000 0x4000"
```

### 0.3 Метрики измеренного прогона (до `0x40000`)

| Метрика | Значение |
|---|---|
| Машинных шагов до передачи управления | 146 295 (столько же инструкций MeP) |
| Исполненных сайтов в окне `0x5C000..0x60000` (2 байта/бит) | **934** (0x5C000: 894, 0x5E000: 29, 0x5F000: 11) |
| Записей keyring (триггер `0xE0030020`) | 1 — только слот `0x501` |
| Операций Bigmac | 14 (`0x0301`, `0x010A`, `0x0301`, `0x0033`, `0x030A`×7, `0x0033`, `0x010A`, `0x000C`) |
| Операций Bignum | 1 (RSA-2048, `e = 0x00010001`) |
| SC-транзакций к Ernie | **0** (путь `bit0` не трогает eMMC) |
| Итог | `0xE0000000 <- 1`, передача управления на `0x40000` |
| Не исполнено вовсе | альтернативные пути `0x5C206..0x5C4FE` (bit5) и `0x5C5B6..0x5C5D2` (bit6); хвостовой обход `0x5CB60..0x5CBB8`; путь отказа `0x5C5FE..0x5C61C` |

### 0.4 Карта шагов

| № | Адрес | Функция | Что делает | В модели |
|---|---|---|---|---|
| 1 | `0x5C004` | `_start` | CRT: `.bss`, `$sp/$gp/$tp`, `main(0x40000)` | реальный код |
| 2 | `0x5C0B8` | `init_emmc_keyrings` | включает eMMC-крипту, настраивает keyring `0x20E/0x20F` | реальный код + `EmmcCryptoDevice` |
| 3 | `0x5C0EE` | `check_boot_mode` | keyring `0x501` + страп `0xE0062020` → `'A'`/`'!'` | реальный код, страп и флаги — модель |
| 4 | `0x5C4FE` | `main` | выбирает путь по битам режима | реальный код |
| 5 | `0x5C574` | `main` (bit0) | ждёт mailbox, копирует контейнер в `0x40000` | реальный код; адрес ставит ARM boot ROM (подстановка) |
| 6 | `0x5C61C` | `validate_header` | проверки ENP-заголовка | реальный код |
| 7 | `0x5CC00` | `process_image` | диспетчер пяти этапов + хвост | реальный код |
| 8 | `0x5C67E` | `img_proc_5C67E` | keyring 8/9, keyed-проверка `0x010A`, замки | реальный код; тело проверки — подстановка в Bigmac |
| 9 | `0x5C798` | `img_proc_5C798` | keyring `0x20`, SHA-256 заголовка, RSA/Bignum | реальный код; ключ и подпись — dev-набор (`bootkeys`) |
| 10 | `0x5C8DA` | `img_proc_5C8DA` | слоты 10..15, digest-таблица, SHA-256 тела | реальный код; «разворачивание» digest — копия |
| 11 | `0x5CA1C` | `img_proc_5CA1C` | инвалидация keyring по таблицам контейнера | реальный код (в 1.04 таблицы пусты) |
| 12 | `0x5CBBC` | `img_proc_5CBBC` | замок `0x0A` + **AES-128-CBC** распаковка образа | **настоящий AES** |
| 13 | `0x5CC7C` | `process_image` | хвост окна (`0x000C`) и обнуление окна Bigmac | семантика `0x000C` неизвестна; RNG не запускается |
| 14 | `0x5C5E2` | `main` | `keyring_set_value(0x501)`, mailbox `1` / `2` | реальный код |
| 15 | `0x5C044` | `_start` | самоуничтожение и передача управления на `0x40000` | реальный код — переход в second_loader честный |
| 16 | `0x5FF00` | буфер запроса сервиса | вторая стадия пишет туда 32 слова и уходит `jmp` | **только этот шаг — подстановка** (`pc_hook`), см. §15.1 |

> Шаг 16 — единственное место `pc_hook`. Передача «первый → второй загрузчик»
> (шаг 15) исполняется по-настоящему: заглушка `0x5C098` → `0x5FFE0` затирает
> окно и делает `ret` по `$lp = 0x40000`; в прогоне это видно как
> `CMeP handed off to the staged image at 0x402FC` (первая инструкция образа —
> `jmp 0x402E0`), а в RAM после прогона — по байтам заглушки на `0x5FFE0`. Хук
> закрывает обратный вызов второй стадии по `0x5FF00` (§15.1), а не передачу
> управления.

### 0.5 Достоверность листингов

Статический разбор — не истина в последней инстанции: линейный дизассемблер
разбирает `.data` как код, а аннотации (`CMeP_rom/ram_…`, «JIG/debug strap?»)
являются догадками генератора. Поэтому каждый листинг ниже прошёл три проверки:

| Проверка | Как | Результат |
|---|---|---|
| байты | столбец байт листинга сверен с `dumps/vita_prototype_bootrom.bin` | все 4162 строки (включая область данных), 0 расхождений |
| декодирование | листинг objdump сверен с **собственным** декодером zeliboba (`zdis mep … --base 0x5C000`) | 3746 инструкций в области кода (`0x5C000..0x5E6A8`): 0 расхождений по границам и 0 по тексту |
| поведение | значения регистров и порядок обращений к MMIO, снятые прогоном, сверены с тем, что предсказывает листинг | совпадают на всех шагах (§1–§15, Приложение A) |

Следствия, которые надо держать в голове при чтении:

* **границы кода**: код прототипа заканчивается на `ret 0x5E6A8`; всё, что дальше
  (`.data`, 0x5E704…, и нули до 0x5FFFF), в листинге — мусор, а не инструкции;
* **аннотации имён** в листинге (`KeyringClearFlags`, `MailboxCmepToArm.Status`,
  `CMeP_rom/ram_0x5E830`) — не факты, а соглашения анализа; факты — адреса и pc;
* **циклы `repeat`** в листинге не видно целиком: аппаратура исполняет блок
  `[RPB, RPE]` **плюс один завершающий слот**; например, в `memcpy` (0x5E60C)
  блок — `[0x5E61A, 0x5E620]` и слот `0x5E624`, поэтому за 16 итераций копирования
  64 байт оба указателя уходят на `+0x40`. Это подтверждается замером (§1, §5), а
  не текстом листинга.

При сверке в `dumps/bootrom_analysis/` найдены и исправлены реальные ошибки
(счётчик инструкций в таблице разметки, охват очистки `.bss`, атрибуция RSA не той
функции, инвертированное условие в описании записи keyring `0x501`, обрезанные
экстенты в `*.functions.csv`, пропущенный сайт чтения страпа в `*.mmio.csv`,
а также неверная граница кода у retail-образа: `--code-end 0x5E692` вместо
`0x5E684`, из-за чего 14 байт `.data` считались кодом) — подробности и таблица
правок: `dumps/bootrom_analysis/README.md`, раздел «Corrections».

## 1. Сброс и `_start`: CRT-пролог (шаг 1)

**Где:** `0x5C000` (reset vector) → `0x5C004` (`_start`), первый код, который исполняет
CMeP после снятия сброса. Разбираются `0x5C004..0x5C040`; хвост `_start`
(`0x5C044..0x5C0B6`) — это шаг 15, он исполняется уже после возврата из `main`.

### Листинг

```asm
; ---- reset_vector
5C000  28 d8 c0 05    jmp 0x5c004

; ---- _start
5C004  00 d2 eb 05    movu $2,0x5eb00        ; .bss start
5C008  3c d3 ee 05    movu $3,0x5ee3c        ; .bss end
5C00C  00 51          mov $1,0
5C00E  24 03          sub $3,$2
5C010  1a 63          srl $3,0x3             ; $3 = words/8 - 1
5C012  fc 63          add $3,-1
5C014  09 e3 03 00    repeat $3,0x5c01a
5C018  2a 01          sw $1,($2)             ; store bss_start @ 0x5EB00
; ---- loc_5C01A
5C01A  2a c1 04 00    sw $1,4($2)            ; store CMeP_rom/ram_0x5EB04 @ 0x5EB04
5C01E  20 62          add $2,8
5C020  50 e9 05 00    beqi $9,0x5,0x5c02a   ; "вошли из монитора" -> не портить $sp/$gp
5C024  00 0f          mov $sp,$0             ; $sp = значение, оставленное сбросом ($0)
5C026  21 ce 06 00    movh $gp,0x6
; ---- loc_5C02A
5C02A  e0 ce 00 eb    add3 $gp,$gp,-5376     ; $gp = 0x5EB00
5C02E  21 cd 06 00    movh $tp,0x6
5C032  d0 cd 20 e8    add3 $tp,$tp,-6112     ; $tp = 0x5E820
5C036  00 50          mov $0,0
5C038  78 70          stc $0,$hi
5C03A  88 70          stc $0,$lo
5C03C  21 c1 04 00    movh $1,0x4            ; $1 = 0x40000 - аргумент main
5C040  f9 dd 04 00    bsr 0x5c4fe            ; main($1)
```

### Что происходит

1. Reset vector — короткий `jmp` на `_start` (два слова: аппаратный вектор + точка входа).
2. `.bss` `[0x5EB00, 0x5EE3C)` обнуляется **восьмёрками байт**: длина делится на 8,
   из результата вычитается 1 (счётчик `repeat`), тело цикла пишет два слова по
   `($2)` и `4($2)`. Это доказывает, что окно `0x40000..0x5FFFF` — RAM: образ лежит
   в ней целиком, вместе с `.data` и `.bss`.
3. `$sp` берётся из `$0`: аппаратура сброса CMeP оставляет там вершину стека, а
   загрузчик переносит её в `$sp`. `$gp = 0x5EB00`, `$tp = 0x5E820`.
4. `beqi $9,5` — классическая защита «нас вызвал монитор/отладчик»: при `$9 == 5`
   окружение монитора не затирается. В модели `$9 == 0`, поэтому ветка не берётся.
5. `$1 = 0x40000` (буфер следующей стадии) и `bsr 0x5c4fe` — вызов `main`. Возврат
   `bsr` кладёт в `$lp` (в MeP-c5 `bsr` пишет `$lp`, а не стек; сам `main` сохраняет
   его через `ldc $0,$lp` и `sw $0,4($sp)`).

### В модели

```cpp
// src/machine/bootchain.cpp
case BootStage::CmepFirstLoader:
    cmep_->reset(config_.first_loader_base);
    cmep_->prepare_reset_context(board::kCmepStackTop, 0x00040000, 0, 0);
    cmep_->halted = false;
```

`prepare_reset_context` кладёт в `$0` только первый аргумент (вершина стека
`0x60000`); остальные аргументы модель игнорирует — `$1 = 0x40000` загрузчик
выставляет сам (`0x5C03C`). Образ ставится в окно RAM `0x40000..0x5FFFF`
(`cmep::kRamBase`, 128 КиБ, `CMeP.RAM`).

### Измерено

* на `0x5C004`: `$0 = 0x00060000`, остальные регистры нулевые;
* на `0x5C040`: `$0 = 0` (после `stc $0,$hi/$lo` и `mov $0,0`), `$1 = 0x40000`,
  `$2 = 0x5EE38` (указатель дошёл до конца `.bss`), `$gp = 0x5EB00`, `$tp = 0x5E820`;
* на входе `main` (`0x5C4FE`): `$0 = 0`, `$1 = 0x40000`, `$lp = 0x5C045`;
* в первом же прогоне модель печатает `CMeP first loader entered at 0x5C004`.

## 2. `init_emmc_keyrings`: eMMC-крипта и её keyring-слоты (шаг 2)

**Где:** `0x5C0B8`, вызывается из `main` (`0x5C50C`) и, повторно, из
`boot_path_bit5` (`0x5C2B2`).

### Листинг

```asm
; ---- init_emmc_keyrings  ; called from: 5C2B2, 5C50C
5C0B8  01 59          mov $9,1
5C0BA  21 c4 07 e0    movh $4,0xe007
5C0BE  21 cc 03 e0    movh $12,0xe003
5C0C2  21 ca 0f 1c    movh $10,0x1c0f
5C0C6  21 cb 0f 1c    movh $11,0x1c0f
5C0CA  21 c3 07 e0    movh $3,0xe007
5C0CE  20 63          add $3,8
5C0D0  b4 cb 0f 02    or3 $11,$11,0x20f     ; $11 = 0x1C0F020F
5C0D4  a4 ca 0e 02    or3 $10,$10,0x20e     ; $10 = 0x1C0F020E
5C0D8  c4 cc 24 00    or3 $12,$12,0x24      ; $12 = 0xE0030024 KeyringClearFlags
5C0DC  ca 0a          sw $10,($12)          ; mask 0x1C0F -> keyring 0x20E
5C0DE  21 ca 0e 02    movh $10,0x20e
5C0E2  a4 ca 0f 02    or3 $10,$10,0x20f     ; $10 = 0x0000020F
5C0E6  ca 0b          sw $11,($12)          ; mask 0x1C0F -> keyring 0x20F
5C0E8  3a 0a          sw $10,($3)           ; 0xE0070008 <- 0x020E020F
5C0EA  4a 09          sw $9,($4)            ; 0xE0070000 <- 1
5C0EC  02 70          ret
```

### Что происходит

1. Снимаются флаги `0x1C0F` у двух служебных слотов eMMC-крипты — `0x20E` и `0x20F`
   (формат слова `KeyringClearFlags`: индекс в младших 13 битах, маска выше).
   Это не keyring'и загрузчика, а слоты, которыми шифруется поток eMMC.
2. В `0xE0070008` записывается пара индексов `0x020E020F` (старшее/младшее полуword).
3. В `0xE0070000` пишется `1` — тумблер eMMC-крипты.

### В модели

`EmmcCryptoDevice` (`src/hw/cmep/mailbox.cpp`) хранит `EmmcCryptoToggle` и индексную
пару, `enabled_` поднимается по биту 0; `KeyringDevice::write` трактует слово как
`index = v & 0x1FFF`, `mask = v & ~0x1FFF` и пишет в `clear_history_`.

### Измерено

```text
[wtrap] +0xE0030024 w4 = 0x1C0F020E pc=0005C0DE core=CMeP
[wtrap] +0xE0030024 w4 = 0x1C0F020F pc=0005C0E8 core=CMeP
[wtrap] +0xE0070008 w4 = 0x20E020F  pc=0005C0EA core=CMeP
[wtrap] +0xE0070000 w4 = 0x1        pc=0005C0EC core=CMeP
```

* на входе (`0x5C0B8`): `$0 = 0x5C045` (адрес возврата `main`), `$1 = 0x40000`;
* на выходе (`0x5C0EE`): `$3 = 0xE0070008`, `$12 = 1`, то есть тумблер действительно
  взведён, и это подтверждает `keyring`-отчёт: в истории `ClearFlags` ровно две
  первые записи — `0x1C0F020E` и `0x1C0F020F`.

## 3. `check_boot_mode`: откуда берётся режим загрузки (шаг 3)

**Где:** `0x5C0EE`, вызывается из `main` (`0x5C50E`).

### Листинг

```asm
; ---- check_boot_mode  ; called from: 5C50E
5C0EE  01 ca 01 05    mov $10,1281           ; 0x501
5C0F2  21 cc 03 e0    movh $12,0xe003
5C0F6  21 cb 03 e0    movh $11,0xe003
5C0FA  b4 cb 2c 00    or3 $11,$11,0x2c      ; $11 = 0xE003002C (ответ)
5C0FE  c4 cc 28 00    or3 $12,$12,0x28      ; $12 = 0xE0030028 (запрос)
5C102  ca 0a          sw $10,($12)          ; запросить флаги keyring 0x501
5C104  be 0c          lw $12,($11)          ; $12 = ответ
5C106  c5 c4 03 00    and3 $4,$12,0x3
5C10A  34 e4 0e 00    bnei $4,0x3,0x5c126   ; не готов -> -1
5C10E  21 c9 06 e0    movh $9,0xe006
5C112  94 c9 20 20    or3 $9,$9,0x2020      ; $9 = 0xE0062020 (страп, 32 байта)
5C116  9e 0c          lw $12,($9)           ; младшее слово страпа
5C118  c5 cb 01 00    and3 $11,$12,0x1
5C11C  06 ab          beqz $11,0x5c122
5C11E  41 50          mov $0,65             ; 'A' = 0x41
5C120  02 70          ret
; ---- loc_5C122
5C122  21 50          mov $0,33             ; '!' = 0x21
5C124  02 70          ret
; ---- loc_5C126
5C126  ff 50          mov $0,-1
5C128  02 70          ret
```

### Что происходит

1. В `KeyringQueryFlagsRequest` (`0xE0030028`) кладётся `0x501`, ответ читается из
   `0xE003002C`. Младшие два бита должны быть `11` — иначе keyring `0x501` непригоден
   и функция возвращает `-1` (в `main` это уводит на recovery-пути `0x5C514`).
2. Читается младшее слово 32-байтового блока `0xE0062020` (страп/JIG). Бит 0 даёт
   `'A'` (`0x41` — «нормальная» загрузка), ноль — `'!'` (`0x21`, сервисная).

Биты режима далее используются так: `bit0` — «образ придёт от ARM через mailbox
`0xE0000010`», `bit5` — `boot_path_bit5` (SD/eMMC + SC), `bit6` — `boot_path_bit6`;
`'A' = bit0|bit6`, `'!' = bit0|bit5`. То есть режим — не число, а набор флагов,
который `main` передаёт дальше и в `process_image`, и в `keyring_set_value`.

### В модели

`StrapDevice` отдаёт 32-байтовый блок, у которого бит 0 сброшен
(`CmepBlock::reset()` → `strap_device().set_bit0(false)`), поэтому **гость вычисляет
`'!' = 0x21`**. `KeyringDevice` на запрос `0x501` отвечает `owner_.keyring_flags()`,
по умолчанию `3` («все флаги сняты») — проверка `($12 & 3) == 3` проходит.

Поле `CmepBlock::boot_mode_` (по умолчанию `0x41`) — это **значение модели по
умолчанию, а не то, что вычислил гость**; отчёты `boot`/`keyring` печатают именно
его, поэтому в них видно `boot mode: 0x41`, тогда как `$8` в регистрах равен `0x21`.
Оба варианта берут путь `bit0`, но различаются записью в keyring `0x501` (см. §14).

### Измерено

```text
[wtrap] +0xE0030028 w4 = 0x501      pc=0005C104 core=CMeP
[rtrap] +0xE003002C r4 = 0x10000003 pc=0005C106 core=CMeP
[wtrap] ... 0xE0062020 не пишется, читается гостем
```

* на входе в путь `bit0` (`0x5C574`): `$0 = $8 = 0x21` (`'!'`), `$1 = 0x40000`,
  `$3 = 0xE0070008`, `$9 = 0xE0062020`;
* `$8 = 0x21` на всём протяжении пути `bit0` (`0x5C574`…`0x5C61C`).

## 4. `main`: разбор режима и выбор пути (шаг 4)

**Где:** `0x5C4FE`, продолжение после `init_emmc_keyrings` и `check_boot_mode`.

### Листинг

```asm
; ---- main  ; called from: 5C040
5C510  08 e0 2e 00    bgei $0,0x0,0x5c56c   ; режим >= 0 -> берём его
; --- fallback: keyring 0x501 недоступен (0x5C514..0x5C56A, в 1.04 не исполняется)
; ---- loc_5C56C
5C56C  00 08          mov $8,$0             ; $8 = режим ('A'/'!')

5C56E  85 cc 01 00    and3 $12,$8,0x1
5C572  44 ac          beqz $12,0x5c5b6      ; bit0 нет -> альтернативные пути
; ---- loc_5C574  (bit0: образ от ARM через mailbox)
...
; ---- loc_5C5B6  (bit5)
5C5B6  85 cc 20 00    and3 $12,$8,0x20
5C5BA  0c ac          beqz $12,0x5c5c6

5C5C0  0c e0 fe ff    blti $0,0x0,0x5c5bc   ; ошибка -> повтор

5C5C6  85 cc 40 00    and3 $12,$8,0x40

5C5CC  60 01          mov $1,$6
5C5CE  cb bd          bsr 0x5c398           ; boot_path_bit6
5C5D0  0c e0 fe ff    blti $0,0x0,0x5c5cc

5C5D4  f0 03          mov $3,$sp
5C5D6  80 01          mov $1,$8             ; $1 = режим
```

### Что происходит

1. `check_boot_mode` вернул `'A'`/`'!'` (`>= 0`) — режим сохраняется в `$8`; иначе
   идёт fallback-ветка (`0x5C514..0x5C56A`) с recovery-кодами `0x20/0x22/0x44`,
   регистрами SC `0xE3101100/2100/3040/3050` и `mailbox_debug_sc` (`0x5E4E4`).
2. По битам режима выбирается источник образа: `bit0` — mailbox (нормальная загрузка),
   `bit5` — `boot_path_bit5` (`0x5C206`, SC + SD/eMMC), `bit6` — `boot_path_bit6`
   (`0x5C398`). Если не подошёл ни один — путь отказа.
3. Общее продолжение: `process_image($1 = режим, $2 = 0x40000, $3 = &value)`, где
   `value` — слово на стеке `main`, куда `process_image` положит значение для

`boot_path_bit5`/`boot_path_bit6` реальным кодом не исполняются: модель подаёт образ
через путь `bit0` (ARM boot ROM кладёт контейнер в DRAM и пишет `PA|1` в mailbox).
Именно поэтому в измеренном прогоне `sc transfers = 0`, а покрытие не содержит
`0x5C206..0x5C4FE` и `0x5C5B6..0x5C5D2`.

### Измерено

* `0x5C574` (вход в путь `bit0`): `$0 = $8 = 0x21`, `$1 = 0x40000`, `$3 = 0xE0070008`,
  `$9 = 0xE0062020`;
* `cov mep` перечисляет неисполненными ровно альтернативные блоки
  `0x5C206-0x5C4FE` (760 байт) и `0x5C5B6-0x5C5D4` (30 байт).

## 5. Путь `bit0`: mailbox и копирование контейнера в `0x40000` (шаг 5)

**Где:** `0x5C574..0x5C5B4`.

### Листинг

```asm
; ---- loc_5C574
5C574  21 ca 00 e0    movh $10,0xe000
5C578  40 6a          add $10,16            ; $10 = 0xE0000010 (ARM -> CMeP)
5C57A  ae 07          lw $7,($10)           ; опрос: младший бит = "образ готов"
5C57C  75 cb 01 00    and3 $11,$7,0x1
5C580  f4 ab          beqz $11,0x5c574      ; нет -> ждать
5C582  60 01          mov $1,$6             ; $1 = 0x40000 (куда)
5C584  40 53          mov $3,64             ; 64 байта заголовка
5C586  fc 5c          mov $12,-4
5C588  c1 17          and $7,$12            ; $7 = PA & ~3
5C58A  70 02          mov $2,$7             ; $2 = PA (откуда)
5C58C  09 dc 20 00    bsr 0x5e60c           ; memcpy(0x40000, PA, 64)
5C590  60 01          mov $1,$6
5C592  59 dc 00 00    bsr 0x5c61c           ; validate_header(0x40000)
5C596  0c e0 34 00    blti $0,0x0,0x5c5fe   ; плохой заголовок -> отказ
5C59A  60 c1 40 00    add3 $1,$6,64         ; dst = 0x40040
5C59E  6e c4 10 00    lw $4,16($6)          ; $4 = field (+0x10) = длина тела
5C5A2  6e c3 04 00    lw $3,4($6)           ; $3 = size (+0x04)
5C5A6  70 c2 40 00    add3 $2,$7,64         ; src = PA+64
5C5AA  3c 94          add3 $12,$4,$3        ; $12 = field + size
5C5AC  c0 c3 c0 ff    add3 $3,$12,-64       ; len = field + size - 64
5C5B0  e9 da 20 00    bsr 0x5e60c           ; memcpy(0x40040, PA+0x40, len)
5C5B4  20 b0          bra 0x5c5d4
```

### Что происходит

1. Цикл `0x5C57A..0x5C580` ждёт, пока в `0xE0000010` появится бит 0 — «образ
   подготовлен ARM boot ROM».
2. Значение маскируется по `~3` (выравнивание на 4) и трактуется как физический
   адрес источника. Первые 64 байта копируются в `0x40000` — это заголовок ENP.
3. `validate_header(0x40000)`; отрицательный результат уводит на путь отказа `0x5C5FE`.
4. Тело: `len = [image+0x10] + [image+0x04] - 64` байт копируются из `PA+0x40` в
   `0x40040`. Для 1.04 это `0x16600 + 0x2C0 - 0x40 = 0x16880` байт: остаток заголовка,
   записи ключей, digest-таблица, подпись и зашифрованное тело.
5. `memcpy` (`0x5E60C`) попутно считает сумму всех скопированных слов в `$0` — по ней
   в отладчике видно, что копирование состоялось.

### В модели (кто пишет в mailbox)

```cpp
// src/machine/bootchain.cpp - ARM boot ROM, которого нет в дампах
stage_in_dram(board::kSecondLoaderStagingDram, staged);   // 0x407C0000
second_loader_pa_ = board::kSecondLoaderStagingDram;
cmep_block_->set_arm_to_cmep_command(second_loader_pa_ | 1u);
```

Модель ставит в DRAM `second_loader.enc` (именно `.enc`: распаковка в §12 — настоящий
AES-128-CBC, и на вход ему нужен шифротекст), пишет `0xE0000010 = 0x407C0001`
(`PA | 1`) и при `config_.provision_keys` подкладывает dev-ключ и переподписывает
образ (§9).

### Измерено

* `0x5C592` (перед `validate_header`): `$7 = 0x407C0000` (PA), `$2 = 0x407C0040`,
  `$3 = 0x0F`, `$0 = 0xA6151019` (сумма 16 скопированных слов), `$1 = 0x40000`;
* `[rtrap] +0xE0000010 r4 = 0x407C0001 pc=0005C58C` — гость читает ровно то, что
  записала модель;
* в логе модели: `mailbox 0xE0000010 <- 0x407C0001 (image present)`, а также
  `ARM boot ROM staged second_loader.enc at 0x407C0000 (93184 bytes)`.

## 6. `validate_header`: проверки контейнера ENP (шаг 6)

**Где:** `0x5C61C`, вызывается из `main` (`0x5C592`) и из `process_image` (`0x5CC36`).

### Листинг

```asm
; ---- validate_header  ; called from: 5C592, 5CC36
5C61C  21 cb b2 64    movh $11,0x64b2
5C620  1e 0c          lw $12,($1)           ; +0x00 magic
5C622  b4 cb e5 c8    or3 $11,$11,0xc8e5    ; 0x64B2C8E5
5C626  b5 ec 24 00    bne $12,$11,0x5c66e
5C62A  1e c9 04 00    lw $9,4($1)           ; +0x04 size
5C62E  93 c0 b0 02    sltu3 $0,$9,0x2b0
5C632  3d a0          bnez $0,0x5c66e       ; size >= 0x2B0
5C634  90 0a          mov $10,$9
5C636  21 cc 01 00    movh $12,0x1
5C63A  c3 09          sltu3 $0,$9,$12
5C63C  32 a0          beqz $0,0x5c66e       ; size < 0x10000
5C63E  90 0b          mov $11,$9
5C640  1e c9 08 00    lw $9,8($1)           ; +0x08 offset
5C644  b3 09          sltu3 $0,$9,$11
5C646  28 a0          beqz $0,0x5c66e       ; offset < size
5C648  1e cb 0c 00    lw $11,12($1)         ; +0x0C length
5C64C  1e cc 04 00    lw $12,4($1)
5C650  c3 0b          sltu3 $0,$11,$12
5C652  1c a0          beqz $0,0x5c66e       ; length < size
5C654  90 0a          mov $10,$9
5C656  a9 9b          add3 $9,$11,$10
5C658  90 c2 b0 02    add3 $2,$9,688        ; offset + length + 0x2B0
5C65C  25 ec 09 00    bne $12,$2,0x5c66e    ; size == offset+length+0x2B0
5C660  1e c3 10 00    lw $3,16($1)          ; +0x10 field
5C664  00 d4 c0 01    movu $4,0x1c000
5C668  cc 93          add3 $12,$3,$12
5C66A  43 0c          sltu3 $0,$12,$4
5C66C  07 a0          bnez $0,0x5c672       ; field + size < 0x1C000
; ---- loc_5C66E
5C66E  ff 50          mov $0,-1
5C670  02 70          ret
; ---- loc_5C672
5C672  1f cc 16 00    lhu $12,22($1)        ; u16 @ +0x16
5C676  81 6c          slt3 $0,$12,0x10
5C678  f6 a0          beqz $0,0x5c66e       ; u16 < 0x10
5C67A  00 50          mov $0,0
5C67C  02 70          ret
```

### Что происходит

Проверки заголовка ENP (все границы — жёсткие, отказ даёт `-1`):

| Смещение | Поле | Проверка |
|---|---|---|
| `+0x00` | magic | `== 0x64B2C8E5` |
| `+0x04` | size | `0x2B0 <= size < 0x10000` |
| `+0x08` | offset | `offset < size` |
| `+0x0C` | length | `length < size` |
| `+0x04` | size | `size == offset + length + 0x2B0` |
| `+0x10` | field (длина тела) | `field + size < 0x1C000` |
| `+0x16` | u16 | `< 0x10` |

Поле `+0x14` (u16) в прототипной сборке **не проверяется** — его читает
`process_image`, чтобы вернуть значение в keyring-запись; в retail-сборке для него
добавлена проверка `< 6` (§17).

### Измерено (поля контейнера 1.04, `Out/SLB2/second_loader.enp`)

```text
magic=0x64B2C8E5 size=0x2C0 offset=0x10 length=0x0 field=0x16600 u16@0x14=0 u16@0x16=0
```

Все проверки проходят: `0x2C0 == 0x10 + 0 + 0x2B0`, `0x16600 + 0x2C0 = 0x168C0 < 0x1C000`.
На входе `0x5C61C` измерено `$1 = 0x40000`, `$2 = 0x407C0040` (остаток от копирования),
`$7 = 0x407C0000`, `$8 = 0x21`, `$12 = 0xFFFFFFFC`; на выходе `$0 = 0`.

## 7. `process_image`: диспетчер пяти этапов (шаг 7)

**Где:** `0x5CC00`, вызывается из `main` (`0x5C5DA`) с аргументами

### Что происходит

1. Диспетчер вычисляет **три указателя в контейнере**, и они определяют раскладку
   всех последующих этапов:

   | Выражение | Для 1.04 | Что это |
   |---|---|---|
   | `$5 = image + 0x40 + offset` | `0x40050` | база битовых карт и таблиц инвалидации (этап D) |

   | `$tp = $6 + length` | `0x400E0` | конец записей (`length = 0` в 1.04) |
   | `$tp + 0x1E0` | `0x402C0` | зашифрованное тело (`image + 0x2C0`) |

2. Затем последовательно вызываются пять этапов; **любой отрицательный результат
   немедленно завершает `process_image`** (и `main` уходит на путь отказа).
3. После этапов: операция по месту над хвостом окна, «rng»-обнуление окна Bigmac и
   запись `u16 @ image+0x14` в слот `main` (это значение попадёт в keyring `0x501`).

### В модели

Дизассемблированный `process_image` исполняется целиком; модель лишь предоставляет
устройства, к которым он обращается. Никаких подстановок в этом шаге нет.

### Что происходит

1. Ключ из `.data` (`0x5E704`) программируется в keyring **8** с флагами `0x206`,
   после чего копия в RAM затирается (`memset`) — «гигиена ключей» из ANALYSIS §7.
2. Дальше путь зависит от бита 5 режима:
   * **bit5 установлен** (`'!'` = `0x21`): материал keyring 9 (`0x5E724`) и буфер
     `0x5E890` **стираются**, а не программируются; затем идёт keyed-операция
     Bigmac `0x010A` с индексом 8 и ключом `0x5E880`, вызванная «по месту»
     (источник и приёмник — один и тот же адрес `0x400E0`, длина `0x167E0`);
   * **bit5 снят** (`'A'` = `0x41`): keyring **9** получает ключ `0x5E724`
     с флагами `0x207`, и та же keyed-операция выполняется с индексом 9 и ключом
     `0x5E890`.
3. В конце — четыре записи `KeyringClearFlags`, которыми слоты `0x008`, `0x009`,
   `0x206`, `0x207` переводятся в «заблокировано»: `WriteByCmepAllowed` снят.

`0x010A` здесь — не распаковка: источник и приёмник совпадают, поэтому операция
трактуется как **проверка под ключом** (в модели — «успех» без преобразования
данных), а не как AES-расшифровка (она в §12, где источник `0x402C0` и приёмник
`0x40000` различаются).

### Что происходит

1. Ключ `0x5E744` программируется в keyring **0x20** (флаги `0x344`), копия в RAM
   стирается, слот тут же блокируется (`0x1C1F0344`).
2. Считается **SHA-256 от `image[0:0x1C0]`** (заголовок контейнера до подписи) в
   буфер `0x5EDC0` — это «хеш сообщения», которое подписано.
3. Выбирается ключ-модуль:
   * если младшие 16 бит страп-регистра `0xE0064060` равны нулю — берётся блок из
     ROM `0x5E970`;
   * иначе требуется, чтобы в страпе был выставлен бит с номером `u16 @ image+0x16`,
     и модуль берётся из таблицы `0xE0066000` по индексу
     `((u16<<3) + 0x700) & 0xFF`, шаг записи 32 байта. Для 1.04 `u16 = 0`, значит
     нужен бит 0 страпа и индекс 0 → `0xE0066000`.
4. `bignum_op` возводит 256-байтовую **подпись** `image+0x1C0` в степень
   `e = 0x00010001` по модулю выбранного ключа (RSA-2048, публичная операция).
5. Результат проверяется как блок **PKCS#1 v1.5**:
   `00 01 FF×203 00` (206 байт), затем 18 байт DigestInfo, совпадающие с константой
   ROM `0x5E774`, затем 32 байта, совпадающие с SHA-256 заголовка из `0x5EDC0`.
   Итого 256 байт; любое расхождение — отказ.
6. Последний цикл (128 итераций) снимает флаг `0x1000` у keyring `0x700..0x77F` —
   таблица ключей, которой только что пользовались, инвалидируется.

### В модели

* `bignum.cpp` — настоящая модульная экспонента (школьное умножение + деление
  бит за битом) над 64-словными окнами `0xE0040108` (основание — подпись) и
  `0xE0040400` (модуль), синхронизация через `0xE0020020`, статус `0xE0040804`.
* `bootkeys.cpp` подставляет **dev-ключ**: пишет 64 слова модуля в
  `0xE0066000`, ставит `0xE0064060 = 1` (чтобы гость выбрал таблицу, а не ROM) и
  переписывает 256 байт `image+0x1C0` готовой подписью. Подписываемый блок
  собирается из ROM-констант самого загрузчика (`0x5E774`) и SHA-256 того же
  заголовка, поэтому проверки в п.5 проходят по-настоящему:
  `00 01 FF×203 00 ‖ ROM[0x5E774:18] ‖ SHA-256(image[0:0x1C0])`.
  Если подставленный образ — другая сборка, `provision_boot_keys` отказывается
  работать (`sha256` блока не совпадает с ожидаемым) — это и происходит с
  retail-образом, см. §17.
* `read_keyring` для таблицы `0xE0066000` модель не эмулирует: она пишет в неё
  данные, а гость читает их обычной шиной (`sl2ad3` в `bignum_op`).

```asm
5C9FE  ba 0c          sw $12,($11)          ; KeyringClearFlags <- 0x1C1F0020

5CA04  08 a0          beqz $0,0x5ca0c

```

Перед этим (0x5C986…0x5C9B4) идут записи `KeyringClearFlags` для
`0x1C1F0208..0x1C1F020D` — слоты, из которых только что читали материал.

### Что происходит

1. **Слот 10.** Гость читает keyring-слот 10 (32 байта) в буфер `0x5E8A0`, но с
   флагами `0x208` и «маленьким» индексом в поле `+0x04` — это форма **загрузки
   слота** (`+0x04` < 0x1000 = индекс, а не адрес). Источником служит `image+0xE0`,
   то есть материал, привезённый в контейнере.
2. **Слоты 11..15** читаются тем же способом из `image+0x100 + 0x20*i`, каждый
   результат затем частично затирается (`memset(…, 0, 16)`); буферы `0x5E900` идут
   с шагом 16 байт, поэтому «окна» перекрываются — в RAM остаётся только вторая
   половина каждого.
3. **Digest-таблица.** 32 байта `image+0x1A0` читаются «большой» формой
   (`+0x04` = приёмник `0x5EDE0`, индекс ключа — в поле флагов: `10`) — на железе
   это разворачивание блока ключом слота 10.
4. **Хеш тела.** SHA-256 от `image+0x2C0` длиной `[image+0x10]` пишется в `0x5EE00`
   и сравнивается (`memcmp`) с развёрнутой таблицей `0x5EDE0`. Совпадение —
   единственное, что связывает подписанный заголовок с зашифрованным телом.
5. Затем снимаются флаги `0x1C1F0208..0x20D` и `0x1C1F0020` — прочитанный материал
   и keyring `0x20` инвалидируются.

### В модели

```cpp
// keyring.cpp / bigmac.cpp: чтение слота в двух формах
if (cmd.small_index()) {           // +0x04 < 0x1000 -> это загрузка слота
    std::vector<u8> existing;
    if (!owner_.keyring_device().read_keyring(cmd.index(), existing)) {
        owner_.keyring_device().stage_keyring(cmd.index(), cmd.flags, block);
    }
    return ok();                   // уже запрограммированный (fused) слот не трогаем
}
std::vector<u8> value;
if (!owner_.keyring_device().read_keyring(cmd.flags, value)) value.assign(32, 0);
// «большая» форма трактуется как копия блока, а не как разворачивание ключом:
if (cmd.raw_command >= 0x400) owner_.keyring_device().copy_to_bus(cmd.raw_command, block);
```

Два следствия, которые видно в измерениях:

* слот **10** остаётся «fused»: `KeyringDevice::reset()` программирует его парой
  `ENC_KEY ‖ ENC_IV` (`AAAA…` ‖ `AF5F…`), и загрузка из `image+0xE0` (там
  `5496a709…` в `.enc`) игнорируется — как на однократно программируемом слоте;
* слоты **11..15** пусты, поэтому модель их действительно программирует материалом
  из образа (`7B4542BD…`, `599E84A4…`, … — ровно байты `second_loader.enc[0x100…]`);
* разворачивание digest-таблицы модель делает **копией**, поэтому `bootkeys.cpp`
  заранее кладёт в `image+0x1A0` сам SHA-256 тела
  (`provisioned the payload digest at image+0x1A0`) — иначе `memcmp` в п.4 не сошёлся бы.

## 11. Этап D: `img_proc_5CA1C` — таблицы инвалидации контейнера (шаг 11)

**Где:** `0x5CA1C`, вызывается из `process_image` (`0x5CC66`) с
`$1 = image+0x40+offset` (`0x40050`), `$2 = $6` (`0x400E0`), `$3 = length` (`0`).

### Листинг (начало и структура)


### Что происходит

Контейнер сам сообщает, какие keyring'и надо аннулировать после проверки — и
`img_proc_5CA1C` добросовестно проходит по этим таблицам:

1. две **битовые карты** (по слову на `+0x00` и `+0x04`): биты дают индексы
   `0x200+i` (24 бита) и `0x600+i` (8 бит) с маской `0x1C1F`;
2. шесть **байтовых таблиц** (`+0x10`, `+0x20`, `+0x30`, `+0x50`, `+0x60`, `+0x70`)
   по 128/256 записей: байт для каждого бита — это индекс keyring'а, который надо
   снять (маска `0x1C1F`);
3. если `length` (поле `image+0x0C`) ненулевое — дополнительный обход
   3-байтовых записей по указателю `$2`.

Для 1.04 **все эти таблицы нулевые** (проверено чтением `second_loader.enc`:
`image+0x50..0xDF` — нули), поэтому этап не делает ни одной записи в устройства; и
`length = 0`, поэтому хвостовой обход тоже пропускается. В карте покрытия это видно
как неисполненные участки внутри этапа: `0x5CA28-0x5CA3C`, `0x5CA50-0x5CA64`,
`0x5CAAA-0x5CABE`, `0x5CB60-0x5CBB8` и соседние.

### В модели

Этап исполняется реальным кодом; модель только применяет записи `ClearFlags`.
Важное наблюдение модели (не подтверждённое железом): слово трактуется как
`index = v & 0x1FFF`, `mask = v & ~0x1FFF`, а `locked` выводится из бита `0x0800`
записанных флагов слота. Для наблюдавшихся значений (`0x1C1F0344`, `0x10000700`…)
это означает, что `flags` слотов в отчёте остаются такими, какими их записал
триггер (`0x206`, `0x208`, `0x200`, `0x344`), а запись `ClearFlags` служит
историей и признаком замка.

### Измерено

* вход `0x5CA1C`: `$1 = 0x40050`, `$2 = 0x400E0`, `$3 = 0` (length), `$4 = 0`;
* за весь прогон **нет ни одной** записи в `0xE0030024`, у которой pc лежал бы в
  `0x5CA28..0x5CBB2`: таблицы контейнера пусты;
* в покрытии этот этап — один из крупнейших «неисполненных» участков.

### В модели

то есть из «fused» значения, которое модель собирает из `ENC_KEY`/`ENC_IV`
(`KeyringDevice::fused_boot_key`, `src/loader/keys.h`). Поэтому в модель подаётся
именно **`second_loader.enc`**: расшифровка выполняется по-настоящему, и уже
расшифрованный образ исполняется с `0x40000`.

## 13. Хвост окна: операция `0x000C` и «rng»-обнуление (шаг 13)

**Где:** `process_image`, `0x5CC7C..0x5CC92` (сразу после успешного этапа E).

### Листинг

```asm
5CC7C  71 98          add3 $1,$8,$7         ; $1 = image + field  = 0x56600
5CC7E  00 52          mov $2,0
5CC80  00 d3 c0 01    movu $3,0x1c000
5CC84  74 03          sub $3,$7             ; $3 = 0x1C000 - field = 0x5A00
5CC86  09 dc 00 00    bsr 0x5cd06           ; keyring_op: function 0x000C, по месту
5CC8A  0c e0 07 00    blti $0,0x0,0x5cc98
5CC8E  49 da 01 00    bsr 0x5cdd6           ; bigmac_rng
5CC92  0b 4c          lw $12,0x8($sp)
5CC94  00 50          mov $0,0
5CC96  ca 06          sw $6,($12)           ; *value = u16 @ image+0x14
```

### Что происходит

1. `keyring_op_5CD06` (0x5CD06) выставляет `function = 0x000C`, `+0x04 = +0x00 = $1`
   и `+0x08 = $3`: операция **по месту** над участком `[image+field, 0x1C000)`, то
   есть над «хвостом» окна `0x40000..0x5FFFF`, который не занят образом второй
   стадии (`0x40000 + 0x16600 = 0x56600`, до `0x5C000`). Содержимое этого участка
   нигде не читается до перезапуска CMeP, поэтому операция выглядит как
   «затирание/подготовка» остатка окна.
2. `bigmac_rng` (0x5CDD6) пишет нули в `0xE0050000`, `+0x04`, `+0x08`, `+0x14`,
   `+0x0C` — то есть **обнуляет окно ключа/команды Bigmac** и возвращается.
   Команда при этом не запускается: бит старта `+0x1C` не выставляется.
3. В слот `*value` (`main` передал `$3 = $sp`) кладётся `u16 @ image+0x14`
   (в 1.04 — `0`); это значение уйдёт в запись keyring `0x501` (§14).

### В модели

* `0x000C` — это `BigmacFunction::AesCbcDecrypt`; для вызова «по месту»
  (`pointer == raw_command`) ветка `0x010A` возвращает «успех» без преобразования,
  а вот `0x000C` уходит в общий AES-путь и **реально** расшифровывает хвост
  нулевым ключом (16 нулевых байт, поскольку `flags = 0`). Регион не используется,
  поэтому на цепочку это не влияет, но это модельное допущение, а не проверенный
  факт: настоящая семантика `0x000C` в дампах не подтверждена.
* `0x5CDD6` в модели — `BigmacOp::Rng`; однако гость не выставляет бит старта,
  поэтому операция RNG в этом прогоне **не выполняется**: наблюдаются только
  записи нулей (см. измерения). Детерминированный RNG модели (`DeterministicRng`)
  используется второй стадией, не первым загрузчиком.

```text
[wtrap] +0xE0050004 w4 = 0x0     pc=0005CDF8   ; bigmac_rng: обнуление окна
[wtrap] +0xE0050000 w4 = 0x0     pc=0005CDFA
```

```asm
5C618  00 b0          bra 0x5c618           ; вечный цикл
```

`keyring_set_value` (`0x5C12A`) в этом вызове (режим `0x21`, `$2 = 0`):

```asm
5C12A  80 6f          add $sp,-32
5C12E  15 cb 01 00    and3 $11,$1,0x1
5C132  33 ab          bnez $11,0x5c164      ; bit0 установлен -> запись = страп + режим
; ---- loc_5C164  (32 байта из страп-блока 0xE0062020)
5C164  17 6c          sll3 $0,$12,0x2
5C166  04 6c          add $12,1
5C168  21 ca 06 e0    movh $10,0xe006
5C16C  a4 ca 20 20    or3 $10,$10,0x2020    ; $10 = 0xE0062020
5C170  a4 90          add3 $4,$0,$10
5C172  4e 09          lw $9,($4)            ; read 0xE0062020 + 4*$12
5C174  0b 9f          add3 $11,$sp,$0
5C176  ba 09          sw $9,($11)           ; -> локальный буфер на стеке
5C178  8c ec f6 ff    blti $12,0x8,0x5c164
5C17C  e7 62          sll3 $0,$2,0x1c      ; $0 = ($2 & 0xF) << 28
5C17E  1f 4c          lw $12,0x1c($sp)      ; $12 = word7
5C180  21 cb 00 10    movh $11,0x1000
5C186  fc 6b          add $11,-1            ; $11 = 0x0FFFFFFF
5C184  fe 04          lw $4,($sp)           ; $4 = word0
5C188  44 ca 04 00    or3 $10,$4,0x4        ; word0 |= 4
5C18C  b1 1c          and $12,$11           ; word7 &= 0x0FFFFFFF
5C18E  c0 10          or $0,$12             ; word7 |= ($2 & 0xF) << 28
5C190  fa 0a          sw $10,($sp)
5C192  ...                                   ; запись 8 слов в KeyringNewValue[0..7]
5C1FE  9a 0b          sw $11,($9)          ; 0xE0030020 <- 0x501 (триггер)
5C200  ca 0a          sw $10,($12)         ; 0xE0030024 <- 0x08000501 (замок слота)
```

### Что происходит

1. Успешный путь: `keyring_set_value` строит 256-битную запись для слота `0x501`
   и **этим передаёт режим следующей стадии**: при установленном `bit0` берётся
   32 байта страп-блока `0xE0062020`, к первому слову добавляется бит `0x4`, а
   старшие 4 бита (28..31) последнего слова заменяются на `($2 & 0xF) << 28`; затем
   пишется триггер `0x501` и снимается флаг `0x0800` (слот запирается).
2. В `0xE0000000` пишется `1` — «success» для ARM; `main` восстанавливает регистры
   и возвращается в `_start`.
3. Путь отказа: читается статус-исключение Bigmac (`0xE005003C`), вызывается
   `delay_ticks` (задержка через сопроцессорные регистры `0x400..0x405`),
   в `0xE0000000` пишется `2` и загрузчик уходит в **вечный цикл** `0x5C618`.

### В модели

* `0xE0000000` — `MailboxDevice`; `CmepBlock::reported_success()`/`reported_failure()`
  читают это слово, `Vita::poll_boot_chain()` по нему фиксирует milestone
  `first loader reported SUCCESS to the ARM mailbox` либо переводит цепочку в
  `Failed` и печатает pc (по нему видно, *какая* проверка отвергла образ).
* keyring `0x501`: модель отвечает на запрос флагов значением `3`
  (`CmepBlock::keyring_flags_`), а саму запись сохраняет как слот.

### Измерено

```text
[wtrap] +0xE0030000 w4 = 0x4     pc=0005C1A6   ; KeyringNewValue[0] = страп[0] | 4
[wtrap] +0xE0030004 w4 = 0x0     pc=0005C1AC
... (слова 1..6 = 0)
[wtrap] +0xE003001C w4 = 0x0     pc=0005C1FE   ; word7 = ($2 & 0xF) << 28 = 0
[wtrap] +0xE0030020 w4 = 0x501   pc=0005C200   ; триггер
[wtrap] +0xE0030024 w4 = 0x8000501 pc=0005C202 ; замок слота 0x501
[wtrap] +0xE0000000 w4 = 0x1     pc=0005C5F2   ; "success"
```

* `0x5C5E6`: `$1 = 0x21` (режим), `$2 = 0` (значение из `process_image`);
* `0x5C5F0`: `$10 = 0x08000501`, `$11 = 0xE0000000`, `$12 = 1`, `$9 = 0xE0030020`;
* итог: `keyring writes = 1`, слот `0x501` = `04000000…` с флагами `0x004`,
  слот заперт (`locked=1`);
* счётчики на момент успеха: `bigmac ops = 14`, `bignum ops = 1`, `sc transfers = 0`.

## 15. Самоуничтожение и передача управления второй стадии (шаг 15)

**Где:** хвост `_start`, `0x5C044..0x5C0B6` — исполняется после возврата из `main`;
затем заглушка, скопированная в `0x5FFE0`.

### Листинг

```asm
5C044  00 53          mov $3,0              ; значение для затирания
...    (mov $4..$12 = 0, $tp/$gp/$sp = 0)
5C05E  28 73          stc $3,$sar
...    ($hi,$lo,$tmp,$epc,$npc = 0)
5C06A  00 d0 00 04    movu $0,0x40000
5C06E  18 70          stc $0,$lp            ; $lp = 0x40000 - куда "вернёмся"
5C070  e0 d0 ff 05    movu $0,0x5ffe0       ; приёмник заглушки
5C074  98 d1 c0 05    movu $1,0x5c098       ; источник заглушки
5C078  07 52          mov $2,7              ; repeat: 8 слов
5C07A  09 e2 04 00    repeat $2,0x5c082
5C07E  1e 02          lw $2,($1)
5C080  10 61          add $1,4
; ---- loc_5C082   (плюс завершающий слот 0x5C084)
5C082  0a 02          sw $2,($0)
5C084  10 60          add $0,4
5C086  00 d0 c0 05    movu $0,0x5c000       ; с чего начать затирание
5C08A  01 c1 f7 0f    mov $1,4087           ; repeat: 4088 итераций по 4 байта
5C08E  e0 d2 ff 05    movu $2,0x5ffe0       ; заглушка
5C092  2e 10          jmp $2
; ---- loc_5C094  (аварийная петля, если что-то пришло не туда)
5C094  a8 dc c0 05    jmp 0x5c094
; ---- заглушка (тело скопировано в 0x5FFE0)
5C098  09 e1 03 00    repeat $1,0x5c09e
5C09C  00 00          nop
5C09E  0a 03          sw $3,($0)            ; *$0 = 0
5C0A0  10 60          add $0,4             ; (завершающий слот цикла)
5C0A2  00 50          mov $0,0
5C0A4  00 51          mov $1,0
5C0A6  00 52          mov $2,0
5C0A8  48 73          stc $3,$rpb
5C0AA  58 73          stc $3,$rpe
5C0AC  68 73          stc $3,$rpc
5C0AE  02 70          ret                   ; ret -> $lp = 0x40000
```

### Что происходит

1. Регистры `$3..$12`, `$tp/$gp/$sp` и системные `$sar/$hi/$lo/$tmp/$epc/$npc`
   обнуляются; `$lp` получает `0x40000`.
2. **Заглушка** (32 байта, `0x5C098`) копируется в конец окна — в `0x5FFE0`.
3. Управление передаётся на неё (`jmp $2`), и она в цикле `repeat` (4-байтовыми
   шагами: `nop`, `sw $3,($0)`, `add $0,4` — 4088 итераций) записывает нули
   от `0x5C000` до `0x5FFDF`. **Точка входа первого загрузчика уничтожается** —
   повторный сброс CMeP не запустит его снова.
4. `ret` уходит по `$lp = 0x40000` — в только что расшифрованный образ второй
   стадии. Дополнительно заглушка обнуляет `RPB/RPE/RPC`, то есть снимает
   аппаратный цикл.

### В модели

Всё это — реальный код. Важно, что `0x5FFE0..0x5FFFF` и `0x40000..0x5FFFF` лежат
в одном окне `CMeP.RAM` (128 КиБ), которое модель отображает как RAM; поэтому запись
нулей по `0x5C000` действительно стирает код (что можно увидеть в отладчике после
шага).

### Измерено

* `0x5C070`: `$0 = 0x40000`, `$1 = 0x5C045`, `$lp = 0x40000`;
* `0x5FFE0` (вход в заглушку): `$0 = 0x5C000`, `$1 = 0x0FF7` (4087), `$2 = 0x5FFE0`,
  `$3 = 0`;
* `0x40000` (первая инструкция второй стадии): все регистры `$0..$12`, `$tp/$gp/$sp`
  равны нулю — ровно то, что предписывает этот код;
* сообщения модели: `CMeP handed off to the staged image at 0x40000`
  (`boot_.detail = "CMeP second loader executing at 0x40000"`).

### 15.1 Что именно перехватывает `pc_hook` (уточнение)

Хук стоит на **обратном** вызове второй стадии, не на передаче управления из §15.
Разбор кода второй стадии (`zdis mep Out/SLB2_dec/second_loader.bin --base 0x40000`):

```asm
4039A  mov $6,1280              ; код GPO 0x500 (шаблон ошибки лежит на 0x40100)
403A2  movu $3,0x5ff00          ; приёмник дескриптора
403A6  mov $2,31                ; repeat: 32 слова
403AE  lw $1,($4)               ; источник 0x40100 - свой же образ
403B2  sw $1,($3)
...
40404  jmp 0x5ff00              ; -> перехват
```

То есть `0x5FF00` — буфер запроса из 32 слов, который вторая стадия заполняет сама;
сама роутина, читающая запрос, в дампах отсутствует. Измерено без подстановок
(`ZLB_NO_SUBSTITUTION=1`): исполнение входит в дескриптор и упирается в `sleep`
(`0x5FF1E`), дальше — `CMeP halted: sleep instruction`, GPO `0x54`. Прототипный
дамп содержит по `0x5FF00` нули, retail-снимок — таблицу указателей
(`0x5EDA0, 0x5FF6C, …`), которая наводит на уже затёртый `.bss` этого снимка.
Подробнее — `docs/BOOT.md` §4.

Полный список подстановок цепочки — `docs/STATUS.md` §4; выключаются они
переменной `ZLB_NO_SUBSTITUTION=1` (тогда запуск встанет там, где встал бы на
реальном железе без ключей).

**Два расхождения, которые стоит держать в голове.**

1. *Режим загрузки.* `CmepBlock::boot_mode_` (поле модели) равен `0x41`, и именно
   его печатают отчёты `boot`/`keyring`, тогда как **гость вычисляет `0x21`**:
   `StrapDevice` отдаёт `0xE0062020` с битом 0 сброшенным, поэтому
   `check_boot_mode` возвращает `'!' = 0x21` (измерено: `$8 = 0x21` на всём пути
   `bit0`). Оба режима содержат `bit0` (образ от ARM), так что цепочка проходит;
   но это меняет ветку внутри `img_proc_5C67E` (ветка «стереть материал keyring 9»)
   и запись в keyring `0x501` (`word0 = 4`, а не `5`). Формулировку «boot mode =
   0x41» в `docs/BOOT.md` §3 следует читать как «поле модели», а не как состояние
   гостя.
2. *Семантика `ClearFlags`.* Модель хранит `flags` слота из записи `KeyringNewValue[0]`
   (16-битные значения `0x206`, `0x208`, `0x200`, `0x344`) и применяет к ним
   `mask = v & ~0x1FFF` (в наблюдавшихся словах это `0x1C1F0000` и т.п.), поэтому
   запись `ClearFlags` фактически ничего не снимает, а `locked` выводится из бита
   `0x0800`. На железе эти слова, по смыслу имени, снимают биты маски — здесь
   модель осторожнее, чем железо, и это задокументированное допущение, а не
   проверенный факт. На наблюдавшийся путь оно не влияет: ответ на запрос флагов
   `0x501` задаётся полем модели, а не содержимым слота.

## 17. Retail-сборка: что измерено (и что в документах было неточно)

Второй образ, `dumps/pch-5c-cold_first_loader.bin` — тот же загрузчик другой сборки
(сдвиг `.data`/`.bss` на `-0x80`, более строгая проверка заголовка, страп
`0xE0064060`/`0xE3100194`, заглушка в `0x5FFF0`; `COMPARISON.md`). Прогон модели с
`--first-loader dumps/pch-5c-cold_first_loader.bin` даёт следующее:

1. **Провижининг ключей отказывается работать**, и в логе видна причина:

   ```text
   boot key provisioning skipped: the fitted first loader expects a different signed
   block (sha256 2A8C6B8C98260E023C37A9A493FDE37C47F334292EC1A3F29AD9912BBCA1B778,
   development key was made for F8E372301A476346110ECC31803B988128CFB7610CFC601A45500B0FA649811C)
   ```

   Причина техническая: `bootkeys.h` читает 18-байтовую константу DigestInfo из
   **прототипного** адреса `0x5E774`; в retail-образе она лежит в `0x5E6F4`
   (байты идентичны), а по `0x5E774` находятся таблицы степеней десяти
   (`A0860100 40420F00 80969800` = 100 000 / 1 000 000 / 10 000 000). Подписываемый
   блок собирается с чужими байтами, поэтому SHA-256 не совпадает и провижининг
   отказывается. Это ограничение модели, а не свойство сборки.
2. **Заголовок retail-сборка проходит**: `bp 0x5C630` (её `validate_header`)
   срабатывает с тем же состоянием, что и у прототипа (`$1 = 0x40000`,
   `$7 = 0x407C0000`, `$8 = 0x21`), и mailbox читается по `pc = 0x5C58C`
   (`[rtrap] +0xE0000010 r4 = 0x407C0001`). То есть утверждение, что retail
   «отвергает наш образ на валидации заголовка» (`docs/BOOT.md` §0), неверно:
   заголовок принимается, несмотря на добавленные проверки
   (`field + size < 0x1BC00`, `u16@+0x14 < 6`).
3. **Падение происходит позже** — на RSA/PKCS#1: с пустой таблицей `0xE0066000`
   `bignum_op` даёт мусор, проверка `00 01 FF…` не проходит, и `main` уходит на
   путь отказа: `bp 0x5C62A` срабатывает на `sw $12,($11)` при `$12 = 2`, то есть
   `0xE0000000 <- 2` (при этом успело выполниться 4 операции Bigmac: keyring 8,
   keyed-проверка, keyring `0x20`, SHA-256 заголовка).
4. Чтобы retail пошёл дальше, достаточно сделать адрес DigestInfo выбираемым по
   сборке (например, читать его из `symbols.txt` подобранного образа) — тогда
   dev-ключ соберётся под ту же сборку, что и раньше. Это следующий очевидный шаг,
   если понадобится сверять поведение retail на первом же этапе.

## Приложение B. Как воспроизвести

```powershell
# сборка
cd zeliboba
powershell -ExecutionPolicy Bypass -File .\build.ps1

# 1. цепочка до передачи управления второй стадии + метрики
build\bin\zeliboba.exe -q -ex "boot" -ex "core mep" -ex "bp 0x40000" -ex "run 400000" -ex "boot" -ex "quit"

# 2. остановки на любом шаге (bp без архитектуры адресуется MeP)
build\bin\zeliboba.exe -q -ex "boot" -ex "core mep" -ex "bp 0x5C61C" -ex "run 400000" -ex "regs" -ex "keyring" -ex "quit"

# 3. хронология MMIO (Приложение A)
$env:ZLB_WTRAP="0xE0000000-0xE007FFFF"; $env:ZLB_RTRAP="0xE0030000-0xE0030030"
build\bin\zeliboba.exe -q -ex "boot" -ex "core mep" -ex "bp 0x40000" -ex "run 400000" -ex "quit"

# 4. покрытие кода первого загрузчика
$env:ZLB_MEP_COV="1"
build\bin\zeliboba.exe -q -ex "boot" -ex "core mep" -ex "bp 0x40000" -ex "run 400000" `
    -ex "cov mep 0x5C000 0x4000" -ex "quit"

# 5. дизассемблер самого эмулятора (им же проверялись листинги)
build\bin\zdis.exe mep ..\dumps\vita_prototype_bootrom.bin --base 0x5C000 --offset 0x61C --count 40
```

Готовый сценарий отладчика — `scripts/first-loader.cmd` (останавливается на опросе
mailbox и показывает, что видит загрузчик).

Связанные документы: `docs/BOOT.md` (вся цепочка), `docs/STATUS.md` (состояние и
подстановки), `docs/HARDWARE.md` (карта памяти и регистров), `docs/KBL.md`
