# Syscon (Ernie): загрузка, DRAM и JIG

Документ отвечает на вопрос «кто инициализирует DRAM на PS Vita и при чём тут
Syscon / JIG / eMMC» и фиксирует **найденные дефекты модели Ernie** в этом
проекте. Метки источников:

* **[В]** — Vita Development Wiki (`wiki.henkaku.xyz`), страницы `Boot_Sequence`,
  `Ernie`, `Ernie_Firmware`, `Second_Loader`, `SLSK`, `Syscon_UART_RPC`. Тексты
  проверены по живым ревизиям (`oldid` совпадают с локальными PDF).
* **[Ф]** — прошивка `ernie-master/USS-1001.bin` (дамп flash Ernie) или дампы
  воркспейса.
* **[Р]** — собственный реверс/трассировка эмулятора (воспроизводимо).
* **[М]** — модельное допущение.

---

## 1. Короткий ответ

1. **Syscon не инициализирует DRAM и не может этого делать.** Ernie — это
   8/16-битный микроконтроллер NEC 78K0R/Kx3 (`uPD79F0109`) на Fat/PS TV и
   Renesas RL78/G13 (`R5F1ZCRK`, 384 КиБ code flash + 8 КиБ data flash) на Slim
   **[В]**. Наружу у него SPI (к Kermit), UART0, GPIO, I2C (топливный элемент),
   силовые ключи. Шины к LPDDR2 у него нет физически, и **в таблице его команд
   нет ни одной DRAM/DDR/тренировочной команды** — проверено разбором таблицы
   диспетчера на `0x26BE` (70 записей) **[Ф]**.
2. Фраза вики «*Syscon powers up and sets up DRAM*» **[В]** означает
   **подъём питания и клоков** (rails / `sceSysconCtrlVoltage` = SC-команда
   `0x088E`), а не тренировку интерфейса. Ту же мысль вики проговаривает ниже
   прямо: «*The Second Loader … It initializes DRAM*» **[В]**.
3. **DRAM (LPDDR2) инициализирует CMeP Second Loader**, и это подтверждено
   тремя независимыми способами:
   * GPO-чекпойнт `0x45` в таблице вики подписан «`?Initializing LPDDR2?` /
     ERROR: LPDDR2 initialization failed» и стоит **на second_loader**, а `0x47` —
     «`Calling testMemory`» **[В]**;
   * декомпиляция 3.60 second_loader: ровно на этом месте вызывается
     `something_with_dram_808662(1, is_resume)` **[В]**;
   * код `second_loader.bin` исполняется в окне CMeP `0x40000` и на холодной
     загрузке **обнуляет первые 2 МиБ DRAM** (`dmac_memset_int_804F04(
     0x40000000, 0x200000, 0)`) **[В]** — это и есть «настройка» памяти со
     стороны прошивки.
4. **«Чем» приезжает DRAM-инициализация:** *кодом* самого `second_loader.enp`
   из загрузочного раздела eMMC (`sloader`, формат SLB2) **[В]**. Отдельного
   «DRAM-блоба» нет ни на eMMC, ни в Ernie, ни в JIG — поиск не нашёл ни
   блоба, ни соответствующей команды/патента **[В]**.
5. **JIG — это не путь инициализации DRAM.** Это два разных отладочно-заводских
   механизма, оба про *источник загрузки и доступ к сервису*, а не про память:
   * **Jig-донгл у Ernie**: аналоговый «Jig Sense» на входе АЦП (ANI6/P26),
     id=4 при 1.017–1.140 В → включается **UART RPC** Syscon («Jig Handler»),
     приветственный пакет `55 55 55` («UUU») **[В]**;
   * **secret debug mode у CMeP boot ROM**: AES-challenge-response с внешним
     устройством через `0xE0000020/24` → `0xE0000028/2C`; при успехе MBR
     читается **с картриджного слота** (обычная SD-карта) и персонализация
     снимается ключевым слотом `0x207` вместо `0x206` **[В]**. Это та самая
     «SD BOOT challenge», о которой пишет Boot_Sequence.
6. **Данные boot-контекста берутся у Syscon (NVS + scratchpad), а не с eMMC.**
   eMMC отдаёт *payload* (`second_loader.enp`, `kernel_boot_loader.self`,
   `kprx_auth_sm.self`, `prog_rvk.srvk`), а *параметры* (boot type, hardware
   info, DIP-switches, Safe Mode / Update Mode / Qaf Token) — из NVS и
   scratchpad Ernie **[В]**.
7. **В модели эмулятора эти команды размечены неверно** — см. §7. Трассировка
   показывает, что second_loader 1.04 шлёт `0x1082` с payload `80 04 08`
   (NVS offset 0x0480, длина 8) и `0x0090` с payload `E0 00 20` (scratchpad
   offset 0x00E0, длина 0x20 = блок CP DIP-switches), а модель отвечает на
   первое — байтами CSD карты, на второе — пустым ответом **[Р]**.

## 2. Железо Ernie: почему DRAM мимо него

| Что | Значение | Источник |
|---|---|---|
| Fat / PS TV | NEC `uPD79F0109` (78K0R/KH3, 121 pin), flash 0x40000 | [В] |
| Slim | Renesas `R5F1ZCRK` (RL78/G13, 121 pin): Code Flash 384 КиБ @0, Data Flash 8 КиБ @0xF1000 | [В] |
| Связь с Kermit | SPI0 (основная) + отдельные GPIO + линия сброса | [В] |
| UART | UART0: CTS0/RTS0/TX0/RX0/SW0 — консоль и **Jig-донгл** | [В] |
| Питание | `PWR_SW` через два транзисторных буфера; `sceSysconCtrlVoltage` (SC `0x088E`) | [В] |
| NVS | data flash: 0xBA0 (новые ревизии) / 0xC20 (старые); с 3.60 наружу видно 0xB60 | [В] |
| Scratchpad | 0x100 байт: +0xC PA контекста resume, +0xE0 блок CP DIP-switches (0x20) | [В] |

Собственная «загрузка Syscon» — это его reset-вектор и рабочий цикл:

* **RL78/G13**: reset-вектор `0xE000` (USS-1001) / `0x0DC00` (USS-1002) **[Ф]**;
* пролог: `sel rb0` → `movw sp,#0xFE20` → `clrb !0x02F0` → `call !0x104F5` →
  `0x30035` (инициализация портов/клоков) → **ожидание `cmp !0xFFFA2,#0xC0`**
  (аппаратное рукопожатие «питание готово»), затем `0xFFFA4 = 0x10` и ожидание
  бита 5 **[Ф]**;
* дальше — **Worker Loop: конечный автомат из 10 состояний (0..9)**, в
  состояниях 3/4 вызывается обработчик команд, читающий заголовок из `SDR00`
  **[В]**. В эмуляторе это подтверждено: PC уходит `0x3005E → 0x363F`, и
  `0x363F` — как раз диспетчер по состоянию (`mov a, es:!0xD66A` + цепочка
  `dec a / bz`) **[Р]**.

Итого: Ernie — это **power/clock/reset + NVS + SPI-линк**, а не контроллер
памяти. Это же подтверждает PS3/PS4-аналогия: там syscon владеет
последовательностью питания и флагами в NVS, а свою память (XDR / DDR3)
инициализирует уже сам SoC своим boot-кодом **[В]**.

## 3. Кто на самом деле инициализирует DRAM

Порядок по вики и по декомпиляции second_loader **[В]**:

| GPO | Событие |
|---|---|
| `0x42` (66) | что-то с Syscon; ошибка «communication with Syscon failed» |
| `0x43` (67) | запись keyring 0x508/0x51B (версия Ernie и model info из SC-команд 1 и 5) |
| `0x44` (68) | boot type из SC-команды `0x10` (`0xFF14` холодная / `0xFF80` resume) |
| **`0x45` (69)** | **`?Initializing LPDDR2?`** ← `something_with_dram_808662(1, is_resume)` |
| `0x47` (71) | `Calling testMemory` |
| `0x48`/`0x49` | инициализация SD/eMMC, загрузка `kernel_boot_loader.self` |
| `0x5A` (90) | «About to write SceKblParam to SPAD32K» |
| `0x60` (96) | «Setting SceKblParam complete…» |

Существенные следствия:

* DRAM-шаг **зависит от типа загрузки** (`is_resume`): на resume интерфейс уже
  обучен, на холодной загрузке вторым загрузчиком делается
  `dmac_memset_int_804F04(0x40000000, 0x200000, 0)` — **обнуление первых 2 МиБ
  DRAM** **[В]**. Это же объясняет, почему структура с подписью `0x61CE6649`
  по `DRAM+0xA0`, которую проверяет вторая стадия на `0x40A76`, на холодной
  загрузке не может «доехать» из прошлого запуска: она заполняется уже *после*
  этого обнуления (ветка resume копирует TZ-векторы из DRAM в SPAD —
  `copy_arm_tz_reset_vectors_800A9A`) **[В]**, **[Р]** (`docs/KBL.md`, §48.20).
* Размер/база DRAM в `SceKblParam` (+0x60/+0x64) — **продукт софта** (выбор
  DevKit-ветки по DIP-switch), а не то, что «сообщает» Syscon **[В]**.
* Код DRAM-шага едет с eMMC внутри `second_loader.enp`; отдельных данных
  тренировки нет — искать блоб бессмысленно **[В]**.

### 3.1 Где именно DRAM-шаг в образе (раунд 152)

Дизассемблирование `Vita_104_Firmware/Out/SLB2_dec/second_loader.bin`
(91 648 байт, база `0x40000`) **[Р]**:

* точка вызова — ровно чекпойнт `0x45`: `0x40590 mov $1,69` (`'E'`), `0x40592
  bsr 0x4896c` (GPO), затем `0x40596..0x405A2` читает бит 7 ответа syscon
  (команда `0x0010`) и делает `bsr 0x483DA` — **единственный вызов `0x483DA` во
  всём образе**;
* **`0xE6000000` — это и есть контроллер LPDDR2**, тот самый «неотождествлённый
  блок CMeP», который в `docs/HARDWARE.md` §1.2 помечен как неизвестный.
  `0x483DA` пишет 16-битное `0x0003` в `0xE6008100 + i*8`, коммитит `1` в
  `0xE6008180` и опрашивает его обратно (`0x48422..0x48436`), затем блоками
  пишет регистры режима `0xE6000020..0xE6000094` (16 значений с шагом 0x10) и
  слот-регистры `0xE6008038..0xE6008178`;
* **параметры — константы в самом образе**: таблицы `{addr, value}` по `0x554C0`
  (35 пар, терминатор `0xFFFFFFFF`) и `0x55620` (18 пар). Их разворачивает
  `0x4827A` **обычным `sw $0,($3)`** по адресу из таблицы — поэтому
  сканирование только по `movh/or3` весь блок не находит. Например:
  `E6000020=0`, `E6000024=0x00010003`, `E60080C8=0x1FFF`,
  `E6008260=0x67`, `E60083B0=0x0D068235`, `E60083B4=0x014E014E`;
* каждая запись сопровождается **обратным чтением** (`0x48290`);
* `testMemory` (чекпойнт `0x47`) — **заглушка**: `0x41A46`/`0x41A5C` это
  `mov $0,0; ret`, упасть он не может;
* таймер задержек `stcb`/`ldcb` (`0x400..0x405`) в DRAM-пути не используется;
* **единственный вход от syscon здесь — бит 7 ответа команды `0x0010`**
  (cold/resume). Ни eMMC, ни idstorage, ни first loader в этом шаге не
  участвуют: ответ на вопрос «чем» — **собственными константами образа**;
* коды ошибок LPDDR2: `0x800F0039` (`0x48452`) и `0x800F0002` (`0x484BA`);
  вызывающий рапортует `{2, 0x45, err}` на `0x405BC`.

Побочный вывод: в модели `CmdBlockDevice` описаны только
`0xE6008000/8020/8100/8120/8180`, а блок регистров режима
`0xE6000020..0xE6000094` не смоделирован вообще (`RegisterFile` принимает любую
запись и возвращает её же на чтение, поэтому проверки `0x483DA` проходят
«сами»).

## 4. JIG: что это на самом деле

### 4.1 Jig-донгл у Ernie (вход в UART RPC)

* При старте Syscon по таймеру (флаг `0x79`) читает **АЦП канал ANI6 (порт
  P26)** и по таблице напряжений получает id; при **id = 4 (1.017–1.140 В,
  удерживается ≥32000 клоков)** настраивается **UART-контроллер** и печатается
  приветствие `55 55 55` («UUU»), если в Hardware Info установлен бит 3 **[В]**.
* После этого включается **Jig Handler**: команды принимаются по UART от
  внешнего агента (UART RX прерывание → флаг `0x32` → состояния 1/3/8/9) **[В]**.
* В NVS есть флаг `0x481` «Extra UART Flag»: `0x01` — «extra UART enabled only
  when Jig dongle is connected» **[В]**. Это и есть «как включается JIG» —
  **аналоговое напряжение на sense-пине**, а не страп в SoC.
* Пароль `uuu` у архива `dumps/emmcdump.zip` **[Ф]** — из того же приветствия.

### 4.2 secret debug mode у CMeP boot ROM (SD BOOT challenge)

* Boot ROM ставит режим вывода на порт, читает пин, ставит бит `0x10` в
  `0xE0020000` (мультиплексор SPI-пинов syscon «на CMeP»), шлёт челлендж в
  `0xE0000020/24`, читает ответ из `0xE0000028/2C` и сверяет с
  `AES-256-ECB(g_debug_challenge_key, challenge)`; ключ после проверки
  затирается **[В]**.
* При успехе: MBR читается **с картриджного слота** (не-подписанная SD-карта
  работает), персонализация снимается слотом `0x207` вместо `0x206`; HMAC и RSA
  при этом **всё равно проверяются** **[В]**.

### 4.3 Чего в JIG нет

Ни в одном источнике JIG не связан с DRAM: **0 упоминаний JIG/страпов/DDR в
локальных `boot_sequence.pdf` и `Security.pdf`** (проверено пословно), и нет
DRAM-команды в прошивке Ernie **[Р]**. Единственный «альтернативный boot» —
SD BOOT challenge из §4.2 **[В]**.

## 5. Чем Syscon реально питает цепочку загрузки

По декомпиляции 3.60 second_loader **[В]** и таблице команд **[Ф]**:

| SC | Что делает | Куда попадает |
|---|---|---|
| `0x0001` | версия Ernie | keyring 0x508; если < 0x80300 — отказ загрузки |
| `0x0005` | hardware info (модель) | keyring 0x51B, `SceKblParam.+0xD4` (у нас `0x00406000`) |
| `0x0002` | timestamp прошивки | лог/проверки |
| `0x0010` | boot type | бит 7 → cold/resume, `SceKblParam.+0xC4` |
| `0x0003` | sleep factor | `SceKblParam.+0xC0` |
| `0x1082` | **NVS read** (`u16 offset` + `u8 len`) | 0x480 Qaf/ExtraUART/SafeMode, 0x4A0 Update Mode, SNVS 0x400–0x460 |
| `0x00D0`/`0x00D2` | SNVS RW (шифрованная сессия) | mgmt-данные, keyring 0x50B |
| `0x0090`/`0x0091` | **scratchpad read/write** (`u16 offset` + `u8 len`) | **offset 0xE0, 0x20 байт = CP DIP-switches** → `SceKblParam` |
| `0x088E` | `sceSysconCtrlVoltage` | питание SoC |
| `0x0800`, `0x0100`, `0x0103` | прочая телеметрия | QA/boot-флаги |

Ключевой фрагмент декомпиляции: `read_syscon_cmd_0x90_off_0xE0_802056(line_0x510)`
→ `write_kbl_param_fields_from_syscon_801FC0()` → `keyring_writeX(0x510, line_0x510, 0x20)`
**[В]**. То есть **DIP-switch-поле SceKblParam (+0x40..0x5F) приходит из
scratchpad Ernie по команде `0x0090`**, а boot-флаги — из NVS по `0x1082`.

## 6. Проверка по eMMC: кто хост

`second_loader` сам гоняет eMMC-инициализацию (`GO_IDLE_STATE, SEND_OP_COND,
SEND_CID, SET_RELATIVE_ADDR, SEND_CSD, SELECT_CARD, SEND_EXT_CSD, SET_BLOCKLEN,
SWITCH×2`) и **во время `SEND_OP_COND`** вызывает хук, который «включает Syscon
по GPIO и шлёт команды 1/5/2, опционально 0x80» **[В]**. То есть eMMC — на
стороне SoC (SDIF0), а Syscon инициализируется **рядом** с ней, а не «через»
неё. Это согласуется с моделью проекта (`Sdif` + ADMA2, `docs/EMMC.md`).

Команд `storage_read` / `emmc_get_csd` в протоколе Ernie **не существует** —
ни в таблице `0x26BE`, ни в вики **(проверено отдельным поиском)** **[Ф]**, **[В]**.

Это ставит под сомнение посылку `src/hw/syscon/ernie_emmc.cpp` («the syscon is
the storage host for the early boot path»): eMMC висит на SDIO0 Kermit
(`CLK0 AC7 / CMD0 AB2 / DAT0-7 AC6..AD3`, `eMMC RST_N B26`), а second_loader
сам гоняет полную последовательность инициализации карты **[В]**. Группа
`0x1080..0x1083` / `0x1100..0x1101` / `0x1180..0x1185` в модели помечена как
eMMC-команды **по группировке, а не по реверсу** (комментарий в `ernie_sc.cpp`
это честно оговаривает). Для `0x1082`/`0x1083` это уже опровергнуто (см.
таблицу ниже); для `0x1080`, `0x1081`, `0x1101`, `0x1180..0x1185`
подтверждения нет ни в ту, ни в другую сторону — их ярлыки **требуют
проверки**, и опираться на них как на факт нельзя.

Что при этом совпадает с `docs/EMMC.md`: образ eMMC от Syscon не зависит —
в цепочке 1.04 он читается через SDIF SoC (ADMA2, `0xE0B00000`), а не через
SC-команды [Р].

## 7. Найденные дефекты модели Ernie

Трассировка (`zeliboba.exe -q --log debug -ex boot -ex "runm 20000" -ex quit`)
даёт по 1.04 second_loader такой поток **[Р]**:

```
cmd 0x1082 payload=3 [80 04 08]   -> code 0x0004 payload=16   (отдано: CSD карты)
cmd 0x1082 payload=3 [00 04 20]   -> payload=16               (NVS 0x0400, len 0x20)
cmd 0x1082 payload=3 [D0 04 10]   -> payload=16               (NVS 0x04D0, len 0x10)
cmd 0x0090 payload=3 [E0 00 20]   -> code 0x0103 payload=0    (пусто!)
cmd 0x1083 payload=19 [D0 04 10 + 16 байт данных]
cmd 0x1100 payload=0              -> payload=6
```

Сопоставление с протоколом:

| Команда | `flags` в таблице `0x26BE` **[Ф]** | Что шлёт second_loader **[Р]** | Что отвечает модель | Что должно быть **[В]** |
|---|---|---|---|---|
| `0x1082` | `0x0001` (с payload) | 3 байта: `u16 offset` + `u8 len` | 16 байт CSD карты | **NVS read**: `len` байт из NVS по `offset` |
| `0x1083` | `0x0001` | `offset`+`len`+данные | 32 байта EXT_CSD | **NVS write** |
| `0x0090` | `0x0001` | `E0 00 20` | пустой ответ (`code 0x0103`) | **scratchpad read** 0x20 байт с offset 0xE0 |
| `0x0091` | `0x0001` | — | нет обработчика | **scratchpad write** |
| `0x1100` | **`0x0000`** (без payload!) | пусто | 6 байт «карта/раздел» | версия Ernie DL (4 байта, `01 01 13 00`) |
| `0x088E` | `0x0001` | `01 22` / `02 29` | читает как «регистр gauge» | `sceSysconCtrlVoltage` |

Три независимых подтверждения того, что права вики, а не модель:

1. **Payload'ы совпадают с документированными смещениями**: `[80 04 08]` —
   ровно NVS 0x480+8 (Qaf Token Flag / Extra UART Flag / Safe Mode Flags),
   `E0 00 20` — ровно scratchpad 0xE0+0x20 (CP DIP-switches) **[В]**, **[Р]**.
2. **Бит `flags` в самой прошивке**: `0x1100` помечена как «payload не нужен»,
   `0x1082`/`0x0090`/`0x1083` — «payload нужен». Модель для `0x1100` требует
   8-байтовый payload — прямое противоречие своей же таблице **[Ф]**.
3. **Пакетный лог вики** `> 0x1082 [80 04 08]` → `< [FF FF FF FF 01 FF FF FF]`
   и имена функций декомпиляции `syscon_read_cmd_0x1082_ptr_0x480_into_gbuf`,
   `read_syscon_cmd_0x90_off_0xE0` **[В]**.

Внутренняя несогласованность видна и в самих тестах проекта: комментарий
`tests/test_syscon.cpp:597` называет `0x1082` «NVS read», а `:322` проверяет,
что `0x1082` возвращает CSD карты.

**Практический эффект:** в прогоне `boot` из 12 видов SC-команд `0x1082`
вызывается **14 раз** и каждый раз получает мусор вместо NVS, а единственный
запрос DIP-switches (`0x0090`) получает пустой ответ. Поэтому boot-флаги и
DIP-поле `SceKblParam` в модели сейчас подставляет `Vita::build_kbl_param()`
(см. `src/machine/bootchain.cpp:1996`), а не получает от Syscon.

## 8. Что делать (по приоритету)

### 8.1 Уже сделано (семантика команд)

В модели появились два хранилища и исправлена семантика пяти команд; замер
«до/после» на `boot` + `runm 60000` даёт **побитово одинаковый результат**
(`cmep=0x40002`, `arm=0x31C`, `insns=9382908`, secure kernel 117 083
инструкции), то есть исправление нейтрально для текущей цепочки, но протокол
теперь верный:

| Что | Файл |
|---|---|
| `ernie::NvsStore` (0xB60, `0xFF` = «не прошито») и `ernie::ScratchPad` (0x100, блок DIP-switches по 0xE0) | `src/hw/syscon/ernie_internal.h`, реализация `ScratchPad::reset` — `ernie_sc.cpp` |
| `0x1082` = NVS read, `0x1083` = NVS write, `0x0090`/`0x0091` = scratchpad read/write, `0x1100` = версия Ernie DL (без payload) | `src/hw/syscon/ernie.cpp` |
| Переименование команд `nvs_read` / `nvs_write` / `scratchpad_read` / `scratchpad_write` / `get_ernie_dl_version`, оговорка про непроверенные ярлыки группы 0x1080/0x1101/0x118x | `src/hw/syscon/ernie_sc.cpp` |

Содержимое NVS — «не прошито» (`0xFF`), как вики описывает отсутствующие
Qaf/WLAN/Safe-Mode/Update-Mode флаги; содержимое блока DIP-switches — те же
0x20 байт release-режима, которые модель уже писала в `SceKblParam +0x40`
**[М]**. Реальных NVS в дампах нет, поэтому подставить настоящие значения
неоткуда.

### 8.2 Осталось

1. **Перевести `build_kbl_param()` на данные Syscon** (раунд 2 той же правки):
   поле DIP-switches `+0x40..0x5F` — из scratchpad `0xE0`, boot-флаги
   `+0x20/+0x30` — из NVS `0x480`/`0x4A0`, `+0xC0/+0xC4/+0xD4` — из уже
   обслуживаемых команд `0x0003`/`0x0010`/`0x0005`, `+0xD0` — из scratchpad
   `+0xC` (PA контекста resume). Сейчас эти поля пишет подстановка
   (`src/machine/bootchain.cpp:1996`), поэтому Syscon в формировании
   boot-контекста не участвует.
2. **Проверить ярлыки группы хранения** (`0x1080`, `0x1081`, `0x1101`,
   `0x1180..0x1185`): после того как `0x1082`/`0x1083` оказались NVS, посылка
   «Syscon — хост eMMC» не подтверждается ничем. Если эти команды тоже не про
   eMMC, `src/hw/syscon/ernie_emmc.cpp` теряет смысл, а чтение карты в цепочке
   идёт только через SDIF SoC.
3. **Не искать DRAM-блоб и не моделировать «DRAM init у Syscon»**: правильная
   модель — питание/клоки/сброс (`0x2080`–`0x2085`, `0x088E`) плюс очистка
   первых 2 МиБ DRAM вторым загрузчиком на холодной загрузке (в эмуляторе это
   уже «бесплатно», но стоит зафиксировать как комментарий/чекпойнт, чтобы
   cold/resume развилка была видна). Точка, где это можно проверять, теперь
   известна: MeP `0x405A2` → `0x483DA`, контроллер `0xE6000000`.
4. **Сверить базу `SceKblParam`.** Второй загрузчик строит структуру по
   **`0x1F000100`** (раунд 152: `0x41B38` обнуляет там 256 байт, `0x41B9E`
   пишет DRAM base в `0x1F000160`, `0x41BA2` — размер в `0x1F000164`), тогда
   как модель пишет её по `0x1F000040` (`board::kKblParamBase`). Раскладка
   полей совпадает, а база расходится на 0xC0. Косвенное подтверждение
   загрузчика: трап чтений ARM в `STATUS.md` §5 видит обращение по PA `0x1C4`,
   а это ровно `0x1F000100 + 0xC4` в раскладке загрузчика. Проверять по
   собственным чтениям KBL, прежде чем менять базу — на текущем размещении
   завязана вся отлаженная цепочка.
5. **Смоделировать блок регистров режима LPDDR2** `0xE6000020..0xE6000094`
   (16 значений с шагом 0x10) и `0xE6008038..0xE6008178`: сейчас в
   `CmdBlockDevice` их нет, а проверки `0x483DA` проходят только потому, что
   `RegisterFile` возвращает то, что в него записали.
6. **JIG** моделировать только как флаг источника загрузки: NVS `0x481`
   (extra UART) и «SD BOOT challenge» = альтернативный источник MBR. На
   текущую цепочку (eMMC) это не влияет.

**Измерение (сделано).** Ветка завернута в отдельную подстановку
`kColdPathPatches` под `ZLB_CMEP_COLD_PATH=1` (по умолчанию выключена —
существующая логика машины ещё не готова к тому, что холодная ветка проходит
дальше). Замер с включённой подстановкой:

| | по умолчанию | `ZLB_CMEP_COLD_PATH=1` |
|---|---|---|
| инструкций CMeP | 117 083 | **15 360 000** |
| PC CMeP | `0x40002` (хук машины) | `0x45508` (драйвер хранилища) |
| ARM | отпущен, KBL до `0x31C` | `0x80000000`, не отпущен |

То есть после снятия барьера **холодная ветка уходит далеко вперёд** — в 130 раз
больше инструкций, — и упирается уже не в криптографию, а в работу с
хранилищем (`0x45508` — окрестности цикла задержки `stcb`/`ldcb`
`0x454F4..0x45526`). ARM при этом не отпускается, потому что цепочка машины
построена вокруг прежнего поведения (ранний отказ → подстановки).

**Вывод раунда.** Криптографический барьер холодной ветки снят: движок окна
работает, метаданные расшифровываются, дайджест-проверка — последняя
криптографическая преграда до чекпойнтов. Дальше вопрос уже не в реверсе
шифрования, а в том, чтобы **адаптировать машинный слой** к тому, что вторая
стадия теперь проходит холодную ветку сама.

### 8.16 Шаг 1, раунд 153-13: `SceKblParam` строит сам second_loader (шаги 2 и 3 закрыты)

**Сделано.**

1. **Холодный путь стал основным.** Обе подстановки, которые его открывали
   (дайджест метаданных `0xA532` и сверка версии `0xF76`), перенесены из
   выключенного эксперимента `kColdPathPatches` в основной список
   `kSecondLoaderPatches` (`src/hw/cmep/bigmac.cpp`). Переменная
   `ZLB_CMEP_COLD_PATH` больше не нужна.
2. **`build_kbl_param()` больше не вызывается** в обычном прогоне
   (`src/machine/bootchain.cpp`): запись строит вторая стадия, а C++-сборщик
   остался только фолбэком для прогона с `ZLB_NO_SUBSTITUTION=1`, где
   загрузчик до этого места не доходит. Зеркало scratch на PA 0 сохранено —
   ARM читает запись именно через него.
3. **База исправлена: `kKblParamBase = 0x1F000040` → `0x1F000100`**
   (`src/machine/vita.h`). Прежнее значение было выведено из викиной фразы про
   «fallback DIP switch buffer по физическому 0x80» и оказалось на 0xC0 ниже:
   оно не только ставило запись не туда, но и **накрывало первые 0x40 байт
   записи загрузчика** (version, size, версии прошивки, QA-флаги).

**Проверка (шаги 2 и 3).** Трап чтений ARM в диапазоне PA `0x100..0x140`:

```
[rtrap] arm_bootrom +0x00100 r4 = 0x1000001 pc=400376E4 core=ARM Cortex-A9
[rtrap] arm_bootrom +0x00104 r4 = 0x0       pc=400376E8 core=ARM Cortex-A9
...
[rtrap] arm_bootrom +0x00130 r4 = 0xFF00FFFF pc=4003772C core=ARM Cortex-A9
```

`0x01000001` = `version = 1` + `size = 0x100` — это **запись загрузчика**, а не
модели (раньше на `+0x100` лежал `0x60`, sleep-фактор подстановки). То есть
**KBL читает `SceKblParam` по базе PA `0x100` = `0x1F000100`**, и вопрос
«по какой базе KBL её читает», стоявший с §8.2, закрыт: по той же, по которой
её пишет загрузчик.

Цепочка при этом работает: ARM отпускается, стартует на `kernel_boot_loader`
по `0x40020000` и доходит до того же состояния `pc=0x31C`, что и раньше.

**Что осталось за рамками шага 1 (честно).**

* Часть полей записи пуста (`+0x04`/`+0x08` — версии прошивки `0`, `+0x30` —
  `0xFF00FFFF`): это per-console данные (idstorage/SMI), которых нет ни в одном
  дампе, и `0x40E40` отвечает на них `0xFFFFFFFF` «не запрограммировано».
  Реконструкция idstorage (`docs/EMMC.md` §5) — стёртый плейсхолдер, так что
  запись честно отражает отсутствие данных, а не подменяет их.
* Машинный слой отпускает ARM по бюджету срезов (холодный путь длинный: CMeP
  проходит сотни миллионов инструкций), а не по сигналу загрузчика. Это
  следующая отдельная задача — «ждать окончания второй стадии», а не «ждать
  бюджет».

**Проверки.** Самотесты **416/0**; `verify.ps1` — все девять пунктов `ok`
(build, self tests, machine layout, boot plan, first loader, second loader,
arm kernel boot loader, kernel stage, eMMC image; 992 файла, 0 расхождений).

### 8.15 Шаг 1, раунд 153-12: сборщик исполнен, база SceKblParam установлена — 0x1F000100

**Цель достигнута по существу.** С `ZLB_CMEP_COLD_PATH=1` вторая стадия
проходит **все** целевые чекпойнты и **сама** строит `SceKblParam`:

```
[mep] pc=0x408A4  (чекпойнт 0x5E)
[mep] pc=0x408C6  (чекпойнт 0x4A)
[mep] pc=0x408DE  (чекпойнт 0x5A)  $1=0x55320 $2=0xFFFFFE00 $3=0x800
[mep] pc=0x408E4  (GPO после 0x5A)
[mep] pc=0x408EC  (вызов сборщика)
[mep] pc=0x41B4A  <-- СБОРЩИК ИСПОЛНЯЕТСЯ
```

Понадобилась одна дополнительная подстановка (§8.14 + этот раунд):
`0x40F5E` сверяет версию, прочитанную через `0x40E40`, с `0x01040000` и падает с
`0x800F0037`; `0x40E40` возвращает `0xFFFFFFFF` («не запрограммировано») —
номер берётся из per-console idstorage/SMI, которых нет ни в одном дампе, а
`docs/EMMC.md` §5 реконструирует idstorage как стёртый плейсхолдер. Вызывающий
уже знает значение (`$6 = 0x01040000`), поэтому подстановка `{0xF76, 2, 0x0360}`
(`lw $3,0x4($sp)` → `mov $3,$6`) входит в тот же выключенный эксперимент.

**Шаг 2 — адрес появления структуры (ответ).** Дамп после прогона:

```
1F000160  00 00 00 40  00 00 00 20  00 00 00 00  04 00 0C 00
          ^DRAM base   ^DRAM size   ^0            ^boot type
1F000100  60 00 00 00  14 FF 00 00  40 00 00 00  00 00 00 00
          ^sleep       ^wakeup      ^USB info
1F000130  ...          00 00 01 00  AA 03 AC CB   <- magic 0xCBAC03AA
```

Смещения загрузчика — `+0x60` DRAM base `0x40000000`, `+0x64` размер
`0x20000000`, `+0x6C` boot type `0x000C0004` — **точно совпадают с раскладкой,
которую документирует вики** (`KBL_Param` +0x60/+0x64/+0x6C). То же видно и
дальше:

```
1F000190  00 05 00 40  F8 88 00 00  00 8F 00 40  C0 06 00 00
          ^kprx paddr  ^kprx size   ^rvk paddr   ^rvk size
```

то есть `+0x90 = 0x40000500`, `+0x94 = 0x88F8`, `+0x98 = 0x40008F00`,
`+0x9C = 0x6C0` — ровно `kprx_auth_sm.self` и `prog_rvk.srvk`, как их описывает
вики. Итого **`SceKblParam` строится по базе `0x1F000100`**, как и говорил
дизассемблер `0x41B4A` в раунде 153-3, а не по `0x1F000040`, как предполагала
модель; вывод вики про «fallback DIP по PA 0x80» оказался ошибочным.

**Важное следствие: подстановка модели не просто стоит не по адресу — она
портит структуру загрузчика.** Массив модели (`base 0x1F000040`, размер 0x100)
накрывает `0x1F000040..0x1F00013F`, то есть **первые 0x40 байт структуры
загрузчика** (`0x1F000100..0x1F00013F` — version, size, версии прошивки, QA
флаги). Видно прямо в дампе: на `0x1F000100` лежит `0x60` (sleep-фактор модели),
хотя по раскладке загрузчика это поле `version` и там должно быть `1`.

**Состояние цепочки.** С включённым холодным путём ARM **отпускается и
стартует на `kernel_boot_loader` по `0x40020000`** (отпускание пока по бюджету
срезов, а не по сигналу загрузчика), CMeP продолжает работу (`pc=0x485E8`).

**Что осталось (шаг 3).** Снять `build_kbl_param()` и сделать холодный путь
основным: тогда `SceKblParam` будет ровно тот, что построил загрузчик, и
проверится главный вопрос — читает ли KBL структуру по базе `0x1F000100`
(тогда всё сходится) или по `0x1F000040` (тогда нужно понять, кто и когда
переносит её на 0xC0 ниже).

### 8.14 Шаг 1, раунд 153-11: найдена и исправлена ошибка ADMA2 — чекпойнты 0x59 и 0x4E пройдены

**Причина простоя найдена и устранена.** Дамп дескрипторов ADMA2
(`ZLB_SDIF_TRACE=1`, добавлен вывод каждой записи) на падающей передаче:

```
CMD23 arg=0x1DF            (479 блоков)
CMD18 arg=0x61F8 count=479 multi=1 dma=1 adma=0x40000400
[sdif] adma rec @0x40000400 attr=0x0021 len=0      target=0x5FFC0000
[sdif] adma rec @0x40000408 attr=0x0021 len=0      target=0x5FFD0000
[sdif] adma rec @0x40000410 attr=0x0021 len=0      target=0x5FFE0000
[sdif] adma rec @0x40000418 attr=0x0023 len=48640  target=0x5FFF0000
[sdif] adma table=0x40000400 moved=48640/245248 ok=0
```

Цели стоят ровно через 64 КиБ, а `3 * 65536 + 48640 = 245248` — **в точности**
размер передачи, который запросил CMD23. Значит **`length == 0` у валидной
записи ADMA2 означает полный блок 64 КиБ, а не пустую операцию**; модель
трактовала такие записи как пустые, обход останавливался после 48 640 байт,
короткая передача давала драйверу ошибку, и он уходил в вечный повтор
(`0x47C5E`, 76 600 итераций с задержкой `0xf4240`, §8.13).

Исправлено в `src/hw/soc/sdif.cpp` (`Sdif::adma_transfer`): эффективная длина
записи `transfer_length = length == 0 ? 0x10000 : length`, она же идёт в
`consumed`/`adma_bytes_`.

**Результат.** С `ZLB_CMEP_COLD_PATH=1` холодная ветка впервые проходит дальше
отказа на `0x4112E`:

* достигнут **чекпойнт `0x59`** (`0x4086C`);
* достигнут **чекпойнт `0x4E`** (`0x4088A`, GPO-значение `0x0A`);
* следующий барьер — `0x40F5E` возвращает **`0x800F0037`**, и ветка уходит в
  ошибку чекпойнта `0x4E` (`0x40920`).

То есть загрузка `kernel_boot_loader.self` с eMMC (шаг чекпойнта `0x49`) теперь
**проходит по-настоящему**, и цель «дойти до `0x5A` и до сборщика `0x41B4A`»
впервые стала вопросом нескольких проверок, а не криптографии.

**Проверки.** Самотесты 416/0; обычный прогон по умолчанию не изменился
(`cmep=0x40002`, `arm=0x31C`, `insns=9382908`) — правка ADMA2 срабатывает
только на таблицах с нулевой длиной записи, которые в обычном прогоне не
встречаются.

**Следующий шаг:** разобрать `0x40F5E` и ошибку `0x800F0037` (готовится на
`0x41FA2`, рядом `0x800F0039` на `0x41F98`) — что именно проверяется между
чекпойнтами `0x4E` и `0x5E`.

### 8.13 Шаг 1, раунд 153-10: холодная ветка проходит крипту и упирается в SDIF

С включённым `ZLB_CMEP_COLD_PATH=1` (см. §8.12) замеры дают такую картину.

**Чекпойнты `0x59/0x4E/0x5E/0x4A/0x5A` всё ещё не достигаются**, но причина
сменилась: загрузчик больше не падает на криптографии, а уходит в реальную
работу с хранилищем.

**Что он делает.** Трасса SDIF (`ZLB_SDIF_TRACE=1`) с включённой подстановкой:

```
CMD13 SEND_STATUS            x20
CMD17 args 0x000200 x10, 0x000266, 0x000267, 0x006000, 0x0061EF, 0x0061F7
CMD23 SET_BLOCK_COUNT        args 0x0001DF, 0x000007
CMD18 READ_MULTIPLE_BLOCK    args 0x0061F0, 0x0061F8
```

То есть читаются блоки области SLB2 в пользовательской части (0x6000 — 12 МиБ,
вторая копия SLB2; 0x61EF/0x61F0/0x61F7/0x61F8 — внутри неё), в том числе
многоблочным чтением. Это именно загрузка файлов `kernel_boot_loader.self` и
соседей.

**Где застревает.** Загрузчик крутится в цикле драйвера:

```
0x47C5E  bsr 0x47448          ; wait/delay (внутри — цикл stcb/ldcb 0x454F4..0x45526)
0x47C68  lw  $2,0x10($sp)
0x47C6A  lw  $3,4($2)
0x47C74  beqi $2,0x0,0x47914
...
0x47C82  lw  $0,44($5)        ; статус передачи
0x47C90  bgei $0,0x0,0x47CA4  ; $0 >= 0 -> выход; иначе повтор
0x47C9A  sw  $2,32($5)
0x47CA0  bgei $3,0x1,0x477B6  ; счётчик попыток -> назад в начало операции
```

То есть **драйвер повторяет операцию, пока результат передачи отрицательный**.
За прогон `0x4552C` (ожидание с задержкой `0xf4240`) вызывается **76 600 раз** из
`0x47C63`, и за 200 тыс. срезов CMeP проходит 51.2 млн инструкций, оставаясь в
`0x4553E`. Это не «долгая загрузка», а бесконечный повтор: модель сообщает
**ошибку передачи** для этих чтений.

**Итог раунда.** Криптографический барьер снят полностью (§8.11–8.12): движок
окна расшифровывает метаданные, дайджест-проверка обойдена, холодная ветка

одноблочные чтения (CMD17) проходят.

**План раунда 11:** трассировать передачу CMD18/CMD23 в `src/hw/soc/sdif.cpp`,
сравнить с одноблочным CMD17 (который работает) и найти, что именно даёт

### 8.12 Шаг 1, раунд 153-9: новый барьер — сверка 32-байтового дайджеста

Разобран новый отказ (`0x800F0627`, `0x4A538`).

**Механика проверки.**

```
0x4A51E  bsr 0x4B546        ; посчитать дайджест в буфер (sp+4)
0x4A526  lw  $2,116($6)     ; ожидаемый дайджест (указатель)
0x4A52A  mov $1,$7          ; буфер с посчитанным
0x4A52C  mov $3,32          ; 32 байта
0x4A52E  bsr 0x4C390        ; memcmp
0x4A532  beqz $0,0x4A540    ; равны -> дальше; иначе...
0x4A538  or3 $5,$5,0x627    ; ошибка 0x800F0627
```

`0x4C390` — это `memcmp`: побайтово `xor` и `or` результата, возвращает 0
только при полном совпадении. В прогоне он возвращает `0xFF`, то есть дайджесты
**различаются**.

* `0x4B546` — «посчитать дайджест»: `bsr 0x44F20` (инициализация контекста,
  `($1)=0`, `4($1)=0x2080`), затем `bsr 0x4C08E` с типом `$1=6`, контекстом,
  получателем и источником. `0x4C08E` — диспетчер: копирует 12 байт таблицы по
  `0x4D42C` и выбирает обработчик по `(тип-4)*4`, то есть тип 6 — это один из
  вариантов хеша/подписи, а не «просто SHA».
* Адреса из трапы: структура `$6 = 0x5DBF0`, в ней `+0x74` → `0x5EF50`
  (ожидаемый дайджест) и `+0x78` = `0x5DC68` (описание источника), сам источник
  описан парой `{2, 0x34}` (`mem 0x5DC60`), а по `0x5DBF0` лежит указатель
  `0x5DE0C`.

**Что это значит.** Расшифровка метаданных теперь проходит (§8.11), но
следующая проверка сверяет посчитанный дайджест со «своим» сохранённым
значением и не сходится. По расположению (`0x49xxx`–`0x4Axxx` — район
валидаторов SCE/записи) и по тому, что в этой же зоне проект уже вынужден
подставлять соседние проверки («configuration record MAC 1-3» на
`0x49122/0x4912C/0x49136`, дайджест записи `0x0F` на `0x4292E`, валидатор
ответа SCE на `0x49D5C`), это, скорее всего, **та же категория проверок,
опирающихся на per-console/ключевые данные**, которых в дампах нет.

**План раунда 9.** Прежде чем реверсить `0x4C08E` до конца, определить *размер*
оставшейся цепочки: временно форсировать ветку `0x4A532` (подстановка в том же
стиле, что уже применяется в проекте для соседних проверок) и измерить, сколько
ещё проверок отделяет холодную ветку от чекпойнта `0x5A`. Это даст ответ, можно
ли дойти до сборщика в принципе, или холодная ветка упирается в per-console
данные, и тогда честный `SceKblParam` недостижим без них.

### 8.10 Шаг 1, раунд 153-7: протокол окна целиком — это расшифровка заголовка SELF

Полная трасса (`ZLB_SCEBLOCK_TRACE=1`, 4000 обращений) даёт протокол из трёх фаз:

| Индексы | Что происходит |
|---|---|
| 0…11 | **запись 48 байт**: `SceHeader` (`SCE\0`, 3, `0x10140`, `0x600`, `0x1000`, `0x55B94`, `0x56B94`) |
| 12…23 | **чтение 48 байт** — валидатор `0x4A740` проверяет записанное |
| 24…3723 | **запись 3700 слов**: смещения окна `0x0000…0x0FCF`, то есть 4048 байт полезной нагрузки |
| 3724… | **чтение** тех же 4048 байт — загрузчик разбирает результат |

**Полезная нагрузка — это `SELF[0x30 .. 0x1000)`.** Доказательства:

* первое слово нагрузки — `0x4`, то есть `SelfHeader.self_offset`, а оно лежит в
  файле по смещению `0x30` (`SelfHeader` начинается на `0x20`, поле — третье);
* независимая сверка по якорю: содержимое окна на `+0xC20` побайтово равно
  `kernel_boot_loader.self` на `+0xC50` (шаблон `15 09 D2 28 7F 93 9D FB`
  встречается в файле ровно один раз — по `0xC50`);
* `0x30 + 0xFD0 = 0x1000` — ровно `SceHeader.header_length`.

**Значит движок должен расшифровать этот блок на месте.** Область `SELF[0x600…]`
внутри нагрузки — это зашифрованные метаданные (`SceHeader.metadata_offset =
0x600`), и загрузчик читает их обратно уже расшифрованными, чтобы разобрать
таблицу секций (`MetadataSection` — 48 байт, ровно тот шаг, что виден в
`0x49F42`). Модель отдаёт записанное без изменений, поэтому загрузчик получает
шифртекст, границы таблицы считаются мусором (§8.6) и холодная ветка падает с
`0x800F0624`.

**Проводка для реализации уже есть:** `CmepBlock` создаётся с ключами
(`src/machine/vita.cpp:173`, `std::make_unique<CmepBlock>(*cmep_bus_, keys_)`), а
`SceBlockDevice` конструируется внутри `CmepBlock` (`cmep_block.cpp:89`) — то
есть ключи доходят до устройства. Расшифровка метаданных реализована в
`src/loader/self.cpp` (`decrypt_metadata`, строка 516: AES-CBC по ключу
метаданных, выбор кандидата по `key_revision`/`self_type`).

**План раунда 7:**

1. выставить из `self.cpp` функцию «расшифровать метаданные SELF в буфере на
   месте» (обёртка над `decrypt_metadata`, которая пишет результат обратно);
2. научить `SceBlockDevice` принимать ключи и запоминать 48-байтовый `SceHeader`
   из первой фазы;
3. по переходу «запись нагрузки → первое чтение» собрать образ
   `SCE-заголовок || нагрузка`, расшифровать метаданные и подменить содержимое
   окна на расшифрованное (ленивая обработка «движок отработал задание»);
4. прогнать и проверить, доходит ли холодная ветка до чекпойнтов
   `0x59/0x4E/0x5E/0x4A/0x5A`.

| `+0x00` | `0x4` | `self_offset` |
| `+0x08` | `0x80` | `appinfo_offset` |
| `+0x10` | `0xA0` | `elf_offset` |
| `+0x18` | `0xE0` | `phdr_offset` |
| `+0x20` | `0x56A04` | `shdr_offset` |

| `+0x40` | `0x1B0` | `controlinfo_length` |

который затем читает 4048 байтами и разбирает по смещению `0xC30`. Модель просто
хранит записанное, поэтому вместо результата загрузчик читает собственный запрос

увенчался успехом; затем проверить чекпойнты `0x59/0x4E/0x5E/0x4A/0x5A`.

### 8.8 Шаг 1, раунд 153-5: окно — это буфер «запрос → ответ», модель возвращает запрос

Уточнил механику окончательно.

**Протокол обмена.** Загрузчик кладёт в окно `0x5FFC0000` первые 512 байт
блока `kernel_boot_loader.self`, прочитанного с eMMC в DRAM `0x40000200`
(источник — `movh $3,0x4000; or3 $3,$3,0x200` в драйвере `0x45D6C`):

| Кто (`lp`) | Копирование |
|---|---|
| `0x45D79` | `0x5FFC0000 ← 0x40000200`, 12 слов = **48 байт** |
| `0x45D79` | `0x5FFC0000 ← 0x40000230`, 116 слов = **464 байта** |
| `0x412F9` | `0x5E800 ← 0x5FFC0000`, 12 слов = 48 байт (проверка заголовка) |
| — | `memcpy(0x5E830, 0x5FFC0000, 0xFD0)` = **4048 байт** — это и есть чтение ответа |

Структура, которую потом разбирает `0x49FE8`/`0x4AD92` (см. §8.6), лежит по
смещению **`0xC30`** внутри этих 4048 байт.

**Проверено, что запрос — это сам SELF.** `mem 0x40000200` даёт
`53 43 45 00 03 00 00 00 40 01 01 00 …`, и это **побайтово равно** началу
`Vita_104_Firmware/Out/SLB2/kernel_boot_loader.self` (magic `SCE\0`, версия 3,
байт 8 = `0x40`). Поэтому проверки `0x4A740` (магия, слово 1 = 3, бит `0x40`)
проходят **на самом запросе** — на эхо-модели они не доказывают ничего.

**Окно в модели заполняется гостем, а не моделью.** `RegisterFile::peek`
(`src/bus/device.cpp`) возвращает 0 для незаданных адресов, и действительно
`mem 0x5FFC1000`/`0x5FFCF000` читаются нулями; но `mem 0x5FFC0C20` даёт
стабильные псевдослучайные значения (`15 09 D2 28 7F 93 9D FB …`), а
`mem 0x5FFC0020` — таблицу малых значений (`04 00 00 00 … 80 00 00 00 …`).
Значит ~4048 байт в окно пишет **сам загрузчик** (в том числе прямыми `sw`, а не
только через memcpy — иначе трапы их бы поймали). Модель в окно не пишет вообще:
`SceBlockDevice` только объявляет 12 регистров заголовка в конструкторе, других
писателей в `src/` нет (проверено grep-ом по `kSceBlockBase`/`SceBlock`).

**Вывод.** Окно — это буфер «запрос → ответ» для защищённого движка: загрузчик
**сам** заполняет 4048 байт и читает те же 4048 байт обратно, ожидая **другой**
результат. Модель отдаёт запрос без изменений, поэтому дальнейший разбор
метаданных даёт мусорные границы таблицы (§8.6) и холодная ветка падает с
`0x800F0624`. Это и есть недостающий компонент шага 1.

**Что для этого уже есть в проекте.** Вся нужная криптография реализована и
проверена: `src/loader/self.cpp` делает разбор SCE-контейнера, расшифровку
метаданных (AES-CBC по ключу метаданных), разбор key vault и AES-128-CTR по
сегментам — и на этом `kernel_boot_loader.self` расшифровывается побайтово
(`seg00..seg03`, `docs/BOOT.md` §5). То есть реализации не хватает только
«проводки»: окно `0x5FFC0000` должно прогонять поданный SELF через этот код и
отдавать результат.

**Следующий раунд:** зафиксировать, что именно загрузчик ожидает в ответе на
смещении `0xC30` (структура с полями `+0x10`/`+0x14`, задающими таблицу секций),
и подключить `self.cpp` к `SceBlockDevice` — после чего проверить, проходит ли
холодная ветка чекпойнты `0x59/0x4E/0x5E/0x4A/0x5A`.

### 8.7 Шаг 1, раунд 153-4: не хватает преобразования в окне SCE (корень найден)

Разобрал, кто и что пишет в `0x5FFC0000`, трапом вызовов memcpy (`pc=0x40B06`;
для word-варианта store на `0x40B0E`, поэтому трап печатает `pc=0x40B10`):

| Кто (`lp`) | Что копируется |
|---|---|
| `0x459F9` | `0x5E200 ← 0x40000200`, 512 байт (кэш прочитанного блока) |
| `0x45D79` | **`0x5FFC0000 ← 0x40000200`, 48 байт** |
| `0x412F5` | **`0x5E800 ← 0x5FFC0000`, 48 байт** |
| `0x45D79` | **`0x5FFC0000 ← 0x40000230`, 464 байта** |

То есть протокол ровно такой, как описано в `docs/HARDWARE.md` §1.2: **48-байтовый
запрос в окно и 48-байтовый ответ из него** (плюс второй запрос на 464 байта).
Данные для запроса берутся из `0x40000200` — это только что прочитанный с eMMC
блок, а `kernel_boot_loader.self` начинается с `SCE\0` (SELF-магия).

**Отсюда важное уточнение к §8.5:** валидатор `0x4A740` проходил не потому, что
модель отдала «правильный ответ», а потому что **эхо возвращает сам запрос**, а в
запросе уже лежит `SCE\0`, слово 1 = 3 и бит `0x40` байта 8. Проверка на
эхо-модели выполняется тривиально и ничего не доказывает.

**Корень.** `SceBlockDevice` (`src/hw/cmep/mailbox.cpp:116`) — это `RegisterFile`
без обработки, то есть `0x5FFC0000` **эхо**: что записали, то и прочитали. На
железе это окно **преобразует** данные (загрузчик кладёт туда необработанный
заголовок `kernel_boot_loader.self` и читает обратно обработанный). Эхо отдаёт
необработанный заголовок, из него `0x4AD92` считает границы таблицы секций
(`[0x62700, 0x6C)` — см. §8.6), поиск записи типа 3 уходит в стёртую память, и
холодная ветка падает с `0x800F0624` на чекпойнте `0x49`.

**Что это значит для шага 1.** Не хватает не SDIF, не idstorage и не проверок
заголовка, а **преобразования в окне `0x5FFC0000`**. Кандидат на реализацию уже
есть в проекте: модель умеет расшифровывать `kernel_boot_loader.self` в C++
(`src/loader/self.cpp` / `self_to_elf`, проверено побайтово на `seg00..seg03`,
`docs/BOOT.md` §5). То есть для прохождения шага 1 нужно соединить эти две части:
окно SCE должно отдавать загрузчику то, что `self_to_elf` уже умеет считать.

**Следующий раунд:** определить точный контракт окна для этих двух запросов
(48 и 464 байта) — что именно загрузчик ожидает получить обратно, и можно ли это
получить существующим кодом `self_to_elf`; затем реализовать окно и проверить,
доходит ли вторая стадия до чекпойнта `0x5A`.

### 8.6 Шаг 1, раунд 153-3: падает разбор таблицы секций (точка найдена)

Довёл цепочку до конкретной инструкции.

**1. Точка отказа.** `0x4131A` после трёх успешных проверок вызывает
`0x49F42($7, &out, 3)` на `0x41462`. Эта функция ищет в таблице запись
запрошенного типа, шагая по записям переменного размера (тип 2 → шаг `0x110`,
тип 1/3 → шаг `0x30`); любой другой первый word — ошибка:

```
0x49F7A  lw $1,($2)              ; первый word записи
0x49F7C  bne $1,$5,0x49f88       ; не наш тип -> разбирать тип
0x49F88  beqi $1,0x2,...; beqi $1,0x3,...; bnei $1,0x1,0x49fc8
0x49FC8  -> выход с $0 = 0x800F0624
```

Наблюдение: `$1 = 0xFFFFFFFF` — то есть **таблица читается как стёртая
память**, и поиск типа 3 не находит ничего.

**2. Откуда берутся границы таблицы.** Их считает `0x4AD92`:

```
0x4ADB4  bsr 0x4A008        -> $0 = 0x61B30   (база)
0x4ADBC  bsr 0x49FE8        -> $0 = 0x5EE70   (заголовок)
0x4ADC2  lw $3,16($0)       -> 0xBD
0x4ADC6  sll $3,0x4         -> 0xBD0
0x4ADC8  add3 $8,$8,$3      -> start = 0x61B30 + 0xBD0 = 0x62700
0x4ADD0  lw $3,20($0)       -> end   = 0x6C
```

То есть таблица объявлена как `[0x62700, 0x6C)` — начало больше конца, а сам
`0x62700` лежит **вне** окна CMeP в модели.

**3. Проверка карты памяти.** `map` показывает
`page-region CMeP.RAM base=0x00040000 size=0x20000` — то есть 0x40000..0x5FFFF
и ничего выше. Трап `ZLB_WTRAP=60000-64000` даёт **ноль** записей от CMeP: адрес
`0x61B30`/`0x62700` только вычисляется и читается, но никогда не пишется, и
чтение оттуда возвращает `0xFFFFFFFF`. Отсюда и «неизвестный тип записи».

**4. Что за заголовок.** `0x49FE8` возвращает `base + field(+0xC) + 0x70`; для
нашего случая это `0x5EE70`. Его содержимое — маленькие байтовые значения,
разложенные по словам (`65 1E 4F EE BD 6C A0 81 …`), и выглядит как
псевдослучайные байты. Трап записей в `0x5EE00-0x5EF00` показывает, что их
пишет **CMeP с `pc≈0x40B10`** — то есть ровно тот адрес, который
`docs/HARDWARE.md` §1.2 связывает с обработкой SCE/SC-блока
(`0x5FFC0000`, проверка на `0x4A774`). Заполнение идёт байтовым копированием
(цикл `lb`/`sb` на `0x40B16..0x40B22`).

**Вывод раунда.** Холодная ветка падает **на разборе метаданных загруженного
`kernel_boot_loader.self`**: структура, из которой берутся границы таблицы
секций, содержит мусор, поэтому границы получаются бессмысленными, а поиск
записи типа 3 уходит в стёртую память. SDIF, idstorage (совпадает с эталонным
дампом на блоке `0x200`) и проверки заголовка SCE-блока тут ни при чём — все
они проходят.

**Что проверять дальше (раунд 3):**

1. кто именно формирует содержимое `0x5EE60` — найти вызов копирования,
   покрывающий этот диапазон, и его источник; мусорные байты означают либо
   неверный источник, либо неверную расшифровку;
2. отдельно решить вопрос окна CMeP: если `0x60000..0x7FFFF` на железе тоже
   RAM, то `0x20000` в модели — заниженный размер, и часть данных загрузчика
   теряется; это проверяется по тому, пишет ли загрузчик туда в других ветках.

### 8.5 Шаг 1, раунд 153-2: падает загрузка `kernel_boot_loader.self` (не SCE)

Главное: **дескриптор `0x4CDA4`, который `0x4112E` передаёт загрузчику, — это
таблица имён файлов, закодированная XOR с `0xFF`.** После декодирования:

```
0x4CDA4  "kernel_boot_loader.self\0"
0x4CDBC  00001000
0x4CDC0  "context_auth_sm.self\0"
0x4CDD8  "kprx_auth_sm.self\0"
0x4CDF0  "prog_rvk.srvk\0"
```

То есть упавший вызов — это ровно тот шаг, который вики помечает чекпойнтом
`0x49` («Loading `kernel_boot_loader.self`», ошибка чтения/загрузки) **[В]**.
Строки закодированы XOR-ом, поэтому `strings` по образу их не находит.

Разбор цепочки:

| Адрес | Что делает |
|---|---|
| `0x4112E` | `movu $1,0x55148; movu $3,0x4CDA4; jmp 0x4131A` — обёртка |
| `0x55148` | vtable хранилища: `{0x45B52, 0x45BB6, 0x45BE0, 0x45C98, 0x45DD8}` |
| `0x45B52` | открыть устройство; сразу `bsr 0x45A3C` — путь SDIF/ADMA2 |
| `0x4131A` | загрузить файл по таблице, распаковать/расшифровать, проверить |
| `0x4A740` | валидатор SCE-блока — **проходит все проверки** |
| `0x498E8` | валидатор записи SLB2: `field0 == 4`, `field1 == 0`, `(field4 & 0xF) == 0`, … |

Проверки SCE-блока (`0x4A774`…`0x4A79A`, ровно те, что описаны в
`docs/HARDWARE.md` §1.2) **проходят**: в трапе на `0x4A786` `$1 == $2 ==
0x00454353` («SCE\0»), на `0x4A78E` `$2 == 3`, на `0x4A796` `$2 == 0x40`.
Инструкция `0x4A782` (`or3 $5,$5,0x624`) только *готовит* код ошибки перед
ветвлением — само по себе её исполнение ни о чём не говорит, и первая версия
диагноза (§8.4), где `0x800F0624` приписывался провалу SCE, была неверна.

Что показывает трасса SDIF (`ZLB_SDIF_TRACE=1`): SDIF жив и работает по-настоящему
— `CMD0`, `CMD1` (`arg=0x40000080`), `CMD2/3/9/7`, `CMD8`, `CMD16`, затем
`CMD17` с **ADMA2** (`dma=1 adma=0x40000400`, `block=512`, `count=1`). Но чтения
идут **повторно по одному и тому же блоку `arg=0x200`**, между ними `CMD13`
(SEND_STATUS): `0x200, 0x200, 0x200, 0x2C0, 0x200, 0x200, 0x264, 0x200 …` —
это retry-цикл вокруг области `0x200` (блок `0x200` = байт `0x40000`, то есть
начало **idstorage**), а idstorage в модели — синтетический плейсхолдер
(`docs/EMMC.md` §5).

Следующий шаг раунда: отделить «плохие данные» от «неверного чтения» —
сравнить то, что модель отдаёт на блоке `0x200`, с тем, что проверяет `0x498E8`
(`field0 == 4`, `field1 == 0`, `(field4 & 0xF) == 0`), и найти конкретную
ветку, уводящую на `0x49D54`/`0x49D5C`.

Коды ошибок этого узла: `0x800F0616` (готовится на `0x498FE`) и `0x800F0624`
(готовится в 12 местах: `0x49932`, `0x499BC`, `0x499F4`, `0x49A3E`, `0x49A72`,
`0x49A94`, `0x49ADA`, `0x49D58`, `0x49F26`, `0x49FCC`, `0x4A782`, …).

### 8.4 Шаг «довести вторую стадию до сборщика»: диагноз (раунд 153)

Замер `ZLB_MEP_PC` в **обычном** прогоне показывает, что реальная холодная
ветка второй стадии **падает**, не доходя до сборщика:

```
pc=0x40848  (чекпойнт 0x49)  lp=0x40831
pc=0x40858  (холодная ветка, beqz $8 на 0x40850)
pc=0x4112E  $1=0x5DF9C (указатель на выходной слот sp+0x34)
pc=0x40860  $0 = 0x800F0624      <-- ошибка
pc=0x40554  $1=2 $2=0x49         <-- доклад «чекпойнт 0x49»
```

То есть чекпойнты `0x59`, `0x4E`, `0x5E`, `0x4A`, `0x5A` и вызов сборщика
`0x408EC → 0x41B4A` не достигаются **вообще**, ни в одном прогоне.

Разбор падения:

* `0x4112E` — это `mov $4,$1; mov $2,1; movu $1,0x55148; movu $3,0x4CDA4;
  jmp 0x4131A`, то есть тонкая обёртка над загрузчиком контейнера `0x4131A`;
* `0x4131A` работает по vtable `0x55148 = {0x45B52, 0x45BB6, 0x45BE0,
  0x45C98, 0x45DD8}` (значения выгружены из образа) и вызывает их по очереди;
  `0x45B52` первым делом делает `bsr 0x45A3C` — это путь SDIF/ADMA2
  (`docs/HARDWARE.md` §4.1), то есть шаг «открыть устройство»;
* затем идут `0x45C98(0, 0x5FFC0000, 0x30)` и `0x45C98(0, 0x5FFC0000, 0xFD0)` —
  чтение **SCE-блока** `0x5FFC0000`, и после второго прохода управление уходит
  на `0x4176A` с `$0 = 0x800F0624`;
* код `0x800F0624` строится в 12 местах образа (`0x49932`…`0x4A782`, район
  валидатора SCE-ответа) — это общий код ошибки проверки контейнера/ответа SCE.

В модели `SceBlockDevice` (`src/hw/cmep/mailbox.cpp:116`) задаёт 12 байт
заголовка (`magic` `"SCE\0"`, status `3`, flags `0x00010140`). **Уточнено в
§8.5:** проверки SCE-блока на самом деле **проходят**, а падает загрузка файла
`kernel_boot_loader.self` — вывод этого пункта про «недоданное содержимое
SCE-блока» не подтвердился.

Отдельно проверено, что падение **предсуществующее**: с застэшенными правками
SC-команд (`ernie*.cpp`, `ernie_internal.h`, `test_syscon.cpp`) прогон даёт тот
же `$0 = 0x800F0624` на `0x40860`, так что правка NVS/scratchpad к нему
отношения не имеет.

**Следствие для плана.** Пункты 2 и 3 (взять базу из памяти, снять
`build_kbl_param()`) недостижимы, пока не закрыт пункт 1: сборщик не
исполняется, значит «адреса, по которому структура реально появляется», не
существует, а снятие подстановки оставит KBL с пустым параметром. Закрытие
пункта 1 = выяснить, что загрузчик ожидает прочитать в SCE-блоке `0x5FFC0000`
после заголовка (в дампах этого нет), либо найти путь, на котором он этого не
требует.

### 8.3 Почему «честный» KBL пока не разворачивается (раунд 152)

Проверено замерами, а не рассуждением. Что **уже** работает по-настоящему:

* ARM-окно PA `0x0` — **настоящий алиас** общей SRAM
  (`vita.cpp:133`, `add_ram_alias("arm_bootrom", 0, …, shared_sram_.data())`),
  а не копия: `mirror_cmep_scratch_to_arm()` пишет буфер сам в себя и является
  no-op. Значит всё, что оставит вторая стадия, KBL видит напрямую — честный
  путь архитектурно открыт;
* вторая стадия реально исполняет **LPDDR2-шаг**: `pc=0x405A2` → `pc=0x483DA`
  (трассировка `ZLB_MEP_PC`), затем `pc=0x40858` не достигается, но
  `clear_kbl_param` **достигается**: `pc=0x41B38`, и трап записей CMeP
  (`ZLB_WTRAP=1F000000-1F000140`) показывает его memset — нули в
  `0x1F000100..0x1F0001FF`.

Чего **не** происходит: `pc=0x408EC` и `pc=0x41B4A` (сборщик `SceKblParam`)
не достигаются ни разу. Причина найдена в модели, а не в железе:
`Vita::cmep_pc_hook` (`bootchain.cpp:2242`) на «done»-прыжке secure kernel
**проглатывает переход и останавливает CMeP**, поэтому бюджет
`cmep_finish_pending_` (`kCmepFinishBudget = 2 000 000`) тратится впустую —
`poll_boot_chain` видит уже остановленное ядро («it stopped by itself, 1
steps») и отпускает ARM.

Эксперимент `ZLB_CMEP_HANDOFF_RUN=1` (не глотать переход, дать второй стадии
доработать) даёт: CMeP впервые доходит до холодной ветки **`0x40858`** и
прогоняет 14.8 млн инструкций вместо 117 тыс., но за 60 тыс. срезов до
сборщика не добирается и сигнала на отпускание ARM не выдаёт — прогон
заканчивается с ARM на `0x80000000`. То есть **однострочником это не
решается**, и по умолчанию эксперимент выключен. Настоящий барьер выше:
`ZLB_NO_SUBSTITUTION=1` доводит CMeP до `0x5FF1E` и `sleep` — сервис первого
загрузчика `0x5FF00` отсутствует во **всех** дампах, и именно его подставляет
`serve_cmep_service_call()`.

Вывод по базе: **`kKblParamBase` — не тот затык, который блокирует честный
KBL**, и менять его сейчас нельзя. Дизассемблер загрузчика даёт `0x1F000100`
(см. §8.2 п.4), вики — `0x1F000040`; противоречие не снято, а ARM в текущем
прогоне читает PA `0x40` и получает `0x01000001` = version 1 + size 0x100,
то есть правдоподобный заголовок именно по базе `0x40`. Пока параметр
подставляет модель, этот опыт ничего не доказывает: сначала нужно, чтобы
вторая стадия дошла до чекпойнта `0x5A` и записала структуру сама, и уже
тогда смотреть, по какому адресу её читает KBL.

## 9. Что осталось непроверенным

* Дампов Ernie для Slim (RL78/G13) в воркспейсе нет — таблица команд снята с
  `USS-1001.bin` (78K0R); у RL78-ревизии номера команд те же ([В] показывает
  тот же набор), но адреса обработчиков другие.
* Содержимое NVS конкретной консоли отсутствует (её и не может быть в PUP):
  модель сможет дать только «не установлено» (`0xFF`) либо синтетику.
* Байтовый формат SNVS (`0x00D0`/`0x00D2`) не разобран — в модели остаётся
  заглушкой.
* **Смысл отдельных битовых полей** `0xE6000xxx` не установлен (документации
  на контроллер нет) — известны только адреса и значения из таблиц образа.
* **Статически не разобрано 2174 из 6830 обращений к памяти** (базы зависят от
  данных); динамический трап MMIO закрыл бы этот пробел.
* **Что заполняет DRAM `0x40000000..0x40000FFF` на холодной загрузке** —
  неизвестно: в самом загрузчике писателя этих байт нет, а вторая стадия на
  `0x40A76` ищет там подпись `0x61CE6649` (только на resume-ветке; на resume
  обязательна и подпись `0x9E3199B7`).
* **`0xE310xxxx`: SD-хост, SC-мост или и то и другое** — смещения совпадают и с
  SDHCI (`+0x0C`/`+0x0E`/`+0x20`/`+0x58`), и с «окном SC» из `docs/BOOT.md`;
  однозначного ответа пока нет.

### Инструментальные грабли (из раунда 152)

* `zdis --offset N` сохраняет `--base` как адрес **нарезанного** файла, то есть
  `--base 0x40000 --offset 0xA86` печатает байты `0x40A86` по адресу `0x40000`.
  Для второго загрузчика нужно `--base 0x40000` по всему файлу.
* `_scratch/second_loader.bin` (131 072 байта) — **не тот образ**: он отличается
  в 233 байтах внутри первых 91 648 и несёт ещё 39 КиБ данных. Эталон —
  `Vita_104_Firmware/Out/SLB2_dec/second_loader.bin` (91 648 = 0x16600 байт,
  база `0x40000`).
