# Venezia: крупная процедура `0x800618B0` — дизассемблер, разбор и псевдокод

Пример реальной крупной процедуры ядра MeP из образа Venezia (`os0/kd/vnzimg.elf`),
которая работает в VLIW-режиме и вызывает **10 VLIW-подпрограмм** и три обычные
функции. Всё проверено на байтах (`_scratch/pkt_probe.cpp` — прогон
`ivc2_split_packet` по реальным 64-битным чанкам).

---

## 1. Формат пакета: проверен, а не выведен

Важная поправка к прежним заметкам (`docs/VNZIMG_VLIW_0x800622E0.md`): там
адресация была сдвинута на 0x100, и листинг относился к другому месту. Ниже —
проверенный вариант.

Файл-смещение MeP-адреса: **`0x130 + (VA − 0x80000000)`** (сегмент 1 ELF грузится
с файла 0x130 на VA 0x81001000, а образ MeP линкован на 0x80000000).

Доказательство формата — два независимых факта по адресу `0x800618B0`:

```
файл 0x619E0: F0 CF 90 FF 00 00 00 00 | 1A 70 00 00 00 00 00 00 | 6E 4D ...
              `add3 $sp,$sp,-112`       `ldc $0,$lp`              `sw $tp,0x6c($sp)`
```

* ядровая инструкция занимает **2 или 4 байта в начале 8-байтового пакета**
  (`f-major` из первого полу слова: ≥ 12 → 4 байта);
* остаток пакета — **нули**: это слоты IVC2, и в этой процедуре они пустые.

Проверка автоматом (`pkt_probe.exe`, 40 пакетов в двух регионах):

```
packets=80  unknown_core=0        <- 100 % ядровых инструкций декодируются
            slots=143 unknown_slots=... (пустые слоты = c1nop/*unknown*)
```

Если бы границы пакетов были неверны, доля `unknown_core` была бы велика —
поэтому раскладка «ядро + паддинг» подтверждена. Тест воспроизводится:

```powershell
# 1) собрать пробник
cl /std:c++20 /EHsc /MD /I zeliboba\src /Fe:pkt_probe.exe _scratch\pkt_probe.cpp zeliboba\build\zeliboba_core.lib
# 2) прогнать по региону
python _scratch\pkt_test.py
```

## 2. Параметры и вызывающие

Точка вызова (`0x80012FA0`) показывает соглашение:

```asm
80012FA0  lw   $12,0x6c($sp)
80012FA2  lw   $1,($12)          ; $1 = *arg
80012FA4  mov  $2,$8             ; $2 = указатель на контекст
80012FA6  bsrv 0x800618b0        ; $lp = 0x80012FAA
80012FAA  lw   $12,128($sp)      ; продолжение после возврата
```

| регистр | роль |
|---|---|
| `$1` | **параметр 1** — значение/адрес, читается вызывающим из своего аргумента |
| `$2` | **параметр 2** — указатель на контекст (используется как `$2+0x6C`, `$2+0x0C`, `$2+0x58`, `$2+0x54`, `$2+0x70`) |
| `$lp` | адрес возврата; процедура уходит через `jmp $1` |
| кадр | `0x70` байт; сохраняются `$c6`, `$1`, `$5`, `$6`, `$7`, `$8`, `$tp` |

Вызывается через `bsrv` — то есть **уже из VLIW-кода** (16 мест) и как минимум
из одного места обычным `bsrv` из core-кода.

## 4. Вызываемые подпрограммы

| адрес | тип | что делает (по листингу) |
|---|---|---|
| `0x80012760` | **VLIW** | выравнивание диапазона: `mov $11,-64`, `and`, `+63`, `+255`, `(addr+size+63)&~63` → `jmp 0x8067cc` (вероятно cache/DMA-операция) |
| `0x80012698` | **VLIW** | тот же шаблон `(addr+size+63)&~63`, затем `bsr 0x800067d4` + `syncm` — сброс/синхронизация буфера |
| `0x80006AB4`, `0x80006AB8` | **VLIW** | короткие служебные (см. `docs/VNZIMG_MEP.md` §7 — семейство утилит 0x800066xx) |
| `0x800622E0` | core `bsr` | та самая функция из `docs/VNZIMG_VLIW_0x800622E0.md` (её листинг там сдвинут на 0x100; корректный адрес начала — `0x800621F0`) |
| `0x800623A0` | core `bsr` | `sra $2,0x5` (деление размера на 32) — блочная операция |

## 5. Псевдокод на C

```c
// Venezia MeP routine at 0x800618B0.
//
//   $1 -> arg   (значение/адрес)
//   $2 -> ctx   (указатель на контекст)
//   возврат через jmp $1; кадр 0x70, сохраняется $c6
//
// Смещения контекста взяты из листинга; имена полей неизвестны.

struct VeneziaCtx;            // ctx[0x6C] -> inner, ctx[0x54] = step, ctx[0x28], ...

extern "C" void venezia_vliw_align(uint32_t addr, uint32_t size);     // 0x80012760
extern "C" void venezia_vliw_sync(uint32_t addr, uint32_t size);      // 0x80012698
extern "C" void  venezia_vliw_util_a(uint32_t v);                     // 0x80006AB4
extern "C" void  venezia_vliw_util_b(uint32_t v);                     // 0x80006AB8
extern "C" void  venezia_core_blocks(uint32_t size32);                // 0x800623A0
extern "C" void  venezia_core_memset16(uint32_t arg, uint32_t ptr);   // 0x800622E0

void venezia_0x800618B0(uint32_t arg /* $1 */, uint8_t* ctx /* $2 */)
{
    // ---- пролог / чтение контекста
    uint8_t*  inner = *(uint8_t**)(ctx + 0x6C);
    uint32_t  count = *(uint32_t*)(inner + 0x0C);   // число записей
    uint32_t  val   = *(uint32_t*)(inner + 0x04);
    uint32_t  base  = *(uint32_t*)(inner + 0x58);
    uint32_t  step  = *(uint32_t*)(ctx + 0x54);

    uint32_t  total = count * val;                  // mulu -> $3
    uint32_t  span  = step + base;                  // add3 -> $10

    uint32_t  prod  = (uint32_t)/*lo*/(count * val); // ldc $lo после mulu
    (void)prod;

    if (count == 0)
        goto done;                                   // bnei на 0x80062298

    // ---- цикл 1: обход записей
    uint8_t* entries = (uint8_t*)(*(uint32_t*)(ctx + 0x70) + span);
    for (uint32_t i = 0; i < count; ++i) {
        uint8_t* rec = entries + i * 16;              // sll3 *0x4, +0x10 на запись
        uint32_t field = *(uint32_t*)(rec + 0x08);
        if (field == 0)
            continue;                                 // beqi -> 0x800621A8

        uint32_t flags = *(uint32_t*)(ctx + 0x24);    // arg->[0x24]
        if ((flags & 1) == 0)
            goto next_record;                         // beqi -> 0x800621B0

        venezia_vliw_align(field, 128);               // bsrv 0x80012760

        // ---- цикл 2: по элементам (шаг 4), деление с остатком
        uint32_t j = 0;
        for (;;) {
            uint32_t* table = *(uint32_t**)(rec + 0x08);
            uint32_t  elem  = *(uint32_t*)(table + j);
            venezia_vliw_util_a(elem);                // bsrv 0x80006AB4
            if (/* результат == 0 */ true)
                break;
            j = (j + 1) % *table;                     // divu + ldc $hi (остаток)
        }
    next_record:;
    }

    // ---- цикл 3: блоками по 32 байта
    uint32_t k = *(uint32_t*)(ctx + 0x28);
    for (; /* по k */; ) {
        uint8_t* p = entries + 32 + k * 8;
        uint32_t elem = *(uint32_t*)p;
        venezia_vliw_align(elem, *(uint32_t*)(ctx + 0x28));  // bsrv 0x80012760
        venezia_core_blocks(elem >> 5);                      // bsr 0x800623A0 (sra $2,5)
        venezia_vliw_sync(elem, *(uint32_t*)(ctx + 0x28));   // bsrv 0x80012698
        /* ... ещё ветки с bsrv 0x80006AB8 / 0x80012760 / 0x80012698 ... */
    }

    venezia_core_memset16(arg, *(uint32_t*)(ctx + 0x28));    // bsr 0x800622E0

done:
    // ---- эпилог (в конце процедуры)
    //   lmcp $c6,80($sp)   -> восстановить $c6
    //   lw $tp/$8/$7/$6/$5/$0 из кадра, add3 $sp,+0x70, jmp $1
}
```

## 6. Про IVC2-слоты: честный статус

* Формат пакета (ядро + паддинг/слоты) **подтверждён** (100 % ядровых
  инструкций декодируются на реальных чанках).
* В **этой** процедуре все слоты пустые: она скалярная, просто упакована по
  одному действию в 64-битный пакет.
* Прогон по всему образу: из 126 398 восьмибайтовых чанков **102 181**
  (81 %) имеют ненулевые байты слотов. Но декодирование этих слотов таблицей
  IVC2 даёт ~94 % `*unknown*`, а из «распознанных» почти все — совпадения на
  данных (`cpfmulia1u.b $cr0,$cr0,0,0` и т.п. с нулевыми операндами). Причина
  известна: таблица IVC2 собрана из `mep-ivc2.cpu` без полного набора полей
  MeP-Integrator, часть кодировок совпадает (527 пар mask/value на 688 форм),
  см. `docs/VNZIMG.md` §5.3.
* Вывод: **использование IVC2 в этом образе не подтверждено декодером**. Чтобы
  его подтвердить, нужно либо достроить таблицу (полный набор полей), либо
  снять трассу выполнения Venezia и посмотреть, какие слова реально попадают в
  слоты.
