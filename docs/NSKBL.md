# NSKBL — небезопасный загрузчик ядра (прошивка 1.04)

NSKBL — небезопасная (Non-Secure) ступень загрузки. Сжатый ARZL-поток лежит в `kernel_boot_loader.self`
(5-й сегмент), SKBL распаковывает его по `0x50000000` в `0x51000000` и передаёт управление с
`SCR.NS = 1`; NSKBL работает с выключенной MMU (после `0x51000138` `SCTLR = 0`), проходит pre-init до
чекпойнта `0xA9` и первым внешним действием грузит `os0:psp2bootconfig.skprx`. Ниже — только
подтверждённые трассой/трапом/дампом/дизассемблером/прогоном/покрытием данные раундов 155–368
(сводка прежнего журнала на 538 КБ).
Документация: `docs/BOOT.md` (цепочка), `docs/STATUS.md` (состояние), `docs/KBL.md` (ARM-загрузчик),
`docs/SYSCON.md` (Ernie).

## 1. Образ и распаковка

Сегменты `kernel_boot_loader.self` (355 220 байт, eMMC SLB2): #0 paddr 0, `0xD4` (PT_NULL/метаданные,
`SecureBool UNUSED`); #1 paddr 0, `0xC0` (векторы ARM `ldr pc,[pc,#0x18]` ×8 + указатели);
#2 paddr `0x40020000`, `0x3BFE0` (SKBL, Thumb-2 + ARM); #3 paddr `0x4005C000`, `0xF0` (`.data`,
memsz `0x5706C`); #4 paddr **`0x50000000`**, **`0x194CF`** (ARZL-поток NSKBL).

* Сегмент 4 начинается `41 52 5A 4C` («ARZL»); в потоке big-endian `LZRA`, флаги `0x16`,
  `ctrl = C8 F8 F2 73`; ARM-фильтр по маске `0xF800F800`; LZ-копии: минимум 2, максимум `0xFF`,
  длина `0x100` = конец потока (оракул `pup_fiction/unarzl/unarzl.c`). Второй ARZL-поток в `.text`
  SKBL — paddr `0x4003DF14`, 123 084 байта: TrustZone-ядро (`SceSysmemForTZS`, `SceDipswForTZS`,
  `SceUartForTZS`; нет `Kernel Boot Loader`/`psp2bootconfig`).
* Декодер и фильтр — в SKBL: `sceArlzDecode` = **`0x4003C330`**
  (`int (void *dst, unsigned dst_max, const void *src, void **dst_end)`), `sceArlzArmFilter` =
  **`0x4003CB40`** (`int (void *data, unsigned size, unsigned version)`). Вызов: `0x40020586 r3=0` →
  `0x40020588 r1=0x1000000` → `0x4002058A r2=[pc,#320]` (= `0x50000004`) → `0x4002058C
  r0=0x51000000` → `0x4002058E blx 0x4003C330` → `0x4002059E blx 0x4003CB40` →
  `0x400205B4 r0=0x89` (чекпойнт «loading NSKBL») → `0x400205B6 bl <GPO>` → `0x400205BA
  r0=0x51000000` → `0x400205BE blx 0x40021AE0`; перед этим `0x40020584 cbnz r0,0x400205AE` по
  MPIDR (распаковывает только ядро 0; прежний §3 давал этот участок со сдвигом +2 байта).
* Результат: `0x2B08C` = 176 268 байт по `0x51000000` (= `unarzl` байт в байт), фильтр возвращает
  `0x2B08A`. Версия фильтра (критерий — доля целей Thumb-BL/BLX внутри `0x51000000..0x5102B08C`):
  без фильтра 3306 вызовов / 69.4 %; **версия 0 — 3306 / 94.4 %**; версия 1 — 3306 / 53.4 %;
  версия 2 — 3306 / 94.4 %, но ломает `movt r3,#0xE20A`; байтовый порт из вики — 656 / 74.2 %.
  Самотест `machine_nskbl_stage_decodes_the_non_secure_loader` (вектор `0x51000000`, указатель
  `0x51000100`, строки `Starting PSP2 Kernel Boot Loader` и `psp2bootconfig.skprx`, 4 ядра).
* Non-Secure: `0x40021AE0 cpsid if,#0x16` (Monitor, SP → `0x400B4B10`); `0x40021AE4 r1=0x93`;
  `0x40021AE8`/`0x40021AEC` — `str` в стек; `0x40021AF0 mrc p15,0,r1,c1,c1,0`; `0x40021AF4 orr
  r1,#1`; `0x40021AF8 mcr` (SCR.NS = 1, лог `SCR = 0x5`); `0x40021AFC rfeia sp!` (`SCTLR =
  0x20005805` при переходе). `smc`: `0x510008E2 blx 0x510002E0`, `0x510002E0 r12=0x103`,
  `0x510002E4 smc #0`, `0x510002E8 bx lr`; всего четыре `smc` (`0xE1600070`): `0x510002E4`
  (**исполнена**), `0x51002BC4`, `0x51002BE0`, `0x510169E4`. Вектор монитора физический
  (`MVBAR = 0x16140`), страница SKBL — `PA 0x40000100` (`VA 0x16100 → PA 0x40000100`). Страница
  монитора: обнуление `PA 0x40000140..0x4000015C` (`0x40037768..0x40037790`, `0x400377EC`), заглушки
  `0xE59FF018` в `+0x148/+0x14C/+0x150/+0x158/+0x15C` (`0x400377F8`, `0x400377FC`, `0x40037804`);
  таблица обработчиков по `PA 0x40000120` = `{0x4002826C, 0x400288C4, 0x40028294, 0x400286C4,
  0x40028460, 0x400282C4, 0x400282DC, 0x40028308}`; обработчик `smc` по `PA 0x40000168` =
  `0x4002831C`. KBL Parm (`PA 0`): заглушка `0x00..0x3F`, `SceKblParam` по `+0x100` (`01 00 00 01`
  = version 1 + size `0x100`), boot-флаги `0xFF00FFFF` по `+0x130`.
* Стадия KBL `0x400204A8` вызывается через ARM-трамплин `0x4003A140` (`mov r13,r2` / `bx r1`) с
  `r0=0x400B2B30 r1=0x400204A9 r2=0x0001A140 r3=0`; адрес собирается `0x400207F8` (`r1=0x04A9`) …
  `0x400207FE` (`movt r1,#0x4002`) … `0x40020806 blx 0x4003A140`.

## 2. Карта чекпойнтов и паник

Писатель GPO — `0x51010F98`. Значение GPO несёт фазу вниз (`0x5E 0x5D … 0x56`) и A-серию NSKBL вверх
(`0xA1 … 0xA9`); трапы `0xE20A0000-0xE20A0010` — 268 записей, все от CMeP.

| код | смысл | сайт (скан) | трасса GPO |
|---|---|---|---|
| `0xA1` | core 0 pre-init complete | `0x510008DC` | `0x510008DE` |
| `0xA2` | interrupts registered | `0x5100094C` | `0x5100094E` |
| `0xA3` | serial console ready | `0x51000C18` | `0x51000C1A` |
| `0xA4` | device buffer initialised | `0x51000C22` | `0x51000C24` |
| `0xA5` | co-processor init, other cores start | `0x510003CA` | `0x510003CC` |
| `0xA6` | MMU enabled, VBAR set up | `0x510004CA` | `0x510004CC` |
| `0xA7` | nothing since `0xA6` | `0x510004FA` | `0x510004FC` |
| `0xA8` | boot setup complete, kernel loading | `0x51000CBC` (дизасм 252 — `0x51000CB8`) | — |
| `0xA9` | kernel pre-init done, before first external load | `0x51000CF6` | — |
| `0xAA..0xAF` | панические | `0x51000C3E…0x51000C92` | `0xAD` — `0x51000C78` |

Дампы панических: `0xAB` — `SPSR`, `0xAC` — `IFSR/DFAR/IFAR`, `0xAD` — `DFSR`; `0xAA/0xAE/0xAF` без
дампа. Аварийный сток: `51000C90 movs r0,#0xAF; bl 0x51010F98; b .`.
Тело стадии `0xA8` (`0x51000CB8`): `push {r4,lr}`; `mov r4,r0`; чекпойнт `0xA8`; `bl 0x51010580`;
`movs r0,#4; bl 0x51000CA4`; `blx 0x51014528`; `cbz r0,0x51000D0E`; `mov r0,r4; bl 0x51018E88`;
`bl 0x51001EAC`; `mov r0,r4; bl 0x51002F4C`; `mov r0,r4; bl 0x51018F20`; `bl 0x51016CC4`;
`bl 0x5101616C`; `movs r0,#0x10; bl 0x51000CA4`; чекпойнт `0xA9`. Прямых `bl` на `0x51000CB8` нет —
стадии вызываются через таблицу. Хвост: `51000CF0 r0=0x10; 51000CF2 bl 0x51000CA4;
51000CF6 r0=0xA9; bl 0x51010F98; 51000CFC r3=0x510014D5; 51000D04 cbz r3,0x51000D0C; 51000D06 r0=r4;
51000D08 bl 0x510014D4; 51000D0C b .`. `0xA9` ставит **каждое** ядро само (трасса: arm3
`pc=0x51000CF6 from pc=0x51000CB4 insns=53386364`, arm1 `insns=53386410`).

## 3. Что NSKBL делает по шагам (подтверждённое)

1. `0x51000000` — вход, `SCTLR = 0x20005805`, MMU off, `sp = 0x51030100` (ядро 0); `0xA1` `0x510008DC`
   (pre-init ядра 0; на стеке возвраты `0x51000537` — адрес после `bl 0x51000FA8` в стадии `0xA7` — и
   `0x51000250`).
2. `0x510002E4` — `smc #0x103`, единственный исполненный secure-вызов; `0x51000138` — `mov r0,#0;
   bic …; mcr p15,0,r0,c1,c0,0` → `SCTLR = 0`.
3. Таблицы: 5 вызовов заполнителя `0x510152A0` — `0x5100085C` (`r0 = 0x40301000`, `[sp] = 0x4000`,
   `[sp+4] = 0x40304000`), `0x51000878` (`0x40308000`), `0x51000894` (`0x4030C000`), `0x510008D2`
   (`0x40310000`), `0x5100E472` (`r0 = 0x2400`, `[sp] = 0x1000`, `[sp+4] = 0x40302000`); для
   `VA 0x000000-0x0FFFFF` реализует `PA = VA + 0x40300000`.
4. `0xA2` `0x5100094C` — прерывания/консоль (`0x51000900…0x5100094E`: `memset` структуры `0x51184E98`,
   обработчики `0xC5`/`0xC4` через `0x51015D18`); `0xA3` `0x51000C18`; `0xA4` `0x51000C22`.
5. `0xA5` `0x510003CA` — co-processor init и старт ядер (`0x51000314` = `wait(0x5102B000, 0)`,
   `0x51000328` = `arrive(0x5102B000)`); `0xA6` `0x510004CA` и `0xA7` `0x510004FA` — MMU включена
   (`TTBR0 = 0x40308000`, `TTBR1 = 0x4030C04A`, построены самим NSKBL), VBAR.
6. `0xA8` `0x51000CB8` — boot setup (`bl 0x51010580`, `0x51000CA4`, `0x51018E88`, `0x51001EAC`,
   `0x51002F4C`, `0x51018F20`, `0x51016CC4`, `0x5101616C`); `0xA9` `0x51000CF6` →
   `0x51000D08 bl 0x510014D4` — первая внешняя загрузка (arm3); терминальный стоп `0x51000D0C`
   (`b .`, Thumb SYS, `CPSR = 0xA000007F`), arm1–arm3 — `wfe` (`0x510147DC`).
7. Куча и классы создаёт сам NSKBL: `map->[0x8C] = 0x5C00` (с подстановками) и `0x60C0` (обычный
   прогон после правки декодера Thumb-2); `SceKernelSysrootClass` (`0x51004F28`) зарегистрирован;
   установщик классов `0x51007E70` исполняется (страницы `0x51008000-0x51009000`: 850/2048 и 434/2048
   слотов). Счётчики слотов по состояниям: 4457 (`PHYSPOOL=1`, `0xAD`), 5432 (`HEAP=1` + второй путь),
   5783 (`HEAP=1`, паника `0x51015B7C`), 6105, 6170.

## 4. Слой хранения: устройства, запросы, очереди (адреса и поля)

**4.1 Тома, кэш, блочное чтение.** `os0` = **`0x51184FF8`** (инициализация хранения `0x51000E7C` →
обёртка `0x51023FD8`, конструктор `0x51023C40`), `sd0` = **`0x51184F9C`** (`0x00100000`, метод
`0x51000D15` = `0x51000D14`); контроллер `0x51021664(dev_id = [0x5102B010], out = &0x5102B014)`;
`[0x5102B014] = 0x51183948`; кэш `0x51033100`. Поля `0x51184FF8`: `+0x18 = 0x00010000`; `+0x1C = 2`;
`+0x20 = 0x00010002`; `+0x24 = 0x13` (FAT 19); `+0x28 = 2`; `+0x2C = 0x414E204F` (`"O NA"` от
`NO NAME`); `+0x30 = 0x0A720290`; `+0x38 = 0x10028` (сектор корневого каталога); `+0x48 = 8`
(секторов/кластер); `+0x50 = 0x200` (длина чтения = `>> 9` = 1 сектор); `+0x54 = 0x51000D55`;
`+0x58 = 0x5102B010`.
`0x51023C40`: `sb = VA 0x51184980`; к `0x51023D4A` структура содержит boot-сектор
`EB FE 90 SCEI … 00 02 08 02 00 02 00 02 00 80 F8 13 00` (копия чтения конструктора: приёмник
`0x51184980`, источник `0x51037310`). Разбор: делитель `0x51025AF4` (`95/32 → 2`); `0x0FF4 = 4084`,
`X > 4084 → 2` (FAT16, `cmp r0,#2` на `0x51023DDE`), иначе 1 (FAT12); `0x51023E74` →
`2*19 + 0x10002 = 0x10028`; `0x51023E82` → `8*(raw-2) + 0x10028 = 0x0A720290`; FAT16-ветка ждёт в BPB
**root cluster** по `+0x2C`, а структура держит там сырой сектор; `0x51023DA2` пишет `[vol+0x50]`.
`0x51000D54` — **кэш-lookup драйвера**: ключ `r1 & ~0x1F`, смещение `r1 & 0x1F`,
LRU `[0x5102B020]`, цикл `0x51000D98` по таблице (сравнение `[entry+4]`/`[entry2+0xC]` с ключом),
попадание отдаёт `cache_line + (offset << 9)` через `blx 0x51011C80` (`memcpy`), промах `0x51000DDC` =
заполнение (`fp = entry<<11; sl = (fp+entry)<<3`, `bl 0x51000D14`); `r2 + (r1 & 0x1F) > 0x20` →
`0x51000E60`; заполнения для ключей `0x00000000`, `0x00010000`, `0x0A720280`. Кэш `0x51033100`: 64
записи по `0x4008` = `{+0 timestamp/state, +4 tag, +8.. 0x4000 данных}`; запись 0 — тег 0 + master
block (`Sony Computer Entertainment Inc.`, version 3, `0x71A000`); запись 1 (`0x51037108`, данные
`0x51037110`) — boot-сектор `os0`; запись 2 (`0x5103B120`) — нули. Диспетчер `0x51000D14`: по `[obj]`
`0` → `0x510205E8`, `1` → `0x51022480`; нулевой handle → `0x80010013`. `0x510205E8` вызывается с
`R0 = 0x240`, `SP = 0x5102BBEC`, `LR = 0x5101F9CB`; `bl 0x5101FE60` из `0x51020626`, `0x5102065C`,
`0x51020668`. Старые подстановки KBL (по умолчанию выключены/`12`): `ZLB_KBL_LOWALIAS` (`12` — только
окно кучи, `0` — выкл., `all` — все три), `ZLB_KBL_PAGENUM`, `ZLB_KBL_INSTANCE_BLOCK`.

**4.2 SDIF, ADMA, eMMC.** Таблица устройств `0x51029FC0`: `0xE0B00000`, `0xE0C00000`, `0xE0C10000`, `0`;
имена `SceSdif0..SceSdif3`, указатели на имена — `0x5102A000`. Записи ARM в SDIF (`ZLB_WTRAP=0xE0B00000-
0xE0B00200`, 801 шт.): `0x08` аргумент (34), `0x0C` transfer mode (34), `0x0E` команда (34), `0x30` (42),
`0x32` (52), `0x34` (2), `0x36` (22), `0x38` normal int **signal** enable (40), `0x3A` (2),
`0x2C/0x2E/0x2F` (76/6/12), `0x28/0x29` (10/3); писатели ARM `0x5101EE2E`, `0x5101EE2A`, `0x5101DB02`,
`0x5101D8F8`, `0x5101D87E`, `0x5101DA9A`, CMeP `0x47960`, `0x4795C`, `0x47912`, `0x47886`. Модель:
`kNormalIntSignalEnable = 0x38`, `kErrorIntSignalEnable = 0x3A` (`sdif.cpp:78-79`); `Irq::Emmc =
32 + 26 = 58` (SPI, нужен `ISENABLER1` по `0x1E001104`). 26 команд ARM (`ZLB_SDIF_TRACE=1`): `CMD0`,
`CMD8(0xAA) ×5 timeout`, `CMD5(0) ×4 timeout`, `CMD55 ×5`, `CMD1(0x40000080)`, `CMD2`,
`CMD3(0x00010000)`, `CMD9(0x00010000)`, `CMD7(0x00010000)`, `CMD6(0x03AF0100)`, `CMD8(arg=0, data=1 —
SEND_EXT_CSD)`, `CMD16(0x200)`, `CMD23(0x20 = 32 блока)`, затем `CMD18` (READ_MULTIPLE_BLOCK) и
`CMD13`; `[dev+0x2410]` (`VA 0x5117EF10`) = **1** — «identified» (`0x5102074A`) проходит. Обёртки
гостя: `0x51022D84` (CMD8: `and r2,r3,#0xff`, `cmp r2,#0xaa` → `0x80320160`; `ands r4,r4,r3,lsr #8` →
`0x80320161`); `0x51022DE4` (CMD5, повтор пока ответ < 0), `0x51023012`, ошибка ведёт на `0x51022ED8`.
Три ADMA-таблицы ARM `0x5117D480`, `0x5117D900`, `0x5117DD80` — `moved=16384/16384 ok=1`, соответствуют
`CMD18 arg=0`, `0x10000`, `0x10020` = LBA 0, 65536, 65568; 22 ADMA-прохода, четвёртого `CMD18` нет.
Submit: `0x51022664` (writer команд, `R4 = 0xE0B00000`, `R5 = 0x5117D400`); `51022608 ldr r4,[r0,#0x78]`
(устройство запроса, сохраняет `0x5101D67A`) → `add.w r3,r4,#0x2400` (= `VA 0x2640`) →
`ldr r4,[r3,#0x30]` (`+0x2430` = `VA 0x2670`) → `0xE0B00000`; submit-рутина драйвера `0x51022604` пишет
`str r1,[r4,#0x58]`, `str r3,[r4,#8]`, `strh r0,[r4,#0xc]` и возвращает 0. Чтение `0x510205E8..
0x51020676` (адреса `0x51020610`, `0x51020614`, `0x51020618`, `0x51020626`, `0x51020646`, `0x5102065C`,
`0x51020668`): `len == 0` → `0x8032000E`; чанк = `min(0x1000 - (r1 & 0xFFF), r6, 0x1000)`; каждый чанк
идёт через `0x5101FE60`. Примитив `0x5101FE60` (`0x5101FE66`, `0x5101FE74`, `0x5101FE7E`, `0x5101FE8E`,
`0x5101FE96`, `0x5101FE98`): `r5 = [r0]` (подадрес устройства); `0x5101E78C` — **заглушка**
`movs r0,#0; bx lr`; `0x5101FA5C` — walk (возвращает 0); `0x5101F9BC` — pop списка завершений; пусто →
`0x510205D4`.

**4.3 Устройство `VA 0x240`, запросы, отправка.** Ожидаемые поля устройства: `+0x2430` (`VA 0x2670`) =
`0xE0B00000`; `+0x2440` (`VA 0x2680`) — значение, копируемое в запросы (`+0x70`); `+0x2480 + 0x20`
(`VA 0x26E0`) — указатель на таблицу диспетчеризации; `+0x2400` (`VA 0x2640`) — список завершений;
`#0x2440` в образе один раз (`0x5101D668`), `#0x2480` — 26 раз (`0x5101DAB6`, `0x5101DB8A`,
`0x5101DFC2`, `0x5101DFCE`, `0x51022502`, `0x5102311A`, …); `0x240` строится в `0x51006B80` и
`0x5100A240` как `0x0B100240`/`0x0B100260`. Отправка `0x5101F6BC` → `0x5101EE98` → `0x5101D660` с
callback `0x5101D65D`; аргументы `R0 = 0x00000240` (устройство), `R1 = 0x5117E180`, `R2 = 0`, `R3 = 3`,
`LR = 0x5101FDE3`. `0x5101D660` (`0x5101D668`, `0x5101D670`, `0x5101D69A`, `0x5101D6A0`, `0x5101D6A2`,
`0x5101D6A4`, `0x5101D6A8`): `r1 = [device+0x24A0]` → `r3 = [r1]` → `blx r3`; оба косвенных вызова
гейтятся `tst.w r1,#0x400` по `[request+4]` (`0x5101D674`, `0x5101D6B6`). Рабочий узел `0x5117D400`:
`+0x00 = 0x240`, `+0x04 = 0x00000514` (бит `0x400` **установлен**), `+0x08 = 0x12`, `+0x0C = 0`,
`+0x10 = 0`, `+0x20 = 0x51033108`. Контрольный `0x5117CB00`: `+0x00 = 0x240`, `+0x04 = 0x80000042`
(бит снят), `+0x08 = 0x01`, `+0x0C = 0x40000080`, `+0x10 = 0xC0FF8000`, `+0x20 = 0`, `+0x60 = 0x5117CD40`,
`+0x6C = 0x5101D65D`, `+0x78 = 0x5117CB00`. Второй объект `0x51183948` **инициализирован**: слоты от

**4.6 GIC, прерывания, замки.** `map 0x1E001000 → arm device=Kermit.GIC`; трап `0x1E000000-0x1E004000`

## 5. Исправленные баги ядра ARM и модели

Баг → симптом (→ где).

1. `ldmia sp!,{…,pc}` без write-back → после `0x4003C330` `SP` не восстанавливался на 36 байт, `pop
   {r4-r7,pc}` (`0x40021C4A`) брал 0 → `pc = 0` (`arm_core.cpp`, `execute_arm_block_transfer`; тест
   `arm_ldm_with_pc_in_list_still_writes_back`).
2. `decode_arm_rfe_srs` читал слова RFE наоборот → `rfeia sp!` (`0x40021AFC`) клал в CPSR `0x51000000`,
   прыжок на `0x93`, ядра в мусоре (`arm0 = 0x31C`, `arm1 = 0x34`, `arm2 = 0x3EE4`; тест
   `arm_rfe_restores_cpsr_and_pc`).
3. Thumb-2: `1111 1010` уходило в `parallel_add_sub32` → на `0x5100C150` `uadd8` вместо `clz`, класс
   19 вместо 4 → `0x80020005`, sysroot не регистрировался, кучи не было (`thumb32_data_processing_register`
   переписан: CLZ/RBIT/REV*/SEL/QADD/SXT*/UADD*/SH*, ~200 инструкций; Unicorn 2.1.4, 1408 векторов;
   `docs/CPU_ARM_AUDIT.md` T32-1).
4. `SEL` брал байты из `Rm` при GE = 1 → идиомы `usub8`/`sadd8` + `sel` зеркальны; `UADD8` ставил GE по
   знаку, а не по переносу (ARM ARM A8.8.157).
5. MMU: XN малой страницы читался из бита 15 → ядро вечно на своём векторе (`IFSR = 0xF`,
   `IFAR = 0x4010C`), хотя `vpa 0x4010C` давал `0x4011847E` (`CPU_ARM_AUDIT.md` MMU-1).
6. Монитор эксклюзива: `clear_exclusive` с PA, `mark`/`take_exclusive` с VA → счётчик `PA 0x40304038`
   терял декременты, `strexh` всегда «удавался», `0xA9` недостижим; `ArmCore::exclusive_phys(va)` и все
   восемь мест `ldrex*`/`strex*` (`0xA7 → 0xA9`).
7. `Kermit.GIC` занимал окно DRAM `0x40000000` → записи SKBL в `PA 0x40000140` уходили в GIC, DRAM
   нулевая, `smc` шёл на нули (`kermit::kScuBase = 0x1E000000`).
8. `wfe` блокирующий, будит только `sev` → кластер засыпал на `0x4003A01C`; сторож в `Vita::run_slice`.
9. `supply_kbl_partition_block` обнулял страницы → `[block] << 12` давало `PA 0` и накладывало три окна
   на класс-дескрипторы (стена `0x40033FF2`; `ZLB_KBL_LOWALIAS`).
10. Тождественное низкое окно отдавало зеркало скретча CMeP (`PA 0`) → `VA 0x10, 0x38, 0x10B0, 0x19FF8,
    0x1A12C` давали мусор-указатели (`DFAR 0x656C7398`, `0xF8D1B178`); при `VA < 0x10000` берётся
    `PA = VA + 0x40300000` (кроме `VA 0 → PA 0`).
11. Thumb-2 VFP load/store: размер брался как `(instr & 0x100) != 0` → `vstr d16,[r0]` (`0x5101FEA4`)
    писал 32 бита, `[request+0x04] = 0`, `CMD18` не выдавалась, открытие → `0x803FF007`
    (`thumb32_coprocessor`: single = cpnum == 10).
12. Thumb-2 `LDRH (immediate)` округлял невыровненный адрес вниз → `ldrh.w r7,[r6,#0xb]` (`0x51023D9A`)
    давал `0x20` вместо `0x200` → `[vol+0x50] = 0x20`, пустой lookup; коммит `1777447`:
    `mem_read_half`/`mem_write_half` побайтово на нечётном адресе (11 мест).
13. SDIF `case 8` всегда = MMC `SEND_EXT_CSD` → на SD `CMD8` — `SEND_IF_COND` без данных; гость
    `0x51022D84` возвращал `0x80320160`/`0x80320161` (ветвление по наличию данных).
14. SDIF `case 5` вечно отвечал `0x00000900` → `0x51022DE4` крутился, `[dev+0x2410] = 3`, открытие
    `0x80320017`; теперь command timeout (карта — eMMC, не SDIO).
15. `ERROR_INT_STATUS` (`0x32`) невидим (чтение шло словом `0x30`) → `0x5101EDE8` читал `0x0000`;
    статус перенесён в `Sdif::error_status_` и вливается в слово `0x30`.
16. Самоочищался только бит 0 SDHCI software-reset → гость (`0x5101ED04`/`0x5101ED0A`) вставал
    навсегда; самоочищаются все три бита.
17. R1b (CMD6 = `0x61B`) не давал второго normal-interrupt → маппер `0x5101EBE4` выходил рано;
    `transfer_complete_in_ = 8` → слово статуса `0x0000002B` → `0x8000002B`.
18. ADMA: сначала `dma_bus_for(address, 8)` → `0x00033140` уходил в boot-окно, таблицы разделов
    нулевые, `0x803FF007` по `0x51023CF4`; ниже `0x01000000` — оконное (`0x00033140 → 0x51033140`).
19. Не было `Sdif::dma_translate()` → `no bus for table 0x0017D480`, `page translation fault (fsr 0x7)`;
    адрес как есть, иначе тот же offset в окне NSKBL; после — `moved=16384/16384 ok=1`.
20. `Kermit::raise` не обновлял линию CPU (`refresh_line` после `set_level`); GIC не привязан к CPU
    (`kermit_set_cpu` без вызывающих → `id=58 (cpu=null)`; `Vita` вызывает `kermit_set_cpu`).
21. Окна Ernie SC перекрывали SDIF0 (`0xE0B00000`, «smallest matching window wins») → `0x5101E970`
    читала 0, `0x80320013`; `Ernie.ScCmd`/`ScReply` больше не зеркалятся на шину ARM.
22. `ScMessageWindow` сбрасывал бит «ответ готов» после любой записи → `pc 0x5101D7C6` — 0 попаданий;
    сброс только при записи в порты данных (`offset <= 0x33 && offset+size > 0x30`) → 3 попадания.
23. `ZLB_NSKBL_SECTION_KEEP`: тип малой страницы проверялся как `(l2 & 3) == 2`, а запись NSKBL
    `0x4030245F` = `(l2 & 3) == 3` → перенос мёртв; правильная проверка `(l2 & 2) != 0`.
24. `ZLB_NSKBL_PHYSPOOL`: страницы пула и слова номеров в одном мегабайте → после 128 страниц пул
    затирал свои дескрипторы; слова вынесены в `VA 0x01F00000`/`0x01F80000`, пул ≤ 2560 страниц.
25. Низкое окно `VA 0x30000`: правка L2 из первой точки шла по устаревшей таблице (`L2 0x40101000`
    вместо `L1 → L2 0x40301000`); триггер перенесён в конструктор `0x5100B41C`.

## 7. Текущая стена: чекпойнт 0xA9

**Состояние.** `GPO raw=0x00A90000`, **checkpoint `0xA9`** («kernel pre-init done, before first external
load»), пройдены `0xA1`–`0xA6`. Финал: `arm0 pc=0x51000D0C` (самопереход, Thumb SYS, mmu=on,
`CPSR = 0xA000007F`), `arm1`–`arm3` `pc=0x510147DC` HALTED (`bx lr` после `wfe` `0x510147D8`,
`lr = 0x51015893`); `[lock+4] = 4`, `[lock+6] = 0` (owner = CPU 0). Счётчики: `runm 400000` →
`r0 = 0x80320011`; `runm 2000000` → **767 606 285** инструкций, **22 чтения eMMC**, тот же чекпойнт;
с `ZLB_NSKBL_DEV=1` длинный прогон **бит-в-бит идентичен**. Прежние опорные значения: `153 205 277`
(после правки SC), `153 203 131`, `153 158 543`, `99 565 288`, `114.7 млн` после фикса декодера.

**Что не читается.** **Данные файла `os0:kd/psp2bootconfig.skprx` не читаются ни разу**: после
`lba=65568 count=32` трафик прекращается. 22 чтения: загрузочная цепочка (LBA 512, 704, 612, 614, 615,
0, 24576, 25071 дважды, 25072 count=7), затем `lba=0 count=32`, `lba=65536 count=32` (boot-сектор
активного `os0_1` по `0x02000000`), `lba=65568 count=32` (32-секторная кэш-линия корневого каталога);
короткий прогон 400 000 слайсов стоит **до** этих заполнений. Четвёртый запрос чтения не доходит до
карты: `0x510205E8` входит **четыре** раза, завершаются **три** передачи (LBA 0, 65536, 65568);
контроллер простаивает (`+0x24 = 0x30000` idle), четвёртого `CMD18` нет, ARM выдал 34 команды; три
ADMA-передачи ARM — `moved=16384/16384 ok=1`. Работает: сборка пути; префикс `os0:` (`0x51001548`);
открытие `0x510240C0`; lookup `0x510232EC` доходит до LFN (`seq 0x42 'g.skp'`, `seq 0x01 'psp2b'`,
`PSP2BO~1SKP`), выход «не найдено» `0x51023966` не срабатывает; чтение тома; `[dev+0x2410] = 1`.

**Точная цепочка отказа.** `0x510014D4` (единственный вызывающий — `0x51000D06`/`0x51000D08`,
исполняется на **arm3**) → `bl 0x51001104` → `0x80320011`:

```
0x5101FE60 (ожидание) → 0x5101E78C (заглушка movs r0,#0; bx lr) → walk 0x5101FA5C возвращает 0
  (гейт: VA 0x20 и [0x5117CDB8] — младшие байты указателей 0x51000100/0x5117CB00, т.е. 0;
   5101FDAA beq 0x5101FDF6 → возврат)
→ 0x5101FE8E bl 0x5101F9BC (pop списка VA 0x2640) → пусто
→ 5101FE98 beq.w 0x510205D4 (единственная ветвь входа во всём образе)
→ 510205D6 movs r7,#0x11 + movt r7,#0x8032 = 0x80320011
→ 0x51000E40 (blt кэш-заполнения) → загрузчик возвращает 0x80320011 → 0x51000D0C.
(В прежней записи этого места стоял ещё `mount 0x510012F4`; покрытие ARM его **не
подтверждает** — `0x510012F4` в прогоне не исполнялся, исполнялся `0x510014D4`.)
```

`bp arm 0x51001540` (arm0, `insns = 53767801`): `R0 = 0x80320011`, `R4 = 0x510B3204`,
`R5 = R6 = 0x51184C00`, `R7 = R8 = 0x00004000`, `R14 = 0x51001677`. На ошибке (`bp 0x510205D6`):
`R0 = 0x240`, `R4 = 0x5117CB00`, `R5 = 0x240`, `R8 = 0x20`, `R9 = 0x11C60`, `R11 = 0x5103F120`,
`SP = 0x5102BBEC`, `LR = 0x5101F9CB`; `step 6` → `R7 = 0x80320011`, `PC = 0x5101FF6A`, ещё `step 6` →
`R0 = 0x80320011`, `PC = 0x51000E40`. `0x80320011` нет ни в образе NSKBL (нет байтов `11 00 32 80`),
ни в KBL (`save 0x40020000 0x60000`); внутри NSKBL его собирают ровно четыре места, и **ни одно не
исполняется**: `0x5101FDFE`/`0x5101FE00` (printf `0x5102A180` = `0x%x %d -> %d`),
`0x510205D6`/`0x510205DC`, `0x5102252E`/`0x51022530`, `0x51022544`/`0x51022546`.

**Почему очередь пуста: устройство `VA 0x240`.** Оно никем не заполняется: `ZLB_WTRAP` по
`PA 0x40300240-0x40300300` — **0** записей; по `PA 0x40301600-0x40301700` — 65 записей, **все
нулевые** (инициализация блокировок `0x51015036`/`0x5101503A`). Поэтому `[device+0x24A0] = 0` и
`0x5101D6A4 blx 0` → отправка отрицательная → `blt 0x5101FE26`. Ожидаемые поля: `+0x2430` =
`0xE0B00000`, `+0x2440`, `+0x2480 + 0x20` (таблица диспетчеризации, первая запись — submit-рутина),
`+0x2400` — список завершений. Рабочий запрос `0x5117D400` несёт `+0x04 = 0x00000514` (бит `0x400`
установлен), контрольный `0x5117CB00` — `0x80000042` (бит снят); оба косвенных вызова в `0x5101D660`
гейтятся `tst.w r1,#0x400`. Ожидание 1 (объект `0x51183948`, устройство `0x5117CB00`, список
`0x5117EF00`) успешно, ожидание 2 (объект `0x5117CB00`, устройство `0x240`, список `0x2640`) пусто →
`0x510205D4` → `0x80320011`. Пул драйвера `0x5117EF00`: 1 build + 10 pop'ов, ни одного возврата
(≈11 узлов); производителя завершений в модели нет (в исходниках — только семафор bignum CMeP,
mailbox-каналы дескрипторов и защёлка завершения таймера MeP). Второй объект `0x51183948` гостем
**инициализирован** (слоты от `0x51183BB8`, шаг `0x28`: `1..7`, `0xE3400000`, `0x71A000 = SEC_COUNT`,
`0x71C000`; `0x51020EDC-0x510210EA`), структурно нулевой — только `0x5117CB00`.

**Раскладка запроса (измерено по писателю команд SDIF `0x51022640`).** Писатель берёт запрос в `r5`:

| Поле запроса | Куда идёт | Что это |
|---|---|---|
| `+0x04` | — | флаги; бит `0x400` — «диспетчеризуемый» (гейт `tst.w r1,#0x400` в `0x5101D660`/`0x5101D674`/`0x5101D6B6`) |
| `+0x08` (u16) | `strh → SDIF+0x0E` | индекс команды: `0x12` = CMD18 (read multiple block) |
| `+0x0C` | `str → SDIF+0x08` | **аргумент SDIF** (байтовое смещение; драйвер сам умножает номер блока на 512) |
| `+0x7C` | `str → SDIF+0x58` | адрес таблицы ADMA2 |
| — | `strh → SDIF+0x04`/`+0x06` | блок-размер и счётчик приходят в `r0`/`r1` на входе писателя |

Сверка по дампам: рабочий запрос `0x5117D400` (`+0x04 = 0x80000514`, `+0x08 = 0x12`, `+0x20 =
0x51033108`) — это запрос CMD18; контрольный `0x5117CB00` (`+0x04 = 0x80000042`, `+0x08 = 0x01`,
`+0x0C = 0x40000080`, `+0x10 = 0xC0FF8000`, `+0x7C = 0`) запросом данных не является: индекс команды 1,
на месте смещения — флаг, таблицы ADMA нет.

**Попытка раунда 371: заполнить пул узлов (`ZLB_NSKBL_DEV=1`).** `0x5101FA10`/`0x5101FA24` — это
push/pop списка по `[device+0x2400]` (голова и хвост в `+0x2400`/`+0x2404`, связь узлов через `+0x60`),
то есть список — **пул**: обход берёт из него узлы под запросы, ожидание — под обработку; узел занимает
`0x1C0` байт (ожидание читает `[node+0x1B0]` и `[node+0x1B8]`). Подстановка с **одним** узлом была
бит-в-бит нейтральна (см. выше), с **восемью** узлами картина меняется, и это регресс:

```
checkpoint 0xA4 (а не 0xA9), 157 440 582 инструкции (а не 268 406 285),
все четыре ядра в спин-замке 0x510147DC, чтений карты по-прежнему 22 (новых нет);
трасса SDIF: CMD arg=0x0238C000 count=32 dma=1 → raise CmdComplete ok=1,
             но передача на карту не идёт (у запроса нет таблицы ADMA)
```

Вывод: узлов в пуле недостаточно — нужен **реальный производитель завершений** (завершённая
передача, которую драйвер затем вернёт в пул), иначе драйвер уходит в ожидание и держит замок.
Подстановка оставлена в исходном (одноузловом) виде.

**Раунд 377: объекта устройства нет ни в одном из дампов — статическая и динамическая проверка.**
Инструмент `tools/arm_xref.py` (capstone-обход образа по ветвлениям + линейные сканы; capstone 5.0.7,
unicorn и keystone в этом окружении **есть**, так что измерения воспроизводимы):

* **в образе NSKBL нет ни одной инструкции, материализующей базу SDIF**: линейный скан обоих режимов
  по всему файлу (176 268 байт) не находит ни `0xE0B0`, ни `0xE0C0` как непосредственное значение —
  то есть код, который мог бы положить `0xE0B00000` в поле `+0x2430` объекта, в NSKBL отсутствует;
* **таблица устройств `0x51029FC0` — только данные**: слова `0xE0B00000`/`0xE0C00000` там есть
  (`0x51029FC0`/`0x51029FC4`), но ни одного указателя на саму таблицу (`0x51029FC0`/`0x5102A000`) в
  образе нет, и поиск PC-относительных обращений в диапазон таблицы находит только сами элементы
  таблицы, а не код;
* **читает таблицу KBL, а не NSKBL**: трап `ZLB_RTRAP=0x51029FC0-0x5102A100` показывает байтовые
  чтения из неё на `pc=0x4003CA60`/`0x4003CA74` (**secure**-ступень, `arm_priv +0x11029FC0`, значения
  `0x00`/`0xE0` — первые байты `0xE0B00000`), при нуле записей по `PA 0x40300240`.

**Следствие.** Объект, который опрашивает драйвер NSKBL, не может быть создан ни одной из имеющихся
ступеней: в дампах нет его конструктора. Значит закрыть стену «включением существующего кода» нельзя,
и остаётся только **модель устройства** — функциональная подстановка, отвечающая на запросы драйвера;
писать её надо от наблюдаемых запросов (поля сняты в раундах 371-373), а не от спецификации, которой
в рабочей папке нет.

**Попытка раунда 372: дать узлам настоящую ADMA-таблицу.** Дизассемблирование точки
диспетчеризации `0x51022604` (её и подаёт подстановка) показывает, какие поля запроса она читает:
`[request+0x78]` — устройство, `[device+0x2430]` — база SDIF, `[request+0x04]` — флаги,
`[request+0x24]`/`[request+0x26]` (u16) — блок-размер и счётчик, `[request+0x08]` — код команды,
`[request+0x0C]` — аргумент, `[request+0x7C]` — таблица ADMA2. Узлам прописали таблицу
(`0x510FF000`: один дескриптор `attr=0x23`, `len=0x4000` → буфер `0x51100000`) и буфер. Результат:
писатель **действительно** программирует SDIF нашими значениями (`+0x58 = 0x510FF000`,
`+0x04 = 0x1`, `+0x06 = 0x20`, аргумент `0x0238C000`), но код команды выходит `0x3625` (индекс
`0x36`), и модель выполняет её как command-only: обхода ADMA нет, карта не читается, завершения нет.
Причина: **ожидание перезаписывает узел перед отправкой** (`vstr d16 → +0`/`+4`, затем `+8 = 12`,
`+0x0C`, `+0x20`, `+0x24`, `+0x26`), а база кода команды приходит не из узла, а от вызывающего
(`r6` = второй аргумент диспетчера, передаваемый `0x5101F6BC`/`0x5101D660`). Значит предзаполненный
узел не может задать команду — разбирать надо именно вывод кода команды в `0x5101D660`.

**Раунд 373: рабочий против падающего вызова писателя (`ZLB_KBL_TRACE_PC=0x51022664`).** Регистры в
момент записи командного регистра SDIF:

| вызов | `lr` | `r1` | `r3` (аргумент) | `r5` (запрос) | `r6` | `r7` |
|---|---|---|---|---|---|---|
| рабочий (чтение тома, 3 шт.) | `0x5101DAE3` | `0x0017D480` / `0x0017D900` / `0x0017DD80` | `0` / `0x10000` / `0x10020` | `0x5117D400` / `0x5117D880` / `0x5117DD00` | **`0x1A`** | `0x5117EF00` |
| падающий (наш узел, 8 узлов + ADMA) | `0x5101D6EB` | `0x510FF000` | `0x0238C000` | `0x00000300` | **`0x51022605`** | `0x00000300` |

`r6` — младший байт командного регистра (тип ответа и проверки), и рабочий путь выбирает его сам:
`0x5101DABC movs r6,#0x1A`, `0x5101DACA movs r6,#9`, `0x5101DAD0 movs r6,#0x1B`, после чего вызывает
писателя напрямую (`lr = 0x5101DAE3`). Падающий путь идёт через **диспетчер устройства**
(`0x5101D6E4 ldr r2,[device+0x24A0]; 0x5101D6E6 ldr r1,[r2]; 0x5101D6E8 blx r1`), то есть в `r1`
передаётся **сам указатель на рутину**: подстановка положила туда таблицу, первый элемент которой —
рутина драйвера `0x51022605`, поэтому `r6 = 0x51022605` и командное слово выходит мусорным.

**Вывод.** Форма подстановки неверна: `[device+0x24A0]` — это **метод устройства**, а не «таблица с
методом», и его значение одновременно служит базой младшего байта команды. Правильный путь для
модели — перехватить сам вызов диспетчера `0x5101D6E8` (штатный механизм `satisfy_arm_boot_pc`) и
выполнить передачу в C++: взять запрос (`r7`), прочитать его поля (`+0x0C` — аргумент SDIF, `+0x7C` —
таблица ADMA2, `+0x24`/`+0x26` — размер и счётчик) и вернуть узел в `[device+0x2400]` завершённым.

**Раунд 374: проверена гипотеза «стена из-за пустого boot-контекста» — опровергнута.** Хук
`Vita::cmep_pc_hook` по умолчанию гасит CMeP на «done»-прыжке secure kernel, поэтому вторая стадия не
доигрывает свою ветку и запись по PA `0x100` остаётся нулевой. С `ZLB_CMEP_HANDOFF_RUN=1` вторая
стадия доигрывает:

```
checkpoint 0xA9 (тот же), arm0 = 0x51000D0C, 473 206 774 инструкции (против 268 406 285 по умолчанию)
MeP-покрытие: впервые исполнены 0x403C0 (сервис), 0x40858 («холодная» ветка), 0x45508 (цикл хранилища);
              0x41B4A (сборщик SceKblParam) и 0x40A86 (memcpy контекста) по-прежнему НЕ исполнены
```

и запись по PA `0x100` действительно появляется — её пишет прошивка, а не модель:

```
00000100  20 01 01 00 00 00 00 00  01 00 00 00 00 00 01 00
00000110  00 10 00 00 00 D0 0F 40  00 00 00 00 9B 9E 51 D2
00000120  00 00 00 00 00 00 00 00  02 00 00 00 00 10 01 00
00000130  00 10 00 00 00 00 00 00  00 00 00 00 9B 9E 51 D2
```

(два блока по 0x20 байт с сигнатурой `0xD2519E9B`, указателем в DRAM `0x400FD000` и полями
`0x00010120`/`0x00010000`/`0x1000`). **Но структура устройства по PA `0x40300240` остаётся нулевой**
(`mem 0x40300240 4` → все нули), и NSKBL стоит на том же `0xA9`. Значит первая внешняя загрузка
упирается не в пустой boot-контекст, а в отсутствующий объект устройства — гипотеза «дадим контекст,
и поедет» снята измерением.

**Раунд 375: ещё две проверки, обе отрицательные.**

1. **Бит `0x400` у управляющего запроса — не блокер.** Подстановка ставила бит `0x400` на самом
   запросе драйвера при входе в ожидание (`0x5117CB00`: `0x80000042 → 0x80000442`, подтверждено
   логом), то есть гейт `tst.w r1,#0x400` в `0x5101D660` проходил. Прогон при этом **бит-в-бит совпал
   с базовым** (268 406 285 инструкций, `0xA9`, 22 чтения): узлы, которые ожидание реально
   отправляет, оно заполняет своим шаблоном само (`+4 = 0x514`, бит уже стоит), поэтому флаг
   запроса на исход не влияет.
2. **Указатель `0x400FD000` из контекста второй стадии ведёт в пустую DRAM.** В записанном контексте
   (раунд 374) поле `+0x14 = 0x400FD000`; по этому адресу — 96 байт нулей, как и по `PA 0x40300240`.
   Контекст ссылается на буфер, который прошивка заполняет позже (или не заполняет на нашем пути);
   объекта устройства там нет.

**Уточнение про `[device+0x24A0]`.** Диспетчер делает `0x5101D6E4 ldr r2,[device+0x24A0];
0x5101D6E6 ldr r1,[r2]; 0x5101D6E8 blx r1`, то есть метод получает **свой же адрес** в `r1`, а рутина
драйвера `0x51022604` трактует `r1` как байт команды (`r6 = r1`) — отсюда `r6 = 0x51022605`. Значит
`0x51022604` **не является** методом устройства: у диспетчера другое соглашение о вызове. Метод
устройства должен делать то, чего у модели нет, поэтому единственный доступный путь — перехватить сам
`blx` (`0x5101D6E8`) в `satisfy_arm_boot_pc` и смоделировать метод в C++: выполнить запрошенную
операцию и вернуть узлы в пул завершёнными.

**Раунд 376: прерывание завершения поднимается, но до ядра не доходит — путь «просто доставить IRQ» закрыт.**

1. **Линия SDIF действительно поднимается.** С восемью узлами `ZLB_SDIF_IRQ_LOG=1` печатает
   `irq assert: normal=0x0001 n_enable=0x01FB` (и `drop` при снятии статуса) — контроллер завершает
   команду и ассертит свою линию; делает он это и в базовом прогоне (чтения тома).
2. **GIC её не пропускает.** С `ZLB_GIC_LOG=1` **ни одной** строки `GIC line ...` не появляется:
   дистрибьютор гостём не включается (0 записей в `0x1E001000+`), поэтому линия SDIF умирает на входе
   GIC, а ядро её не получает.
3. **Форсирование политики CPU-интерфейса (`ZLB_GIC_CPUIF=1`) ломает *предыдущую* ступень, а не
   лечит стену:** прогон останавливается на чекпойнте **`0x8E`** (это уже KBL), `arm0 = 0x400219E8`
   — фатальная заглушка KBL (`0x40021998+`), 268 282 816 инструкций. То есть «включим прерывания» не
   является безобидным исправлением.
4. **Драйвер *расходует* пул, а не ждёт его наполнения.** С восемью узлами к моменту простоя
   (`0xA4`, все ядра в idle-цикле `0x510147DC`): голова и хвост списка `VA 0x2640` — **нули**
   (`vmem 0x2640 2`), узел `0x300` остался с полями, записанными драйвером (`+8 = 0x00030000`,
   `+0x10 = 0x00010000`, `+0x14 = 0xFFFFFFFF`), узлы `0x500`/`0x700` пусты. Значит узлы **изымаются и
   не возвращаются**, и без производителя завершений цепочка дальше не идёт.

**Итог:** ни «дать узлы», ни «доставить прерывание» стену не двигают (первое даёт `0xA4` и простой,
второе ещё и роняет KBL на `0x8E`). Остаётся один путь: смоделировать **метод устройства** —
перехватить `0x5101D6E8` и в C++ выполнить операцию запроса и вернуть узлы в пул завершёнными.

**Подстановка `ZLB_NSKBL_DEV=1`** (по умолчанию выключена): `supply_nskbl_device_object` заполняет
`+0x2430 = 0xE0B00000`, `+0x24A0` → одноэлементную таблицу с submit-рутиной `0x51022605`, кладёт узел
в `+0x2400` и повторяет на каждом входе в `0x5101FE60`. Объект виден (`vmem 0x2670 = 0xE0B00000`,
`vmem 0x2640 = 0x00000300`), подстановка **доставляется** (`bp 0x510205D4` → `R6 = 0x300` против
`R6 = 0`), но результат тот же: первый poll ожидания 2 успешен, **второй пуст** → `0x510205D4` →
`0x80320011` (`0xA9`, 22 чтения). Флаг `0x514` и `+8 = 0x12` узлу — тоже без эффекта. Причина: нужен
производитель готовых запросов в `[device+0x2400]`, которого в модели нет.

**Прочие измерения.** Прерывания не помогают: GIC гостем не программируется (0 записей,
`ICDDCR`/`ICCICR`/`ICCPMR` = 0), non-secure вектор не срабатывает (VBAR гость не пишет); с
`ZLB_GIC_CPUIF=1` линия SDIF доходит, но `CPSR.I = 1` и гость его не снимает. `0xE0B0002F` — SDHCI
`SOFTWARE_RESET` (не «бит окна SC»): `0x5101D784 strb.w r3,[r4,#0x2f]`, опрос `0x5101D788..0x5101D790`;
после правок устройство отдаёт 0 (`Kermit.Sdif0 read 0xE0B0002F size 1 -> 0x0 (word 0x0)`). Цифры:
`zlb_tests` **436/436**, `verify.ps1` **9/9**, образ eMMC — 992 файла, 0 расхождений; SDIF поднимает
линию 188 раз, `ZLB_ARM_IRQ_LOG=1` без подстановки — 0 событий. Диагностика в дереве (все выключены):
`ZLB_EMMC_LOG`, `ZLB_NSKBL_OPEN_EXIT` (+`_PC`), `ZLB_SDIF_TRACE`, `ZLB_SDIF_IRQ_LOG`,
`ZLB_SDIF_CMD8_NORESP`, `ZLB_ARM_IRQ_LOG`, `ZLB_GIC_CPUIF`, `ZLB_GIC_STRICT`, `ZLB_NSKBL_VBAR`,
`ZLB_NSKBL_DEV`, `ZLB_NSKBL_CTX`, `ZLB_NSKBL_BOOTCFG`, `ZLB_ARM_TRACE_RING`, `ZLB_ARM_TRACE_RANGE`,
`ZLB_ARM_TRACE_TRIGGER`, `ZLB_ARM_TRACE_LIMIT`, `ZLB_ARM_BRANCH_LOG`, `ZLB_ARM_COV`, `ZLB_WTRAP`,
`ZLB_RTRAP`, `ZLB_NSKBL_LOWIDENT`. Инструменты: `ZLB_ARM_BRANCH_LOG` **не** сообщает целей переходов в
`0x51020000..0x51030000`, хотя код там исполняется; точки останова сравнивают PC точно
(`debugger.cpp:262`); `insns` — счётчик планировщика (слайс = `budget_.arm` шагов на ядро).

   на передачу есть всё нужное (`+0x08` = индекс команды, `+0x0C` = аргумент SDIF, `+0x7C` = таблица

   пути выбирает младший байт команды сам (`r6 = 0x1A/9/0x1B` в `0x5101DABC/DACA/DAD0`), а на пути

   в команду. Поэтому подстановка не должна класть туда таблицу с рутиной драйвера: правильный шаг —
   перехватить вызов `0x5101D6E8` в `satisfy_arm_boot_pc` и выполнить передачу в C++ (взять запрос из
   `r7`, провести чтение по `+0x0C`/`+0x7C`/`+0x24`/`+0x26` и положить узел в пул завершённым).
